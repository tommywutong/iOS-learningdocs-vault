# 键控归档的向前和向后兼容性

键控归档为你提供了极大的灵活性，使你的类能够实现向前和向后兼容。以下小节先描述一些实现兼容性的通用技巧，然后针对特定类型的变更给出一些维护兼容性的指导原则。

键控编码的主要好处是，它使实现向后和向前兼容变得更加容易。能够按任意顺序从归档中读取键值、忽略不需要的键、以及在不影响类旧版本的前提下添加新键，这些都是使用键控编码实现向后和向前兼容性的基础。

为了获得最大程度的兼容性，你需要能够做到以下几点：

- 读取由你的类的旧版本创建的归档。
- 创建可以被你的类的旧版本读取的归档。
- 读取由你的类的未来版本创建的归档。
- 创建可以被你的类的未来版本读取的归档。

前两点提供了完全的向后兼容性：类的旧版本和当前版本可以互相读取对方的归档。要实现这一点，你必须清楚地知道你需要支持的所有先前版本的类都编码了哪些值，以及先前版本是如何解码自身的。如果你没有这些信息，也许可以从现有的归档以及现有的 `NSCoding` 方法实现中推断出一些内容。

后两点提供了完全的向前兼容性：当前版本和未来版本的类可以互相读取对方的归档。要实现这一点，你需要预见未来可能进行的变更类型，并相应地编写当前的 `NSCoding` 方法。

为了便于识别正在解码的类的版本，你可以在归档中添加一些版本信息。这可以是任何你想要的信息类型，而不一定像非键控编码中那样只能是一个整数（例如类版本）。你可以只用某个键编码一个“版本”整数或字符串，在某些少见的情况下，你可能还想用一个装满各种信息的字典对象。当然，如今添加版本信息的前提是，你在今天的 `initWithCoder:` 中也要有处理不同版本的方案。如果没有，将来更改版本信息也不会对该类的当前版本有任何帮助。

请记得让你的 `NSCoding` 实现保持同步。每当你修改了类的 `encodeWithCoder:` 方法中写出对象状态的方式，就需要更新 `initWithCoder:` 方法，使其能够理解新的键。因为键控归档中的信息可以按任意顺序编码和解码，所以这两个 `NSCoding` 方法不需要按相同的顺序处理键。你可以为每个方法选择最方便的顺序。

一个类编码的某些值，可能有一组特定的可能取值。例如，一个按钮可以是复选框、单选按钮、按压按钮等等。将来，你的取值集合可能会扩展；你可能会创建一个具有另一种行为的按钮，并需要为按钮类型添加一个新值。

为了给未来归档中的这类变更做好准备，你可以测试某个键解码出的值是否属于允许的取值之一。如果不是，你可以为其赋一个默认值。这样，未来版本的类就可以直接将新值赋给旧键，而当前的类仍能表现得相当合理。

如果你正在进行这样的变更，而某个旧版本没有为此变更做出相应处理，或者其处理方式不充分或不可接受，你很可能需要为新状态创建一个全新的键（参见 [Adding New Keys](#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpgiydambrga2tkljzgiytqni)），并将旧键作废（参见 [Removing or Retiring Keys](#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpgiydambrga2tkljzgi4deni)）。

随着类的演进，你可能需要添加信息以描述其新特性。例如，一个按钮具有标签和样式。之后，你可能允许该按钮拥有自定义颜色。此时你需要在归档中创建一个新键来保存颜色数据。

因为你不需要解码键控归档中的每一个值，所以新增的键值对旧版本的类而言是无害的，只要旧版本可以不必用这些状态进行初始化就行。你可以安全地按需添加任意数量的新键，而不会影响旧版本；旧版本会自动忽略这些值。

在解码旧归档时，你必须准备好处理新键缺失的情况。如果合适，你仍然可以尝试解码这个新键，直接接受缺失键的默认值（`nil`、0、`NSZeroPoint` 等等）。不过，编码器的默认值对某些键来说可能并不有效。在这种情况下，你应该检测到默认值，并用一个更合理的默认值来替代它。如果新键是用来替代某个旧键的，那么合适的替代值应该来自旧键，这可能需要将旧值映射到新键允许的取值之一。如果你必须区分“缺失键的默认值”和“已有键恰好也是该默认值”这两种情况，请使用 `NSCoder` 方法 `containsValueForKey:`。

如果新键是要替代一个旧键，你需要妥善处理这个作废的键（参见 [Removing or Retiring Keys](#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpgiydambrga2tkljzgi4deni)）。

随着类的演进，某些信息可能会变得过时，或者被更新的实现所取代。

因为你不需要解码键控归档中的每一个值，所以在解码旧归档时，你可以直接忽略不再需要的键。这样解码速度也会稍快一些。

在解码未来的归档时，你必须准备好处理缺失的键。如果合适，你可以直接接受缺失键的默认解码值（`nil`、0、`NSZeroPoint` 等等）。如果编码器的默认值对某个特定键来说无效，你应该检测到默认值，并用一个更合理的默认值来替代它。如果你必须区分“缺失键的默认值”和“已有键恰好也是该默认值”这两种情况，请使用 `NSCoder` 方法 `containsValueForKey:`。这样一来，你就有了灵活性，可以在以后停止编码某些值。

在某些情况下，你需要放弃一个旧键而采用新键，但旧版本的类无法妥善处理缺失的键。这时你需要同时继续为旧键和新键写入某个值。为旧键写入的值应该是旧类能够理解的内容，并且应尽可能接近对新状态的模拟。例如，考虑这样一个类，它最初只有“香草”、“巧克力”和“黄油山核桃”三种口味，现在新增了“双重巧克力”和“焦糖”两种口味。为旧键编码值时，你可以将“双重巧克力”映射为旧类中的“巧克力”，但可能不得不将“焦糖”映射为“香草”。当然，你要用新键写出完整的新取值集合，并且你的 `initWithCoder:` 方法应优先使用新键（如果存在的话）。

在某些情况下，构建后备处理机制也可能很有用。当某个值可能由一组键中的某一个进行编码时，后备处理机制就很有用。这组受支持的键可能会随时间演变，未来版本的类会更偏好使用较新的键。后备处理机制定义了一个必须永远可读的基础键，但只有在没有其他可识别的键存在时才会使用它。未来版本可以同时用新键和后备键写入一个值。旧版本的类不会看到新键，但仍然可以用后备键读取该值。

以一个名为 Image、用于表示图像的类为例（这个例子未必反映任何实际图像类，例如 `NSImage` 的真实行为）。假设 Image 类能够根据具体实例最方便的方式，将其实例编码为 URL、JPEG 或 GIF。因此，一个已编码的 Image 对象只包含以下键之一：`@"URL"`、`@"JPEG"`、`@"GIF"`。`initWithCoder:` 方法按照 `@"URL"`、`@"JPEG"`、`@"GIF"` 的顺序检查这些键，并使用它找到的第一种表示形式来初始化自身。将来，可能这些方式都不再容易或方便归档（例如，把 Image 实例现有的数据转换为 JPEG 可能开销相当大）。

在这种情况下，后备处理的一个例子，就是允许一个额外的键（或一组键），比如 `@"rawdata"`，当这个值（图像数据）的其他键都不存在时，Image 的 `initWithCoder:` 方法就会理解并使用它。举例来说，`@"rawdata"` 键的值可以定义为一个包含 32 位 RGBA 像素的 `NSData` 对象。也可能存在一些辅助键，比如 `@"pixelshigh"` 和 `@"pixelswide"`，`initWithCoder:` 会查找它们，以获取从归档信息生成一个 Image 实例所需的最基本信息集合。将来，Image 的编码过程可能会写出当时最方便的信息，同时也不得不写出 `@"rawdata"` 等键，以便让旧的解码器仍能读取该对象。

在某些情况下，你可能会在 32 位和 64 位平台上使用相同的代码和归档（例如，你可能有一个应用程序的 iOS 版本和 OS X 版本，它们通过 iCloud 共享数据）。在这种情况下，你需要注意确保整数值被正确处理。

将一个 32 位整数编码为 64 位整数，未必是最好的解决方案。你在把值交给归档器时附加上的额外高位零，都是被浪费掉的。不过，这样做也无害，而且实现起来很简单。

通用的 `encodeInt:forKey:` 和 `decodeIntForKey:` 方法读写的是计算机上原生的 `int` 大小。在 64 位计算机上，`int` 可能是 64 位宽（也可能不是；C 语言在这方面比较灵活）。因此，`encodeInt:forKey:` 方法有可能写入需要超过 32 位才能表示的值。如果这样的归档被传输到 32 位计算机上，`decodeIntForKey:` 方法可能无法在 `int` 返回值中表示该整数，此时不得不抛出 `NSRangeException`。

试图通过始终以 64 位解码此类整数来处理这个问题是否有用，尚存争议。举例来说，如果这个整数是某种事物的“计数”，那么在 32 位计算机上，物理上就不可能出现超过 2^32 个这种事物，因此继续尝试解档该文件可能是在浪费时间，抛出异常是合理的做法。或者，你也可以选择捕获该异常，或者对解码出的 64 位值执行自己的边界检查，并从 `initWithCoder:` 返回 `nil`。不过，调用 `decodeObjectForKey:` 方法来解包你的类实例的调用方，可能并不比遇到异常更乐意接受这个 `nil`，甚至最终可能会抛出它自己的、比范围异常更难说明问题原因的异常。
