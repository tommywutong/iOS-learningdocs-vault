# Bonjour 操作

本章介绍支撑三层网络服务 API 的 Bonjour 操作——服务发布、浏览和解析——以及这些 API 层本身。如果你想编写发布或发现网络服务的应用程序或工具，就应该阅读本章。

Bonjour 中的网络服务架构提供了一套易用的机制，用于发布、发现和使用基于 IP 的服务。Bonjour 支持三种基本操作，每一种都是零配置网络服务不可或缺的组成部分：

- 发布（通告一个服务）
- 发现（浏览可用的服务）
- 解析（把服务实例名转换成可供使用的地址和端口号）

以下各节将详细讨论这些操作。

要发布一个服务，应用程序或设备必须把该服务注册到多播 DNS 响应程序上，可以通过高层 API 完成，也可以直接与响应程序（`mDNSResponder`）通信。Bonjour 还支持使用动态 DNS 更新，把记录存放在传统的 DNS 服务器上。

注册一个服务时，会创建三条相关的 DNS 记录：服务（SRV）记录、指针（PTR）记录和文本（TXT）记录。TXT 记录包含解析或使用该服务所需的附加数据，不过它往往也是空的。

SRV 记录把服务实例名映射到客户端真正使用该服务所需的信息。客户端随后把服务实例名保存下来，作为访问该服务的持久方式，等到要连接时再执行 DNS 查询取得主机名和端口号。多出来的这一层间接性带来两个重要好处。第一，服务是用人类可读的名称来标识的，而不是用域名和端口号。第二，只要服务名保持不变，即使服务的端口号、IP 地址或主机名发生变化，客户端仍然能访问到它。

SRV 记录包含两项用于标识服务的信息：

- 主机名
- 端口号

主机名是当前能找到该服务的域名。这里给出的之所以是主机名而不是单个 IP 地址，是因为它可能是一台拥有多个 IP 地址的多宿主主机，也可能同时拥有 IPv6 和 IPv4 地址，等等。用名称来标识主机可以妥善处理所有这些情况。

端口号标识该服务所用的 UDP 或 TCP 端口。

SRV 记录按以下约定命名：

`<Instance Name>.<Service Type>.<Domain>`

`<Instance Name>` 是服务实例的名称，可以是任何 UTF-8 编码的 Unicode 字符串，其用意是让人能读懂。

`<Service Type>` 是标准的 IP 协议名，前面加一个下划线，后面跟主机到主机的传输协议（TCP 或 UDP），同样前面加一个下划线。例如，跑在 UDP 上的 Trivial FTP 服务的服务类型是 `_tftp._udp`，而跑在 TCP 上的 IPP 打印服务会以 `_ipp._tcp` 服务类型注册。官方协议名列表由 IANA 维护；更多信息请参阅[域名命名约定](Domain%20Naming%20Conventions.md#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpkridimbqgazdinrqfvjvomi)。

`<Domain>` 是标准的 DNS 域。它可以是某个具体的域，例如 `apple.com.`，也可以是通用后缀 `local.`，表示该服务仅在本地链路上可访问。

下面是一个 SRV 记录的例子（采用标准 DNS 记录格式），对应一个名为 `PrintsAlot`、跑在 TCP 端口 `515` 上的打印后台处理程序：

`PrintsAlot._printer._tcp.local. 120 IN SRV 0 0 515 blackhawk.local.`

这条记录会创建在本地链路上一台名为 `blackhawk.local.` 的打印机的多播 DNS 响应程序中。开头的 `120` 表示用于缓存的生存时间（TTL）值。两个零是权重和优先级，在传统 DNS 中用于在多条匹配同一名称的记录之间做选择；对多播 DNS 而言，这两个值会被忽略。

关于域名、服务名和实例名的更多信息，请参阅[域名命名约定](Domain%20Naming%20Conventions.md#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpkridimbqgazdinrqfvjvomi)。

PTR 记录把服务类型映射到该类型服务的一组具体实例名，从而实现服务发现。这条记录又加了一层间接性，使得只需查找以服务类型为标签的 PTR 记录就能找到服务。

这条记录只包含一项信息，即服务实例名（与 SRV 记录的名称相同）。因此，PTR 记录的命名方式与 SRV 记录一样，只是不带实例名：

`<Service Type>.<Domain>`

下面是一个针对名为 `PrintsAlot` 的打印后台处理程序的 PTR 记录示例：

`_printer._tcp.local. 28800 PTR PrintsAlot._printer._tcp.local.`

同样地，`28800` 是生存时间（TTL）值，以秒为单位。

TXT 记录与对应的 SRV 记录同名，可以包含少量关于该服务实例的附加信息，通常最多不超过 100–200 字节。这条记录也可以是空的。例如，网络游戏可以通告多人游戏中正在使用的地图名称，聊天程序可以通告用户的在线状态（例如空闲、离开或在线）。如果你需要传输更大量的数据，主机应当与客户端建立连接并直接发送数据。

从历史上看，这条记录曾用于处理同一 IP 地址、同一端口上运行的多个服务，例如同一台打印服务器上的多个打印队列。在这种情况下，可以用 TXT 记录中的附加信息来标识目标打印队列，如下例所示：

__表 4-1__  用 TXT 记录做多路分解

| 服务名 | 类型 | IP 地址 | 端口 | 队列名（来自 TXT 记录） |
| --- | --- | --- | --- | --- |
| `Paper Printer` | `_ipp._tcp` | `10.0.0.2` | `631` | `rp=lpt1` |
| `Slide Printer` | `_ipp._tcp` | `10.0.0.2` | `631` | `rp=lpt2` |

之所以需要这种做法，是因为历史上服务类型都与知名端口绑定在一起。我们鼓励新 Bonjour 协议的设计者让服务的每个实例跑在各自动态分配的端口号上，而不要试图把它们全都塞进同一个知名端口，再用额外信息来指明客户端想要访问的是哪个实例。

TXT 记录中数据的性质和格式因服务类型而异，因此每种新的服务类型还需要定义其关联 TXT 记录（如果有的话）的数据格式，并把该格式作为协议规范的一部分发布出来。

举一个具体的例子，设想有一台在本地网络上分享音乐的假想设备——一台支持 IP 的点唱机。假设它的传输协议是 TCP，应用协议名叫 `music`。当有人把这台设备插入以太网集线器时，会发生一系列事情，如图 4-1 所示。

第 1 步，设备从 IPv4 链路本地地址段 `169.254.0.0`（子网掩码为 `255.255.0.0`）中随机选取链路本地 IP 地址 `169.254.150.84`，并把它公告到网络上。由于没有设备对这次公告作出响应，该设备就把这个地址据为己有。第 2 步，它启动自己的多播 DNS 响应程序，申请主机名 `eds-musicbox.local.`，确认该名称可用后据为己有。接着第 3 步，设备在 TCP 端口 `1010` 上启动音乐分享服务。最后第 4 步，它在 `local.` 域中以 `Ed’s Party Mix` 为名发布类型为 `_music._tcp` 的服务，发布前先确认没有同名的服务存在。这会创建两条记录：

- 一条名为 `Ed’s Party Mix._music._tcp.local.` 的 SRV 记录，指向 `eds-musicbox.local.` 的 TCP 端口 `1010`
- 一条名为 `_music._tcp.local.` 的 PTR 记录，指向 `Ed’s Party Mix._music._tcp.local.` 服务。

__图 4-1__  发布一个音乐分享服务

!

服务发现利用服务发布期间注册的 DNS 记录，找出某一类服务的所有具名实例。为此，应用程序通常会通过更高层的 API 发起查询，寻找与某个服务类型（例如 `_http._tcp`）匹配的 PTR 记录。运行在各台设备上的多播 DNS 响应程序会返回带有服务实例名的 PTR 记录。

__图 4-2__  发现音乐分享服务

!!

图 4-2 展示了一个客户端应用程序浏览音乐分享服务的过程。第 1 步，客户端应用程序向标准多播地址 `224.0.0.251` 发出查询，寻找 `local.` 域中类型为 `_music._tcp` 的服务。网络上每个多播 DNS 响应程序都会听到这个请求，但只有那台音乐分享设备用一条 PTR 记录作出响应（第 2 步）。返回的 PTR 记录中带有服务实例名，本例中是 `Ed's Party Mix._music._tcp.local.`。客户端应用随后就能从 PTR 记录中取出服务实例名，并把它加入屏幕上的音乐服务器列表。

服务发现通常只是偶尔进行一次——例如用户第一次选择打印机的时候。这个操作保存下来的是服务实例名，它是任一服务实例的稳定标识符。端口号、IP 地址乃至主机名都可能天天变化，但用户不应该因此每次都要重新选一遍打印机。因此，从服务名到套接字信息的解析要等到真正使用该服务时才进行。

要解析一个服务，应用程序会以该服务的名称去查找 SRV 记录。多播 DNS 响应程序会返回包含当前信息的 SRV 记录。

图 4-3 展示了音乐分享示例中的服务解析过程。解析过程始于向多播地址 `224.0.0.251` 发出一次 DNS 查询，请求 `Ed’s Party Mix._music._tcp.local.` 的 SRV 记录（第 1 步）。第 2 步，这次查询返回该服务的主机名和端口号（`eds-musicbox.local.`、`1010`）。第 3 步，客户端发出一个多播请求来获取 IP 地址。第 4 步，该请求解析出 IP 地址 `169.254.150.84`。随后客户端就可以用这个 IP 地址和端口号连接到服务。每次使用该服务时都会走一遍这个流程，从而始终拿到服务最新的地址和端口号。
