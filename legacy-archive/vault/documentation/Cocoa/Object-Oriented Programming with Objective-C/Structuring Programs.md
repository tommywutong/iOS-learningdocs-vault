# 组织程序结构

面向对象程序有两种结构。一种体现在类定义的继承层级中。另一种则体现在程序运行时消息传递的模式里。这些消息揭示出一张对象之间的连接网络。

- 继承层级说明的是对象在类型上如何彼此关联。例如，在模拟用水的程序里，也许会发现水龙头和管道是同一种对象，只不过水龙头能开能关，而管道可以与其他管道有多个连接。如果 `Faucet` 类和 `Pipe` 类继承自同一个超类，这种相似性就在程序设计中体现出来了。
- 对象之间的连接网络说明的是程序如何运转。例如，`Appliance` 对象可能向阀门发送请求用水的消息，阀门再向管道发送消息。管道可能与 `Building` 对象通信，`Building` 对象与所有的阀门、水龙头和管道通信，但不直接与家电通信。要这样互相通信，对象必须彼此知晓。`Appliance` 对象需要有一条通往 `Valve` 对象的连接，`Valve` 对象需要有一条通往 `Pipe` 对象的连接，如此等等。这些连接定义出一种程序结构。

设计面向对象程序，就是把对象连同它们的行为和交互模式铺排成一张网络，并安排好类的层级。程序的活动和程序的定义两方面都有结构。

设计面向对象程序，任务之一就是安排好这张对象网络。网络不必是静态的；它可以随程序运行而动态变化。对象之间的关系可以按需临场生成，扮演既定角色的对象阵容也可以时不时更换。但总得有一个剧本。

有些连接可以完全是临时的。一条消息里可能带有一个参数，标识出某个对象（也许就是消息的发送者），接收者可以与它通信。在响应这条消息的过程中，接收者可以向那个对象发送消息，也许还会在其中标识出自己或又一个对象，让对方接下来能与之通信。这类连接转瞬即逝；它们只在这条消息链存续期间有效。

但并非对象之间所有的连接都能临场处理。有些需要记录在程序的数据结构里。做法有好几种。可以维护一张对象连接表，也可以有一个按名字标识对象的服务。不过最简单的办法，是让每个对象都拥有一些实例变量，用来记住它必须与之通信的其他对象。这些实例变量被称为 _outlet_，
 因为它们记录着消息发出的出口——它们定义了程序网络中对象之间的主要连接。

尽管 outlet 实例变量的名字可以随意起，它们通常还是反映出 outlet 所指对象扮演的角色。图 4-1 展示了一个带有四个 outlet 的对象——一个经纪人、一个朋友、一个邻居和一个老板。扮演这些角色的对象可能时不时更换，但角色本身保持不变。

有些 outlet 在对象最初初始化时就设定好，此后可能永不改变。另一些可能作为其他动作的结果被自动设定。还有一些可以通过专为此目的提供的方法自由设定。

无论以何种方式设定，outlet 实例变量都揭示出应用的结构。它们把对象连成一张通信网络，就像供水系统的各个部件靠物理连接连在一起，又像人与人靠各自的社会关系模式联系在一起。

outlet 连接可以刻画对象之间许多不同类型的关系。有时连接发生在两个大体平等的伙伴对象之间，它们在应用中各有各的角色要演，谁也不支配谁。例如，`Appliance` 对象可能有一个 outlet 实例变量，用来记住它连接到的那个阀门。

有时则应该把一个对象看成另一个对象的一部分。例如，`Faucet` 对象可能用一个 `Meter`（水表）对象来计量放出的水量。这个 `Meter` 对象不为其他任何对象服务，只听命于 `Faucet` 对象行事。它是 `Faucet` 对象的内在组成部分，这与 `Appliance` 对象到 `Valve` 对象的那种外在连接形成对比。

类似地，一个管辖其他对象的对象，可能会保存一份它所管对象的清单。例如，`Building` 对象可能持有程序中所有 `Pipe` 对象的清单。这些 `Pipe` 对象会被视为 `Building` 对象的内在组成部分，归它所有。而 `Pipe` 对象彼此之间维持的则是外在连接。

内在 outlet 与外在 outlet 的行为不同。当一个对象被释放，或者被归档到磁盘上的文件中时，它的内在 outlet 所指向的对象必须随之一起释放或归档。例如，水龙头被释放时，它的水表也就没用了，因此也应当一并释放。归档时不带水表的水龙头，解归档之后没多大用处（除非它能给自己新建一个 `Meter` 对象）。

而外在 outlet 刻画的是程序在更高层次上的组织方式。它们记录的是相对独立的程序子部件之间的连接。当 `Appliance` 对象被释放时，它原先连接的 `Valve` 对象仍然有用，也仍然留在原处。当 `Appliance` 对象被解归档时，它可以连到另一个阀门上，继续扮演它此前扮演的那类角色。

对象网络由外部刺激启动。如果你写的是带用户界面的交互式应用，它会响应用户在键盘和鼠标上的操作。一个试图分解大数因子的程序，可能在你从命令行传给它一个目标数字时才开始运转。还有些程序可能响应从电话线收到的数据、从数据库取得的信息，或者关于程序所监控的某个机械流程的状态信息。

程序常常由_事件_（event）流来激活，事件就是对某种外部活动的报告。显示用户界面的应用由来自键盘和鼠标的事件驱动。每一次按键、每一次点击鼠标，都会产生应用要接收并响应的事件。面向对象的程序结构（一张准备好响应外部刺激的对象网络）非常适合这类由用户驱动的应用。

设计任务的另一部分，是决定类该如何安排——什么时候通过定义子类来给已有的类添加功能，什么时候另外定义一个独立的类。把极端情况想一遍，这个问题就清楚了：

- 可以设想一个只由一个对象构成的程序。因为它是唯一的对象，它只能给自己发消息。于是它既无法利用多态，也无法利用多个类带来的模块化，更无法利用“把程序设计成一张互连对象网络”的思路。程序真正的结构会被藏在类定义内部。尽管是用面向对象语言写的，其中面向对象的成分却少得可怜。
- 另一方面，也可以想象一个由成百上千种对象构成的程序，每种对象只有寥寥几个方法、功能十分有限。在这里，程序的结构同样会丢失，只不过这次是丢在了对象连接的迷宫里。

显然，最好避开这两个极端：让对象大到足以在程序中承担实质性的角色，又小到能让这个角色界定清晰。程序的结构应当能从对象连接的模式中一眼看懂。

尽管如此，还是常常会碰到这样的问题：是给某个类再添些功能，还是把这些额外功能抽出来，放进一份单独的类定义里？例如，`Faucet` 对象需要记录一段时间内用了多少水。要做到这一点，你既可以把必要的方法实现在 `Faucet` 类里，也可以像前面提到的那样，造一个通用的 `Meter` 对象来干这活儿。这样每个 `Faucet` 对象都会有一个 outlet 连到一个 `Meter` 对象，而这个水表除了水龙头之外不与任何对象交互。

怎么选往往取决于你的设计目标。如果 `Meter` 对象能用在不止一种场合，甚至能用在完全另外的项目里，那么把计量任务抽成一个单独的类，就能提升你代码的复用性。如果你有理由让 `Faucet` 对象尽可能自成一体，那就可以把计量功能加进 `Faucet` 类。

一般来说，更好的做法是争取写出可复用的代码，避免出现那种什么都干、以至于无法适应其他场合的庞大类。当对象被设计成组件时，它们的复用性就大大提高了。在一个系统或配置中管用的东西，很可能在另一个里也管用。

把功能分摊到不同的类中，未必会让编程接口变复杂。如果 `Faucet` 类把 `Meter` 对象保持为私有，那么 `Meter` 的接口就不必对 `Faucet` 类的使用者公开；这个对象会像 `Faucet` 的其他任何实例变量一样被隐藏起来。

对象把状态和行为结合在一起，因而与现实世界中的事物很像。正因为它们像真实的东西，设计面向对象程序在很大程度上就像在思考真实的东西——它们做什么、如何工作、一件东西与另一件如何相连。

当你设计一个面向对象程序时，你实际上是在拼装一套关于“某样东西如何运作”的计算机模拟。对象网络看起来、用起来都像是真实系统的模型。面向对象程序可以被看成一个模型，哪怕它在现实世界中并没有实际的对应物。

模型的每个部件——每一种对象——都是用它的行为、职责以及与其他部件的交互来描述的。因为对象的接口在于它的方法而不是它的数据，你可以从“某个系统部件必须做什么”入手开始设计，而不是从“它在数据上如何表示”入手。一旦对象的行为定下来，就可以挑选合适的数据结构，但这属于实现问题，而不是最初的设计。

例如，在这个用水程序里，你不会一上来就决定 `Faucet` 的数据结构长什么样，而是先想清楚你希望 `Faucet` 对象做什么——连到一根管道上、能开能关、能调节流速等等。因此设计从一开始就不被数据上的选择所束缚。你可以先决定行为，之后再实现数据。你对数据结构的选择可以随时间变化，而不影响设计。

设计一个面向对象程序，未必意味着要写大量代码。类定义的可复用性意味着，你有很大机会主要用别人写好的类来搭建程序。甚至有可能完全用别人定义的类构造出有意思的程序。随着可用类定义的集合不断扩大，你能挑选的可复用零件也越来越多。

可复用的类有很多来源。开发项目常常会产出可复用的类定义，一些有生意头脑的开发者还会把它们拿去卖。面向对象编程环境通常自带类库。Cocoa 库中的类远超一千个。其中一些类提供基础服务（散列、数据存储、远程消息传递）。另一些则更为具体（用户界面部件、视频显示、声音）。

通常，库中的一组类会协同工作，共同定义出一部分程序结构。这些类构成了一个软件框架（framework，或称 kit），可以用来构建各种不同类型的应用。当你使用一个框架时，你接受了它所提供的程序模型，并让自己的设计去适配它。你通过以下方式使用框架：

- 初始化并铺排框架类的实例
- 定义框架类的子类
- 定义你自己的新类，与框架中定义的类协同工作

以上每一种方式，都不只是让你的程序去适配框架，同时也是让通用的框架结构去适配你这个应用的专门用途。

框架本质上是为你的程序搭好了对象网络的一部分，并提供了类层级的一部分。你自己的代码则把框架开了个头的程序模型补充完整。
