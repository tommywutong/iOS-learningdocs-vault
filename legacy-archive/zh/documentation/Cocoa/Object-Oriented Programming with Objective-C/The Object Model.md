# 对象模型

面向对象编程的洞见在于：把状态和行为——数据以及作用于数据的操作——合并进一个高层次的单元，也就是_对象_（object），并让语言为它提供支持。一个对象就是一组相关的函数，外加一个为这些函数服务的数据结构。这些函数称为该对象的_方法_（method），其数据结构中的字段则是它的_实例变量_（instance variable）。
 方法把实例变量包裹起来，把它们藏在程序其余部分看不见的地方，如图 3-1 所示。

如果你处理过任何一类棘手的编程问题，你的设计里很可能已经出现过若干组作用于某种特定数据的函数——它们就是没有语言支持的、隐式的“对象”。面向对象编程把这些函数组显式地摆出来，让你可以从整组的角度、而不是从组成部分的角度去思考。要触及一个对象的数据，唯一的途径、唯一的接口，就是它的方法。

把状态和行为合进单个单元之后，对象就超越了两者中的任何一个；整体确实大于部分之和。对象是一种自给自足的“子程序”，对某个特定的功能领域拥有管辖权。它可以在更大的程序设计中扮演一个完整的模块化角色。

举例来说，如果你要写一个模拟家庭用水的程序，你可能会造出一些对象来代表供水系统的各个部件。其中之一可能是 `Faucet`（水龙头）对象，它有一些方法用来开启和停止水流、设置流速、返回某个时段内的用水量等等。为了完成这些工作，`Faucet` 对象需要用实例变量来记录龙头是开是关、用掉了多少水，以及水从哪里来。

显然，程序里的 `Faucet` 对象可以比真实的水龙头聪明得多（它类似于一个装了许多量表和仪器的机械水龙头）。但即便是真实的水龙头，也和任何系统部件一样，同时表现出状态和行为。要有效地为一个系统建模，你需要像对象这样同时结合了状态与行为的编程单元。

一个程序由一张互相连接的对象网络构成，网络中的对象彼此调用，各自解决谜题的一部分（如[图 3-2](#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpkridimbqga2tcnbzfvbuqnjnha2tsnrt)所示）。每个对象在程序的整体设计中扮演特定的角色，并且能与其他对象通信。对象之间通过_消息_（message）通信，消息就是执行某个方法的请求。

网络中的对象不会全都一样。例如，除了 `Faucet` 对象之外，这个模拟用水的程序可能还有 `Pipe`（管道）对象负责把水送到 `Faucet`，还有 `Valve`（阀门）对象负责调节管道之间的水流。可能还有一个 `Building`（建筑）对象来协调一组管道、阀门和水龙头；一些 `Appliance`（家电）对象——对应洗碗机、马桶和洗衣机——可以开关阀门；也许还有一些 `User`（用户）对象来操作这些家电和水龙头。当有人询问 `Building` 对象目前用了多少水时，它可能会挨个要求每个 `Faucet` 和 `Valve` 对象报告自身的当前状态。当用户启动一件家电时，这件家电需要打开某个阀门，才能取到它所需要的水。

每一种编程范式都自带一套术语和隐喻。面向对象编程的行话，是在请你从一个特定的视角去看待程序里发生的事情。

举个例子，人们往往会把对象看成演员，赋予它们类似人的意图和能力。有时候你会忍不住这样说：某个对象在决定该如何应对某种情况、在向别的对象索取信息、在内省自身以取得别人要它提供的信息、在把责任委托给另一个对象，或者在管理某个流程。

这个隐喻要求你把对象看成在执行它们自己的方法，而不是像在过程式编程语言里那样，认为是函数或方法在干活。对象不是盛放状态和行为的被动容器，而被视为程序活动的施动者。

这个隐喻其实非常有用。对象在几个方面都像演员：它在程序的整体设计中有特定的角色要演，而在这个角色范围内，它可以相当独立于程序的其他部分行事。它会与正在扮演各自角色的其他对象互动，但它是自足的，在一定程度上能够自主行动。就像舞台上的演员一样，它不能脱离剧本，但它所扮演的角色可以是多面而复杂的。

把对象看成演员，与面向对象编程的核心隐喻——对象之间通过消息通信——十分契合。你不是像调用函数那样去调用一个方法，而是向一个对象发送消息，请求它执行自己的某个方法。

这个隐喻可能需要一点时间才能适应，但它带来了一种看待方法和对象的有益视角。它把方法从其所作用的具体数据中抽离出来，转而专注于行为本身。例如，在一套面向对象的编程接口里，`start` 方法可能启动某项操作，`archive` 方法可能归档某些信息，`draw` 方法可能生成一幅图像。究竟启动的是哪项操作、归档的是哪些信息、画出的是哪幅图像，光看方法名是看不出来的。不同的对象可能以不同的方式执行这些方法。

因此，方法是一套抽象行为的词汇表。要唤起其中某个行为，你必须把方法与某个对象关联起来，让它变得具体。做法是指定那个对象作为消息的接收者。你选定的接收者，决定了究竟启动哪项操作、归档哪些数据、画出哪幅图像。

由于方法属于对象，它们只能通过某个特定的接收者来调用（接收者既是方法的拥有者，也是方法将要作用的那个数据结构的拥有者）。不同的接收者可以对同一个方法有不同的实现。因此，面对同一条消息，不同的接收者可以做出不同的事情。消息的结果无法仅凭消息名或方法名推算出来；它还取决于接收这条消息的对象。

消息（所请求的行为）与接收者（能响应该请求的方法的拥有者）被分开之后，消息传递这个隐喻就完美地体现了这样一个思想：行为可以从它们各自的具体实现中抽离出来。

 一个程序里可以有多个同类的对象。比如那个模拟用水的程序，可能有好几个水龙头和管道，还有若干家电和用户。同类的对象被称为同一个_类_（class）的成员。一个类的所有成员都能执行相同的方法，并拥有一一对应的实例变量集合。它们还共享同一份定义；每一类对象只需定义一次。

在这一点上，对象和 C 的结构体很像。声明一个结构体就是定义了一个类型。例如，下面这个声明

```c
struct key {
    char *word;
    int count;
};
```

定义了 `struct key` 类型。一旦定义好，就可以用这个结构体名字产出该类型的任意多个实例：

```c
struct key  a, b, c, d;
struct key *p = malloc(sizeof(struct key) * MAXITEMS);
```

这个声明是某类结构体的模板，但它并没有创建出程序可以使用的结构体。还需要再走一步，为该类型的一个实际结构体分配内存，而这一步可以重复任意多次。

同样，定义一个对象就是为某类对象创建一个模板。它定义了一个对象的类。这个模板可以用来产出任意多个相似的对象——也就是该类的_实例_（instance）。
 例如，`Faucet` 类只会有一份定义。程序可以依据这份定义，分配出它所需要的任意多个 `Faucet` 实例。

类定义与结构体定义相似之处在于，它排布出一组数据元素（实例变量），这些元素会成为每个实例的一部分。每个实例都有为自己那套实例变量分配的内存，用来存放该实例特有的值。

不过，类定义与结构体声明也有不同：它还定义了方法，用以规定这个类的成员的行为。每个实例的特征之一，就是它能够访问为该类定义的那些方法。两个数据结构相同但方法不同的对象，不属于同一个类。

对 C 程序员来说，模块无非就是一个包含源代码的文件。把一个大（甚至不那么大的）程序拆成不同的文件，是把它分割成可管理片段的便捷办法。每一片都可以独立开发、单独编译，然后在链接程序时与其他片段整合到一起。

用 `static` 存储类说明符把名字的作用域限制在声明它们的文件内，可以增强源代码模块的独立性。这种模块是由文件系统定义的单元。它是源代码的容器，而不是语言层面的逻辑单元。往容器里放什么，由每个程序员自己决定。你可以用它们把逻辑上相关的代码归到一起，但并非非这么做不可。文件就像五斗柜的抽屉；你可以把袜子放一个抽屉、内衣放另一个抽屉，如此等等，也可以采用别的整理方案，或者干脆全部混在一起。

面向对象编程语言支持用文件作为源代码的容器，但它们还给语言添加了一种逻辑模块——类定义。不出所料，通常每个类都定义在自己的源文件里——逻辑模块与容器模块正好对应。

举例来说，在 Objective-C 中，你完全可以把 `Valve` 类中与 `Pipe` 对象交互的那部分，定义在定义 `Pipe` 类的那个文件里，这样就为与 `Pipe` 相关的代码建立了一个容器模块，同时把 `Valve` 类拆到了不止一个文件中。无论源代码分布在多少个文件里，`Valve` 类的定义在程序的构造中仍然是一个模块化单元——它仍然是一个逻辑模块。

使类定义成为语言中的逻辑单元的那些机制，会在[抽象的机制](#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpkridimbqga2tcnbzfvbuqnjnha3dgmjw)中详细讨论。

面向对象编程的一个主要目标，是让你写的代码尽可能可复用——让它能服务于许多不同的场景和应用——这样你就不必去重新实现某个已经做过的东西，哪怕只是稍有不同。

复用性（reusability）受下列因素影响：

- 代码有多可靠、有多少 bug
- 文档有多清楚
- 编程接口有多简单直接
- 代码执行任务的效率有多高
- 功能集有多完整

这些因素并不只适用于对象模型。它们可以用来评判任何代码的复用性——标准 C 函数和类定义都一样。举例来说，高效且文档完备的函数，就比没有文档、不可靠的函数更容易复用。

尽管如此，笼统地比较一下就会看出，类定义在一些方面比函数更适合写出可复用的代码。你可以做不少事情来让函数更可复用——例如把数据作为参数传入，而不是假定存在某些特定名字的全局变量。即便如此，事实证明只有一小部分函数能被推广到它们最初设计目标之外的应用中。函数的复用性至少在三个方面存在固有的局限：

- 函数名是全局的；每个函数都必须有唯一的名字（用 `static` 声明的除外）。这个命名要求使得在构建复杂系统时很难大量依赖库代码。这样的编程接口既难学，又因为太过庞杂而无法轻易体现出重要的通用规律。

  而类是可以共享编程接口的。当同一套命名约定被反复使用时，大量功能就可以用一个相对小巧、易于理解的接口打包起来。
- 函数是从库里一个一个挑出来用的。程序员得自己去挑选所需的一个个函数。

  相比之下，对象是以整包功能的形式出现的，而不是一个个孤立的方法和实例变量。它们提供的是成套的服务，因此面向对象库的使用者不会陷在自己拼凑解决方案的泥潭里。
- 函数通常与为某个特定程序设计的特定数据结构绑在一起。数据与函数之间的这种耦合，是接口中无可回避的一部分。一个函数只对那些愿意使用它所接受的参数数据结构的人有用。

  因为对象把自己的数据藏了起来，它没有这个问题。这正是类比函数更容易复用的主要原因之一。

对象的数据受到保护，程序的其他任何部分都碰不到它。因此方法可以信赖这份数据的完整性。它们可以确信，外部访问没有把数据搞成不合逻辑或站不住脚的状态。结果就是，对象的数据结构比传给函数的数据结构更可靠，方法也就可以更多地依赖它。于是，可复用的方法也更容易写。

而且，由于对象的数据是隐藏的，一个类可以改用不同的数据结构重新实现，而不影响它的接口。所有使用该类的程序都能用上新版本，无需改动任何源代码；不需要重新编程。

到这里为止，我们介绍的对象既是体现更高层次抽象的单元，也是应用中连贯的角色扮演者。然而，若没有各种语言机制的支持，对象是无法这样使用的。其中两个最重要的机制是封装（encapsulation）和多态（polymorphism）。

_封装_把对象的实现挡在它的接口之外，而_多态_则源于让每个类拥有各自的命名空间。接下来的几节将依次讨论这两种机制。

要在任何抽象层次上做出有效的设计，你都得能把实现细节抛在脑后，转而从“把这些细节归拢在一个共同接口之下的单元”这个角度去思考。要让一个编程单元真正有效，接口与实现之间的壁垒必须是绝对的。接口必须把实现封装起来——也就是把实现藏起来，不让程序的其他部分看到。封装保护实现不受意外操作和无意访问的干扰。

在 C 中，函数显然是被封装起来的；它的实现对程序其他部分不可访问，也不会受到函数体之外任何操作的影响。在 Objective-C 中，方法的实现同样是被封装的，但更重要的是，对象的实例变量也是如此。它们藏在对象内部，在对象之外不可见。实例变量的封装有时也叫作_信息隐藏_（information hiding）。

乍一看，把信息藏在实例变量里似乎会束缚你作为程序员的自由。其实恰恰相反，它给了你更大的施展空间，让你摆脱了本来可能被强加的种种约束。如果一个对象的实现有任何部分会泄漏出去、变得可被程序其他部分访问、或者需要被它们操心，那就等于同时捆住了对象实现者和对象使用者的手脚。任何一方想做改动，都得先去跟另一方核对。

举例来说，假设你对那个模拟用水的程序里正在开发的 `Faucet` 对象很感兴趣，想把它用到你正在写的另一个程序里。一旦这个对象的接口定下来，别人继续开发它、修 bug、找出更好的实现办法，你都不必操心。这些改进的好处你能享受到，而其中没有一项会影响你在自己程序里的做法。因为你只依赖接口，他们做的任何事都不会弄坏你的代码。你的程序与这个对象的实现是隔离的。

而且，虽然实现 `Faucet` 对象的人可能会关心你怎么使用这个类，也可能会努力确保它满足你的需要，但他们不必操心你写代码的方式。你做的任何事情都碰不到这个对象的实现，也限制不了他们在未来版本中修改实现的自由。实现与你或其他使用者可能做的任何事情同样是隔离的。

不同的对象能各以自己的方式响应同一条消息，这种能力叫作_多态_。

多态之所以成立，是因为每个类都活在自己的命名空间里。在类定义内部指定的名字，不会与该类之外任何地方指定的名字冲突。这一点对对象数据结构中的实例变量和对象的方法都成立：

- 正如 C 结构体的字段处在受保护的命名空间里，对象的实例变量也是如此。
- 方法名同样受到保护。与 C 函数的名字不同，方法名不是全局符号。一个类中某个方法的名字不会与其他类中的方法名冲突；两个截然不同的类可以实现同名的方法。

方法名是对象接口的一部分。当发出一条消息、要求某个对象做点什么时，消息指明了该对象应当执行的方法。因为不同的对象可以有同名的方法，一条消息的含义必须相对于接收它的那个具体对象来理解。同一条消息发给两个不同的对象，可能会调用两个截然不同的方法。

多态的主要好处是简化了编程接口。它让你可以确立一些约定，在一个又一个类中反复复用。你不必为程序中新增的每个功能都发明一个新名字，同样的名字可以反复使用。编程接口可以被描述成一组抽象行为，与实现它们的那些类无关。

举例来说，假设你想报告某个 `Appliance` 对象在给定时段内的用水量。你不必为 `Appliance` 类定义 `amountConsumed` 方法、为 `Faucet` 类定义 `amountDispensedAtFaucet` 方法、再为 `Building` 类定义 `cumulativeUsage` 方法，只需给每个类都定义一个 `waterUsed` 方法即可。这样一归并，用于同一个概念性操作的方法数量就减少了。

多态还使得代码可以分散到不同对象的方法中，而不必汇集到一个枚举所有可能情况的函数里。这让你写的代码更易扩展、更易复用。当出现新情况时，你不必重新实现已有代码；只需添加一个带有新方法的新类，原先写好的代码原封不动。

举例来说，假设你有一段代码向某个对象发送 `draw` 消息。视接收者不同，这条消息可能产生两种图像中的一种。当你想加入第三种情况时，你不必改动消息，也不必改动现有代码；只要允许把另一个对象指定为消息的接收者就行了。

解释新事物最容易的办法，是从已被理解的事物讲起。如果你想描述纵帆船是什么，那么听众已经知道帆船是什么会很有帮助。如果你想解释羽管键琴如何工作，最好能假定你的听众已经看过钢琴内部、见过有人弹吉他，或者至少熟悉乐器这个概念。

要定义一种新的对象也是同样的道理；如果描述能从某个已有对象的定义出发，事情就简单多了。

有鉴于此，面向对象编程语言允许你在一个已定义的类的基础上去定义新类。作为基础的那个类叫作_超类_（superclass）；
 新的类则是它的_子类_（subclass）。子类的定义只需指明它与超类有什么不同；其余一切都视为相同。

没有任何东西是从超类拷贝到子类的。相反，这两个类被连接了起来，使得子类_继承_（inheritance）超类的全部方法和实例变量——就像你希望听众对纵帆船的理解，能继承他们已经掌握的关于帆船的知识一样。如果子类的定义是空的（没有定义任何自己的实例变量或方法），那么这两个类除了名字之外将完全相同，并共享同一份定义。这就好比在解释 fiddle（提琴）是什么时说，它跟 violin（小提琴）一模一样。不过，声明一个子类并不是为了造同义词；而是要造出至少与超类有一点差别的东西。比如，你可能会扩展 fiddle 的行为，让它除了古典音乐之外还能演奏蓝草音乐。

任何类都可以用作新类定义的超类。一个类可以同时是另一个类的子类，又是它自己那些子类的超类。这样一来，任意多个类就能连成一个继承层级，如图 3-3 所示。

每个继承层级都始于一个没有超类的根类。从根类开始，层级向下分叉。每个类都从它的超类继承，并通过超类从层级中位于它上方的所有类继承。每个类都继承自根类。

每个类都是其继承链上所有类定义的累加。在上面的例子中，类 D 既从 C（它的超类）继承，也从根类继承。D 类的成员拥有在 D、C 和根类这三个类中定义的方法和实例变量。

通常，每个类只有一个超类，而子类的数量可以不限。不过，在某些面向对象编程语言中（Objective-C 不在此列），一个类可以有多个超类；它可以通过多个来源继承。多重继承不像图 3-3 那样只有一条向下分叉的层级，而是让层级（或不同层级）的某些分支合并到一起。

子类可以对它从超类继承来的定义做三类改动：

- 它可以通过添加新方法和新实例变量来扩充所继承的类定义。这是定义子类最常见的原因。子类总是会添加新方法，并在方法有需要时添加新实例变量。
- 它可以通过用新版本替换已有方法来修改所继承的行为。做法很简单：实现一个与继承来的方法同名的新方法。新版本会_覆盖_（override）
   继承来的版本。（继承来的方法并不会消失；对定义它的那个类以及继承它的其他类来说，它依然有效。）
- 它可以通过用新版本替换已有方法来细化或扩展所继承的行为，同时把旧版本纳入新方法中而保留下来。子类会在新方法体内发送一条消息去执行旧版本。继承链上的每个类都可以为一个方法的行为贡献一部分。例如在[图 3-3](#apple-f4xwc4dqnrsv64tfmyxwi33df52wszbpkridimbqga2tcnbzfvbuqnjnha3dknbs)中，类 D 可能覆盖类 C 中定义的某个方法，并把 C 的版本纳入进来，而 C 的版本又纳入了根类中定义的版本。

因此，子类往往是在把超类的定义填充完整，使之更具体、更专门化。它们是在添加代码、有时是替换代码，而不是删减代码。注意，方法一般无法“取消继承”，实例变量也不能被移除或覆盖。

继承层级的经典例子借自动植物分类学。例如，可以有一个类对应松科（Pinaceae）树木。它的子类可以是 `Fir`、`Spruce`、`Pine`、`Hemlock`、`Tamarack`、`DouglasFir` 和 `TrueCedar`，对应构成这一科的各个属。`Pine` 类可能又有 `SoftPine` 和 `HardPine` 两个子类，其中 `SoftPine` 的子类是 `WhitePine`、`SugarPine` 和 `BristleconePine`，`HardPine` 的子类是 `PonderosaPine`、`JackPine`、`MontereyPine` 和 `RedPine`。

很少有理由真去编写这样一套分类体系，但这个类比很贴切。子类往往是把超类专门化，或者让它适应某个特殊用途，就像一个物种是对一个属的专门化一样。

下面是继承的一些典型用法：

- 复用代码。如果两个或更多的类有一些共同之处，同时又在某些方面有差别，那就可以把共同的部分放进一份类定义里，让其他类去继承。共同的代码得以共享，只需实现一次。

  例如，为模拟用水的程序定义的 `Faucet`、`Valve` 和 `Pipe` 对象，都需要连接到水源，也都应当能记录流速。这些共同点可以在一个类里编码一次，再由 `Faucet`、`Valve` 和 `Pipe` 类继承。可以说 `Faucet` 对象是一种 `Valve` 对象，所以 `Faucet` 类也许会把自身的大部分内容从 `Valve` 继承过来，只添加很少一点自己的东西。
- 建立协议。一个类可以声明若干方法，期望它的子类去实现。这个类可能给出这些方法的空版本，也可能实现部分版本，供子类的方法纳入使用。无论哪种情况，它的这些声明都确立了一份所有子类都必须遵循的_协议_（protocol）。

  当不同的类实现名称相似的方法时，程序在设计上就更能利用多态。建立一份子类必须实现的协议，有助于把这些约定落到实处。
- 提供通用功能。一位实现者可以定义一个类，其中包含大量用于解决某个问题的基础性、通用性代码，但并不把所有细节填满。其他实现者随后可以创建子类，把这个通用类改造成适合自己具体需要的样子。例如，模拟用水的程序里的 `Appliance` 类，可能定义了一种通用的用水设备，由子类把它变成具体种类的家电。

  因此，继承既是让别人的编程任务变得更轻松的一种方式，也是分离实现层次的一种方式。
- 做小幅修改。当继承被用来提供通用功能、建立协议或复用代码时，人们设计出的是一个供其他类继承的类。但你也可以用继承去修改那些本来并不打算当超类用的类。举例来说，假设有个对象在你的程序里用起来不错，但你想改动它做的一两件事。你可以在一个子类里做这些改动。
- 预览各种可能。子类还可以用来把备选方案抽出来做测试。例如，如果某个类要与特定的用户界面绑在一起编码，那么在项目的设计阶段可以把各种备选界面分别抽到子类中。然后把每种备选方案演示给潜在用户，看他们更喜欢哪一种。方案定下来之后，选中的那个子类可以再合并回它的超类。

在编程史上曾经有一段时期，一个程序会用掉多少内存，通常在源代码编译和链接时就定死了。程序可能需要的全部内存，都会在它启动时一次性划拨给它。这块内存是固定的；既不能增长也不能缩小。

现在回头看，这是何等严重的约束已经很明显了。它限制的不只是程序如何构造，还有你能设想程序去做什么。它约束的是设计，而不只是编程技巧。能在程序运行时动态分配内存的函数（比如 `malloc`）的出现，开启了此前并不存在的可能性。

编译期和链接期的约束之所以束缚人，是因为它们迫使各种问题必须依据程序员源代码中的信息来定夺，而不是依据程序运行时从用户那里得到的信息。

尽管动态分配去掉了其中一个约束，还有许多其他约束依然存在，其限制程度不亚于静态内存分配。例如，构成一个应用的各种元素必须在编译期与数据类型对上号。而应用的边界通常在链接期就定死了。应用的每一部分都必须汇合到单个可执行文件里。程序运行时无法引入新的模块和新的类型。

Objective-C 力图突破这些限制，让程序尽可能动态、尽可能灵活。它把大量决策的负担从编译期和链接期挪到了运行时。目标是让程序的使用者来决定会发生什么，而不是让语言的要求、编译器和链接器的需要人为地限制他们的行为。

有三类动态性对面向对象设计尤为重要：

- 动态类型（dynamic typing），等到运行时才确定一个对象的类
- 动态绑定（dynamic binding），在运行时确定该调用哪个方法
- 动态加载（dynamic loading），在程序运行过程中往程序里添加新的组件

如果你写的代码把一个值赋给了容纳不下它的类型，编译器通常会抱怨。你可能会看到这样的警告：

```
incompatible types in assignment
assignment of integer from pointer lacks a cast
```

类型检查很有用，但有时它会妨碍你从多态中获益，尤其是当每个对象的类型都必须让编译器知道的时候。

举例来说，假设你想给一个对象发送消息，让它执行 `start` 方法。和其他数据元素一样，这个对象由一个变量来表示。如果这个变量的类型（它的类）必须在编译期就确定，那就不可能让运行时的因素来影响“该给这个变量赋哪种对象”的决定。如果变量的类在源代码中就固定了，那么消息所调用的 `start` 版本也就固定了。

反过来，如果可以等到运行时再去弄清这个变量的类，那么任何一种对象都可以赋给它。视接收者的类不同，`start` 消息可能调用该方法的不同版本，产生截然不同的结果。

由此可见，动态类型让动态绑定（下一节讨论）有了实质内容。但它的作用不止于此。它使对象之间的关联可以在运行时确定，而不必被硬编码进一个静态的设计中。例如，一条消息可以把某个对象作为参数传过去，却不必声明它究竟是哪种对象——也就是不必声明它的类。消息的接收者随后可以向这个对象发送自己的消息，同样完全不必在意它是哪种对象。因为接收者要靠这个传进来的对象完成一部分工作，所以从某种意义上说，它被一个类型不确定的对象定制过了（这里说的不确定是在源代码层面，而不是在运行时）。

在标准 C 中，你可以声明一组可互相替代的函数，比如标准的字符串比较函数，

```c
int strcmp(const char *, const char *);   /* 区分大小写 */
int strcasecmp(const char *, const char *); /*不区分大小写*/
```

并声明一个指向具有相同返回类型和参数类型的函数的指针：

```c
int (* compare)(const char *, const char *);
```

然后你可以等到运行时再决定把哪个函数赋给这个指针，

```c
if ( **argv == 'i' )
    compare = strcasecmp;
else
    compare = strcmp;
```

再通过这个指针调用函数：

```c
if ( compare(s1, s2) )
    ...
```

这类似于面向对象编程中所说的_动态绑定_，也就是把“究竟执行哪个方法”的决定推迟到程序运行时。

虽然并非所有面向对象语言都支持它，但动态绑定通过消息传递就能例行而透明地完成。你不必像上面例子那样，绕一圈去声明一个指针再给它赋值。你也不必给每个备选过程起不同的名字。

消息是间接地调用方法的。每个消息表达式都必须找到一个方法实现来“调用”。为了找到那个方法，消息机制必须先查出接收者的类，再在其中找到消息所指名的那个方法的实现。当这件事在运行时完成时，方法就是动态绑定到消息上的。当它由编译器完成时，方法就是静态绑定的。

即使没有动态类型，动态绑定也是可能的，只是意义不大。当接收者的类是固定的、且编译器已经知道时，等到运行时再去为消息匹配方法并没有多少好处。编译器完全可以自己找到那个方法；运行时的结果不会有任何不同。

然而，如果接收者的类是动态类型的，编译器就无从确定该调用哪个方法。只有在运行时解析出接收者的类之后，才能找到方法。因此，动态类型必然带来动态绑定。

动态类型还让动态绑定变得有意思，因为它开启了这样一种可能：同一条消息，视接收者的类不同，结果可能大相径庭。运行时的因素既能影响接收者的选择，也能影响消息的结果。

动态类型和动态绑定还开启了另一种可能：你写的代码可以给尚未被发明出来的对象发送消息。如果对象类型不必在运行前就定下来，你就可以把设计自己的类、给自己的数据类型命名的自由留给别人，而你的代码依然能向他们的对象发送消息。你们需要达成一致的只是消息，而不是数据类型。

历史上，在许多常见环境中，一个程序在运行之前，它的所有部分都必须链接到一个文件里。程序启动时，整个程序会被一次性载入内存。

一些面向对象编程环境突破了这个约束，允许一个可执行程序的不同部分保存在不同的文件里。程序可以按需要一块一块地启动。每一块在被启动时动态加载，并与程序的其余部分链接起来。用户的操作可以决定程序的哪些部分在内存中、哪些不在。

一个大型程序在启动时只需要载入它的核心部分。其他模块可以在用户请求其服务时再添加进来。用户没有请求的模块不会向系统索取任何内存。

动态加载带来了一些有意思的可能性。例如，整个程序不必一次性开发完成。你可以分块交付你的软件，一次更新其中一部分。你可以设计一个程序，把若干工具归到同一个界面之下，只加载用户想用的那些工具。程序甚至可以为同一项工作提供多套备选工具——由用户从中选一个，然后只加载那一个工具。

动态加载眼下最重要的好处，也许是它让应用变得可扩展。你可以允许别人为你设计的程序添加内容、做出定制。你的程序需要做的，只是提供一个框架供别人填充，并在运行时找到他们实现的那些部分，把它们动态加载进来。

动态加载面临的主要挑战，是让新加载进来的那部分程序与已经在运行的部分协同工作，尤其是当不同部分出自不同的人之手时。不过在面向对象环境中，这个问题在很大程度上消失了，因为代码被组织成了逻辑模块，实现与接口之间界限分明。当类被动态加载时，新加载的代码不会与已经就位的代码发生冲突。每个类都封装了自己的实现，并拥有独立的命名空间。

此外，动态类型和动态绑定让别人设计的类可以毫不费力地融入你设计的程序。一个类一旦被动态加载进来，对待它就与对待其他任何类没有区别。你的代码可以给他们的对象发送消息，他们的代码也可以给你的对象发送消息。你们双方都不需要知道对方实现了哪些类。你们只需在一份通信协议上达成一致。
