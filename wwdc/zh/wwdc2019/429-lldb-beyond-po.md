大家好，我是 Davide，是 Apple 调试技术团队的一名工程师。我和我的同事 Jonas 一起来了。你可能熟悉 `po`，这是在 LLDB 中打印变量的方式。今天，我们将讨论它以及它的工作原理。我们还将介绍其他查看源代码中变量的方法，以及格式化输出的强大机制。LLDB 是驱动 Xcode 中变量视图的调试器。

你可以在那里看到你定义的变量及其类型。

在 Xcode 中调试时，你也可以直接发送命令，并通过窗口右下角的控制台与 LLDB 进行交互。

这包括在调查 App 中的 bug 时，打印源代码中定义变量的值的能力。LLDB 提供了几种完成此任务的方式。每一种方式都有不同的权衡。让我们来看看它们。举个例子，假设我们有一个表示 Trip（旅行）的结构体（struct），包含一个名称和一个目的地列表。让我们开始一次地中海巡游吧。

我们要探索的第一个命令是 `po`，你可以认为它代表 print object description（打印对象描述）。当我们使用这个命令时，返回的是对象描述（object description），它是对你的类型实例的文本化表示。系统运行时提供了一个默认的描述，但也可以自定义它。

我们可以通过添加对 `CustomDebugStringConvertible` 协议的遵循来实现这一点。这要求拥有一个名为 `debugDescription` 的属性（property）。

现在，如果我们在调试器中打印对象描述，我们将看到我们提供的描述，而不是默认的描述。

这个更改只影响顶层描述。如果你需要修改子结构，请查阅 `CustomerReflectable` 协议的文档。

对于 Objective-C 对象，也可以通过实现 `description` 方法来完成。

但 `po` 能做的不仅仅是打印变量。例如，你可以获取我们巡游的名称并计算它的大写版本，或者获取一个按字母顺序排序的巡游目的地数组。

一般来说，它可以求值任意表达式。所以，任何能在程序的给定提示符下编译的东西都可以作为参数传递给该命令。

实际上，`po` 是一个名为 `expression` 的命令的别名，并带有一个用于打印对象描述的参数。LLDB 中的别名是保存按键操作的便捷方式。例如，如果你想自己实现 `po`，你可以使用 `command alias`。将你自己的命令名称作为第一个参数，然后指定你想要创建别名的命令。定义后，你可以像使用 LLDB 中的任何其他命令一样使用它。

既然我们知道 `po` 能做什么，让我们更深入地了解它是如何工作的。

让我们看看 `po` 为了提供一个值必须执行的步骤。为了提供你所用语言的完整表达能力，LLDB 并不会自己解析和求值表达式。相反，它首先生成一段可以从你给出的表达式编译的源代码，类似于这里显示的片段。然后它使用嵌入的 Swift 和 Clang 编译器来编译这段代码，该代码会在你调试的程序上下文中执行。一旦执行完成，LLDB 必须访问结果值。

然后你需要获取对象描述。为此，LLDB 将前一个结果包装在另一段源代码中。这段代码也会在你调试进程的上下文中编译和执行。这次执行的结果是一个字符串，LLDB 会将其显示为 `po` 命令的结果。`po` 只是我们介绍的三种在 LLDB 中打印变量方式中的第一种。让我们看看其他的。

在 LLDB 中打印变量的第二种方式是 `p` 命令。你可以把它理解为不带对象描述的 print。让我们看看它的输出。

首先要注意的是，表示形式与 `po` 提供的略有不同，但它们是等效的，包含相同的信息。

第二点要注意的是，结果值被赋予了一个名称 `$R0`。这是 LLDB 中的一个特殊约定。每个表达式的结果都会获得一个递增的名称，例如 `$R1` 和 `$R2`。这个名称可以在 LLDB 的后续表达式中使用。你可以像使用项目中任何其他变量一样引用 `$R0`。例如，你可以打印 destruction 的字段。

与 `po` 类似，`p` 在 LLDB 中并不是一个头等命令。它只是 `expression` 命令的一个别名，但没有 `-- object description` 参数。正如我们之前对 `po` 所做的，让我们看看 `p` 在底层是如何工作的。

由于 `p` 不需要获取描述，它不需要做那么多工作。你可能还记得 `po` 早期描述中的这个图表。事实上，编译和求值表达式的第一部分对于两个命令来说是完全相同的。但是一旦获得结果，LLDB 会对结果执行一个名为动态类型解析（dynamic type resolution）的步骤。

让我们更详细地描述它。为此，我们必须稍微修改我们的代码示例。让我们看看如何修改。

我们将 `Trip` 结构体改为遵循一个名为 `Activity` 的协议。

在 Swift 中，源代码中类型的静态表示和运行时的动态类型不一定是相同的。例如，一个变量可能使用协议类型声明。

在这个例子中，`cruise` 的静态类型是 `Activity`。但在运行时，该变量将有一个类型为 `Trip` 的实例，这就是动态类型。如果我们打印 `cruise` 的值，我们会得到一个类型为 `Trip` 的对象，因为 LLDB 会检索类型元数据来显示给定变量在给定程序点最准确的类型。这就是我们所说的动态类型解析。对于 `p` 命令，动态类型解析只在表达式的结果上执行。

假设我们想要访问 `cruise` 的其中一个字段。当 LLDB 尝试通过 `p` 来求值这个表达式时，它看到 `cruise` 是一个 `Activity` 类型的对象，并且没有一个名为 `name` 的成员。求值失败并返回一个错误。这是因为，如果你还记得，LLDB 在运行 `p` 时会编译代码，而它看到的唯一类型就是源代码中的那个——静态类型。

这和在源代码中输入表达式 `cruise.name` 是一样的。静态编译器会拒绝它并返回一个错误。如果你想求值表达式而不出错，你需要先将对象显式地转换为其动态类型，然后访问结果上的字段。这既适用于调试器，也适用于你的源代码。

`P` 还没有完成它的工作。在对结果执行动态类型解析后，LLDB 将结果对象传递给格式化器子系统（formatter subsystem），这是 LLDB 中负责打印对象的可读描述的部分。让我们深入了解一下。

为了展示格式化器（formatter）的工作原理，我们将显示它们的输入和输出。如果该类型没有格式化器，字符串看起来是这样的。

如果你自己想尝试，你可以向 `p` 传递 `-- raw` 选项。标准库类型，即使是像字符串和整数这样简单的类型，也有复杂的表示形式，因为它们为了速度和大小进行了高度优化。格式化器处理之后，字符串看起来正如你所期望的那样——一个字符序列。LLDB 了解许多常用类型，并为它们提供了格式化器。你也可以编写自定义格式化器。我们稍后会讨论这个。

我们讨论了 `p` 和 `po`。

现在我们准备描述在 LLDB 中打印变量的第三种方式，`v` 命令。

`v` 的输出与 `p` 完全相同，因为它也依赖于我们刚才描述的格式化器。

与其他两个命令一样，`v` 是我们在 Xcode 10.2 中为 `frame variable` 命令引入的一个别名。

与其他两种机制不同，`v` 命令完全不编译和执行代码，这使得它非常快。由于 `v` 不编译代码，它有自己的语法，这不一定与你正在调试的语言相同。例如，它使用点操作符和下标操作符来访问字段/时间。但它不会执行重载解析，并且计算属性也无法求值，因为这需要代码执行。

如果你需要这些功能，可以使用 `p` 或 `po`。正如你所猜测的，`v` 的工作方式与另外两种打印变量的机制大不相同。让我们继续澄清一些细节。按照我们制作图表的传统，这是 `v` 的图表。我们想要打印一个变量。为此，`v` 首先查询程序状态以在内存中找到该变量。然后它从内存中读取变量的值。接着它对其执行动态类型解析。如果用户要求访问子字段，它会为每个子字段重复此步骤，在每一轮都执行动态类型解析。完成后，它将结果传递给数据格式化器子系统。

`v` 可能会多次执行动态类型解析，这一事实是一个需要记住的重要细节，也是 `p` 和 `v` 工作方式的巨大区别。实际上，格式化器只执行一次动态类型解析。让我们看看这个问题出现在哪里。

我们回到之前的例子，其中 `p` 无法访问 `cruise` 的成员。通过在解释的每一步执行动态类型解析，`v` 能够理解 `cruise` 是一个 `Trip` 类型的对象，并在内存中访问其字段。在这个场景中，`v` 严格比 `p` 更强大，允许你在 `p` 无法做到或需要显式转换的情况下查看你的类型。

我们已经介绍了在 LLDB 中打印变量的三种不同方式。

让我们回顾并排比较一下 `po`、`p` 和 `v` 命令的不同之处。

我们要讲的第一点关于对象如何呈现。

`po` 命令使用对象描述，而 `p` 和 `v` 命令使用数据格式化器来显示对象。我们还需要记住结果是如何计算的。`po` 和 `p` 都编译表达式并可以访问完整的语言能力。而 `v` 有自己的语法，解释表达式并为解释的每一步执行动态类型解析。

我们之前提到过 LLDB 格式化是可以自定义的。为了更详细地讨论这个问题，有请我的同事 Jonas。大家好，我是 Jonas，也是调试技术团队的一名工程师。

在 LLDB 中，数据格式化器（data formatter）定义了变量在调试器中如何显示。

有为常见类型构建的格式化器。例如，当使用 `v` 命令时，我们可以打印巡游的目的地，数组元素以可读的格式显示。

通常，默认格式化器对于用户定义的类型和来自标准库的类型都工作得很好。但有时你可能想要调整现有的格式化器，或者自己定义一个格式化器。

你可以这样做，因为 LLDB 中的数据格式化器是完全可扩展的。每种类型都可以有自己的表示形式。为了帮助你自定义该表示形式，LLDB 提供了过滤器（filter）、摘要（summary）和合成子项（synthetic children）。

过滤器用于限制现有格式化器的输出。现在，我们的 `Trip` 只有几个目的地，但随着数量的增加，输出可能会变得杂乱。

通过添加过滤器，我们可以指定只想看到 `Trip` 的名称。

这不仅影响控制台中格式化器的输出，也影响 Xcode 中的变量视图。

在继续之前，让我们再次移除过滤器。

摘要提供了类型的字符串表示形式。为了让你一眼了解该类型的信息，它们相当于你为实现与 `po` 一起使用而实现的描述的数据格式化器。与过滤器一样，它们也会影响 Xcode 中的变量视图。

虽然我们 `Trip` 的成员都有摘要，但 `Trip` 本身没有。让我们改变这一点。

一个好的摘要应该是第一个和最后一个目的地。

摘要字符串可以包含普通文本和特殊变量，这些变量用于访问正在被打印的类型（time）的字段。这些变量以美元符号开头，并包裹在花括号中。它们使用与 `v` 命令相同的语法。当前定义摘要的类型通过 `var` 访问。

摘要使用 `var.name` 来访问 `Trip` 的名称，使用 `var.destinations` 来访问其目的地。

但是摘要存在一个问题。它只对包含恰好三个目的地的 `Trip` 有效。因为格式化器无法访问计算得出的变量，比如数组的 count，我们必须硬编码最后一个元素的索引。

幸运的是，我们有另一种强大的工具可用。我们也可以用 Python 定义摘要。

Python 格式化器可以进行任意的计算，并且可以完全访问 LLDB 的脚本桥接 API，该 API 提供了几个用于访问当前调试会话状态的对象。`target` 是当前正在被调试的程序。`process`、`thread` 和 `frame` 提供了对相应运行时信息的访问。

变量、寄存器或表达式的值由 `SBValue` 类表示。这些对数据格式化器来说特别有趣，因为它们用于导航类型及其值。更多详情请查看在线文档。

从 Xcode 11 开始，脚本使用 Python 3。如果你有现有的 Python 2 脚本，请查看 Xcode 发行说明以获取关于迁移到 Python 3 的更多信息。

让我们探索一下 LLDB API。

执行 `script` 命令会进入一个交互式 Python 解释器。

当前帧可以通过 `lldb.frame` 变量访问。这会返回一个 `SBFrame` 实例。我们知道当前帧包含一个名为 `cruise` 的变量。所以，我们可以继续使用 `find variable` 来获取它的 `SBValue`。

由于这些对象在底层驱动着数据格式化器，因此打印它们看起来与相应的数据格式化器输出完全相同也就不足为奇了。

我们也知道 `cruise` 有一个名为 `destinations` 的成员。我们可以通过调用 `GetChildMemberWithName` 来访问它。

结果是一个表示 `destinations` 数组的另一个 `SBValue`。让我们尝试使用 Python 模拟我们早期的格式化器，这次不硬编码最后一个元素的索引。

我们可以在 `destinations` 的 `SBValue` 上使用 `GetNumChildren` 来获取元素的数量。使用 `GetChildAtIndex`，我们可以访问第一个元素和最后一个元素。

注意，打印出的值是上下文相关的。它们包含数组中的索引。`SBValue` 实例维护其父级关系的上下文。

现在，我们可以将所有内容整合到一个字符串中。然而，结果并不完全是我们想要的，通过打印 `begin` 和 `end`，我们得到的是 `SBValue` 对象的描述。我们真正想要的是它们的摘要。我们可以使用 `GetSummary` 来检索格式化后的值并使用它。现在，结果只包含目的地字符串本身。让我们把一切整合起来。

格式化器可以直接在调试器控制台中定义，或者你可以使用一个文件并将其加载到 LLDB 中。在这种情况下，我们将创建一个名为 `Trip.py` 的文件。

当在一个文件中定义提供者时，而不是使用当前帧来访问我们想要显示的变量时，`SBValue` 会作为输入参数传递给一个函数。

实现的其余部分与我们之前所做的几乎相同。

使用 Python 定义格式化器的另一个优点是我们拥有控制流。如果这次旅行没有目的地，我们只需打印它是一个空旅行。

我们获取第一个和最后一个目的地的摘要并返回摘要字符串。

现在，我们需要将新的摘要提供者加载到 LLDB 中。这是使用 `command script import` 命令完成的。

接下来，我们需要指定我们新的格式化器是用于 `Trip` 类型的格式化器。使用 `type summary add`，并提供要格式化的类型和要使用的提供者函数。

在这里使用完全限定的类型非常重要。一切连接好后，`v` 现在使用 Python 摘要提供者来打印 `cruise` 对象。

摘要不仅会显示在控制台中，还会显示在 Xcode 的变量视图中。

我们已经讨论了过滤器和摘要。自定义类型显示的最终方式是使用合成子项（synthetic children）。

这使得自定义你的类型暴露什么样的子项成为可能，例如当你在 Xcode 的变量视图中展开类型时。

在 Python 中，每个子项都有一个 `SBValue`，并且每个子项都可以有自己的摘要。

定义你自己的合成子项提供者类似于定义摘要提供者。但你不是定义一个函数，而是定义一个实现特定方法的类。除了 `__init__`，你还需要提供一个方法来获取子项的总数、合成子项本身以及给定名称的索引。

本场会议的资源链接中提供了完整的示例。

和之前一样，使用 `command script import` 将 Python 源代码加载到 LLDB 中。在这种情况下，我们之前已经加载了这个文件，再次运行该命令将重新加载该文件。

要指定用于合成子项的格式化器，请使用 `type synthetic add`，并提供要格式化的类型和要使用的类。

在花了力气定义我们自己的自定义提供者之后，我们不想在调试会话结束时丢失它们。

你在控制台中输入的任何命令都可以持久化保存在你家目录下的 `.lldbinit` 文件中。

该文件在调试会话开始时自动加载。

LLDB 有多种功能可以帮助你在调试时查看程序的状态。根据你是只需要显示值、执行代码还是获取对象描述，分别使用 `v`、`p` 或 `po` 来打印变量。

使用过滤器、字符串摘要和合成子项来自定义或定义你自己的数据格式化器。最后，如果你有用 Python 2 编写的脚本，请更新它们以兼容 Python 3——从 Xcode 11 开始，LLDB 使用的版本。
