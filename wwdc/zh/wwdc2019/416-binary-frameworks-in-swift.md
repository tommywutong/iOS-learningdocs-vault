「Compiled module was created by a newer version of the compiler.」这个错误到底是什么意思呢？当 Swift 编译器要导入一个模块时，它会去找一个叫「已编译模块（Compiled Module）」的文件，找的就是这个库对应的那份文件。

如果它找到了这样一个文件，就会读取里面那份可供调用的公开 API 清单，让你使用它们。这种「已编译模块格式」是一种二进制格式，本质上包含的是编译器内部的数据结构。

而正因为它们只是内部数据结构，它们会随着 Swift 编译器的每一个版本而发生变化。

这意味着，如果有人试图用某个版本的 Swift 去导入一个模块，而这个模块是用另一个版本的 Swift 创建的，那么他的编译器就无法理解它，也就没法使用它。

为了解决这种版本锁定的问题，Xcode 11 引入了一种新的 Swift 模块格式，叫 Swift Module Interface（模块接口）。

对于那些你事后没法再改的东西，比如你类型的名字，一定要在一开始就仔细考虑清楚——这些名字不仅在这次发布里说得通，在未来所有的发布里也都要说得通。最后，不要过早添加可扩展性。你不需要在框架的第一个版本里就把你的类做成 open，也不需要提供任意的回调。

为什么这一点很重要？因为当你不得不同时考虑客户端可能在做什么的时候，去推理你框架的行为就会变得困难得多。

所以，你随时都可以在未来把你的类改成 open，随时都可以添加代表额外回调的属性，但你没法收回默认就赋予出去的那些灵活性。那这一切究竟是怎么运作的呢？答案是「间接层」。

这只是个词，我们来一步步过一个例子看看。左边同样是 Spaceship 类，不过这次只保留了它的 module interface，右边是对 fly 方法的一次使用。

这来自 FlightKit 框架之外的一段客户端代码。

而在运行时会发生的事情是：客户端得去问「哪个方法是 fly 方法？」，而框架会回答：是第二个。这就是 Swift 在你给一个类添加新方法时，依然能确保二进制兼容性的方式。

这基本上和 Objective-C 做消息派发的方式是一样的，只不过是在从一个库调用到另一个库的时候发生，而 Swift 只有在跨越这条「客户端-框架」边界时才会这样做。

这里还有另一种形式的间接层，那就是当客户端使用框架里定义的结构体或枚举的时候。

在这个例子里，fly 方法的其中一个参数，是 Speed 枚举里的那个 fast case。我之前说过，枚举可以添加新 case，而不会破坏二进制兼容性。

这意味着客户端不能假设自己知道这个枚举在内存里会有多大。

所以，使用这个枚举需要客户端去问框架：它有多大？框架回答：只有一个字节。

这里的另一种可能是，未来新加的某个 case 可能带有关联值。

而这些关联值可能需要某种清理工作。

所以客户端也会在用完这个枚举值之后，请求框架帮忙清理它，框架也会照做。这时候，在座的各位有些人可能已经开始有点坐立不安了，因为我们一直在讲客户端和框架之间的这些额外通信，那是因为你们有性能敏感型的框架，这也是为什么接下来这一部分要讲的是：用 Swift 给你的灵活性，去换取客户端的可优化性。

这确实是一种权衡。作为框架作者，我们希望拥有改动东西、添加东西、改进东西的灵活性，同时又不破坏源码兼容性或二进制兼容性。

但为了让编译器能把客户端代码做得尽可能快，它需要对框架里的内容做出一些假设。所以 Swift 需要能够同时应对这个光谱的两端。而实现这一点的方式，就是 Build Libraries for Distribution 这个构建设置。Harlan 之前说过，这个设置除了会生成 Module Interface 文件之外，还有多种效果，其中一个效果就是把默认值设定在「灵活性」这一端。

但同样地，Swift 需要能够处理所有这些使用场景，所以在这一部分，我要讲讲当你从外部对你框架的行为做了性能剖析、发现确实需要更好的性能之后，你可以做些什么。有三种方式可以做到这一点：可内联函数（inlinable function）、冻结枚举（frozen enum）和冻结结构体（frozen struct）。我们先从可内联函数讲起，这是去年在 Swift 4.2 中引入的一个特性。

在这个例子里，我有一个 CargoShip，它是我们之前看到的 Spaceship 类的子类，它有一个 canCarry 方法，用来判断这艘 CargoShip 能不能装载某件货物。

我把它标成了可内联的，因为我认为这对我客户端的性能很重要。

这样做的效果是，让这个方法成为我公开接口的一部分——不只是它的声明，还包括它的方法体。

而这样做的效果是：把这个方法体复制进了 Module Interface 文件里。如果你读得足够快，你还会看到这个方法引用了 CargoShip 类的一个内部属性。

这是可以做到的，因为我把那个属性标记成了「可从内联代码使用（usable from inline）」。

这能让你两头都占到便宜：这个属性作为你框架公开接口的一部分是可用的，但只对可内联的代码可用。它仍然不会被外部客户端随意读取或写入，它依然是 internal 的，只不过可以从内联代码里使用。

值得注意的是，这是一个按声明逐一决定的选择。这里那个同样是 internal 的 current cargo 属性就没有包含在 Module Interface 里。

好了，现在我们的 Module Interface 里有了 canCarry 方法的方法体。当客户端针对这份接口做编译时，他们就能把这个方法体直接复制进自己的代码里，甚至有可能——如果他们对正在检查的货物有所了解——做进一步的优化。但如果框架的所有者改变了这个方法的方法体，而客户端没有重新编译，那会发生什么呢？举个例子，如果新增了一条规则，说 CargoShip 不允许装载放射性货物，那会怎样？在这种情况下，我们就会遇到麻烦，因为现在程序里两个不同的部分，对这个方法应该做什么这件事持有不同的看法。

在某些输入上，它们仍然会一致——对于一些普通货物，客户端和框架都会说没问题。但如果我们试着检查放射性货物，客户端代码会说没问题，因为那是它编译时在 Module Interface 里看到的内容。

而框架用的是这个方法的新版本，会拒绝它。这可能意味着程序里存在一个严重的逻辑错误。

所以，作为一条经验法则：如果你是一个把某个函数标成可内联的框架作者，一定要确保不去改变它的输出或者可观察的行为。

添加一个更好的算法，或者一些额外的快速路径，是可以的；但如果你改变了这个函数可观察的行为，那你就可能遇到这种极其微妙、只有在运行时才能看出来、甚至可能只在某些特定输入下才会出现的问题。如果你确实需要这样做，那就得让所有客户端重新编译。接下来我想聊聊枚举。

Swift 的枚举很棒，我很喜欢它们。我们这里提到过一点：你可以给一个枚举添加新 case，而不破坏源码兼容性或二进制兼容性。

这对客户端意味着，他们在对这个枚举做 switch 的时候，必须始终有一个 default case。而在这段客户端代码里，他们选择使用 Swift 4.2 里同样引入的「unknown default」语法。这意味着，他们已经处理了这个枚举里所有已知的 case，但仍然会处理未来可能新增的任何 case，这在对 C 枚举、以及二进制框架里构建的枚举做 switch 时都是必要的。这样做的另一个效果，就是我之前提到过的那种客户端和框架之间的「握手」——关于这个枚举有多大、是否需要清理。但我这里选的例子是一个 Flight Plan（飞行计划）。实际上只能有单程航班或者往返航班。

所以，把这个枚举标上 frozen 特性，我作为框架作者就可以承诺：框架未来的发布版本里不会再添加新的 case。

这样做的第一个效果是，客户端不再需要写那个 default case 了，可以直接省略掉。

其次，编译器就能更高效地编译它。客户端可以假设这个枚举不会再有额外的 case，也不需要任何清理工作。

这非常棒。

只可惜我忘了一件事：还有另一种 Flight Plan，一种多程中转航班。

现在我们就麻烦了，因为那段客户端代码已经没有 default case 了，所以给一个冻结枚举添加新 case，会同时破坏源码兼容性和二进制兼容性，需要递增 Major 版本号，并要求所有客户端重新编译。好了，讲完冻结枚举之后，冻结结构体也大同小异。默认情况下，二进制框架里的一个结构体可以毫无问题地添加新的存储属性，或者重新排列已有的属性，但这同样会导致客户端和框架之间那种「握手」和额外的通信。所以，为了避免这一点，对于那些已知会保持冻结布局的结构体，可以使用 frozen 特性来承诺：它的存储属性不会改变，不会被添加、重新排序或移除。这样做的另一个效果是，要求所有的存储属性的类型都是 public 的，或者是可从内联代码使用的。因为记住我们这里的目标是：我们希望编译器在处理客户端代码时，能够直接操作这个结构体的存储属性，从而在客户端这一侧生成更高效的代码。

这还有一个语义上的效果，那就是框架作者现在可以写可内联的初始化方法了。一个初始化方法本来就必须设置好结构体里所有的存储属性，但现在编译器可以确信，未来版本的框架也会同样这样做。好了，在结束这一部分之前，我想提醒大家：默认采用「灵活性」是有原因的。其中最主要的原因是，破坏性改动对客户端来说真的很不方便。

客户端会不得不重新斟酌，到底要不要采用你框架的新版本，因为这可能会以某种方式破坏他们的代码。而且当一个二进制框架依赖另一个二进制框架时，你还可能陷入麻烦。

同样值得提醒的是，这些特性只影响客户端代码。在你自己的框架内部，你依然能获得编译器优化的全部威力。

所以，在选择使用 frozen 或者 inlinable 之前，一定要先从外部对你框架的行为做过性能剖析，并证明你确实需要额外的性能。否则的话，就保留那份灵活性，因为你可能会需要它。

现在，我想讲的最后一部分，是确保你的客户端能获得尽可能好的体验。这部分内容会和这场演讲前半部分 Harlan 讲的很多内容相呼应。我们先从「权限（Entitlements）」讲起。

如果你的框架需要某些权限才能完成它的工作，那我们先从基本的事情说起：一定要把它们记录在文档里，这样任何潜在的客户端都能知道，要成功采用你的框架，他们需要做些什么。而且，尽量把你这个框架所要求的权限降到最低，因为这意味着它能适用于更多的场景，你也能获得更多使用你框架的客户端。最后，要记住，虽然框架和应用都可以向用户请求权限，但最终是否授予，取决于用户自己的选择。

所以，如果某个特定权限被拒绝了，一定要确保你的框架能优雅地处理这种拒绝。它不应该导致 App 崩溃，也不应该停止工作，要确保它仍然能做一些有用的事情，这样你的客户端就能继续使用这个框架，而不必放弃。

现在，「依赖」和「权限」有很多相似的顾虑，因为就像权限一样，你框架的依赖会变成应用的依赖。

所以同样地，你应该首先把它们记录在文档里，这样潜在的客户端就能知道自己在接受些什么。而且你应该尽量减少你的依赖，这样你对客户端的要求就会更少——不管是在信任的延伸方面，还是在一些实际的事情上，比如你的依赖占用的代码体积。

最后，你所有的依赖都必须用 Build Libraries for Distribution 这个构建设置来构建，才能获得我们前面讲的那种二进制兼容性保证。这就带来了一个特定的结论：二进制框架不能依赖于 Package。

我们来看一张依赖关系图。

我几分钟前说过，框架的依赖会变成 App 的依赖。但当一个 App 构建一个 Package 的时候，它必须为此选定一个特定的 tag。

而那个 tag 可能和你构建框架时所用的版本对不上，甚至可能完全不兼容。

而且，不光如此，也不是所有框架都一定能以一种和 Build Libraries for Distribution 兼容的模式构建出来。

所以这种配置是不受支持的。现在，我想讲的最后一件事是你的 Objective-C 接口。是的，各位 Swift 框架作者，你们很可能都有一个 Objective-C 接口，因为 Xcode 的默认模板就是为一种混合源码框架设置的，它同时带有一个 Objective-C 的总头文件（Umbrella Header），以及一个包含你框架里 Swift 部分对应 Objective-C 内容的生成头文件。但如果你的 Swift 代码根本没有想要发布的 Objective-C API，那你完全不需要安装那第二个头文件。有一个叫 Install Objective-C Compatibility Header 的构建设置，你可以直接关掉它。而如果你的框架不对外提供任何 Objective-C API，那也就没有理由支持这种 Objective-C 导入语法了，你同样可以通过 Defines Module 这个构建设置把它关掉。把它设为 No，这样它就不再是有效的 Objective-C 代码了。

做完这些之后，你就可以把 Xcode 替你生成的那个总头文件删掉了。

好了，我们来做个总结。今天我们聊了很多内容，但其中最重要的是 XCFrameworks。它是一种新的 bundle 格式，用来以一种让你的用户超级容易使用的方式，分发框架的多个变体。

要构建一个 XCFramework，你需要打开 Build Libraries for Distribution 这个构建设置，它会激活你需要的一切，从而得到一个正确的、二进制兼容的框架。作为框架的所有者，一定要清楚你对客户端所肩负的责任，这样你才能把服务做到最好。这场演讲结束后，Harlan 和我马上就会去实验室，但对所有来到这里的各位，非常感谢大家，让我们一起做出一些出色的框架吧。[ 掌声与欢呼 ]
