在自定义 Instruments 架构中，建模是由中间这个称为 modeler 的组件完成的。Modeler 的工作本质上是对操作系统记录的原始事件进行分析，执行一些转换，并为 Instruments UI 中的 Instruments 生成可显示的事件或作为另一个 modeler 的输入。

这个架构在 2018 年的 session《创建自定义 Instruments》中已经完整介绍过。因此，本次 session 将聚焦于中间这个称为 modeler 的组件。

Modeler 对我们所有的 Instruments 都很重要，包括这里的 Time Profiler。

在 Time Profiler 中，你在 UI 中看到的数据与内核记录的数据并不完全相同。

我们使用 modeler 进行一些转换。

当内核对你的线程（thread）当前执行内容进行采样时，它会创建或捕获一个所谓的原始 backtrace，并将其放入时间采样表中。然后，Time Profiler modeler 会拾取它，将其转换为更易于显示形式的 backtrace，并放入 Time Profiler 表中，最终由 Time Profiler instrument 查看。我们这样做是因为捕获这些原始 backtrace 更简单、更高效。之后，我们可以在 modeler 内部的用户空间中对它们进行修复，从而使内核一侧的记录保持非常高效。

内核进行的另一种优化是，如果内核采样了一个它知道自上次采样以来没有移动过的线程（thread），就不会获取完整的 backtrace，而只是将一个占位 backtrace 放入时间采样表中。然后，我们的 Time Profiler modeler 会拾取它，获取该线程（thread）最后已知的 backtrace，并将其复制到 Instrument 查看的 Time Profile 表中。

这样做有两个好处。它节省了内核记录缓冲区的大量空间，尤其是在你的线程（thread）大部分处于空闲状态时。同时，它也使 UI 保持高效，因为 UI 不需要知道这个占位约定——这些都已经由我们的 modeler 归一化了。

因此，在今天的 session 中，你会看到这些主题重复出现。本质上就是，将自定义 instrument 的复杂性吸收到建模层中。这将简化其他方面，特别是在你的逻辑中嵌入的追踪代码以及 Instruments 中使用的 UI。今天的 session 结构如下。我们将复习一些建模基础知识，然后带你了解构建自定义 modeler 的过程。

在 CLIPS 中定义规则时，规则由左侧和右侧通过一个产出操作符分隔。左侧实际上是语言的声明式部分。这是你定义模式的地方，你希望规则引擎在工作内存的事实（fact）中找到该模式。

当规则引擎识别出一组满足左侧模式的事实（fact）时，它会创建一个所谓的激活（activation）。对于每个激活（activation），它会触发规则的右侧。规则的右侧实际上是语言的命令式部分。在这里，你可以访问诸如 retract 之类的函数，它允许你从工作内存中移除一个事实（fact）。

或者 assert，它允许你向工作内存中添加一个事实（fact）。

还有一些专门的函数，允许你写入 modeler 的输出表，以便写入输出。

现在，让我们谈谈事实（fact）。当我们使用 assert 函数向工作内存中断言一个事实（fact）时，每个新事实（fact）都会被分配一个所谓的事实地址（fact address），它们用小写的 f 加连字符再加一些唯一数字来标识。

当我们想要修改工作内存中的一个事实（fact）时，我们还有一个 modify 函数，它接受事实地址（fact address）和我们要在该工作内存片段上更改的槽。

这实际上是通过 retraction 和 assertion 的组合实现的。所以这里发生的是，我们首先从工作内存中收回该事实（fact），进行更改，然后用更新后的字段或槽将其重新断言回工作内存。

这很重要，因为当你将某些内容重新断言回工作内存时，它会重新触发并可能重新激活某些规则，这在大多数情况下正是你想要的，因为你的规则系统会对你正在对工作内存所做的更改做出反应。

然而，在某些情况下，这会导致我称之为逻辑循环的复杂情况。那么，让我们看看我们是如何在代码中意外创建逻辑循环的。这里有一个非常小的规则。它的设计目的是计算工作内存中出现的移动代理（agent）实例的数量。

它从一个 counter 事实（fact）开始，其 count 槽初始为零。

对于放入工作内存的每个移动代理（agent），它将触发规则的右侧，该侧简单地修改 counter，将 count 槽增加 1。这听起来很简单。

然而，让我们看看它实际执行时的情况。

首先，我们在工作内存中有一个 counter，初始计数为零。

假设在将来的某个时刻，一个移动代理（agent）被断言到工作内存中。现在我们在左侧有足够的信息来触发右侧。因此，它会调用我们的 modify 函数，该函数首先会收回那个事实（fact）。

它会通过增加计数值来修改，然后将其重新断言回工作内存。当我们这样做时，请注意，它重新触发了同一个规则。

因此，对于同一个移动代理（agent）实例，它会计数：2、3、4、5、6、7，对吧？它会一直继续下去，直到最终追踪停止，Instruments 告诉你这是一个致命错误，规则引擎似乎卡住了。

在你 modeler 控制台的 Instruments 检查器中，你会看到 trace，其中显示了在该循环期间发生的所有事件和激活（activation）。这将为你调试并解决它提供一个良好的开端。根据我的经验，摆脱逻辑循环的最简单方法是做一点我称之为目标导向的编程。

因此，我们不是直接修改 counter 事实（fact），而是创建一个 goal 事实（fact）来为我们增加计数。这次，当我们检测到一个移动代理（agent）实例时，我们断言一个 goal 事实（fact）来计数该实例。然后，在我们的计数规则中，我们捕获 counter 和 goal，并收回 goal，因为现在当我们增加计数器时，它已经被满足了。这将阻止该规则再次回来，这样我们就打破了那个逻辑循环。

好的，现在让我们谈谈规则的触发顺序，以及这如何可能改变我们 modeler 的输出。

让我们回到 executeStop 函数。这是在移动代理（agent）进入其执行阶段之前调用的。现在你会注意到，在我们的 OS Signpost 中，在我们代码的第一个版本中，第一个参数实际上是我们使用了代理（agent）的类型字符串。

在这种情况下，它将是 sorting agent 或大约 14 字节的数据，必须记录到追踪缓冲区中。我们认为可以通过将其从字符串改为类型代码来改进这一点。这只是一个 4 字节的整数，将为每个事件节省大约 10 字节。如果这些事件成千上万地出现（确实如此），那么在追踪缓冲区中将节省成千上万的字节。

为了做到这一点，我们必须在 modeler 内部创建一些映射，将该代码转换为字符串，因此我们将使用事实（fact）来实现。

这一次，在我们的检测规则中，我们将捕获代理（agent）的类型代码，并且当我们断言我们的移动代理（agent）时，我们将使用一个种类槽（kind slot）为 sentinel 符号来断言它。它将指示我们尚未设置完整的字符串。

因为在第二个规则中，我们要查找任何种类为 sentinel 的移动代理（agent），并且我们要找到对应类型代码的类型字符串映射，就像你在上一张幻灯片中看到的那样。一旦我们有了这两部分，我们将修改种类槽，将其从 sentinel 符号更改为真正的字符串。

整个设计在很大程度上依赖于这第二个查找规则，在我们执行断言后立即触发。

但是，如果系统中的另一个规则，例如我们的 agent parked 规则，它也引用了移动代理（agent）并捕获和使用了种类槽，那该怎么办？如果它恰好在断言和查找规则之间插入进来呢？那么，它将看到一种 sentinel。由于这是我们正在对规则系统进行的更改，它可能还没有为此做好准备。我们现在会遇到全新的一组错误。

解决这个问题的一种方法是向该规则添加一个限制，规定只要种类不等于 sentinel，这就能有效地延迟该规则的触发，直到查找规则将代理（agent）的种类从 sentinel 更改为真正的值。你当然可以这样做，但你必须对所有规则都这样做。如果你已经有一个假设种类永远不会是 sentinel 的现有规则集，那么这可能会成为一个维护问题。

那么，让我们看看另一种替代方法。实际上，我们想要做的是让查找规则在我们执行断言后立即触发。实现这一点的一种方法是告诉 CLIPS，该特定规则比默认的零显著度（salience）更重要或更具显著度。

只要该规则是系统中最具显著度的规则，一旦我们的第一个规则完成，第二个规则就会被触发。如果你在其他地方使用了显著度（salience），你将需要检查你的代码以确保 100 仍然是最高显著度值，但这是确保这一点的一种方法。还有一种更直接的方法来控制规则排序和规则触发，但这需要我们更多地了解激活（activation）。

提醒一下，激活（activation）本质上是工作内存中满足我们模式左侧的事实（fact）的组合。对于每个激活（activation），我们触发规则的右侧。

我们不会立即触发规则的右侧。相反，我们会将激活（activation）记录到一个称为议程（agenda）的数据结构中。

议程（agenda）基本上是一个由工作内存更新产生的激活（activation）列表。规则引擎需要做的就是从这个列表的顶部开始，依次向下处理，以该特定模式触发规则。这里我们触发了第一个规则，现在来到第二个规则。这个数据结构是动态的，所以如果这里的规则 99 收回了事实（fact）17，而事实（fact）17 被另外两个激活（activation）引用，CLIPS 会首先收回这些激活（activation），然后再继续执行，因此当执行恢复时，议程（agenda）看起来会是这样。议程（agenda）按显著度（salience）排序，这就是显著度发挥作用的地方。显著度越高，它在议程（agenda）上的位置就越高。

但这里更重要的部分是，你的 modeler 上并非只有一个议程（agenda）。实际上，每个定义的模块都有一个议程（agenda）。我们通过在分析核心中为你定义几个标准模块来利用这一点。

第一个是 modeler 模块，你应该在这个模块中放置你的纯推理逻辑和推理规则，方法是在规则名称前加上 `modeler::`。我们定义了第二个模块，称为 recorder 模块，你应该在这个模块中放置你的输出写入规则，方法是在规则名称前加上 `recorder::`。你这样做的原因是，当我们执行这些规则时，我们会先执行 modeler 议程（agenda）上的所有内容，直到它完全为空，然后再转到 recorder 模块。这让你有信心，当你在执行输出写入规则时，你不会看到工作内存正在被 modeler 模块推理。

你可以通过自己在 CLIPS 中定义自定义模块来利用这一点。那么，让我们看看如何通过这样做来更好地调整我们的查找规则执行。首先，我们要做的是为我们的查找模块定义模块。

然后，我们通过在其前面加上 `lookup::` 将我们的查找规则放在该模块内部。

当我们断言一个移动代理（agent）事实（fact）时，我们紧接着要做的就是告诉 CLIPS 将焦点（focus）放在查找议程（agenda）上。基本上，在返回 modeler 的议程（agenda）并因此执行下一组建模规则之前，先运行查找议程（agenda）中的所有激活（activation）。所以，这是一种在执行的顺序中插入规则的好方法。

你好。谢谢你，Alejandro。好的，要描述 Alejandro 看到的这种现象（或解决它），我们必须引入一个称为推测（speculation）的概念。那些区间（interval）发生了什么？它们与众不同的原因首先是它们很长。它们延伸超过几秒钟，所以更明显，更可见。

但其次，真正的问题是这些区间（interval）存在的唯一记录就在你 modeler 的工作内存中。而你的 UI 实际上正在查看 modeler 的输出表，所以它看不到它们。在我们知道它们何时关闭之前，我们无法真正将这些区间（interval）写入输出表。这就是你在那个特定情况下看到的现象。

我们真正想要的是能够将临时或占位行写入 modeler 的输出表中。为此，我们引入了一个称为推测模式（Speculation mode）的概念。

推测模式（Speculation mode）在你的 modeler 中表示：如果这是你最后一次机会写入输出表，你现在会写入什么？让我们看一个例子。

所有数据都被处理到这条白线这里，我们称之为事件视界（event horizon）。事件视界（event horizon）是一个时间点，超过这个点 modeler 就不可见了。这可能是因为追踪刚刚结束，或者可能是因为分析核心尚未填充追踪的那一部分。因此，它不知道那条线另一边的情况。你看到我们已经创建了一个表示“移动到后台”的区间（interval）。我们能这样做是因为它恰好被一个移动和一个执行 Signpost 对很好地框住了。

但我们不知道那个后续执行区间（interval）到底会在哪里结束，因为它的结束事件在事件视界（event horizon）的另一边。所以，我们想要做的是，当进入推测模式时，只是将一个临时的占位事件写入表中，这样 UI 就能看到一些东西，我们将从执行 Signpost 开始，到事件视界（event horizon）的当前值结束，来粗略地表示那个区间（interval）。

你知道你的 modeler 处于推测模式（Speculation mode），因为你会得到一个被注入工作内存的 Speculate 事实（fact）。

在你的 recorder 规则中，你可以将该 Speculate 事实（fact）与任何区间事实（fact）结合起来，将这些开放的区间（interval）连同捕获到的事件视界（event horizon）时间戳一起写入表中。这就是你写入开放区间（interval）的机会。

那么，让我们看看一个我们可以在这里定义的示例规则。

首先，我们将把推测性输出写入规则放在 recorder 模块中。所以，在其前面加上 `recorder::`。

接下来，我们将匹配 Speculate 事件，捕获事件视界（event horizon）的值。这样我们就有了区间（interval）的结束时间，我们的理论结束时间。

然后，对于工作内存中的每个开放区间事实（fact），我们将触发规则的右侧。

我们要做的是，根据结束时间（即事件视界（event horizon））和开始时间（即区间（interval）开始的时间）计算持续时间。

然后创建一个新行并填充列，就像在正常的输出写入规则中一样。正常的输出写入规则和推测性输出写入规则之间唯一的区别是，你在 Speculate 事实（fact）上测试或断言这条规则，并且你查看的是开放区间（interval），而不是你通常写入输出表的已关闭区间（interval）。

当处于即时模式时，随着记录头向前移动，旧的推测数据会被清除，你的 modeler 会再次以新的事件视界（event horizon）值进入推测模式（Speculation mode），并且你能够重新放置那些推测事件。UI 会像往常一样继续更新。

当追踪停止时，你的 modeler 将再进入一次推测模式（Speculation mode）。但是你现在写入的任何内容都会被实际记录并保存在真实的追踪数据中，并且可供下游的 modeler 使用，而不仅仅是 UI。如果我们对我们现有的 Instrument 进行这样的更改，它将像这样工作：现在有了我们的移动代理（agent）追踪，你会看到这个停放区间（interval）在末尾继续增长。它会实时更新。如果你在底部的详情表中查看，你会看到持续时间在继续增长。

当我们按下停止并结束录制时，你会注意到这个区间（interval）保留了下来。它实际上已被记录并保存为追踪的一部分。
