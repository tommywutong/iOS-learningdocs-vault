大家好。谢谢。我叫 Tony Parker，是 Apple Foundation 团队的负责人。今天我非常荣幸能向大家介绍我们最新的框架。它叫 Combine。

我们来聊聊异步编程。

这里有一个我正在开发的 App，让学生报名我的全新魔法学校。可以看到，它的需求相当简单。

首先，我们需要一个有效的用户名，我们会通过网络请求到服务器来校验。当然我们还需要两次输入的密码匹配，这可以在 App 内本地检查。

而在做这一切的同时，我们当然需要保持用户界面响应灵敏，不能阻塞主线程。我们来试用一下，看看它如何工作。

首先，我开始输入用户名，比如……梅林怎么样？听起来是个很不错的巫师名字。此时已经有许多异步行为在发生了。我用 Target/Action 监听用户输入的通知；我用一个定时器等待用户停止输入片刻，以免网络请求把服务器压垮；最后，我用类似 KVO 的东西监听那个异步操作的进度更新。继续操作后，我们会收到那个请求的响应，还得更新 UI。于是我选了一个新用户名，然后输入我超级机密的密码 12345。请别用这个密码，仅作演示。

而现在我们又做了多得多的异步工作：我们要等 URL session 请求的响应；要把那个结果与同步校验的结果合并；最后，等这一切都完成之后，我还得用类似 KVC 的东西再次更新 UI。

在整个 Cocoa SDK 中你会发现大量异步接口。有些你刚才看到了，比如 Target/Action，但还有更多，包括 NotificationCenter 和大量临时性的回调——也就是接受闭包或完成处理程序块的 API。它们都有各自重要的使用场景。但当你需要把它们组合在一起时，有时会颇具挑战。

所以做 Combine 时，我们并不是要取代所有这些，而是要找出它们的共性。

这就是 Combine：一个处理随时间变化的值的统一声明式 API。Combine 用 Swift 编写，也为 Swift 而写。这意味着我们可以利用泛型等 Swift 特性。泛型让我们减少需要编写的样板代码。这也意味着我们可以把关于异步行为的泛型算法只写一次，就让它们适用于各种不同的异步接口。

Combine 还是类型安全的，让我们能在编译期而非运行期捕获错误。Combine 的主要设计原则是“组合优先”。也就是说，核心概念简单易懂，但把它们组合起来，你就能造出大于各部分之和的东西。

最后，Combine 是请求驱动的，让你有机会更细致地管理你 App 的内存使用和性能。

我们来谈谈那些关键概念。只有三个：发布者（Publisher）、订阅者（Subscriber）和运算符（Operator）。我们依次介绍。首先是发布者。

发布者是 Combine API 中声明式的部分。

它们描述值和错误如何产生，而它们本身未必是实际产生这些东西的东西。

这意味着作为描述，它们是值类型——在 Swift 里就是结构体。

发布者也允许注册订阅者；订阅者是随时间接收这些值的东西。

这是协议，叫 Publisher。它有两个关联类型：Output，即它产生的值的类型；Failure，即它产生的错误的类型。如果一个发布者不可能产生错误，你可以把那个关联类型设为 Never。

Publisher 有一个关键函数，叫 subscribe。从这个函数的泛型约束可以看出，subscribe 要求订阅者的 Input 与发布者的 Output 匹配，订阅者的 Failure 与发布者的 Failure 匹配。这是一个发布者的例子。这是我们为 NotificationCenter 新增的发布者。

可以看到，它是一个结构体，Output 类型是 Notification，Failure 类型是 Never。

它用三样东西初始化：哪个中心、哪个名称、哪个对象。如果你熟悉现有的 NotificationCenter API，它们看起来会非常眼熟。所以再说一次，我们不是在取代 NotificationCenter，只是在适配它。接下来是订阅者。

订阅者是发布者的对应物。它们是接收值的东西——如果发布者是有限的，还包括接收完成。

因为订阅者通常在收到值时会执行动作并修改状态，我们在 Swift 中使用引用类型，也就是类。

这是 Subscriber 协议。可以看到，它有同样的两个关联类型：Input 和 Failure。同样，如果订阅者无法接收失败，可以用 Never 类型。

还有三个关键函数。它可以接收一个订阅（subscription）。订阅是订阅者控制数据从发布者流向订阅者的方式。

它当然也可以接收输入（Input）。最后，如果它连接的发布者是有限的，它可以接收一个 Completion，它要么是 Finished，要么是 Failure。这里是一个订阅者的例子。

这个叫 Assign。

Assign 是一个类，用一个类的实例、一个对象的实例，以及一个指向该对象的类型安全键路径来初始化。

它做的事是：收到输入时，把输入写到那个对象的那个属性上。因为在 Swift 中，单纯写属性值时没办法处理错误，所以把 Assign 的失败类型设为 Never。我们来看看它们如何拼在一起。

假设你有某种控制器对象或其他持有你订阅者的类型，它负责对发布者调用 subscribe，把订阅者挂接上去。

此时，发布者会向订阅者发送一个订阅，订阅者会用它向发布者请求一定数量或无限数量的值。此时，发布者就可以向订阅者发送该数量的值或更少。同样，如果发布者是有限的，它最终会发送一个 Completion 或一个 Error。

所以再说一遍：一个订阅，零个或多个值，和一个 Completion。回到我们的例子：假设我有一个叫 Wizard 的模型对象，今天我关心的只是这位巫师在几年级。从 Merlin 开始，他现在读五年级。我想做的是监听关于我的学生毕业的通知，一旦他们毕业，我想更新我的模型对象的值。

所以我从默认中心上关于 Merlin 毕业的 NotificationCenter 发布者开始。

接着，我创建一个 Assign 订阅者，告诉它把新年级写入 Merlin 的 grade 属性。

接下来，我可以用 subscribe 把它们连接起来。然而，正如你所料，这无法编译。原因在于类型不匹配。

NotificationCenter 产生通知，而配置为写入整数属性的 Assign 期望整数。

所以我们需要一个中间的东西来在通知和整数之间转换。那就是运算符（Operator）。

运算符也是发布者——它们同样遵循 Publisher 协议。它们同样是声明式的，因此是值类型。它们描述的是一种改变值、添加值、移除值或其他各种行为。

它们订阅另一个发布者（我们称之为上游 upstream），并把结果发给一个订阅者（我们称之为下游 downstream）。这是一个运算符的例子。这个你用 Combine 时会非常熟悉，叫 Map。

Map 是一个结构体，用它连接的上游，以及如何把上游的输出转换成它自己的输出的方式来初始化。

因为 Map 自身不产生失败，它只是镜像上游的失败类型，原样传递。

有了 Map，我们就有了在通知和整数之间转换的工具。

看看怎么做。

保持之前的发布者和订阅者不变，我加上这个转换器。可以看到它被配置为连接到 graduationPublisher，并带有一个闭包。该闭包接收一个通知，查找名为 NewGrade 的 user info 键。

如果存在且是整数，就从闭包返回它。如果不存在或不是整数，就使用默认值零。这意味着无论怎样，闭包的结果都是一个整数，因此我可以把它连接到订阅者。一切连接成功、编译通过、正常工作。

所有这些构造语法可能有点啰嗦，所以我们还有更流畅的语法。它的工作方式是：作为 Publisher 协议的扩展——也就是对所有发布者可用——我们为每个运算符添加了一系列以运算符命名的函数。这是 Map 对应的那个。

可以看到，它的参数是初始化一个 Map 所需的一切，除了上游。原因在于：作为 Publisher 的扩展，我们可以直接用 self。

这看似只是一个小便利，但实际上，它才是真正改变你在 App 中思考异步编程方式的东西。

回到我们的例子，改用新语法。这里我从监听 Merlin 毕业事件的 NotificationCenter 发布者开始。

收到通知后，我用之前看到的同一个闭包对它做 map，然后把它赋值给 Merlin 的 grade 属性。

你可以看到，这种语法提供了一个非常线性、易于理解的一步步流程。

Assign 返回一个叫 cancelable 的东西。取消（cancelation）同样内置于 Combine。取消让你可以在需要时提前拆除发布者和订阅者的序列。

这种逐步语法正是你使用 Combine 的核心。每一步都描述链条中的下一组指令：值从第一个发布者出发，经过一系列运算符的变换，最终抵达一个订阅者。我们有大量这样的运算符，我们称之为声明式运算符 API。

它们包括像 Map 这样的函数式变换。我们还有 Filter 和 Reduce，以及列表式操作，比如取发布者的第一个、第二个或第五个元素。

还有错误处理，比如把错误转换为默认值或占位值。线程或 QoS 迁移，例如把繁重的处理工作移到后台线程，或把 UI 工作移到主线程。还有调度与时间，包括与 RunLoop 的集成、派发队列、对定时器、超时等的支持。

运算符这么多，想想如何在其中穿行也许有点让人不知所措。所以我鼓励你回到 Combine 的核心设计原则——组合。

与其提供少数功能繁多的运算符，我们提供了大量各自只做一点事情的运算符，让它们更易于理解。

为了帮助你在这些运算符中穿行，我们从现有的 Swift 集合 API 中汲取了命名的灵感。

方法是这样的。

想象一个象限图。一边是同步 API，另一边是异步；上面是单个值，下面是多个值。

在 Swift 中，如果你需要同步地表示一个整数，你可能用 int 之类的东西。如果你需要同步地表示许多整数，你会用整数数组之类的东西。

在 Combine 中，我们把这些概念映射到了异步世界。所以如果你需要异步地表示单个值——它稍后才会到达——我们有 future。如果你需要异步地表示多个值，那就是 Publisher。

这意味着：如果你在找某种操作，而且你已经知道如何用数组做，那就试着在 Publisher 上用那个名字。

我能做的一件事是让这个闭包返回 nil，然后把 nil 值过滤掉。

我们再用几个熟悉的名字来搭建逐步指令。

比如说，只有五年级以上的学生才被允许进入我的学校。我可以用 Filter 做到。Filter 接受一个谓词，只让通过谓词的元素继续。这与 Array 上的 Filter 行为完全一致。

再比如说，你最多只允许毕业三次。

在 Array 上，如果你需要取前三个元素，可以用 prefix 3。在 Publisher 上，如果你只想接收前三个元素，可以用 prefix(3)。它做的事是：收到三个值之后，它会取消上游，并向下游发送一个 Completion。回头看看我们这里有什么：我们有一个监听 Merlin 毕业事件的 NotificationCenter 发布者。

一旦他毕业，我们就从那条通知里取出 NewGrade。然后我们确认该值大于五年级、且毕业次数最多不超过三次，最后才把它赋给 Merlin 的 grade 属性。

Map 和 Filter 是很棒的 API，但它们主要面向同步行为。当你在异步世界里工作时，Combine 才真正大放异彩。

这里还有两个运算符要介绍，它们在这方面非常有用。第一个是 Zip。

比如说在我的 App 里，在允许用户继续之前，他们需要等待他们的魔杖被制造完成——这是三个长耗时的异步操作，像这样。

Continue 按钮要等这三件事都完成才启用。这正是 Zip 的用武之地。

Zip 把多个上游输入转换成一个元组。

由于它要求所有上游都有输入才能继续，它本质上是一种“当……且……”操作，也就是：当这个、这个和这个都完成时，就做那件事。

例如，我的第一个发布者产生了 A，然后当我的第二个发布者产生 1 时，我现在就有足够的信息创建一个元组，并把该值向下游发给我的订阅者。

在我的 App 里，我使用接受三个上游的 Zip 版本，等待三个各自给我布尔结果的异步操作。然后我把元组映射成一个布尔值，在这里我把它写进按钮的 isEnabled 属性来启用它。

在魔杖制作完成之后，和其他所有人一样，我的学生必须同意一组条款和条件，才被允许开始玩他们的魔杖。这意味着所有三个开关都必须打开，Play 按钮才会启用。然而，如果之后其中一个被关掉，我们需要禁用按钮。这是 CombineLatest 的用武之地。

与 Zip 一样，它把多个上游输入转换成单个值。但与 Zip 不同的是，它只要求任何一个上游有输入即可继续，本质上是一种“当……或……”操作。

为了支持这一点，它会存储从每个上游收到的最近一个值。它还配置了一个闭包，让你把这些值转换成一个向下游发送的值。

例如，当我的第一个发布者产生 A，而我的第二个发布者产生 A1 时，我运行闭包，把它们拼成字符串并向下游发送。之后，当第二个发布者产生新值时，我可以把它与之前从第一个发布者拿到的值组合，把新值往下发。

这意味着任何上游一变化，我就会收到新事件。

在我的示例 App 里，我使用了一个接受三个上游的 CombineLatest 版本：那三个开关的布尔状态随它们变化，我把它们再次转换成一个布尔值，并写到 Play 按钮的 isEnabled 属性上。

这意味着只要有一个是 false，结果就是 false；而如果全部为 true，结果就是 true，从而启用按钮。我们把 Combine 设计成可以在你的 App 中渐进采用的。你不必把所有东西都转换过来。作为入门，我有几个建议，指出你今天的 App 里可能用得上 Combine 的地方。例如，如果你用 NotificationCenter，收到通知后要查看内部再决定是否行动，试试 Filter。如果你要等待多个异步操作的结果，可以用 Zip，包括网络操作。

最后，如果你用 URL Session 接收一些数据，然后用 JSON Decoder 把数据转换成自己的对象，我们也有一个运算符可以帮忙，叫 Decode。

今天我们过了一遍基础：发布者、订阅者和运算符。不过 Combine 还有更多内容，包括错误处理与取消、调度器与时间，以及一些很棒的设计模式，比如在不同模块之间或 App 的不同区域之间使用 Combine。当然还有与 SwiftUI 的集成。要了解更多，请观看《Combine 实践》。
