大家好，我是 Kai Kaahaaina，今天我将和 Alejandro Lucena 一起讨论如何优化 App 的存储。就像 CPU 内存一样，存储也是一种有限的资源。

当 App 对存储的利用达到最优时，我们能更好地确保更长的电池续航、更好的性能、更小的 App 占用，以及良好的设备健康状况。

我们今天的主要优化主题包括：高效的图像资源、同步到磁盘、序列化数据文件、Core Data 与 SQLite。首先从高效的图像资源说起。随着屏幕尺寸越来越大，图像资源的大小也相应增长。

为了本次讲座，我们制作了一个非常简单的演示 App，用于编目和收藏照片。然而，即使只预装了几张照片，我们的 App 大小也已经达到 24.6 兆字节。

接下来我们将讨论两种可以减小 App 大小的方法。

第一种是 HEIC。HEIC，有时也称为 HEIF，是 JPEG 的一种更高效、更强大的替代方案。HEIC 在与 JPEG 相当的质量下提供小 50% 的文件，这当然意味着更小的磁盘占用，而且更小的文件可以更轻松地在网络上上传下载。它们也可以更快地加载和保存到磁盘。HEIC 还提供了 JPEG 所不具备的许多功能，例如存储包含深度和视差信息的辅助图像。

HEIC 还支持 alpha 和无损压缩。HEIC 甚至允许你在单个容器中存储多张图像。

iOS 自 iOS 11 起支持 HEIC，macOS 自 macOS High Sierra 起支持 HEIC。

它在其他操作系统中也可用。

回到我们的演示 App，我们起初使用 JPEG 资源，磁盘占用为 24.6 兆字节。仅仅通过采用 HEIC 而非 JPEG，我们就将这个 App 的大小减小到了 17.9 兆字节。仅通过采用 HEIC 就实现了 27% 的缩减。

我们可以减小 App 占用的另一种方式是使用资源目录（Asset Catalogs）。资源目录是组织 App 资源的绝佳方式。包括 App 图标以及图像的设备与缩放变体。资源目录提供了一种非常便捷的方式来存储同一图像的多种分辨率，从而非常容易地支持各种设备。

我们还可以使用资源目录标记按需资源，这样用户直到准备使用时才需要下载它们。

通过使用资源目录，我们既能获得存储优势，也能获得性能优势。首先，我们可以减小磁盘占用，因为资源目录将所有图像资源存储在单一的优化格式中，而非单独的文件。App Store 还会使用你资源目录中的元数据来帮助支持 iOS App 的 App 切片（app slicing）。

这样，当顾客从商店下载你的 App 时，他们只会得到其特定设备所需的资源。这使得下载更小，用户等待 App 下载的时间更少，也就能更早地开始享受你的 App。

我们还能获得性能提升。同样，由于资源目录以优化格式保存图像资源，图像可以加载得更快。这对 App 启动时间尤其有益。特别是在带有硬盘的 Mac 上，我们看到 App 启动性能最多提升了 10%。

资源目录还使得采用基于 GPU 的压缩变得非常容易。这种压缩默认无损，但也可选择有损图像选项。

所有选项都享有硬件加速的解压缩，其中一个选项还提供了降低图像资源内存占用的方式。

回到我们的演示 App，前面我们看到通过采用 HEIC 将 App 大小减小到了 17.9 兆字节。

现在，通过同时采用资源目录，主要借助 App 切片功能，我们能够进一步将这个 App 的占用减小到 14.9 兆字节。

自我们开始以来，仅通过采用 HEIC 和资源目录就实现了 40% 的占用缩减。

因此，如果你还没有为图像资源使用 HEIC，也没有使用资源目录来帮助组织资源，我们强烈建议你考虑使用它们。它们是获得更高效、更小 App 占用的绝佳且简单的方式。

接下来我想稍微谈谈文件系统元数据。我们的演示 App 维护着一个很小的 plist，只记录 App 最后一次启动的时间。每次 App 启动时，我们读取这个 plist，更新最后启动时间属性，然后将更新后的 plist 写回磁盘。如果我们使用 Alejandro 稍后在讲座中会讨论的文件活动（File Activity）Instrument 来观察这种行为，可以看到这种行为导致一次读取（读取 plist，理所当然），但它导致三次写入操作，这可能有些令人惊讶，因为我们只是写出了一个文件。我们还看到一次 fsync 操作，这些操作可能很昂贵，稍后我们将更多地讨论为什么它可能昂贵。那么为什么是三次写入而不是一次呢？答案是文件系统元数据。

文件系统元数据是文件系统每次创建文件或删除文件时需要更新的数据。因此在本例中，我们写入 plist、创建文件，就产生了额外开销。

那么文件系统元数据是什么？文件系统元数据是文件系统需要跟踪的关于我们文件的信息。诸如文件名、大小、位置，以及创建日期或最后修改日期等日期。还有很多其他内容。为了更好地理解每次创建文件时文件系统需要做什么，让我们逐步了解 APFS 在我们把 NSDictionary 文件写入磁盘时要做什么。APFS 首先要更新文件系统树，它通过更新其中一个节点来完成。

然而，由于 APFS 的写时复制（copy-on-write）特性，我们实际上并不更新现有节点，而是创建现有节点的副本。让我们详细看看。

这是现有的文件系统树。我们看到对现有节点进行了一次复制。

这个新节点与原始节点的区别不在于节点名称——实际上与原始节点相同——而是新节点拥有一个递增的或至少不同的事务 ID。正是这个不同的事务 ID 使 APFS 能够支持快照等高级功能。回到上一层，现在我们有了更新后的文件系统树，APFS 需要更新对象映射，以便它了解这个新节点。因此，为了支持写入这个新文件，APFS 必须执行两次独立的操作，总共 8K 的写入 I/O：4K 用于更新文件系统树，另外 4K 用于更新对象映射。我们仍需要写入文件本身，本例中即使它只有 240 字节的 NSDictionary 数据，iOS 设备上能写入磁盘的最小文件也是 4K，所以会被向上取整。因此，为了存储一个 240 字节的 NSDictionary，我们总共需要向磁盘写入 12K 的数据。

效率约为 2%。这个例子不仅向我们展示了 APFS 跟踪文件创建需要做的工作，还凸显了在文件系统上以单个文件存储少量数据可能有多么昂贵。

在我们刚走过的例子中，我们看到为了在 APFS 上创建文件必须进行 8K 的 I/O。那么删除文件呢？那是 8K。其他常见操作，如重命名文件是 16K。修改现有文件是 8K。

这里最大的收获是：文件系统更新不是免费的。事实上，它们可能涉及比被存储数据更多的 I/O 使用。因此，我们需要谨慎地创建、修改和删除文件。

我们希望尽量避免诸如快速创建和删除文件这类昂贵的行为。

如果我们有一个需要在文件系统上保留临时数据的用例，这里有一种很好的方式来降低临时数据对系统的成本。首先，创建文件但保持打开且取消链接，并且不要对其调用 fsync。这样做会给文件系统提供它需要的提示，以便尽可能长时间地将临时文件保留在操作系统缓存中，而不是像可能需要的那样频繁地写入磁盘。如果你想了解更多关于 APFS 中文件系统元数据的内容，我们开发者网站上有一份很好的参考文档，我强烈建议你查看。接下来，同步到磁盘。

在管理数据所在位置时，我们希望把数据保存在离 CPU 最近的缓存中以获得最佳性能，但我们也希望确保数据在需要时能到达磁盘。

首先让我们谈谈我们拥有的各种缓存。

首先是操作系统缓存。这是我们希望保存数据以获得最佳性能的地方。

对操作系统缓存的读取和写入被称为逻辑 I/O。由于这个缓存由内存支持，逻辑 I/O 操作完成得非常快。对于频繁使用和修改的数据，将数据保留在操作系统缓存中通常是有利的。接下来，我们有磁盘缓存，它实际上物理地位于存储设备上。

最后，我们有永久存储。这是实际长期持久化数据的物理介质。在 iOS 设备和大多数 Mac 上，这是 NAND。物理 I/O 是对物理存储的读取和写入。这些 I/O 可能针对磁盘缓存或永久存储，也可能来自它们。现在我们已经谈了一些关于缓存和永久存储的内容，让我们谈谈我们最常用的、将数据从操作系统缓存移动到存储设备的 API。首先是 fsync。fsync 会导致数据从操作系统缓存移动到磁盘缓存。但它并不保证数据会立即写入永久存储。如果没有软件的进一步输入，由设备固件决定何时将数据从磁盘缓存移动到永久存储。

它也不保证写入顺序。也就是说，数据从操作系统缓存写入磁盘缓存的顺序，不一定与数据从磁盘缓存写入永久存储的顺序相同。如果过度使用，fsync 也可能很昂贵。当我们的数据在操作系统缓存中时，操作系统缓存能够轻松吸收对相同数据的覆盖或修改。一旦我们使用 fsync，它就被移动到了磁盘缓存。

而且根据我们需要确保数据移动到磁盘缓存的频率，手动调用 fsync 可能甚至没有必要，因为操作系统会定期为我们做这件事。

将数据从操作系统缓存一路移动到永久存储的主要方式是使用 F 控制，即 FFULLFSYNC。

这会导致驱动器磁盘缓存中的数据被刷新。然而，这会导致磁盘缓存中的所有数据都被刷新，所以不仅我们感兴趣的、想要移动到永久存储的数据会被移动到永久存储，磁盘缓存中的所有数据都会。因此，它很昂贵，因为这可能是大量数据，也可能花费大量时间。

而且，同样地，手动执行这一步可能实际上没有必要，因为操作系统会定期为我们做这件事。

如果我们使用 FFULLFSYNC 的主要原因是确保 I/O 顺序，一个很棒且高效得多的替代方案是使用 F BARRIERFSYNC。F BARRIERFSYNC 强制执行 I/O 顺序。F BARRIERFSYNC 最好被理解为基本上是一个带屏障的 fsync，这个屏障是对 Apple SSD 的提示，让它在执行屏障之后收到的任何 I/O 之前，先执行屏障之前收到的所有 I/O。因此，它比 F FULLFSYNC 便宜得多，因为我们在不把磁盘缓存中的所有数据推送到永久存储的情况下，就得到了我们想要的相同结果。所以，如果你关心 I/O 顺序，请使用 F BARRIERFSYNC 而不是 F FULLFSYNC。这是让你的数据到达磁盘的一种更快、更高效的方式。

序列化数据文件。诸如 plist、XML 和 JSON 这样的文件很棒。它们使用方便。它们是存储不常修改数据的绝佳方式，而且解析起来极其容易。

然而，所有这些易用性都伴随着一些权衡。每次我们对文件做单个更改时，整个文件都必须重新序列化并重写到磁盘。

因此，它们扩展性很差。

而且由于它们非常容易使用，也很容易被误用。

而且因为我们每次更改都要替换文件，它们对文件系统元数据的要求很高。而且它们绝不是数据库的替代品。从文件活动 Instrument 的截图中我们可以看到，创建、读取和修改 plist 的行为导致了 12 次独立的 I/O 操作，对于大概四行代码来说相当多了。

如果我们从稍微不同的视角来看，就会看到每次我们调用 NSDictionary 的 writeToFile:atomically:，操作都以一次 fsync 结束。这意味着我们存储在这个 NSDictionary 中的所有数据在推送到磁盘时永远无法享受操作系统缓存的好处。因此，真正大型的数据集，或者频繁修改的数据集，在序列化的 plist 格式中效率并不高。如果你的数据量太大或修改太频繁，Core Data 是一个非常好的替代方案。Core Data 管理构建在 SQLite 之上，并在 SQLite 数据源与 App 的模型层之间提供了一个出色的抽象层。Core Data 自动管理对象图和关系，支持变更跟踪和通知，自动进行版本跟踪和多写入者冲突解决。Core Data 甚至会自动为多个并发操作池化连接。而且 iOS 13 新增了 Core Data 对 CloudKit 集成的支持，这对 Core Data 采用者来说是巨大的胜利。Core Data 还支持实时查询，允许你即时生成查询，这样你就不必预先手写所有你认为可能需要的 SQLite 查询。Core Data 还提供自动内存管理、语句聚合和事务、模式迁移，以及 iOS 13 新增的数据反规范化等等。我们还观察到，Core Data 的采用者需要编写少 50% 到 70% 的代码来支持他们的模型层。这些代码永远不必被编写、修改或调试。然而，如果你的用例需要直接使用 SQLite，我们确实有一些最佳实践想要分享。这是一个更大的主题，所以有一些子主题，包括连接、日志记录、事务、文件大小与隐私，以及部分索引或子连接。SQLite 的健壮性保证不是免费的。打开和关闭数据库可能……（行被截断到 2000 字符）

接下来是日志记录。删除模式日志记录是 SQLite 的默认日志模式，但它不一定是效率最高的。为了理解为什么，让我们看看删除模式日志记录是如何工作的。假设我们有一个数据库，想要修改其中的四页。首先发生的是，这四页被复制到一个日志文件中。然后我们就可以在数据库中修改这四页。

一旦完成，日志文件就被删除。所以如果我们想想，我们不得不写入我们想要修改的页数的两倍，并且还有这个只在单个事务中保留的短命日志文件所带来的所有文件系统开销。

幸运的是，SQLite 在预写日志（Write Ahead Log，WAL）模式日志记录中提供了更高效的替代方案。WAL 模式日志记录提供了减少写入的绝佳方式。它允许我们合并写入——对同一页的多次写入。它使用更少的屏障。它可以同时支持多个读取者和一个写入者，并支持快照。

让我们看看 WAL 模式是如何工作的。

同样假设我们有一个数据库，想要修改四页。我们不是直接在数据库中修改页面，而是把它们写入预写日志文件，随着我们进行额外的事务，这些页面也会被添加到预写日志文件中，直到预写日志文件变得足够大，进行检查点操作才有意义。

而且，当我们进行检查点操作时，我们获得了 WAL 模式的巨大优势之一：在删除模式数据库中会被多次修改的页面，所有对同一页的这些更改在 WAL 检查点期间都会被合并，同一页只需要写入一次。完成后，只需覆盖 WAL 文件的头部，就可以让它供将来使用，从而降低维护这个预写日志文件的文件系统成本。因此我们可以看到，对于 SQLite 的大多数用例，WAL 模式更高效。如果你还没有为 SQLite 数据库使用 WAL 模式，我们强烈建议切换到 WAL 模式。它可能是为你的 App 获得巨大性能提升的绝佳方式。

在单个事务中使用多个 INSERT、UPDATE 和 DELETE 语句，是给 SQLite 更多信息以便它能代表你进行更高效操作的绝佳方式。

在同一个事务中被多条语句多次更改的页面，只会被写入磁盘一次。假设在这个例子中有三个独立的事务，每个事务有一条语句修改数据库中的同一页。我们会看到数据库中的同一页被修改三次。然而，如果我们有一个包含这三条语句的单个事务，所有这些更改都会被合并，数据库中的那一页只会被写入一次。

因此，在单个 SQLite 事务中使用多条语句，是随时间聚合更改的绝佳方式。

文件大小与隐私。那么当我们从数据库中删除数据时会发生什么？包含被删除数据的空间被标记为自由空间，虽然它不再是数据库的一部分，但在技术上仍在磁盘上。

那么我们如何以高效的方式安全地删除敏感信息呢？我们推荐使用 secure delete=fast。secure delete=fast 很棒。它会自动将被删除的数据置零，并且对于与我们为了标记数据为自由空间而必须修改的头部文件位于同一页的数据，没有任何成本。而且从 iOS 13 起，这已成为 SQLite 的默认行为。如果你需要它用于旧版 iOS 构建，请指定 secure delete=fast pragma。

在管理数据库文件大小时，我们强烈建议不要使用 VACUUM。

VACUUM 是一种非常慢、内存和 I/O 密集型的操作。为了更好地理解为什么，让我们看看 SQLite 数据库的 VACUUM 是如何工作的。假设我们有一个数据库，想要把所有空闲页 vacuum 出来。发生的情况是，我们最终为数据库打开一个缓存门，创建一个日志文件，然后对数据库执行 SQLite 转储，将所有有效数据复制到日志文件中。

然后稍后到了检查点日志文件的时间，数据库被截断到日志文件的大小，所有来自日志的数据被重新插入数据库。

然后当那完成时，日志文件被丢弃。

正如我们所见，这相当昂贵，因为我们数据库中所有有效数据至少要被写入两次，一次写入日志文件，然后再次写入数据库。而且如果数据库的工作集太大，无法装入内存，SQLite 实际上必须使用溢出文件来帮助管理额外数据，直到操作完成。

同样，幸运的是，SQLite 中有一个更高效的替代方案，在本例中就是 auto vacuum=INCREMENTAL。增量自动 vacuum 很棒，因为它不仅允许我们以更高效的方式管理数据库文件大小，还让我们可以指定想要从数据库中 vacuum 出来多少页，从而可以选择在数据库中保留一些空闲页供将来使用。

让我们看看 auto vacuum=INCREMENTAL 是如何工作的。在这个例子中，我们要 vacuum 出两个空闲页。而之前我们不得不把数据库中的所有数据移动到 WAL 文件，对于增量自动 vacuum，我们所做的是把数据库末尾的两页迁移到预写日志中，以及在数据库树重新平衡过程中被修改的任何父节点也会被写入预写日志。然后，当预写日志进行检查点操作时，数据库文件本身被截断，我们从数据库末尾迁移的页面会去到空闲页原来的位置，任何更新后的父节点会被写入数据库。所以正如你所见，之前我们必须把所有数据移入移出数据库，现在我们只是修改数据库内的一部分页面。

这要高效得多。

我们强烈建议使用增量自动 vacuum 和快速安全删除，来同时管理 SQLite 数据库的文件大小与隐私。

部分索引。

索引很棒。索引允许更快的 ORDER BY、GROUP BY 和 WHERE 子句。不幸的是，它们不是免费的。数据库需要做一些额外开销来支持这些索引。而且在我们添加更多索引之后，每次向数据库写入新数据都可能变得更加昂贵。

幸运的是，有一种更高效的替代方案，即部分索引。部分索引允许你使用 WHERE 子句来描述你希望在哪里为索引付出代价，这很棒，因为现在你可以在需要时获得索引的好处，而不必在索引不会给你带来好处时也付出索引的代价。

所以对 SQLite 的总结是：请尽可能长时间地保持数据库连接打开。使用 WAL 日志模式而不是删除日志模式。只要可能，每个事务使用多条语句，以便 SQLite 能为我们做一些优化。

使用快速安全删除和增量自动 vacuum 来同时管理数据库的文件大小与隐私。

而且，当实际可行时，使用部分索引而不是常规索引。

而且如果你真的不想操心 SQLite 的这些细节，我们强烈建议直接使用 Core Data。Core Data 为你处理所有这些繁重的工作，而且随着 Core Data 随时间改进，Core Data 的采用者也会免费获得这些好处。
