欢迎来到《网络技术进展》。我是 Joshua Graessley。我和来自 Internet Technologies 的同事们很高兴能与大家分享过去一年我们在平台网络方面所做的诸多改进。在第一部分，我们将讨论低数据模式。这是一个令人兴奋的新功能，通过它我们可以共同努力，在关键时刻帮助节省用户的网络数据。我们将讨论如何使用 Combine 和 URLSession 编写优雅的异步网络代码。我们还将介绍 WebSocket API。去年，这是您在实验室中提出的首要需求之一，今年我们很高兴能提供一个解决方案。最后，我们将讨论一系列移动性改进，以及我们如何共同努力，在设备从一个网络移动到另一个网络时，为用户提供更无缝的体验。

在第二部分，我们将涵盖更多主题。那将在今天下午 5:00 进行。我鼓励你们回来参加。现在，在深入探讨低数据模式之前，我想花点时间谈谈我们平台上的网络 API。我们平台上最好的网络 API 是 URLSession 和 Network.framework。正如你们将在本次会议及第二部分中听到的，我们做了许多重大改进，如果你们的应用程序使用这些框架，所有这些改进都将可用。

如果你们使用 socket，将无法利用这些优势。不幸的是，socket 没有足够的丰富性来在该层提供我们需要的功能。现在，如果你们在构建像 VPN 或内容过滤器这样的东西，NetworkExtension 框架是一个很好的解决方案，我们也在那里做了许多改进，这些将在明天上午 9:00 讨论。说到这里，我想谈谈低数据模式。低数据模式是 iOS 13 中一个非常令人兴奋的新功能。

我认为介绍低数据模式的最佳方式是让你们回想一下是如何来到 WWDC 的。你们很可能乘坐飞机飞往阳光明媚的圣何塞。在飞机上，可能有一个 Wi-Fi 网络，而这个 Wi-Fi 网络可能相当昂贵，或者非常拥堵，你们可能希望有一种方法告诉设备上的应用程序和系统，在这个特定网络上，使用网络数据时需要非常保守。低数据模式就是为了解决这个问题。

低数据模式为用户提供了一种偏好设置，可以向你的应用程序和系统发出信号，表明你在这个网络上确实希望非常小心地使用数据。

这可以根据 SSID 在每个 Wi-Fi 网络上设置，并根据 SIM 在每个蜂窝网络上设置。

当设备处于低数据模式网络时，这会产生两个主要影响。系统策略会发生变化，并且采用了低数据模式的应用程序也会发生变化。对于系统策略，当我们在低数据模式网络时，会推迟所有后台自由决定的任务。所以，如果你们在飞机上，并且开启了低数据模式，我们会推迟所有这些后台自由决定的任务。当你们下飞机入住酒店，连接到可能不那么拥堵或昂贵的 Wi-Fi 网络时，我们会让所有这些后台任务恢复并继续执行。我们做的另一个改变是禁用后台 App 刷新。这有助于避免允许可能与用户实际兴趣无关的后台应用程序消耗网络数据。这为我们带来了一些巨大的优势，但我们认为最大的优势将来自于你们在应用程序中为采用低数据模式所做的改变。所以，我想花些时间谈谈你们可以使用的一些技术。这一切都始于研究你们的应用程序是如何使用网络数据的。当你们开始深入探究时，牢记一点非常重要：任何时候只要能节省数据且不影响用户体验，你就应该总是这样做。我知道这看起来显而易见，但你们可能会对减少网络数据使用量的优化方式感到惊讶。

现在，一旦你们完成了所有这些轻松就能实现且无影响的优化，你们就需要开始在一些权衡中做出决定了。

在很多情况下，你们有机会消耗更多数据以提供非常好的体验，或者使用少一点数据但仍能提供不错但可能稍逊一筹的体验。而低数据模式正是用户向你的应用程序发出信号的一种方式，表明他们更希望你节省数据，选择仍能提供良好体验但可能不是最佳的那个选项。那么，让我们谈谈你们可以使用的一些技术。第一个是降低图像质量。如果你的应用程序并不以图像为核心，降低图像质量可以节省大量数据，同时仍然让用户完成他们想做的事情，但在此过程中节省数据。

你可以减少预取。预取是提高性能的好技术，但它有一个缺点，即你可能最终会获取用户永远不需要的资源。当用户非常在意他们使用了多少网络数据时，预取实际上可能适得其反。

因此，在低数据模式下，你可以消除预取，节省那些数据。用户可能需要等待更长时间才能让滚动到视图中的内容加载完成。你可以降低同步频率。数据过时的时间会更长一些，但你仍然会有数据。用户仍然可以完成他们想要做的事情，但长期来看，通过降低同步速率，你可以获得相当大的节省。你可以将后台任务标记为自由决定。你会惊讶地发现，你设置的许多后台任务并不需要立即完成。通过将后台任务标记为自由决定，系统在何时实际调度该操作方面获得了很大的灵活性。正如我之前提到的——当你在飞机上时，这给了系统机会将该任务推迟到我们进入非低数据模式网络时。另一个很好的解决方案是禁用自动播放。这非常好，因为它不会阻止用户播放他们感兴趣的内容，但意味着用户不必为他们不关心的内容付费。这就引出了另一个非常重要的点，即当你们选择如何实现低数据模式时，请不要阻塞用户发起的工作。低数据模式是为了告诉系统减少它使用的网络数据量，但要确保用户仍然可以完成他们想要做的事情。当你们审视自己的应用程序时，可能会意识到你们执行的一些操作确实消耗大量网络数据，并且对此无能为力。尽你所能减少这些操作所使用的网络数据量是很好的，但我们真的不希望你们弹出一个对话框，询问“您确定要这样做吗？我看到您正在使用数据网络，这将消耗大量数据。”不要质疑用户的选择。他们已经开启了低数据模式，并要求你的应用程序执行该操作。请直接执行。那么，我们来谈谈你的应用程序可以用来实现低数据模式的 API。

我们为 URLSession 和 Network.framework 添加了 API。需要记住的是，当网络处于低数据模式时，`constrained` 属性会在该网络上被设置。因此，我们提供的所有 API 都基于 `constrained` 属性。在 URLSession 中，我们添加了一个名为 `allowsConstrainedNetworkAccess` 的属性。默认情况下，它被设置为 `true`。你的应用程序默认被允许使用低数据模式网络。你可以将其设置为 `false` 来选择退出。你可以在 URLSession 请求以及 URLSession 配置上设置此属性。对于 URLSession，我们强烈建议你尝试进行大型资源获取或预取，并将 `allowsConstrainedNetworkAccess` 设置为 `false`。如果你遇到失败，并且错误具有值为 `constrained` 的 `networkUnavailableReason`，这表明操作因处于低数据模式而失败，正确的做法是转而执行你的低数据模式操作。对于大型资源获取，那就是转而获取较小的资源。对于预取，只需等待直到用户真正需要该内容。这样做还有一个额外的好处，即让你可以利用任何可能已经在缓存中的内容。现在，对于 Network.framework，你有一个类似的属性叫作 `prohibitConstrainedPaths`。你可以将其设置为 `true` 来阻止你的连接和其他网络对象使用低数据模式网络。

不过，使用 Network.framework 你还有另一个选择。无论你是否处于低数据模式，如果你要连接到同一个主机，你可以直接建立那个连接。一旦连接建立，你可以获取当前路径，并在当前路径上检查它是否受限制（constrained），这将告诉你这个连接是否建立在低数据模式网络上。

现在，如果选择这条路线，确保处理路径更新非常重要。

`constrained` 属性在你的连接生命周期内是很有可能发生变化的。

所以，我花了很多时间讨论 `constrained` 属性和低数据模式。还有一些其他属性，你的应用程序可以用它们在特定网络上决定做什么。有 `expensive` 属性，我们去年在 Network.framework 中引入了它，今年通过 `allowsExpensiveNetworkAccess` 属性将其带到了 URLSession。

此外，还可以检查特定的接口类型，例如 Cellular 或 Wi-Fi。

如果你还没有采用这些功能中的任何一个，那么你现在处于一个很好的位置，可以专注于采用低数据模式，这绝对是正确方向。对于与 `constrained` 属性相关的低数据模式，用户拥有控制权。他们有一个自己可以控制的设置。另一方面，`expensive` 是一个由系统设置的属性，它几乎总是为蜂窝网络设置，并且也适用于与个人热点关联的 Wi-Fi 网络。你也可以检查 cellular，但这同样是用户无法控制的。因此，如果你目前正在基于蜂窝接口或 `expensive` 属性进行检查，那么转向使用 `constrained` 并利用低数据模式是一个非常棒的主意。如果你已经审视了这些选项，并决定仍然希望基于某物是 `expensive` 还是 `cellular` 来做决定，我们强烈鼓励你使用 `expensive`。

`expensive` 灵活得多，并且在很多方面可以有效地使你的应用程序面向未来。目前，蜂窝网络几乎总是被标记为 `expensive`，但将来可能不是，并且可能出现其他可能也是 `expensive` 的接口类型。通过使用 `expensive` 属性，你的应用程序将来在面对不同接口时会做出正确的行为。如果你检查特定的接口（如 `cellular`），你将无法利用这一点。看到大家采用低数据模式，我感到非常兴奋。非常感谢你们的时间。说到这里，我想请 Guoye 上台谈谈 Combine 在 URLSession 中的应用。谢谢你，Josh。

Combine 将声明式异步编程带到了 Swift。为了解释它是什么，让我从一个构建响应式搜索字段的示例开始。所以，每当用户输入时，搜索字段会发布值，这里的 `sink` 订阅并接收一个 URL 来开始搜索。在中间，我们使用 `map` 操作符将值映射成一个 URL。

现在，假设我只想在内容足够时才启动搜索。我们可以使用 `filter` 操作符。

这个例子中的 `filter` 操作符会丢弃所有短于三个字符的字符串。

现在我们消除了用户类似单个字母 H 的查询。然而，搜索仍然过于频繁。如果我只想在用户停止输入的片刻之后才搜索，该怎么办？我们可以使用 `debounce` 操作符。因此，`debounce` 会延迟值，并且只有在有显著延迟（本例中为 0.2 秒）时才将其转发。

然而，使用 `debounce`，如果用户输入了一些内容然后删除了它，我们可能会沿着链发送相同的值，一遍又一遍地启动相同的搜索。为了解决这个问题，我们可以添加 `removeDuplicates` 操作符。

`removeDuplicates` 会记住最后接收到的值，并且只在值发生变化时才转发新值。

现在我们有了搜索字段的最终版本。通过改变这些强大的操作符，你的异步代码可以变得线性且可组合。

Combine 随时间处理值。它由发布者（publisher）、操作符（operator）和订阅者（subscriber）组成。

链由订阅者发送的请求驱动。

作为对请求的响应，发布者会将值沿链向下发送。这就是 Combine 处理背压的方式。如果你想了解更多，Introducing Combine 会议的视频很快就会发布，我鼓励你们今天下午参加 Combine in Practice 会议。网络本质上是异步的，这就是为什么它非常适合采用 Combine。

今年，我们在 URLSession 中引入了 `DataTaskPublisher`。它是一个单值发布者，其工作方式与我们现有的基于闭包的便捷方法类似，这意味着你可以从共享的 URLSession 或你自己的 URLSession 创建它，并在你的委托（delegate）上接收认证挑战和指标。这是 `DataTaskPublisher` 的接口。它遵循 publisher 协议。成功时，它会向你发送一个包含数据（data）和响应（response）的元组。失败时，它会向你发送一个 `URLError`。

WebSocket 允许通过单个 HTTP 连接进行双向通信。

这使得开发者能够编写像聊天、多人在线游戏和其他实时应用这样的应用程序。WebSocket 在众所周知的 HTTP 端口上工作，并且与现有的 Web 基础设施完全兼容，允许你连接到代理、CDN 和防火墙。

从历史上看，WebSocket 协议作为 JavaScript API 在 Web 浏览器中可用，但考虑到 WebSocket 为 Web App 带来的好处，我们决定将此 API 扩展到我们的网络框架，除了 Web 视图中已有的 JavaScript API 之外。

这使你能够利用现有的 Web 基础设施，并将其带入 Apple 平台上的原生 App。

在讨论 WebSocket 之前，让我们先看一下目前用于实现双向通信的一种常见技术。我们以聊天应用为例。当客户端想要从服务器接收响应时，它会发送一个请求。

服务器立即用 200 状态码响应，但它不发送响应体，因为此时还没有。在未来某个时刻，一旦服务器准备好给客户端的响应，它就会将其发送给客户端。此时，客户端发送一个新的请求，表示它想要接收下一条消息。

这被称为长轮询，但长轮询有一些缺点。

两端在想要发送消息时，都必须发送 HTTP 请求或 HTTP 响应，这有很多开销。

此外，服务器端必须维护复杂性才能支持长轮询。

这是我们通常表示 Wi-Fi 的方式。中间是 Wi-Fi 接入点，周围是同心圆，表示 Wi-Fi 信号逐渐减弱，随着手机越来越远，信号变得越来越弱。在这种场景下，手机决定是使用 Wi-Fi 还是切换到蜂窝非常容易。对吧？现在，问题是，这种 Wi-Fi 的表征方式实际上与现实相去甚远。在现实中，它看起来更像这样。中间是 Wi-Fi 接入点，周围是斑驳的 Wi-Fi 信号。这种斑驳是由于房间内的物体干扰了信号。房子、墙壁，一切都使得 Wi-Fi 信号成为一个非常不确定的质量指标。手机的一个微小移动都可能使手机从一个好位置移动到一个坏位置。因此，对于手机来说，很难知道 Wi-Fi 是否仍然良好。它可能仍然接收到来自接入点的信标，但信号可能仍然太低以至于无法实际发送或接收任何数据。所以，在这种环境中，手机需要决定是使用 Wi-Fi 还是使用蜂窝。正是这种围绕 Wi-Fi 信号的不确定性构成了移动性的全部挑战。

在 iOS 7 中，我们为 Siri 引入了多路径 TCP（Multipath TCP）。Multipath TCP 允许同时使用 Wi-Fi 和蜂窝。因此，从 iOS 7 开始，每当人们使用 Siri 并走出家门时，Multipath TCP 将确保流量通过 Wi-Fi 或蜂窝传输，从而降低 Siri 用户的延迟并降低错误率。

我们看到多路径 TCP 带来了很好的结果。

现在，像多路径 TCP 这样的真正的端到端多路径协议，需要客户端和服务器都了解它。两者需要协同工作，对吧？它们需要协同工作来决定是通过 Wi-Fi 还是蜂窝发送流量。因此，我们问自己，如何在不要求客户端和服务器协同工作、无需修改服务器配置的情况下改善移动性？

下一个具有非常关键用户体验并且在走出家门时也经常被使用的应用是当你在流式传输音乐时。对吧？当你在流式传输音乐时，你正在下载一个充满音乐内容的大文件，你不希望音乐中断。因为一旦中断，用户就会受到干扰。因此，自 iOS 13 起，我们为 Apple Music 启用了多路径 TCP。我们看到音乐流式传输中断大大减少，因为现在当我们接近中断时，MPTCP 会将流转移到蜂窝。因此，用户将获得更好的体验。现在，关于这一点，我们已经为 Siri、Maps 和 Music 启用了它，你们也可以这样做。我们推荐——我们鼓励你们研究一下你们的应用。哪些应用在走出家门时经常被使用？哪些应用具有对用户体验至关重要且难以恢复的流？这类流非常适合多路径服务类型，在 URLSession 和 Network.framework 中，你可以选择切换（handover）或交互（interactive）类型。

现在，不要忘记，如果你确实进入了多路径，它仍然需要客户端和服务器协同工作，因此请访问此 URL 以确保你的服务器配置正确。
