那我们先从值和引用聊起。先快速回顾一下。Swift 有三种创建类型的基本方式：类、结构体和枚举。

类是引用类型。也就是说，当你有一个变量时，它只是指向真正持有这些值的对象。

当你复制它时，你只是复制了那个引用。这意味着当你通过引用修改一个值时，你实际上改变的是这两个变量共同指向的同一个对象。

所以它们都会看到这个变化。而结构体和枚举则是值类型。当你复制它们时，会复制它们的全部内容。也就是说，当你做出修改时，你只是在修改那一份副本。

在你的 API 中使用值类型，能在使用点的清晰性上带来很多好处。如果你知道每次拿到的都是一份全新、独一无二的副本，那你就不需要担心这个值是从哪来的，也不需要担心是不是还有别人持有它的引用、可能在背后悄悄改动它。

比如说，你不需要再做防御性拷贝。既然如此，一个常见的问题就来了：在我具体这段代码里，我应该用引用类型还是值类型？每个使用场景都不一样，所以没有硬性规定。但这里有一些一般性的建议：总的来说，除非你有充分理由使用类，否则应该优先使用结构体而不是类。

如果你习惯每次创建类型时默认用类，那不妨从今往后把这个默认值翻转过来，看看效果如何。

不过类在 Swift 中仍然扮演着关键角色。如果你需要通过引用计数来管理资源，类是必不可少的——尽管很多时候你会想把那个类包在一个结构体里面，我们马上就会看到这种情况。

如果某个东西本质上就是被集中存储和共享的，类也是一种有用的构造方式。

还有很重要的一点：如果你的类型具有「身份」，而这种身份概念与它的值是分开的，这往往也是一个信号，说明用类可能更合适。

但这些实体的属性，比如它们在场景中的位置或朝向，则是用值类型来建模的。

我们刚才说过，当你复制一个值类型时，会复制它所有的存储属性。

这样做是否可以，其实取决于 texture 的具体实现。如果纹理是不可变的，那完全没问题，甚至从共享的角度来看还相当理想。

但如果 texture 本质上是一个可变类型，那我在这里创建出来的东西其实就有点奇怪了：它既不完全像引用，也不完全像值。我可以修改结构体上的属性，这只会影响其中一个变量；但如果我通过 texture 引用去修改那个对象，那就会同时影响两个变量。这对你的 API 使用者来说可能会非常出乎意料，而且很可能比你从头到尾都坚持使用引用语义更让人困惑。

值类型和引用类型、结构体和类、值语义和引用语义（也就是类型的行为方式）之间，是一个非常关键的区别。

仅仅因为某个东西是值类型，比如结构体，并不意味着你就自动获得了值行为。一种可能出问题的方式——不是唯一的方式，但是很常见的一种——就是在它的公开 API 里包含了一个可变的引用类型。所以第一个要问的问题是：如果你希望某个东西表现得像值，它暴露出来的引用里有没有可变的？记住，这一点并不总是显而易见的。

如果我们处理的是一个非 final 的类，那你实际拥有的可能是一个可变的子类。好在我们有很多技巧可以避免这类问题。

最简单的一种，就是沿用我们一直以来对引用类型的做法：做一次防御性拷贝。于是我们可以把 texture 这个存储属性改成 private。

然后改用一个计算属性代替。在它的 setter 里，我们只需要复制一份 texture 对象。这样就避免了可变子类的问题。

但如果 texture 本质上是可变类型，这个办法并不能解决问题，因为你仍然可以直接通过 getter 属性去修改它——引用就是这么工作的。

于是我们再考虑另一个选项：干脆完全不暴露这个引用类型，而是把我们想要的属性，作为计算属性直接暴露在我们的 material 值类型上。

这样，我们就可以创建一个计算属性，在 getter 里直接转发到对象的相应属性上。

而在 setter 里，我们可以先检查这个对象是否已知是唯一被引用的。如果不是，这时我们就可以在进行修改之前先对 texture 对象做一次完整拷贝。

只需加上这一行「唯一性检查」，我们就实现了完整的写时复制（copy-on-write）值语义，同时仍然把我们想要的属性暴露在这个引用类型上。

接下来，我们聊聊协议和泛型。

我们已经看到值类型能为你的 API 在使用点的清晰性上加分。

但值类型并不是什么新东西。在 Objective-C 里我们一直就有 CGPoint 或 CGRect 这样的类型。

那 Swift 有什么不同呢？Swift 的不同之处在于，除了类之外，结构体和枚举也可以应用协议。这意味着你可以通过泛型在各种类型之间共享代码。

所以，如果你觉得需要在不同类型之间共享一些代码，不要觉得非得创建一个带共享功能基类的类层次结构不可。

相反，正如那句老话所说：在 Swift 里，从一个协议开始。

但这并不是说，当你打开 Xcode、面对一个空的源文件时，第一件事就是敲下关键字 "protocol"。

在 Swift 的 API 设计中，就像任何 Swift 设计一样，先用具体类型探索使用场景。当你发现自己在不同类型上反复写着相同的多个函数时，去理解你到底想共享的是什么代码。

然后再用泛型把这些共享的代码提炼出来。

这可能意味着要创建新的协议。但首先，考虑用已有的协议组合出你需要的东西。在设计协议时，确保它们是可组合的。

作为创建协议的替代方案，也可以考虑创建一个泛型类型。

我们来看几个例子，展示一下这些不同的做法。

假设我想创建一个几何 API，作为其中一部分，我想为几何向量定义一些操作。我可能会先创建一个几何向量的协议，给它定义我想要的操作，比如点积，或者两个向量之间的距离。

现在，我需要存储向量的维度。于是我可能会让我的几何向量细化（refine）自 SIMD 协议。如果你还不熟悉 SIMD 类型，它们基本上就像是一种同质的元组，可以非常高效地对每个元素同时执行计算。

它们在 Swift 5.1 中获得了很多出色的新特性，非常适合用来做几何计算。所以，我们会把维度存储在那个基础的 SIMD 类型里，同时我们还想把它约束成只对标量 SIMD 有效，这样才能做我们想要的计算。定义好这个协议之后，我们就可以为我们想在向量上执行的所有操作实现默认实现。

然后我们想把这个协议的一致性赋给我们想让它们获得这些新能力的每一个类型。

而这个「定义协议、实现默认实现、再为多个类型添加一致性」的三步流程，其实相当繁琐。这时候值得停下来想一想：这个协议真的有必要吗？事实上，这些一致性都没有自己定制的实现，这本身就是一个警示信号，说明这个协议可能并没有用处。这里根本没有针对每种类型的定制，实际上这个操作在每一种不同的 SIMD 类型上都是一样的。

那这个协议到底给我们带来了什么呢？如果退一步想，与其在我们的新协议上写默认实现，不如直接在 SIMD 协议上用同样的约束写一个 extension，那就完事了。就这一页代码，我们就自动把我们需要的所有能力赋给了所有包含浮点数的 SIMD 类型。

有时候你可能会忍不住想去构建一套精心设计的协议层次结构，把不同的类型归类到这个层次结构里。但这种「类型分类学」，虽然做起来很有满足感，却并不总是必要的。

这里还有一个实际的考虑。

这种更简单的、基于 extension 而不用协议的方式，对编译器来说处理起来要容易得多。

而且，因为没有一堆不必要的协议见证表（protocol witness table），你的二进制体积也会更小。

事实上，我们发现在一些非常大的项目里，那些拥有大量复杂协议类型的项目，通过采用这种简化方式、减少协议的数量，我们能显著改善这些应用的编译时间。

不过，这种基于 extension 的做法只适合少量的辅助功能。当你在设计一个更完整的 API 时，它确实会遇到扩展性问题。前面我们在考虑创建协议时说过，我们会定义 geometric vector（几何向量），并让它细化自我们用来做存储的 SIMD。

但这样真的对吗？这真的是一种「是一个（Is-a）」的关系吗？我们真的能说一个几何向量「是一个」SIMD 类型吗？我是说，有些操作是说得通的，你可以对向量做加减法。

但有些操作就不行了。你不能把两个向量相乘，也不能给一个向量加上数字 1。但这些操作在所有 SIMD 类型上都是可用的，而且在其他上下文中它们确实有说得通的定义——只是在几何这个语境下说不通。

所以，如果我们要设计一个易于使用的 API，我们不妨考虑另一个选项：不用「是一个」的关系，而是实现「有一个（has-a）」的关系。也就是说，把一个 SIMD 值包在一个泛型结构体里面。

于是我们可以创建一个 geometric vector 结构体，让它对我们的 SIMD 存储类型是泛型的，这样它就能处理任意的浮点类型和任意不同数量的维度。

完成这一步之后，我们对到底在这个新类型上暴露什么样的 API，就有了更细粒度的控制。

比如我们可以定义两个向量相加，但不定义一个数字加到向量上；或者我们可以定义一个向量乘以一个缩放因子，但不定义两个向量互相相乘。

而且我们仍然可以使用泛型 extension。所以我们对点积和距离的实现，和之前几乎一模一样。

我们其实已经在标准库里用到了这个技巧。比如说，我们只有一个 SIMD 协议，然后有一些泛型结构体，分别代表每种不同大小的 SIMD 类型。注意这里并没有 SIMD2 或 SIMD3 协议，它们其实也不会带来太多价值。

用户仍然可以为某个特定大小的 SIMD 写泛型代码，比如通过给 SIMD3 类型加一个只想在三维 SIMD 类型上定义的叉积操作的 extension 来实现。

体会一下泛型类型可以和协议一样强大、一样具有可扩展性。

这里我们其实仍然在用协议的力量。

我们有一个 floating point（浮点）协议来约束泛型 SIMD 上的标量类型，这给了我们写这段代码所需要的构建模块。现在，我们本可以在我们的 geometric vector 类型上写同样的这个叉积操作。

但当我们这么做的时候，这段实现看起来有点丑，因为我们不得不不断地通过值存储去间接获取 x、y、z 坐标。如果能把这个清理干净就好了。当然，我们可以直接在向量类型上为 x、y、z 写计算属性。但 Swift 5.1 里其实有个新特性，叫 key path 成员查找（Key Path Member Lookup），它能让你写一个单一的 subscript 操作，就一次性把一个类型上的多个不同计算属性都暴露出来。所以如果我们愿意、如果这样做说得通的话，就可以用这个特性一次性把 SIMD 上的所有属性都暴露到我们的 geometric vector 上。我们来看看具体怎么做。

首先，我们给 geometric vector 类型打上 dynamic member lookup 特性标签。

接下来，编译器会提示我们写一个特殊的 dynamic member subscript。

这个 subscript 接收一个 key path。实现这个 subscript 的效果是：任何可以通过这个 key path 访问到的属性，都会自动作为一个计算属性暴露在我们的 geometric vector 类型上。所以在我们这个例子里，我们想接收一个指向 SIMD 存储类型的 key path，并返回一个标量。然后我们就用这个 key path 转发过去，从我们的值存储里取出这个值并返回。做完这些之后，我们的 geometric vector 会自动获得 SIMD 拥有的所有属性。

比如说，它会获得 x、y、z 坐标，它们甚至会出现在 Xcode 的自动补全里。

如果你在 Swift 5 里试过这个基于字符串的旧版本特性，这里的区别是：这个新版本是完全类型安全的。

而且更多工作是在编译期完成的。既然现在我们已经能访问 x、y、z 属性了，我们就可以大幅清理叉积操作的实现。瞧，好多了。这个 dynamic member 能力不仅仅可以用来转发属性，你还可以把复杂的逻辑放进这个 subscript 里。我们再来看一个例子。

回到我们之前的例子，那里我们用写时复制值语义暴露了 texture 上的一个特定属性。这对一个属性来说没问题，但如果每次都要重复写同样的代码，那就不太妙了。

如果我们想把 texture 上的所有属性都以写时复制语义暴露成我们 material 类型上的属性呢？用 dynamic member lookup 就可以做到。

首先，我们给类型加上 dynamic member 特性。
