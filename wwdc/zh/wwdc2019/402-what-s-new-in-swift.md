今天我们将讨论两个重要且令人兴奋的 Swift 版本。Swift 5（最近于三月发布）以及 Swift 5.1（现已作为开发者预览版在 Xcode 11 中提供）。

这两个版本共同进一步释放了 Swift 作为一门语言与技术的潜力，供 Apple 和所有开发者在此之上构建。

这表现为 Swift 与 API 之间极为强大的协同关系。

随着第三方 App 共享的 Swift 运行时已随 Apple 操作系统发布，以及以 Swift 编写的二进制框架如今可以部署，我们看到了 Apple 推出的一系列仅基于 Swift 的重要框架。

此外，Xcode 中集成的 Swift Package Manager 支持，将 Swift 软件包直接带入了 App 开发的核心工作流。而 Swift 语言本身也新增了用于构建精美、丰富的 API 的新特性，以及表达 API 演进的能力。这是语言与整体故事中一个真正激动人心的时刻。那么，让我们先从二进制框架谈起，尤其是深入研究实现这一目标的核心要素。这些要素就是 ABI 与模块稳定性。

ABI 代表应用二进制接口（Application Binary Interface），它规定了编译后的代码在运行时如何相互交互的底层规则。

例如函数调用的细节。它实际上如何工作？参数中的值如何从调用方传递给被调用方？有哪些可用的元数据？它们在内存中如何布局？所有这些细节都是编译后的代码相互交互所必需的。为了说明这个概念，想象你有一个用 Swift 编写的程序。它是一个 App，也可以是命令行工具，这并不重要。它只是一个可执行文件。

它使用了一个同样用 Swift 编写的框架，所有这些编译后的代码都在一个运行中的进程内一起运行。因此，可执行文件使用来自框架的 API，它们必须能够在运行时相互通信。

为了使其工作，它们必须具有兼容的 ABI，就像这两个部分一样，它们是独立编译的，但编译后的代码需要协同工作。在 ABI 稳定之前，我们唯一能保证的是，只有使用相同编译器构建时，它们才会拥有兼容的 ABI。之所以如此，是因为我们当时正在真正地演进 Swift 的核心基础，确保我们希望在未来构建于其上的所有构建块都处于正确的位置。而在 Swift 5 中，我们已将这些细节固化，Swift 现在具备了 ABI 稳定性，这意味着这两个组件不再需要使用相同的编译器构建，只要使用 Swift 5 或更高版本的编译器即可。第二个重要要素是模块稳定性，这是一个编译时概念。如果你使用 Swift 框架中的所有 API，这些 API 都属于一个共享的命名空间，称为模块。当 Swift 编译器用于构建该框架时，它会生成一个清单，列出框架中的所有 API，供该框架的客户端使用。这个清单称为 Swift 模块文件。因此，回到这个例子，想象我们正在编译程序，我们有一个源文件，它引用了框架，编译器会去读取 Swift 模块文件，获取可用的 API。但这个模块文件中的细节非常丰富，在很多方面与编译器本身紧密耦合。因此，我们遇到了与 ABI 稳定性相同的问题。唯一能工作的方式是，这两个部分必须使用相同的编译器编译。在 Swift 5.1 中，我们引入了一个新的互补清单。它称为 Swift 模块接口文件。框架可以用它提供一个稳定的接口供客户端使用。如果你打开它，它看起来像 Swift 源代码。因此，它也建立在源代码稳定性的概念之上……

关于 ABI 稳定性，有很多真正有趣的细节，这是长期推进的工作。如果你有兴趣了解很多更多细节，我们今天也会谈到，swift.org 是一个很好的资源。这是 Swift 开源项目的主页。有几篇关于 ABI 稳定性的非常棒的博客文章。

此外，如果你有兴趣将二进制框架用于你自己的用途，比如与他人共享，本周晚些时候有一个精彩的演讲《Swift 中的二进制框架》，它讨论了与他人共享框架时应考虑的一些事项。

现在，二进制框架只是 API 故事的一部分，另一大块是 Swift 软件包。

随着 Swift Package Manager 现在集成到 Xcode 中，它们已成为构建 App 的核心工作流的一部分。

本周有两场关于在 Xcode 中创建和采用软件包的精彩演讲。因此，二进制框架与 Swift 软件包的结合，为与他人共享 API 提供了一组非常丰富的选项。

那么，让我们换个方向，谈谈性能。Swift 语言被构建为一门现代、安全且高性能的编程语言。ABI 稳定性带来了一些关键的性能优势。

其中之一来自于操作系统中供 App 使用的共享 Swift 运行时，这在三月推出，因此对于 macOS、iOS、tvOS、watchOS，现在随着这些版本发布，还有 iPadOS，系统中都有一个共享的 Swift 运行时，第三方 App、第一方 App、系统中的所有组件都在使用它。那么，这实际上如何工作，何时发挥作用？如果你的 App 是使用 Swift 5 或更高版本构建的，那么当共享运行时存在于操作系统中时，它将始终使用它。

然而，你可能仍在构建 App 以部署到更早的、没有该运行时的操作系统版本。

在这种情况下，Xcode 将继续在你的 App 中捆绑运行时的副本，以便它能在那些更旧的操作系统版本上继续运行。

但我们始终会优先使用操作系统本身中的副本，因此当在较新的系统上运行时，App 中的那份副本将处于惰性状态。作为一项优化，iOS App Store 在下载到装有运行时的操作系统设备时，会从你的 App 中移除那份运行时副本。因此，你的用户无需承担那份下载成本。这是非常重要的代码体积优势，但拥有操作系统中的运行时真正的优势在于，现在它可以作为操作系统本身的一部分进行优化。然后这些优势可以转嫁给 App 本身。

其中一个重要的优势是启动时间。让我们把时间倒回一年前，我们谈到了 Swift 4.2。

如果你有一个 Objective-C App，它什么都不做，只是启动，一个 Swift App 同样没有功能，只是启动，使用 Swift 大约有 5% 的开销，因为需要处理嵌入的运行时。但当你的 App 使用 Swift 5 编译器重新编译并在装有共享运行时的操作系统上运行时，这份开销就消失了。

这真的非常重要。我的意思是，那份延迟是用户想要开始使用你的 App 的那一刻与他们开始体验它之间的差距。

另一个重要的优化领域是进一步调整编译器生成的代码。它减少了——进一步减少了 Swift 应用程序的代码体积。这真的就像微调，比如查看 Swift 应用程序中的特定模式，例如字典字面量在代码生成时是如何表示的，等等，只是确保编译器的输出针对这些用例进行了优化。因此，借助一系列优化，我们看到使用 Swift 5.1 编译器时代码体积最多减少 10%。如果你已针对体积进行优化，代码体积减少约 15%。所以相当显著。

我们还继续改进桥接的性能。我说的桥接，指的是 Swift 与 Objective-C 之间的桥接。这两种语言之间存在非常深度的互操作性。

因此，Swift 和 Objective-C 都有所谓的通用货币类型（common currency types），在整个 API 空间中使用。比如 String 和 NSString、Dictionary 和 NSDictionary。这些货币类型之间的互操作性是 Swift 与 Objective-C 互操作性中相当基础的部分。使用它们货币类型的 Objective-C API 会被重新映射为使用 Swift 的货币类型。现在，这是编译器的工作，但也有运行时方面的工作——当你把一种类型的一个值传递给另一种类型，跨越这些 API 边界时。

这是我们作为 Swift 现已成为操作系统的一部分而进一步调整的部分。

例如，NSDictionary 与 Dictionary 之间的桥接现在快了 1.6 倍。

如果你把一个 Swift 字符串传递给 Objective-C，它桥接为 NSString 并从 Objective-C 一侧使用，其操作最多可快 15 倍。

而所有这些小的改进确实会累加起来，因为这些类型在整个 API 生态系统中都被使用。说到字符串，我们继续改进其核心表示，并在 Swift 5 中对字符串类型做出了重大改变。

这是一次底层的改变，我们将字符串的 Unicode 表示从 UTF-16 改为 UTF-8。

这完全是出于性能考虑。

关于这一改变有很多丰富的细节。如果你有兴趣了解比我即将说的更多的内容，swift.org 上有一篇博客文章，深入介绍了实际的技术变化及其动机。我将突出几个重要的点。

首先，我们创建 Swift 作为一门可以达到 C 级性能的语言。

但其中的关键方面是，我们希望 Swift 与现有的 C API 生态系统具有良好的互操作性。当 Swift 字符串使用 UTF-16 时，当你把字符串传递给 C API 时——也许你并不知情——你必须进行一次分配、一次复制和一次转码，只是为了将其转换为可以传递给 C 的兼容格式。这是相当大的开销。

通过转向 UTF-8，我们现在可以直接传递一个以 null 结尾的 UTF-8 字符串给 C API。没有分配、没有复制、零开销。

我们还能够扩展字符串类型本身的优化。因此，字符串有一种小字符串优化（small string optimization）：如果字符串中的字符数大约 15 个或更少，我们不需要单独的分配来承载这些字符的负载，我们可以直接把它们打包到字符串值本身中。这是一次真正的胜利。在 Swift 5 中，我们能够将此优化扩展到包含基本上所有 Unicode 字符，而不仅仅是 ASCII，这意味着它现在也适用于使用非罗马字符的语言。我们还在此过程中保持了 NSString 与 String 之间在性能层面的良好互操作性。

但真正令人兴奋的是，这一切都是关于性能的。我已经说过好几次了。

一个很好的基准测试例子是 SwiftNIO。如果你不熟悉它，SwiftNIO 来自 Swift 服务器世界，是一个用于构建网络协议和服务的跨平台框架。它真的为速度进行了调优。

通过切换到 UTF-8，我们看到基于 SwiftNIO 构建的 Web 服务器吞吐量提升了 20%。所以这只是一个文本处理的基准测试。这真正与我们希望字符串成为一种你可以用于高性能密集字符串操作的类型，同时也用户友好且易于使用的愿望产生共鸣。在把舞台交给 Anna 之前——她将主要谈论 Swift 5 和 Swift 5.1 中的语言变化——我想谈谈一些核心的工具改进，其中一部分是开源项目的关键方面。

现在，让我们谈谈聚焦。API 设计的一部分是决定从你的 API 中排除什么。在 Swift 5.1 中，我们特别改进了返回类型。虽然返回类型必须表示 API 用户应推理的能力，但有时我们想抽象我们返回的内容。

一个函数可能在运行时多次返回，或者它总是返回相同类型，但该类型可能泄露你 API 的实现细节，暴露 API 用户不应推理的内容。

让我们看看 Swift 为这些情况提供的选项。

我们将在示例中使用简单的形状 API。这里，正如你所期望的，我们有一个 shape 协议，以及定义基本形状（如 circle、oval 和 square）的类型。

进一步地，我们有操作形状的结构体，创建它们的并集并进行变换。考虑这个 face shape 示例。注意这个 API 根据你的形状——face 的类型返回不同的类型，但它们都符合 shape 协议。所以这是一个使用协议类型作为返回类型的好地方。现在，这个例子中，我们通过创建 square 和变换后的 square 的并集来构造一个八角星。在这里声明具体的返回类型，会把大多数实现细节泄露给客户端，暴露——暴露这些不必要的细节会让 API 难以推理。

然而，在这里使用协议类型 shape 也不是很好。让我们看看为什么。

当返回协议类型时，不保证每次调用 API 都返回相同的类型，这除了 Swift 泛型模型之外，还带来这些根本性限制。如果你有两个八角星的值，由同一个 API 返回，但两次不同的调用，它们可能不是相同类型，因此你无法对它们进行相等比较。

返回类型不能有任何关联类型，也不能有涉及 self 的要求。

此外，失去这种类型身份可能阻止某些编译器优化。

Swift 5.1 引入了另一个概念，称为不透明结果类型（opaque result type）。它非常适合那些已知返回相同具体类型，但可能希望对用户隐藏该类型的 API。

不透明结果类型写作 some shape，它传达了这个 API 返回一个特定的 shape 类型。

这种类型身份的保证也允许我们在 API 主体内进行更强的类型检查。

因此，如果你有若干返回语句返回不同的类型，编译器会缓存并提醒你修复问题。

不透明结果类型在 Swift 5.1 中可用，你可以在我们的文档中阅读更多内容。

注意，这个特性需要新的 Swift 运行时。因此它只会在较新的 Swift 操作系统上工作。

如果你向后部署，你可以使用这个特性，但你需要用静态可用性检查来守护它们的使用。
