大家好。我是 Apple 软件电池寿命团队的 Roberto，今天能和大家聊 App 后台运行的进展，我真的很兴奋。

用户喜欢 App，他们喜欢 App，是因为 App 能提供许多很棒的体验。其中一些体验发生在前台，也就是用户正在主动使用 App 时；另一些发生在后台，需要后台执行才能实现。所以，如果我们列出哪些事情可能需要后台执行，我们可能会得到这样一份清单：导航、配件通信，或者周期性的更新与下载等等。而在 Apple，我们设计 API 来提供后台执行，以支持这些用例和体验。

所以，今天我们先谈后台执行，给出一个总体概述，然后谈一些应遵循的最佳实践，最后我的同事 Thomas 会上台，介绍一个新的后台任务框架，它提供了新的后台执行机会。让我们从后台执行的概述开始。我们先回答一个问题：什么是后台执行？我们指的到底是什么？所以当我们想到“后台”时，它可能意味着很多东西，后台线程或后台队列，但当我们谈后台执行时，我们说的是 App 在不在前台时运行或执行代码。

所以看这张图，我们谈的是第三个方框，App 在后台运行，但不一定对用户可见。现在，我们为什么会进入这种状态？归根结底有两种方式。第一种是 App 的请求。这适用于更通用的后台执行，App 想要做一些工作并向系统发出请求。你可以想到下载、周期性更新，或者完成某些前台工作。

第二种是通过特定的事件触发，App 获得后台运行时间来响应世界上发生的事情。例如，也许用户进入某个陌生区域，或者出现了你的 App 需要被知悉的新健康数据。

而在后台运行时，我们非常关心用户体验，因此在设计 API 来支持这些用例时，我们会考虑许多重要因素。我想强调其中三个。

功耗、性能与隐私。让我们先从功耗说起。无论你的 App 在前台还是后台运行，它都在消耗功耗，随着时间推移，这会消耗能量、耗尽电池。

为了可视化这一点，我们取一条时间线。左边可能是太阳升起的清晨，右边可能是一天结束，也许用户决定在一天快结束时插上设备充电，我们用那块绿色的充电区域来表示。于是我们可以把 App 在前台运行的时间标成这些浅色矩形，把 App 在后台运行的时间标成这些深色矩形。

如果运行时间更长，就会消耗更多电池；如果运行时间更短，就会消耗更少电池。

因此在设计 API 时，我们专注于为特定用例提供恰当的运行时间，同时保持出色的电池寿命；而在使用这些 API 时，要想着如何高效，并在完成工作后通过调用 completion handler 来告知系统。这样，如果系统给了你的 App 运行时间，你就能告诉系统：嘿，我提前一点做完了。系统可以挂起你的 App，你就会停止消耗用户的电池。

接下来是性能。我们希望系统尽可能流畅地运行。这意味着我们希望快速启动 App、响应灵敏的 UI，这在后台运行时尤其重要。原因是，虽然我们可能倾向于认为一天中只有一个 App 在运行，但实际上在一天的不同时刻，多个 App 会在前台和后台运行。

当我们把它们叠起来看时，可以看到我们的 App 可能在后台运行，而另一个 App 在前台运行，或者在某个 App 在前台运行时，多个 App 可能在后台运行。因此在设计 API 时，我们会考虑设置智能的 CPU 和内存限制，以最小化对其他使用的影响；而在使用这些 API 时，你应该了解这些限制是什么，这样你才不会影响用户正在做的事情，更重要的是，不让系统终止你的 App，否则未来启动时可能会更慢。

最后一个重要因素是隐私。用户对他们的个人数据非常敏感、非常在意。虽然他们可能清楚 App 在前台运行的所有时刻，并预期 App 能访问某些信息，但他们可能不会意识到 App 在后台运行的所有时刻。

因此在设计 API 时，这意味着我们为不同的用例提供不同的 API，每个 API 都有自己为了支持该用例所需的一组特定数据。而在使用这些 API 时，要想着如何对用户保持透明，让用户知道你正在使用哪些数据。

以上就是后台执行中要考虑的三个重要因素：功耗、性能与隐私。当我们回到用例清单时，这些不同的用例会转化为不同的 API，每个 API 都有各自不同的要求，以在维持出色用户体验的同时达成期望的行为。现在我们有了总体概述，让我们深入一些特定模式的最佳实践，并谈谈 API 的变化。为此，我们取一个消息 App。它可能有核心功能，比如发送消息或拨打电话，还可能有一些额外功能，比如允许用户静音某个吵闹的会话，或下载过去的附件。现在我将逐一介绍这四点，谈一谈我们会用哪个 API 来完成它。

第一是发送消息。发送消息是你的 App 的核心功能。如果我给朋友发消息，我希望它现在就送达，而不是一天后或一周后。

所以用户期望它会立即完成。

虽然这通常会非常快，但有时可能并非如此。也许网络拥堵，或者后端服务器很慢，发送消息可能需要额外的时间。

在这段额外时间里，用户甚至可能离开 App、放下手机并锁定它。因此，我们需要一种方式来保护这项任务的完成。我们要确保消息发送完成，这样用户回到 App 时不会想：嘿，为什么我的消息没发给我朋友。为此使用的 API 是后台任务完成。

这会为 App 提供额外的后台运行时间，使其在被挂起前完成运行。要使用它，你可以调用 UIApplication Begin Background Task，或者如果你在扩展中运行，调用 Process Info Perform Expiring Activity。再说一次，这是为了完成在前台开始的工作。所以其他例子可能包括把文件保存到磁盘，或完成任何用户发起的请求。让我们看看在发送消息这个例子里，代码可能长什么样。

这里我们有 send message 函数。在其中，建立发送操作之后，我们调用 Begin Background Task。这会告知系统：嘿，我们正在启动一项任务，即使用户把 App 置于后台，也要让我们继续运行以完成它。

然后，当我们发送完消息后，在 completion block 中，我们会告知系统结束后台任务。我们不再需要时间了。这是针对系统可能给了我们时间、用户把 App 置于后台、我们做完了、并且可以告诉系统挂起我们以便停止消耗用户电池或潜在影响性能的情况。

还有一件事我想强调。在某些情况下，系统可能给了我们额外时间，但条件太糟糕，比如太拥堵，即使有额外时间我们也没有完成。因此我们有到期处理程序，系统会在那个时间点调用到期处理程序。所以这种情况下，我们会向用户发布一条用户通知，一条本地横幅，说：嘿，回到 App 里来，因为消息没发送成功。所以总结一下：发送消息时，我们希望用后台任务完成来保护它发送完成，并且要基于用户操作来启动它。我们不想等到进入后台才调用 begin background task，因为如果那样做，我们就会限制在系统可能挂起 App 之前，我们主动尝试发送的时间。

现在我们谈完了发送消息，来谈谈电话。

我可能总是想给朋友发消息，但有时你就是想拿起电话快速打个电话，告诉他们一件事，这样就不用打字了。有一个 API 可以做到，就是 VoIP 推送通知。这是一种特殊的推送，会启动你的 App 并提供运行时间，以便你能向用户呈现他们正在被呼叫的事实，用户可以接听电话。

要注册它，你只需在注册 VoIP 推送时在 PK push registry 中设置 VoIP push type。

并且今年新推出的一点非常重要：你必须在 didReceiveIncomingPush 回调中用 CallKit 报告来电，否则你的 App 会被终止。而且，如果你反复这样做，或者反复未能报告来电，系统可能会完全停止为 VoIP 推送启动你的 App。

让我们看看如何在代码中适应这一变化。

这里我们有 didReceiveIncomingPush 回调，在其中我们看到，如果 push type 是 VoIP，我们会用 push payload 中的信息填充一个 CX call update 对象，然后用我们的 CX provider 报告一个新的来电。

因此你需要确保在该方法返回之前报告来电，否则系统会杀死你的 App。你可能还想注意的另外几条技巧是：如果你在 push payload 中包含来电者信息，那你就有全部信息可以快速呈现来电 UI，所以尽量包含尽可能多的信息，以便你能呈现尽可能丰富的 UI。第二，确保你给 push 设置 apns-expiration 为 0 或某个较小值。

这样用户就不会在几分钟后收到一条推送，对应的是已经不再拨打的电话。例如，如果有人呼叫了我的设备，而推送花了两分钟才送达，那我就不希望推送到达两分钟后才报告来电，因为那个人很可能已经不再拨号了。所以如果把过期时间设为 0，意味着立即送达或失败，或者几秒量级，那我们就知道，如果设备收到推送，它仍然是针对一个相关的电话。

并且，值得注意的是，如果你更喜欢横幅，你总是可以用标准推送代替完整——这样你就不必拥有全屏的通话中 UI。并且如果你需要修改推送内容，你可以使用 notification service extension。例如，如果你需要解密它们。这就是 VoIP 推送与电话。现在谈静音会话。

所以当用户有一个消息 App 时，他们可能和很多不同的朋友或很多不同的朋友群发消息，其中一些会话可能相当吵闹，用户可能不想为那个特定会话收到提醒。但内容可能仍然相关，仍然有用。当用户回到 App 时，他们想能看到消息，他们只是不想每次消息进来时设备都震动来告诉他们。

因此我们需要一种方式，把内容可用这件事告知设备，但不告知用户。

为此，你应该使用后台推送。

后台推送是一种机制，用来告知设备有新数据可用，而不提醒用户。

要使用它们，你只需发送一条设置了 content available 标志为 1 的推送，不带 alert、sound 或 badge。然后系统会智能地决定何时启动 App 下载内容，依据功耗与性能影响，并尽量最小化它。在时间线上看，它可能像这样。用户可能把 App 置于前台并决定静音某个特定会话。然后在未来某个时刻，有人给那个会话发了消息，设备收到了一条后台推送。

在那之后的某个时间，App 会被启动并获得一些运行时间来获取该内容，然后当用户在当天晚些时候回到 App 并把它置于前台时，用户打开会话就会看到内容就在那里。并且，后台推送也有一些非常重要的新东西。

你必须把 apns-priority 设为 5，否则你的 App 不会被启动，你还应该把 apns push type 设为 background。这对 watchOS 是必需的，但我们强烈推荐所有平台都这么做。如果你想了解更多关于 watchOS 推送的信息，可以看昨天的 creating independent watch app session。所以总结一下：对于静音会话，把后台推送作为尽力而为的方式来下载内容；在 App 在后台推送被接收后可能没有获得运行时间的情况下，你总是可以在 App 重新进入前台时下载该内容。现在来谈下载过去的附件。假设用户登录他们的账户，这是新设备。他们可能立即想要账户里的一些内容，比如会话列表或最近的消息。

但可能有一堆旧内容，如果在用户正在使用 App 时下载，那就太好了。

为了可视化这一点，为什么要在用户在前台时下载并可能影响他们的性能或电池寿命，而我们可以在设备充电并空闲时的某个时刻下载呢。

实现方式是使用 discretionary background URL session。

这允许系统把下载推迟到更好的时机，它是一个 API，允许你传递更多信息，以便它在调度时更智能。要使用它，你只需像平时一样设置一个 background URL session，然后把 discretionary 标志设为 true。让我们看看你可能能够传递的一些额外信息，以便系统更智能。

你可以传递超时区间。也许你不想让它一直尝试下载某样东西，所以你想限定它做这件事的时间。

你可以传递一个最早开始日期。也许你不想在未来的某个点之前做上传或下载。你还可以传递一个预期工作负载大小，以便系统知道运行你的下载时应该预期做多少工作。

所以，当你下载过去的附件时，你想尽可能推迟工作以最小化用户可见的影响，而且我们可以把相同的原则应用到任何可推迟的下载或上传。所以，也许你有一些想批量打包并在更好的时机上传的分析数据，或者也许用户拍了一些你想稍后备份的照片。

所以总结一下，我们有一个消息 App，它具有一些核心功能。你可以发送消息、拨打电话、允许用户静音会话、下载过去的附件。我们用不同的 API 完成了每一件事。我们用后台任务完成来保证消息即使用户离开 App 也会发送；我们用 VoIP 推送作为启用电话的方式；我们用后台推送作为尽力而为的方式给 App 运行时间来响应新内容；我们用 discretionary URL session 在恰当的时机下载附件。

但仍有许多其他用例，我们现有的模式并未覆盖，因此我想邀请我的同事 Thomas 上台，介绍一种新的后台模式和为此设计的框架，专门针对这些用例。谢谢大家。谢谢，Roberto。

让我们谈谈这些用例。

这些包括主动与服务器同步状态、清理数据库，或把数据备份到云端。这些是可推迟的维护型任务，理想情况下你希望在后台做，以免影响前台用户活动。而今天我们看到的是，App 正在进入后台时就做这类工作，一天下来，这真的会累积起来。

所以，如果你能把所有这些工作推迟到稍后，比如设备充电并且空闲时再做，会怎样？这就是我们今年推出的东西：一种全新的后台模式，以及与之配套的全新框架，我们称之为后台任务。后台任务让你调度稍后在后台要做的工作。

我们在 iOS、iPadOS、tvOS，以及 Mac 上的 iPad App 上提供它。

我们不仅推出这种我们称为后台处理任务的新后台模式，还借此机会改进了现有的后台 App 刷新 API。让我们谈谈新的后台模式。后台处理任务给你的 App 在系统友好时刻提供几分钟的运行时间，这样你就能做我前面提到的那种可推迟的维护级工作，以及全新的事情，比如在后台进行设备端的 Core ML 训练与推理，你可以在它们的 session 中了解更多。

CPU Monitor 是我们系统中的一个功能，它会自动终止在后台使用过多 CPU 周期的 App，以保护用户的电池寿命。我们有史以来第一次，给你能力在处理任务期间把 CPU Monitor 关掉，这样当设备插电时，你可以充分利用硬件。最后，只要你请求任务时 App 在前台，或 App 最近在前台使用过，我们就会确保你有资格运行这些任务。接下来我想谈新的后台 App 刷新 API。

这是一个新 API，但它有和现有 API 相同的策略，这意味着每次你的 App 被启动时，它都会获得 30 秒的运行时间，来获取新内容并全天保持自身更新。

你的 App 多久被启动、在什么时间被启动，取决于用户历史上如何使用你的 App。

所以，如果用户通常在早上、下午和晚上使用你的 App，系统会学习这个模式，并在这些时间前不久开始启动你的 App，以便你有机会获取所需的内容。这也意味着，不那么频繁使用的 App 可能不会那么频繁地启动。正如我所提到的，这是后台 App 刷新的新 API，所以我们正在弃用 UIApplication 上现有的那些 API，这里显示的。

这些 API 会在 iOS、iPadOS 和 tvOS 设备上继续像今天一样工作，但它们不支持 Mac，所以请确保在 Mac 上为后台 App 刷新采用后台任务。

让我们看看这个 API 如何工作。

假设我们有一个 App 和其中包含的几个扩展。你将与之交互的主要对象是 BG Task Scheduler。

BG Task Scheduler 是你与系统智能、动态的活动调度器之间的接口，它持续监控各种系统条件，包括电池电量、App 使用情况、网络连接等。当你的 App 运行时，你可以请求它稍后被唤醒以在后台做工作。为此，你将创建一个 BG task request 对象的实例，对应你想执行的任务类型。在这种情况，我们想做后台 App 刷新，所以我创建了一个 BG app refresh task request。

然后我们把它提交给调度器。如果你有几种类型的任务想做，可以提交多个请求。在这种情况，我们还想做数据库清理，所以我将创建一个 BG processing task request 并同样提交。

你也可以在扩展运行时从扩展提交请求。

所以，如果我们的键盘扩展想基于用户的打字习惯做一些学习，它可以创建一个 BG processing task request 并同样提交。

如你所见，你可以有多个待处理的 BG processing task request，每个代表一个你希望你的 App 做的特定任务。现在调度器知道我们 App 想做的所有任务，当所有必要的系统条件和策略都满足时，它将通过唤醒你的 App、启动它进入后台并交付一个 BG task 对象来完成该任务，对应你应该执行的任务。在这种情况，我们得到了一个 BG app refresh task，所以现在我们可以执行后台 App 刷新、获取内容并更新 UI。

当我们完成时，我们会调用 set task completed，这会把任务标记为完成并允许你的 App 挂起。

根据你如何配置 BG task request 以及各种系统条件和策略，我们可能选择同时为多个任务启动你的 App。所以在这种情况下，我们的 App 被启动并交付了早前请求的两个 BG processing task。
