下午好，欢迎参加我们的“打造出色的性能分析体验”讲座。我是 Daniel Delwood，和我一起的还有 Kasper Harasim。今天，我们来讨论如何制作出色的自定义 Instruments 包。

作为开发者，我们都在努力编写优秀、可维护、模块化且可复用的代码。我们都用过别人设计的框架，也创建过希望别人能很好使用的代码。

良好的 API 设计和文档对于用户使用你框架的体验至关重要。但我希望今天你能考虑也开发一个 Instruments 包。

为了说明原因，以 Metal 为例。API 设计是核心，调用围绕着一组核心概念（设备、命令缓冲区、纹理等）组织。但这并非故事的全貌。API 表面（API surface）表达了什么是可能的，但文档和示例代码才是别人学习如何将这些概念组合成一个出色 App 的方式。但这依然不是故事的全貌。前两者都能帮助开发者使用你的类或框架编写代码。但出了问题怎么办？实际上，自定义 Instruments 是作为作者的你，教会其他人如何调试、优化并真正充分利用你 API 的一种方式。如果你在 Instruments 中使用过 Metal System Trace 模板，那你就已经看到了一些可能性。为你的概念和 API 专门创建可视化工具。Instruments 包是你构建透明度的一种方式，让用户了解你的框架是经过测试的、可理解且得到良好支持的。花时间创建自定义 Instrument 有助于建立信心和信任，让用户相信代码确实按预期运行。

工具也是开发成本模型的好方法，可以知道哪些调用开销大，哪些开销小。当存在性能问题时，工具是区分框架 bug 还是客户端代码 bug 的最佳方式。但最重要的是，Instrument 是你讲述自己故事的机会。Instruments 包让你能够解释正在发生的事情，帮助可视化重要指标，并帮助用户在问题出现时快速定位。所以今天，我们将涵盖如何从内到外构建出色的仪器化，从在你的框架中开发出色的跟踪点开始，然后通过模式（schema）、建模（modeling）和结构在 Instruments 内部构建，最后讨论可视化和 Instrument 的 UI。因此，以跟踪、建模和可视化作为今天的路线图，让我们直接开始讨论 OSSignpost。

OSSignpost 是 2018 年引入的一种低成本跟踪原语。Signpost 有两种类型：事件（event）和区间（interval）。它们通过类似 printf 的格式化字符串和参数来支持记录任何类型的数据。与 printf 不同的是，所有 signpost 都使用静态字符串命名。

在 Swift 中，OSSignpost 是一个核心 API，有三种类型：开始（begin）、结束（end）和事件（event）。在 C 中，其接口通过三个便捷宏暴露。

需要注意的是，OSSignpost 构建在 OSLog 之上，这意味着许多跟踪行为和可配置性由提供的日志句柄决定。

日志句柄实际上是用于跟踪的命名空间。它们允许你指定子系统（subsystem）和分类（category），再加上每个 signpost 的静态名称，为你的跟踪点提供了逻辑结构（logical structure）和层级关系（hierarchy）。

自定义 Instruments 基于 OSSignpost 有两个主要原因。首先，它们是时间性的（temporal）。

所有 signpost，无论是事件还是区间，都会隐式记录高精度时间戳。

在我们高度并发的世界里，为重叠的区间提供一等支持也很重要。OSSignpost 通过 Signpost ID 做到了这一点。这些 ID 记录了足够的上下文来匹配相关的事件，即使开始或结束事件发生在不同的线程（thread）或不同的调度队列（dispatch queue）上。OSSignpost 的第二个原因是它们成本低廉。日志机制在设计上考虑了效率，当你提交一个 OSSignpost 时，它记录的数据量最少。关于静态字符串有一些优化，例如你的格式化字符串和 signpost 名称实际上作为二进制文件文本段的一个偏移量被发出。实际上，OSSignpost 的开销足够低，在大多数情况下你可以将它们保留在生产代码中。这使得它们不仅有助于在你的工作台上解决问题，也适用于构建调试优化后代码的工具。当 Instruments 记录 signpost 数据时，你将能访问所有显式指定的字段，包括格式化字符串和你提供的参数。但在 Instruments 中，你还可以访问所有隐式指定的字段，比如时间戳或调用线程，这非常有用。如果你使用的日志句柄启用了回溯（backtraces），那么调用栈也会被记录并在 Instruments 中提供。

因此，在向代码添加跟踪时，需要注意 OSLog 和 OSSignpost 有三种不同的模式。默认情况下，OSLog——每个 OSLog 句柄都启用了 signpost。即便如此，它们仍然是低成本的，仅记录到一个环形缓冲区。

当 Instruments 或其他客户端请求立即显示这些数据时，OSLog 系统会进入流式模式，该模式的成本稍高。

但今年有两个新的动态分类（dynamic categories），仅在 Instruments 记录时才启用。这些动态分类被配置为记录栈回溯，第二个分类会增加一些额外开销。考虑到这一点，OSSignpost 的实际成本是多少？嗯，许多因素会影响实际性能，如设备类型、硬件型号、操作系统版本、系统负载、发热情况等，因此很难给出一个精确的数字。但我想在对数坐标上给出一些数量级的近似值，因为我认为这有助于了解相对成本。如果我们看看发布构建中的 Signpost，它们的耗时都在一微秒以下。新的默认关闭的动态分类实际上在低纳秒范围内。

当 Instruments 以延迟（deferred）或最后几秒模式记录时，这些动态分类会开启以匹配默认开启分类的行为。它们的开销相同，除了动态栈分类，由于记录调用栈，其成本稍高，在低微秒范围内。然而，当需要使用流式模式时，所有这些的成本都会显著增加，达到数十微秒的范围。那么，如果你担心运行时开销，或者这些开销开始出现在你的分析数据中，你可以做些什么来在记录时最小化 OSSignpost 的开销呢？有两件简单的事情可以做。首先，你可以使用 Instruments 的延迟或最后几秒模式，而不是即时模式。这可以使 OSSignpost 避免进入流式模式，从而减少开销。而且，在打开模板时，很容易将其配置为在这些模式之一中记录。

此外，如果你使用新的动态跟踪分类，这是在不记录时最小化开销的好方法。因为这些 signpost 默认是关闭的。它们只能由自定义 Instruments 启用，所以这些数据也不会挤占内置 OSSignpost 工具中的轨道。那么，作为框架或子系统的作者，在你进行性能分析时，发射多少个 signpost 是合理的呢？嗯，你可以发射很多。但让我们假设一个非常保守的目标：在分析时，将开销保持在单个核心 CPU 使用率的 1% 以下。然后，假设每个启用的 signpost 大约有半微秒的粗略成本。

那么，计算结果是每秒 20,000 个 signpost。即使在 iPad Pro 上以 120 帧每秒运行的显示链路（display-link）上下文中，这仍然足以每帧使用 83 个区间。

再次强调，实际性能会发生变化，这些只是估算值。因此，重要的是要记住，signpost 是一种共享资源。你用得越多，对日志系统的影响就越大。尽管如此，它们的设计允许这种高速率跟踪，有时这非常有用。有时，这是找出代码中管道安装或排序问题的关键。不过，请记住，你可能希望根据受众将 signpost 分离到不同的分类中。你框架的客户端可能需要的细节比框架贡献者要少，后者可能需要跟踪更多实现细节。如果你将跟踪点分散到多个日志句柄，那你的工具就可以只启用必要的子集。

由于跟踪是仪器化的基础，我想快速介绍四个最佳实践。

首先也是最重要的，始终结束你开启的任何区间。这对于正确性至关重要，永久开放的区间也可能会严重拖慢 Instruments 的分析速度。

在这个例子中，我们有 OSSignpost 调用包裹了一段昂贵且可能抛出错误的代码。问题是，如果抛出错误，控制流会跳转到 catch 作用域，完全跳过了我们的结束 signpost。

Swift 的 `defer` 语句是处理此问题的好方法，确保无论提前返回还是抛出错误，当退出当前作用域时，结束 signpost 调用仍然会被执行。

其次，为了提高效率，避免在开始和结束跟踪点中记录相同的数据，而应在首次可用的点记录。这可以避免重复工作，并使 Instruments 尽快获得一个值。在这个例子中，我们不需要重复请求号或原始大小，并且为了防止重叠时匹配区间，这些点实际上可以为这个日志句柄的每对区间生成一个唯一的 Signpost ID。

第三，当 signpost 未启用时，避免做不必要的工作。如果你的日志句柄配置使用了一个动态跟踪分类，那么 `signpostsEnabled` 属性会指示 Instruments 当时是否正在记录，这意味着这是将昂贵的计算放在检查之后的好方法。

第四，只跟踪你的工具实际需要的数据。思考你的 guard 语句和前置条件（preconditions），因为有时你会想要跟踪它们以包含短区间。例如，如果你的方法想查看缓存命中与缓存未命中的区别。

但其他时候，这些提前返回可能不感兴趣。对于这些情况，考虑将 signpost 移到前置条件之后，以减少发送给 signpost 系统的数据量。

有了所有这些技巧，记住跟踪点实际上是你在其上构建的所有工具的基础，这很重要。大多数时候，它们会存在于你的生产代码中。所以，这就是为什么考虑跟踪点的性能和可维护性很重要。由于它们位于核心，对 signpost 调用的更改可能会导致需要更改在此基础上构建的工具。因此，为保持跟踪点的稳定，避免跟踪实现细节，并尽可能将 OSSignpost 调用添加到靠近 API 层的地方。

在代码库中移动跟踪点不是问题。你不需要担心编译器优化（如内联）可能会为你移动它们。

你需要确保不变的是静态字符串，具体来说，我是说子系统、分类、signpost 名称或格式化字符串。如果你更改了其中任何一个，你需要记得同时更新你的 Instruments 包。

那么，让我们继续讨论在 Instruments 内为数据添加建模和结构。

Instruments 的架构基于所有内容都存储在表中。模式定义了这些表的结构，所有这些都由 Instruments 的即时分析核心进行测量。有关 Instruments 架构的更深入介绍，我推荐观看 2018 年的“创建自定义 Instruments”讲座。现在，让我们看看建模如何融入创建性能分析体验。左侧，我们已经介绍了 OSSignpost，这是 Instruments 记录的主要数据源之一。这些数据被填入具有预定义模式的表中，供你的自定义 Instruments 使用。

建模是中间的下一个阶段。模型器（modeler）观察来自一个或多个输入表的数据，进行推理，然后向一个或多个你规范定义的输出表发射数据。

模型器是你的领域特定逻辑所在之处，输出表的模式是你的规范，指定了要对数据应用哪些类型和格式化器。

最右侧的步骤是可视化，在 Instruments 中通过 XML 描述给标准 UI。它指定了如何绘制和显示模型器输出表中的数据。比如哪些列用于绘图并使用其值，或者哪些列用于标签和颜色。

由于所有自定义 Instrument 的可视化都基于你的模式和模型器的输出，因此有必要讨论一下检查 OSSignpost 跟踪点是否良好，以及如何将这些数据放入你自定义定义的模式的整个过程。

因此，自定义 Instrument 中的所有数据都必须存储在表中，这些表以两种方式之一处理数据。点模式（point schema）有一个时间戳列，区间模式（interval schema）则同时有时间戳和持续时间列。这意味着你需要至少定义一个点或区间模式，然后为其余列指定名称和类型。

数据将由作用于输入数据的建模规则（modeling rules）填充。这些规则用 Eclipse 语言表示。好消息是，Instruments 提供了一些会自动生成模型器的模式。因此，在你想之前，你不需要去编写 Eclipse 代码。

实际上，如果你刚开始，想确保数据正确，Instruments 在库（library）中提供了一个内置的 OSSignpost 工具，非常适合记录和检查你的 OSSignpost 区间是否合理。检查器（Inspector）可以帮助你验证原始数据是否正是你期望的。

一旦你检查了数据，新的 Instruments target 是开始构建自己工具的好方法。借助 Xcode 为自定义 Instruments 内置的 XML 代码片段，只需几个元素就可以在库中拥有一个自动模型器和一个 Instrument。而看到其效果的最佳方式是通过演示。为此，我想邀请 Kasper 上台。谢谢你，Daniel。大家好。

由于 Instruments 处理两种时间排序数据：点和区间，我想讨论一下显示两者的方法。

要总结事件，评估它们的重要性是有帮助的。如果它们都相对同等重要，那么直方图（histogram）是在时间线上显示事件密度非常好的方式。较高的柱状图能让人一眼就看出从哪里开始看、从哪里开始放大。对于自定义 Instruments，绘图行为很容易自定义。直方图元素允许你指定每个时间桶的宽度，还有一个 `bestForResolution` 元素，可以让用户缩小时使用直方图，而放大时则替换为单个事件的绘图。

当事件的重要性不同时，有时为关键事件专门分配一条轨道是很有帮助的。

多个图形和详情视图可以引用同一个表中的数据，因此指定顶部绘图（top plot）只需要向 Instruments 描述如何切片以及从表中选择哪些值来显示。这两种情况都可以完全在 XML 中实现，无需自定义模型器。

点数据或区间数据的表格摘要是你定义哪些指标重要的机会。在聚合详情视图（Aggregation Detail view）中，有 Min、Max、Average 和 Standard Deviation 等函数用于组合值。新用户会查看你提供的这些摘要，以了解哪些是重要的、哪些需要优化。因此，甚至像列标题是什么或它们出现的顺序这样的显示属性都很重要。当用户进一步深入了解细节时，叙述工程类型（Narrative engineering type）是解释发生了什么的好方法。它允许你使用自然语言和其他类型格式化器，以一种易懂的方式解释运行时行为。这些视图是告诉用户本应发生但未发生的事件，或者当他们可能想要进一步调查的某些有趣事件的好方法。

绘制区间数据可能有点棘手。

与点不同，区间通常不能放在单个垂直空间中，因为它们会重叠。如果你可以处理固定或有界数量的重叠区间，有两种方法可以将一个轨道垂直拆分为多个视觉区域。限定图（Qualified plots）适用于将轨道拆分为多个带有单一标题的空间，而实例图（Instance plots）适用于每个空间都有自己的标题。OSSignpost 工具同时使用了这两种技术，但这仅在要显示的重叠区间数量有限时才有效。

当有很多重叠区间时，Instruments 11 中新增的层级（Hierarchies）可能是一条出路。

将跟踪数据分离到嵌套轨道中，使得更容易过滤、查找甚至固定你正在寻找的内容，特别是当绘图上下文数量很大时。但无论你是否提供轨道层级，规划好汇总你的区间数据都很重要，无论是在层级的每个级别还是作为你的 Instrument 的主要图形。对于简单的区间数据，可能会想使用与点数据相同的解决方案，使用直方图元素。
