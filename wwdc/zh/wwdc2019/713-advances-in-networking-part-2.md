发现代理（discovery proxy）解决了这个问题。

以前，一直建议在浏览时将 domain 参数指定为 nil。这一点现在仍然适用，并且在几乎所有情况下都是正确的做法。

过去你可能没注意到太大区别，但现在这开始产生更大的影响。指定 local 会明确阻止发现任何远程或代理的服务。这很可能不是你想要的。所以请仔细检查你的浏览调用是否无意中指定了 domain。

另外，在为你的 App 构建服务浏览功能时，我们来看看 Network.framework 中的一些新特性如何让 Bonjour 浏览变得更简单，特别是在 Swift 中。

去年，我们随 Network.framework 引入了 NWListener 和 NWConnection。例如，你可以有一个 NWListener 来发布 Bonjour 服务，也可以有一个 NWConnection 来连接到 Bonjour 服务端点。

今天，我们激动地宣布，通过 NWBrowser 对象，Network.framework 原生支持了浏览功能。

NWBrowser 加入到了 connection 和 listener 的行列，覆盖了从发布、发现到连接的整个工作流程，全都使用你已经熟悉的 Network.framework 对象。

许多服务器在其 DNS 记录上配置了非常短的生存时间（TTL）。它们这样做是为了，如果服务器宕机或服务器想要通过另一个 IP 地址进行负载均衡，它可以快速更改 IP 地址记录，让客户端调整并开始使用新地址。

然而，缺点是这会严重影响客户端性能。

由于 TTL 很短，客户端几乎总是需要花一个往返时间来执行 DNS，请求你想要连接的主机名的地址。对于有高延迟链路的客户端来说，这尤其糟糕。这将在它们的连接时间上增加数百毫秒甚至数秒。最糟糕的是，大多数情况下，服务器地址根本没有改变，所以这是一个浪费的往返。

因此，乐观 DNS（Optimistic DNS）是我们去年发布的一个解决方案，用于解决这个问题。

乐观 DNS 允许你的连接乐观地连接到该主机名上次已知的好的 IP 地址，同时并行地发出一个针对该主机名当前地址的新查询。

如果没有变化（绝大多数情况都是如此），连接将直接建立到旧的 IP 地址。但如果发生了变化，你仍然会得到新的 IP 地址并连接到它。我们已经对此做了大量测量和测试，这是一个非常好的解决方案。所以今年，对于使用 Network.framework 和 URLSession 的连接，它默认是开启的。

我知道很多人对此感到兴奋。在联网方面，Apple 平台之间的差异非常小。有一件事你们需要注意，在你们的 Xcode 设置中，当你勾选 Mac 的复选框时，你现在会看到一些新的选项。默认情况下，允许出站连接，但如果你也想允许你的 App 的入站连接，你必须勾选那个复选框。

在 watchOS 上，我们有新的联网能力。

使用 AVFoundation 进行音频流式传输的应用现在可以使用直接联网，只要它们使用 URLSession 或 Network.framework。

Sockets 不可用。

我们还引入了 TLS 1.3，它带来了很多好处。

TLS 1.3 的连接性能更好。TLS 1.2 通常需要两次往返来建立连接。TLS 1.3 几乎总是在一次往返中完成。

TLS 1.2 使用的加密算法当时被认为是好的，但后来已经暴露出一些弱点。这不仅仅是学术上的担忧。这些弱点在实践中已经被利用过。

所有这些在 TLS 1.3 中都已被移除，并且 TLS 1.3 中的所有加密算法都支持关联数据的认证加密和前向保密。

最后，你们都知道隐私对 Apple 非常重要。TLS 1.3 有更好的隐私保护。TLS 1.2 中的许多头部字段和证书是明文发送的。现在在 TLS 1.3 中，这些都被加密了。所以，行动呼吁是开始在你的应用中使用 TLS 1.3，当然，也要确保你的服务器更新到支持 TLS 1.3。现在，你们都知道隐私对 Apple 的重要性。我们意识到的一件事是，访问 Wi-Fi 信息可能被用来推断位置。所以从现在开始，要访问那些 Wi-Fi 信息，你需要拥有获取其他位置信息时所需的同类型的权限。

第一步是在 Xcode 中，你必须添加访问 Wi-Fi 信息的能力，将 entitlement 添加到你的项目中，然后你的 App 必须满足三个其他条件之一。如果用户已经给了你的 App 位置访问权限，那么你可以访问 Wi-Fi 网络信息。

如果你的 App 是设备上当前已启用的 VPN App，你可以访问该信息。最后，如果你的 App 是任何热点配置 App，那么它也可以访问该信息，但只能访问它已经配置过的网络。

更多信息你还可以参考 Wi-Fi 框架。今天你已经听到了很多次，我将以提醒使用网络链路调节器的重要性来结束。

当你在模拟器中开发你的应用时，在带有千兆以太网的 Mac 上，或者通过回环与本地服务器通信，这很容易。当你有一个零延迟、无限带宽的服务器时，它表现良好不足为奇。但如果你那样构建你的应用，可能会非常具有误导性，你以后可能会发现，当你的 App 到了真实用户手中时，它表现得并不好。如果你养成习惯，去设备条件（Device Conditions）中选择一个真实的网络链路条件，从你开始开发应用时就一直这样做，并且总是在模拟真实网络条件下测试和运行你的应用，那么那些 bug 一开始就不会发生。我们多年来一直在传达的另一个信息是避免预检检查。使用诸如 allowCellular 或 allowExpensiveNetwork 这样的约束条件可以给你更好的控制。使用起来也容易得多。一旦你开始以这种方式编写你的 App，你会想不通当初为什么要做预检检查。更何况，预检检查从来都不能可靠工作，因为它们总是会有竞争条件。

为了说明这一点，我将用一个例子。这是一个我真的很喜欢的 App。为了说明问题，我用一个故意夸张的例子来展示，如果它是一款编写得很糟糕的 App，可能会做什么。这个例子告诉用户：“确保我们在 Wi-Fi 上，然后点击按钮”。但是用户没有办法控制网络连接会走哪条路径，他们通常会寻找 Wi-Fi 信号格数，然后祈祷一切顺利。但正如你今天所学到的，在你尝试之前，预先知道 Wi-Fi 会表现如何是不可能的。设备可能认为它已连接到 Wi-Fi，但当它尝试使用时，却发现它实际上不可用。现在，当 Wi-Fi 助理将你从 Wi-Fi 切换到蜂窝网络时，那些 Wi-Fi 信号条将会消失，但到那时已经太晚了，你的连接已经发生了。所以，不要让用户去猜。不要只是建立连接然后指望最好。让我向你展示这个应用实际上是怎样工作的。它将其连接设置为受限，不允许使用蜂窝网络。并且从 iOS 13 开始，它可以使用 allowsExpensiveNetworkAccess 控制来让系统决定哪个是昂贵的网络。

它还设置了 waitsForConnectivity 等于 true。这意味着应用不必重复重试。系统会耐心等待，直到连接成功。

当应用尝试连接时，如果没有 Wi-Fi，它的 taskIsWaitingForConnectivity 委托会被调用，那时它可以显示 UI，给用户选择：要么移动到有 Wi-Fi 的地方，要么如果你想继续，可以按下按钮使用蜂窝数据。
