女士们先生们，下午好。欢迎参加文件系统分会。在本场会议中，我们将介绍与文件系统相关的几个主题。首先，我们将了解文件系统在保护 macOS 系统软件方面扮演的角色。

APFS 引入的特性之一是内置的卷管理器。

卷的概念对 APFS 来说并不新鲜。它们在 HFS Plus 中就已存在。

HFS Plus 卷与此分区是一一映射的。并且它占据磁盘上连续的 block 范围。

由于这种与分区的一一映射关系，HFS Plus 卷不容易添加。为了在已分区的磁盘上添加新卷，你需要先缩小现有卷。然后才能添加新卷。APFS 卷要灵活得多，因为它们与其兄弟卷共享磁盘分区空间。

这种灵活性使得系统的更高层能够实现一些功能，而这些功能在旧式卷上是无法实现的。

我们将在 APFS 中实现的功能之一是保护系统软件免受恶意或意外更新。

你可能还记得在 macOS El Capitan 时代，我们引入了系统完整性保护（System Integrity Protection）的概念。

它用于控制对目录层次结构部分的访问。

某些目录会被写保护，而文件系统的其他部分则允许修改。今年，我们要更进一步。我们将使整个根文件系统变为只读。

显然，一个无法安装新软件或用户无法保存数据的系统用处不大。

为了理解如何调和只读和可写这两个相互冲突的目标，让我们来看一下从 macOS Mojave 升级到 macOS Catalina 时会发生什么。macOS Mojave 上的典型容器会有一个主卷和几个服务卷。例如，VM 卷。主卷用于存储用户数据和系统软件。

当我们开始升级到 macOS Catalina 时，我们首先更改主卷的角色，并将其标记为数据卷。

然后我们可以修剪目录层次结构中仅包含系统软件的部分。

完成此操作后，我们可以进入下一阶段，创建一个新的空卷，该卷将仅用于存储系统软件。我们将用系统内容填充该卷。一旦这个过程完成，我们就可以在保护方面宣布胜利。我们是只读的。我们受到了保护。这很好，但这还不够。

我们仍然需要以某种方式将新的系统内容与用户内容联系起来。为此，我们引入了卷组（volume group）的概念。一个卷组由一个数据卷和一个系统卷组成。并且它们被视为一个单一的实体。

用户界面将其呈现为单个磁盘。它们共享加密状态。如果你的卷已加密，则可以使用相同的密码来解锁两个卷。几乎所有方面看起来都像一个统一的实体。

还缺少一样东西。我们仍然需要以某种方式提供单个目录层次结构的假象。传统上，这是通过将文件系统挂载到根文件系统的目录上来完成的。

由于需要引入的交叉点数量和文件系统中所需的卷数量，这种方法变得相当昂贵。因此，为了解决这个问题，我们引入了一个名为 Firmlink 的新概念。Firmlink 是一种新的文件系统对象。

它类似于符号链接（Symlink）。但与符号链接不同，Firmlink 支持前后路径反转，其表示是一致的。这种一致性相当重要。如果你曾经处理过一个坚决要求位于特定目录（例如 Applications 目录）的应用，你就会知道必须能够从文件系统的顶部向下遍历到叶子节点，然后再返回，并得到相同的路径。我们可以通过 Firmlinks 做到这一点。

Firmlink 是从系统卷上的目录到数据卷上的目录的遍历点。

它们只有一对一的映射。一个源。一个目标。

你不能使用 Firmlink 跨越卷组的边界。

Firmlink 对用户和应用来说是相当透明的。它们由安装程序在安装时创建。它们不应该被注意到。

一旦我们有了这个新工具，我们就可以用它来缝合各个卷。安装程序将在系统卷上创建入口。

并将它们指向数据卷上相应的卷。

完成后，我们就有了一个统一的目录层次结构。我们可以重新启动，将根卷挂载为只读，并享受它带给我们的保护。

生活很美好。一切都受到了保护。一切都在运行。但你仍然需要记住，卷在安装过程中会被拆分。这是无法避免的。它会发生。在开发者预览版中，我们选择将根文件系统保持为可写，以便你更容易测试你的应用。如果你想模拟未来版本中的行为，可以在根目录中创建一个特殊文件，重新启动后，你的卷将被挂载为只读。

这将在下一个版本的下一个 seed 中改变。

在发布版本中，如果你禁用系统完整性保护，你仍然可以将根文件系统挂载为读写。

但这不是持久的更改。重新启动后，它会恢复到只读状态。你可以再次将其重新挂载为只读或读写。

同样，在重新启动时，它会恢复到相同的状态。

正如你可以想象的，这是 macOS 形态和安装方式的一个相当大的变化。这可能会影响到某些应用。例如，如果你的应用在文件系统上使用了复杂的布局，或者附带了安装程序包，请确保它在新的只读根分区上正常工作。

听起来很简单。但重要的一点是，我们希望这个副本的保真度尽可能地高。通常，仅仅进行逐文件复制是不够的。我们希望复制所有卷内容。所有数据、所有元数据、卷属性。如果源卷包含可启动的操作系统，我们希望复制使该卷可启动的元数据，以便我们副本的目标卷也是可启动的。现在，我将介绍 Apple 软件还原（Apple Software Restore）命令行工具（即 ASR）上下文中的复制。ASR 已经存在很长时间了。你们中的许多人可能对它很熟悉。它的主要功能是做卷复制。

现在，使用 ASR，我们复制的源很常见是一个磁盘映像。在这种上下文中，我们通常将执行此复制到目标卷的过程称为还原（restoring），因此得名 Apple 软件还原。但你会听到我基本可以互换地使用术语“还原”和“复制”。

并且它的数据可能与同一容器中另一个卷（如此示例中的卷 2）的数据交错。

此外，我们当然关心安全性和隐私。所以我们必须考虑加密。现在，在 APFS 中，加密是在文件系统级别完成的。更重要的是，在具有 T2 安全芯片的内部存储设备的 Mac 上，该加密始终处于开启状态。并且它与硬件直接绑定，这意味着它特定于该 Mac 中的那个存储设备。因此，如果我们尝试复制该卷的块并将其带到别处，它们将无法解密。所以结果是，对于 APFS 卷，块复制确实不是一种可行的复制方式。那么，我们如何将其与我们的需求协调起来呢？在 macOS Catalina 中，我们引入了使用 ASR 进行的 APFS 卷复制。ASR 和 APFS。谢谢。ASR 和 APFS 紧密集成。ASR 可以让 APFS 从源卷生成一个流。然后该流被写入目标卷。现在，由于 APFS 正在生成这个流，它知道需要从哪里读取源卷的各个部分。

因此，源卷不是连续的块设备就不是问题了。

至于加密，如果源卷已加密，那么当流生成时，其中的数据将被即时解密。当然，如果源卷受 FileVault 保护，那么在进行此复制之前，它需要由用户操作解锁。如果目标卷本身已加密，那么当数据从流写入目标卷时，它会被（或已经被）加密。在这种情况下，数据在到达目标卷时从一开始就是加密的。好吗？这种复制的另一个不错的功能是，在生成流时，卷数据会即时进行碎片整理。元数据被压缩，因此生成的流以及由此产生的目标卷都得到了很好的优化。这可能是一种很好的方式来制作主映像（master image），例如。如果你正在制作一个映像，并且最后一步是执行复制操作，那么你的映像卷将得到很好的优化。

那么这对你作为开发者意味着什么呢？正如我所说，如果你在 iOS 13 或更高版本上链接，就可以使用。所以，重新构建你的应用并进行测试。

我们正在向 iOS 添加五种不同的文件系统类型。这些文件系统的行为与内部闪存存储上的 APFS 略有不同。

一个区别是 iOS 一直使用区分大小写的文件系统。FAT 和 ExFAT 不区分大小写。

而 HFS 和 APFS 可以配置为任一种方式。

“克隆”系统调用可能并不总是可用。

因此，如果这些差异对你很重要，或者正因如此，请注意卷的功能。有两个不同的 API（或者说几个 API）可以为你获取这些信息。我想特别指出的是 NSURL 中的 resourceValues。

这些可以为你提供正在使用的文件系统的参数。

另一个重要点是，文件移动可能需要时间。因此，请将你的临时文件放在工作文件附近。如果你不这样做，这个提示会很有帮助。因为“保存-保存”在最后使用重命名，以便用户始终看到正确的文件。他们要么看到他们开始时的文稿，要么看到新的保存。

为了实现这一点，我们需要那个重命名。而这只有在它们位于同一文件系统上时才有效。

此外，如果你不注意临时文件，它们最终可能会落在内部存储上的容器中。这将导致大量不必要的 IO。

文件管理器（File Manager）可以帮你解决这个问题。如果你请求一个适合你的文稿的 itemReplacementDirectory 的 URL，它会给你一个同一文件系统上的临时目录。

另一件事是，外部设备可能会消失。

网络可能超出范围。文件服务器可能宕机。小猫可能会断开电缆。

这些事情都可能发生。你的应用需要能够稳健地面对这些情况。我特别想指出的一点是，mmap 可能很危险。它可能非常强大。但是如果文件消失了，内核能通知你的唯一方式是通过总线错误（BUS error）。

所以，有一点是，如果你在使用 NSData，你可以给 NSData 一个提示，说如果安全的话，从这个文件中 mmap 数据。

最后一点是，所有外部设备的延迟都高于内部闪存存储上的 APFS。

因此，如果你正在进行大规模的 IO，请保持多个操作并发执行。
