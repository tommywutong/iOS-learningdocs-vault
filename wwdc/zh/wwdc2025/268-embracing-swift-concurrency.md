大家好！我是来自 Swift 团队的 Doug，很高兴能与大家讨论如何在你的 App 中充分利用 Swift 并发。

并发允许代码同时执行多个任务。你可以在 App 中使用并发来提升等待数据时的响应能力，例如从磁盘读取文件或执行网络请求时。它还可以用于将计算密集型的繁重任务卸载到后台，例如处理大型图片。

Swift 的并发模型旨在让正确编写并发代码变得更加容易。它显式地标记出并发的引入，并识别哪些数据在并发任务之间共享。

它利用这些信息在编译时发现潜在的数据争用，这样你就可以在需要时引入并发，而无需担心产生难以修复的数据争用。

许多 App 可能只需要在少数场景下使用并发，有些则完全不需要。并发代码比单线程代码更复杂，你应该只在需要时才引入并发。

你的 App 应该从将所有代码运行在主线程开始，单线程代码已经能覆盖很多需求。主线程是你的 App 接收 UI 相关事件并相应更新 UI 的地方。如果你的 App 没有执行大量计算，将所有内容保留在主线程上就很好！最终，你可能需要引入异步代码，例如通过网络获取一些内容。

你的代码可以等待网络传回内容，而不会导致 UI 挂起。

如果这些任务运行时间过长，我们可以将它们移到一个与主线程并发运行的后台线程。

随着我们进一步开发 App，我们可能会发现将所有数据保留在主线程内会导致 App 性能不佳。这时，我们可以引入专用于特定目的的数据类型，这些类型始终在后台运行。

Swift 并发提供了诸如 Actor 和任务之类的工具来表达这类并发操作。一个大型 App 可能具有类似这样的架构。但你不必从那里开始，也不是每个 App 最终都需要这样。在本场讲座中，我们将讨论将一个 App 从单线程逐步演变为并发的各个步骤。对于每一步，我们都会帮你确定何时采取这一步、你将使用哪些 Swift 语言特性、如何有效使用它们，以及它们为何如此工作。首先，我们将描述单线程代码如何与 Swift 并发协同工作。然后，我们将引入异步任务来处理高延迟操作，例如网络访问。

接下来，我们将引入并发以将工作移至后台线程，并学习如何在不引入数据争用的情况下在线程间共享数据。

最后，我们将使用 Actor 将数据移出主线程。

让我们从单线程代码开始。当你运行一个程序时，代码开始在主线程上执行。

你添加的任何代码都保留在主线程上，直到你显式引入并发以在别处运行代码。单线程代码更易于编写和维护，因为代码一次只做一件事。如果你之后开始引入并发，Swift 会保护你的主线程代码。

主线程及其所有数据由主要 Actor 表示。主要 Actor 上没有并发，因为只有一个主线程可以运行它。我们可以使用 `@MainActor` 标记来指定数据或代码位于主要 Actor 上。

Swift 会确保主要 Actor 代码只会在主线程上运行，并且主要 Actor 的数据只会从主线程访问。我们说这样的代码隔离到主要 Actor 上。

默认情况下，Swift 使用主要 Actor 保护你的主线程代码。

这就像 Swift 编译器在该模块的所有内容上为你添加了 `@MainActor`。它允许我们在代码中的任何位置自由访问共享状态，例如静态变量。在主要 Actor 模式下，在开始引入并发之前，我们不必担心并发访问。

默认使用主要 Actor 保护代码是由构建设置驱动的。这主要适用于你的主 App 模块以及任何专注于 UI 交互的模块。对于使用 Xcode 26 创建的新 App 项目，此模式默认启用。在本讲座中，我们将假设在代码示例中都启用了主要 Actor 模式。

让我们在我们的图片模型上添加一个方法，从 URL 获取并显示图片。我们想从本地文件加载图片。然后解码，并在 UI 中显示。

我们的 App 中完全没有并发。只有一个主线程在做所有工作。

整个函数在主线程上一次性执行。只要这里的每个操作都足够快，那就没问题。

目前，我们只能读取本地文件。如果我们想让 App 能够通过网络获取图片，我们需要使用不同的 API。

这个 URLSession API 允许我们在给定 URL 的情况下通过网络获取数据。但是，在主线程上运行这个方法会冻结 UI，直到数据从网络下载完成。

作为开发者，保持 App 的响应能力很重要。这意味着要注意不要让主线程占用太长时间，以免导致 UI 卡顿或挂起。Swift 并发提供了有用的工具：异步任务可以在等待数据（例如网络请求）时使用，而不会占用主线程。

为了防止此类挂起，网络访问是异步的。

我们可以改变 `fetchAndDisplayImage`，让它能够处理异步调用：将函数设为 `async`，并使用 `await` 调用 URL session API。

`await` 指示了函数可能挂起的位置，这意味着它停止在当前线程上运行，直到它等待的事件发生。然后，它可以恢复执行。

我们可以将其视为将函数分成两部分：一部分运行到我们开始获取图片之前，另一部分在图片获取完成后运行。通过这种方式拆分函数，我们允许其他工作在两部分之间执行，从而保持 UI 的响应能力。

在实践中，许多库 API（如 URLSession）会为你将工作卸载到后台。我们仍然没有在自己的代码中引入并发，因为我们不需要！我们通过使部分代码异步化并调用替我们卸载工作的库 API，改进了应用程序的响应能力。我们只需要在我们的代码中采用 `async`/`await`。

到目前为止，我们的代码只运行一个异步函数。一个异步函数在一个任务中运行。任务独立于其他代码执行，应被创建来端到端地执行特定操作。通常，会响应某个事件（例如按钮按下）而创建任务。这里，任务执行完整的获取并显示图片操作。

一个给定的 App 中可能有许多异步任务。除了我们一直在讨论的获取并显示图片任务之外，这里我添加了第二个任务，它获取新闻，显示它，然后等待刷新。每个任务将按顺序从头到尾完成其操作。获取操作在后台进行，但每个任务中的其他操作都将在主线程上运行，并且一次只能运行一个操作。这些任务彼此独立，因此每个任务可以在主线程上轮流执行。主线程将在各个任务准备好运行时，运行它们的片段。

单个线程在多个任务之间交替执行称为“交错执行”。这通过最有效地利用系统资源来提高整体性能。线程可以尽快在任何任务上开始取得进展，而不是在等待单个操作时让线程空闲。

如果获取图片在获取新闻之前完成，主线程将在显示新闻之前开始解码和显示图片。

但是，如果获取新闻先完成，主线程可以在解码图片之前开始显示新闻。

当你的 App 需要同时执行许多独立操作时，多个异步任务非常有用。当你需要以特定顺序执行工作时，你应该在单个任务中运行该工作。

为了使你的 App 在有高延迟操作（如网络请求）时保持响应，请使用异步任务来隐藏该延迟。库可以在这方面提供帮助，它们提供异步 API，这些 API 可能会代表你执行一些并发操作，而你的代码仍保留在主线程上。URLSession API 已经为我们引入了一些并发，因为它正在后台线程上处理网络访问。我们自己的获取并显示图片操作正在主线程上运行。我们可能会发现解码操作耗时过长。这可能会在解码大型图片时表现为 UI 挂起。

异步、单线程通常足以满足一个 App 的需求。但是，如果你开始注意到你的 App 响应不佳，这表明主线程上发生的事情太多了。诸如 Instruments 之类的性能分析工具可以帮助你确定哪些地方花费了太多时间。如果这些工作可以通过不使用并发来加速，请先这样做。

如果无法使其更快，你可能需要引入并发。并发允许部分代码在后台线程上与主线程并行运行，因此不会阻塞 UI。它还可以通过使用系统中更多的 CPU 核心来更快地完成工作。

我们的目标是将解码操作移出主线程，使其可以在后台线程上进行。因为我们默认处于主要 Actor 模式，所以 `fetchAndDisplaylmage` 和 `decodelmage` 都隔离到主要 Actor。主要 Actor 代码可以自由访问所有仅可通过主线程访问的数据和代码，这是安全的，因为主线程上没有并发。

我们想卸载对 `decodeImage` 的调用，这可以通过将 `@concurrent` 特性应用于 `decodeImage` 函数来实现。

`@concurrent` 告诉 Swift 在后台运行该函数。

更改 `decodeImage` 的运行位置也会改变我们对 `decodeImage` 可以访问哪些状态的假设。让我们看看它的实现。

该实现检查了一个字典，该字典存储了位于主要 Actor 上的缓存图片数据，这只有在主线程上操作才是安全的。

Swift 编译器向我们展示了函数试图访问主要 Actor 上数据的位置。这正是我们在添加并发时需要了解的信息，以确保不会引入错误。有几种策略可用于解除与主要 Actor 的绑定，以便你可以安全地引入并发。

在某些情况下，你可以将主要 Actor 代码移动到始终在主要 Actor 上运行的调用者中。如果你希望确保工作同步发生，这是一个好策略。

或者，你可以使用 `await` 从并发代码异步访问主要 Actor。

如果代码根本不需要位于主要 Actor 上，你可以添加 `nonisolated` 关键字将其与任何 Actor 分离。

我们现在将探讨第一种策略，稍后讨论其他策略。

我将把图片缓存移到 `fetchAndDisplayImage` 中，它运行在主要 Actor 上。在进行任何异步调用之前检查缓存对于消除延迟很有好处。如果图片在缓存中，`fetchAndDisplayImage` 无需挂起即可同步完成。这意味着结果会立即交付给 UI，并且仅当图片尚不可用时，它才会挂起。

我们可以从 `decodeImage` 中移除 `url` 参数，因为我们不再需要它了。现在，我们只需要 `await` `decodeImage` 的结果。

`@concurrent` 函数总是会切换出 Actor 来运行。如果你希望函数保持在调用它的 Actor 上，可以使用 `nonisolated` 关键字。

Swift 还有其他引入更多并发的方法。更多信息，请参阅“结构化并发进阶”。

如果我们作为库为许多客户端提供解码 API，使用 `@concurrent` 并不总是最佳 API 选择。

解码数据所需的时间取决于数据的大小，在主线程上解码少量数据是可以接受的。对于库来说，最好提供一个非隔离 API，并让客户端决定是否卸载工作。

非隔离代码非常灵活，因为你可以在任何地方调用它：如果你从主要 Actor 调用它，它将停留在主要 Actor 上。如果你从后台线程调用它，它将停留在后台线程上。这使其成为通用库的绝佳默认选择。

当你将工作卸载到后台时，系统会处理将工作调度到后台线程上运行。并发线程池包含所有系统的后台线程，可以包含任意数量的线程。对于像手表这样的小型设备，池中可能只有一两个线程。具有更多核心的大型系统，池中会有更多后台线程。任务运行在哪个后台线程上并不重要，你可以信赖系统会最佳地利用资源。例如，当任务挂起时，原线程将开始运行其他已准备好的任务。当任务恢复时，它可以在并发池中的任何可用线程上开始运行，这可能与它开始时的后台线程不同。

既然我们引入了并发，我们将在不同线程之间共享数据。众所周知，在并发代码中共享可变状态很容易出错，导致难以修复的运行时 bug。Swift 帮助你在编译时捕获这些错误，以便你可以自信地编写并发代码。每当我们从主要 Actor 进入并发池时，我们都会在不同线程之间共享数据。当我们从 UI 获取 URL 时，它从主要 Actor 传递到后台线程以获取图片。

获取图片会返回数据，这些数据被传递给图片解码。

然后，在解码图片后，图片（连同 `self`）被传递回主要 Actor。

Swift 确保所有这些值在并发代码中都能被安全访问。让我们看看如果 UI 更新最终创建了涉及 URL 的额外任务会发生什么。

幸运的是，`URL` 是一个值类型。这意味着当我们将 `URL` 复制到后台线程时，后台线程拥有一个与主线程上的副本独立的副本。如果用户通过 UI 输入了一个新的 URL，主线程上的代码可以自由使用或修改其副本，这些更改不会影响后台线程上使用的值。

这意味着共享像 `URL` 这样的值类型是安全的，因为实际上并没有共享：每个副本都是相互独立的。

值类型从一开始就是 Swift 的重要组成部分。所有基本类型，如字符串、整数和日期，都是值类型。

值类型的集合，例如字典和数组，也是值类型。存储值类型的结构体和枚举也是如此，就像这个 `Post` 结构体一样。

我们将始终可以安全并发共享的类型称为 Sendable 类型。`Sendable` 是一个协议，任何符合 `Sendable` 的类型都是安全可共享的。像 `Array` 这样的集合定义了 `Sendable` 的条件一致性，因此当它们的元素是 Sendable 时，它们就是 Sendable 的。

当结构体和枚举的所有实例数据都是 Sendable 时，它们可以被标记为 Sendable。

主要 Actor 类型隐式地是 Sendable 的，因此你无需显式声明。

像主要 Actor 这样的 Actor 通过确保其状态一次只能被一个任务访问来保护非 Sendable 状态。Actor 可能会存储传递到其方法中的值，并且 Actor 可能会从其方法返回对其受保护状态的引用。

每当一个值被发送进或发送出 Actor 时，Swift 编译器都会检查该值是否可以安全地发送给并发代码。让我们关注对 `decodeImage` 的异步调用。

`decodeImage` 是一个实例方法，因此我们传递了一个隐式的 `self` 参数。

这里，我们看到两个值被发送出主要 Actor，一个结果值被发送回主要 Actor。

`self` 是我们的图片模型类，它被隔离到主要 Actor。主要 Actor 保护可变状态，因此将指向该类的引用传递给后台线程是安全的。而 `Data` 是一个值类型，因此它是 Sendable 的。

这样就剩下图片类型了。它可能是一个值类型，就像 `Data` 一样，那样它就会是 Sendable 的。我们来讲讲不是 Sendable 的类型，比如类。类是引用类型，这意味着当你将一个变量赋给另一个变量时，它们指向内存中同一个对象。如果你通过一个变量更改了对象的某些内容，例如缩放图片，那么这些更改会立即通过指向同一对象的其他变量可见。

`fetchAndDisplayImage` 不会并发地使用图片值。`decodeImage` 在后台运行，因此它无法访问任何由 Actor 保护的状态。它从给定的数据创建一个新的图片实例。这个图片不能被任何并发代码引用，因此将其发送到主要 Actor 并在 UI 中显示是安全的。

让我们看看当我们引入并发时会发生什么。首先，这个 `scaleAndDisplay` 方法在主线程上加载一张新图片。`image` 变量指向这个图片对象，它包含猫的图片。

然后，该函数创建一个在并发池上运行的任务，该任务获得图片的一份拷贝。

最后，主线程继续显示图片。

现在，我们遇到了一个问题。后台线程正在更改图片：更改宽度和高度，并用缩放版本的像素替换原有像素。同时，主线程正在基于旧的宽度和高度遍历像素。

这就是数据争用。你最终可能会出现 UI 卡顿，或者更可能是在程序尝试访问像素数组边界之外时崩溃。如果你的代码尝试共享非 Sendable 类型，Swift 并发会通过编译器错误防止数据争用。这里，编译器指示并发任务捕获了 `image`，而该 `image` 也被主要 Actor 用来显示图片。为了纠正这一点，我们需要确保避免并发地共享同一个对象。如果我们希望图片效果显示在 UI 中，正确的解决方案是等待缩放完成后才显示图片。我们可以将这三个操作都移入任务中，以确保它们按顺序发生。

`displayImage` 必须在主要 Actor 上运行，因此我们使用 `await` 从并发任务中调用它。

如果我们可以直接让 `scaleAndDisplay` 成为异步函数，我们可以简化代码，无需创建新任务，并在调用 `scaleAndDisplay` 的任务中按顺序执行这三个操作。

一旦我们将图片发送到主要 Actor 以在 UI 中显示，主要 Actor 就可以自由地存储对图片的引用，例如通过缓存图片对象。

如果我们尝试在图片显示在 UI 中后更改它，我们将收到关于不安全并发访问的编译器错误。

我们可以通过在将图片发送到主要 Actor 之前对其进行任何更改来解决此问题。如果你为你的数据模型使用类，你的模型类很可能会从主要 Actor 开始，这样你就可以在 UI 中呈现它们的一部分。

如果你最终决定需要在后台线程上处理它们，请将它们设为非隔离。但它们可能不应该是 Sendable 的。你不希望出现模型的一部分在主线程上更新而另一部分在后台线程上更新的情况。保持模型类非 Sendable 可以防止这种并发修改的发生。这也更简单，因为使类成为 Sendable 通常需要使用诸如锁之类的底层同步机制。与类类似，闭包也能创建共享状态。

这是一个类似于我们之前缩放并显示图片的函数。它创建一个图片对象。然后，它调用 `perform(afterDelay:)`，并传入一个缩放图片对象的闭包。这个闭包包含了指向同一张图片的另一个引用。我们称之为对 `image` 变量的捕获。就像非 Sendable 类一样，带有共享状态的闭包只要不被并发调用，仍然是安全的。

仅在需要并发共享时，才将函数类型设为 Sendable。

每当数据在 Actor 和任务之间传递时，都会进行 Sendable 检查。它存在是为了确保没有可能导致 App 出现 bug 的数据争用。

许多常见类型都是 Sendable 的，这些类型可以自由地在并发任务之间共享。

类和闭包可能涉及不可安全并发共享的可变状态，因此请一次只从一个任务中使用它们。

你仍然可以将对象从一个任务发送到另一个任务，但务必在发送之前对对象进行所有修改。

将异步任务移至后台线程可以释放主线程，从而保持 App 的响应能力。如果你发现主要 Actor 上有大量数据导致这些异步任务过于频繁地“报到”主线程，你可能想引入 Actor。

随着你的 App 随着时间的推移而增长，你可能会发现主要 Actor 上的状态量也在增长。

你会引入新的子系统来处理诸如管理网络访问之类的事情。这可能导致大量状态驻留在主要 Actor 上，例如网络管理器处理的开放连接集合，每当我们需要通过网络获取数据时，都会访问它。

当我们开始使用这些额外的子系统时，之前的获取并显示图片任务变得更加复杂：它试图在后台线程上运行，但不得不跳到主线程，因为网络管理器的数据在那里。这可能导致争用，即许多任务试图同时运行主要 Actor 上的代码。单个操作可能很快，但如果有很多任务这样做，累积起来可能会导致 UI 卡顿。

之前，我们将代码移出主线程，方法是将其放入 `@concurrent` 函数中。

这里，所有的工作都在访问网络管理器的数据上。要将其移出，我们可以引入自己的网络管理器 Actor。

与主要 Actor 一样，Actor 隔离其数据，因此只有在运行该 Actor 时才能访问该数据。

除了主要 Actor，你还可以定义自己的 Actor 类型。Actor 类型类似于主要 Actor 类。像主要 Actor 类一样，它会隔离其数据，以便一次只有一个线程可以触及数据。

Actor 类型也是 Sendable 的，因此你可以自由共享 Actor 对象。与主要 Actor 不同，一个程序中可以有许多 Actor 对象，每个都是独立的。

此外，Actor 对象不像主要 Actor 那样绑定到单个线程。

因此，将一些状态从主要 Actor 移到 Actor 对象将允许更多代码在后台线程上执行，让主线程保持空闲以保持 UI 响应。

当你发现将数据存储在主要 Actor 上导致太多代码在主线程上运行时，请使用 Actor。此时，将代码中非 UI 部分的（例如网络管理代码）的数据分离出来，放到一个新的 Actor 中。

请注意，App 中的大多数类可能并非设计为 Actor：面向 UI 的类应该保留在主要 Actor 上，以便它们可以直接与 UI 状态交互。模型类通常应该与 UI 一起位于主要 Actor 上，或者保持非 Sendable 状态，这样你就不会鼓励对模型进行大量并发访问。

在本讲座中，我们从单线程代码开始。

随着需求增长，我们引入了异步任务来隐藏延迟，引入了并发代码以在后台线程上运行，并引入了 Actor 将数据访问移出主线程。

随着时间的推移，许多 App 都会遵循同样的路径。

使用性能分析工具来确定何时以及将哪些代码移出主线程。

Swift 并发将帮助你正确地将该代码与主线程分离，从而提升 App 的性能和响应能力。

我们为你的 App 推荐了一些构建设置，以帮助你引入并发。`Approachable Concurrency` 设置启用了一套即将推出的功能，使并发更易使用。我们建议所有项目都采用此设置。

对于主要与 UI 交互的 Swift 模块，例如你的主 App 模块，我们还建议将默认 Actor 隔离设置为“主要 Actor（main actor）”。除非另有说明，否则这会将代码放在主要 Actor 上。这些设置协同工作，使单线程 App 更易于编写，并在你需要时提供一条更易用的途径来引入并发。
