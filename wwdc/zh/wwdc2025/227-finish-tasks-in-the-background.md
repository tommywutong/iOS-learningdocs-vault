Hey，我是 Ryan，Apple 的一名软件工程师。今天，我想聊聊你的 App 如何拥抱后台运行时间。

App Store 上有数百万个 App，每一个都带来独特的价值。当你的 App 处于最前沿时，它最闪耀。在你能支配的每一个像素上，你都能营造难忘的体验。

人们也期望如此——来自像你这样的开发者的快速、有用、精心打造的 App。

但当 App 转到后台时会发生什么？在本场讲座中，我将探索后台运行时间，构建一套适合你 App、既高效又行为端正的工具包。这不只是为了保持存活。而是为了真正有用，去做预取、同步和上传之类的事情，为下一次启动做好准备。用得好的话，后台运行时间会让你的 App 感觉快速、顺畅，甚至有一点神奇。

我会先快速概述前台和后台实际意味着什么，并分享一些关于系统如何决定 App 何时以及多频繁在后台运行的原则。

然后我会介绍许多现有的做法，包括一个用于继续在前台已启动任务的新 API。

每一个处于前台的 App 都遵循同样的节奏。

App 本身以及它所需要的一切——框架、资源等等——都被加载到内存中。正是在这种状态下，你的 App 界面是设备上的焦点，你的 App 被定义为处于前台。

当有人离开你的 App，但进程仍然存活时，它就进入后台。默认情况下，后台 App 会被挂起。它们不会获得 CPU 时间。这能保护电池续航、维护隐私，并为前台 App 释放资源。

在某些情况下，你的 App 可以请求后台时间，以便在被挂起之前完成正在进行的工作。当有人通过 App 切换器返回你的 App 时，系统会在它移向前台时将其恢复。

在使用后台运行时间之前，了解系统如何确定优先级和管理资源，以及你可以在 App 中做些什么来构建最佳体验，会很有帮助。

系统的主要目标很直接：保护电池续航并优化性能，同时保持流畅且响应迅速的体验。

这意味着后台执行不是有保证的。相反，它是机会性的，往往是自行裁量的，并且受到严格管理。成功的工作负载理解这一背景，并被设计为与系统协作，而不是对抗它。

最根本的约束是能量。

每一次操作——CPU 周期、GPU 渲染、网络请求，甚至 Neural Engine 的使用——都有相应的电池成本。电池续航是有限资源。为了保全它，系统会在设备唤醒时合并工作，减少一天中不必要的后台活动。由于后台运行时间有限，请把你的 App 应在后台做的事情想成离散、量身定制的任务。每个任务高效地做一件事，并保持对系统优先级和约束的意识。这些后台工作会反映在「电池」设置中，人们在那里了解哪些 App 对他们的电池续航有显著影响。iOS 26 为设备的电池性能带来了出色的洞察，提供详细的按 App 细分。

你在这里最好的做法是保持高效。如果某个任务不需要立即运行，考虑将其推迟到设备充电时。如果确实需要运行，保持轻量并以目标为导向。

除了电池，系统还负责管理其他共享资源，例如内存、CPU 时间和网络带宽。当有人在使用设备时，前台 App 会被优先处理。如果一个后台 App 消耗了过多内存或 CPU，这不仅低效——它还在与前台体验竞争。这时系统可能会介入：限制、挂起，甚至终止代价过高的进程。

结论很简单。让你的后台工作保持最小。避免臃肿的工作，并优先使用批处理来尽量减小内存占用空间。

即使工作负载行为端正，也不能保证它们会被允许长时间运行。后台工作队列永远不会空，因此系统可能选择优先处理其他工作负载。话虽如此，我们都在作为团队协作，系统的职责是最大化前台体验。

你的工作负载必须具备韧性。尽早并经常保存增量进度。及时响应到期信号，并相信系统很快会回到你的工作负载。它欣赏协作进程，并利用这些行为来影响未来的调度。但归根结底，使用设备的人拥有最终决定权。他们通过切换「低电量模式」、「后台 App 刷新」和「低数据模式」等设置来影响调度。系统提供透明度，赋能人们自行做出这些决定。例如，如果你的 App 在后台耗电过多，他们可能会采取行动，而且未必对你有利。

因此，后台工作应当有礼貌，保持轻量并尊重偏好，同时确保你的影响与你所提供的价值成比例。

即便系统中的每个进程都充分遵循这些原则，它们仍然运行在一个复杂且高度动态的环境中。

网络可用性、CPU 负载、设备活动、热状态和电池电量等因素都会被用作告知调度决策的上下文。

幸运的是，系统会把这些具有挑战性的条件纳入考量，始终打造最佳体验。这意味着，即使设计良好的任务，在条件不太合适时也可能被推迟，以优化更大的全局。保持适应性至关重要。让你的工作保持原子且轻量，同时清楚地声明你的需求。把工作负载设计成能从离开的地方继续，就能在运行时间机会出现时实现增量进度。你对系统条件和优先级理解得越深、适应得越好，工作负载就越成功。

高效、最小、有韧性、有礼貌、可适应。这些是构建能无缝融入平台的后台工作的关键。在开发过程中问自己几个关键问题可能会有帮助。

谁发起了任务？工作是被显式启动的，还是可以在稍后时间运行的自行裁量工作？工作需要多长时间？试着把任务归类为短、中、长时长。这项工作对 App 状态和新鲜度是否关键？后台下载能增强 App 的活力感，但遥测上传对设备所有者没有即时益处。最后，工作是否需要同意或输入？后台运行时间不适合这类工作负载，如果是这种情况，我建议采取不同的方法。

有了这一基础，让我们探索如何有效地设计你的任务。iOS 提供了许多不同的 API，让你可以请求后台运行时间，每个 API 根据所支持的工作假定一种不同的类型或配置文件。这使系统能够根据我前面谈到的约束和条件调整你的 App 的运行时间。例如，人们期望他们最常用的 App 始终拥有最新、最好的内容。让系统理解 App 使用模式、优化后台任务和支持是合理的。

这就是第一个 API——BGAppRefreshTask——的情况。

App 可以用它在即将使用前静默地从服务器获取内容，同时充分体现礼貌的理念。系统会根据 App 使用历史对齐这些任务。

常用的 App 被调度的机会更高，从而保证每次启动都有新鲜内容。

要在 SwiftUI 中创建 App 刷新任务，把 BackgroundTask 修饰符添加到一个场景。当系统在后台唤醒 App 时，它会调用这个闭包，并在闭包返回时挂起 App。

虽然刷新任务覆盖了基于获取的用例，你可能还想维护更新不频繁或不规则的远程文稿。

后台推送通知提供了一种优雅的解决方案。当你的服务器发送关于新内容的通知时，系统会在合适的时机唤醒你的 App 去获取它。注意这与 App 刷新的情况不同。这里是把更新推送到设备，而不是机会性地获取数据。

因为后台推送通知用于指示新的远程内容，它们始终被视为自行裁量。

它们也会以低优先级发送并被合并，以尽量降低开销和功耗。

当有人从 App 切换器中移除你的 App 时，系统会尊重他们的意图。在你的 App 再次启动之前，通知不会被投递给它。

不过有时，你可能希望你的 App 执行其他类型的工作。也许你想在生成的数据上运行一个机器学习模型，或者甚至只是处理数据库维护。

BGProcessingTask API 正好能让你做到这些。

注册此任务很直接。只需要一个任务标识符、回调队列，以及一个在运行时调用的闭包。

你必须在启动期间立即注册 BackgroundTasks。这样，如果它在后台启动，系统能迅速知晓你的任务，并立即调用其处理程序。处理任务还支持额外配置，以践行我前面介绍的原则。例如，如果工作对延迟不太敏感，一个出色的任务可以选择仅在设备接通充电器并连接到网络时运行。这能尽量减小电池影响，降低你的 App 在电池设置中的足迹。

到目前为止，我介绍了让你的 App 为在后台开始的任务获得运行时间的 API。但有时你可能只想在转到后台时再多一点时间继续运行。

begin 和 end 后台任务 API 允许你的 App 完成那些一旦被中断并留下未完成状态就可能无法恢复的工作。

哪怕只是一个简单的状态保存，也是例子。取决于工作内容，过早终止可能导致糟糕的体验。

把你的代码包在这些 API 调用中，就告知系统你的 App 正在处理不应被中断的关键工作。当你在清理文件句柄或关闭数据库连接时，这个 API 非常合适。

iOS 上的后台支持版图很广阔，旨在处理各种各样的任务，包括由用户发起的那些。

确保这些用户发起的操作可靠地完成，对出色体验至关重要。在 iPadOS 和 iOS 26 中，BGContinuedProcessingTask 为你的 App 提供了一种支持这些确切功能的方式。此任务允许你在 App 进入后台后继续工作，并由系统提供 UI 来传达进度。以「日记」App 为例。它使用持续处理任务在后台驱动导出，进度更新会反映给发起者。

一旦完成，系统会短暂更新，然后自动关闭 UI。

人们始终保持控制。他们可以随时查看任务中的进度并取消工作，从而支持复杂功能。

持续处理任务始终从有人在你的 App 中执行的显式操作开始，例如按钮轻点或手势。每个任务代表某人希望你的 App 执行的清晰且即时的目标，例如导出文件、发布社交媒体内容，或完成对已连接配件的更新。这些任务会取得可衡量的进度，并且很容易理解任务完成意味着什么。

人们不期望任务自动开始，即使他们之前在你的 App 中设置过偏好。避免自动工作负载，例如维护、备份或照片同步。如果任务在没有显式操作的情况下开始，人们可能不理解任务的目标或其进度真正意味着什么。

做这些意料之外的工作可能导致你的 App 的任务被取消。

对于这些需求，考虑更合适的其他 API。

有了这些考量，采用持续处理任务就很容易了。首先，在 Info.plist 中添加一个任务标识符。你将用它注册一个管理状态和进度报告的启动处理程序。然后，在收到提示时简单地提交一个任务请求。

让我们从标识符开始。你通过在 Info.plist 的 permitted background task scheduler identifiers 数组中添加一个新值来定义它，并确保它以你的 App 的 bundle ID 为前缀。

除了静态标识符，持续处理任务还支持一种带动态后缀的新通配符表示法。

通配符标识符始终以你的 bundle ID 开头，后跟一些语义上下文。这里的新组件是点星号，表示将在注册和提交时向标识符追加动态后缀。

现在，让我们坚持使用更静态的形式。

选定之后，调度器需要知道当你的持续处理任务被要求运行时要执行什么代码。和之前一样，在提交任务请求后会调用提供给调度器的闭包。但这里有一个关键变化。启动处理程序不必在你的 App 完成启动之前注册。相反，你现在会在表达使用意图时动态注册这些处理程序。

就像在「日记」中一样，及时提供关于工作负载进展的更新至关重要。如果进展比预期慢，系统会提示发起者，询问他们是否希望工作继续。

系统依赖这些进度更新来管理正在进行的工作。因此，不报告任何进度的任务将被到期，以便系统回收和重新分配资源。你的 App 使用 Progress Reporting Protocol 主动传达这些更新。在它这样做时，系统会持续监视它们，并在 UI 中呈现进度。

我们仍然需要留意，如果条件发生变化，系统可能需要提前停止你的任务。为了处理这一点，你的任务必须提供一个到期处理程序，在需要停止时会被调用。把处理程序想成你的机会，快速翻转一个变量，以便任务能优雅停止并避免做额外工作。

关键是，当你的任务确实完成工作时，你必须调用 setTaskCompleted。这告诉系统你已完成。

好的，我已经介绍了如何管理进度更新、处理潜在中断，以及发出正在运行任务完成的信号。现在，让我们通过构建并提交一个有效的、用户发起的任务请求把它们组合起来。

你首先初始化一个任务请求对象。这需要三部分信息：一个与 Info.plist 中某个标识符匹配的标识符、一个本地化标题，以及一个本地化副标题。这些是用户在系统 UI 中看到的内容。

接下来，你需要为系统提供一个提交策略以遵循。默认情况下，如果系统发现无法立即运行你的持续处理任务，它会把它加到队列末尾。对此你不需要指定任何额外内容。

然而，有时排队并不是正确的方法。如果任务只有在现在立即开始才有用呢？你可以不让它排队，而是告诉系统：如果无法立即启动，就让提交失败。这会给你的 App 即时反馈，让你能适当地处理这种情况。

一旦你决定了策略并配置了请求，只需把它提交给调度器，让系统管理工作负载。这就是与持续处理任务协作的核心流程。通过提供标题和副标题并考虑提交策略，你在坚持关键的同意原则的同时，与系统顺利集成。这个 API 提供的能力甚至比肉眼所见更多。在 iPadOS 和 iOS 26 中，你的持续处理任务还可以在受支持的设备上受益于后台 GPU 访问。

要利用这一点，请确保在 Xcode 项目设置中添加后台 GPU capability。

添加之后，你可以——并且应该——动态查询调度器的 supported resources 属性。这让你的 App 确切了解当前设备在运行时支持什么，以便你适当地调整任务需求。

这一检查很重要。系统会强制执行这些要求。对不可用资源的任何请求都会在提交时被拒绝，使系统和你的任务保持在健康、已知的状态。

最后，请记住系统优先级的更广阔背景。iOS 优先处理前台体验，这意味着与你的 App 处于活动状态时相比，你的后台任务可能获得较低的服务质量。不过，系统对此很聪明。当你的 App 返回前台时，它会智能地提升你的任务优先级，帮助确保事情保持流畅且响应迅速。

这些新 API 实现了迄今为止最强大、最无缝的后台执行能力，把至关重要的 BGContinuedProcessingTask 加入你的工具包。在完整理解这些任务以及它们如何融入更广阔的系统后，你已准备好开始采用它们。我们很期待看到你如何使用这些工具创造更智能、更高效的后台体验。感谢观看！
