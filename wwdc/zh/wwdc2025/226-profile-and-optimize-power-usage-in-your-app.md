大家好！我是 Wiam，Apple 的一名软件工程师。

很高兴与大家探讨功耗优化。

打造出色、高质量的 App 体验是你们最擅长的事。

用户喜欢那些可以全天依赖的 App，而卓越的电池续航正是这种可靠性的关键部分。

功耗高效的 App 能带来更长的使用时长和更高的满意度，这确实是双赢。

然而，一个耗电过高的 App 会迅速破坏这种积极的体验。

那么，如果我向大家展示一件秘密武器——一个能帮你构建既强大又极为节能的 App 的工具，会怎么样呢？在这段视频中，你将学到利用此工具的功能来解决功耗问题的新方法。

在深入细节之前，我先快速概述一下今天的旅程。

我将从处理那些可以轻松在你的工作台上复现的问题开始。

我会通过一个实际示例，展示如何识别和减少过高的功耗。

然后，我将探索如何处理那些更具挑战性、更贴近真实场景、也更难定位的问题。

我会展示如何在任何环境下捕获数据。

接下来，我将演示如何比较不同实现的功耗。这提供了一种清晰的方法来衡量和改进 App 的效率。

最后，我将介绍如何在开发早期主动发现功耗问题，并发布一个高度优化过的 App 版本。

也许你已经注意到 Xcode 中显示了高能耗影响，说明存在问题，但很难找到根本原因。在这种情况下，你真正需要的是能够运行你的 App、复现问题并记录功耗指标的能力。

Instruments 中的 Power Profiler 正是解决这个问题的完美工具。

它让你能够剖析你的 App 并记录一条功耗追踪，然后在 Instruments 中将其可视化。

这正是我试图在我的 App 中解决的问题。我正在开发一个视频流 App——Destination Video，专为在 iPhone 和 iPad 上观看内容而设计。我想增强它，所以添加了一个“资料库”面板，以便轻松浏览整个视频集合。之后当我检查 Xcode Organizer 的能耗报告时，发现 CPU 使用率相比之前有了显著升高。这直接意味着性能变慢和电池续航缩短。我将使用 Instruments 中的 Power Profiler 来调查这个性能衰退。

首先，我将打开 Xcode 项目，并以无线方式连接我的 iPhone。

然后我前往“产品”并点击“Profile”。这将把 App 构建并安装到我的设备上，然后打开 Instruments。

我选择空白模板，勾选 Power Profiler 和 CPU Profiler，以便同时捕获 CPU 使用率的信息。

你可以根据需要选择其他 instrument。

我使用默认设置开始录制。

现在我将切换到设备上，打开那个“资料库”面板。

我还注意到打开这个面板时出现了挂起，这很可能与我正在调查的问题有关。我现在停止录制并检查追踪轨迹。我按下 Command + Control + Z 来聚焦录制的轨迹。

我点击 Power Profiler 轨迹左侧的展开三角形来展开它。通过 Power Profiler，我可以访问系统级的功耗指标以及每个 App 的功耗影响指标。

第一个轨道是系统功耗轨道，它提供了整体能耗的指示。值越高，你的 App 可能消耗的功率就越大。你可以选择一个区域，然后在摘要窗格中查看平均值。在此轨迹中选择一段时间后，摘要窗格显示为 10.5%/小时。

下一步是检查我的 App 的功耗影响指标。我可以检查许多与不同子系统相关的指标：CPU、GPU、显示器和网络功耗影响。CPU 功耗影响轨道至关重要，因为高 CPU 活动是功耗的主要因素。

持续或高强度的 CPU 使用会直接增加功耗。就在我尝试打开“资料库”面板后，出现了一个 CPU 功耗影响的峰值。我将高亮峰值之前的区域，以便确定平均 CPU 功耗影响值。

平均值是 1。现在我高亮峰值区域。

平均 CPU 功耗影响是 21，比之前高得多。这个值是一个分数，可以让你识别何时出现了意外的功耗峰值，并优先调试影响最大的子系统。

Time Profiler 通过识别哪些函数消耗了最多的 CPU 时间，来帮助定位这种 CPU 开销的来源。

我将点击 CPU Profiler，为了将分析聚焦于特定于 App 的代码，我将检查“调用树”视图并选择“隐藏系统库”。在最重的堆栈轨迹窗格中，Instruments 显示大量时间耗在了 `VideoCardView` 中。

由于这个视图的 `body` 相对简单，问题很可能来自它被调用的频率。这意味着我接下来需要检查 `LibraryThumbnailView`。它负责在“资料库”面板中生成所有视频缩略图，所以它很可能就是问题所在。

我将跳回 Xcode 来分析这个视图中的代码。

代码遍历了整个视频数组。对于每个视频，它生成一个 `VideoCardView`，该视图创建缩略图并创建一个视图来显示它。所有这些视图随后被放入一个 `VStack` 中。现在，想象一下有数百甚至数千个视频。这种方式强制 App 在“资料库”面板变为可见时立即加载每一个缩略图并创建每一个视图，无论它们是否实际出现在屏幕上。这是低效的，也解释了我在 Instruments 中发现的高 CPU 使用率。App 做了太多工作来加载那些甚至还不必加载的内容。

幸运的是，SwiftUI 为此提供了一个很棒的 API：`LazyVStack`。它只创建和渲染当前可见或即将通过滚动进入视野的项目的视图。所以，优化很直接。我将用 `LazyVStack` 替换 `VStack`。我会向它提供相同的视频数组，但在滚动时，视图本身会智能地处理项目视图的创建和销毁。我现在来测试这个优化。我再次点击“Profile”，然后开始录制。

接着在设备上，我打开“资料库”面板。

我的 App 现在响应迅速了，不再挂起。

我现在停止录制，并向下滚动到 CPU 功耗影响轨道。

我高亮同一区域以确定平均值。现在显示的平均值更小：4.3，而之前是 21。这修复了 CPU 性能衰退。在“资料库”面板中预先加载所有视频缩略图被确定为导致不必要功耗的原因。

Instruments 帮助定位了低效代码，改用按需加载使得这个功能性能更佳。

为了更深入地理解 CPU 性能剖析和优化技术，我强烈推荐观看 WWDC 视频“使用 Instruments 优化 CPU 性能”。

Power Profiler 为你 App 的功耗提供了宝贵的洞察。请记住，无论何时你怀疑存在功耗问题，但是不确定该关注哪个子系统或优化什么，都可以用它。

到目前为止，我都是将 iPhone 连接到 Xcode 进行剖析。这对于受控测试来说很棒，但它并不能总是展示全局。

那些只有在实际环境中才出现的令人恼火的问题呢？那些无法在工作台上稳定复现的问题呢？也许你正面临这样的场景：你的 App 在使用 CarPlay 导航时到底表现如何？或者你的增强现实功能在室外到底会消耗多少功率？如何调试需要数小时才会出现的后台电池使用问题？你的质量团队如何轻松地从现场测试中提供可操作的功耗诊断？为了解决这些问题，我需要一种从实际使用中收集数据的方法——而不需要直接连接到 Xcode。

Power Profiler 也可以在设备上使用，并可用于查找在开发过程中无法复现的问题。

这里有一个具体的例子。最近，我的同事报告了一些严重的电池续航问题——我的 App Destination Video 在他设备上的电池使用量总是排名第一。我试了各种方法，但就是无法在我的设备上复现。

人们使用 App 的方式各不相同，他可能遇到了我尚未遇到的边界情况。

得益于设备上的功耗剖析，我不需要他的实体设备。我只是请他使用这种新模式收集一条追踪轨迹，然后把文件发给我。我来展示一下收集这些数据有多简单。

首先，你需要在“设置”App 中打开开发者模式，这在你将设备连接到 Xcode 后即可使用。然后，前往开发者设置中的“Performance Trace”。启用 Performance Trace 后，会有启用 Power Profiler 的选项。确保此项已打开。接下来，你需要指定要剖析的 App。只有通过 Xcode、TestFlight 或企业计划安装的 App 才能被监控。从列表中选择你的 App。太好了！现在，开始数据收集。从设备右上角向下滑动以打开控制中心。

Performance Trace 图标用于开始数据收集。添加该图标后，点击即可开始录制。你可以让它运行几个小时，或者直到你能复现问题为止。现在，停止收集。只需再次点击控制中心中的 Performance Trace 图标即可。

这会生成一个包含所有收集到的功耗指标的追踪轨迹文件，你可以将其共享到你的 Mac，并直接在 Instruments 中打开。就是这样！这正是我同事所做的，现在我将向你展示如何分析他发送的文件，以找出根本原因。我使用 Instruments 打开文件。

通过设备上的功耗追踪，你可以访问系统级功耗指标、每个 App 的功耗影响指标以及 Time Profiler。此模式下的 Time Profiler 具有较低的采样率，以减少观察者效应。CPU 功耗影响轨道揭示了一个清晰的 CPU 影响模式，其中明显的高 CPU 影响区域之后是低 CPU 影响区域，并周期性地重复。这绝对不是我对 Destination Video App 的预期。如果我放大其中一个高影响区域，我就能找出导致这种功耗的原因。我将检查 Time Profiler 以了解在此时间段内运行了哪些函数。

`videoSuggestionsForLocation` 排在最前面，消耗了大量 CPU 时间。该函数是我的“基于位置推荐视频”功能的一部分，你知道的，就是推荐附近地标或事件的视频，并在位置发生变化时被调用。这就解释了为什么我在这里无法复现它！坐在我的工作台前，我的位置变化不大。所以这个函数可能在 App 启动时运行一次，然后就闲置了。

但我的同事在通勤时使用该 App——他们一直在移动！那些频繁的位置更新反复触发了这个繁重的过滤过程。我快速切换到 Destination Video App 本身。

这个功能出现在“附近建议”面板中。那些基于位置的推荐都出现在那里，全部由同一个函数驱动。好了，我现在知道是哪个函数在捣乱了。我将深入代码，看看可以做些什么来优化它。

每次我的位置发生变化时，`videoSuggestionsForLocation` 都会被调用。

它负责生成一个要显示的相关视频列表。

目前，每次调用它时，它都会将这个 `RecommendationRules` 文件读入一个 `Data` 对象，然后使用 `JSONDecoder` 将其解析到 `RecommendationRule` 映射中。而且这个 JSON 文件并不小——它包含数百条复杂的规则。文件 I/O 和 JSON 解析，尤其是对于大文件，是资源密集型操作！每次位置变化时，App 都在一遍又一遍地执行所有这些繁重的工作。

这绝对是问题的根源。规则本身在 App 运行时不会改变。

所以，一个优化方案基本上就是延迟加载和解析规则，只做一次，然后缓存起来。

这个简单的变化将减少每次位置更新时完成的工作。对于我的 App，在我进一步优化后，我会请同一位同事再次测试它。

当你在自己的 App 中进行此类修复时，你总是可以让某人在相同条件下进行测试，并获取一条新的功耗追踪。这是确认你确实解决了原始问题的完美方法——同样重要的是——验证你没有在做出更改时意外引入新的功耗问题。

这确实有助于你形成闭环，并对你的优化充满信心。

好了，我已经介绍了如何追踪现有问题。但是在发布之前，你如何自信地在不同的优化策略之间做出选择呢？也许一个优化涉及权衡——CPU 使用更少，但网络活动可能会稍有增加。你怎么知道对电池续航的净影响呢？这是一个常见场景：你正在开发一个新功能。

你已经有了自己的实现——我称之为方案 1。它很直接，用小数据量测试时看起来效率很高。但随后你的同事提出了方案 2。它的架构不同，可能更复杂一些，在处理那些小数据集时可能稍微慢一点，但它被设计为能更从容地处理大量数据。现在你面临一个两难选择：哪个方案对电池续航更好？仅仅基于本地测试或检查代码来决定真的很难。你的本地测试可能无法代表遇到时的典型数据大小，或者网络条件、后台活动如何影响性能。这时你可以利用 Power Profiler，特别是用于比较影响。你可以用一个方案剖析你的 App，再用第二个方案剖析一次，然后比较这些值。

请记住，热状态、设备状态和系统压力等条件会影响最终消耗了多少功率。这还包括你的 App 状态，例如它管理了多少数据、打开了哪些偏好设置或启用了哪些功能。为了应对这些变量，你可以，例如，在不同条件下为每个方案捕获多次运行并取结果的平均值，然后使用这些数据来指导你关于功能和实现的决策，最终优化你的 App 以获得最佳体验。Power Profiler 是你工具库中的工具之一。

在编码时，通过 Xcode Energy Gauges 获取即时反馈，并使用 Instruments 进行深入探究。通过自动化 XCTest 尽早发现问题。

发布后，使用 Xcode Organizer、MetricKit 和 App Store Connect API 监控实际影响。这些工具是你争取能效的盟友，它们提供了宝贵的背景信息和洞察。通过有效利用它们，你可以将强大的能效策略构建到你的开发过程中。你现在已经拥有了构建节能 App 的工具和知识。

尽早并经常使用 Power Profiler，让数据指导你的决策，并根据你学到的东西进行迭代。这里有一个挑战：现在就获取一个你 App 的追踪轨迹，并检查结果数据！这是将你的新技能付诸实践的有趣方式。好了，这就是我所有的功耗技巧。谢谢观看！
