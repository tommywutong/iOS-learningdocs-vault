嗨，我是 Matt，一名操作系统内核工程师。今天，我将教你如何使用 Instruments 来为 Apple 芯片的 CPU 优化代码。当你的 App 需要处理大量数据或快速响应交互时，高效利用 CPU 资源可以避免明显的等待时间。但预测软件的性能表现是困难的，原因有二。

第一个原因是，你写的 Swift 源代码和最终实际运行的内容之间存在多层抽象（abstraction）。

你为 App 编写的源代码会被编译成机器指令，最终在 CPU 上执行。

但你的代码并非孤立运行：它会被编译器生成的辅助代码、Swift 运行时以及其他系统框架所增强，所有这些都可能调用内核的系统调用（system call）来代表你的 App 处理特权操作。

这使得了解代码所依赖的软件抽象的成本变得困难。

第二个导致代码性能难以预测的原因在于 CPU 执行所收到指令的方式。在单个 CPU 内部，其功能单元并行工作以高效执行指令。

为了实现这一点，指令会被乱序执行，只给人按序执行的假象。同时，CPU 也得益于多层内存缓存，这些缓存确保了对数据的快速访问。这些特性极大地加速了常见的编码模式，例如对内存的线性扫描或防御性检查（如针对罕见情况的提前退出）。

但某些数据结构、算法或实现方法，如果没有经过仔细的优化甚至重大的重构，CPU 很难高效执行。我们将介绍为 CPU 优化代码的正确路径。首先，我们将回顾如何进行性能调查，以数据为引导，优先关注潜在的最大加速方向。然后，我们将考虑传统的性能分析（profiling）方法，它们是识别代码中 CPU 过度使用的绝佳第一步。为了深入挖掘并填补性能分析的空白，我们将使用 Processor Trace 来记录每条指令并衡量软件抽象的成本。最后，我们将使用改进后的 CPU Counters instrument 来分析 CPU 瓶颈，并了解如何对我们的算法进行微优化。让我们首先建立正确的心态，来着手进行性能调查。第一步是保持开放的心态：变慢的来源可能令人惊讶且出乎意料。收集数据以检验假设，并验证你对代码执行方式的思维模型是否准确。

例如，除了单线程 CPU 性能之外，还要考虑变慢的其他原因。除了在 CPU 上执行，线程和任务也可能花费时间处于被阻塞状态，等待文件或共享可变状态（mutable state）访问权等资源。

“可视化和优化 Swift 并发”讲座涵盖了用于了解任务为何可能不在 CPU 上运行的工具。

当你的线程解除阻塞并在 CPU 上运行时，可能存在 API 被误用的情况，例如为你的代码应用了错误的服务质量等级（quality of service class），或隐式创建了太多线程。阅读“针对 Apple 芯片调优代码性能”的文档以获取更多详细信息。但如果是效率问题，那么你要么改变算法及其关联的数据结构，要么改变实现（即算法在编程语言中的表达方式）。使用工具来确定你应该首先关注这棵树中的哪个分支。尝试使用 Xcode 内置的 CPU Gauge 来检测在与你 App 交互时 CPU 是否被大量使用。要分析线程之间的阻塞行为以及最终将由哪些线程解除阻塞，请使用 System Trace instrument。

对于影响 UI 或 App 主线程的问题，请使用专门的 Hangs instrument。“使用 Instruments 分析挂起”讲座包含了更多关于如何确认你的 App 的 CPU 使用率需要优化的详细信息。但即使有工具的指导，也要留意你实施的优化类型。无节制的微优化可能会使你的代码更难扩展和理解。而且它通常依赖于可能脆弱的编译器优化，例如自动向量化或引用计数省略。在你投入侵入性微优化之前，请先寻找可能完全避免慢速操作的替代方案。考虑一下代码最初为何要运行。也许你可以完全避免执行这项工作，直接删除代码。

感谢观看本次讲座，并且……开个玩笑。但说真的，这通常是不可能的，但这可以很好地检验你对工作结果重要性的假设。

你也可以尝试稍后在关键路径之外再做这项工作，或者只在结果对某人可见时才进行。

同样的，预计算（precomputing）值也可以隐藏完成工作所需的时间。这甚至可能包括在构建时就将值固化。然而，这些方法可能会不必要地消耗电量或增加 App 的下载体积。对于输入相同的重复操作，缓存（caching）是另一种解决方案，但通常伴随着一系列难题，例如缓存失效或处理增加的内存使用。一旦你穷尽了在性能表现明显时避免执行工作的尝试，你就需要让 CPU 更快地完成工作。这就是我们今天要关注的重点。将你的优化工作优先放在那些对用户体验影响最大的代码上。通常，这是用户与你 App 交互的关键路径上的代码，他们会注意到性能问题，但也可能是长时间运行的操作消耗了电量。在本次讲座中，我们将专注于在准备好的整数列表中搜索，因为这位于我 App 的关键路径上。

我的 App 已经在使用二分查找，这是一种经典的算法，它利用已排序数组通过不断将搜索空间减半来查找元素。在这个例子中，数组有 16 个元素，我们要搜索持有数字 5 的元素。

5 小于数组中间的元素 20，因此它的元素必然在前半部分。

5 也小于前半部分中间的元素 9，因此它必然在数组的前四分之一部分。在与 3 进行比较后，我们仅用 4 步就锁定了匹配的元素。

这是我 App 所使用的框架中的二分查找实现。它是一个独立函数，使用在干草堆中找针（finding a needle in a haystack）的比喻来命名其参数。它支持在 haystack `Collection` 中搜索一个 `Comparable` 的 needle。该算法跟踪两个变量：`start` 中当前搜索区域的起始位置，以及 `length` 中剩余要搜索的元素数量。当还有剩余元素要搜索时，它会检查搜索空间的中间值。如果 needle 小于该值，那么它只是将搜索空间减半，保持 `start` 不变。如果 needle 相等，则已找到该元素，并返回中间索引。否则，需要将起始位置调整到中间元素之后，并将搜索空间减半。

我们将准备逐步优化此算法，通过比较搜索吞吐量（即算法每秒能完成的搜索次数）来确认每一步都在取得进展。不要觉得每次更改都必须取得巨大飞跃：有些优化可能难以量化，但微小的改进会随着时间的推移而累积。

为了帮助我们持续优化，我编写了一个自动化测试来衡量搜索吞吐量。我们不需要特别健壮的设置：我们只需要一个性能估算。这个 `repeat-while` 循环会调用搜索闭包（closure），直到指定的持续时间过去。

我在搜索闭包调用周围使用了 OS 信号标记区间（signpost interval），以便工具可以聚焦于我们正在优化的测试部分。我选择了“Points of Interest”类别，因为 Instruments 默认包含它。

计时本身使用了 `ContinuousClock`，与 `Date` 不同，它不会倒退且开销低。这是一种简单但有效的方法，用于收集关于算法性能的一些粗略数据。

我的测试叫做 `searchCollection`，模拟了我的 App 如何使用二分查找。我们会运行搜索一秒钟，并为信号标记使用描述性名称，以防我们在单次录制中运行多个测试。

闭包内部的一个循环将调用二分查找函数，以分摊检查时间开销。

让我们在 Instruments 性能分析器下运行此测试，以分析二分查找的 CPU 性能。有两个专注于 CPU 的性能分析器可供选择：Time Profiler 和 CPU Profiler。

经典的 Time Profiler instrument 会基于定时器定期采样系统 CPU 上正在运行的内容。

在这个例子中，有两个 CPU 上有一些工作在进行。在每个采样点，Time Profiler 会捕获在 CPU 上运行的每个线程的用户空间调用栈（call stack）。

然后 Instruments 可以在其详情视图中将这些样本可视化为调用树（call tree）或火焰图（flame graph），以近似估计哪些代码对于优化 CPU 性能是重要的。这对于分析工作如何随时间分布或哪些线程同时处于活动状态很有帮助。但是，使用定时器来采样调用栈会遇到一个称为混叠（aliasing）的问题。混叠是指系统上某些周期性的工作与采样定时器以相同的节奏发生。在这里，蓝色区域负责大部分 CPU 时间，但橙色函数恰好在采样器收集调用栈时运行。这使得橙色在 Instruments 调用树中不公平地占据过高份额。

为避免此问题，我们可以改用 CPU Profiler。

它基于每个 CPU 的时钟频率独立地对 CPU 进行采样。对于 CPU 优化，你应该优先选择 CPU Profiler 而非 Time Profiler，因为它更准确，并且能更公平地权衡消耗 CPU 资源的软件。

这些铃声代表 CPU 的周期计数器何时对正在运行的调用栈进行采样。Apple 芯片的 CPU 是非对称的，其中一些会以较慢但更节能的时钟频率运行。会提升频率的单个 CPU 将被更频繁地采样，而不会出现 Time Profiler 对运行更快的 CPU 的偏见。

我们将使用 CPU Profiler 来找出我的二分查找函数中哪些部分消耗了最多的 CPU 周期。

在 Xcode 的测试导航器中，你可以通过右键单击测试名称并选择其 Profile 项，从单元测试快速启动 Instruments。

在这种情况下，我们将选择 Profile searchCollection。

这将打开 Instruments 并呈现模板选择器。我将选择 CPU Profiler。

在录制设置中，我们将切换到延迟模式以降低开销并开始录制。性能分析器的默认即时模式对于确认你的 App 交互已被捕获很有用。但对于在与 Instruments 相同的机器上运行的自动化测试，我们希望通过在停止录制后再进行分析来最小化工具可能添加的任何开销。

Instruments 中的新文档通常令人生畏。窗口分为两半。顶部是显示时间线上活动的轨道。每个轨道可以包含多个通道以及指示级别或区域的图表。

时间线下方是详情视图，包含有关正在检查的时间线范围的摘要信息。任何扩展详情都显示在右侧。

为了定位，我们将在“Points of Interest”轨道中找到搜索发生的区域。

右键单击该区域将提供设置检查范围的选项，将下方的详情视图限制为仅在信号标记区间内捕获的数据。我们可以点击测试运行器进程轨道，以在时间线下方的详情视图中显示 CPU profile。此视图显示了测试中函数的调用树，这些函数被每个 CPU 的周期计数器采样。按住 Option 键并单击列出的第一个函数旁边的箭头，将展开树直到样本计数首次出现显著差异的点，这接近我们的二分查找函数。我们将通过单击其名称旁边的箭头并选择“Focus on Subtree”项来聚焦于我们的二分查找函数。

每个函数都按样本计数乘以每次样本之间的周期数加权。这个调用树显示了大量在为二分查找调用的函数中采集的样本，这些函数是用来处理 `Collection` 类型的。此协议见证（protocol witness）出现在大约四分之一的样本中。还有分配，甚至 `Array` 对 Objective-C 类型的检查。如果我们切换到一个更匹配我们正搜索的数据类型的容器类型，就可以避免 `Array` 和泛型的开销。让我们试试新的 `Span` 类型。当元素在内存中连续存储时（这对于许多类型的数据结构很常见），可以使用 `Span` 代替 `Collection`。它实际上就是一个基地址和计数。但它也防止内存引用逃逸或泄漏到使用它的函数之外。有关 `Span` 的更多详细信息，请观看“使用 Swift 改善内存使用与性能”讲座。

采用 `Span` 只需要将 `haystack` 和返回类型更改为 `Span`，算法本身不变。

这个微小的改动使搜索速度提高了四倍。但这个版本的二分查找仍然影响我的 App，我想研究 `Span` 的边界检查是否导致了开销。为了更深入地挖掘，我们将切换到一个名为 Processor Trace 的新工具。从 Instruments 16.3 开始，Processor Trace 可以收集你的 App 进程在用户空间执行的所有指令的完整轨迹。这是衡量软件性能方式的一个根本性转变：没有采样偏差，并且对 App 性能的影响仅为微不足道的 1%。Processor Trace 需要专门的 CPU 特性，这些特性仅在配备 M4 的 Mac 和 iPad Pro 或配备 A18 的 iPhone 上可用。

在我们开始之前，我们需要为设备进行处理器追踪设置。在 Mac 上，在“隐私与安全性”和“开发者工具”下打开该设置。对于 iPhone 或 iPad，该设置位于“开发者”部分。为了获得 Processor Trace 的最佳体验，请尽量将追踪时间限制在几秒内。与使用 CPU Profiler 进行采样不同，你不需要批处理你的工作：即使只有一个你想要优化的代码实例也足够了。让我们在 `Span` 版本的二分查找上运行 Processor Trace。我们的测试现在只需要少量的迭代。为了分析这个测试，我会右键点击行号间隙中的测试图标。

这会显示与我们之前使用的相同的菜单，但可能比切换导航器更方便。

我将选择 Processor Trace 模板并开始录制。

Processor Trace 必须处理大量数据，因此捕获和分析可能需要一些时间。

Processor Trace 设置 CPU 来记录每一个分支决策。周期计数和当前时间也被记录下来，以跟踪 CPU 在每个函数中花费的时间。然后 Instruments 使用你的 App 和系统框架的可执行二进制文件来重建执行路径，并用经过的周期数和持续时间来注释函数调用。我们限制追踪时间，因为即使 CPU 记录的信息尽可能少，对于一个多线程应用来说，每秒仍然可能产生数 GB 的数据。现在文档已准备好，让我们放大以便检查二分查找函数调用。

搜索现在只占完整录制的一小部分，所以我们将在时间线下方详情视图的感兴趣的区域列表（Regions of Interest List）中找到它，然后右键单击其行并选择“Set Inspection Range and Zoom”。为了定位执行二分查找的线程，我们将右键单击“Start Thread”单元格并选择“Pin Thread in Timeline”。

Processor Trace 为每个线程轨道添加了一个新的函数调用火焰图，所以我将向上拖动固定区域的分隔线以腾出空间。

Processor Trace 以火焰图的形式可视化地显示执行过程。火焰图是函数成本和关系的图形化表示：条形的宽度表示函数执行所需的时间，行表示嵌套的调用栈。但大多数火焰图显示的是来自采样的数据，其成本仅是基于样本数量的估计。

在我们再次开始使用 Instruments 之前，我们需要建立一个关于 CPU 如何工作的思维模型。

在基本层面上，CPU 只是在遵循一系列指令，修改寄存器和内存，并与外围设备交互。

当 CPU 执行时，它必须遵循一系列步骤，这些步骤大致分为两个阶段。第一是指令供应（Instruction Delivery），确保 CPU 有指令要执行。然后，指令处理（Instruction Processing）负责执行它们。

在指令供应中，指令被提取和解码成 CPU 更容易执行的微操作（micro-operation）。大多数指令解码为单个微操作，但有些指令执行多项操作，例如发出内存请求和递增索引值。

为了处理微操作，它被发送到映射和调度单元，这些单元负责路由和分派操作。从那里，操作被分配给执行单元，或者如果需要访问内存，则分配给加载-存储单元。

如果 CPU 必须串行地运行这些阶段，然后才能开始下一次提取，那将会非常慢，所以 Apple 芯片处理器采用了流水线（pipeline）技术。

一旦一个单元完成工作，它就可以继续处理下一个操作，使每个单元保持忙碌。

流水线和创建执行单元的额外副本支持指令级并行性（instruction-level parallelism）。

这与使用 Swift 并发或 Grand Central Dispatch 所能访问的进程或线程级并行性不同，后者是多个 CPU 执行不同的操作系统线程。指令级并行性允许单个 CPU 利用那些原本可能空闲的单元，高效地使用硬件资源，使流水线的所有部分保持忙碌。你的 Swift 源代码不直接控制这种并行性，而是必须帮助编译器生成一个合适的指令序列。

不幸的是，由于 CPU 中各个单元之间的交互，可并行的指令序列并不直观。单元之间的每个箭头都显示了操作可能在流水线中停顿的位置，从而限制了可用的并行性。我们称之为瓶颈（bottlenecks）。

为了找出与我们的工作负载相关的瓶颈是哪个，Apple 芯片 CPU 可以统计每个单元中的感兴趣事件以及正在执行指令的其他特征。CPU Counters instrument 读取这些计数器，从中构建更高级别的指标。今年，我们为这些计数器添加了预设模式，使它们更易于使用。Instruments 在一种指导性的、迭代式的方法中使用它们来分析代码的性能，称为瓶颈分析（bottleneck analysis）。让我们用它来找出为什么我们的二分查找仍然很慢，尽管没有任何明显的函数调用开销。

CPU 很狡猾，会乱序执行指令。由于指令完成时额外的一个重排序步骤，才使得指令看起来是顺序执行的。

这意味着 CPU 会向前看并预测接下来将执行哪些指令。负责此任务的分支预测器通常很准确，但当先前的执行中没有关于分支是否会被执行的一致模式时，它们可能会走错路径。

我们二分查找算法中的循环有两种类型的分支。第一个循环条件通常会被执行直到循环结束，因此预测效果很好，没有出现在采样中。但 needle 的检查实际上是一个随机分支，所以难怪预测器会出错。

我重写了循环体，以避免难以预测且影响控制流的分支。`if` 语句的主体仅基于条件赋值。这允许 Swift 编译器生成条件移动指令，并避免分支到不同的指令。

基于条件从函数返回或中断循环必须使用分支来实现，因此我还移除了提前返回。

我使用了不加检查的算术（unchecked arithmetic）来避免会终止程序的分支。这也是微优化变得脆弱且容易破坏的领域之一，更不用说它更不安全且更难理解了。当我们做出这样的更改时，你应该回到最初的 CPU Bottlenecks 模式，以检查它如何影响其他瓶颈。

让我们了解更多关于 CPU 和内存的知识，找出原因。

CPU 通过缓存层次结构来访问内存，这使得对相同地址的重复访问，甚至是可预测的访问模式，都变得更快。

它从位于每个 CPU 内部的 L1 缓存开始。这些缓存不能存储太多数据，但提供了最快的内存访问。较慢的 L2 缓存位于 CPU 外部，提供了更大的空间。最后，两个缓存都未命中并需要访问主存的请求比快速路径慢 50 倍。

这些缓存还将内存分组为 64 或 128 字节的段，称为缓存行（cache line）：即使指令只请求 4 个字节，缓存也会拉入更多数据，期望后续指令需要访问附近的其他字节。

让我们考虑一下这对我们的二分查找算法有何影响。在这个例子中，蓝色线条是数组中的元素，而灰色胶囊是 CPU 缓存操作的缓存行。

数组一开始完全不在缓存中。第一次比较将几个元素及其所在的缓存行带入 L1 数据缓存。但是接下来的比较遇到了缓存缺失。随后的迭代会持续在缓存中缺失。这种情况一直持续到搜索范围缩小到一个缓存行大小的区域。事实证明，二分查找是 CPU 内存层次结构的一种病态情况。

但是，如果我们能容忍重新排列元素使其对缓存更友好，那么我们就可以将搜索点放在同一个缓存行上。这被称为 Eytzinger 布局（Eytzinger layout），以一位 16 世纪的奥地利系谱学家的名字命名，他就是这样组织家谱的。

这不是一个没有重大后果就能实施的一般性优化。它以降低顺序遍历速度为代价提高了搜索速度，使得该操作现在在缓存中缺失。让我们回到二分查找的第一个例子，展示如何将已排序数组重新排列为 Eytzinger 布局。以中间元素作为根节点，我们将二分查找操作建模为一棵树，其中中间点是子节点。Eytzinger 布局按这棵树的广度优先遍历进行排列。

更接近树根的节点排列得更密集，并且更有可能共享缓存行。再次查找 5 现在前三步都在同一个缓存行中。叶子节点在数组的末尾排序，这将导致不可避免的缓存缺失。
