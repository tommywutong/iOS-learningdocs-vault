Swift 入门从未如此简单。Allan 将向你展示 Swift 6.2 如何带来更多灵活性，来创建适合你的开发环境。谢谢，Holly。

今年的 Swift 发布包含大量开发工作流改进，无论你选择如何编写 Swift 代码，你都会从中受益。这些增强涵盖广泛的工作流，包括编写代码、构建和调试。让我们先看看如果你在 VS Code 中开发，今年有什么新东西。

VS Code 市场中的 Swift 扩展现在由 Swift.org 官方验证并分发。过去一年它还获得了许多新功能。第一是后台索引。在 Swift 6.1 中，我们为 VS Code 和其他 IDE 中的 Swift PM 项目默认启用了后台索引。这允许编辑器功能（如跳转到定义）在你修改项目时保持更新。VS Code 中的代码补全结果现在更相关，这要归功于对 SourceKit-LSP 的改进。调试也已简化。安装 Swift 扩展时，LLDB 支持现在会自动包含。

扩展的最新版本还包含新的项目面板，便于查找包的依赖、target 和任务。最后，VS Code Swift 扩展还有一种查看项目文档的新方式。你可以把 DocC 预览与代码并排显示，它会在你输入时实时更新。VS Code Swift 扩展在开源中开发，你可以在 GitHub 的 swiftlang 组织中找到它。

现在让我们谈谈在所有地方都可用的构建 Swift 代码的改进。你生产力最重要的方面之一是工具的性能。

Swift 6.2 显著改进了使用基于宏的 API 的项目的 clean build 时间。为了看看如何做到，假设你有一个使用来自名为 Stringify 的虚构包的宏的项目。

之前，为了构建项目，Swift PM 首先必须获取 swift-syntax 的源码，这是一个为宏提供动力的库。然后它会构建 swift-syntax、构建 Stringify 宏插件，最后构建你的代码。虽然 swift-syntax 的构建可以缓存，但它仍然延长了执行 clean build 所需的时间。这在持续集成环境中尤其明显。为了加速构建，Swift PM 和 Xcode 的最新版本支持预构建的 swift-syntax 依赖。这完全消除了一个昂贵的构建步骤，对某些项目来说，把 clean build 时间减少了数分钟。

如果你拥有提供宏的包，只要包依赖于 swift-syntax 的 tagged release，你的客户就能利用这一优化。你的生产力并不总是只关于构建性能。有时试图解决编译器发现的问题才是拖慢你的原因。例如，当你在 Swift 6 语言模式中编写并发代码时，编译器可能会检测到你需要防止的潜在数据争用。这个错误指出了一些重要的东西，但这并不意味着如何解决是显而易见的。

这就是为什么在 Swift 6.2 中，我们开始为许多类别的诊断扩展可用文档。

这些对常见警告和错误的扩展解释帮助你理解问题，并给你具体的解决方案。你可以从 IDE 和 swift.org 在线访问文档。控制诊断的行为也可能很重要。例如，为了保持代码没有警告，你可能使用「warnings as errors」设置。这适用于易于处理的警告，但有些警告，比如废弃 API 的警告，你可能不想被强迫立即解决。Swift 6.2 给你灵活性来决定哪些警告视为错误。例如，你可以决定默认把所有警告视为错误，但对废弃声明例外。另一方面，如果你只对防止某些类别警告感兴趣，你可以只把那些警告提升为错误。添加对编译器警告的控制是社区驱动改进 Swift 的一个很好的例子。感谢提案作者和所有参与论坛讨论的人。

最后，让我们看看 Swift 6.2 中几个很棒的调试改进。

在这个版本中，我们大大改进了调试异步代码的体验。当你单步执行在 Swift 任务中运行的代码时，LLDB 现在会跟随执行进入异步函数，即使这需要在不同线程之间切换。调试器对 Swift 任务中心模型的理解允许它向你展示哪个任务正在执行。你甚至可以命名一个任务以便更容易识别。任务名称也会出现在使用 Swift Concurrency 模板记录的 Instruments 配置文件中。你还可以使用新命令如 swift task info 获取关于当前执行任务的更多信息，例如它的优先级和子任务。最后，你的调试会话今年会更响应，这要归功于 explicitly built modules，这是一个支持在构建模块依赖时并行化和重用的构建系统特性。在 explicitly built modules 之前，Xcode 构建和调试器会使用完全独立的模块图。现在调试器能够重用构建中的模块。这意味着第一次在调试器中运行 p 或 po 时，命令会求值快得多，因为类型信息立即可用。Explicitly built modules 在 Xcode 26 中默认启用。那些只是我们今年对 Swift 工具做的一些改进。接下来，我将带你了解我们对每天使用的 Swift 核心库进行的重要更新。

库帮助你完成各种任务，Swift 的核心库提供编写 Swift 代码的基本构建块。Swift 6.2 现代化了更多 Foundation 的 API 表面，并提供新 API 来简化日常编程任务。

为了改善使用 Swift 进行脚本任务的体验，Foundation Workgroup 引入了一个带有启动 subprocess API 的新包。

你从添加和导入新的 Subprocess 包开始。然后通过调用 run 函数并 await 结果来启动一个 subprocess。

如果你提供包含进程名称的字符串，run 方法将基于 `$PATH` 环境变量查找可执行文件。

在大多数情况下，你将使用 FilePath 来指定可执行文件的完整路径来启动 subprocess。当 subprocess 终止时，你可以检查退出状态、标准输出和关于进程执行的其他信息。subprocess 库还有许多更多能力，给你对进程执行的细粒度控制、平台特定的配置选项等。你可以在 swift-subprocess 仓库中探索完整 API 表面。包处于 0.1 版本，来自你的采用的反馈将告知 1.0 版本发布的 API。

Foundation Workgroup 还改进了在 App 项目中最常用的日常 API。

在 iOS App 中响应 UIKit 的通知非常常见，但观察通知的代码容易出错。首先，你必须小心注册一个对象支持发布的通知名称。如果你犯了错误，你的通知回调将永远不运行。关于通知的信息存储在无类型字典中，需要你使用正确的键手动下标并动态转换结果到正确类型。即使通知保证在主线程发布，你在访问 main actor API 时仍会得到并发错误。通知名称和负载现在支持具体类型。具体类型允许编译器检查对象支持你注册的通知种类。它们还消除了处理通知负载时的样板代码。通知类型指定通知在哪里发布。如果通知在 main actor 上发布，你可以自由访问 main actor API。对 MainActorMessage 的符合保证通知总是同步地在主线程发布。对 AsyncMessage 的符合意味着通知异步地在任意线程发布。具体通知类型在 SDK 中可用于框架如 UIKit 和 Foundation 发布的通知。你还可以为自己的通知添加具体通知类型。

广播系统通知给已注册观察者基于更一般的观察者模式。Observation 库提供通用 API，用于自动跟踪对象图中的状态变化。

你可以使用 `@Observable` 宏选择让类加入观察跟踪。Swift 6.2 引入了一种用 AsyncSequence 从可观察类型流式传输状态变化的方式。

你从用闭包创建新的 Observations 类型实例开始。在闭包中，你计算想要观察变化的值。这里，我想要观察描述玩家当前状态的字符串，并且每次分数更新或玩家获得新物品时都想要一个新值。你将基于闭包中使用的可观察属性获得更新值。更新是事务性的。

更新的跟踪在闭包中任何可观察属性的 willSet 被调用时开始。它在代码暂停的下一个 await 处结束。更新值将包括这两个代码点之间对其他属性的所有同步更改。这确保对多个属性的同步更新不会导致对象处于不一致状态的观察更新。

如果我同步更新分数和物品，我只会得到一个包含两个更改的更新值。

observations 类型符合 AsyncSequence，所以你可以使用 for-await 循环迭代更新值。

作为开发者，我们每天写测试。

Swift Testing 是一个跨平台库，提供用于描述和组织测试的宏，如用于声明测试函数的 `@Test` 属性。你使用 expect 和 require 宏验证你的假设，Swift Testing 在期望或要求失败时给你可操作的信息。

但有时，测试失败难以分诊，尤其当它们只在远程环境如 CI 中失败时。理解测试失败可能需要更多关于测试使用的数据的上下文。

Swift 6.2 引入自定义 attachments 来帮助你诊断测试失败。你可以通过调用 Attachment.record 方法向测试添加 attachment。你可以附加库类型如 Data 和 String，并且可以通过符合 attachable 协议为自己的类型实现 attachment 支持。

Swift 6.2 还支持 exit tests，允许你测试在某些条件下你期望终止的代码。

例如，如果你编写一个通过前置条件验证输入参数假设的函数，你可以编写一个测试用例，当前置条件失败时成功。

你通过向 `#expect` 或 `#require` 传递 processExitsWith 参数来编写 exit test。当你编写 exit test 时，Swift Testing 将启动一个新进程运行你的测试，你可以验证进程以特定退出代码或信号或任何失败状态成功退出。

这些通用库允许你在项目中编写和测试可移植的 Swift 代码，甚至超越 App 代码。在 Apple，我们在整个软件栈中使用 Swift。

我们用它做固件、App 和框架，以及大规模 Web 服务。在为嵌入式设备、安全关键组件和服务器编写代码时，你可以利用 Swift 6.2 的改进。你还将能够针对几个新平台。让我们从栈的底部开始，Embedded Swift。

Embedded Swift 是 Swift 的子集，允许你编写针对最受限环境的代码，如嵌入式设备的固件和操作系统内核。它是一种编译模式，支持核心 Swift 特性，如值类型和引用类型、闭包、可选值、错误处理、泛型等。在 Apple，我们在 iPhone 上运行的最低层软件中使用 Embedded Swift。例如，在 iOS 26 中，Embedded Swift 运行在管理 CPU 和 GPU 之间共享内存页访问的协处理器上。如果你想试用 Embedded Swift，你可以通过观看《Go small with Embedded Swift》了解更多。Swift 6.2 用新能力扩展了 Embedded Swift。它现在涵盖 Swift 的完整字符串 API，包括字符串插值。Swift 的 any 类型，可以表示符合协议的类型的值，现在只要协议被约束为类类型就可用。Swift 标准库还获得 InlineArray 和 Span，这是两个用于高效处理内存区域的新 API。这些类型，Holly 将在后面更详细地介绍，非常适合嵌入式程序中经常发现的那种性能敏感代码。随着 Embedded Swift 变得越来越 capable，社区一直在忙于创建你可以用于自己嵌入式项目的示例。在 GitHub 的 swift-embedded-examples 仓库中查看它们。

Embedded Swift 的好处之一是它允许你用默认内存安全的语言编写低层软件。内存安全的代码更安全，我们一直在努力让 Swift 对有最强安全要求的代码更好。

有时你需要编写代码来完成本质上不安全的事情。例如，当与用 C 编写的依赖集成时，常见的是使用接受指针的 API。在安全关键上下文中，应尽可能避免不安全代码。但如果无法避免，它应该易于识别。这就是为什么我们在 Swift 6.2 中引入了一个新的 *opt-in* 特性，叫做 strict-memory-safety。这个模式要求所有不安全 API 的使用在源代码中被明确确认。模式要求的注解帮助你识别代码中从安全角度需要额外关注的部分。随着这个新模式，Swift 6.2 还支持 C 和 C++ 头文件的新注解，导致 API 被导入 Swift 时使用安全、符合人体工程学的类型，如 Span。要了解更多关于新互操作性特性，查看《Safely mix C, C++, and Swift》。

在 Apple 的操作系统中，我们在两个安全关键组件中采用严格内存安全：WebKit 和 Messages App 中解析传入消息和附件的子系统。这两个组件都处理不可信输入，这使得限制不安全 API 的使用尤其重要。

Array 类型是元素的有序列表，是整个 Swift 项目中最常用的数据类型之一。

Array 的特性如动态调整大小使它易于使用并适用于许多任务。但这种灵活性是有代价的。

为了支持动态调整大小，数组存储对堆分配缓冲区的引用。

当添加更多元素且数组已满时，必须动态分配新内存，并把现有元素复制过去。

如果你正在分析使用 Array 的性能关键代码中的 hot path，你可能会注意到需要消除的数组缓冲区内存分配或引用计数。如果数组大小从不改变，就没有必要支付堆分配的代价。InlineArray 是一种新的固定大小数组类型，其元素使用内联存储。大小是类型的一部分，写在元素类型之前的尖括号中。

InlineArray 的元素不存储对包含元素的缓冲区的引用，而是直接存储。这意味着元素可以存储在栈上，或直接存储在其他类型中，而无需额外堆分配。

InlineArrays 可以存储可复制和不可复制的类型。

存储可复制类型时，InlineArray 本身可以复制，元素值会急切复制。把大小写成类型的一部分是通过新的泛型特性实现的，允许整数作为类型参数。

就像元素类型一样，InlineArray 的大小可以从数组字面量推断。如果你写一个 1、2 和 3 的 InlineArray，类型被推断为 3 个 int 的 InlineArray。在编译时知道 InlineArray 的大小还支持更多优化，比如当索引小于大小时消除边界检查。

容器类型通常需要提供对其底层存储的直接访问。

这对于在不需要知道原始容器布局的情况下对连续内存执行本地处理很有用。

例如，函数可能想要允许直接操作 Array 或 InlineArray 的连续存储。

在 Swift 6.2 之前，常见解决方案是降到不安全指针，它们高效，但从根本上不安全且容易出错。

新的 Span 类型是一种抽象，提供对连续内存的快速、直接访问，而不损害内存安全。

标准库为所有具有元素连续存储的容器类型提供 span 属性，包括 Array、ArraySlice、InlineArray 等。

Span 通过确保你在使用 Span 时连续内存保持有效来维持内存安全。这些保证定义了指针固有的内存安全问题，包括 use-after-free 和重叠修改。

它们在编译时检查，没有运行时开销。

例如，修改原始容器将阻止之后访问 span。

修改之后，你不能再访问 span 变量。

span 也不能比原始容器活得更久。这叫做生命周期依赖，它防止底层存储在仍可通过 span 访问时被销毁。

性能的另一个方面是响应性，当程序需要同时执行多个任务时。

并发编程很难，因为多个任务之间共享内存容易出错，导致不可预测的行为。Swift 6 中的数据争用安全在编译时防止这些错误，所以你可以编写并发代码而不必担心引入难以调试的运行时 bug。

但在许多情况下，最自然的代码容易数据争用，导致你必须处理的编译器错误。

像这个 PhotoProcessor 类这样的具有可变状态的类，只要你不并发访问它就是安全的。它有一个 async 方法，通过计算给定图片数据的主题来提取 Sticker。

但如果你尝试从 UI 代码在 main actor 上调用 extractSticker，你会得到一个错误，说调用有数据争用风险。这是因为语言中有几个地方会隐式地把工作卸载到后台，即使你从未需要代码并行运行。

Swift 6.2 改变这种理念，保持默认单线程，直到你选择引入并发。

Swift 6.2 中的语言更改使最自然的代码默认数据争用安全。这为在项目中引入并发提供了更易上手的路径。

当你选择引入并发是因为你想并行运行代码时，数据争用安全将保护你。

首先，我们让在具有可变状态的类型上调用 async 函数更容易。

async 函数不再被急切地卸载到特定 actor 之外，而是继续在被调用的 actor 上运行。

这消除了数据争用，因为传入 async 函数的值永远不会离开 actor。async 函数仍然可以在其实现中卸载工作，但客户端不必担心它们的可变状态。

接下来，我们让在 main actor 类型上实现 conformances 更容易。这里我有一个名为 Exportable 的协议，我正在尝试为我的 main actor StickerModel 类实现 conformance。

export 要求没有 actor 隔离，所以语言假设它可以从 main actor 之外调用，并阻止 StickerModel 在其实现中使用 main actor 状态。

Swift 6.2 支持这些 conformances。需要 main actor 状态的 conformance 被称为 *isolated* conformance。这是安全的，因为编译器确保 main actor conformance 只在 main actor 上使用。我可以创建一个 ImageExporter 类型，把 StickerModel 添加到任何 Exportable 项的数组中，只要它保持在 main actor 上。

但如果我允许 ImageExporter 从任何地方使用，编译器会阻止把 StickerModel 添加到数组，因为从 main actor 之外调用 StickerModel 上的 export 是不安全的。

使用 isolated conformances，你只需在代码表明它并发使用 conformance 时才解决数据争用安全问题。

全局和静态变量容易数据争用，因为它们允许从任何地方访问可变状态。

保护全局状态的最常见方式是 main actor。并且在没有很多并发任务的项目中，用 main actor 注解整个类来保护其所有可变状态是很常见的。

你可以通过在项目中的所有东西上写 `@MainActor` 来建模完全单线程的程序。

为了更容易建模单线程代码，我们引入了默认推断 main actor 的模式。这消除了关于不安全全局和静态变量、对其他 main actor 函数（如 SDK 中的函数）的调用等的数据争用安全错误，因为 main actor 默认保护所有可变状态。

它还减少了大部分单线程代码中的并发注解。

这个模式非常适合在 main actor 上做大部分工作的项目，以及并发代码封装在特定类型或文件中的项目。它是 opt-in 的，推荐用于 App、脚本和其他可执行 target。

把工作卸载到后台对于性能仍然重要，例如在执行 CPU 密集型任务时保持 App 响应。

让我们看看 PhotoProcessor 上 extractSticker 方法的实现。

它首先检查是否已经为图片提取了 sticker，以便可以立即返回缓存的 sticker。

如果 sticker 尚未缓存，它从图片数据提取主题并创建新的 sticker。extractSubject 方法执行昂贵的图片处理，我不想阻塞 main actor 或任何其他 actor。我可以使用 `@concurrent` 属性把这项工作卸载。`@concurrent` 确保函数始终在并发线程池上运行，释放 actor 同时运行其他任务。

这些语言更改共同工作，使并发更易上手。

你从默认在 main actor 上运行的代码开始，在那里没有数据争用风险。当你开始使用 async 函数时，这些函数运行在它们被调用的地方。仍然没有数据争用风险，因为所有代码仍然在 main actor 上运行。当你准备好拥抱并发以提高性能时，很容易把特定代码卸载到后台以并行运行。
