大家好，欢迎来到理解 Swift 性能这场演讲。我是 Kyle。Arnold 和我今天非常激动能来这里和大家聊聊 Swift。

作为开发者，Swift 为我们提供了一个广阔而强大的设计空间可供探索。Swift 拥有多种一等类型，以及各种用于代码复用和动态性的机制。

所有这些语言特性都可以以有趣的、涌现的方式组合起来。那么，我们该如何缩小这个设计空间、为手头的工作挑选合适的工具呢？首先，也是最重要的一点，你需要考虑 Swift 不同抽象机制的建模影响。值语义还是引用语义更合适？这个抽象需要多动态？Arnold 和我今天也想让你们学会用性能来缩小设计空间。以我的经验，把性能影响纳入考虑，往往能帮我找到更符合 Swift 惯用法的方案。所以，我们今天会主要聚焦在性能上。我们也会稍微谈一点建模，但去年有几场很棒的演讲，今年也有一场很棒的演讲，讲的是如何用强大的技巧在 Swift 中为你的程序建模。如果你想从这场演讲中获得最大的收获，我强烈建议你至少看一下其中一场。

好，我们想用性能来缩小设计空间。理解 Swift 抽象机制性能影响的最佳方式，就是理解它们底层的实现。这就是我们今天要做的事。我们会先确定评估不同抽象机制选项时应该考虑的几个维度。针对每一个维度，我们会用 struct 和 class 追踪一些代码，来加深我们对其开销的心智模型。然后我们会看看如何应用所学到的东西，来清理和加速一些 Swift 代码。

在这场演讲的后半部分，我们会评估面向协议编程的性能。我们会看看协议和泛型这类进阶 Swift 特性的实现，从而更好地理解它们在建模和性能上的影响。先做个简单声明：我们接下来会看到的是 Swift 编译并在你的代码背后执行时的内存表示和生成代码表示。这些不可避免会是简化版本，但 Arnold 和我认为我们在简洁和准确之间取得了很好的平衡。这是一个很好的心智模型，可以用来推理你的代码。

好，让我们先从确定性能的不同维度开始。

所以，当你在构建一个抽象、选择一种抽象机制时，你应该问自己："我这个实例会分配在栈上还是堆上？当我传递这个实例时，我会产生多少引用计数开销？当我在这个实例上调用方法时，它会是静态派发还是动态派发？"如果我们想写出高速的 Swift 代码，我们就需要避免为用不上的动态性和运行时特性付出代价。

而且我们需要学会何时以及如何在这些不同维度之间做权衡，以获得更好的性能。

好，我们会逐一讲解这些维度，先从分配开始。

Swift 会自动为你分配和释放内存。其中一部分内存会分配在栈上。

栈是一个非常简单的数据结构。你可以往栈的末端压入内容，也可以从栈的末端弹出内容。因为你只能在栈的末端添加或移除内容，我们可以只靠保持一个指向栈末端的指针来实现栈——或者说实现压入和弹出。这也意味着，当我们调用一个函数时——或者说，栈末端的那个指针叫作栈指针。当我们调用一个函数时，我们只需简单地递减栈指针来腾出空间，就能分配所需的内存。当我们的函数执行完毕后，我们只需把栈指针递增回调用这个函数之前的位置，就能轻松地释放这块内存。如果你对栈或栈指针不太熟悉，我希望你从这张幻灯片中带走的一点是：栈分配有多快。它的成本几乎就等于赋值一个整数。

这和堆形成对比，堆更加动态，但效率比栈低。堆能让你做一些栈做不到的事，比如分配具有动态生命周期的内存。

但这需要更高级的数据结构。所以，如果你要在堆上分配内存，你实际上得搜索堆这个数据结构，找到一块大小合适的未使用内存块。然后当你用完之后，要释放它，你得把那块内存重新插回到合适的位置。

所以，很明显，这里涉及的工作比栈上简单地赋值一个整数要多。但这些甚至不一定是堆分配涉及的主要成本。因为多个线程可能同时在堆上分配内存，堆需要用加锁或其他同步机制来保护自身的完整性。这是一笔相当大的开销。如果你今天没有留意在你的程序中何时、何地在堆上分配内存，那么只要稍微用心一点，你很可能就能大幅提升性能。

让我们把这段代码和完全相同的代码做个对比，只是这次 point 是一个 class 而不是 struct。

好，当我们进入这个函数时，就和之前一样，我们在栈上分配内存。但这次不是为了 point 上属性的实际存储分配内存，而是为 point1 和 point2 的引用分配内存。

指向内存的引用会被分配在堆上。所以，当我们在 (0, 0) 处构造 point 时，Swift 会锁定堆，然后搜索这个数据结构，找到一块大小合适的未使用内存块。然后，一旦拿到这块内存，我们就可以用 x 为 0、y 为 0 来初始化它，并用那块堆内存的地址来初始化我们的 point1 引用。请注意，当我们在堆上分配时，Swift 实际上为我们的 point class 分配了四个字（word）的存储空间。这和 point 是 struct 时分配的两个字形成对比。这是因为现在 point 是一个 class，除了为 x 和 y 存储的部分之外，我们还多分配了两个字，这两个字是由 Swift 代为管理的。在堆示意图里，这两个字用蓝色方框标出。

当我们把 point1 赋值给 point2 时，我们不会像 point1 是 struct 时那样拷贝 point 的内容。相反，我们会拷贝引用。所以，point1 和 point2 实际上指向的是堆上同一个 point 实例。这意味着，当我们把 5 赋值给 point2.x 时，point1.x 和 point2.x 的值都是 5。这就是所谓的引用语义，可能导致状态的意外共享。然后，我们会使用 point1、使用 point2，接着 Swift 会代为释放这块内存，锁定堆，把那块未使用的内存重新插入到合适的位置。然后我们就可以把栈弹出。

好，我们刚才看到了什么？我们看到 class 的构造成本比 struct 高，因为 class 需要一次堆分配。

因为 class 分配在堆上并具有引用语义，class 拥有一些强大的特性，比如身份标识和间接存储。但是，如果我们的抽象不需要这些特性，用 struct 会更好。

而且 struct 不像 class 那样容易出现状态的意外共享。让我们看看如何把这一点应用到改进一些 Swift 代码的性能上。这是我一直在开发的一个消息应用里的例子。这是来自视图层的代码。我的用户发送一条文本消息，在那条文本消息背后，我想画一个漂亮的气泡图片。我的 makeBalloon 函数就是生成这张图片的，它支持不同气泡的各种配置——也就是不同气泡的整个配置空间。举个例子，我们看到的这个气泡是蓝色的，方向朝右，带一个尾巴。我们还支持，比如说，一个灰色的气泡，方向朝左，带一个气泡形尾巴。

现在，makeBalloon 函数需要非常快，因为我在分配启动和用户滚动期间会频繁调用它。所以我加了这层缓存。这样一来，对于任意给定的配置，我都不需要生成这张气泡图片超过一次。如果我已经生成过一次，我就可以直接从缓存里取出来。我实现这一点的方式，是把颜色、方向和尾巴序列化成一个 key，这个 key 是一个字符串（String）。现在，这里有几件事不太让人满意。

String 作为这个 key 并不是一个特别强的类型。我用它来表示这个配置空间，但我同样可以轻易地把我家狗的名字塞进那个 key 里。所以那里没有太多安全性可言。而且，String 能表示的东西太多了，因为它实际上是把字符内容间接存储在堆上的。这意味着，每次我们调用这个 makeBalloon 函数时，即使命中缓存，我们也会产生一次堆分配。

看看我们能不能做得更好。在 Swift 中，我们可以只用一个 struct 来表示颜色、方向和尾巴这个配置空间。这比用 String 来表示这个配置空间安全得多。而且因为 struct 在 Swift 中是一等类型，它们可以被用作我们字典里的 key。

现在，当我们调用 makeBalloon 函数时，如果命中缓存，就没有分配开销，因为构造一个像这样只有一个属性的 struct 不需要任何堆分配。它可以分配在栈上。所以这样既安全得多，也会快得多。

让我们进入下一个性能维度：引用计数。

刚才讲堆分配的时候，我略过了一个细节。Swift 是怎么知道什么时候可以安全地释放它在堆上分配的内存的？答案是，Swift 会为堆上的每个实例保留一个总引用数的计数，并且把这个计数保存在实例本身上。当你添加一个引用或移除一个引用时，那个引用计数就会递增或递减。当这个计数变为零时，Swift 就知道已经没有人再指向堆上的这个实例了，可以安全地释放这块内存。

关于引用计数，需要记住的关键一点是：这是一个非常频繁的操作，而且实际上远不止递增和递减一个整数这么简单。首先，执行递增和递减本身就涉及好几层间接寻址。但更重要的是，就像堆分配一样，这里也需要考虑线程安全，因为多个线程可能同时对任意一个堆实例添加或移除引用，我们实际上必须以原子方式递增和递减引用计数。而且由于引用计数操作的频率很高，这项成本会累积起来。

那么，让我们回到我们的 point class 和我们的程序，看看 Swift 实际上代我们做了什么。这里我们现在有——作为对比——一些生成的伪代码。我们看到我们的 point 多了一个属性，refCount。我们还看到 Swift 加了几处对 retain 的调用——或者说一次对 retain 的调用和几次对 release 的调用。Retain 会原子性地递增我们的引用计数，release 会原子性地递减我们的引用计数。这样一来，Swift 就能追踪堆上的 point 还有多少个存活的引用。好，如果我们快速地追踪一下，我们可以看到，在堆上构造完 point 之后，它会以引用计数为一进行初始化，因为我们有一个存活的引用指向那个 point。随着我们的程序继续执行，我们把 point1 赋值给 point2，我们现在有了两个引用，所以 Swift 添加了一次对我们 point 实例引用计数的原子递增调用。随着我们继续执行，一旦我们用完了 point1，Swift 就添加了一次原子递减引用计数的调用，因为就 Swift 而言，point1 不再是一个真正存活的引用了。类似地，一旦我们用完了 point2，Swift 又添加了一次对引用计数的原子递减。这时，已经没有更多引用在使用我们的 point 实例了，所以 Swift 知道现在可以安全地锁定堆，把那块内存归还给它。

那 struct 呢？struct 涉及任何引用计数吗？嗯，当我们构造 point struct 时，没有涉及堆分配。当我们拷贝它时，也没有涉及堆分配。这整个过程都没有涉及引用。所以，我们的 point struct 没有引用计数开销。那更复杂一点的 struct 呢？这里我们有一个 label struct，它包含 text（String 类型）和 font（UIFont 类型）。就像我们前面听到的，String 实际上是把字符的内容存储在堆上的。所以它需要被引用计数。而 font 是一个 class。所以它也需要被引用计数。如果我们看看内存表示，label 有两个引用。而当我们对它做一份拷贝时，我们实际上又多加了两个引用——一个给 text 的存储，另一个给 font。Swift 追踪这些堆分配的方式，就是添加对 retain 和 release 的调用。

所以，这里我们看到，label 实际上会产生一个 class 两倍的引用计数开销。好，总结一下，因为 class 分配在堆上，Swift 必须管理这次堆分配的生命周期。它是通过引用计数来做到这一点的。这并不是一件小事，因为引用计数操作相对频繁，而且因为引用计数具有原子性。

这只是使用 struct 的又一个理由。

但如果 struct 里包含引用，它们也会产生引用计数开销。事实上，struct 产生的引用计数开销是和它们包含的引用数量成正比的。所以，如果它们包含的引用超过一个，它们产生的引用计数开销就会比一个 class 更多。让我们看看如何把这一点应用到我那个理论上的消息应用的另一个例子中。我的用户并不满足于只发送文本消息。他们还想互相发送附件，比如图片。所以我有这个 struct attachment，它是我应用里的一个模型对象。它有一个 fileURL 属性，存储这个附件在磁盘上数据的路径。它有一个 uuid，是一个唯一的随机生成标识符，这样我们就能在客户端和服务器、以及不同的客户端设备上识别这个附件。它有一个 mimeType，存储这个附件所代表的数据类型，比如 JPG、PNG 或 GIF。这个例子里唯一算得上不简单的代码大概就是那个可失败的初始化方法（failable initializer），它会检查 mimeType 是不是我这个应用支持的 mimeType 之一，因为我并不支持所有的 mimeType。如果不支持，我们就会中止初始化。否则，我们就会初始化我们的 fileURL、uuid 和 mimeType。所以，我们注意到有不少引用计数开销，而如果我们实际看看这个 struct 的内存表示，我们的这三个属性在被传递时都会产生引用计数开销，因为这些 struct 底层的每一个属性都是指向堆分配的引用。

我们可以做得更好。

首先，就像我们前面看到的，uuid 是一个定义得非常清楚的概念。它是一个 128 位的随机生成标识符。而我们不想让你随便把任何东西塞进 uuid 字段。而如果它是 String 类型，你确实可以随便塞。今年，Foundation 新增了一个值类型，用于 uuid，这非常棒，因为它把这 128 位直接内联存储在这个 struct 里。所以让我们用上它。这样做会消除我们为那个原本是 String 的 uuid 字段所付出的所有引用计数开销。而且我们获得了更严格的安全性，因为我不能随便往里塞东西了。我只能塞一个 uuid。这太棒了。让我们看看 mimeType，看看我是怎么实现这个 isMimeType 检查的。今天我实际上只支持一个封闭的 mimeType 集合：JPG、PNG、GIF。

而且，你知道的，Swift 有一个很棒的抽象机制，用来表示一组固定的东西。那就是枚举（enumeration）。所以，我打算把那个 switch 语句放进一个可失败的初始化方法里，把那些 mimeType 映射到我枚举里相应的 case。这样一来，我现在用这个 mimeType 枚举获得了更强的类型安全，而且我也获得了更好的性能，因为我不需要把这些不同的 case 间接存储在堆上了。Swift 实际上有一种非常紧凑、便利的写法来写完全相同的代码，那就是用一个以原始 String 值为底的枚举。所以这段代码实际上和之前那段完全等价，只是它更强大，具有同样的性能特征，但写起来方便得多。所以，如果我们现在再看看我们的 attachment struct，它的类型安全性强得多。我们有了强类型的 uuid 和 mimeType 字段，而且我们付出的引用计数开销也大大减少了，因为 uuid 和 mimeType 都不再需要被引用计数或堆分配。

好，让我们进入性能的最后一个维度：方法派发。

当你在运行时调用一个方法时，Swift 需要执行正确的实现。

如果它能在编译时就确定要执行哪个实现，这就叫作静态派发。而在运行时，我们只需直接跳转到正确的实现。这非常棒，因为编译器实际上能够洞察到哪些实现会被执行。所以它就能相当激进地优化这段代码，包括内联（inlining）之类的手段。

这和动态派发形成对比。

对于动态派发，我们没法在编译时就直接确定要走哪个实现。所以在运行时，我们实际上要查找这个实现，然后跳转过去。所以，单看动态派发本身，它并不比静态派发贵太多。只是多了一层间接寻址。不涉及像引用计数和堆分配那样的线程同步开销。但是这种动态派发会挡住编译器的视线，所以虽然编译器能为我们的静态派发做那些非常酷的优化，对于动态派发，编译器就没法推理穿透它了。所以我提到了内联。什么是内联？让我们回到我们熟悉的 struct point。

它有 x 和 y，还有一个 draw 方法。我还加了这个 drawAPoint 方法。drawAPoint 方法接收一个 point，然后就在它上面调用 draw。相当花哨。然后我程序的主体在 (0, 0) 处构造了一个 point，并把这个 point 传给 drawAPoint。drawAPoint 函数和 point.draw 方法都是静态派发的。这意味着编译器确切地知道会执行哪些实现，所以它实际上会把我们对 drawAPoint 的调用，直接替换成 drawAPoint 的实现。

然后它会把我们的 point.draw 方法调用，因为这是静态派发，替换成 point.draw 的实际实现。所以，当我们在运行时执行这段代码时，我们就只需构造我们的 point，运行这个实现，然后就结束了。我们不需要那两次静态派发的开销，也不需要建立和拆除相应调用栈的开销。所以这非常棒。这也解释了为什么静态派发以及静态派发是如何比动态派发更快的。

单个静态派发和单个动态派发相比，差别没有那么大，但一整条静态派发的链条，编译器就能洞察这整条链条。而动态派发的链条则会在每一步都挡住更高层次的推理。所以，编译器能够把一整条静态方法派发的链条，折叠成一个没有任何调用栈开销的单一实现。这真的很棒。那么，我们为什么还需要动态派发这种东西呢？其中一个原因是它让像多态这样强大的东西成为可能。如果我们看一个传统的面向对象程序，有一个 drawable 抽象超类，我可以定义一个 point 子类和一个 line 子类，它们各自用自己定制的实现来重写 draw。然后我有一个程序，可以多态地——可以创建一个 drawable 数组。里面可能有 line，也可能有 point。它可以对每一个都调用 draw。

那这是怎么运作的呢？因为 drawable、point 和 line 都是 class，我们可以创建一个由这些东西组成的数组，它们大小都一样，因为我们是按引用把它们存在数组里的。然后当我们遍历它们时，我们会对每一个调用 draw。所以，我们应该能理解——或者至少有点直觉——为什么编译器没法在编译时确定该执行哪个正确的实现。因为这个 d.draw，它可能是一个 point，也可能是一个 line。它们是不同的代码路径。那它是怎么确定该调用哪一个的呢？编译器会给 class 添加另一个字段，这个字段是指向该 class 类型信息的指针，存储在静态内存中。所以，当我们调用 draw 时，编译器实际上代我们生成的代码，是通过这个类型去查找存储在静态内存里的类型上的一个叫作虚方法表（virtual method table）的东西，这个表里包含指向要执行的正确实现的指针。所以，如果我们把这个 d.draw 换成编译器代我们做的事，我们会看到它实际上是在通过虚方法表查找要执行的正确 draw 实现。然后它把实际的实例作为隐式的 self 参数传进去。

好，我们在这里看到了什么？class 默认是动态派发它们的方法的。单看这一点本身影响不大，但在涉及方法链式调用等场景时，它会妨碍像内联这样的优化，而这些影响是会累积起来的。不过不是所有 class 都需要动态派发。如果你从来不打算让某个 class 被子类化，你可以把它标记为 final，向你的队友和未来的自己传达这个意图。编译器会察觉到这一点，并静态派发那些方法。此外，如果编译器能推理并证明你在你的应用里永远不会去子类化某个 class，它也会主动把那些动态派发转换成静态派发。如果你想了解更多关于这是怎么做到的，可以看看去年那场关于优化 Swift 性能的精彩演讲。
