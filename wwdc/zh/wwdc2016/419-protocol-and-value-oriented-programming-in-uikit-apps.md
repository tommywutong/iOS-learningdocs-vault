至于内容类型，我们就直接用子对象自身的内容类型。这意味着我们可以做出一个只用 UI view 的 DecoratingLayout，也可以做出一个只用 SK node 的 DecoratingLayout。两者都是强类型的，所以我们可以取出它们的内容，并且清楚知道它们具体是什么，同时它们仍然可以共享全部的布局逻辑。

所以关联类型是让你的协议变得更强大的一个很棒的方式。

既然我们已经改进了布局协议，我们也可以重新审视一下 DecoratingLayout 的子对象类型。

目前它们被要求是相同的类型，如果它们都是 UI view，这样做效果很好，但如果我们像之前讲组合时提到的那样，想把一个 CascadingLayout 和一个 UIView 组合在一起，这样就不行了。

我们这里真正想要的，是所有内容都具有相同的类型。

那我们就更新一下我们的布局来体现这一点。我们可以把这个结构体改成带有两个不同泛型类型参数的形式，每个子对象各对应一个。

然后，我们还可以加一个泛型约束，要求这两个类型具有同一种内容类型。

这就让我们能表达出我们真正想要的那个精确限制：我们的子对象的内容必须是同一种类型。这就是我们最终完成的协议，它代表了我们的布局抽象，比我们之前那个版本要好得多。它现在有了真正的意义，是一整套操作，完整地表达了「成为布局过程一部分」意味着什么。

你也可以查看我们的示例 App，了解这一切是怎么运作的所有细节，包括我们是怎样用它在后台线程上做图像渲染的布局的。我们新的布局协议还有最后一个可以派上用场的地方，那就是我们的单元测试。我们可以写一个带 frame 属性、并遵循我们布局协议的结构体，然后把我们的单元测试改成用它、而不是用 UI view 来作为布局里的子对象。

现在我们的布局就只是在这些简单的结构体上设置 frame。

这意味着我们的测试完全脱离了 UIView，只依赖我们自己布局和测试用结构体里的逻辑。所以我们是在不使用 GUI 的情况下对我们的布局做单元测试。我想 Crusty 一定会为此感到骄傲。

我想重点讲讲我们怎样在控制器层使用值类型，我们会结合 App 的撤销（Undo）功能来聊这个话题。

我们为我们的梦境列表实现了撤销功能，效果非常好，但我们注意到有一个小 bug：撤销对我们的「最爱生物」功能不起作用。

现在我们来重现一下这个问题：我们可以点一下「最爱生物」这一行。目前我们设置的最爱生物是那只粉色独角兽，我们把它改成龙。要完成这次修改，我们只需要点一下右上角的「完成」按钮。好了，我们已经修改了最爱生物，但问题是，如果我们摇一摇来撤销，什么都不会发生。

这就是一个 bug。我们来看看代码，看看这到底是为什么发生的。目前我们的视图控制器上有两个模型属性：一个是我们的梦境，一个是我们的最爱生物。这在 UIKit App 里是相当典型的安排，尤其是当它们变得越来越大、你的功能集越来越多的时候。我们一开始只有梦境这一个功能，所以我们为它实现了撤销，而且效果很好。但在我们加入「最爱生物」功能之后，我们没有为它写撤销代码，这个 bug 说白了就是我们忘了写那段代码。

要修复这个问题，我们本可以再加一条代码路径，专门为最爱生物实现撤销。但这听起来就是一场维护上的噩梦，因为这样一来，每次我们再加一个模型属性，就得再加一条代码路径来实现撤销，这看起来可不太好，我们不想要这样。所以在那之后，我们退了一步，想找出一个能随着我们加入更多模型属性而更好扩展的方案。这个方案就是把这些模型属性组合成一个单独的值——我们的 model 结构体，而我们的撤销逻辑将只针对这一个类型来处理。这里有一点非常重要：我们的 model 仍然要具有值语义，这是因为它是由另外两个值组合而成的。

这个方案非常棒，因为现在我们这两个模型属性只对应一条代码路径了，而且如果我们再加一个模型属性，也仍然只有一条代码路径。这真的很棒。

在代码里实现这一点的方式，就是把视图控制器上原来那两个模型属性，挪到我们新的 model 结构体里。

从这之后，我们要做的就只是给视图控制器添加一个新的 model 属性。这就是我们要采用的结构方式，但现在我们需要实现撤销代码了，那该怎么做呢？我想先给大家展示一下通常的做法，然后我们会看看它为什么有点问题。左边是我们视图控制器当前的 model 值，右边是我们的操作和撤销栈。

在我们 App 最初的版本里，我们把撤销栈想成一系列小步骤。每一步都负责先修改 model，再修改 view 使其保持一致。比如说，在第一个撤销步骤里，我们要移除用户刚添加的那个梦境，然后在那个表格视图里删掉对应的行。我们可以继续下一个撤销步骤：在这个撤销步骤里，我们要把 model 改回一只粉色独角兽。这种「分别修改各个 model 属性、再独立更新 view」的做法，真的很容易出错，因为你需要让 model 里的改动和 view 里的改动精确匹配。

而一旦没能做到这一点，就会在你的 model 和 view 之间引发大量不一致，于是你就会遇到这样的 bug。

我相信你们所有人都遇到过这种情况，我自己也是经常遇到。

而且真的很难调试。但为什么难调试呢？我们再看一眼我们最初的撤销栈。这些可撤销的改动到底是从哪来的？每一个可撤销的改动都来自我们的视图控制器，而且这些可撤销改动的顺序还很重要。随着我们给 App 添加功能，出错的机会也在不断蔓延。

所以我们的代码里没有哪一个地方，能让我们对 model 和 view 更新之间的对应关系进行推理。这就很糟糕，因为它实在太复杂了。那我们来想一个更简单的方式来处理撤销。如果不去记录那些小的改动，而是让栈里的每一项都是一个全新的值——一个全新的 model，那会怎样？这样一来，对 model 执行撤销就变得非常简单：只需要用栈里的那个值替换当前的 model，这样我们甚至都不用担心顺序问题，直接替换这个值就行了。既然我们已经把 model 这边理顺了，接下来我们需要弄清楚该怎样更新我们的 UI。所以在我们的视图控制器里，每当 model 发生变化，我们就会调用这个 modelDidChange 方法。

我建议大家去下载这份示例，仔细看看这个方法，了解更多关于它是怎么运作的细节。但在这个方法里，我们需要找出旧 model 值和新 model 值之间的差异，并相应地更新我们的 UI。

比如说，我们可以检查一下旧 model 的最爱生物是否和新 model 的最爱生物不同。

如果不同，我们就更新包含「最爱生物」那一行的表格视图分区。

正如我刚才提到的，工程里有一份更完整的实现，我建议你们去看看我们在那里更新的更多 UI。最后，我们只需要在重置 model 为旧值的地方注册撤销逻辑就行了。这非常棒，因为现在我们只需要——或者说我们只在一个地方注册撤销逻辑。那这样做的好处是什么呢？正如我们所看到的，现在更新 UI 只有一条代码路径了，而且各个操作之间是顺序无关的，这在之前可不是这样。

这确实极大地帮助我们对代码、对我们的 UI 更新代码进行局部推理。我们还看到了值是怎样和其他值很好地组合在一起的：如果我们把两个值作为一个值的属性，那个值仍然具有值语义。

但按照我们目前写代码的方式，当你设置一个属性时，你需要清空所有其他的属性，这真的非常容易出错。那我们要怎么解决这个问题呢？枚举其实非常适合表达互斥的值。所以我们把所有的 UI 状态属性都变成一个枚举值上的各个 case。

然后，我们就可以给视图控制器加一个 state 属性。通过使用枚举，我们可以确保我们的各个状态是互斥的。这非常棒，因为现在我们之前遇到的那种无效状态 bug 根本不可能出现了，而且这是由类型系统强制保证的。这种做法也意味着我们的状态是一次性整体改变的，不存在任何中间状态的可能性。所以我们不需要去协调那些带有隐式时序依赖的属性翻转。而作为一个额外的好处，把状态都放在一个地方，能让你更容易地把 App 启动到和用户离开时完全一样的状态。所以我强烈建议大家再去看看、下载一下这个工程，了解我们是怎样在 App 里实现状态恢复的。好了，我们今天讲了很多内容，一开始的目标是通过在基于「模型-视图-控制器」的应用里引入值类型和协议，来改善局部推理。那我们做得怎么样呢？我们首先让我们的 model 具有值语义，把 dream 类型做成了一个结构体。这让我们更容易对代码进行局部推理，因为我们的 dream 变量不会再被隐式共享。
