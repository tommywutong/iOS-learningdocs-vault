我们向你展示了如何把你的应用一路分析到反汇编层面。我们当时的目标是向你展示如何让你的代码尽可能快。而在某个时间点，你可能会想在被优化的代码上使用多个 CPU，以便完成更多工作。但这样做的同时，你也在增加系统负载。

随着系统负载的增加，几个二阶效应会悄然出现，例如抢占增多、锁争用加剧，以及虚拟内存活动增多。这三者中的任何一个，都足以抵消你做时间剖析时取得的成果。

所以在今天的专场里，我们会向你展示如何使用 System Trace 分析这些二阶效应。

我们会向你展示如何在保持最佳性能的同时高效地给系统加载任务。今天的专场结构如下。我们会先简单介绍 System Trace，以及它为什么与应用开发者相关。然后 Joe 和我会带你走一遍 System Trace。我们还会聊一聊线程、标记（signpost）、一点点虚拟内存，并向你展示一些充分利用这些工具的最佳实践。

那么，为什么应用开发者需要 System Trace？当你的应用成为设备上的焦点时，从用户的角度看，它就是整个系统。

用户不会把你的应用看作是与众多系统服务和守护进程平等竞争 CPU 时间和内存等共享资源的一员。

他们只看到你的 App。所以如果你的应用因为一阵虚拟内存活动，或者某个优先级设置不当的线程而卡顿，他们会来找你要修复。这是坏消息。

好消息是，当你的应用处于设备焦点时，它就是设备上最重要的东西。

操作系统知道这一点，会尽可能把 CPU 时间和内存都让给你。

所以我们说用 System Trace 做调优时，其实不是在调优系统，而是在调优你的应用，让它用好分配给它的资源。

System Trace 是 Instruments 中的一个模板。它在我们的全部四个平台上都工作得很好。

用它录制时，它会把内核置于一种特殊的追踪模式，记录所有正在发生的调度活动、系统调用和虚拟内存操作。

这些数据会随时间累积，可能非常庞大。所以我们在 Instruments 8 中做的一个改动，是把这个模板默认设为窗口模式（Windowed Mode）。也就是说，我们只保留最近大约 5 秒的数据。

这样做的好处是：你可以开始录制、摆弄你的应用，花多久去复现性能问题都行；当性能问题复现时，你按下停止，就能得到最后 5 秒的可操作数据。

这就是 5 秒数据可能的样子。这些轨迹可以相当稠密。

我们发现，如果你能把这份数据与应用内部的一些高层活动关联起来会非常有用，比如“我正在更新表格视图”“我有一个下载正在后台进行”“也许我正在更新图表”。这类高层信息。

好，Joe 看到的是一个教科书式的锁争用模式。现在有两个线程在工作，它们在带属性字符串创建代码的某处争用一个共享资源。即便我们只持有那把锁几微秒，性能影响也远不止于此。Joe 已经给你看了一点，但我想再多说一些。

当你的线程处于运行状态，意味着线程在 CPU 上。它在全速奔跑，你用 Time Profiler 做的所有性能优化此刻都在产生回报。在某个时刻，你确实调用了 ulock wake，在那之后不久它把线程置入阻塞状态。这里发生的事情是：ulock wait 系统调用意识到那把锁被另一个线程持有，于是它请求内核把你从 CPU 上拿下来，等那个线程——抱歉，等那把锁真正被获取时再把你放回来。

3.42 微秒之后，这确实发生了。我们进入可运行状态。

但当我们在可运行状态时，这就是我们回到 CPU 上所需的时间。

注意我们在可运行状态待了大约 7 微秒。那几乎是那把锁实际被争用时间的两倍。所以我们付出了可观的额外开销。

现在来谈谈抢占。我们在例子里没看到抢占，但它在 System Trace 中相当常见。

抢占是把你线程从 CPU 上非自愿地移除。

因为某个更高优先级的工作需要 CPU，但没有可用的，所以你的线程必须被移除。

这有一个例外。有一种你偶尔会看到的自愿式抢占。

它发生在自旋锁内部。当自旋锁意识到自己无法继续推进时，它会调用线程切换系统调用，实质上把它的时间片让给锁的持有者。

在 System Trace 的线程叙事里，它表现为一次 thread switch 调用。

其后的抢占叙事会说这是在让出 CPU，而不是被从 CPU 上移除。另一种更轻量的抢占形式叫中断状态。中断状态是指你的线程正在某个 CPU 上运行，而那个 CPU 必须处理一次硬件中断。

于是你的线程被挂起，中断处理程序运行，然后你的线程恢复。此时你的线程优先级并不重要。哪怕你优先级最高也没用，中断永远优先。好消息是这些通常很短暂，只有几微秒，通常不会累积成你应用里的性能问题。但它们确实会出现，所以我想提一下。Instruments 8 的另一个好东西叫 System Load instrument。它的作用是帮你找出 System Trace 中可能导致掉帧的热点。它通过两种方式做到。第一种是底部的表视图。它展示调度状态的图景：蓝色检查线下方所有准备运行的线程。

你可以看出在那一刻，我们有三个线程：一个是内核线程，两个是 Graphasaurus 线程。这些就是未被阻塞、正在尝试运行的线程。还能看到它们的核心分配。这个 instrument 的另一个功能叫 User Interactive Load Average 图。

它的含义是：每一根柱子代表一个 10 毫秒的时间窗，柱高是该 10 毫秒内活跃线程的平均数量。也就是正在运行、可运行、被抢占或被中断的线程——基本上就是未被阻塞的线程。

由于这是“用户交互负载平均值”，我们只纳入优先级大于等于 33 的线程，因为那些是可能干扰用户交互 QoS 等级体验的线程。

为了让它更醒目，当线程柱变成橙色时，意味着你的负载平均值已经超过该设备的核心数量。所以无论你在哪里看到一阵橙色，都能知道那里即将发生掉帧。你可能想放大那些橙色区域，确保你正在运行的线程平衡在正确的服务质量等级上。

那么，服务质量（Quality of Service）到底是什么？如果你还没接触过，QoS 是一种附加到 block、队列和线程上的属性。它基本上是向内核表达：你愿意投入多少系统资源来尽快完成这一件特定的工作。

不同的 QoS 等级会约束优先级范围。可以看到我们的 utility 等级把优先级压到了 4，而我们的用户交互代码运行在 30 多到 40 多的高位。

但 QoS 等级还会限制诸如 IO，以及代码运行时的 CPU 频率之类的东西。

所以为你的代码选择 QoS 时，务必仔细阅读文档，确保它与你在做的工作类型相匹配。

另一件会影响应用性能的事情是虚拟内存缺页。随着内存压力增大，它们在高负载下会稍微恶化。

好消息是它们是可管理的。

System Trace 拥有分析虚拟内存缺页所需的全部工具。在线程策略里，虚拟内存缺页显示为这些蓝色小胶囊。

在线程叙事里它会报告虚拟内存缺页，甚至附上在你的代码中该缺页在何处被解析的回溯。

我们还有一个专门分析虚拟内存缺页的 instrument。例如，你可以看到你的代码更容易受哪种缺页影响。比如，也许你的代码经历了更多的零填充（zero fill）或更多的写时复制（copy on write）。

关于虚拟内存缺页，你需要知道的下一件事是：缺页发生在访问时而不是分配时。你可以向内核请求一次很大的分配，比如 500 MB，但在你的进程中真正开始触碰或访问那次分配的页面之前，系统不会为它投入物理内存。这是分配内存时要考虑的一点。关于虚拟内存缺页另一件重要的事是：它们是内联解析的。你不需要显式调用什么来解析缺页。

你只需触碰标记为需要缺页的页面内的任意一个字节，内核就会接管你的线程，解析缺页，然后把控制权还给你。所以当你在 System Trace 的线程策略里看到那些蓝色胶囊时，发生的正是这件事。那么对你的应用里的虚拟内存缺页能做什么呢？最简单的做法——抱歉。

最简单的做法就是直接吸收它们。

我的意思是：在你的性能预算里留出足够的空间，让你在触碰期限之前能承受一定数量的虚拟内存缺页。

这会让你在高负载下更有韧性。这样随着内存压力增大，只要你的预算够大、余量够足，你就不会察觉性能差异。

我们知道，有些人对 UI 生成的期限并没有这么宽松。

那么另一种选择是尝试在后台线程上触发缺页。比方说你有一个游戏，玩家即将完成第一关并要过渡到第二关。你可以做的是向后台队列 dispatch async，然后在那个后台队列上触碰第二关内容的页面。等到你的渲染线程过来取新内容时，就不会有卡顿。

对这个方法我们要给一个警告：确保只触碰你绝对会用到的页面。因为如果你触碰的页面超出了所需，反而会让问题更糟。
