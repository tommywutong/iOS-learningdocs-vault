大家好。我是 Phil Azar，是能耗与性能工具团队的一名软件工程师。今天我很高兴能与大家分享 iOS 14 上 MetricKit 的新变化。你们的 App 是软件体验的关键部分，而且这些 App 的使用比以往任何时候都更频繁。当你的 App 在电池续航方面表现良好且性能出色时，它能让用户感到愉悦，并有助于提升整体软件体验的健康度。我们团队致力于为你提供强大的工具，以改善 App 的电池续航和性能表现。去年，我们推出了一系列相关工具来帮助你做到这一点，其中包括 MetricKit——一个用于收集电池续航和性能指标的设备端框架。

今天我很兴奋地要和大家分享 MetricKit 下一个版本将带来的内容。我们将从快速回顾如何使用 MetricKit 开始。然后，我们将讨论一些强大的新指标和诊断信息，接着深入探讨这些新接口。最后，我们将做一个简要总结。

让我们先回顾一下当前如何使用 MetricKit。

MetricKit 作为一个框架，从一开始就被设计为在开发周期的各个阶段为你提供数据，而这些阶段你通常无法直接访问运行你 App 的用户或设备。

这些阶段包括在外部 beta 测试（如 TestFlight）期间，或在你将 App 上架到 App Store 之后。

这意味着，作为开发者，在这些阶段利用 MetricKit 是一个强大的工具，因为它能让你真实地获取大量用户关于 App 的性能数据，并帮助你发现性能衰退中的趋势和模式。要使用 MetricKit，你需要遵循三个简单的步骤。第一步是在代码中链接并导入 MetricKit 框架。

第二步是实例化一个我们称之为 MetricManager 的共享实例，这个类充当了你与该框架的接触点。

最后，你需要实现一个提供的订阅者委托协议，以开始从框架接收指标。

让我们回顾一下系统是如何聚合这些负载并通过 MetricKit 传递给你的 App 的。

在一天中，操作系统会在你的 App 被使用时被动地聚合其性能数据。这些数据是匿名的，旨在保护用户隐私。

在一天结束时，这些数据被捆绑成一个 24 小时的负载，我们称之为 MetricKit 负载。指标负载由 MetricKit 接口强类型化。

让我们看看这些负载包含哪些类型的数据。MetricKit 负载包含多种数据，包括启动时间、CPU 时间、内存等等。在这里，我们提取了一个 MetricKit 负载并将其转换为人类可读的格式。

这使我们更容易看到数据被分成了三种聚合类型——累计（cumulative）、平均（averaged）和分桶（bucketized）数据。

处理后，这些数据在识别 App 不同构建版本之间的性能衰退方面极其有用，并且可以结合本地上下文来解决棘手的问题。然而，在某些方面，我们目前拥有的指标可能不足以完全定性一次衰退。

让我们看一个常见的例子——我们的启动性能数据。

我们在这里看到，冷启动（cold launch，即当我们的 App 从零开始启动且内存中没有资源时）的次数远远超过了恢复（resume）的次数。

在一个性能通常良好的 App 中，我们期望恢复的次数远多于启动的次数。似乎这里有些不对劲。另一个常见的情况是我们的累计 CPU 时间。

注意我们的累计 CPU 时间远小于累计前台时间。

这看起来也许是件好事，但尚不清楚这个工作量水平是表明性能衰退还是改进，因为 CPU 时间受时钟频率限制。

作为开发者，我们的第一直觉可能是更精确地量化这一点。但就目前情况来看，这并非一个简单的问题。

这里显然有发展空间。我们需要更多的细节来深入挖掘这些问题。今年，借助 MetricKit 2.0，我们将提供一些新指标，我们认为这些指标将帮助你更深入地挖掘这些常见问题。我们的团队努力扩展了一部分指标，以进一步明确 App 的工作负载、性能和稳定性。

这些指标包括 CPU 指令、滚动卡顿和 App 退出。让我们先从 CPU 指令开始。

MetricKit 中的 CPU 指令是 `MXCPUMetric` 类的新增内容。

该指标汇总了你的 App 每日累计已退役（retired）的指令数。

CPU 指令是衡量你的 App 在 CPU 上所做工作的绝对指标。它既与硬件无关，也与频率无关。

这将使你能够更精确地量化 App 的总工作量。接下来，让我们谈谈滚动卡顿（scroll hitches）。滚动卡顿是我们今年为你提供的一个新指标，旨在帮助你深入了解 App 的图形性能。当滚动过程中渲染的帧未能在预期时间显示到屏幕上时，就会发生滚动卡顿。

这通常会导致丢帧，从而引起用户可察觉的动画平滑度中断。

在 MetricKit 中，我们将提供你的 App 发生卡顿的时间与使用 UIScrollView 进行滚动的时间之比。

要深入了解卡顿的技术细节，我鼓励你观看我们今年关于滚动卡顿以及如何使用 XCTest 指标测量它们的讲座。

最后但同样重要的是，我们提供了 App 退出原因。

今年，我们提供了关于 App 退出和终止的指标。你将收到一份每日摘要，说明你的 App 在前台和后台退出的原因和次数。

我们认为这将有助于你追踪与 App 启动以及使用后台运行时框架相关的常见问题。

要更深入地了解如何利用这些指标并采用最佳实践，我鼓励你观看我们今年关于 App 终止的讲座，标题是“我的 App 为什么被杀掉了？”以上就是我们今年的新指标。我们认为，当你在 MetricKit 数据中寻找衰退时，它们将为你提供额外的确定性。

让我们更仔细地回顾一下我们的指标负载，并聚焦于我们仍然无法确定情况的一个方面。

在我们的 App 挂起持续时间直方图中，我们看到一些条目令人担忧，它们可能会严重干扰用户体验。

就目前情况来看，这肯定是一次衰退。但我们无法仅从指标中确定根本原因。

我们需要一些额外的诊断数据，比如挂起发生时的回溯（backtrace），才能弄清楚发生了什么。

这就引出了我们今年为 MetricKit 带来的另一个重要功能，它将帮助你查清另一类衰退的根本原因——MetricKit 诊断。

MetricKit 2.0 将提供一个新接口，让你能够访问有针对性的诊断信息。

这些诊断信息对于各种类型的衰退都是可操作的，包括挂起（hangs）、崩溃（crashes）、磁盘写入异常（disk write exceptions）和 CPU 异常（CPU exceptions）。

要在 MetricKit 2.0 中开始接收诊断信息，你需要做的只是实现一个新的 MetricManagerSubscriber 协议方法。就这么简单！这个新协议看起来几乎与去年接收指标负载的 didReceive 委托方法完全相同，我们预计你们中的许多人将能够使用已经为 MetricKit 构建的相同管道。

然而，这个协议不仅看起来一样，功能也相同。

从语义上讲，MetricKit 诊断的功能几乎与 MetricKit 指标完全相同。

如果我们再次看看之前的时间线，当你的 App 被全天使用时，除了指标外，MetricKit 系统现在还会被动地收集使用过程中发生的衰退的诊断信息。然后，系统将它们捆绑成一个并行的每日诊断负载，你可以将其与每日指标负载一起使用。现在，当你在指标（如挂起）中看到衰退时，你将能够引用（如果存在的话）与指标负载同时出现的关联诊断负载。

这个诊断负载有效地与其配套的指标负载一一对应。

现在让我们换个角度，更深入地研究这个新接口，熟悉它的功能。新的诊断接口反映了旧的指标接口，因为我们有几个新的基类——`MXDiagnostic`，所有诊断类都继承自这个基类；`MXDiagnosticPayload`，一个载体类，在一天结束时包含所有诊断信息；以及 `MXCallStackTree`，一个新的数据类，它封装了衰退发生时的回溯，供设备外使用。

包含在 `MXDiagnosticPayload` 中的 `MXDiagnostics`，包含了衰退发生时 App 的元数据，例如具体的构建版本和诊断特定数据。

诊断特定数据是我们今年提供的每个诊断子类所独有的数据子集。

然而，所有诊断子类中一致的部分是 `MXCallStackTree`。

`MXCallStackTree` 是我们提供的一个新数据类，它封装了衰退发生时的回溯。

这些回溯未经符号化（unsymbolicated），旨在用于设备外处理。它们将为你提供丰富的信息，帮助你诊断并抓住衰退的本质。

以下是这些调用栈树在转换为人类可读的 JSON 后的样子。

我们可以看到，使用 ATOS 这样的工具对各个帧进行符号化所需的一切信息都已齐备。这包括二进制信息，例如 UUID、偏移量和名称，以及帧地址。

这些新的调用栈树数据结构具有高度可移植性，并且可以在我们今年推出的其他性能工具中找到。要了解更多信息，我鼓励你观看我们关于新能耗和性能 API 的讲座。

正如我们之前所说，今年我们将提供 `MXDiagnostic` 的四个新子类——挂起（hangs）、CPU 异常、磁盘写入异常和崩溃。现在让我们看看每个新诊断子类中包含的独特数据，从挂起开始。挂起是指你的 App 长时间对用户输入无响应时发生的衰退。

这是由于你的 App 的主线程被阻塞或忙碌所致。

通过 MetricKit 接口提供的挂起诊断将为你提供 App 主线程无响应的时间以及主线程的回溯。

接下来是 CPU 异常，也就是 Xcode Organizer 中所谓的能耗日志。这些诊断将包含消耗的 CPU 时间、高 CPU 使用率期间采样的总时间以及消耗 CPU 时间的线程的回溯。

CPU 异常诊断与指标负载结合使用，对于识别可能难以复现的衰退极其有用。

接下来是磁盘写入。磁盘写入异常诊断与 CPU 异常诊断非常相似。

每个诊断将包含导致异常的写入总次数以及导致过度写入的线程的回溯。当你的 App 每日写入量超过 1 GB 阈值时，就会生成这些诊断。

最后但同样重要的是崩溃诊断。今年，我们很高兴地宣布 MetricKit 将为你提供 App 崩溃的诊断。

每次你的 App 崩溃时，一个包含异常信息、终止原因、虚拟内存区域信息（在发生错误访问崩溃的情况下）以及回溯的 `MXCrashDiagnostic` 将通过 MetricKit 诊断接口提供给你。

以上就是 MetricKit 诊断的介绍，这是一个强大的新工具，可以帮助你在真实用户场景中找到衰退的根本原因。让我们总结一下今天讨论的内容。

MetricKit 2.0 包含了丰富的新功能，这些功能将帮助你在优化工作上更进一步。我们提供了新的指标，让你能够更深入地了解在你的客户和 beta 测试群体中发生的衰退。我们还提供了有针对性的诊断信息，使你能够捕获这些群体中更难复现的衰退。

最后，我们通过易于实现的接口和现有接口来提供这些新功能，这一切对你来说成本极低。

今年我们有许多很棒的新内容和有用的旧内容，我鼓励你去看看。再次感谢你的收听，祝你在 WWDC 2020 的剩余时间里过得愉快。
