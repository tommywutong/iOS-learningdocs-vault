大家好，我叫 Holly，是 Swift 编译器团队的一名工程师。欢迎收看《拥抱 Swift 类型推断》。Swift 广泛使用类型推断，在不牺牲代码安全性的前提下实现简洁的语法。今天，我们会聊聊你什么时候可以利用类型推断，我们会了解类型推断在编译器里是怎么运作的，最后，我们会看看如何借助 Swift 和 Xcode，去理解并修复代码里的编译器错误。在开始之前，我们先回顾一下什么是类型推断。类型推断让你可以在编译器能从周围上下文推断出细节的时候，省略源代码里显式的类型标注和其他冗长的细节。在这个例子里，源代码里并没有为 x 写类型，但编译器会根据赋值时提供的值——一个字符串字面量——推断出 x 的类型是字符串。

x 的类型本来也可以显式指定，比如在 x 后面加一个冒号写一个类型标注，或者用 "as" 关键字把右边的值强制转换成 String。这是一个很小的例子，但当代码大量依赖类型推断时，事情会变得有趣得多，比如在一个 SwiftUI 项目里。许多 SwiftUI App 是通过组合一些小型的、可复用的视图，来构建出庞大而复杂的界面的，而这类代码在这些可复用组件的调用处，会大量依赖类型推断。我们会深入看一段 SwiftUI App 的代码，看看它是怎样在这些调用处利用类型推断的。然后，我们会了解编译器是如何解开这个类型推断谜题的，最后，我们会看看如何借助 Swift 编译器和 Xcode，去理解并修复代码里的编译器错误。

我们要看的是我和团队一直在开发的一个 App，叫 Fruta，用来点思慕雪（smoothie）。目前，这个 App 会展示一份思慕雪列表，你可以在右边的 Preview 里看到。

我想加一个功能，让用户可以搜索思慕雪。

我们先来看看目前的思慕雪列表是怎么实现的。

SmoothieList 的 body 从一个思慕雪数组创建了一个 SwiftUI List，把每一款思慕雪都映射成一个 SmoothieRowView。要加上搜索功能，我需要根据用户搜索的字符串来过滤思慕雪，所以 SmoothieList 需要一个 State 属性来存储这个字符串。

我构建了一个新的可复用视图，叫 FilteredList，它和 List 很像，但允许我给它的初始化方法多传两个参数，用来指定该怎么过滤这些思慕雪。

第一个参数是一个指向思慕雪上我想用来过滤的那个属性的 KeyPath，第二个参数是一个函数，用来根据这个属性计算某款思慕雪是否应该被包含在列表里。

在这个例子里，思慕雪会按标题过滤，如果标题里包含 searchPhrase 作为子字符串，这款思慕雪就会被包含进来。

hasSubstring 方法负责检查标题里是否包含 searchPhrase，如果 searchPhrase 是一个空字符串，它也会返回 true。

单看调用处，不太容易看出来，但这次对 FilteredList 初始化方法的调用，其实大量依赖了类型推断。我们来聊聊是什么导致这段代码依赖类型推断的，以及调用处是怎样借助类型推断写出更简洁代码的。要理解这个调用处省略掉的那些细枝末节，我们需要看看 FilteredList 及其初始化方法的声明。

因为 FilteredList 是一个通用视图，它应该能配合客户端想在列表里展示的任意数据类型和内容类型工作。这种灵活性是靠泛型实现的。

我引入了三个类型参数，它们是占位符，会在调用处被替换成实际的类型。这些实际的类型，正式的说法叫具体类型，要么在调用处指定，要么由编译器推断出来。在这个例子里，Element 是数据数组里元素类型的占位符，FilterKey 是 Element 上、数据将据以过滤的那个具体属性的类型的占位符，RowContent 是列表每一行要展示的视图类型的占位符。现在有了这三个类型参数，我就可以在初始化方法的参数列表里用上它们了。类型参数在初始化方法参数列表里出现的每一处，都是一次利用类型推断的机会——通过提供一个参数，给编译器一个线索，告诉它这个类型参数该被替换成什么。

我们稍后会看到这具体是怎么运作的，但现在，让我们先聚焦在我们构建这个列表时每个参数的类型上。首先，FilteredList 会用要映射的数据来初始化，这是一个由 Element 组成的数组。

下一个参数，是 Element 上用来过滤的一个具体属性，它是一个基类型为 Element、值类型为 FilterKey 的 KeyPath。

再下一个参数是 isIncluded 闭包，它是一个接收 FilterKey 作为输入、返回 Bool 的函数类型。这个闭包被标记为 "escaping"，因为 FilteredList 需要把这个闭包存进一个属性里。

最后一个参数是一个把数据元素映射成视图的闭包，它是一个接收 Element 作为输入、返回 RowContent 的函数类型。

这个闭包同样被标记为 "escaping"，因为它也需要被存储起来。

请注意，这个参数被标记为一个 ViewBuilder，从而让调用处这个闭包参数里可以使用 SwiftUI 的 DSL 语法。SwiftUI 的这套 DSL 让你可以通过在闭包体里把子视图一一列出来，声明出多个子视图，而 ViewBuilder 会把这些子视图收集进一个元组里，供父视图使用。这就是 FilteredList 完整的初始化方法。当一个 FilteredList 被初始化时，它的类型参数会被替换成具体类型。我们把这个初始化方法和 SmoothieList 里的调用处放在一起对比看看，看看调用处是怎么依赖类型推断的。

注意这个调用处写得有多干净。调用处没有写任何显式的类型标注，但它仍然给了编译器推断 FilteredList 每个类型参数具体类型所需的全部信息。

我们来看看，如果代码里所有的参数类型都被显式指定了，这个调用处会长什么样。我们会用占位符来表示类型参数，这样就能准确看出类型推断需要在哪些地方填入一个具体类型。

首先，FilteredList 的这三个类型参数，本可以在调用处、FilteredList 后面的尖括号里显式指定。

第一个参数的类型，也就是一个由 Element 组成的数组，本可以在 "smoothies" 参数后面用 "as" 关键字来指定。

在第二个参数里，Element 是 KeyPath 的基类型。这本可以通过在 KeyPath 字面量里、反斜杠和点之间显式写出一个基类型来指定。

KeyPath 这个类型整体，本可以在 KeyPath 字面量后面用 "as" 关键字来指定。

接下来，isIncluded 闭包的类型，本可以在闭包体里用一个类型标注来指定。

最后，RowContent 闭包的类型，同样本可以在闭包体里用一个类型标注来指定。

好，我最初写的源代码里，堆满了大量冗长的类型标注，其中还有一堆需要靠类型推断来填的占位符。

我没有去手动搞清楚这些占位符该填什么，而是依赖类型推断去准确弄清楚这些类型应该是什么。换句话说，类型推断能帮你更快地写出源代码，因为你不需要确切知道该怎样在代码里拼出所有这些类型。

我们来聊聊编译器是怎么弄清楚这些占位符该被替换成什么的。你可以把类型推断想象成一个拼图游戏。类型推断算法通过利用源代码里的线索，把缺失的碎片一块块填上，来解开这个拼图。

填上拼图的一块，也可能会为剩下的碎片揭示出更多线索。

我们来看看能不能一起解开这个拼图，就像编译器用类型推断替我们做的那样，利用源代码里的线索。首先，"smoothies" 这个参数可以告诉我们 Element 该填什么，我们知道 "smoothies" 是一个已经有类型的属性。用 QuickHelp，我们可以看到这个属性是一个由 "Smoothie" 元素组成的数组，所以 Element 可以填上 "Smoothie"。现在我们已经填上了一个 Element 占位符，我们可以把所有其他的 Element 占位符都替换成同样的 "Smoothie" 类型。

好，填上其他的 Element 占位符，又为 FilterKey 的具体类型揭示出了一条线索，因为现在我们知道，这个 KeyPath 字面量指的是 Smoothie.title。

再用一次 QuickHelp，我们可以看到 Smoothie.title 是一个字符串，所以 FilterKey 可以填上 "String"。既然我们知道了 FilterKey 是什么，其他的 FilterKey 占位符也可以替换成 "String" 了。拼图的最后一块是 RowContent，也就是那个尾随 ViewBuilder 闭包的返回类型。

因为这个闭包体里只有一个视图，ViewBuilder 会返回这唯一的子视图，它的类型是 SmoothieRowView。

同样，既然我们知道了 RowContent 是什么，最后一个占位符也可以替换成 SmoothieRowView 了。至此，我们解开了拼图的最后一块。这就是编译器在你整段代码里用来推断类型的策略。你写的代码为编译器提供线索。而算法的每一步，都会为后续的步骤揭示出更多信息。不过，源代码里的某条线索，也有可能导致编译器把某个占位符填成一个和拼图其余部分对不上的具体类型。如果有一块拼不上、导致这个拼图解不开，那就意味着源代码里有一个错误。我们来聊聊，在源代码存在错误的情况下，编译器是怎么调整它的类型推断策略、来解开这个拼图的。然后，我们会看看你可以怎样利用你的工具，去理解并修复这些错误。

我们回到编译器为 FilterKey 推断具体类型的那一步。记住，在前一步里，编译器把 Smoothie 推断为 key-path 的基类型，并用这个信息、通过查找 Smoothie.title 的类型，来推断出 FilterKey 的具体类型。

如果我在这个 key-path 字面量里犯了个错误，用错了属性，编译器就会试图把 FilterKey 的类型推断成那个错误属性的类型，在这个例子里就是 Bool。

然后，它会继续用这个同样错误的类型，去填其他的 FilterKey 占位符。

好，如果我们看看这个 Bool 类型在 isIncluded 闭包里是怎么用的，很明显这一块是拼不上的，因为 Bool 没有一个叫 hasSubstring 的方法。所以，编译器需要报告到底哪里出了问题。

在我们写的代码里犯错，是不可避免的，编程语言及其工具的设计，必须把我们作为人类的这种局限性考虑进去。Swift 编译器的设计思路，是把错误追踪整合进类型推断算法里，以便之后在错误消息里使用。在类型推断的过程中，编译器会记录下它遇到的任何错误的信息。然后，编译器会用一些启发式方法来"修复"错误，以便类型推断能继续进行下去。

一旦类型推断完成，编译器就会报告它收集到的所有错误，通常还会附带一些可操作的 fix-it，用来自动修复源代码里的错误，或者附带一些关于编译器推断出的、可能导致这个错误的具体类型的提示。这套集成的错误追踪机制，是在 Xcode 11.4 里的 Swift 5.2 中，为许多错误消息引入的，而在 Swift 5.3 和 Xcode 12 里，编译器已经把这套新策略用到了表达式里所有的错误消息上。好，我们都经历过那种在代码里修复编译器错误时令人沮丧的时刻。但错误消息的设计初衷，是想成为一个内建在编译器里的结对编程伙伴，帮你抓出错误、帮你修复它们，而不是任由你带着代码里的这个错误继续走下去。

我们切到 Xcode 里，看看该怎样借助这些工具，在写 Swift 代码时修复错误。在写任何代码之前，我要先打开 Xcode 菜单里的 behaviors，点击"编辑行为"。

我要为构建失败这种情况添加一个行为，让它自动帮我显示问题导航器。这样一来，每次我的项目构建失败时，我都能看到我项目里的所有错误。这里，我们在看 SmoothieList 目前的实现，以及它的 Preview。我已经把 FilteredList 加进了我的项目，你可以在项目导航器里看到它。但在我把 List 换成 FilteredList 之前，我需要先在列表上方加一个搜索栏。我已经加了那个 State 属性，用来存储用户的搜索字符串。所以现在，我要在 VStack 里、列表上方加一个 TextField。

我想让这个文本栏的标题是"Search"，然后我会传入搜索字符串。现在我要用 Command+B 构建一下，确保我没犯什么错。

注意，我刚加的那行代码现在出现了一个编译器错误。

我可以点开它，展开这个错误。

看起来是我用了一个类型为 "String" 的参数，而它和这个 TextField 初始化方法期望的参数类型不兼容——期望的是一个 binding。我犯的错误是传了搜索栏的值，而不是它的 binding，Swift 编译器能够看出这个 binding 确实具有兼容的类型，于是给了我一个 fix-it，建议我改用美元符号来引用这个 binding。

接下来，我想把这个 List 换成我新做的 FilteredList。

我要再构建一次，确保我没犯什么错。

但看起来又出现了一个错误。如果我展开这个错误，可以看到它是关于 Smoothie 没有满足 FilteredList 的 identifiable 要求。这可能会让人有点困惑，因为这部分代码里根本没写 "Identifiable" 这几个字。

请注意，在左边的问题导航器里，这个错误附带了一条编译器提示。

有了这套新的集成错误追踪机制，编译器会记录下遇到这个错误时、类型推断过程中发生了什么，这让编译器得以通过提示留下一些"面包屑"，引导你去看看你代码里的其他部分。这些提示能帮你把源代码编辑器里看到的错误，和项目里其他文件中的关键信息联系起来。而且，在 Swift 5.3 和 Xcode 12 里，你会看到多得多的提示。

我想把这条提示和错误并排看看，所以我要关掉画布，可以用 cmd+enter 这个快捷键来做到。现在，我按住 Option 和 Shift，同时点击这条提示，打开目标选择器。

现在我可以按右箭头，然后按回车，在一个新的编辑器里打开这个文件。

现在，我们在看 FilteredList 的声明。如果我展开这条提示，它指出编译器推断出 Element 的具体类型是 Smoothie。

在这个声明里，我可以看到 Element，也就是 Smoothie，被要求遵循 "Identifiable"。我一定是在把 Smoothie 用到 FilteredList 里之前，忘了给它加上这个一致性。在左边的编辑器里，我要 cmd+click 点一下 Smoothie，用"跳转到定义"。这里我就可以给它加上 Identifiable 所要求的一致性了。Smoothie 已经有一个叫 "id" 的属性了，所以 identifiable 协议的要求其实已经实现了。不过为了保险起见，我再构建一次，确认这确实修复了这个错误。

看起来我们又没有错误了。现在，我们关掉右边的编辑器，点一下"后退"按钮，回到 SmoothieList。现在，如果我在传给 FilteredList 初始化方法的某个参数上用 QuickHelp，我就能看到编译器推断出的具体类型。我们试试在这个 key-path 字面量上用 option+click 打开 QuickHelp。

就像我们解那个类型推断拼图时看到的一样，编译器根据推断出的 key-path 基类型，把 title 的类型推断成了一个字符串。记住，编译器是根据上面那一行的 smoothies 参数，把这个基类型推断成 Smoothie 的。

在结束之前，我想用画布确认一下过滤功能确实好用。我可以用 cmd+option+enter 这个快捷键把画布重新打开。

当我在代码里犯了拼写错误和其他一些错误时，编译器给出的错误消息是可操作的、也是有信息量的。此外，编译器里这套新的集成错误追踪机制，让编译器得以收集到关于失败原因多得多的信息，并通过提示呈现出来。
