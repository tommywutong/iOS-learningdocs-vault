大家好，欢迎来到 WWDC。

大家好，我是 Ben。我来自语言和运行时团队，今天我将向大家介绍今年我们在 iOS 和 macOS 的 Objective-C 运行时中所做的更改，这些更改显著改善了内存使用。这场讲座与大多数讲座有所不同。你不需要修改任何代码。我不会介绍任何需要学习的新 API，也不需要处理任何弃用警告。如果一切顺利，你什么都不用做，你的 App 就会变得更快。我们为什么要告诉你这些改进？部分原因是我们认为它们很酷很有趣，但也因为这些运行时层面的改进之所以成为可能，正是因为我们的内部数据结构隐藏在 API 之后。当 App 直接访问这些数据结构时，事情就会变得有点容易崩溃。

在这场讲座中，你将了解一些值得留意的场景——当与你协作的其他人（当然不是你）访问了不该访问的东西时，就可能出现这些状况。我们将介绍本次会议的三项变化。首先，是 Objective-C 运行时用于追踪类的数据结构发生了变化。

然后，我们将看看 Objective-C 方法列表（method list）的变化。

最后，我们将看看标记指针（tagged pointer）的表示方式的变化。

那么，让我们从类的运行时数据的更改开始。在磁盘上，在你的 App 二进制文件中，类的结构是这样的。

首先，是类对象本身，它包含最常访问的信息：指向元类（metaclass）、超类（superclass）以及方法缓存（method cache）的指针。

它还有一个指针，指向一块存储额外信息的数据，称为 `class_ro_t`。这里的“ro”代表只读（read only）。这块数据里包含类名，以及关于方法、协议（protocol）和实例变量（instance variable）的信息。

Swift 类和 Objective-C 类共享这套基础设施，因此每个 Swift 类同样拥有这些数据结构。

当类首次从磁盘加载到内存时，它们最初也是这样的，但一旦被使用，它们就会发生改变。那么，要理解接下来会发生什么，了解干净内存（clean memory）和脏内存（dirty memory）之间的区别会很有帮助。

干净内存是指加载后内容就不再发生变化的内存。

`class_ro_t` 是干净的，因为它是只读的。

脏内存则是指在进程运行期间内容会被修改的内存。

类结构在类得到使用后就会被弄脏，因为运行时会向其中写入新数据。例如，它会创建一个新的方法缓存，并从类结构指向它。

脏内存的代价比干净内存高得多。它必须在进程运行的整个生命周期内一直保留。

而另一方面，干净内存则可以被换出，从而为其他内容腾出空间，因为如果有需要，系统总是可以从磁盘重新加载它。

macOS 可以选择将脏内存交换出去，但在 iOS 中，脏内存的代价尤其高昂，因为 iOS 不使用内存交换机制。

正是由于脏内存代价高昂，才导致类的数据被一分为二。

能够保持干净的数据越多，效果就越好。通过将永不变化的数据分离出去，就可以让大部分类数据维持为干净内存。

这些数据已经足够让我们起步，但运行时需要追踪每个类的更多信息。因此，当一个类首次被使用时，运行时会为其分配额外的存储空间。

这个由运行时分配的存储空间就是 `class_rw_t`，用于存放读写数据（read/write data）。在这个数据结构中，我们存放的仅是在运行时才会生成的新信息。

例如，所有类都通过“第一个子类（First Subclass）”和“下一个兄弟类（Next Sibling Class）”这些指针被链接到一个树形结构里，这让运行时能够遍历所有当前正在使用的类，这对于让方法缓存失效等操作非常有用。

但是，为什么方法和属性已经在只读数据里有了，在这里还要再有一份呢？这是因为它们可能在运行时被修改。当一个分类（category）被加载时，它可以向类添加新方法，程序员也可以使用运行时 API 来动态添加方法。

由于 `class_ro_t` 是只读的，我们就需要在 `class_rw_t` 中追踪这些内容。

事实证明，这占用了相当多的内存。在任何一台给定的设备上，都有非常多的类在被使用。我们测量过，在一部 iPhone 上，整个系统范围内这些 `class_rw_t` 结构体大约占据了 30 兆字节。

那么，我们该如何给它们瘦身呢？别忘了，我们需要把这些东西放在可读写区域，是因为它们可能在运行时被修改。

但通过检测真实设备上的使用情况，我们发现只有大约 10% 的类真正在运行时修改过它们的方法。

而这个解构后的名字（demangled name）字段，只有 Swift 类在用；并且即便对 Swift 类来说，也只有当有代码请求其 Objective-C 名称时才需要用到它。

因此，我们可以把那些通常用不到的部分拆分出去，这就将 `class_rw_t` 的尺寸直接减半。

而对于那些确实需要这些额外信息的类，我们可以分配一个像这样的扩展记录（extended record），并把它挂载给对应的类去使用。

大约 90% 的类永远不需要这个扩展数据，仅此一项，就在整个系统范围内节省了大约 14 兆字节。这些内存现在可以用于更有成效的用途，比如存放你的 App 的数据。那么，你可以亲自在你的 Mac 上，通过在终端里运行几个简单的命令，看到这项变化带来的影响。我们现在就来看一下。我会进入我 MacBook 上的终端，然后运行一个在任何 Mac 上都可用的命令，叫做 `heap`。这个命令可以让你检查某个正在运行的进程所使用的堆内存。我将针对我 Mac 上的“邮件”App 来运行它。如果我只是直接运行它，它会输出成千上万行信息，显示“邮件”App 的每一次堆分配。所以，我准备只针对我们今天一直在讨论的那几个类型，用 `grep` 过滤一下。

也就是 `class_rw_t` 类型。我还会一并搜索一下表头。

从返回的结果中，我们可以看到“邮件”App 中使用了大约 9000 个这样的 `class_rw_t` 类型，但其中只有大概十分之一，也就是九百多一点，实际需要那些扩展信息。因此，我们可以轻松计算出这项改动所节省的内存。

这是尺寸减半的那种类型。所以，如果我们将总的节省量减去为扩展类型额外分配的内存量，就能看到仅为“邮件”这一个 App，我们就节省了大约四分之一兆字节的数据。如果把这个数字扩大到整个系统范围，那将是脏内存层面实实在在的节省。

现在，很多从类里取数据的代码，都要同时面对“有扩展数据”和“没有扩展数据”这两类类结构。当然，运行时已经为你处理好了一切，从外部视角来看，一切照常工作，只是占用更少的内存而已。

这之所以能行得通，是因为读取这些结构的代码都位于运行时内部，并且它们是同步更新的。

坚持使用这些 API 真的非常重要，因为任何试图直接访问这些数据结构的代码，都将在今年的操作系统发布后停止工作——因为内部布局已经变了，但这些代码对新的布局一无所知。我们见过一些因此而坏掉的真实代码；另外，除了你自己的代码，还要留意那些你可能在不知情的情况下引入 App 的外部依赖，它们也有可能在你没注意到的时候深入挖掘了这些数据结构。

这些结构体中的所有信息都可以通过官方 API 获取。比如 `class_getName` 和 `class_getSuperclass` 这样的函数。当你使用这些 API 来访问信息时，你就知道无论在幕后我们做了什么改动，它们都将持续工作。所有这些 API 都可以在 developer.apple.com 上的 Objective-C 运行时文档中找到。

接下来，让我们更深入地看看这些类数据结构，再了解另一项改动：相对方法列表（relative method list）。

每个类都挂载着一个方法列表。当你在类上编写一个新方法时，它就会被添加到这个列表里。运行时用这些列表来解析消息发送。

每个方法包含三部分信息。

首先是方法的名称，或称选择器（selector）。选择器是字符串，但因为它们是唯一的，所以可以直接用指针相等性来比较。

接下来是方法的类型编码。这是一个表征参数和返回类型的字符串，它不用于发送消息，但在诸如运行时自省（introspection）和消息转发（message forwarding）等场景中是必要的。

最后是一个指向方法实现（implementation）的指针——也就是方法的实际代码。当你编写一个方法时，它会被编译成一个包含你的实现的 C 函数，然后方法列表中的条目会指向该函数。我们来看一个单一方法。我选择了 `init` 方法。它包含了方法名、类型和实现这几个条目。

方法列表中的每一项数据都是一个指针。在我们的 64 位系统上，这意味着方法表中的每个条目都要占用 24 字节。

现在，它属于干净内存，但干净内存并非没有开销。它依然需要从磁盘加载，且在使用时就一直占据着内存。

现在，这是对进程内部内存布局的一个缩略视图。请注意，它并非按实际比例绘制。有那么一个巨大的地址空间，需要用 64 个位才能寻址。在这个地址空间内部，栈、堆、以及可执行文件和库（或称二进制映像，binary image）各自划分出了一片片区域，这里用蓝色表示。

让我们放大来看其中一个二进制映像。

在这里，我们展示了三个方法表条目，指向它们各自二进制文件内部的位置。这向我们揭示了另一项开销。一个二进制映像可以被加载到内存中的任何位置，具体取决于动态链接器（dynamic linker）决定把它放在哪儿。

这意味着链接器需要解析那些指向映像内部的指针，并在加载时把它们修正为指向其在内存中的实际位置，而这个过程也同样有开销。现在注意，来自某个二进制文件的类方法条目，永远只会指向它自己那个二进制文件内部的方法实现。不可能创建这么一个方法：它的元数据在一个二进制文件里，而实现它的代码却在另一个二进制文件里。

这意味着方法列表条目其实并不需要能够引用整个 64 位地址空间。

它们只需要能够引用它自己那个二进制文件内的函数，而这些函数总是在它附近的。

所以，与其使用绝对的 64 位地址，它们完全可以使用二进制文件内部的 32 位相对偏移量。而这正是我们今年做出的一项改动。这样做有几个好处。

首先，无论映像被加载到内存的哪个位置，这些偏移量始终是相同的，所以它们从磁盘加载之后就不需要再被修正了。

而且，因为它们不需要被修正，就可以被保存在真正的只读内存中，这更安全。

当然，32 位的偏移量也意味着我们把 64 位平台上这部分占用的内存量直接减半了。我们测量过，在一部典型的 iPhone 上，整个系统范围内大约有 80MB 这类方法数据。由于它们尺寸减半，我们就节省了 40 兆字节。这就意味着有更多内存可以给你的 App 用来取悦用户。

但是方法调配（swizzling）怎么办？二进制文件里的方法列表现在没法引用完整的地址空间了，但如果你调配了一个方法，那个替换的实现可能在任意位置。更何况，我们才刚说过希望保持这些方法列表为只读。

为了处理这种情况，我们另外维护了一个全局表，用来把方法映射到它们被调配后的实现。

方法调配是很少见的。绝大多数方法事实上从未被调配过，所以这个表最终并不会变得非常大。

更妙的是，这个表是很紧凑的。内存是以页面（page）为单位被弄脏的。在旧式的方法列表下，调配某一个方法就会把整个它所在的页面都弄脏，导致单次调配就产生好几千字节的脏内存。

而有了这个表，我们只需要为一个额外的表条目付出代价即可。一如既往，这些更改对你而言是透明的，一切照常工作。这些相对方法列表，将在今年晚些时候发布的新操作系统版本上得到支持。

当你在以对应的最低部署目标（minimum deployment target）进行构建时，工具就会自动在你的二进制文件中生成相对方法列表。

如果你仍然需要支持旧版操作系统，也不必担心。Xcode 同样会生成旧式的方法列表格式，这种格式依然被完全支持。你仍然可以从操作系统本身是用新的相对方法列表构建的这一事实中获益，而且，系统完全有能力在同一时间、同一个 App 里同时使用两种格式而不出问题。

但如果你的 App 能以此年的操作系统版本作为部署目标，你就能得到更小的二进制文件和更低的内存占用。

这一条建议在整个 Objective-C 或 Swift 开发中普遍适用。

最低部署目标的意义并不仅仅是哪些 SDK API 对你可用。当 Xcode 知道自己不需要支持旧版操作系统时，它通常就能生成优化得更好的代码或数据。

我们理解你们当中许多人需要支持旧版操作系统，但这也就是为什么，只要条件允许就去提高你的部署目标，是个好主意。

现在，有一点需要留意：那就是用比你的实际目标平台更新的部署目标进行构建。Xcode 通常会阻止这种情况，但它偶尔还是会漏过去，特别是当你在其他地方构建你自己的库或框架，然后再把它们引入的时候。

当在旧版操作系统上运行时，那个老版本的运行时会看到这些相对方法，但它对它们一无所知，所以它会尝试像解读旧式的基于指针的方法那样去解读它们。

这意味着它会尝试把一对 32 位字段读作一个 64 位指针。

结果就是，两个整数被粘合在一起当作一个指针，这是个毫无意义的野值，一旦被实际使用，必定导致崩溃。

当你在运行时读取方法信息的地方遇到崩溃，并且那个出错的指针看起来就像是这样两个 32 位值挤在一起（如本例所示），你就能识别出这种情形。

而如果你运行了那种会从这些结构里直接挖出值来的代码，那么这段代码就会遭遇和这些旧版运行时一样的问题，导致在用户升级设备后 App 崩溃。

所以再次强调，不要这么做。用 API。那些 API 无论底层如何变化都会继续工作。例如，有一些函数，只要给它一个方法指针，就能准确返回它的各个字段的值。

让我们再来探索今年即将到来的另一项变化。那就是 arm64 平台上标记指针格式的变化。

首先，我们需要知道什么是标记指针。我们将要深入到非常底层的细节，但别担心。就像我们聊过的其他所有事情一样，你不需要知道这些。这纯粹是因为它很有趣，并且或许能帮你稍稍更好地理解你的内存使用情况。

让我们先来看一下普通对象指针的结构。通常，当我们看到它们时，它们会被打印成那些大大的十六进制数字。我们前面已经见过一些了。

让我们把它分解成二进制表示。

我们有 64 个位，然而，实际上我们并不会用到所有这些位。

在一个真正的对象指针里，只有中间这里的这些位才会被真正用上。

低位永远是零，因为存在对齐要求——对象必须总是放在一个其地址是指针尺寸的整数倍的位置上。

高位也永远是零，因为地址空间是有限的——我们实际上并不会真的用到一直到 2 的 64 次方那么高的地址。

这些高位和低位永远都是零。

所以，让我们从这些永远是零的位里挑一个，把它翻成 1。

这就可以立刻告诉我们：这不是一个真的对象指针。然后我们就可以给所有其他位赋予某些别的含义了。我们管这个叫标记指针。

例如，我们可以把某个数值塞进其他的位里。只要我们教会 `NSNumber` 如何读取这些位，并教会运行时恰当地处理这些标记指针，系统的其余部分就可以把这些东西当作对象指针来对待，完全察觉不到任何区别。

这省去了为诸如此类的每一种情形都去分配一个小小的数字对象所带来的开销，这能带来显著的收益。

顺便提一个小点，这些值其实是通过与一个在进程启动时初始化的随机值进行组合来混淆的。

这是一项安全措施，让伪造一个标记指针变得非常困难。

我们在接下来的讨论中会忽略这一层，因为它只是加在最外层的额外保护。你只需要知道，如果你真的试图在内存中查看这些值，它们会是乱作一团的。那么，这就是 Intel 平台上标记指针的完整格式。最低位被置为 1，以表明这是一个标记指针。如我们此前讨论过的，对于一个真正的指针，这一位必须永远为零，因此这让我们能够将它们区分开。

接下来的三位是标记编号（tag number）。它指示了这个标记指针的类型。例如，3 表示它是一个 `NSNumber`，6 表示它是一个 `NSDate`。

因为我们有 3 个标记位，所以一共有 8 种可能的标记类型。

其余的位就是有效载荷（payload）。这是特定类型可以随心所欲去使用的数据。

对于一个打了标记的 `NSNumber` 来说，这里面就是实际的数字。

现在，标记 7 是一个特例。它表示这是一个扩展标记（extended tag）。扩展标记会使用接下来的 8 个位来编码类型，从而以缩小有效载荷为代价，额外多出 256 种标记类型。

这让我们可以对更多类型使用标记指针，只要它们能把数据塞进这小小的空间里就行。

这会被用于诸如标记的 `UIColor` 或者 `NSIndexSet` 之类的东西。

那么，如果这让你觉得非常趁手，当你听到“只有运行时维护者，也就是 Apple，才能添加标记指针类型”时，你可能会有点失望。但如果你是一名 Swift 程序员，你应该会很高兴知道：你可以创建你自己形态的“标记指针”。如果你曾经用过那种关联值是一个类型的枚举，那就很像标记指针了。Swift 运行时会把这个枚举的判别符（discriminator）存储在那个关联值有效载荷的多余位数里。

更重要的是，Swift 对值类型的使用，实际上让标记指针变得不那么重要了，因为值已经不再需要恰好是指针尺寸的大小。

例如，一个 Swift 的 `UUID` 类型可以是两个字长，直接内联存放，而不必因为它塞不进一个指针内就去分配一个单独的对象。以上就是 Intel 平台上标记指针的情况。让我们再看看 ARM 平台。

在 arm64 上，我们把情况翻转了过来。不再用最低位，而是将最高位置为 1 来表示一个标记指针。

然后标记编号就紧跟在接下来的三位中，再之后是有效载荷使用剩余的位。为什么在 ARM 上我们用最高位来表示标记指针，而不是像 Intel 那样用最低位呢？这个嘛，其实这是针对 `objc_msgSend` 的一个微小优化。

我们希望 `msgSend` 中最常见的路径尽可能快，而最常见的路径就是处理普通指针。我们还有另外两种不那么常见的情况：标记指针和 `nil`。

事实证明，当我们使用最高位时，我们可以单凭一次比较就同时检出标记指针和 `nil` 这两种情况；与分别检查 `nil` 和标记指针相比，这为 `msgSend` 中的常见情况节省了一条条件分支。

和 Intel 上一样，对于标记 7，我们有一个特例，其中接下来的 8 位用作扩展标记，再剩下的位用作有效载荷。

或者我应该说，那其实是 iOS 13 里所用的旧格式了。在今年的发布里，我们对布局做了些许调整。标记位依然保留在最高位，因为那个 `msgSend` 的优化仍然非常有用。

标记编号现在移到了最低的三位。而扩展标记，如果你启用了它，会占据标记位之后的高 8 位。

我们为什么要这么做？这个嘛，让我们回过头再考虑一下普通的指针。

我们现有的工具，比如动态链接器，由于 ARM 上一个名为 Top Byte Ignore（TBI，最高字节忽略）的特性，会忽略指针的高八位；我们就把扩展标记放到这些会被最高字节忽略特性忽略掉的位里。

对于一个对齐了的指针，最低三位始终为零，但我们可以稍稍拨弄一下，只要给指针加上一个小小的数字就行。我们会给它加上 7，来把低位置为 1。别忘了，7 就表示这是一个扩展标记。

而这就意味着，我们实际上可以把上面说的这种普通指针塞进一个扩展标记指针的有效载荷里。

最终得到的，就是一个有效载荷里装着普通指针的标记指针。这为什么很有用？这开启了一种可能，让标记指针能够引用你二进制文件里的常量数据——比如字符串或其他数据结构——而这些数据本来不得不占用脏内存。

现在，可以肯定的是，这些更改意味着那些直接访问这些位的代码，在 iOS 14 于今年晚些时候发布后将不再工作了。

像这样的逐位检查，在过去或许是可行的，但在将来的操作系统上，它会给出错误的结果，而你的 App 就会开始神秘地损坏用户数据。

所以，千万别用依赖于我们刚刚讲到的任何内部细节的代码。相反，你大概能猜到我要说什么了，那就是：用 API。

像 `isKindOfClass` 这类的类型检查，在旧的标记指针格式下工作得好好的，在新的标记指针格式下也将继续工作。所有 `NSString` 或 `NSNumber` 的方法，都只管继续用。所有这些标记指针中的信息，都可以通过标准 API 来获取。

值得留意的是，这一点同样适用于 CF 类型。

我们不想隐藏任何东西，而且我们绝对不想破坏任何人的 App。这些细节之所以没有被暴露出来，仅仅是因为我们需要保有进行如此更改的灵活性，而只要你的 App 不依赖这些内部细节，它们就将继续正常运作。

那么，我们来总结一下。在这场讲座中，我们看到了几项幕后改进，它们缩小了我们运行时的开销，为你和你的用户留下了更多可用的内存。

你无需做任何事就能获得这些改进，除了或许可以考虑一下提高你的部署目标。

为了帮助我们年复一年地做出这些改进，只需遵循一条很简单的规则就好：不要直接读取内部位。用 API。感谢观看，尽情享受你更快的设备吧。
