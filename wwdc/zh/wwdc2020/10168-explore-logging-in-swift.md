修复错误非常重要。用户期望高质量的 App 可靠且错误少。即使微小的错误也可能导致糟糕的用户体验。然而，有些错误比其他错误更难修复。通常，最难以捉摸的是那些在开发过程中难以重现的错误。日志是发现和修复难以重现的错误的宝贵工具。它们提供了一系列线索，即使不重现错误，你也可以通过这些线索来理解它。现在我将演示我开发中的 App 里一个难以重现的错误。稍后我将展示如何添加日志记录来帮助理解和修复这个错误。

我们看到，使用 "log collect" 命令，你可以在你的 App 运行结束后收集日志。在你的 App 运行时，也可以流式传输日志。如果你的设备连接到 Mac，你可以在控制台 App 中实时查看日志消息。如果你的 App 是从 Xcode 启动的，你也会在 Xcode 的控制台中看到它们。这是 "printf" 调试的一个有用的替代方案，因为它提供了结构化的输出，并且易于过滤。

你可能注意到当我在控制台 App 中浏览日志时，「失败」消息被高亮显示了。这是因为我是以 fault 日志级别记录它的。日志记录 API 提供了五个日志级别来指示消息的重要性。

按其重要性递增的顺序，它们是：debug、info、notice（也是默认级别）、error 和 fault。

使用 debug 级别记录仅用于调试时有用的消息。info 级别用于那些有帮助但对于故障排除并非必不可少的消息。Notice 表示该消息对故障排除至关重要。你可以使用 error 级别来记录执行期间发生的错误。fault 级别是最严重的。你应该使用它来记录由于程序中的潜在错误而导致的情况。例如，记录程序期望成立的前提条件在运行时被违反的情况。在控制台 App 中，error 和 fault 级别分别用黄色和红色气泡高亮显示。

Logger 类型为每个日志级别提供了对应的方法。例如，要记录一条 debug 消息，请在 logger 上调用 `debug` 函数。在选择日志级别时，你必须考虑的一个重要因素是持久性（persistence）。即，一条日志消息是否会被归档，并在 App 执行完毕后可以稍后检索。未被持久化的日志只能在 App 运行时进行流式传输。消息是否被持久化取决于日志级别。持久性随方法重要性的增加而增加。

Debug 级别的消息不会被持久化，这意味着它们在 App 执行完毕后无法被检索。Info 级别的消息大部分不会被持久化，除非它们是在执行 log collect 命令之前不久生成的。其他所有级别记录的消息都会被持久化，你可以稍后检索它们。但是，归档的消息数量有存储限制。一旦超出该限制，较旧的消息将被清除并变得不可用。Error 和 fault 级别的消息比 notice 级别的消息持久化时间更长。通常，消息会被持久化几天。但是，这取决于你设备上的存储空间。

日志级别也会影响性能。尽管日志记录的开销总体上较低，但不同日志级别的性能相对而言有所不同。越不重要的级别速度越快。Fault 级别最慢，而 debug 级别性能最佳。

在 debug 级别记录日志之所以如此之快，是因为 debug 消息根本不会被持久化。当日志没有被流式传输时，它们会被丢弃。此外，Swift 编译器使用复杂的优化技术来确保，当 debug 消息被丢弃时，创建消息的代码甚至不会被执行。这意味着你可以在 debug 级别记录冗长的消息，并调用昂贵的函数来构造消息。你的用户不会为此付出代价。

正如我在我的 Fruta App 中演示的那样，在日志消息中包含运行时数据（例如任务标识符）使其对调试更有用。然而，像数字和字符串这样的原始数据可能难以理解和解析。日志记录 API 提供了多种方式来格式化数据以提高可读性，且没有运行时开销。让我们回到 Fruta App，看看日志消息的格式化如何帮助调试。我发现在礼品卡视图中存在一个性能问题。有时加载卡片需要太长时间。App 使用多个服务器来加载礼品卡。我怀疑性能问题与选择哪些服务器有关。为了调查这一点，我添加了一些日志记录来收集与服务器通信相关的一些统计数据。

回顾一下，你可以使用可选的 "format" 和 "align" 参数来格式化数据。由于使用日志记录 API 格式化数据不会增加日志调用的成本，你可以尽情使用格式化功能，让你的数据看起来美观且易于理解。日志记录 API 提供了许多格式化选项，我刚刚只向你展示了其中一部分。

正如我们之前看到的，你可以使用隐私选项来控制数据在日志中的可见性。认真对待所记录数据的隐私问题确实非常重要。这是因为日志记录一直在进行，即使你的 App 已发布并在用户手中。任何拥有设备物理访问权限以及其密码的人都可以收集日志。因此，日志消息不应将任何个人信息标记为公开，这一点很重要，否则这些信息可能会暴露在日志中。

通过使用保留相等性的哈希（equality-preserving hash），你可以在不实际将其设为公开的情况下获得许多相同的好处。这不会揭示数据的内容，但仍然可以让你知道记录的值何时相同，这有助于过滤日志。

例如，这里我向 `.private` 隐私选项传递了一个 `mask` 参数，以便使用哈希记录客户的银行账号。这让我能够找出两条日志消息何时引用同一个账户，而不会泄露账号。

我描述的 Logger API 可在 iOS 14 中使用。如果你的 App 面向更早的版本，你可以使用接受 printf 风格格式字符串的 `os_log` 函数。从这一版本开始，字符串插值也可以传递给 `os_log` 函数，就像使用 Logger 一样。

总结一下，你可以利用新的 Swift 日志记录 API 来调试那些原本几乎不可能理解和修复的问题。这是可行的，因为你可以从你的开发设备中检索日志，并深入分析，甚至不需要重现该错误。日志记录 API 既为你提供了高性能，同时提供了丰富的格式化功能。因此，你可以记录信息丰富的消息，并确信你不会因此而使你的 App 对最终用户变慢。感谢观看。
