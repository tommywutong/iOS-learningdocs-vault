你好，欢迎来到 WWDC。

大家好，我叫 Andy。我要跟大家讲讲如何"在 Swift 中安全地管理指针"。这个 session 是直接建立在同样来自 WWDC 20 的"Unsafe Swift"这个 session 之上的。在那个 session 里，我们把不安全操作定义为：对某些输入会有未定义行为的操作。

在这次演讲中，我会更深入地讲一些在通常安全区域之外编写 Swift 代码的细节。

这些并不是应用程序开发者通常需要操心的那种细节。安全地管理指针，意味着要了解指针可能不安全的所有各种方式。

我大部分时间会讲类型安全。这是 C 语言中一种未定义行为的来源，人们往往对它理解得不够透彻。

我会解释一下那些赋予 Swift 同样底层能力的 API，并说明如何使用它们来避免那种未定义行为。指针安全性可以看作是一系列层级。

每往下一层，你就要为代码的正确性承担更多责任。

所以建议你尽量在最高的安全层级上编写代码。

第一层是安全代码。

Swift 的一个主要目标，就是提供一些新的写代码方式，让你不需要用到任何不安全的构造。Swift 有一套健壮的类型系统，提供了很大的灵活性和性能。

Swift 的集合 API、切片和迭代器提供了你可能想从指针那里得到的大部分功能。而完全不使用指针，是保证代码安全的一个很好的策略。

但 Swift 的另一个重要目标，是与不安全的语言实现高性能的互操作。

要做到这一点，Swift 需要以不安全 API 的形式提供底层的表达能力。

这些 API 在类型名或函数名里都带有"Unsafe"前缀。Swift 的 UnsafePointer 让你可以在不用担心类型安全的情况下，为使用指针的一些危险之处承担责任。如果你需要把原始内存当作字节序列来处理，Swift 提供了 UnsafeRawPointer。

从原始内存加载和存储值，需要你自己负责了解类型的内存布局。

在最深的那一层，Swift 提供了几个用于把内存绑定到类型的 API。只有当你使用这些最底层的 API 之一时，你才算把管理指针类型安全性的全部责任从 Swift 那里接过来。

我来解释一下我说的"安全层级"是什么意思。

安全代码不一定是正确的代码，但它的行为是可预测的。在大多数情况下，如果一个编程错误可能导致不可预测的行为，编译器就会捕获它。

对于那些无法在编译期捕获的错误，运行时检查能保证程序会立刻崩溃并给出诊断信息。

它不会带着一个错误的假设继续往下执行。

所以安全代码其实说的是错误的强制检查。

如果你不使用任何被标记为 unsafe 的 Swift 类型或 API，并且注意管理好线程安全，那么你就可以确信，可预测的行为得到了完全的强制保证。

在不安全的 Swift 代码里，可预测的行为并没有得到完全的强制保证，所以你要承担额外的责任。

测试仍然能提供有用的诊断信息。

但诊断信息的层级取决于你选择的安全层级。不安全的标准库 API 在 debug 构建里带有断言，可以捕获某些类型的无效输入。

添加你自己的前置条件来验证不安全的假设，也是个好习惯。

你可以通过启用 sanitizer（比如 address sanitizer）来用更多运行时检查进行测试。

Sanitizer 的诊断信息通过精确定位 bug，能帮你节省大量时间，但它们并不能捕获所有的未定义行为。

当错误在测试中没有被发现时，它们就可能导致意料之外的运行时行为。那可能是一个很难调试的崩溃，发生的位置离问题的源头很远。而比崩溃更糟的是，你的程序可能会做出错误的行为，甚至损坏用户数据。崩溃是一种糟糕的体验，但损坏或丢失数据更糟。你在不安全的领域里探得越深，找到这些错误就越难，症状也可能越让人困惑。症状甚至可能要到 bug 被引入很久之后才会显现出来。

我们来看看指针，了解一下代码可能不安全的一些方式。Swift 的设计目标是可以不使用指针来编程，看看指针为什么不安全，会让我们更清楚为什么避免使用指针是个好策略。

但如果你确实需要用底层 API 直接访问内存，了解如何自己管理安全性的各个方面也很有用。你可能需要指向一个变量的存储、一个数组的元素，或者你直接分配的内存。

在你能指向那个对象之前，它需要有一个稳定的内存位置。你所指向的那块稳定存储有一个有限的生命周期，要么是因为它离开了作用域，要么是因为你直接释放了那块内存。

不过，你的指针值有它自己的生命周期。当指针的生命周期超过了存储的生命周期时，任何访问它的尝试都是未定义的。这是指针不安全的主要原因，但不是唯一的原因。

对象可以由一系列元素组成。指针可以通过在指针上加上偏移量，移动到不同的内存地址。这是寻址不同元素的一种高效方式。但加上或减去过大的偏移量，就会指向不属于同一个对象的内存。访问一个已经超出其对象边界的指针是未定义的。在这次演讲中，我们会聚焦在另一个容易被忽视的安全方面。

指针有它们自己的类型，这与内存中值的类型是不同的。

我们怎么确保这些类型是一致的？如果它们不一致，会发生什么？当我们请求一个指向 Int16 类型存储的指针时，我们得到的是一个指向 Int16 的指针。目前为止都还好。

我们接下来会看到，在 Swift 中要得到一个指向错误类型的指针其实相当困难。现在假设我们设法用另一种类型（现在是 Int32）覆写了同一块内存。

到那时，我们就会有一个指向正确 Int32 类型的指针，但我们的 Int16 指针可能仍然还留在那里。

访问那个旧的 Int16 类型指针是未定义行为，因为指针类型和内存中的实际类型现在不一致了。你可能会想："未定义行为怎么可能比程序崩溃还糟糕，而且指针类型怎么会导致这种情况？"要理解这一点，我们来看一些非常不安全的代码。

我不指望有人会写出这样的代码，但当 Swift 代码是从 C 移植过来、并且仍然调用旧 C 代码的部分内容时，你可能会惊讶于它看起来是什么样子。做可怕事情的代码理应看起来很吓人，但我们其实还不需要理解所有这些底层类型，就能看出问题所在。

设想我们有一个 collage 结构体，它持有一个指向内存中某些图像数据的独立指针，还有另一个用来表示图像数量的属性。

也许这个类型是从 C 导入的。

我们还有一个函数 addImages，它会把图像数据写入内存，并增加图像数量。

当我们调用 addImages 时，我们希望它能更新我们 collage 结构体里的图像数量，但我们结构体的 imageCount 类型 Int，和函数参数的 UInt32 指针之间存在类型不匹配。

安全的做法应该是创建一个正确类型的新 count 变量，并使用 Swift 的整数转换。

但这行复杂的代码却直接在我们的结构体里创建了一个指针。

之后，代码需要再次读取图像数量，把它传给 saveImages。

问题在于，在运行时，这个 count 可能是零，也就是说程序悄无声息地把所有图像都丢失了。

因为我们给 count 属性设了 Int 类型，给指针设了 UInt32 类型，我们其实是在向编译器发出信号，说这些值位于不同的内存对象中。编译器看不到对某个 Int 对象的任何更新，所以它完全可以直接复用零这个初始化值。实际情况中，编译器还是比较宽容的，所以这么小的一个例子多半不会出问题。

但我们没法预测会发生什么。

对编译器来说，类型信息是一个假设所依据的事实。一旦编译器做出了一个错误的假设，这个假设就可能渗透到编译器流水线的各个环节，并以意想不到的方式显现出来。

所以，同一编译器的两个不同版本可能会导致程序出现不同的行为。

指针类型的 bug 会导致你的程序出现比崩溃更糟糕的异常行为。但更阴险的是，这类 bug 很少会被观察到。所以，一个程序可能表现得完全正常，而一个 bug 却在代码里潜伏了好几年都没人注意到。之后可能有人对源代码做了一个安全的、看似无关紧要的改动，结果就暴露了这个问题。或者它可能在一次常规的编译器更新之后才显现出来，于是你的程序在没人改动代码的情况下,就开始表现出不同的行为。

指针类型安全这个难题的历史比 Swift 还要久远。

要知道如何在 C 里正确使用指针类型，需要对这门语言的规范有很深的了解。

你可以在"strict aliasing"（严格别名）和"type punning"（类型双关）这两个术语下找到相关的讨论。幸运的是，你并不需要理解这些规则,就能安全地使用 Swift 指针。

不过，把指针从 Swift 传到 C 里是很常见的做法，所以 Swift 的指针至少需要和 C 一样严格，才能安全地互操作。

Swift 的 UnsafePointer 给了你 C 指针的大部分底层能力。作为交换，你需要自己管理对象的生命周期和对象边界。"Unsafe Swift"那次演讲解释了该怎么做。

但你不需要为类型安全承担责任。

UnsafePointer 的泛型类型参数是在编译期强制检查的，这让它成为一个类型安全的 API。

我们来看看 Swift 关于指针类型安全的规则，了解一下为什么这样能行得通。

UnsafePointer 的类型参数表示预期存储在内存中的值的类型。我们把这称为一个类型化指针（typed pointer）。在 Swift 中，关于类型化指针的规则是严格而简单的。从概念上说，内存状态包括了一块内存位置所绑定的类型。那块内存位置只能持有该类型的值。作为一个类型安全的 API，UnsafePointer 只从内存中读取该类型的值，而 UnsafeMutablePointer 也只读取或写入该类型的值。

你可能很自然地会觉得，只要字节在内存中的布局是正确的，指针类型就无关紧要。而在 C 里，把指针转换成不同的类型、同时两个指针继续指向同一块内存，也不是什么罕见的做法。

至于这在 C 里到底是不是合法的，取决于各种各样的特殊情况。

在 Swift 中，访问一个类型参数与其内存位置所绑定类型不一致的指针，永远是未定义行为。

为了防止这种情况，Swift 不允许用那种我们熟悉的 C 风格来转换指针类型。这样一来，指针类型就由 Swift 的类型系统在编译期强制保证了。不需要在内存里存储额外的运行时信息、额外的类型信息，也不需要执行额外的运行时检查。我们来看看内存是如何绑定到某个类型的，以及类型化指针是从哪里来的。如果你声明一个 Int 类型的变量，并请求一个指向该变量存储的指针，你会得到一个与该变量声明一致的指向 Int 的指针。数组存储绑定到数组的元素类型。当然，请求一个指向数组存储的指针，得到的就是一个指向数组元素类型的指针。

你也可以通过在 UnsafeMutablePointer 上调用静态的 allocate 方法来直接分配内存。

分配操作会把内存绑定到它的类型参数，并返回一个指向这块新内存的类型化指针。

这和指向变量与数组的指针不同，因为，正如状态图所示，即便内存还没有持有任何已初始化的值，它也已经被绑定到了某个类型。你可以使用分配操作给你的那个类型化指针，只把内存初始化为正确的类型。在已初始化状态下，内存是可以被重新赋值的。

赋值操作会隐式地把之前的内存中的值反初始化，并把内存重新初始化为同一类型的新值。

你可以用同一个类型化指针来反初始化内存。

到那时，内存仍然绑定着同一个类型，但现在可以安全地释放它了。

对于变量和数组存储来说，这些步骤都是由 Swift 自动处理的。而对于直接分配的内存，你要负责管理内存的初始化状态，但 Swift 仍然会确保类型安全。因为类型化指针遵循的是简单、严格的规则，一般来说，你不会同时有两个指向同一内存位置、却在类型上不一致的活跃指针。

但我们来看看复合类型会发生什么。

在这个例子里，我们有一块包含 MyStruct 类型值的内存。

我们既可以得到一个指向外层结构体的指针，也可以得到一个指向它的某个属性的指针，而且这两个指针可以同时有效。我们可以访问其中任何一个，而不改变内存所绑定的类型。这仍然遵守着指针安全的同一条基本规则，因为当内存绑定到一个复合类型时，它实际上也就绑定到了这个类型的各个成员，因为它们就是这样在内存中排布的。

Swift 的类型化指针让你可以直接访问内存，但只能在类型安全的范围之内。你不能有两个指向同一块内存、类型却不一致的类型化指针。所以，如果你的目标是把内存中的字节重新解释成不同的类型，那你就需要使用一个更底层的 API。

UnsafeRawPointer 让你可以引用一段字节序列，而不需要指定它们可能代表的值的类型。

你自己掌控内存布局。

有了原始指针，你会在从内存中加载字节时，把它们解释为类型化的值。

设想有一块用类型化指针初始化为 Int64 的内存。

从类型化指针总是可以向下转换为原始指针。

对那个原始指针执行的操作，看到的只是内存中的字节序列。内存所绑定的类型是无关紧要的。你可以要求那个原始指针加载任意类型。它的做法是读取所需数量的字节，并把它们组装成请求的类型。举例来说，当我们调用 load as UInt32 时，会从当前地址加载四个字节，生成一个 UInt32 值。

甚至加载一个更小的类型也是可以的，只要你考虑到目标平台的字节序（endianness）。你也可以用一个原始指针把某个值的字节写入内存。存储字节和加载字节是不对称的，因为它会修改内存中的值。和用类型化指针赋值不同，存储原始字节并不会反初始化内存中之前的值。所以现在你要负责确保内存里不包含任何对象引用。在这个例子里，在一个原始指针上调用 storeBytes，会从一个 UInt32 值中提取出四个字节，把它们写入到内存中一个 Int64 值的高四个字节里。

当这些字节被写入内存时，它们会被重新解释为内存所绑定的那个类型。所以那个已经指向这块内存中的值的类型化指针，仍然可以用来访问它。

我们不能把一个原始指针转换回类型化指针，因为那样做会和内存所绑定的类型发生冲突。在这个例子里，我们最终会同时得到一个指向 Int64 和一个指向 UInt32 的指针，指向重叠的内存。

从类型化指针转换过来，并不是获得原始指针的唯一方式。withUnsafeBytes API 会在其闭包执行期间，把一个变量的存储暴露为一个原始缓冲区。

UnsafeRawBufferPointer 是一个字节的集合，就像 UnsafeBufferPointer 是一个类型化值的集合一样。这里，缓冲区的数量就是这个变量类型的字节大小。集合的索引是一个字节偏移量，读取带索引的元素，会得到该字节对应的 UInt8 值。

你也可以修改一个变量的原始存储。

withUnsafeMutableBytes 给你一个可变字节的集合，这样你就可以在特定的字节偏移量处存储 UInt8 值。

而且，就像数组有一个 withUnsafeBufferPointer 方法一样，它也有一个 withUnsafeBytes 方法，可以暴露数组元素的原始存储。缓冲区的大小会是数组的元素个数乘以元素的步长（stride）。其中一些字节可能是为了元素对齐而填充的。

Foundation 的 data 类型经常被用来传递一组字节。Data 也有一个 withUnsafeBytes 方法，会在闭包执行期间暴露底层的原始指针。这里，我们用它在选定的字节偏移量处读取一个特定的元素类型 UInt32。

你可以通过在 UnsafeMutableRawPointer 上调用静态的 allocate 方法来直接分配原始内存。

在这里，你要负责以字节为单位计算内存大小和对齐方式。

进行原始分配之后，这块内存的状态既没有初始化，也没有绑定到某个类型。

要用原始指针初始化内存，你需要指定这块内存将要持有的值的类型。初始化操作会把内存绑定到该类型，并返回一个类型化指针。

向已初始化内存的转变只能朝一个方向进行。要反初始化内存，你需要知道内存中值的类型。所以没有办法用原始指针来反初始化。你可以使用初始化操作返回的那个类型化指针来反初始化。我们已经看过类型化指针的内存状态图了。只要内存处于未初始化状态，你就可以用原始指针来释放这块内存。释放操作并不关心内存是否绑定到了某个类型。用类型化指针来分配内存更安全、也更方便，所以应该优先选择这种方式。

不过，这里有个例子，说明了为什么你可能想改为分配原始存储。假设我们想在同一块长度可变的连续内存里，存储一些互不相关的类型。在计算出总的字节大小和对齐方式之后，我们调用 allocate 的原始版本。

这会给我们一个指向一块连续字节的原始指针。现在我们可以把这块内存的一部分初始化为 header，得到一个指向 header 类型的指针。

在加上 header 的字节偏移量之后，我们可以把剩下的字节初始化为整数。这会给我们一个单独的、只指向那块只持有整数的内存区域的类型化指针。

这种存储分配技巧非常适合用来实现像 Set 和 Dictionary 这样的标准库类型，但通常不是你会想去用的东西。总的来说，原始指针是一种强力工具，很适合用来实现高性能的数据结构，但我们不希望把它们暴露得太多。

摆弄字节偏移量和数据对齐是件非常棘手的事。

你更有可能想用原始指针的场景，是当你有一段外部生成的字节缓冲区，并且想把这些字节解码成 Swift 类型的时候。使用 UnsafeRawBufferPointer 的 load API，我们先读取一个描述符，来确定后续数据的大小和类型。接下来，我们在不断增加的字节偏移量处，继续调用 load API，每次都指定我们想从这段流中解码出的类型。

原始指针保留了重要的一层类型安全性。你要在使用它们的那个点上，负责内存布局，但它们并不会影响类型化指针何时可以合法使用，所以使用原始指针并不会让"对同一块内存同时使用原始指针和类型化指针"变得更危险。在最深的那一层，Swift 提供了一些能暴露内存所绑定类型的 API。当你使用这些 API 时，你就要为指针类型安全承担全部责任。在用到它们之前，先看看能不能改用某个更高层级的 API。

你会知道自己什么时候在绕开指针类型的强制检查，因为那时你需要显式调用一个引用内存所绑定类型的 API。

绕开类型安全的危险之处在于，你很容易在代码中使用类型化指针的其他地方，无意中引入未定义行为。

这里仍然只有一条规则需要遵守：对一个类型化指针的访问，需要和内存所绑定的类型保持一致。

这条规则很简单，但并不容易遵守，因为代码的不同部分都需要在内存类型上达成一致，而编译器又没法指导你。我们来看看你可能会用到这种危险 API 的一些原因，并留意一下每一种用法为什么是安全的。

在少数情况下，代码可能没有保留一个类型化指针。

如果我们手头只有原始指针，但我们确切地知道这块内存绑定的是什么类型呢？我们应该能够告诉 Swift："我知道自己在做什么"，然后拿回我们的类型化指针。

在这个例子里，我们有一个持有原始内存的容器，但我们还有一个变量 pointsToInt，告诉我们这块内存是否只能持有整数值。在我们的原始指针上调用 assumingMemoryBound-to，并把 Int 类型作为参数传给它，就会给我们一个指向整数的类型化指针。

我们知道这是安全的，因为在我们分配这块内存的时候，它就已经被绑定为 Int 类型了。

只有当你能保证内存已经绑定到你想要的那个类型时，才调用 assumingMemoryBound-to。它在运行时不会被检查。这只是一种要求编译器做出某个假设的方式，所以这个假设是否正确，责任就在你身上。

这里还有一个我们需要用到 assumingMemoryBound-to 的例子。这次我们是在调用 C 的 API pthread_create。首先，我们用自定义的 ThreadContext 类型初始化一个 context 指针。当我们调用 pthread_create 时，我们把这个 context 指针传给它。但当 pthread_create 在一个新线程里回调我们的 start 例程时，它只会给我们一个原始指针。

这个 C 函数把回调的参数声明为 void 星号（void*），它会被导入为 UnsafeMutableRawPointer。这种情况在 C 里时有发生，而且没有办法让它整体上做到类型安全。在这个例子里，我们确实知道，通过调用 assumingMemoryBound-to 来恢复一个类型化的 context 指针是安全的，因为那正是我们在上面几行分配这块内存时，刚刚绑定给它的类型。在前面几个例子里，原来的指针类型都被擦除了。

有时候，我们手头有一个类型化指针，但它在一个复合类型的层级结构里位置不对。

这里我们有一个接受整数指针的函数。如果我们有一个 Int 元组，我们应该能把一个指向该元组元素的指针传给这个函数。要得到一个指向元组存储的指针，我们需要调用 withUnsafePointer。但那会给我们一个指向元组类型本身的指针，这和我们函数的参数类型不兼容。内存在任一时刻只能绑定到一个类型，但因为元组类型是一个复合类型，把内存绑定到元组类型，也就同时把它绑定到了元素类型。所以，我们知道对元组的存储使用一个指向整数的指针是类型安全的，但我们需要用一个类型不安全的 API 来得到那个指针类型。首先，我们构造一个原始指针，刻意擦除掉我们元组指针的类型。

然后，就像之前那样，我们可以使用 assumingMemoryBound-to，来创建一个指向整数的指针。

像这样把一个指针下降到某个成员类型，需要知道这个复合类型的内存布局。Swift 的实现确实保证了：元素类型全部相同的元组，会按照标准的模式排布，也就是根据元素类型的步长，一个值紧接着另一个值排列。我们来看看这一点是如何应用在结构体属性上的。

我们又一次有了一个接受整数指针的函数。这次，我们没有用元组，而是有一个带整数属性的结构体。withUnsafePointer 给了我们一个指向外层结构体的类型化指针。使用 MemoryLayout API，我们计算出 value 属性的字节偏移量。把结构体指针向下转换为原始指针，再加上那个字节偏移量，我们就得到了一个指向 value 属性的原始指针。

一个属性的内存总是绑定到该属性所声明的类型，所以调用 assumingMemoryBound-to 来得到一个指向整数的指针是安全的。一般来说，结构体属性的内存布局是没有保证的，所以当你得到一个指向结构体属性的指针时，你只能用它来指向该属性的单个值。指向结构体属性是很常见的情况，所以幸运的是，有一个简单的替代方案可以避免使用不安全的 API。当你把这个属性作为一个 inout 参数传递时，编译器会隐式地把它转换成该函数参数所声明的那个不安全指针类型。assumingMemoryBound-to 是在告诉编译器，对内存所绑定的类型做一个不经检查的假设。而 bindMemory API 实际上可以让你改变内存所绑定的类型。如果这块内存位置之前没有绑定过类型，它就只是第一次为它绑定类型。如果这块内存已经绑定了某个类型，那么它就会重新绑定这个类型，内存中原有的值也会变成这个新类型。

假设我们分配了一块内存，用来持有两个 UInt16 值。然后我们请求一个指向这块内存的原始指针。通过在那个原始指针上调用 bindMemory，我们就地把类型改成了一个单独的 Int32 值。这只是一次按位转换，所以你得不到正常类型转换时会有的那些安全检查。事实上，在运行时根本什么都不需要发生。

bindMemory 实际上就是向编译器声明：这块内存位置上的类型已经变了。

bindMemory 返回一个 Int32 指针，现在应该用它来访问这块内存。访问旧的 UInt16 指针是未定义的。

在程序的任何一个时间点上，一块内存位置只绑定到一个类型。改变内存所绑定的类型并不会在物理上修改内存，但你仍然应该把它看作是在改变内存状态的一个全局属性。

这做法之所以不是类型安全的，有两个原因。首先，它是就地重新解释了原始字节。所以，就像使用原始指针时一样，你把内存中类型布局的责任从 Swift 那里拿了过来。

但重新绑定内存比使用原始指针更危险，因为它还会让已有的类型化指针失效。它们的指针地址仍然有效，但只要内存绑定到了错误的类型，访问它们就是未定义的。当你手头有一个指向具有声明类型的对象（比如变量、数组和其他集合类型）存储的指针时，用那个指针来重新绑定内存，可能会让这个对象本身失效。

bindMemory API 实际上是 Swift 中的一个底层语言原语。

它并不是为常规代码设计的。

不过在现实中，确实存在一些你会想要重新绑定内存类型的情况。

这种情况会发生在：你有多个外部 API，它们对某些数据的类型意见不一致，而你又想避免来回复制这些数据。这在那些没有仔细考虑过指针类型安全的 C API 里比较常见。这里我们有一个接受 UInt8 指针的函数，而我们手头有一个指向 Int8 类型内存的指针。

Swift 会强制检查指针类型，所以它不会允许我们把那个指针传给那个函数。我们可以用正确的类型分配一块新的内存，并复制数据。

这在指针类型方面是安全的，但速度较慢。因为我们只需要在一次调用期间重新解释这块内存，所以我们可以使用 Swift 的 withMemoryRebound to API。

就像 UnsafePointer 一样，withMemoryRebound to 会给你一个指针，它保证在其闭包的作用域内是有效的。我们知道在这个闭包内重新绑定内存是安全的，因为我们的 Int8 指针在闭包内部任何地方都没有被使用。当闭包返回时，withMemoryRebound to 会把内存重新绑定回原来的 Int8 类型。这让它独立于周围代码中对类型化指针的访问。我们只需要推理闭包内部的代码，就能证明这样使用是安全的。withMemoryRebound to API 让绑定内存相对于周围代码而言是安全的，但它也有一些严格的限制。正因为如此，你可能仍然需要直接调用 bindMemory。当你这么做时，用同样的方法来推理安全性。只在一个受控的作用域内使用 bindMemory 来获取指针，在这个作用域里，你知道代码不会用一个旧指针去访问同一块内存。当这个作用域结束时，一定要在其他代码可以用之前获得的指针访问同一块内存之前，把内存重新绑定回原来的类型。我们来回顾一下这几个内存绑定 API。

assumingMemoryBound-to 是从一个原始指针恢复出类型化指针的预期方式。它很危险，因为你需要知道这块内存已经绑定到了那个类型。bindMemory 是一个底层原语，会改变内存所绑定类型的状态。

它尤其危险，因为当代码中其他地方访问类型化指针时，它可能会导致未定义行为。withMemoryRebound to 是一种在必要时临时绑定内存的、安全得多的方式。它对于调用那些在类型上意见不一致的 C API 很有用，而且不需要复制底层内存。

bindMemory API 最常见的误用，就是单纯地想从内存中读取一个不同的类型。这段代码调用 bindMemory 来得到一个它想读取的类型的指针。而那个类型化指针其实只是为了读取一个值。

但在创建那个指针的过程中，我们已经改变了内存状态，并且很可能让其他指针失效了。当你只是想重新解释一个类型时，UnsafeRawPointer 的 load API 是一个能避开指针类型陷阱的解决方案。你只需要为内存布局负责。这个解决方案在你需要的任何地方都能用，所以如果你手头有一个指向内存的类型化指针，你可以把它转换成一个原始指针。如果你有一个变量、一个数组，或者一个 Data 对象，withUnsafeBytes 方法会直接让你访问一个原始缓冲区。假设你想把一块内存区域看作是由某种特定元素类型组成的序列，但底层的存储是以原始指针的形式暴露出来的，并且可能被代码的不同部分看作不同的类型。你可以很容易地围绕那个原始指针创建一个包装器，来保留你的元素类型。我们把它叫做 BufferView。我们会给这个名字加上 Unsafe 前缀，这样我们就不需要自动管理内存，并且我们会把边界检查限制在 debug 构建里。要在一个原始缓冲区上创建一个 BufferView，我们根据元素的步长，计算出这个缓冲区里能容纳多少个元素。

当然，我们还会加上前置条件，来验证这个缓冲区具有正确的字节数和对齐方式。现在，要读取一个带索引的元素，我们只需要计算它的字节偏移量，然后请求这个原始缓冲区加载我们的元素类型。因为从原始内存加载是相对于指针类型而言安全的，我们就不需要担心代码的其他部分是怎么看待同一块内存的了。我们的 BufferView 让我们可以安全地重新解释这段字节序列，同时保留元素类型，所以就不需要用到类型化指针了。最后，我们来回顾一下处理指针类型的这些策略。最好的策略是尽可能避免使用指针。

在极少数你确实需要把同一块内存位置重新解释成不同类型的情况下，你应该仔细选择。

因为类型化指针总是需要和内存所绑定的类型保持一致，所以最好不要用它们来重新解释类型。

不过这一点可能不太容易记住，因为 C 代码经常是通过转换指针类型来处理这种情况的。

Swift 为此提供的，是基于原始指针的 API。

即便在纯 Swift 代码里，这些也是很有用的 API。

举例来说，你可能需要从一个字节流里解码出一些值。
