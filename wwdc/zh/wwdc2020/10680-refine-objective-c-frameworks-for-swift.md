从那些几乎出现在 API 所有地方的隐式展开的可选值开始。它们留下了你框架行为中非常重要的未声明部分。那么，它们从何而来，我们又该如何摆脱它们呢？Objective-C 指针类型，包括 id 类型（id-types）和 block，可以有一个有效值，也可以有一个零值，我们称之为“null”或“nil”。这很像 Swift 的可选类型（optional type），它要么有值，要么是 `nil`，区别在于在 Objective-C 中，每个指针类型实际上都是可选的，而每个非指针类型实际上都是非可选的。但是，当然，很多时候，一个属性或方法实际上并不会处理 `nil` 输入，或者永远不会返回 `nil` 结果。因此，当 Swift 导入一个 Objective-C 指针类型时，默认情况下，它会将其标记为隐式展开的可选值，以告诉你这个值可能为 `nil`，但 Swift 不确定它是否真的会是 `nil`。

幸运的是，Objective-C 提供了两个可空性注解（nullability annotation），`nonnull` 和 `nullable`，让你可以说明 `nil` 对于特定的属性、方法参数或方法结果来说是否是一个合理的值。

Objective-C 不会强制执行这些注解。它们只是记录你的意图。但 Swift 会获取这些信息，并用它来决定是否将类型设为可选类型。

你通过编辑你的 Objective-C 头文件来应用这些注解。

在属性中，注解放在属性特性（attribute）的列表中。

在方法参数或结果类型中，它放在类型名称之前。

所以，假设你从这个 `name` 属性开始。你决定这个类的实例可能并不总是有名字，所以你添加了 `nullable` 注解，然后在生成的接口中，类型变为了可选类型。很好。但随后你点击了“构建”，并开始看到新的警告出现。

不要惊慌。你没有破坏任何东西。发生的情况是，Xcode 注意到你开始在此头文件中使用可空性注解，因此它开始告诉你所有你仍然需要填写这些注解的地方。

这就给你提供了一个很好的工作流。在头文件中的某处添加第一个注解，然后逐个警告地处理，填写 `nullable` 或 `nonnull`，直到所有警告消失。

完成之后，还有一个清理步骤你应该做——在文件顶部添加 `NS_ASSUME_NONNULL_BEGIN` 宏，并在底部添加匹配的 `END` 宏，然后删除它们之间的所有 `nonnull`。这仅仅是为了清理一下文件，这样每当你看到这些关键字之一时，它总是表明你会在 Swift 中得到一个可选类型。当你添加这些内容时，偶尔会遇到这些注解不起作用的情况，比如这个常量。如果你尝试将 `nonnull` 注解放在它前面，你会得到一个编译器错误，并且生成的接口可能根本不会显示。我向你展示的注解适用于方法和属性，但在其他地方，比如常量、全局函数或 block，你将不得不改用这些注解的限定符（qualifier）版本。

这些以带下划线的`_`大写字母开头，它们适用于 Objective-C 中任何地方的任何指针类型。你也会需要它们用于指针到指针（pointer-to-pointer）类型。在这种情况下，你将需要为指针的每一级指定一个关键字，这样你可以说明内部指针可以为 `nil`，但外部指针不能，Swift 会正确地嵌套可选类型和不安全可变指针类型。所以，回到我们的全局变量，我们应用了下划线限定符，它就像我们希望的那样在 Swift 中变成了非可选类型。

当你这样做的时候，你需要小心你的注解是正确的。例如，也许你扫了一眼这个头文件，然后决定，“当然，每个任务都会有一个太空舱。让我们把 `capsule` 属性设为 `nonnull`。”但后来发现有一个任务他们没有发射太空舱，你是通过将 `capsule` 设为 `nil` 来模拟这种情况的。换句话说，`nonnull` 注解是错误的。那么，当 Objective-C 为一个 Swift 认为不能是可选类型的值返回 `nil` 时，会发生什么？嗯，如果在 Objective-C 端它是一个 `NSString` 或 `NSArray`，有一个特殊情况。你会得到一个空的 Swift 字符串或数组。

这里可能是个问题，因为 SpaceKit 期望这个字符串等于它的一个 `SKCapsule` 常量，而这些常量都不等于空字符串，所以你会得到一个你可能无法正确处理的值。

对于其他类型，情况可能会变得奇怪得多。

你最终可能会得到一个无效的对象，这通常只有通过不安全的操作才能得到。

如果它是一个 Objective-C 对象，你甚至可能不会注意到，因为 Objective-C 方法调用会忽略 `nil`。但在某些情况下，你会因为空指针解引用而崩溃，或出现其他意外行为，并且编译器不保证会发生什么，因此切换到发布模式或更改 Xcode 版本可能会改变这种错误的症状。

重要的一点是，当你在头文件中写明某些东西不能为 `nil` 时，Swift 不会强制解包它，所以你不会在它返回 `nil` 的地方看到崩溃。

Swift 不会质疑你的 Objective-C 头文件。它相信头文件告诉它的内容。好消息是 Objective-C 编译器和 Clang 静态分析器也会查看可空性注解，并且可以指出你 Objective-C 代码中的许多违规行为。所以，如果你说某些东西不能为 `nil`，但你有 Objective-C 代码使其变为 `nil`，这些工具可能会告诉你有些不对劲。完成添加可空性注解后，最好在框架的实现文件以及你能访问的任何 Objective-C 客户端中查找新的警告或静态分析结果。这些结果可能表明你注解错误，或者它们可能告诉你一些你从未意识到的微妙错误。但假设你看到了一些警告或分析结果，并且无法确定它们是否真的会发生。或者你有一些非常复杂的旧代码，无法弄清楚是否存在一个边缘情况会导致它返回 `nil`。那你该怎么办？嗯，我之前提到了 `nonnull` 和 `nullable` 注解。实际上还有第三个选项，叫做 `null_unspecified`，它会让 Swift 将该值作为隐式展开的可选值导入。你应该在你会在 Swift 中使用隐式展开的可选值的所有地方使用它，比如在对象的生命周期早期才为 `nil` 的值。但当你认为一个 API 可能不会返回 `nil` 但你不确定时，你也可以使用它，这样 Swift 客户端仍然可以在不解包的情况下使用结果。但如果框架确实返回了 `nil`，你会可靠地在使用点得到一个崩溃，而不是可能在稍后的某个时间点出现一些看似不可能的错误行为。

我们已经检查了我们的项目，并添加了所有的可空性注解。很好。接下来，我们想要处理这个“Any”数组以及其他桥接得不太好的集合。事实证明，Objective-C 支持一种很像 Swift 的泛型语法，所以如果你在 Objective-C 中把它做成一个 `SKAstronauts` 的 `NSArray`，你会在 Swift 中得到一个 `SKAstronauts` 的 Swift 数组。这也适用于 `NSSet` 和 `NSDictionary`，所以它可以真正改善许多 API。接下来，让我们看看项目的一个不同区域。这里我们有一个叫做 `SKRocketStageCount` 的函数，正如你从名字中所期望的那样，它返回一个计数。因为计数不能为负，它把它作为 `NSUInteger` 返回，这意味着在 Swift 中，它返回一个 `UInt`，这意味着这个函数打破了 Swift 的惯例。在 Objective-C 和 Swift 中，通常的做法是，当一个整数表示一个位集合，并且你想对这些位执行位运算，或者进行一些有符号算术可能会妨碍的计算时，使用无符号类型。通常，当你在此级别工作时，你关心的是值的确切位数。`NSUInteger` 的大小因架构而异，所以很少有人以这种方式使用它。相反，人们在 Objective-C 中使用 `NSUInteger` 的主要原因是表明一个数值永远不会为负。Objective-C 通过自动转换和精心设计的溢出行为来支持这种风格，但这些确切的特性可能导致严重的安全错误，因此 Swift 不包含它们。相反，Swift 要求你显式地将无符号类型转换为有符号类型（如果你想要有符号算术的话），并且如果无符号算术会产生负结果，则停止执行。这使得在 Swift 中混合 Int 和 UInt 比在 Objective-C 中混合 NSInteger 和 NSUInteger 更加困难。

因此，传统的 Swift 风格就是不这样做。

相反，地道的 Swift API 使用 `Int`，即使对于永远不会为负的值也是如此。

对于 Apple 的框架，我们应用了一个通用规则，即当 Swift 导入它们时，所有 `NSUInteger` 都变成 `Int`。

对于你的框架，是否更新你的头文件以使用 `NSInteger` 是你的选择，但我们建议你这样做。

这在 Objective-C 中几乎没有区别，但在 Swift 中却有着巨大的影响。

如果我们看看更广泛的上下文，这个函数有一个更大的问题，那就是客户端可以很容易地误用它。`SKRocketStageCount` 函数应该与这些 `SKRocket` 常量一起使用。这就是匹配名称应该指示的内容。但 Swift 不知道这一点，因为 Swift 看到的是这个函数接受一个字符串。这些常量都是字符串，但外面还有更多的字符串。如果你向 `SKRocketStageCount` 传递了其中一个，它很可能不会做什么好事。在一个纯 Swift 框架中，你可以预防这种情况。你只需要把这些常量变成一个 `enum` 或一个带有 `String` 原始值类型的 `struct`，然后改变函数，使其只接受那个类型。你可以通过手动包装这些 API 来对 SpaceKit 做到这一点，但有一个更简单的方法。

首先，你引入一个新的 `typedef` 来将常量分组在一起，并更改所有涉及这些常量的地方来使用它。就其本身而言，这几乎什么都不做。一个 `typedef` 在 Swift 中被导入为一个类型别名（type-alias），在这两种语言中，这只是原始类型的一个精确同义词。但这只是一个准备步骤。

接下来，你在 `typedef` 之后添加 `NS_STRING_ENUM` 宏。这会显著地重塑 Swift 中的 `typedef`。它现在作为一个结构体（struct）导入，里面嵌套了这些常量，使得结果看起来和感觉起来就像一个带有原始字符串值的枚举（enum）。

最重要的是，这意味着 `StageCount` 函数不再接受任意字符串。它只接受 `SKRocket` 的实例。任务完成。

你可以使用这个特性来定义你自己的自定义字符串枚举，但 Apple 的框架也定义了很多这样的枚举。

我在这里列出了 Foundation 中的一些常见例子，但仅在 iOS SDK 中至少有 50 个。最好在你的 API 中查找那些本应是这些枚举之一的 `NSString` 参数或常量，并像这样更新它们。接下来，让我们谈谈当 Swift 以为你遵循了 Objective-C 约定，而你却没有正确遵循时，可能会陷入麻烦的一些方式。

当你查看 `SKAstronaut` 的生成接口时，你会看到一些有趣的东西。这个类有两个初始化方法。两者都传递一个人的名字，但形式略有不同。

一个接受 `PersonNameComponents`，这是一个 Foundation 类型，具有诸如 given name 和 surname 之类的属性。另一个接受一个标记为“name”的字符串。按理说，其中一个初始化方法很可能调用了另一个。然而，如果你子类化 `SKAstronaut`，Swift 会要求你重写这两个方法。这似乎有点不必要。

但实际上这个类的初始化方法还有第二个问题，一个在生成的接口中不可见的问题。

如果你查看 `SKAstronaut` 的代码补全，你会看到第三个没有参数的初始化方法。这个 `init` 不在生成的接口中，也不在原始头文件中。它似乎来自外太空。但实际上它来自这里，来自超类（superclass）。

`SKAstronaut` 从 `NSObject` 继承了它，即使你的客户端可以调用它，它可能实际上并不能正常工作。这两个问题有相同的根本原因。

在 Objective-C 中，有一个初始化方法的约定，它可以确保客户端知道如何编写一个能够始终正确初始化的子类（subclass）。

该约定将初始化方法分为两类——指定（designated）初始化方法和便捷（convenience）初始化方法。

你需要重写所有指定初始化方法，以便安全地继承便捷初始化方法。现在，如果你在想，“天哪，这听起来真的很熟悉……”那是因为确实如此。Swift 类对其初始化方法使用相同的基本模型。在细节上有一些差异。例如，你在一种语言中标记指定初始化方法，而在另一种语言中标记便捷初始化方法。但 Swift 类具有这两类相同的初始化方法，并且它们的工作方式基本相同。

但不幸的是，这里语言之间最大的区别在于，在 Objective-C 中，指定初始化方法不是一个语言规则。它们是一个约定，每个类必须通过标记至少一个初始化方法为指定初始化方法来选择遵循这个约定。许多 Objective-C 类没有选择加入。这意味着客户端不知道如何子类化你的类。

这对任何类来说都不好，但对于框架来说尤其糟糕，因为这样客户端不得不阅读你的源代码或逆向工程你的行为，或者只能猜测，而这些都可能导致有错误的子类。

这已经够糟糕了，但这还意味着，如果你忘记重写你想要重写的东西，你作为框架维护者不会收到警告。

如果客户端使用了一个你忘记重写的初始化方法，这意味着你的类在初始化过程中会被跳过。所以，你原本以为总会引用一个对象的实例变量（ivar）将会是 `nil`。

即使你确实重写了所有你需要重写的东西，错误也非常普遍，以至于客户端无法真正确定这一点。因此，解决这个问题的第一步是在你的头文件中通过标记你的指定初始化方法来选择加入这个约定。

如果你不确定哪些初始化方法应该是指定的，可以看一下实现。通常，指定初始化方法会通过 `[super init…]` 调用一个 `init`，便捷初始化方法会通过 `[self init…]` 调用一个 `init`。因此，通过查看它们的方法体，你可以确定 `initWithNameComponents` 应该是指定的，而 `initWithName` 应该是便捷的。

但是那个 `catch` 子句实际上是什么样子的呢？嗯，我们需要从错误中提取域和代码，所以首先我们必须将其捕获为 `NSError`。

接下来，我们需要确保该错误在 `SKErrorDomain` 中，而不是可能在同一个错误码用于其他东西的其他域中。

然后，我们需要将错误码从一个 `int` 转换为 `SKErrorCode`。最后，我们可以检查它是否是我们想要的那个 case。看看所有这些检查放在一起，这，呃……

不是我想让我的用户编写的东西。

仅仅匹配一个错误不应该需要这么多工作。

如果你用 Swift 编写了 SpaceKit，并且这是一个 Swift 错误枚举，你可以用不到一行代码完成同样的事情。只需命名错误类型和 case，Swift 就会将它们与抛出的错误进行匹配。那样好多了。但是，当然，你没有 Swift 错误枚举。你有一个 Objective-C 枚举和一个错误域常量。

你能把它们变成类似于 Swift 错误枚举的东西吗？你能，而且真的没有比这更容易的了。你需要做的就是用 `NS_ERROR_ENUM` 替换 `NS_ENUM`。

然后用错误域常量替换原始类型。

这对错误码枚举有着巨大的影响。

`SKErrorCode` 被嵌套在一个全新的类型 `SKError` 内部，这是 Swift 凭空创造出来的。

在 Xcode 生成的接口中，你会看到该枚举拥有所有错误码作为其 case，并且它们也作为该结构体（struct）上的静态常量重复出现，并且还有一个用于错误域的静态常量。

但 `SKError` 也遵循了 `Error` 协议，所以你可以像使用原生 Swift 错误一样抛出和捕获它。

它拥有用于错误码和用户信息字典的初始化方法和属性。

并且错误码枚举有一个 `~=` 操作符。

这是 `case` 和 `catch` 子句使用的匹配操作符。在这里，它表示如果你在 `switch` 或 `catch` 一个错误，你可以将其与一个 `SKErrorCode` 进行匹配。只有当错误域和错误码都正确时，匹配才会成功。由于 `SKError` 上有那些静态代码常量，你可以编写 `catch SKError.launchAborted`，Swift 将使用此操作符将错误与该错误码进行匹配。`SKError` 的这些部分在生成的接口中是不可见的，因为 Swift 编译器合成了它们。但它们在那里供你使用，并且它们使 Objective-C 错误码在 Swift 中工作得相当好。而获得所有这些你只需要做的是更改两个标识符。对于一个单行差异来说还不错。

但我想回到我们开始讨论这些错误码的地方，并思考一个更大的教训。

在生成的接口中没有明显的问题迹象。

只有当你看到了 `SKErrorCode` 将如何被使用时，你才意识到有改进的空间。在整个演讲中，我一直向你展示生成的接口，因为它们是了解 Swift 如何导入你的头文件的好方法。但生成的接口只是理解框架内容的工具。真正重要的是你的客户端在尝试使用它时会编写的调用。因此，当你在开发一个框架时，你应该查看生成的接口，但你应该思考使用点。在你的脑海中想象它们。在小白板上草草写下它们。在 playground 中调整它们。在测试中整理它们。你的客户端会基于他们使用你的框架编写的代码来喜爱或厌恶你的框架，而不是基于他们在 Command-点击时看到的接口。

那么，总结一下。

如果你有一个 Objective-C 框架，你可以仅通过头文件注解，有时再辅以少量 Swift 代码，使其对 Swift 客户端工作得非常出色。

当你这样做的时候，寻找机会向 Swift 客户端提供更强大、更具体的类型。

并确保你遵循 Objective-C 约定，以便 Swift 能正确地使用你的框架。

并且，尽管 Xcode 向你显示了生成的接口，但要看透它，并思考你的 API 将如何被使用。这应该是驱动你设计的东西。
