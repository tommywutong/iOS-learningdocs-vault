我们先来看看 Swift 运行时性能方面的一些重大进展。

首先要看的是代码体积。代码体积指的是 App 里代表其逻辑的机器码那部分。这几个版本以来，它一直是我们优化的重点。

为了追踪进展，我们一直在用 iOS 自带的一个 App 的 Swift 重写版本。从 Swift 4 开始，我们就一直在追踪这个 App 的 Swift 版本相对于 Objective-C 版本的代码体积。

一开始，Swift 版本的代码体积大约是 Objective-C 版本的 2.3 倍。

Swift 4.1 靠"为代码体积优化"这个优化设置，砍掉了一大块。

在之后的每个版本里，我们都进一步缩小了这个差距。到 Swift 5.3，我们已经把这个差距降到了 Objective-C 版本代码体积的一倍半以内。请注意，一定程度的差距是不可避免的，因为 Swift 自带的安全特性，在 App 里实现时需要占用一定的代码体积。不过，不同风格的应用会产生不同的二进制体积。这个应用是一个 UIKit App。那 SwiftUI App 呢？在 Swift 5.3 中，SwiftUI App 的代码体积有了显著改进。这是 MovieSwiftUI，一个由 Thomas Ricouard 开发的出色开源 App。我们可以看到，它应用逻辑的代码体积减少了超过 40%。二进制体积对下载时间之类的事情当然很关键，但当 App 运行起来之后，它属于我们所说的"干净内存"（clean memory）——也就是可以被清除的内存，因为需要时它可以被重新加载。所以它的重要性不如"脏内存"（dirty memory），也就是应用在运行时分配和操作的内存。接下来，我们看看脏内存的使用情况有了怎样显著的改善。

Swift 对值类型的运用，相比基于引用类型的语言有一些根本性的优势。为了理解这一点，这里有一个 Objective-C 的例子：一个简单的模型类型，带有一个 UUID、一个字符串和一个数字。我们来看看，当我们把它存进一个数组时，这个模型在内存里是怎么保存的。

在 Objective-C 里，对象变量其实就是指针。所以这个数组保存的是指向这些模型对象的指针。

而这些对象，又保存着指向它们各自属性的指针。你分配的每一个对象，都会带来一定的性能和内存开销。这一点太重要了，以至于 Objective-C 为极短的 ASCII 字符串专门设计了一种小字符串表示方式，让它们能直接存在指针里，从而省下额外分配一个对象的开销。

现在，我们来看看同一个模型在 Swift 里是什么样子。

Swift 对值类型的使用，避免了让许多值都必须通过指针来访问的需要。因此，这些 UUID 可以直接保存在 Mountain 对象里面。

而且 Swift 的小字符串能容纳多得多的字符，最多 15 个代码单元，还包括非 ASCII 字符。

最后，所有的 Mountain 对象都可以直接分配在数组的存储空间里。所以，除了少数几个字符串之外，一切都保存在一整块连续的内存里。像这样使用值类型，Swift 程序能获得显著的内存收益。

所以，如果我们检查一个由 400 个这种模型对象组成的数组所占用的堆内存，我们会看到 Swift 的模型数据更紧凑：大约是 20 KB，而不是 35 KB。请注意，这些数据是在 Swift 5.1 上测得的。

尽管有这样的优势，一些 Swift 程序以前仍然会因为运行时开销而使用更多的堆内存。以前，Swift 会在启动时创建一批缓存和内存。这些缓存存储的是协议一致性之类的东西，以及其他类型信息，还有用来把类型桥接到 Objective-C 的数据。

所有语言的运行时都有一定的开销，但在 Swift 这里，这个开销一直偏大。这一直是我们重点优化的方向。

我很高兴地告诉大家，在 Swift 5.3 中，我们已经大幅削减了这部分开销，以至于这个 App 的 Swift 版本现在使用的堆内存，还不到去年版本的三分之一。要充分获得这些改进的好处，App 的最低部署目标需要设为 iOS 14。不过其中许多改进，也会让那些需要向后部署到更早操作系统版本的 App 受益。

在大多数应用里，这些差异往往不太容易被察觉，但像这样优化 Swift 的内存使用，对于我们把 Swift 进一步推广到 Apple 系统的各个角落——用到守护进程和底层框架里，那些每一字节内存都要精打细算的地方——至关重要。

为此，我们还做了另一项重要的改动：我们把 Swift 标准库挪到了整个技术栈里 Foundation 的下面。这意味着，它现在实际上可以用来实现那些位于 Objective-C 层级之下的框架，而这在以前是必须用 C 来做的。

但现在，它们被整齐地对齐在了一起。这些改进，以及我提到的其他改进，会给你的编辑体验带来明显的影响。接下来，我们聊聊调试 Swift 代码的核心体验有哪些改进。

当调试信息可用时，调试器现在会显示常见 Swift 运行时故障陷阱（trap）的具体原因，而不是只显示一条不透明的"无效指令"崩溃信息。

此外，Swift 的调试支持总体上也变得更加健壮了。要理解为什么，我们来看看 Swift 在编译时和 Objective-C 互操作的一个关键方式。

Swift 是通过 Clang 模块来导入 Objective-C 的 API 的。为了解析关于类型和变量的信息，LLDB 需要导入当前调试上下文里所有可见的 Swift 和 Clang 模块。

虽然这些模块文件包含了大量关于类型的信息，但由于 LLDB 对整个程序及其所有动态库都有一个全局视角，导入 Clang 模块有时会以编译时不会出现的方式失败。一种常见的失败场景，是来自不同动态库的搜索路径发生冲突时。

作为一种后备方案，当这种情况发生时，LLDB 现在也可以从 DWARF 调试信息里为 Swift 调试目的导入 C 和 Objective-C 类型。这大大提升了诸如 Xcode 变量视图和表达式求值器这类功能的可靠性。

Swift 是一门出色的通用编程语言。Swift 非常适合用来构建 Apple 平台上的 App，但它同样也很适合许多其他任务。正因如此，我们认为 Swift 的跨平台支持非常重要。

结果就是，如果我们哪天需要再追加一个闭包参数，我们中很多人就会发现，自己不得不把代码折腾得比看起来该有的程度要多得多。

我们可以做得更好。因为人们可以省略参数标签，所以最好在给方法命名时，就假设标签会被省略。

接下来，我们聊聊把 KeyPath 表达式当函数使用。早在 Swift 4.1 中，我们引入了智能 KeyPath，这是一种表示对属性的未调用引用的类型，可以用来读取和设置底层的值。

在你设计 API 的时候，如果你预期调用处只是一次简单的属性访问，KeyPath 是函数参数一个很有吸引力的替代方案，因为它更简洁、嵌套更少。这个例子，我借用了 Ruby 里的一个算法：chunked。它是集合上的一个适配器，把相邻且 key 相等的元素分到一组。我碰巧手头有一份朋友和家人鞋码的清单。送一双新鞋总是不错的礼物。我可以通过先排序、再按鞋码对我的联系人分组，快速浏览一遍。嗯，如果我哪天要转送一双鞋，看起来我应该找 Charles 试试。当然，偶尔你也会遇到不是简单属性访问的使用场景。比如说，你在挑一双没有半码的凉鞋。

要同时支持这两种调用处的写法，你得重复声明这个方法。Swift 5.2 新增的特性是，你可以把 KeyPath 表达式当作一个函数来用。

这意味着，你可以把一个 KeyPath 参数传给任何签名匹配的函数参数。而且，你之前为了接受 KeyPath 而额外添加的任何重复声明，现在都可以删掉了。

接下来，我要给大家介绍 @main，一个基于类型的程序入口点工具。每个程序总得有个办法开始执行。这里，我用新的 ArgumentParser 包，声明了一个简单的工具，用来把从命令行取到的名字打印出"hello"。

但启动执行所需的样板代码，长度跟程序本身差不多，这严重破坏了那种声明式的感觉。

从 Swift 1.0 开始，你就一直可以在你的 AppDelegate 上使用 UIApplicationMain 属性标注，告诉编译器生成一个隐式的 main.swift 来运行你的 App。在 Swift 5.3 中，我们把这项特性做了推广，让每个人都能用上。

如果你是一个库的作者，只需要在你希望用户的入口点从中派生出来的那个协议或超类上，声明一个 static main 方法。

对 ArgumentParser 来说，那就是 ParsableCommand。

这会让你的用户可以给那个类型标上 @main，编译器就会代他们生成一个隐式的 main.swift。这种标准化的、委托程序入口点的方式，应该能让你更容易地跑起来，不管你是在做一个命令行工具、一个既有的应用、一个全新的应用，还是完全其他的东西。

我们迫不及待想看看大家会怎么用上这些强大的新 API 设计工具。接下来，我想强调一些能消除样板代码、提升表达力的语言增强特性。

我们先从闭包里隐式 self 的可用范围扩大说起。为了提醒大家注意潜在的循环引用，Swift 要求在捕获 self 的逃逸闭包里显式使用 "self"。但当你不得不接连写下一长串 self. 时，就会开始觉得有点多余。

Swift 5.3 新增的特性是：如果你在捕获列表里包含了 "self"，你就可以在闭包体里省略它。

你仍然需要显式表明你要捕获 self 的意图，但现在，这种显式表达的代价只是一次声明而已。

不过，有时候，就连单次使用 self. 也会显得没必要——比如在 SwiftUI 里，self 往往是一个值类型，这就让引用循环变得极不可能发生。好，我很高兴地告诉大家，在 Swift 5.3 中，如果 self 是一个 struct 或 enum，你可以在闭包里完全省略它。

我们认为，这些改进会提升与闭包里隐式使用 self 相关的编译器错误的信噪比，减少大家不假思索就随手加上 self. 的冲动。接下来，我们聊聊多模式 catch 子句。

一直以来，do-catch 语句的表达力都不如 switch 语句，这导致大家不得不在 catch 子句里再嵌套一层 switch。好，在 Swift 5.3 中，我们扩展了 catch 子句的语法，让它拥有了和 switch case 一样完整的能力。

这让你可以把这种多子句的模式匹配，直接压平写进 do-catch 语句里，读起来容易得多。

接下来，我们看看我们对 enum 类型做的几项改进。

从 Swift 4.1 开始，编译器就已经能为各种各样的类型合成 Equatable 和 Hashable 一致性了。

不过，有时候，你会遇到这样的情况：要是有个比较运算符就太方便了。我很高兴地告诉大家，在 Swift 5.3 中，编译器已经学会了为符合条件的 enum 类型合成 Comparable 一致性。接下来，我们聊聊把 enum case 用作协议见证。

来看看这两处调用。

fileCorrupted 是一个 static var，还是一个 enum case？keyNotFound 是一个 static func，还是一个 enum case？static var 和 static func：enum case。这两种声明的调用处写法是一模一样的。

正因如此，在 Swift 5.3 中，我们增强了 enum case，让它们现在可以用来满足 static var 和 static func 这两种协议要求。

去年，Swift 加入了对内嵌 DSL 的支持，为 SwiftUI 的声明式语法提供动力。

这其中就包括用来构建集合视图子项的构建器闭包，以及像 if-else 这样的基本控制流语句。

我很激动地告诉大家，在 Swift 5.3 中，我们扩展了内嵌 DSL，让它支持 if-let 和 switch 这样的模式匹配控制流语句。

这里，我可以用一个 switch 语句，在这个可滚动的垂直叠放里，在不同的图片布局之间切换，从而组合出一个我最喜欢的动物的照片画廊。接下来，我要给大家介绍构建器推断。这里，我写了一个 App，用来追踪我读书会里正在读的书。

SwiftUI 今年新增了大量令人兴奋的特性。如果你想了解更多，我建议你看看《SwiftUI 的新特性》这场演讲。

现在我想换个话题，聊聊一些提供给你的强大新 Swift API，先从 SDK 里的这些开始。我们从 Float16 说起。

Float16 是 IEEE 754 标准里的一种浮点格式，是 Swift 5.3 新增的。

顾名思义，一个 Float16 只占用两字节内存，而单精度浮点数要占用四字节。

因为体积只有一半，你可以在一个 SIMD 寄存器或一页内存里塞下两倍数量的 Float16，在支持的硬件上，这通常能带来一倍的性能提升。

不过要当心。作为一种更小的数据类型，它的精度和范围也更有限，所以在把原本为 double 或 float 实现的代码改用 Float16 时要小心。

想了解更多关于 Float16 的内容，我建议你看看我们准备的《Swift 中的数值计算》这场演讲。接下来，我们聊聊 Apple Archive，一种新的模块化归档格式，基于 Apple 用来分发系统更新的、久经考验的技术。

它针对快速的多线程压缩做了优化，还配备了访达集成、一个命令行工具，以及一大堆其他强大的特性，包括一套符合 Swift 惯用法的 API。用 Apple Archive 高效地压缩并归档一个源目录，就是这么简单。

我想请大家注意一下这个 FileStream 构造方法，它用到了我们今年推出的另一个新库：Swift System。

Swift System 为系统调用，以及像 Apple Archive 这样的底层系统 API 提供的通用类型，提供了现代化、符合惯用法的接口。

通过 Darwin overlay 导入的原始弱类型接口，可能会很难用、容易出错。

Swift System 用一些技巧把这些 API 包装了起来，比如强类型的 RawRepresentable struct、错误处理、带默认值的参数、命名空间，以及函数重载，为 SDK 里一个更符合 Swift 惯用法的系统层打下了基础。

最后，我们来看看我们对 OSLog 做的一些增强。

OSLog 是一个统一的日志 API，经过优化，开销极小，而且经过精心设计，能防止不小心记录下敏感数据。

在 Swift 5.3 中，我们利用了一些精巧的编译器优化，让 OSLog 变得快得多、表达力也强得多，加入了对字符串插值和格式化选项的支持。如果你现在还在用 print 作为你的日志方案，现在正是重新考虑一下的好时机。如果你想更深入了解这些 API，以及如何借助日志追查那些难以复现的 bug，我建议你看看《Swift 中的日志记录》这场演讲。最后，我们把目光转向那些通过 Swift Package Manager、在 SDK 之外提供给你的、数量还在不断增长的 API。我们先从 Swift Numerics 说起，这是一个用于数值计算的新开源包。

Swift Numerics 以一种在泛型上下文中好用得多的方式，定义了所有基础的数学函数，比如正弦和对数，同时也支持复数及其运算。Swift Numerics 的复数在内存布局上和它们对应的 C 类型兼容，但速度更快、精度更高。
