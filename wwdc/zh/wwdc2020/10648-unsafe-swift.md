大家好，欢迎来到 WWDC。

大家好，我叫 Karoy Lorentey，是 Apple Swift 标准库团队的工程师。今天我要讲 Swift 中的不安全 API。

标准库提供了许多不同的构造：类型、协议、函数、属性等等。其中一小部分被明确标记为 "unsafe"。这是什么意思？它们有什么特殊之处？安全与不安全构造之间的区别在它们提供的接口中并不明显。相反，它源于它们的实现如何处理无效输入。标准库中的大多数操作在执行前都会完全验证输入，因此我们可以安全地假设，我们可能犯下的任何严重编码错误都会被可靠地捕获并报告。

这种操作的一个例子是 Swift `Optional` 类型上熟悉的强制解包运算符。它确实要求值不能为 nil，但如果我们弄错了，我们保证会得到一个漂亮、干净的致命运行时错误。这里我们要求 `Optional` 做一件无意义的事，因此停止执行是它唯一负责任的做法。当然，尝试强制解包 nil 值仍然是一个严重的编程错误，但其后果是明确定义的。

我们说强制解包运算符是"安全的"，因为我们能完全描述它对所有可能输入的行为，包括不满足其要求的输入。

因此，反过来说，不安全操作在至少某些违反其文档化预期的输入上必然表现出未定义行为。

例如，`Optional` 也通过其 "unsafelyUnwrapped" 属性提供一种"不安全的"强制解包操作。就像常规的强制解包运算符一样，它也要求底层值非 nil。然而，当启用优化编译时，该属性不会验证这一要求；它信任你只在非 nil 值上调用它，并直接读取它。

那么，如果你不小心在 nil 上调用它会发生什么？它会读取一个不存在的值，而很难说这究竟意味着什么。根据任意环境，它可能触发立即崩溃，也可能返回某个垃圾值；或许还会做别的事。它可能每次做同样的事，也可能每次执行结果都不同。

关键是，通过使用这个属性，你承担了完全的责任来满足其要求。如果你不小心违反了它们，效果可能不可预测，调试问题可能异常困难。

这是标准库中所有不安全类型和操作的典型属性：它们都有假设，而这些假设它们无法或不愿完全验证。

"unsafe" 前缀是一种命名约定，有点像危险符号。它警告你以及任何阅读你代码的人，使用它们时固有的危险。标记为 "unsafe" 的接口仍可用来构建可靠工作的代码；事实上，有些任务只能用它们完成。然而，当你取用这些时需要格外小心，必须完全理解它们的使用条件。

作为交换，我们得以实现否则难以或不可能做到的事。不安全 API 的用例通常分为两类：要么它们提供与 C 或 Objective-C 的互操作性，要么它们提供对运行时性能或其他程序执行方面的细粒度控制。

`Optional` 的 `unsafelyUnwrapped` 属性 squarely 属于第二类。它使我们能消除对 nil 值的多余检查。这最好保留给代码库中最关键的部分，性能测量表明即使是可能不必要的检查的微小、微小成本也会产生有害影响。

为了帮助我们捕获潜在错误，这个属性只在优化构建中省略 nil 检查；在未优化的调试构建中，它仍然完全验证输入值。如果你自己实现面向性能的不安全接口，复制这种行为是个好主意，因为它使在开发期间检测问题容易得多。

重要的是要注意，安全 API 的目标不是防止崩溃。事实上，某种程度上是相反的：当它们收到超出其文档化约束的输入时，安全 API 保证通过抛出致命运行时错误来停止执行。

这些情况表明严重的编程错误：我们的代码破坏了关键契约，我们需要去修复它。继续执行将是不负责任的。错误生成的崩溃报告让我们知道问题发生的环境，以便我们调试并纠正它。

当我们说 Swift 是一门安全的编程语言时，我们是指默认情况下，它的语言和库级特性会完全验证其输入。任何不这样做或不能这样做的构造都会被明确标记为不安全。

例如，Swift 标准库提供了强大的不安全指针类型，抽象级别大致与 C 编程语言中的指针相同。为了理解指针如何工作，我们需要稍微谈谈内存。

Swift 有一个扁平内存模型：它把内存视为线性地址空间，由可单独寻址的 8 位字节组成。每个字节都有自己的唯一地址，通常打印为十六进制整数值。

在运行时，地址空间被稀疏地填充了反映我们 App 在任何时刻执行状态的数据。它包括：我们 App 的可执行二进制；我们导入的所有库和框架；栈，为局部和临时变量以及一些函数参数提供存储；动态内存区域，包括类实例存储和我们手动分配的内存；某些区域甚至可能映射到只读资源，如图像文件。

每个单独的项都被分配一块连续的内存区域，在同一个共享的线性地址空间中存储某种数据。随着 App 执行，其内存状态持续演进。新对象被分配，栈持续变化，旧项被销毁。幸运的是，Swift 语言和运行时会为我们跟踪东西在哪里。我们通常不需要在 Swift 中手动管理内存。

然而，当我们确实需要这样做时，不安全指针为我们提供了有效管理内存所需的所有底层操作。当然，所有这些控制的另一面是随之而来的责任。这些指针只是表示内存某处位置的地址。它们提供强大的操作，但它们必须信任你会正确使用它们，这使它们从根本上不安全。如果你不小心，你的指针操作可能会在地址空间上胡写，破坏 App 仔细维护的状态。

例如，为一个整数值动态分配存储会为你创建一个存储位置，并给你一个直接指针。指针给你对底层内存的完全控制，但它不会为你管理它。它也无法跟踪该内存位置后来发生了什么。它只是执行你告诉它做的操作。

当底层内存被反初始化并释放时，指针就失效了。然而，无效指针看起来就像常规的有效指针。指针本身不知道它已经失效。任何解引用这种悬空指针的尝试都是严重的编程错误。

如果我们幸运，内存位置因释放而完全不可访问，尝试访问它会导致立即崩溃。然而，这并不保证。后续分配可能复用相同地址存储其他值。在这种情况下，解引用悬空指针可能导致更严重的问题。尝试通过它写入可能静默破坏我们 App 中某个不相关部分的状态。

这很糟糕，因为它可能有任意效果；例如，可能导致静默损坏甚至用户数据丢失。当访问的值包含对象引用，或内存现在包含不兼容类型的 Swift 值时，这类 bug 尤其阴险。

Xcode 提供一个名为 Address Sanitizer 的运行时调试工具，帮助你捕获这类内存问题。关于此工具和类似 Xcode 工具的更多信息，参见前一届大会的 "Finding Bugs Using Xcode Runtime Tools" 会议。关于如何避免指针类型安全问题的更详细讨论，请查看我同事 Andy 本周的 talk。

所以，如果指针如此危险，你为什么还要使用它们？嗯，一个重要原因是与 C 或 Objective-C 等不安全语言的互操作性。

在这些语言中，函数经常接收指针参数，因此要从 Swift 调用它们，你需要知道如何生成指向 Swift 值的指针。事实上，C 指针类型与其对应的 Swift 不安全指针对应物之间存在直接映射。我们导入到 Swift 的 C API 使用这种映射进行翻译。

获取这种指针的一种方式是使用 `UnsafeMutablePointer` 上的静态 "allocate" 方法，创建一个适合容纳整数值的动态缓冲区。然后我们可以使用指针运算和专用初始化方法，把缓冲区的元素设置为特定值。一旦都安排好，我们终于可以调用 C 函数，把指向已初始化缓冲区的指针传给它。函数返回后，我们可以反初始化并释放缓冲区，允许 Swift 稍后重用其内存位置。

我们可以通过把缓冲区建模为 (起始地址, 长度) 值对来改进代码的清晰度。这样，缓冲区的边界始终容易获得，例如，就可能在任何点轻松检查越界访问。

这就是标准库提供这四种不安全缓冲区指针类型的原因。每当我们需要处理内存区域而非指向单个值的指针时，它们就派上用场。通过把区域的大小及其位置打包在一个不错的包中，它们鼓励最佳实践，让你能更小心地管理内存。

在未优化的调试构建中，这些缓冲区指针通过其下标操作检查越界访问，贡献一点安全性。然而，这种验证必要时是不完整的：它仅限于边界检查。像指针一样，它们无法验证底层内存处于预期状态。尽管如此，部分检查远比完全没有验证有帮助，而仅仅把长度和地址作为单个单元考虑这一行为本身就已经帮助防止了一些简单错误。

Swift 的标准连续集合使用这些缓冲区指针，通过这些方便的不安全方法提供对底层存储缓冲区的临时直接访问。也可以获取指向单个 Swift 值的临时指针，然后传给期望此类的 C 函数。我们可以使用这些方法来简化代码，把不安全操作隔离到尽可能小的代码段。

为了摆脱手动内存管理，我们可以把输入数据存储在 `Array` 值中。然后我们可以使用 `withUnsafeBufferPointer` 方法临时直接访问数组的底层存储。在我们传给该函数的闭包内，我们可以提取起始地址和 count 值，并直接把它们传给要调用的 C 函数。

事实上，把指针传给 C 函数的需求如此频繁，Swift 提供了特殊语法。我们可以简单地把数组值传给期望不安全指针的函数，编译器会自动为我们生成等价的 `withUnsafeBufferPointer`。

记住，尽管如此，这并不改变指针仅在函数调用期间有效这一事实。如果函数逃逸指针并稍后尝试访问底层内存，那么无论我们用什么语法获取指针，都会导致未定义行为。

虽然 inout 到指针的转换可能很方便，但它们实际上只是为了帮助调用 C 函数。在纯 Swift 代码中，我们需要传递指针的频率要低得多，因此更有意义的做法是，当我们做这种事时，优先使用基于闭包的 API 来高亮这些情况。它们可能更冗长，但我发现它们的显式性使更容易理解究竟发生了什么。

特别是，它们基于闭包的设计使结果指针的实际生命周期更加显式，帮助你避免生命周期问题，比如这个无效的指针转换。这里，把临时指针传给可变指针初始化器使其值逃逸出初始化器调用。访问结果悬空指针值是未定义行为：底层内存位置可能不再存在，或者可能已被重用于其他值。为了帮助捕获这类 bug，Swift 5.3 编译器现在在能检测到这种情况时会产生有用的警告。

另一个最近的改进是，Swift 标准库现在提供了新的初始化器，允许我们通过直接把数据复制到其底层未初始化存储中来创建 `Array` 或 `String` 值。这消除了只为准备此类数据而分配临时缓冲区的需要。

例如，`String` 的新初始化器可用于调用同一个 sysctl 函数来检索字符串值。这里，我们想要找出我们运行的操作系统的内核版本，它由 kernel 部分的 VERSION 条目标识。

与缓存行例子不同，我们事先不知道版本字符串的大小。因此，为了弄清楚，我们将需要调用 sysctl 两次。

首先，我们用 nil 输出缓冲区调用函数。返回时，"length" 变量会被设置为存储字符串所需的字节数。和之前一样，我们需要记得检查任何报告的错误。手握结果大小，我们现在可以让 `String` 为我们准备未初始化存储，以便获取实际数据。初始化器给我们一个缓冲区指针，我们可以把它传给 sysctl 函数。函数会把版本字符串直接复制到这个缓冲区。返回时，我们验证调用成功。我们双重检查函数确实复制了一些字节到缓冲区，并且最后一个字节是零，对应终止 C 字符串的 NUL 字符。这个 NUL 字符不是版本字符串的一部分，所以我们通过返回比复制的字节数少一来丢弃它。这向 `String` 精确地发出信号，说明我们把多少字节的 UTF-8 数据复制到了它的存储中。

通过使用这个新的 `String` 初始化器，我们摆脱了这里的手动内存管理。我们得到对最终将成为常规 Swift 字符串实例存储的缓冲区的直接访问。我们不需要手动分配或释放内存。当我们调用这个函数时，我们得到预期的版本字符串。

所以，正如我们所见，我们可以使用标准库的不安全 API 优雅地解决即使是最棘手的互操作难题。

总结一下，要有效使用不安全 API，你需要了解它们的预期，并小心始终满足它们；否则你的代码会有未定义行为。

如果你把不安全 API 的使用保持在最小，这更容易做到。只要有更安全的替代方案，总是选择它们是个好主意。

当处理包含多个元素的内存区域时，最好使用不安全缓冲区指针而不是仅指针值来跟踪其边界。

Xcode 提供一组很棒的工具来帮助调试我们如何使用不安全 API 的问题，包括 Address Sanitizer。在把代码投入生产之前使用这些来识别 bug，并调试可能被 uncovered 的问题。
