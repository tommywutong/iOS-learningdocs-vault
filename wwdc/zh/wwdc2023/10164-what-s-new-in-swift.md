一年前，Swift 项目的治理结构经历了一次重大重组。核心团队宣布成立了 Language Steering Group（语言指导组），主要负责监督 Swift 语言和标准库的演进。此后，这个语言组已经监督了 40 项新的语言提案，我们今天会聊聊其中几项。

不过，有时候单个的语言提案会作为一个更大主题的一部分组合在一起，比如 Swift 并发的加入，它就是通过十份独立的提案引入的。

对于这样的情况，语言指导组引入了一种新方式，通过愿景文档（vision document）把这些提案串联起来。这些文档为语言的更大范围变化勾勒出一份提案。第一份被语言指导组接受的愿景文档，讲的是 Swift 宏的愿景，这是 Swift 5.9 中的一项新特性，我们稍后会在这场演讲里讲到。

当然，语言的演进只是 Swift 社区工作的一部分。一门成功的语言，需要的远不止这些。它需要出色的工具支持、对多个平台的强大支持，以及丰富的文档。为了监督这方面的进展，核心团队正在成立一个与语言指导组并行的生态系统指导组（ecosystem steering group）。这个新架构最近在 Swift.org 的一篇博客文章里公布了，敬请留意关于这个新组成立的进一步公告。现在，让我们来聊聊今年 Swift 语言的变化，先从更好地在代码里表达自己说起。Swift 5.9 加入了可能是我们收到请求最多的语言增强特性：允许把 if/else 和 switch 语句当作表达式使用，这提供了一种很好的方式来清理你的代码。

举个例子，如果你想根据某个复杂的条件初始化一个 let 变量，你以前不得不诉诸一些技巧，比如这种难以阅读的复合三元表达式。

有了 if 表达式，你可以改用一串熟悉得多、也易读得多的 if 语句链。

另一个能从中受益的场景，是当你要初始化一个全局变量或存储属性时。单个表达式在这里没问题，但如果你想用一个条件，你以前不得不用一个技巧：把它包进一个闭包里，然后立即执行这个闭包。

现在，既然 if 语句可以作为表达式，你就可以直接去掉那些多余的东西，让代码更整洁。

结果构建器（result builder）是驱动 SwiftUI 等特性的声明式语法，今年也迎来了重大改进，包括优化后的类型检查性能、代码补全，以及改进后的错误消息。

这次改进特别聚焦在无效代码上。以前，带错误的结果构建器代码要花很长时间才会报错失败，因为类型检查器要探索许多可能的无效路径。

从 Swift 5.8 开始，无效代码的类型检查快得多，无效代码上的错误消息现在也更加精确了。举个例子，以前，某些无效代码可能会在结果构建器完全不同的部分导致误导性的错误。在 Swift 5.7 中，你会收到这样的错误，而实际的错误其实在这里。

在最新版本中，你现在会收到更准确的编译器诊断，能准确指出真正的问题所在。

接下来，我们来聊聊泛型系统的一项新增内容，将如何为你每天使用的框架带来一些出色的改进。

你写的几乎所有 Swift 代码，都在以某种方式使用泛型。类型推断让你可以在不需要理解其背后高级能力的情况下使用这些类型。举个例子，标准库的 Array 类型用泛型来提供一种能容纳任何你想存储的数据类型的数组。当你使用一个数组时，你只需要提供元素。不需要为元素类型显式指定参数，因为它可以从元素值推断出来。

Swift 的泛型系统让人得以写出保留类型信息的自然 API，这样你的代码就能在你提供的具体类型上无缝运作。

这里有一个受 Swift 编译器自身代码库启发的例子：一个接收请求类型并对其求值、生成强类型结果的 API。所以你可以对一个 Boolean 值发起请求，得到一个 Boolean 结果。

现在，有些 API 不仅想对具体类型进行抽象，还想对传入的参数数量进行抽象。所以一个函数可能接收一个请求并返回一个结果，或者接收两个请求并返回两个结果，或者三个、返回三个。

为了支持这一点，泛型系统必须和一种能处理不同参数长度的机制结合起来使用，这样你传进去的所有类型，才能和你取出来的类型对应起来。

在 Swift 5.9 之前，实现这种模式的唯一办法，是为 API 支持的每一种具体参数长度都添加一个重载。但这种方式有局限。它会给你能传入的参数数量强加一个人为的上限，如果你传的参数太多，就会导致编译器报错。

在这个例子里，没有一个重载能处理超过六个参数，但我们传了七个。

这种重载模式及其局限性，在那些概念上应该处理任意参数长度的 API 中随处可见。

在 Swift 5.9 中，泛型系统获得了对这种 API 模式的一等支持，方法是让泛型抽象也能覆盖参数长度。这是通过一个新的语言概念实现的，它可以表示"打包"在一起的多个独立类型参数。这个新概念叫作类型参数包（type parameter pack）。

借助参数包，那些目前为每种固定参数长度都单独写了重载的 API，现在可以合并成一个函数。

evaluate 函数现在不再接收单个类型参数 Result（代表单个请求的结果类型），而是为每个 Result 类型接收一个独立的请求。

这个函数把每个结果实例放在括号里返回，它要么是单个值，要么是一个包含每个值的元组。

现在，evaluate 函数可以处理所有参数长度，没有人为的限制。

类型推断让使用参数包的 API 用起来很自然，你甚至不需要知道这个 API 用到了参数包。

调用我们这个现在能处理任意数量参数的新 evaluate 函数，看起来就和调用那些固定长度的重载一模一样。Swift 会根据你调用这个函数的方式，推断出每个参数的类型，以及参数的总数量。想了解怎么写出这样的泛型库 API，可以看看《使用参数包泛化 API》。

以自然的方式调用泛型 API，正体现了 Swift 的一个基本设计目标：用简洁的代码表达清晰的意图。

Swift 的高级语言特性让人得以写出优美的 API，让"说清楚你的意思"这件事变得更容易。

从你写下的第一行 Swift 代码开始，你就在受益于这些高级语言特性，不管是通过数组或字典使用泛型，还是在 SwiftUI 里设计一个界面。Swift 对渐进展现（progressive disclosure）的拥抱，意味着你可以在准备好的时候，再去了解那些更高级的特性。

Swift 5.9 通过一套用于表达式 API 设计的新工具箱——一个新的宏系统——把这种设计思路又向前推进了一步。接下来请 Doug 来给大家讲讲更多内容。Doug：借助宏，你可以扩展语言本身的能力，消除样板代码，释放出更多 Swift 的表达能力。我们来看看无处不在的 assert 函数，它检查某个条件是否为真。如果条件为假，assert 会让程序停下来，但那种时候，你能获得的关于出了什么问题的信息非常少，只有文件名和行号。你得加一些日志，或者在调试器里让程序中断，才能了解更多信息。已经有一些改进这一点的尝试了。XCTest 提供了一个 assert-equal 操作，它分别接收两个值，这样当出错时，你至少能看到那两个不相等的值。但我们仍然不知道这里到底是哪个值出了问题。是 a、b，还是 max 的结果？而且这种方式对我们在断言里做的各种检查来说，其实并不具备可扩展性。回到原来那个断言，源代码里其实包含了大量信息，我们希望在断言失败时能在日志里看到这些信息。代码是什么样的？a、b、c 的值分别是什么？max 算出了什么结果？在此之前，如果没有某种自定义特性，我们在 Swift 里没法改进这一点，但宏让这一切成为了可能。

在这个例子里，"井号-assert"（hash-assert）语法正在展开一个叫作 assert 的宏。这种井号语法你可能会觉得眼熟，因为 Swift 里已经有几个东西用了同样的写法，比如 hash-file、hash-selector 和 hash-warning。这个 assert 宏看起来、用起来都和函数版本很像，但因为它是一个宏，当断言失败时，它可以提供更丰富的体验。

现在，这个程序展示了失败断言的代码，以及每个参与计算出结果的值。

在 Swift 里，宏和类型或函数一样，都是 API，所以你要通过导入定义它们的模块来访问它们。和许多其他 API 一样，宏是以包的形式分发的。这里的 assert 宏来自 power asserts 库，这是一个在 GitHub 上开源的 Swift 包。

如果你去看这个宏包，你会找到 assert 的宏声明。它是用 "macro" 关键字引入的，但除此之外，它看起来很像一个函数。这里有一个未加标签的 Bool 参数，用来表示要检查的条件。如果这个宏会产生一个值，那个结果类型就会用通常的箭头语法写出来。宏的使用会依据这些参数做类型检查。这意味着，如果你在使用这个宏时犯了错，比如忘了拿 max 的结果去和别的东西比较，你会立刻收到一条有用的错误消息，甚至早于这个宏被展开之前。这让 Swift 在使用宏时能提供出色的开发体验，因为宏是在类型良好的输入上运作的，产生的代码也会以可预测的方式增强你的程序。大多数宏都被定义为"外部宏"（external macro），通过字符串指定宏实现所在的模块和类型。外部宏的类型定义在一个独立的程序里，这个程序扮演编译器插件的角色。Swift 编译器会把宏使用处的源代码传递给这个插件。插件会生成新的源代码，然后这些代码会被整合回 Swift 程序中。在这里，这个宏正在把这个断言展开成能捕获各个值、以及记录它们在源代码中位置的代码。你不会想自己去写这些样板代码，但这个宏替你做了。宏声明还有一项额外的信息：它的角色（role）。这里的 assert 宏是一个独立表达式宏（freestanding expression macro）。之所以叫"独立"（freestanding），是因为它用的是"井号"语法，并直接在这种语法上运作、生成新代码。它是一个表达式宏，因为它可以用在任何能产生值的地方。新的 Foundation Predicate API 就是表达式宏的一个很好的例子。这个 predicate 宏让人得以用闭包、以类型安全的方式写谓词。生成的 predicate 值随后可以配合许多其他 API 使用，包括 Swift 的集合操作、SwiftUI 和 SwiftData。

Swift 类型，不管是 struct 还是 class，默认都是可拷贝的（copyable）。大多数时候，这是正确的选择。虽然过多不必要的拷贝有时会成为你代码里的瓶颈，但比起被编译器不断要求你显式处理这些拷贝，偶尔花点时间在 Instruments 里找出这些瓶颈会更好。

不可拷贝类型还可以用来解决"调用了 close 之后又调用其他方法"这个问题。

close 操作可以被标记为 consuming。调用一个 consuming 方法或参数，会把这个值的所有权让渡给你调用的那个方法。因为我们的类型是不可拷贝的，让出所有权就意味着你没法再使用这个值了。

默认情况下，Swift 里的方法是借用（borrow）它们的参数的，包括 self。所以你可以调用 write 方法，它会借用这个文件描述符，用它写入缓冲区，之后，这个值的所有权会回到调用者手上，然后你就可以调用另一个方法，比如 close。

但由于 close 被标记为 consuming，而不是默认的 borrowing，它必须是这个值的最后一次使用。

这意味着，如果你先关闭了文件，然后又试图调用另一个方法，比如 write，你会在编译期就收到一条错误消息，而不是等到运行时才失败。编译器还会指出 consuming 用法发生的位置。

几年前，我们在 Swift 里引入了一套基于 async/await、结构化并发和 actor 这些构建块的新并发模型。Swift 的并发模型是一个抽象模型，可以适配到不同的环境和库上。这个抽象模型有两个主要部分：Task 和 Actor。Task 代表一个概念上可以在任何地方运行的顺序工作单元。每当程序里出现一个 "await"，Task 就可以被挂起，然后在这个 Task 能继续执行时恢复。

Actor 是一种同步机制，为隔离状态提供互斥访问。从外部进入一个 Actor 需要用 "await"，因为这可能会挂起当前的 Task。

Task 和 Actor 被集成进了这套抽象的语言模型里，但在这个模型内部，它们可以用不同的方式实现，以适配不同的环境。Task 是在全局并发池上执行的。这个全局并发池怎么决定调度工作，取决于所处的环境。在 Apple 的平台上，Dispatch 库为整个操作系统提供了经过优化的调度，并且针对每个平台都做了大量的调优。而在限制更多的环境里，多线程调度器的开销可能是不可接受的。在那种环境里，Swift 的并发模型是用一个单线程的协作队列实现的。同样的 Swift 代码可以在这两种环境里都正常工作，因为这个抽象模型足够灵活，能映射到各种各样的运行时环境。

此外，与基于回调的库之间的互操作性，从一开始就内建在 Swift 的 async/await 支持里。withCheckedContinuation 这类操作，让人得以挂起一个 Task，然后之后再响应某个回调把它恢复。这使得和那些自己管理 Task 的既有库集成成为可能。

Swift 并发运行时中 Actor 的标准实现，是一个用来在该 Actor 上执行的、无锁的任务队列，但这并不是唯一可能的实现。在一个限制更多的环境里，可能没有原子操作可用，这时可以改用另一种并发原语，比如自旋锁（spinlock）。如果那个环境是单线程的，就根本不需要同步，但不管怎样，Actor 模型都会为这个程序维持住这套抽象的并发模型。你依然可以把同样的代码搬到另一个多线程的环境里去。有了 Swift 5.9，自定义 Actor executor 让某个特定的 Actor 得以实现自己的同步机制。这让 Actor 变得更加灵活，也更能适配已有的环境。我们来看一个例子。

这里我们给我们的 Actor 加了一个串行 dispatch queue，还实现了 unowned executor 属性，它会产生和这个 dispatch queue 对应的 executor。有了这个改动，我们这个 Actor 实例的所有同步操作，都会通过那个队列来完成。

当你在 Actor 外部对 pruneOldEntries 的调用发起 "await" 时，现在这会在对应的队列上执行一次 dispatch-async。这让你对每个 Actor 提供同步的方式有了更多控制，甚至能让一个 Actor 和还没采用 Actor 的其他代码同步，比如那些代码是用 Objective-C 或 C++ 写的。

之所以能通过 dispatch queue 来同步 Actor，是因为 dispatch queue 遵循了新的 SerialExecutor 协议。你可以定义一个遵循这个协议的新类型，来提供自己的、可供 Actor 使用的同步机制，这个协议只有很少几个核心操作：检查代码是否已经在这个 executor 的上下文里执行——举个例子，我们是不是正运行在主线程上？取出一个指向这个 executor 的 unowned 引用，让人得以在不产生额外引用计数流量的情况下访问它。以及最核心的操作，enqueue，它接收一个 executor "job" 的所有权。一个 job 是某个异步 Task 里需要在这个 executor 上同步运行的那一部分。在 enqueue 被调用的那一刻，确保在串行 executor 上没有其他代码在运行的某个时刻运行那个 job，就是这个 executor 的职责。举个例子，dispatch queue 的 enqueue 就会在那个队列上调用 dispatch async。
