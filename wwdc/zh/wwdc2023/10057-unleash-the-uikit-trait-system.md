首先，我声明一个新结构体并符合 UITraitDefinition 协议。我实现唯一的必需静态属性 defaultValue。这是在没有设置任何值时该特性的默认值。每个特性定义都有一个关联的值类型，它由 defaultValue 推断而来。在这个例子中，由于我把 defaultValue 赋值为 false，这个特性值的类型被推断为 Bool。如果你以前在 SwiftUI 中定义过自定义环境键，这应该会让你感觉很熟悉。一旦定义了特性，你就可以立即在 UITraitCollection 和 UIMutableTraits 的新 API 上使用它。你可以把这个特性看作一个用来获取和设置值的键。在新的 UITraitCollection 初始化方法中，我可以通过在 UIMutableTraits 上使用下标运算符来为我的特性设置值。然后我可以通过在 UITraitCollection 上使用下标运算符读回该特性的值。添加两个简单的扩展，就能让我像所有系统特性一样使用标准属性语法访问这个特性。这里我在不可变的 UITraitCollection 类的扩展中声明了一个只读属性。然后我在 UIMutableTraits 协议的扩展中声明了一个可读写属性。现在我添加了这些非常简单的扩展，就可以在任何地方使用标准属性语法访问我的特性。定义你自己的自定义特性时，请务必编写这些扩展。我还有一个自定义特性的想法。想象我正在为 App 构建自定义颜色主题的支持。我有一个名为 MyAppTheme 的枚举，代表我的 App 支持的四种不同颜色主题。我要做的第一件事是声明一个符合 UITraitDefinition 协议的新结构体。我会把标准主题用作这个特性的默认值。由于我打算在 App 的自定义动态颜色中使用这个新主题特性，我指明该特性会影响颜色外观，系统会在该特性变化时自动重绘视图。影响颜色外观的特性开销要大得多，所以请谨慎使用，只用于变化不频繁的特性。特性还有一个名称，用于在调试器中打印特性之类用途。默认情况下，它会使用特性类型本身的名称，但我可以给它一个更短的名字，比如 "Theme"。最后，我还可以提供一个标识符字符串。标识符让该特性有资格获得编码等额外功能。请使用反向 DNS 格式，以确保每个特性的标识符在你的 App 中全局唯一。

我想能够使用常规的属性语法来设置和获取这个特性，所以我会扩展 UITraitCollection 和 UIMutableTraits 来声明一个属性，就像我在前一个示例中所做的那样。这就是我实现自定义主题特性所需做的全部工作。现在我可以开始使用这个新特性了。例如，这里展示如何定义一个根据主题改变外观的自定义动态颜色。我使用动态提供程序初始化方法创建一个新的 UIColor。在闭包中，我使用传入的特性集合的主题来决定返回哪种颜色。现在我可以把这个自定义背景色设置给某个视图。由于我在定义时指明了该特性会影响颜色外观，任何使用这个自定义背景色的视图都会在主题变化时自动更新。定义特性时，最重要的考虑因素是特性值的关联数据类型。最好的特性是围绕值类型构建的，包括简单的结构体和枚举。请避免在 Swift 中使用基于类的特性。对特性而言最高效的数据类型是 Bool、Int 和 Double，或者使用 Int 原始值的枚举。枚举是特性最有用的数据类型之一。只需确保明确指定 Int 作为枚举的原始数据类型，就能获得最高效率。你用作特性值的任何自定义结构体数据类型，都应具有 Equatable 协议的高效实现。系统会频繁比较特性值以确定特性何时发生变化，所以你的相等判断函数应尽可能快。

对于使用 Objective-C 的 App，新的特性系统功能在那里同样可用。自定义特性 API 在 Swift 和 Objective-C 中并不相同。不过，你可以在 Swift 中定义一个自定义特性、在 Objective-C 中定义另一个，并让两者指向相同的底层数据。更多细节和特殊注意事项，请参阅文档。

定义了自定义特性之后，下一步是在你 App 的特性层级结构中为它填充一些数据。

特性覆盖（trait override）是你用来修改特性层级结构中数据的机制。在 iOS 17 中，应用特性覆盖比以往更容易。每个特性环境类上都有一个新的 traitOverrides 属性，包括窗口场景、窗口、视图、视图控制器和呈现控制器。回到特性层级结构的示意图，特性覆盖会改变这棵树中任何位置的特性的值。当你对层级结构中的某个特性环境应用特性覆盖时，它会修改该对象及其所有后代的特性集合中该特性的值。从特性层级结构中取一个父级和子级特性环境，看看特性覆盖如何影响两者。应用于父级的特性覆盖影响父级自己的特性集合。然后父级特性集合中的值被子级继承。最后，子级的特性覆盖被应用到它继承的值上，从而产生它自己的特性集合。把特性覆盖看作可选的输入，把特性集合看作输出。任何没有覆盖的特性都会从父级继承。我会用一个例子演示如何使用特性覆盖来改变 App 特定部分的颜色主题。右边是我 App 特性层级结构的示意图。最初我没有应用任何覆盖来为主题特性填充值，所以所有这些特性集合都使用默认值，也就是标准主题。我先从在层级结构的根部——窗口场景上——应用一个特性覆盖开始。traitOverrides 属性利用 UIMutableTraits 协议，让你可以轻松设置特性值。因此，你可以使用我前面解释过的 UIMutableTraits 扩展，用标准属性语法为自定义特性设置覆盖值。通过在窗口场景的特性覆盖上把主题设置为 pastel，该窗口场景内的所有窗口、视图控制器和视图现在都会在它们的特性集合中继承 pastel 值。所以，通过在层级结构的根部这一个地方设置主题，我改变了传播到该层级结构中所有内容的基础值。例如，我可以从该窗口场景内任何视图控制器的特性集合中读取主题，得到 pastel。然后我可以使用层级结构中更深层某个视图上的 traitOverrides 属性，来修改该视图及其下方所有内容的主题。这里我为这个视图设置了一个 monochrome 的主题特性覆盖。所以这个 monochrome 值就是其子视图将继承的值，覆盖了层级结构中更上方的 pastel 值。你可能无法立即在特性集合中看到对特性覆盖的更改。例如，由于视图在布局之前更新其特性集合，对视图特性覆盖的修改在它运行 layoutSubviews 之前不会反映在其特性集合中。traitOverrides 属性还允许你检查是否应用了覆盖，以及完全移除覆盖。这里是一个切换覆盖的例子，使用 contains 方法检查覆盖是否存在，并使用 remove 方法完全移除覆盖。每次调用这个方法时，它要么移除现有的覆盖，要么在尚无覆盖时应用一个新的主题覆盖。特性覆盖是设置值的输入机制。要读取特性值，请始终使用 traitCollection 属性。在没有设置覆盖时从 traitOverrides 读取会引发异常。

以下是使用特性覆盖时要牢记的一些性能注意事项。首先，每个特性覆盖都有少量开销，所以只在需要的地方设置特性覆盖，避免设置未被使用的特性覆盖。而且每次更改特性覆盖时，系统都需要更新层级结构中任何后代的特性集合。因此，请尽量减少更改特性覆盖的次数。最后，应用于层级结构根部附近（例如窗口场景或窗口）的特性覆盖，会影响其下方的所有内容。这非常有用，并且把特性覆盖应用于窗口场景或窗口有很多很好的用例。然而，当某个特性只影响层级结构深处的少数视图时，请把特性覆盖应用到这些视图最近的共同祖先，例如共同的父视图或视图控制器。这样，当层级结构中只有一小部分使用该数据时，你就不必付出把特性传播到整个层级结构的代价。既然你已经知道如何定义特性并在层级结构中填充数据，你就需要处理它们值变化的情况。

traitCollectionDidChange 在 iOS 17 中已废弃。当你实现 traitCollectionDidChange 时，系统不知道你实际关心哪些特性，所以只要任何特性值发生变化，它都必须调用该方法。然而，大多类只使用少数几个特性，不关心其他特性的变化。这就是为什么随着你添加越来越多的自定义特性，traitCollectionDidChange 无法良好扩展。取而代之的是新的特性注册 API，它们更灵活并能提升性能。通过为特定的特性注册变化，系统确切知道你依赖哪些特性。新 API 允许你使用目标-动作模式或闭包接收回调。而且由于你不再需要在子类中重写方法，现在从任何地方观察特性变化都很容易。我先解释如何更新 traitCollectionDidChange 的现有实现。这是我现有的实现。请注意，在调用 updateViews 之前，我如何先检查 horizontalSizeClass 特性是否发生了变化，因为该方法只依赖这一个特性。如果你因为要把 App 部署到较旧的 iOS 版本而需要继续使用 traitCollectionDidChange，请确保你的实现会检查你关心的特定特性是否发生了变化。现在我用 iOS 17 中新的特性注册方法替换这个实现。我先从基于闭包的方法开始。我调用 registerForTraitChanges 并传入要注册的特性数组。所有系统特性都有新的 UITrait 符号，例如这个水平尺寸类别的符号。然后我传入一个闭包，它在那些特定特性变化时被调用。其他任何特性的变化都不会调用这个闭包，所以这里无需比较新旧特性值。特性发生变化的对象作为第一个参数传给闭包。使用这个参数，你就无需为该对象捕获弱引用。当你在 self 上注册特性变化时，请始终在这里写 "self: Self"。你也可以观察另一个特性环境的特性变化。这里我为两个特性注册变化，水平尺寸类别和我之前定义的 ContainedInSettings 自定义特性。当这个另一个视图上的任一特性发生变化时，闭包就会执行。我把注册所在的视图类型写为闭包的第一个参数。

这是一个新的基于目标-动作的方法的例子。调用 registerForTraitChanges，传入要注册的特性数组，以及变化时要调用的目标和动作方法。target 参数是可选的。如果省略它，目标就是调用 registerForTraitChanges 的同一个对象。在这个例子中，那就是 self。与闭包方法一样，你也可以注册其他特性环境的变化。这里我在另一个视图上注册特性变化，但设置的是调用 self 上名为 handleTraitChange 的方法。使用目标-动作注册特性变化时，你的动作方法可以有零个、一个或两个参数。第一个参数总是特性正在变化的对象。用这个参数获取新的 traitCollection。第二个参数总是该对象在变化之前的特性集合。除了为单个特性注册，你还可以使用新的系统特性语义集合来注册。例如，systemTraitsAffectingColorAppearance 返回可能影响系统动态颜色解析方式的所有系统特性。还有 systemTraitsAffectingImageLookup，它返回使用 UIImage(named:) 加载图像时会被考虑的系统特性子集。把这两个集合中的任何一个直接传给 registerForTraitChanges，即可执行自定义失效。

使用新方法注册特性变化时，注册会被自动清理。如果你有高级用例，可以使用每个注册方法返回的令牌手动注销。但这些情况非常少见，所以通常你在调用 registerForTraitChanges 时应忽略返回值。在采用新的特性注册 API 时，有两个最佳实践要牢记。首先，只为你实际依赖的特性注册，这样当无关特性值变化时你无需执行工作。最后，尽量在特性变化时失效而不立即更新。例如，如果你在视图子类的 layoutSubviews 方法中使用特性，请调用 setNeedsLayout 来为特性变化失效。这会让视图被安排接收 layoutSubviews，但不会立即执行更新。既然你可以在 UIKit 中使用特性系统来传播自己的数据，它就为你开启了一种全新的方式，在你 App 的 UIKit 和 SwiftUI 组件之间无缝传递数据。UIKit 中的自定义特性与 SwiftUI 中的自定义环境键非常相似。你可以把它们桥接起来，以便从 UIKit 和 SwiftUI 访问相同的数据。无论你是把 SwiftUI 组件嵌入 UIKit，还是把 UIKit 组件嵌入 SwiftUI，桥接的数据都能在两者之间无缝传递。你可以在 UIKit 代码中使用特性 API、在 SwiftUI 代码中使用环境 API 来读写相同的底层数据。把我在 App 的 UIKit 代码中定义的新颜色主题特性，桥接到 SwiftUI 中相应的环境键，简直易如反掌。
