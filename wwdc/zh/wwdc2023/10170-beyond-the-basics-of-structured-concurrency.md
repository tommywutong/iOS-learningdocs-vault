结构化并发让你能够使用明确定义的节点来推理并发代码——在这些节点上，执行过程会分支并并发运行，之后执行结果重新汇合，类似于 "if" 块和 "for" 循环定义同步代码中控制流行为的方式。当你使用 "async let"、任务组，或创建任务（Task）或分离任务（detached task）时，并发执行就会被触发。

什么会导致任务取消？结构化任务在超出作用域时会隐式取消，不过你可以在任务组上调用 `cancelAll` 来取消所有活跃的子任务以及任何未来的子任务。

非结构化任务通过 `cancel` 函数显式取消。

取消父任务会导致所有子任务被取消。

取消是协作式的，所以子任务不会立即停止。

它只是在该任务上设置 `isCancelled` 标志。实际响应取消的操作在你的代码中完成。

与同步迭代器一样，`next` 函数返回序列中的下一个元素，或者返回 nil 表示已到达序列末尾。许多 AsyncSequence 是通过状态机实现的，我们用它来停止正在运行的序列。

请注意，由于取消处理程序会立即运行，状态机是取消处理程序和主执行体之间共享的可变状态，它们可以并发运行。我们需要保护我们的状态机。

虽然 Actor 非常适合封装状态，但我们想要修改和读取状态机上的各个属性，所以 Actor 并不是完全合适的工具。

这些机制允许我们同步共享状态，避免竞态条件，同时允许我们取消正在运行的状态机，而无需在取消处理程序中引入非结构化任务。

任务树会自动传播任务取消信息。无需担心取消令牌和同步，我们让 Swift 运行时为我们安全地处理。

接下来，让我们考虑结构化任务树如何帮助传播优先级并避免优先级反转（priority inversion）。

首先，什么是优先级，我们为什么关心它？优先级是你向系统传达给定任务的紧急程度的方式。某些任务，比如响应用户点击按钮，需要立即运行，否则 App 会看起来冻结了。

与此同时，其他任务，比如从服务器预取内容，可以在后台运行而无需任何人注意。

第二，什么是优先级反转？当高优先级任务正在等待低优先级任务的结果时，就会发生优先级反转。

默认情况下，子任务从它们的父任务继承优先级，所以假设 `makeSoup` 以一个中等优先级的任务运行，所有子任务也将以中等优先级运行。

假设有一位 VIP 顾客来到我们的餐厅想要喝汤。

我们给他们的汤赋予更高的优先级，以确保我们获得好评。

当他们等待他们的汤时，所有子任务的优先级都会提升，确保没有高优先级任务在等待低优先级任务，从而避免了优先级反转。

等待来自更高优先级任务的结果会提升任务树中所有子任务的优先级。

请注意，等待任务组的下一个结果会提升组中所有子任务的优先级，因为我们不知道哪一个最可能先完成。

并发运行时使用优先级队列来调度任务，因此高优先级任务会在低优先级任务之前被选中运行。

该任务在其剩余生命周期内保持提升后的优先级。

无法撤销优先级提升。

我们有效地用快速的汤品送达满足了 VIP 顾客并获得了好评，所以我们的厨房现在开始受欢迎了。我们想要确保有效地利用资源，并注意到我们创建了很多切菜任务。

新的循环等待直到其中一个正在运行的任务完成，并且当仍有食材需要切时，添加一个新任务来切下一种食材。

让我们提炼一下这个想法，以便更清楚地看到这个模式。

初始循环创建最多上限数量的并发任务，确保我们不会创建太多任务。

一旦达到最大数量的任务正在运行，我们就等待其中一个完成。

在它完成之后，如果我们还没有达到停止条件，就创建一个新任务来继续推进。

这限制了组中的并发任务数，因为我们在较早的任务完成之前不会开始新的工作。

之前，我们谈到了厨师轮班工作，并使用取消来指示轮班结束。

这是处理轮班的厨房服务代码。

每位厨师在一个单独的任务中开始他们的轮班。

一旦厨师们开始工作，我们就启动一个计时器。计时器结束时，我们取消所有正在进行的轮班。

注意，这些任务都不返回值。Swift 5.9 新增了 `withDiscardingTaskGroup` API。丢弃任务组（discarding task group）不会保留已完成的子任务的结果。任务使用的资源会在任务完成后立即释放。

我们可以修改 `run` 方法来使用丢弃任务组。

丢弃任务组会自动清理它们的子任务，因此无需显式取消组并进行清理。

丢弃任务组还具有自动兄弟取消（sibling cancellation）功能。

如果任何子任务抛出错误，所有剩余任务都会被自动取消。

这对我们这里的用例来说非常理想。当轮班结束时，我们可以抛出一个 `TimeToCloseError`，它就会自动结束所有厨师的轮班。

新的丢弃任务组会在任务完成时自动释放资源，而普通任务组则需要你手动收集结果。当你有许多不需要返回任何值的任务时（比如正在处理请求流时），这有助于减少内存消耗。

在某些情况下，你可能需要从任务组中返回值，但同时也希望限制并发任务的数量。我们介绍了一种通用模式：利用一个任务的完成来启动另一个任务，从而避免任务爆炸。我们比以往任何时候都更高效地制作汤，但我们还需要进一步扩展。

是时候将生产迁移到服务器了。

随之而来的挑战是追踪正在处理的订单。

任务本地值可以提供帮助。

任务本地值是与给定任务（更准确地说，是与任务层级结构）关联的一段数据。它就像一个全局变量，但绑定到该任务本地值的值仅对当前任务层级结构可用。

任务本地值被声明为带有 `TaskLocal` 属性包装器的静态属性。

好的做法是将任务本地值设为可选值（optional）。

任何没有设置该值的任务都需要返回一个默认值，这可以通过一个 nil 可选值轻松表示。未绑定的任务本地值包含其默认值。

在我们的例子中，我们有一个可选 String，所以它是 nil，并且当前任务没有关联任何厨师。任务本地值不能显式赋值，但必须在特定作用域内进行绑定。绑定在该作用域持续期间有效，并在作用域结束时恢复为原始值。

回到任务树，每个任务都有一个关联的位置来存放任务本地值。

我们在制作汤之前将名称 "Sakura" 绑定到 "cook" 任务本地变量。只有 `makeSoup` 存储了绑定的值。子任务的任务本地存储中没有保存任何值。

查找绑定到任务本地变量的值涉及递归地向上遍历每个父任务，直到找到具有该值的任务。

如果我们找到一个绑定了该值的任务，任务本地变量将采用该值。

如果我们到达了根任务（由没有父任务的任务指示），表明该任务本地变量未被绑定，我们将得到最初的默认值。Swift 运行时经过优化，可以更快地执行这些查询。

我们不再需要遍历树，而是直接引用包含我们正在查找的键的任务。

任务树的递归性质非常适合在不丢失先前值的情况下遮蔽值。

让我们看看如何使用任务本地值使我们的记录日志更可靠。

在 Apple 设备上，你将继续直接使用 OSLog API，但随着你的应用程序部分迁移到云端，你将需要其他解决方案。

SwiftLog 是一个日志 API 包，具有多种后端实现，允许你插入适合自己需求的后端，而无需更改服务器代码。

MetadataProvider 是 SwiftLog 1.5 中的一个新 API。

实现一个 metadata provider 可以轻松地抽象你的记录日志逻辑，确保你始终如一地发出有关相关值的信息。

metadata provider 使用类似字典的结构，将名称映射到要记录的值。我们想自动记录 orderID 任务本地变量，所以检查它是否已定义，如果已定义，则将其添加到字典中。多个库可能定义自己的 metadata provider 来查找库特定的信息，因此 MetadataProvider 定义了一个 `multiplex` 函数，它接收多个 metadata provider 并将它们合并成单个对象。

一旦我们有了 metadata provider，我们就用它来初始化日志系统，然后就可以开始记录日志了。

日志会自动包含 metadata provider 中指定的信息，因此我们无需担心在日志消息中包含它。

日志显示，当订单 0 进入厨房时，以及我们的厨师在哪处理这个订单。

metadata provider 中的值在日志中清晰地列出，使你更容易跟踪订单在汤制作过程中的流转。

任务本地值允许你将信息附加到任务层级结构。

除了分离任务之外，所有任务都会从当前任务继承任务本地值。它们在给定的作用域内绑定到特定的任务树，为你提供底层的构建块，以通过任务层级结构传播额外的上下文信息。现在，我们将利用任务层级结构及其提供的工具来追踪和分析一个并发的分布式系统。在 Apple 平台上处理并发时，Instruments 是你的好帮手。Swift Concurrency 工具让你深入了解结构化任务之间的关系。更多信息，请查看讲座《可视化和优化 Swift 并发》。Instruments 还在《在 Instruments 中分析 HTTP 流量》讲座中引入了 HTTP 流量分析工具。HTTP 流量分析器只显示本地事件的追踪信息。

分析结果显示，在等待服务器响应时会显示一个灰色框，因此我们需要更多信息来了解如何提高服务器的性能。

隆重推出新的 Swift Distributed Tracing 包。

任务树非常适用于管理单个任务层级结构中的子任务。

分布式追踪允许你跨多个系统利用任务树的优势，深入了解性能特征和任务关系。Swift Distributed Tracing 包实现了 OpenTelemetry 协议，因此现有的追踪解决方案，如 Zipkin 和 Jaeger，开箱即用。

我们使用 Swift Distributed Tracing 的目标是用关于服务器上正在发生的事情的详细信息，来填充 Xcode Instruments 中不透明的“等待响应”区域。我们需要对我们的服务器代码进行插桩，以找出我们需要关注的重点。

分布式追踪与在本地追踪进程略有不同。

我们不按函数获取追踪信息，而是使用 `withSpan` API 对我们的代码进行跨度（span）插桩。

跨度允许我们为代码区域分配名称，这些名称会在追踪系统中报告。跨度不需要覆盖整个函数。

它们可以为给定函数的特定部分提供更深入的洞察。

`withSpan` 使用额外的追踪 ID 和其他元数据来注释我们的任务，使追踪系统能够将任务树合并为单个追踪。追踪系统有足够的信息，可以让你深入了解任务层级结构，以及任务运行时性能特征的信息。

跨度名称会显示在追踪 UI 中。

你希望它们保持简短和描述性，这样你就可以轻松找到特定跨度的信息而无需过多杂乱信息。

我们可以通过使用跨度属性（span attributes）来附加额外的元数据，这样就不需要用订单 ID 来使跨度名称变得杂乱。

这里我们将跨度名称替换为 `#function` 指令，以自动用函数名称填充跨度名称，并使用跨度属性将当前订单 ID 附加到报告给追踪器的跨度信息中。

追踪系统通常在检查特定跨度时呈现这些属性。

大多数跨度都带有 HTTP 状态码、请求和响应大小、开始和结束时间，以及其他元数据，使你更容易追踪通过系统传递的信息。

如上一张幻灯片所述，你可以定义自己的属性。有关如何利用跨度的更多示例，请查看 swift-distributed-tracing-extras 仓库。

如果某个任务失败并抛出错误，该信息也会呈现在跨度中并在追踪系统中报告。由于跨度既包含时间信息也包含任务在树中的关系，因此这是追踪由时序竞态引起的错误并识别它们如何影响其他任务的有用方法。我们已经讨论了追踪系统如何利用追踪 ID 重建任务树，以及如何将你自己的属性附加到跨度上，但我们还没有开始将它整合到分布式系统中。追踪系统的美妙之处在于，不需要再做任何额外的事情。

如果我们从厨房服务中分离出一个切菜服务，并保持相同的代码，追踪系统将自动捕获追踪并将它们关联到分布式系统中的不同机器上。

追踪视图将指示这些跨度正在不同的机器上运行，但其他方面相同。当系统的所有部分都拥抱追踪时（包括 HTTP 客户端、服务器和其他 RPC 系统），分布式追踪最为强大。

Swift Distributed Tracing 利用基于任务树构建的任务本地值，自动传播所有必要的信息以产生可靠的跨节点追踪。结构化任务揭示了并发系统的秘密，为你提供了自动取消操作、自动传播优先级信息以及促进追踪复杂分布式工作负载的工具。

所有这些之所以有效，都归功于 Swift 中并发的结构化本质。
