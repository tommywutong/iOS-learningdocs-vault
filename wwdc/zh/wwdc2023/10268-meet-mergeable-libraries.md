静态库是一组目标文件（object files）的集合。在构建时，静态链接器会找到这些库中要使用的 API，并将相应代码复制到 App 二进制文件中。

由于代码是被复制过来的，因此在构建后就不再需要库本身。如果静态库中的代码发生变化，或者使用了更多的库，就会导致构建时间变慢。这是由于它们被归档和链接到 App 的方式造成的，这使得迭代构建和调试变得更慢。可以使用动态库来避免这种情况。动态库通常称为 dylib。它们是 Xcode 中框架（framework）目标的二进制文件类型。

框架的代码不会被复制到可执行文件中。相反，静态链接器会将库的安装路径记录到 App 二进制文件中，供之后使用。任何不在 Apple SDK 中的框架都必须嵌入到 App bundle 中。关键区别在于，当添加或更新动态库时，静态链接器无需复制代码。这会带来更快的构建速度。然而，这也增加了 App 在运行时使用的复杂性。这时就需要动态链接器上场了。当 App 启动时，名为 dyld 的动态链接器必须找到并加载框架依赖项。这包括这些框架所依赖的库。

随着使用量的增加，这会导致内存消耗和 App 启动时间持续增加。如果算上来自 Apple SDK 的依赖项，App 通常需要加载数百个框架。我们的平台已针对这种情况对系统库进行了深度优化。但这并不适用于嵌入到 App 中的框架。总而言之，在决定使用静态库还是动态库时，存在一些取舍。

虽然动态库对构建时间影响很小，但会带来明显的启动时间代价；而静态库对启动时间影响最小，但在构建时间方面代价高昂。正因如此，我们过去一直建议你衡量哪种方式最适合你的 App。有了可合并库，就无需再做这种权衡了。可合并库兼具两种链接策略的优点。我将介绍可合并库如何能优化性能与开发体验。设想任何二进制映像（binary image），例如可执行文件。这个二进制文件所依赖的框架会交给静态链接器。这些依赖项可以成为可合并库。而链接后的输出则可以成为合并后的二进制文件。但是什么让这些依赖项变得可合并呢？这可以通过它们的构建方式来解释。任何动态库都可以构建为可合并库。当静态链接器创建库时，它也会生成元数据（metadata）。元数据存在于二进制文件内部，这会增加二进制文件的总体大小。它允许链接器在将该库用作链接依赖项时，像对待静态库一样处理它。有了元数据，库的使用者可以选择像普通动态库那样静态链接，也可以选择合并。合并后的二进制输出可以是一个可执行文件（例如 App），也可以是另一个动态库（例如框架）。合并的过程与静态库的链接方式类似。最终，你会得到一个包含这些库的段（segments）的二进制文件，并且该输出二进制文件的文件类型保持不变。合并是 Xcode 15 中一项全新功能，由新版静态链接器实现。它通过使用新的链接器选项来工作。首先，要合并的库需使用 `-make_mergeable` 选项构建。这会告诉链接器记录元数据。接下来，对于合并后的二进制文件，链接器会利用该元数据以及这些库，通过 `-merge_library` 或 `-merge_framework` 选项生成最终输出。Xcode 会为你处理这些细节。不过，你可以在查看构建日志时看到这些选项是如何被应用的。但合并比单纯的链接好在哪里呢？我们来考虑一下合并后的大小。首先，库及其元数据在合并后就不再需要，可以被移除。所以唯一需要关注的是合并后二进制文件的大小。合并时，链接器可以跨所有库对内容（例如字符串）进行去重。例如，它会移除冗余的符号引用、Objective-C 选择器（selectors）和 `objc_msgSend` 存根（stubs）。这会使得整体 App bundle 变得更小。最终二进制文件的映像类型也保持不变。这意味着所有已支持的链接器优化都可以应用。

这也会对 App 启动产生积极影响。当加载的框架减少时，dyld 和内核在启动你的 App 时所需做的工作就会减少，并且会降低内存占用，让用户更加满意。但我们也知道，将代码分离到不同的库中对于高效开发和维护至关重要。使用可合并库，你可以两者兼得。可合并库只需极少的代码和配置更改就能实现这一点，而且随着你采用更新的框架，这种方案也能很好地扩展。让我们重新审视之前关于动态链接的图表。所有这些嵌入的框架都可以变为可合并的，因为链接器可以为它们生成元数据。我们可以创建一个框架来合并其他库的内容。这样你最终只需要嵌入一个框架。dyld 只需加载那个包含了所有嵌入框架的段（segments）的库。以这种方式合并，可以极大地简化大型依赖链。这就是可合并库所能实现的效果。我们来谈谈如何启用它们。在 Xcode 中有两种启用库合并的方法。我将从最简单的自动合并讲起，然后再介绍手动合并，以备你想控制哪些库应当变为可合并时所用。我将介绍可合并库如何在调试模式下提供最佳的构建时间，之后，我会分享在需要调试你的可合并库并对其进行符号化（symbolicate）时应当注意什么。自动合并会告知构建系统合并所有作为嵌入框架目标的直接依赖项。它对 App 目标尤其有用。我来演示一下。我以“Swift and C++ Forest Project”为例。这里有一个链接了四个框架的 App 目标。其中有来自 Apple SDK 的 SwiftUI。另外三个——ForestBuilder、ForestUI 和 Forest——是在项目中构建的。当启用自动合并时，这三个森林框架将变为可合并的。SwiftUI 保持不变，因为它是一个系统库。在链接 App 时，这些框架将直接合并到 App 二进制文件中。这意味着这些框架在启动时不再需要，可以从磁盘中移除。我们来看看如何在 Xcode 中开启这项功能。

为了支持 Xcode 中的迭代开发，链接器在调试模式下不会执行合并。构建系统会指示链接器改为重新导出（reexport）这些库。重新导出是一种链接器选项，它允许代码的实现存在于一个动态库中，却表现得像是在另一个库中实现的一样。换句话说，这意味着只需依赖合并后的目标（例如你的 App 扩展或测试），就可以访问所有库的 API。这会带来与动态库类似的构建时间优势。启动时，dyld 会将它对重新导出库的引用重定向，而不是期望它们直接来自合并后的二进制文件。这确实意味着在调试情况下，可合并库会保留在磁盘上。

说到调试，我们来看看可合并库中可能用到的一个符号。我有一个函数，接收一个整数并返回其平方结果。这是构建出来的代码。然而，我们都知道，这并不是机器真正执行的代码。相反，这份代码会经历许多转译。在我们需要排查代码中的 bug 之前，这都没什么问题。这就是 Xcode 支持符号化（Symbolication）的原因。符号化是将这些机器指令关联回原始源代码的过程。这对于读懂崩溃日志，或是剖析和调试代码都非常有用。那么，这对合并后的二进制文件是如何生效的呢？当你启用合并时，源代码位置信息仍会从原始库中保留。这意味着你的调试体验保持不变。但请记住，当显示库信息时（例如堆栈跟踪），它会显示合并后二进制文件的路径。这些信息会呈现在崩溃日志中、Instruments 内部以及调试器中。是时候考虑一下你自己的项目可以如何采用可合并库了。在许多情况下，启用它们只需改动几个 Xcode 设置。但有一些因素值得注意。我将介绍五个值得重点考虑的方面。

我将从如何处理你对可合并库的任何既有依赖开始。然后，我会介绍什么是自动链接（autolinking）以及它与可合并库如何协同工作。如果你使用了运行时查找 API，例如 `dlopen` 或 bundle 接口，我会讲到接下来要提到的一些限制。由于合并是由 Xcode 15 中的新版静态链接器实现的，我会提一下它与旧版链接器之间的重要区别。最后一项注意事项是针对那些有兴趣将自己的框架分发给其他开发者的朋友。

对于库的依赖，让我们回到演示 dyld 工作的那个图表。如果有尚未合并的可合并库的依赖者（dependents）——例如，其他可执行文件——它们将需要更新为依赖合并后的框架，因为可合并的库会被从磁盘中移除。另一种可能出现此问题的情况是，当 App 依赖自动链接时。自动链接是一项默认开启的编译器选项。当编译器在源代码中发现模块导入时，它会检测到框架依赖，然后传递给链接器。所以，如果你从可合并库中导入模块，就可能导致动态链接问题。不过，你无需禁用自动链接。这里的解决方案与之前相同：链接到合并后的框架。

实现这一点的最常用方法是在“Link Binary with Libraries”构建阶段中添加合并后的框架，并移除已经存在的可合并库。否则，dyld 将无法为你的 App 加载正确的框架。

大多数开发者不需要使用像 `dlopen` 这样的动态链接 API。但如果你使用了，那些输入路径也需要指向合并后的框架目标。

同样，资源查找也可能受到库合并的影响。这是因为运行时的预期行为所致。在 Swift 中，`Bundle` 是一种 API，用于让运行时加载框架的 bundle。在 Objective-C 中，等效的 API 是 `NSBundle` 的 `bundleForClass`。这些 API 用于在不关心 bundle 结构的情况下处理框架的资源。

在 iOS 12 之前，运行时需要框架的二进制文件来发现 bundle，但在进程运行时，可合并框架内部将不再包含二进制文件。好消息是！在 iOS 12 中，我们添加了一个钩子（hook）来支持这种场景下的查找。这意味着，如果你依赖 bundle 查找支持，就应该将最低部署版本更新到 iOS 12 或更高版本，才能使用可合并库。但如果你不依赖这些 API，就可以使用新的链接器选项 `-no_merged_libraries_hook` 来禁用此支持。这样你就不需要更新 App 的部署版本。如果你正在合并的框架不包含 bundle 资源，也可能不需要 bundle 钩子。如果是这种情况，你仍应考虑添加此选项，以改善启动时间性能。在整个讲座中，我提到了一些新的链接器选项。这些选项仅适用于新版链接器。但如果你仔细观察工具链内部，会发现存在两个静态链接器。为了向后兼容，旧版链接器仍然受支持。最值得注意的是，旧版链接器仍可以为 armv7k 构建，但新版链接器不行。最后一个支持 armv7k 架构的平台是 watchOS 8。如果你不需要部署到 watchOS 8 或更早版本，请将部署版本升级到 watchOS 9 以使用新版链接器。我已经介绍了如何在自己的 App 中构建和使用可合并库，但如果你想将可合并库分发给其他人使用呢？你可以通过在 Xcode 或 Swift Package Manager 中创建一个 XCFramework 来实现。这允许你构建包含元数据的框架用于分发。当其他开发者使用该框架时，他们可以自行决定是否启用合并。可合并元数据大约会使 dylib 的大小翻倍。但这不会影响 App 的大小，因为元数据会随着可合并库在构建 App 后被一并丢弃。否则，在将这类库嵌入 App 时，元数据也会被剥离，以防体积膨胀。我已经介绍了可合并库的一些细微之处。现在我来分享我们的建议。将对合并后二进制文件的依赖设置好，是实现无缝采用的关键。这对任何链接依赖而言都是必要的。如果你在脚本阶段将库提供给期望二进制文件的工具，这一点就尤为重要。静态链接器只合并直接依赖项。因此，要想合并更多的可合并库，你就应该将它们设置为显式的链接依赖项。合并相关设置会指示 Xcode 构建系统从磁盘中移除框架的二进制文件。如果这不是你的本意，就会产生副作用。因此我们建议在 Xcode 目标级别启用这些设置。最后，为了在优化性能的同时最大限度地提升生产力，请考虑将任何可以变为可合并库的静态库更新为动态库。

可合并库提供了便利性和灵活性。在自动和手动两种工作流程下，你都可以随时重构和添加可合并库，同时将必要的库保留在磁盘上。这种灵活性在逐步采用或进行性能剖析时非常有帮助。将可合并库应用于框架和可执行文件目标时，它会在体积、构建和运行时方面带来改进。你可以通过使用自动配置让构建系统合并所有直接框架依赖项；而当你需要挑选哪些依赖项来合并时，则可通过手动模式来完成。最后，在更新你的项目以使用可合并库时，请确保这些库的所有依赖者都依赖的是合并后的二进制文件，而不是那些会被移除的库。关于可合并库的文档，请参阅《配置项目以使用可合并库》。要了解有关静态和动态链接的更多信息，请观看讲座《快速链接：缩短构建和启动时间》。我们非常期待看到可合并库将如何运用到你的项目中。感谢你的参与。
