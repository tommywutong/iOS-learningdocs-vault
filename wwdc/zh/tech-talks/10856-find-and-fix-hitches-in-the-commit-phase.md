大家好，我是 Charles Circlaeys。在本演讲中，我们将深入探讨渲染循环（Render Loop）提交阶段中的滚动动画卡顿（hitch）问题。

iOS 使用渲染循环来显示你的视图（view）。触摸事件被发送到你的 App，App 通过改变视图来响应，而 iOS 会将这些视图渲染到显示器上。

我们将重点关注在渲染循环的提交阶段发现并修复动画卡顿。

要了解整个渲染循环以及什么是卡顿，请观看视频“探索 UI 动画卡顿与渲染循环”。我们首先会探讨什么是提交事务（commit transaction）……

使用 Instruments 发现卡顿……

然后分享我们的建议，以避免提交卡顿。让我们先定义一下提交事务。这里有一个例子，展示了一个 App 的视图层级结构（view hierarchy），它正在等待事件。接收到触摸事件后，某个视图会做出响应，通过更改某些子视图（subview）的背景色或 frame（框架矩形）来处理该事件。

系统会记录下这些子视图需要在下一个提交事务期间进行布局（layout）或显示（display）。

在提交事务期间，需要显示或布局的视图会通过调用 `drawRect` 或 `layoutSubviews` 进行相应更新。

让我们看看提交事务包含的不同阶段。一共有四个步骤：布局阶段、显示阶段、准备阶段，最后是提交阶段。

在布局阶段，每个需要布局的视图都会调用 `layoutSubviews`。你可以通过更改视图位置、添加或移除视图，或者显式调用视图的 `setNeedsLayout` 来标记需要布局。

在显示阶段，每个需要显示的视图都会调用 `drawRect`。你可以通过向视图层级结构添加重写 `drawRect` 的视图，或者显式调用 `setNeedsDisplay` 来指示需要显示。在准备阶段，之前尚未解码的图像会在这个步骤中被解码。对于大图像来说，这种操作可能相当耗时。

此外，如果图像是 GPU 无法直接处理的色彩格式，它也会在此步骤中被转换。这需要复制图像，而不是发送指向原始图像的指针，从而消耗额外的时间和内存。要了解更多关于优化 App 中图像的内容，请观看“图像与图形最佳实践”视频。

最后，在提交阶段，视图层级结构会被递归地打包并发送给渲染服务器。注意，深层嵌套的视图层级结构需要更长的时间来打包。

现在我们可以分析哪些调用可能代价高昂。我们可以看到，这个调用树源自一个提交事务，并且显示我们在 QSTEM CollectionViewCell 中一个名为 `updateTags` 的方法里花费了大约十毫秒。

让我们看看这个 App 的内容。

它由一个普通的 CollectionView（集合视图）组成，每个单元格（cell）使用 UIImageView 显示照片缩略图，使用 UILabel 显示一些文字，并使用自定义的 TagLabel 视图显示一些标签。让我们看看 QSTEM CollectionViewCell 类的实现，特别是这个方法被调用的位置。这里我们看到，`menuItem` 上有一个属性（property）观察者（observer）。

这个属性观察者会在两种情况下调用 `updateTags`：设置了有效的 `menuItem`，或者将其设为 `nil`。

在第一种情况下，我们会解析要显示的标签数组。在第二种情况下，我们会解析一个空数组来移除所有剩余的标签。现在让我们看看 `updateTags` 方法的内部实现。不出所料，如果标签数组为空，我们会从视图层级结构中移除所有视图。否则，我们会根据需要创建一个 StackView（叠放视图）。

然后，我们为每个标签创建或复用现有的 TagLabel。

之后，我们会移除任何未使用的现有 TagLabel，以防该单元格先前使用的标签比新设置的多。现在，既然我们更好地了解了事物是如何实现的，让我们回到调用作用域，看看潜在的问题。QSTEM CollectionViewCell 重写了 `prepareForReuse` 方法，该方法在单元格出列复用时被调用。在这个方法内部，我们将 `menuItem` 设为 `nil`。这样做会触发第二种情况，即从单元格的视图层级结构中移除所有之前的 TagLabel，而没有利用我们的复用实现逻辑。

这意味着，对于每个出列的单元格，我们都会移除之前所有的标签子视图，然后为显示所有标签而重新实例化每一个所需的视图。

这并非最优方案，而且可能就是导致卡顿的原因。解决办法很简单：我们不需要清空 `menuItem`，只需从实现中移除 `prepareForReuse` 方法即可。现在，当我们设置新单元格的 `menuItem` 时，我们可以利用可复用的逻辑，避免昂贵的视图层级操作。如果我们在修复之后记录一个新的 trace，会注意到检测到的卡顿数量与第一次 trace 相比大幅减少。Instruments 中的 Time Profiler 对于发现哪些代码耗时过长并导致卡顿非常有帮助。要了解更多关于 Time Profiler 的信息，请观看“在 Instruments 中使用 Time Profiler”视频。

在学习了如何使用 Instruments 分析应用之后，让我们讨论一些避免提交阶段卡顿的建议。

规则一：保持视图轻量。为此，请尽量利用 CALayer 上可用的、由 GPU 加速的属性，并避免 CPU 自定义绘制。在有充分理由时，务必衡量其性能。避免 `drawRect` 的空实现，因为系统必须做额外工作，这会在即将到来的事务中消耗额外的时间和内存。尽量复用视图，以避免像添加和移除这样昂贵的视图层级操作。关于移除视图，如果你需要在动画期间停止显示某个特定视图，请尽量利用视图的“hidden”属性。这要轻量得多。规则二：减少昂贵的冗余布局。只在需要更新布局时才依赖 `setNeedsLayout`。`layoutIfNeeded` 会延长当前事务的生命周期，并可能导致卡顿。大多数情况下，你可以等待下一个运行循环（run loop）来更新你的布局。尽量使用最少的约束，避免增加求解的复杂度。最后，视图只应使其自身或其子视图失效，而不应使其兄弟视图或父视图失效。否则，视图的布局会被再次递归地失效。我建议你观看下面提到的两场 WWDC 演讲，了解更多关于性能布局以及图像和图形最佳实践的细节。

既然你已经了解了提交事务的流水线，就可以避免昂贵的提交，并可以使用 Instruments 中新的动画卡顿模板来检测和调查卡顿。你学到了一些防止提交卡顿的策略，例如确保 `prepareForReuse` 不会带来额外工作、保持视图层级结构浅而轻量，以及避免昂贵的冗余布局。另外，请务必在“揭秘并消除渲染阶段中的卡顿”视频中了解渲染循环的下一个阶段。谢谢。
