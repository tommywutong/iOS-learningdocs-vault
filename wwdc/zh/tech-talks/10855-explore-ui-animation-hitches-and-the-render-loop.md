大家好，我是 Patrick，在 Apple 的一个性能团队工作。今天我们将讨论你 App 中的滚动和动画卡顿（hitch），并详细查看渲染循环（Render Loop）。

首先，我们大致了解一下什么是卡顿。然后，我们将讨论渲染循环以及可能发生的不同类型的卡顿。

最后，我们将讨论如何测量卡顿。

那么首先，什么是卡顿？在你的 App 中，用户可能会用手指在屏幕上拖动来滚动。他们可能会点击一个按钮并期望得到反馈，或者在层级结构中的视图之间进行过渡。这些动画建立了用户与屏幕上内容之间的视觉联系感。

动画卡顿可能导致动画中的跳变并打破这种联系，从而引发困惑而不是愉悦。

卡顿是指任何帧（frame）晚于预期时间出现在屏幕上的情况。让我们看看滚动集合视图的一个常见例子。

这里我们有一个膳食计划 App，它帮助我们精选最爱的食谱。当用户向上拖动手指时，滚动视图会通过向上移动内容来响应。但在滚动过程中，我们注意到内容出现了跳变。

如果我们逐帧查看，可以看到在前三帧中，手指随着内容一起移动，但在下一帧中，内容似乎停滞了。这是因为第三帧实际上被重复了，在显示器上多停留了一帧。最后，第四帧到来，它似乎向前跳到了手指所在的位置。

第三帧被重复是因为第四帧来晚了，用户因此看到了一个卡顿。

卡顿是由于渲染循环未能按时完成一帧而导致的。所以让我们来看看渲染循环。

渲染循环是一个持续的过程，通过这个过程，触摸事件被交给 App，然后 UI 的变更被发送到操作系统，在那里完成帧的最终处理。它是一个循环，以设备的刷新率运行。

在 iPhone 和 iPad 上，刷新率为每秒 60 帧，这意味着每 16.67 毫秒可以显示一个新帧。在 iPad Pro 上，刷新率为每秒 120 帧，这意味着每 8.33 毫秒可以显示一个新帧。

在一帧开始时，硬件会发出一个名为 VSYNC 的事件。VSYNC 表示新帧必须准备好的时间。我们在显示轨道中把它们高亮显示，这样就能很容易地看到截止时间。渲染循环与 VSYNC 同步。它必须沿途到达检查点才能准备好一帧。

它分为三个阶段。第一个阶段在你的 App 中，事件在此被处理，UI 被变更。这项工作必须在下一次 VSYNC 之前完成，以便下一阶段可以开始。下一阶段发生在一个名为渲染服务器（render server）的独立进程中。这是你的 UI 真正被渲染的地方。这个阶段也必须在下一次 VSYNC 之前完成，这样帧才能被显示，这是第三也是最后一个阶段。

关于三阶段过程的一个重要说明是，帧在显示之前要经过两个帧的处理。我们称之为双缓冲（double buffering），但还有另一种模式。为了避免卡顿，系统可能会切换到三缓冲（triple buffering），即给渲染服务器多一帧的持续时间来完成其工作。由于这是一种后备模式，我们在讨论渲染循环中的卡顿时，将专注于双缓冲。

总的来说，整个渲染循环由五个阶段组成。循环从第一阶段开始，即事件阶段。在这里，你的 App 处理触摸事件并决定是否需要对 UI 进行更改。接下来是提交阶段。在提交阶段，你的 App 更新其 UI，并将其提交给渲染服务器进行渲染。在下一次 VSYNC 时，渲染服务器接收该提交，并在渲染准备阶段准备好在 GPU 上绘制。在渲染执行阶段，GPU 将你的 UI 绘制成最终图像，以便在下一次 VSYNC 时，该帧可以显示给用户。

每个阶段对于每帧流畅的用户体验都至关重要，即使是渲染工作也不例外。尽管它发生在一个独立的进程中，但它是代表你的 App 在工作，因此你有责任确保你的图层树（layer tree）能够被及时处理和绘制。为了进一步理解这一点，让我们看一个例子。

在这个例子中，我们将跟随这个帧通过渲染循环，看看沿途的每个阶段。首先是事件阶段，App 将在此接收事件。这些事件包括触摸、网络回调、键盘按下和定时器等。App 可以通过更改其图层层级结构（layer hierarchy）以任何方式响应这些事件。例如，App 可以更改图层的背景颜色，甚至更改图层的大小和位置。

但是，当 App 更新图层的 bounds 时，Core Animation 也会调用 `setNeedsLayout`。这会识别出所有需要重新计算布局的图层。

系统会合并这些“需要布局”的请求，并在提交阶段顺序执行，以减少重复工作。

如果需要任何布局，提交阶段将在事件阶段结束后自动开始。首先，系统会获取所有需要布局的图层，并从父图层到子图层逐个进行布局。

布局是一个常见的性能瓶颈，请记住你的 App 只有几毫秒的时间来完成这项工作。某些视图还需要自定义绘制，例如标签、图像视图或任何重写了 `drawRect` 的视图。如果这些视图需要视觉更新，它们必须调用 `setNeedsDisplay`。与布局类似，系统会合并这些请求，以便在所有布局完成后一次性执行。

在绘制过程中，每个自定义绘制图层都会获得一个纹理支持的 Core Graphics 上下文，它们会绘制到该上下文中。

对于 Core Animation 来说，这些图层现在只是图像。现在，所有图层都已完成布局和绘制，整个被修改的图层树被收集并发送到渲染服务器进行渲染。

现在我们进入了渲染服务器，它负责将我们的图层树转换为实际可显示的图像。在准备阶段，渲染服务器遍历 App 的图层树，并准备一个 GPU 可以执行的线性管线。

从顶层图层开始，它从父图层到子图层、再到兄弟图层依次进行处理，以便图层按从后到前的顺序排列。

接下来，这个线性管线被传递到 GPU，GPU 将每个图层合成到最终纹理中。有些图层可能需要更长的渲染时间，这是我们将很快讨论的另一个常见性能瓶颈。

很好。一旦 GPU 执行完毕并渲染出右侧的图像，它就可以在下一次 VSYNC 时显示了。

渲染循环的每个阶段都对性能敏感，并且有截止时间。截止时间就是下一次 VSYNC。为了达到目标帧率并保持低输入延迟，整个过程实际上是每帧并行发生的。

这样，管线就变得并发，我们的 App 可以在系统渲染前一帧的同时准备新的一帧。这就是为什么任何错过截止时间的情况都如此重要。

现在你了解了渲染循环的工作原理，让我们深入了解你在 App 中可能会看到哪些类型的卡顿。

主要有两种类型：提交卡顿（commit hitch），它发生在 App 进程中；以及渲染卡顿（render hitch），它发生在渲染服务器中。

提交卡顿是指 App 处理事件或提交耗时过长。

在这里，提交耗时过长，错过了截止时间，因此在下一个 VSYNC 时，渲染服务器没有东西可以处理，现在必须等待下一个 VSYNC 才能开始渲染。这导致我们延迟了帧的交付时间一帧。以毫秒计算，在 iPhone 或 iPad 上这是 16.67 毫秒。我们将这段延迟时间称为“卡顿时长（hitch time）”，并以毫秒为单位进行测量。

如果提交工作耗时更长，超过了下一个 VSYNC，那么该帧将延迟两帧，即 33.34 毫秒。

这意味着用户有 33.34 毫秒没有看到平滑的滚动。

我们在之前的幻灯片中看到了卡顿时长。在讨论单个卡顿时，它非常有用，但在讨论持续时间更长的事件（如滚动、动画或过渡效果）时，可能会变得难以处理。

首先，除非每次滚动或动画耗时完全相同（因此帧数也完全相同），否则很难进行比较。

更糟糕的是，iOS 设备并不总是更新屏幕。如果没有提交发送到渲染服务器，就不会提交新帧。这使得跨测试和设备比较卡顿时长变得更加困难。因此，我们使用一个名为“卡顿率（hitch time ratio）”的指标。卡顿率是一个时间间隔内的总卡顿时长除以其持续时间。由于它已相对于总时间进行了归一化，因此我们可以跨不同体验进行比较。它以每秒卡顿毫秒数来衡量，表示设备每秒卡顿的毫秒数。要了解如何使用此指标来衡量你自己的 App 性能，请查看“MetricKit 的新功能”。要了解如何在你的测试套件中跟踪卡顿率，请查看“使用 XCTest 消除动画卡顿”。最后，让我们看一个可以使用卡顿率的例子。

这里我们有 30 帧，在 iPhone 上相当于半秒的工作量。每帧都达到了截止时间，用户没有看到任何卡顿。卡顿时长为零，卡顿率也为零。

但现在我们看到底部的显示轨道上有不连续的间隔。

有些帧在屏幕上停留的时间比其他帧长，一些提交和渲染导致了卡顿。如果我们把这些卡顿时长加起来，得到 100.02 毫秒。在半秒内，我们的卡顿率为每秒 200.04 毫秒。这只是一个例子。总的来说，以下是我们在 Apple 工具中推荐和使用的目标卡顿率。尽管目标是每秒零卡顿毫秒，但任何低于每秒五卡顿毫秒的情况都可以认为是良好且用户几乎察觉不到的。在每秒五到十卡顿毫秒之间，用户会注意到一些中断，这些情况应该被调查。超过每秒十卡顿毫秒，卡顿会严重影响用户体验，你应该立即调查如何优化你的渲染循环。
