其中一些改进你可能几乎不会注意到，只会感觉到一些小小的烦恼消失了，所以我们先来看看一些比较小的变化。

举例来说，以前如果你想在一个可选类型上使用 some 或 any，你必须给它加上括号。

这种行为源自 Swift 的运算符优先级规则，但确实有点过于死板。所以，在 Swift 6.4 中，你可以直接去掉那些括号，编译器会把它理解为唯一说得通的那种含义。

现在，如果你悄悄忽略了从一个 Swift 并发任务中抛出的错误，你会收到一条警告，提醒你要么在任务里处理这个错误，要么保存这个任务，稍后再检查错误。而且，之前那条"不能在 defer 块里调用 async 函数"的限制现在也没有了。如果你有一个类，因为有一个 weak var 属性而必须使用 @unchecked Sendable，现在你可以把这个属性改成 weak let，让它变成不可变的，这样就不会妨碍你使用 Sendable 检查了。

或者，如果某个类型不应该是 Sendable 的，你可以用新的波浪号 Sendable 语法（tilde Sendable）明确地声明这一点。这样做还有一个额外的好处，就是不会阻止子类成为 Sendable。

而且，一个混合了 internal 和 private 属性的结构体，现在会有第二个逐成员初始化方法，你可以在项目里的其他文件中使用它。不过，也有一些变化你肯定会注意到。

在过去二十年里，Apple 生态系统一直在成长，随着它的成长，你 Swift 代码里的可用性标注也跟着变多了。去年，Apple 通过统一各操作系统发行版的版本号，开始着手解决这个问题。现在，Swift 把这一点又向前推进了一步，让你可以把所有这些平台名称压缩成一个："Any Apple OS"。所以，如果可用性在你关心的所有平台上都是一致的，你就可以一次性指定所有这些操作系统；如果有一些例外情况，你可以用 anyAppleOS 来设定默认值，然后针对例外情况再添加更具体的标注。而且，如果你想把某段代码整体编译排除掉，这个方法在 #if os 条件里也同样适用。

另一个随着时间不断变化的东西是 API。

随着 API 的演进，旧的 API 有时会被标为已废弃，提示你应该迁移到更新的版本。但有时候你没法立刻这么做，可能新的 API 变化很大，你需要时间去适配。

要是能暂时关掉这些警告，又不影响项目里的其他部分，那不是挺好的吗？现在你可以做到了。@diagnose 标注可以让你在某个特定的声明内部，改变特定警告的行为。所以，你可以告诉 Swift 忽略 deprecated declaration 这个警告组，让这一类警告在那一处地方消失。

你也可以用它来有选择地启用一些默认关闭的警告。

举例来说，你可以在安全关键的函数里打开严格内存安全检查，确保你已经审查过它们对不安全 API 的使用。

或者，你也可以把某些警告当作错误来处理。

在这里，我们把将来会变成错误的警告，现在就升级成了错误。

所有这些都给了你很大的灵活性。

Swift 6.3 还有一个新特性，可以更好地处理"两个模块里有同名 API"这种情况。举例来说，Rocket 模块里可能有一个类型，表示一枚真实的、一百米高的 SaturnV 火箭，而 GiftShopToys 模块里则有一个类型，表示一个儿童尺寸的 SaturnV 模型。如果你在同一个文件里导入了这两个模块，Swift 就没法分辨你想用的是哪一个，于是就会给你报错。

发生这种情况时，你一直都可以用点语法来让代码更清楚：Rocket.SaturnV 会先找到 Rocket 模块，然后在里面查找类型 SaturnV，完全不会注意到别处还有另一个 SaturnV。

这通常是可行的，但也有一些棘手的情况会让它失效。举例来说，如果 Rocket 模块里同时还有一个类型也叫 Rocket，会发生什么？我来告诉你会发生什么：Swift 会优先把它当作类型名而不是模块名，所以它会认定你说的是类型 Rocket，然后到它里面去找一个叫 SaturnV 的成员。

当它找不到时，就会给你报错。Swift 6.3 对这个问题有一个解决方案：只要把那个点改成双冒号就行。这种新语法叫做模块选择器（module selector），左边的名字总是会被当作模块名来处理。所以 Swift 会忽略类型 Rocket，直接进入模块 Rocket，从那里开始，它就能毫无困难地找到你要找的类型。这种语法也可以用在方法名或属性名上，如果一个类型从两个不同模块的扩展里获得了同名的方法，这就很方便了。毕竟，调用错方法真的会毁掉一个人的一整天。

现在，当你无法控制的两个模块之间出现冲突时，模块选择器就非常有用了。

比如说，如果 SwiftUI 和你正在使用的数据库包里都有一个叫 View 的类型，模块选择器真的能帮你省不少麻烦。

在宏展开和其他自动生成的代码里，防御性地使用模块选择器也是个好主意，因为你不知道项目里还导入了什么别的东西。但是，我们不建议你故意设计出会产生名称冲突的 API，然后依赖模块选择器来区分它们。即使你的代码没有歧义，一些错误信息和文档也可能仍然会让人困惑。

所以……不要这么做。

看完了这门语言的新特性，接下来请 Evan 来告诉大家一些重要库的更新。

所有这些语言层面的改进都有一个共同的目标：帮助你准确地表达出你的意思，而不带多余的噪音。同样的目标也延续到了你每天都在用的这些库的更新中。

标准库、Swift Testing、Subprocess，还有 Foundation。

我们先从标准库的更新说起，具体来说，是一些用于任务取消、字典变换和文件路径操作的新工具。

在开始任何开销较大的工作之前，检查任务取消状态很重要，但有些时候，我们其实希望即便任务已经被取消了,也要完成这项工作，比如把数据写完到磁盘，以避免文件损坏。

现在你可以使用任务取消屏蔽（task cancellation shield）了。在这个屏蔽区域内部，任务取消检查始终返回 false。重要的是要让这段区域保持简短，专注于完成或回滚你已经开始的工作。字典的值映射也得到了更新。mapValues 只会把旧的值传给映射闭包，所以如果你需要用键来计算新的值，就得手动构造一个新字典。

现在，我们可以调用 mapKeyedValues，它会把键和旧值都传给映射闭包，用来计算新的值。

程序经常需要处理文件路径。不同平台表示文件路径的方式之间存在一些细微差异，这会让正确处理它们变得棘手。今年，我们在标准库里加入了一个新的 filepath 类型，它基于 Swift System 里的类型，让处理文件路径更容易做对。

Swift 6.4 中的测试功能让你对测试的行为拥有更多控制权，可以呈现非致命性的问题，并动态跳过测试用例。

现在你可以设置用 Issue.record 记录下来的问题的严重级别了。

把它设为 warning，意味着你可以呈现出测试用例里值得调查、但不值得阻塞 CI 工作流的问题。

你可以通过调用 Test.cancel API 来动态取消测试。

这在参数化测试里特别强大，你可以取消不该运行的单个参数，而不是把它们跑到底或者让整个测试失败。

有时候你要处理的是一个不稳定的测试。swift test 命令新增了一个功能，可以重复运行一个测试，直到它通过或失败为止，同时你还可以控制最大重复次数。如果你指定要重复运行直到测试通过，那么只有失败的测试会被重新运行，这样就不会重复运行已经通过的测试，从而节省时间。

许多项目都有基于 XCTest API 构建的大型测试套件工具。在 Swift 6.4 中，当从 Swift Testing 里调用时，XCTest 的断言失败现在会被报告为测试问题。

这意味着你可以迁移到 Swift Testing，而不用担心在迁移过程中意外丢失测试覆盖率。而且这种互操作性反过来也同样有效，Swift Testing 的 API，比如 #expect 宏，在从一个 XCTestCase 里调用时也能正常工作。这意味着你可以用 Swift Testing 构建辅助 API，而且无论是从 XCTest 还是从 Swift Testing 调用，它们的行为都是一致的。

如果你在一个已有的项目里工作，你可能已经在从 Swift Testing 里调用 XCTest 断言，反过来也是如此。

为了让这种过渡更顺畅，这些问题默认会被报告为警告。你可以在 Xcode 构建设置里选择让它们升级为测试失败。

想更深入了解 Swift Testing 的互操作性和迁移策略，请查看"迁移到 Swift Testing"。

去年，我们发布了 Subprocess 包，里面包含了用于启动子进程的现代 API。今年，我们要发布 Subprocess 1.0，它融入了大家在实际使用中反馈的意见。

这次 API 的改进包括一个简化的执行类型、改进的错误处理，以及方便地对进程输出进行流式处理的便捷 API。

跨平台支持也得到了大幅改进，包括针对特定平台的进程文件描述符和终止状态，以更准确地反映不同平台上的语义。这里是 Subprocess 1.0 中改进后 API 的一个例子。

在调用 run 方法启动一个子进程时，标准输出流和标准错误流可以作为 AsyncBufferSequence 包含在执行对象里。这种模型保证每个流只会被创建一次。AsyncBufferSequence 上新增的 strings() 方法，让你可以很方便地逐行读取子进程的输出。

这个 API 遵循字位簇（grapheme cluster）边界，所以你不用担心多字节字符被拆开。

最后，我们来说说 Foundation 方面的改进。

ProgressManager 是 Foundation 中一个用于进度报告的新类型。它的设计能够很好地配合 async/await 风格的并发工作，把进度的组合与进度的报告清晰地分离开来，并提供了一种结构化、类型安全的机制来附加额外的元数据。

我们两年前宣布了 Swift-Foundation，这项工作致力于把 Foundation 迁移到一个安全、一致、跨平台、用 Swift 编写的代码库。今年，我们继续推进这项工作，用现代 Swift 取代了几十年历史的 Objective-C 代码。

今年，我们对 Data 的更多部分做了现代化改造，带来了全方位的改进，包括更快的 span 访问、相等性检查、迭代和变更操作。

在 Apple 平台上，Data 和 NSData 之间的桥接也变得更快了。

NSURL 和 CFURL 被统一成了一个单一的 Swift 实现。

利用 Swift，可以让这些类型运行得更快、占用更少内存。像 Foundation 这样体量庞大、历史悠久的库之所以能够迁移，正是因为 Swift 具备语言互操作性。

你可以用 Swift 添加全新的 API，也可以在不改变 API 表面的情况下，把现有 API 的实现迁移到 Swift。

Swift 的设计目标是，即便你只是用最直接、最富表现力的方式实现了你的逻辑，也能获得出色的性能。

但当你要做大量计算，或者运行在嵌入式系统这样的受限环境里时，有时候把代码写得复杂一点，在关键时候多榨取那么一点点性能，是值得的。

你通常不会需要这些进阶性能特性，但当你真的需要的时候，你会庆幸自己拥有它们。

我要重点讲讲我们今年在两个方面所做的工作：显式控制优化器的决策，以及进一步扩展所有权系统，以安全地防止不必要的复制。

Swift 编译器的优化器会应用几十种技术来让你的代码运行得更快，但其中一些威力最强的技术,如果应用不当，反而会适得其反。

这些技术涉及复制代码，以便针对特定情况进行定制，但如果这种定制并没有带来收益，你最终得到的程序可能会变得更大、更慢，而不是更小、更快。

举例来说，编译器执行的最重要的优化之一，就是内联（inlining）：把函数调用替换成它们的实现，然后针对具体的调用点对这些实现进行优化。

当内联有效果时，程序就能用更少的工作量得到同样的结果，但如果没有效果，它只会让二进制文件变大，却不会让程序变得更快。为了防止这种情况发生，优化器会分析函数和调用点，来判断内联是否可能有效果，但有时候它还是会做出错误的判断，所以你可能需要一种方法来强制决定这件事。

Swift 早就有一个 @inline(never) 标注，可以完全禁止内联，当你知道内联某个函数永远不会有好处时，这个标注就很有用。在 Swift 6.4 中，现在有了与之对应的 @inline(always) 标注，它会强制编译器进行内联，即便优化器并不确定这样做是不是个好主意。

不过有时候它还是做不到，比如当你调用一个可能被重写的对象方法时，所以对于类的方法，可以考虑把 final 和 @inline(always) 搭配使用。

另一个重要的优化是特化（specialization）：针对某个具体类型克隆一个泛型函数，消除泛型带来的开销，并且常常能带来进一步的优化。只有当优化器知道你会把某个函数用在那个类型上时，特化才会有帮助，但有时候，尤其是在库里，编译器没法看出这个函数将会怎样被使用。

Swift 6.3 引入了 @specialized 标注，让你可以直接控制这一点。

在这个标注内部，你写一个 where 子句，约束部分或全部泛型参数，Swift 就会生成一个满足这些约束的函数特化版本。

所以，如果你有一些运行较慢的泛型代码，它经常被用在一两个特定类型上，你就可以让 Swift 知道需要优先处理它们。不过，我们在性能调优方面做出的最大改进，是针对所有权系统的。

要理解我们做了什么，我们先来回顾一下我们已经拥有的东西。

Swift 里很多性能问题归根结底都是不必要的数据复制。你在一个地方有一份数据，需要在另一个地方用到它，于是你就把数据复制到新的存储空间里。有时候这些组件很大，比如你 App 的 model 层和 view 层，有时候它们很小，比如 for-in 循环两侧的那两个变量，但基本模式是一样的。

解决因为复制而导致的变慢的方法，是要认识到，在某些情况下，复制其实是没有必要的。如果你知道这份存储会一直保持分配状态，并且两个使用它的组件都会遵循 Swift 的独占访问规则，不会去修改它们都能访问到的数据，那么你就不需要复制这份数据，你只需要授予对现有存储的访问权限就行了。避免复制最简单的方法，就是把数据放进一个对象里，然后把这个对象传给另一个组件。

这么做通常已经够用了，但它并没有完全消除这个问题。毕竟，对象是引用计数的，传递一个对象会改变它的引用计数。释放和保留一个对象的开销比复制一个大的值要小，但对于性能最敏感的代码来说，这可能还是太慢了。

当对象这个选项不适用时，传统上你就得改为传递一个指向该存储的 UnsafePointer。但这样做的问题就写在它的名字里：UnsafePointer 是不安全的。像这样共享存储之所以是安全的，仅仅是因为两个组件都在遵守某些规则，但编译器对这些规则一无所知，也没法确保双方都会信守自己那一半的约定。

组件 1 可能会修改组件 2 原本期望保持不变的数据。或者它可能会在组件 2 还在使用这份存储的时候就把它释放掉。

你又回到了一个没有内存安全的世界，就像 C 语言曾经那样。

所以几年前，我们开始着手研究一个更好的解决方案。我们把安全共享存储所需的那一整套保证正式化，称之为借用（borrow）。只要组件 2 在借用这份存储，两个组件就都只能读取它，不能写入。组件 2 必须先用完这份存储，等它用完之后，组件 1 才会重新获得完整的控制权。

变更（mutation）也类似，只不过另一个组件会被完全禁止访问这份存储。这确保了它不会读到修改到一半的数据，也不会因为另一个组件选择写回改动的时机不同而表现出不同的行为。而且，不管是借用还是变更，Swift 都能在编译期验证两个组件是否都遵守了这些规则。

但我们的目标一直都是，在不影响你编写普通 Swift 代码方式的前提下，支持这些进阶用例。这就需要对所有权特性进行谨慎、渐进的设计。这是一个持续多年的过程，而且至今还没有结束，但今年我们又向前迈出了几步。举例来说，Equatable、Comparable 和 Hashable 这几个协议现在可以用在 noncopyable 类型上了。

而且 Equatable 和 Comparable 也可以用在 non-escapable 类型上了。

这让那些针对性能和安全性做了调优的类型，也能享受到普通 Swift 类型所拥有的一些最通用的能力。关联类型现在也可以是 non-copyable 或者 non-escapable 的了。

这为高性能、协议驱动的开发打开了强大的新可能性，就像这里展示的 Iterable 协议一样。

它的元素类型是 non-copyable 的，而它的迭代器类型既是 non-copyable 又是 non-escapable 的。当然，这并不意味着你不能在这些地方使用可复制或可逃逸的类型，这只是意味着协议本身并不要求这样做。不过，这个 Iterable 类型看起来真的很好用，是吧？你是不是希望它是真的？好消息是，它真的是！在 Swift 6.4 中，for 循环支持一个新的 Iterable 协议。我们都熟悉并喜爱的 Sequence 协议，工作原理是把元素从序列里复制出来，而 Iterable 协议则让 for 循环可以改为借用它们。

这意味着它可以配合 non-copyable 的元素工作，而且在处理对象或写时复制类型时，也不需要执行引用计数。此外，它还可以在循环过程中选择性地抛出一个错误，就像 ASYNC Sequence 那样。不过，和任何借用一样，独占检查会禁止你在遍历 Iterable 的同时对它进行变更，这未必是件坏事，因为这在以前用 Sequence 时，常常是一个性能陷阱。正因为这种行为上的差异，for 循环会优先使用 Sequence 协议（如果可用的话），否则才会回退到使用 Iterable。

和 Sequence 很像，一个 Iterable 的工作方式是创建一个迭代器，供 for 循环从中获取元素。

但和 sequence 不同的是，它是分批获取元素的。for 循环会向迭代器请求一个 span 的元素，然后逐个遍历它们。然后再请求下一个 span，继续遍历。

当元素用完时，它会返回一个空的 span，这就会终止 for 循环。这种分批设计让循环的效率高得多，尤其是对于那些可以一次性把所有内容都放进一个大 span 里返回的类型来说。

Swift 6.4 还对访问器（accessor）做了一项重大改进。

要理解这一点为什么重要，来看看这个 UniqueBox 结构体。

它会自动管理一个指向大型值的指针，并提供一个计算属性来访问它。不幸的是，按照目前的写法，这个属性存在一个严重的性能问题。我们来看看为什么。

假设你把一个包含 256 个 Int 的 InlineArray 放进一个 UniqueBox 里。InlineArray 顾名思义就是内联的，所以在一台 64 位设备上，这就是一个两千字节大小的结构体。这可不是你想经常到处复制的东西！这就成了一个问题，因为 get 和 set 的工作方式就是复制数据。要修改数组里的一个 Int，你得把整个数组复制出来，改完之后再复制回去。

这对你的性能可帮不上什么忙！好在，现在有了一个更好的选择：你可以把 get 和 set 换成 borrow 和 mutate。新的 borrow 访问器让你可以只读地访问共享存储,而不需要复制它，而 mutate 访问器则让你可以独占地就地修改它。切换过来之后，Swift 就可以直接在原始数组里修改这个元素，而不需要复制任何东西。

而且，作为一个不错的额外好处，这些新的访问器还意味着 UniqueBox 也可以处理 non-copyable 的值了。borrow 和 mutate 访问器对性能和表达力都有很大帮助，我们很高兴它们已经可以供大家使用了。不过，这个 UniqueBox 类型看起来真的很好用，是吧？你是不是希望它……好啦好啦，你知道接下来是什么套路，我不会再来这一套了。是的，UniqueBox 是标准库里现在真实存在的一个类型。还有一些其他的新 API，可以让你不用再写不安全的代码了。"Unique Array" 很像一个普通的 Swift 数组，只不过它是 non-copyable 的。这意味着你可以存储 non-copyable 的元素，避免引用计数的开销，同时又不局限于固定大小。

withTemporaryAllocation 函数使用 OutputSpan 而不是 UnsafeMutableBufferPointer，来确保临时内存被安全地处理。

Continuation 类型会在编译期检查你是否只恢复了它一次，这让它比 CheckedContinuation 更安全，同时又和 UnsafeContinuation 一样高效。另外，我还想再跟大家介绍一对类型，但它们并不是某个现有 API 的改进版本，它们为这门语言带来了全新的能力。Ref 有点像 Span，只不过它对应的是一个值,而不是多个值。它有点像是一个用来存放借用或变更的容器，可以存储在变量里，可以在函数之间传递和返回，还可以用在泛型类型里。你可以通过借用存储，从一次读访问创建出一个 Ref 类型的实例，或者用前缀 & 符号，从一次写访问创建出一个 MutableRef 类型的实例。这些类型可以用来创造出以前根本没法写出来的新 API，比如一个返回其某个属性的 Mutable Ref 的方法，但它们也可以用来解决性能问题。

举例来说，来看看这个 updateCount 函数。它每次需要递增某个字典键的值时,都要重新查找一次这个键,尽管这个键其实一直都是同一个。你通常会想把这种重复的工作从循环里提出来，这样只需要做一次就行，但在这之前，唯一能做到"查一次字典，然后把它保持打开一段时间"的办法，就是把循环挪进一个函数里，再把这次查找结果当作一个 inout 参数传进去。这算是个挺晦涩的技巧！MutableRef 给了你一个更好的办法。现在你可以在循环开始之前，先从这次字典查找创建出一个 MutableRef，然后在你想变更这个字典条目时使用它。Ref 是 non-escapable 的，所以 Swift 知道，一旦这个变量离开作用域，这次访问也就结束了。所有这些新的所有权特性结合在一起，让加速你性能最敏感的代码，变得比以往任何时候都更安全、更简单。所有权系统并不是唯一还在进行中的工作。下面把话筒交还给 Evan，来讲讲 Swift 的未来。我们今天介绍的这些特性都是在开源环境中开发的，它们改善了整个 Apple 操作系统、Linux、Windows 等等平台上的整体体验。这里还有一些正在开源社区里进行的未来发展方向，欢迎大家参与进来。
