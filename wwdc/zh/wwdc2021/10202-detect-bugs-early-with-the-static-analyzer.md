我感到很欣慰，这个 bug 在我开发 App 的过程中就被检测出来了。这是因为从一个被标注为返回非空值的 Objective-C 方法返回 nil，当该方法从 Swift 中被调用时（我的代码中就有这种情况），可能导致意外的运行时行为。值得庆幸的是，运行静态分析器在这个 bug 影响到我的 App 用户之前就揭示了它。在 Xcode 13 中，我们让分析器变得更好了，我们还为你准备了一些全新的检查项。分析器现在可以捕获你代码中更多的逻辑 bug。它可以检测无限循环和冗余代码，例如不必要的分支条件。它可以报告断言中的副作用，而在 C++ 代码中，它可以捕获使用 move 和 forward 运算符时的错误。这些新检查中的一部分是对 Apple Clang 编译器的开源贡献。让我们来看一些这些新检查可以捕获的 bug 示例。一般而言，使用断言来验证你对代码的预期是一种好习惯。但是，你必须确保断言没有副作用，例如写入变量或内存。例如，考虑这里展示的代码片段，它遍历一个天体数组并统计其中有卫星的天体数量。它有一个 NSAssert，检查有卫星的天体数量是否小于或等于行星的数量。但这个断言有一个副作用：递增了跟踪有卫星天体的计数器。像这样的更新可能会在 release 构建配置中丢失，因为在那种配置中断言可能被禁用以让你的代码运行得更快。所以这段代码在 release 构建中可能根本不会递增计数器。在开发过程中很容易错过这类 bug，因为它们不会在 debug 构建中显现。从 Xcode 13 开始，分析器可以找出你代码中的这类问题并予以报告。这项检查不仅适用于 NSAssert，也适用于 C 和 C++ 中的断言。这些 bug 很容易修复，你只需把副作用移到断言之外，如下所示。

无限循环是另一类常见的 bug。当循环包含复杂逻辑时，你可能见过它发生。例如，这里展示的嵌套循环试图用一个值填充一个二维网格。它隐藏了一个 bug：变量 value 被内层循环递增，而不是被实际的循环计数器 column 递增。分析器现在可以检测到这类错误并向你解释。

一旦你发现了它，这个 bug 非常容易修复。只需把 value 替换为 column。虽然这些检查发现的是简单的失误，但我们已经用它们找到了真实的 bug。现在你也可以使用它们，在开发 App 的过程中发现并修复 bug。Xcode 提供了许多自定义选项，用于微调分析器以适应你的开发工作流。你可以让分析器随项目的每一次构建一起运行，这需要在项目的构建设置中配置。要快速缩小到相关设置，请利用搜索功能。例如，使用 "analysis" 作为搜索关键字，我可以只查看与分析器相关的那些选项。

要启用 Analyze During 'Build'，你只需打开一个构建设置。与增量构建一样，分析只在被修改的文件上运行。这使得在代码更改后运行分析器既快速又容易。分析器提供两种分析模式：浅层（shallow）和深层（deep）。浅层模式更快，但会避免探索跨越多个函数的 bug。在构建和分析时间敏感的项目中使用这种模式。正如我之前提到的，分析器有用于发现不同类型 bug 的检查项，其中一些是需要主动启用的。你可以通过在构建设置中选择性地启用或禁用它们，来微调适合你项目的检查项。例如，如果你的项目包含安全关键代码，请启用针对安全问题的检查项。反过来，如果你发现某些问题与你的代码无关，你可以单独禁用不太有用的检查项，同时仍然受益于其他检查项。

你还可以分析单个文件而不是整个项目。从 Product > Perform Action 菜单中选择要分析的文件。用它来快速检查你的更改，甚至不需要构建你的项目。这在修改头文件时尤其有用，因为它会跳过重新分析所有导入该头文件的文件。Xcode 中的静态分析器可以在开发过程中非常早地揭示你代码中的 bug。单击一个按钮即可运行它，发现多种类型的 bug。并且别忘了根据你的工作流对它进行自定义。在 Xcode 13 中，我们进一步改进了分析器，并添加了许多用于发现逻辑 bug 的新检查项。使用分析器，在 bug 影响到你的用户之前修复它们。谢谢，祝你在 WWDC 的其余 session 中愉快！[欢快的音乐]
