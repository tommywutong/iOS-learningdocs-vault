大家好，我是 Anubhav，OS Performance Team 的工程师。今天，我很高兴与大家分享如何了解和消除 App 中的挂起。我将把这次演讲分为四个部分。首先，我们来理解“什么是挂起（hang）？”接着，我们将讨论挂起的常见原因以及在开发时需要注意什么。之后，我们将介绍可用于监控和诊断挂起的工具。最后，我们将学习消除挂起的常见策略，以及如何为你的 App 选择最佳方案。让我们直接开始。来看看我的新食谱 App——Desserted，一个教你制作我最喜欢的饮品和甜点的 App。这个芒果探戈冰沙看起来很棒。我点一下，看看是怎么做的。嗯。好像什么都没发生。哇。这比预期的时间长多了。App 卡住了，好几秒都无法接受任何触摸操作。

这种体验可以被描述为“迟滞”、“缓慢”或“卡死”。这可不是我或任何人希望用来描述自己 App 的词。在 Apple，我们把这种无响应的时段称为“挂起”。要理解挂起，以及 Desserted 中发生了什么，我们首先必须了解 App 的 main runloop（主运行循环）是什么。

主运行循环是 App 主线程进入的一个循环，用于运行事件处理程序以响应传入的事件，主要是用户交互。当用户与 App 交互时，运行循环会接收事件、处理事件，然后根据需要更新 UI。这一切都发生在运行循环的一次循环中，并且在主线程上。这个过程对每次用户输入都会重复。这就是主线程在一次运行循环的循环中的样子。

如果处理事件需要很长时间，用户输入和任何 UI 更新之间就会出现延迟。更糟糕的是，事件会被缓冲，并且在挂起期间无法由主线程处理。如果我在挂起期间与 App 交互，该事件不会被处理，直到当前的挂起结束……挂起会层层叠加。

一般来说，超过一秒的延迟看起来总会像挂起，不过较短的延迟也可能被感知为挂起。例如，滚动时半秒的延迟会让人感到突兀，但在进入视图时，同样的延迟却远不那么明显。

通过消除挂起，你的 App 会变得响应迅速、快捷和灵敏。

现在我们知道了什么是挂起，让我们看看通常是什么导致了它们。

当主线程上做了太多工作时，就会发生挂起。要确定具体是什么工作，我们必须查看主线程在处理事件时在做什么。这段时间可以分为两种情况：要么主线程本身忙于执行工作——这可能是一个长任务或多个短任务——要么主线程被另一个线程或系统资源阻塞。让我们首先看看导致主线程忙碌的常见原因。主动执行工作是指做了超出更新 UI 所需的事情，从而使主线程忙碌更长时间。

在 Desserted 中，Recipe View（食谱视图）只显示众多食材图片中的四张图片磁贴。如果主线程一次性加载所有食材图片，它将花费时间读取、准备和合成每一张图片。大部分正在进行的工作甚至不会影响用户看到的内容。

该视图只显示四张图片，只需立即生成这四张图片即可。

导致挂起的另一个原因是在主线程上执行不相关的工作。请注意，主线程服务于来自主调度队列的 block（代码块），但它也可以通过 `dispatch sync` 服务于来自其他队列的 block。每当一个队列通过 `dispatch sync` 同步到另一个队列时，另一个队列上的所有待处理 block 都必须在新入列的 block 之前执行。考虑一个拥有低优先级串行调度队列的 App，比如一个维护队列。如果主线程将某个 block 通过 `dispatch sync` 同步到 `maintenanceQueue`，它就必须等待该队列上所有待处理的 block 执行完毕，然后入列的 block 才能运行。只有一小部分时间花在了原本为主线程准备的工作上。

同样，如果一个 block 从另一个队列被调度到主队列，该 block 必须在主线程上执行。

即使该 block 是通过 `dispatch async` 入列的，情况也是如此。

导致挂起的另一个原因是使用了次优 API。完成一项任务的方法有很多种。请务必阅读 API 文档，以便为手头的任务使用最佳的 API。

Desserted 为食谱视图中的所有图片添加了圆角，尽管这样做也增加了进入此视图时的延迟。

要添加圆角，Desserted 使用基于位图的图形上下文将图片转换为位图，在该位图上应用 `UIBezier` 路径，然后将该位图转换回图片。这组操作是 CPU 密集型的，会占用大量内存，并且可能需要很长时间。这是因为这项工作使用了错误的硬件。我应该利用 GPU，而不是使用 CPU。

通过在图层（layer）上使用 CoreAnimation 方法，添加圆角既简单又即时。这只是使用错误 API 的一个例子。

现在我们已经了解了 App 主线程可能忙碌的一些常见原因，我们来探究一下它为什么会被阻塞。

同步 API 从被调用到返回期间会阻塞执行。如果 API 执行了大量工作或者可能长时间阻塞，则不应在主线程上使用这些 API。除了延迟之外，这些 API 还会增加额外的故障点。

一种情况是 App 的主线程向网络发起同步请求。对于使用 5G 的用户，可能没有任何延迟。对于网络速度较慢的用户，这可能需要更长时间。对于信号非常差的用户，这可能会无限期挂起。无法保证这会持续多久，这就是为什么应该避免在主线程上进行此类同步操作。

另一种阻塞主线程的方式是竞争系统资源，因为系统资源通常是受限的。文件 I/O 是最常用且竞争最激烈的系统资源之一。延迟取决于硬件以及同时发生的其他读写操作，这些可能是 App 无法控制的。因此，App 需要尽其所能，通过避免在主线程上进行 I/O 来防御挂起。

不支持并发的数据存储尤其成问题。如果主线程尝试从一个正在进行写入操作的数据存储中读取，那么该读取操作将被推迟，直到所有写入操作完成，而写入时间可能是无限的。

导致挂起的另一个原因是同步。根据定义，同步原语（synchronization primitives）会阻塞执行，因此限制并谨慎地从主线程进行同步非常重要。

它同步到的线程可能需要很长时间才能释放隐式或显式锁。以下是一些需要注意的常见原语，包括 `@synchronized` 指令、`dispatch sync`、`os_unfair_lock` 和 POSIX 锁。具体而言，要注意信号量（semaphore）的使用，因为它们不会传递优先级，并且可能会因抢占而延长挂起时间。一个常见的反面模式（anti-pattern）是试图通过等待信号量来使异步 API 表现得像同步 API。应始终避免在主线程上这样做。

另一种阻塞主线程的方式是执行工作、进行 IPC（进程间通信）或使用系统资源来获取不常变化的值。

在 Desserted 中，社交功能有一个图标，仅当我将某个联系人添加为好友时才会显示。每次进入此视图时查询所有联系人是一种检查方式，但这会带来不必要的开销和延迟，因为主线程会阻塞在框架上，而框架正在底层执行昂贵的操作。此外，我正在获取的值并不经常变化，因此频繁查询是不必要的，并且会给系统资源增加负担。

系统资源的状态，如 CPU、内存和存储，在很大程度上决定了何时发生挂起。实际使用中的不同硬件和设备条件意味着真实世界的场景将与在桌面上测试时遇到的场景显著不同。至关重要的是，你需要通过稳健的测试并使用支持的最旧硬件作为基准，来尽可能地防御这些情况。概括来说，挂起的原因是主线程上或代表主线程执行了太多工作。为了确保性能，App 的主线程必须专注于更新 UI 所必需的工作。

现在你已经了解了挂起的常见原因，让我们来讨论一些有用的工具，你可以在开发和生产环境中使用它们来监控和分类 App 中的挂起。

为了对挂起进行分类，你需要了解你的 App 在那段时间在做什么。Time Profiler 工具可以让你做到这一点，它会随时间显示你的 App 的调用栈，明确指出正在执行的内容。System Trace 工具则增加了更多上下文，提供有关系统调用、VM 故障、I/O 以及进程间和进程内交互的数据。更多信息，请查看 2016 年的“深入 System Trace”讲座。现在，我将使用 Time Profiler 和 System Trace 工具来找出导致 Desserted 挂起的原因。

捕获挂起的跟踪记录后，这是在 Instruments 中打开时的样子。在 System Trace 输出中，红线表示系统调用，紫色图表表示 VM 故障，水平蓝条表示主线程正忙于执行工作。下一步是查看这些工作是什么。Time Profiler 可以让你做到这一点。它通过聚合 4.7 秒挂起期间主线程的调用栈来呈现一个调用树。树中高亮的部分表明，这次挂起中有 4.6 秒是由于食谱视图中的 `loadAllMessages` 方法导致的。这个模式看起来很熟悉。Desserted 可能加载了比所需更多的图片。

一旦你的 App 发布，你可以使用 MetricKit 来收集实际环境中遇到的挂起的调用树。这使你能够根据客户最常遇到的问题来确定修复的优先级。要了解如何使用 MetricKit 处理挂起，请查看 2020 年的“MetricKit 新变化”讲座。我已经发布了 Desserted，并从 MetricKit 获得了一些挂起报告。让我们看其中一个，看看它是否与我们刚刚分类的挂起类似。

MetricKit 通过聚合挂起期间获取的调用栈来返回一个调用树。这个树格式与 Time Profiler 呈现的相似。

高亮部分表明这次挂起与我们刚刚在 Instruments 中调查的不同。这个是由于我添加的一个新的社交功能导致的，该功能阻塞在查询联系人的调度队列上。没有 MetricKit，我可能不会发现这个问题，它会在实际环境中持续存在。在修复挂起时，为你的 App 设定性能基线并量化其性能非常重要。Xcode Organizer 通过显示性能指标（包括按 App 版本显示挂起率的图表）来做到这一点。这在分类性能衰退时特别有用。有关 Xcode Organizer 的更多信息，请查看这两场讲座。

现在，让我们介绍一些可以用来修复 App 中挂起的常见策略。

每种策略都可以解决导致挂起的多种原因。要知道哪种修复方案对你的 App 最好，你需要考虑它们的副作用和权衡。

要消除和防御挂起，需要减少在主线程上完成的工作量。

这可以通过两种方式实现。第一种是优化已经在主线程上完成的工作以减少执行时间。第二种是以非阻塞方式将工作移出主线程，使其保持响应。让我们首先看看减少主线程执行时间的方法，从缓存开始。缓存是一种快速访问常用资源或先前查询值的绝佳方式。它们通常是内存存储，但如果需要在多次 App 调用之间持久化，也可以持久化到磁盘。以后可能需要的格式化资源，比如 Desserted 中的食材图片磁贴，是很好的缓存候选，因为每次需要时创建这些资源的代价很高。

通过将这些资源缓存在 `NSCache` 中，生成资源的开销被替换为快速的内存读取。这将消除我们在 Instruments 中看到的挂起。

拥有准确的缓存失效机制非常重要，以在保留过时数据和不断更新缓存之间取得平衡。这项工作应在次级调度队列上异步进行，以使主线程能及时响应事件。

通知观察者（Notification observers）是另一种减少主线程工作量的方法。它们允许你的 App 对值或状态的变化做出反应，而无需进行昂贵的按需计算。任何类都可以发布通知，甚至是你自己的类。要查找特定类的通知，请查看其 API 文档。要查找所有可观察的系统通知，请查看 Apple 开发者文档页面 `NSNotification.Name`。Desserted 中的社交功能就是一个很好的应用场景。

通过注册一个针对 `abDatabaseChangedExternally` 通知的观察者，主线程不再需要等待查询联系人。一旦通知到来，观察者就会被调用。在这种情况下，它将更新一个缓存值。

为了保持主线程的响应性，这些更新应该是异步的，这可以通过将处理程序 `dispatch_async` 到另一个队列来实现。

现在，我提供了与之前相同的功能，但没有出现我们在 MetricKit 日志中看到的挂起。消除挂起的另一种方法是将工作移出主线程。首先，我们需要确定这些工作应该是什么。通常，为 UI 提供关键信息的重要任务应保留在主线程上。此外，所有视图和视图控制器（view controllers）都必须在主线程上创建、修改和销毁。

然而，更新 UI 元素所需的计算可以卸载到另一个线程，并通过完成处理程序（completion handler）在主线程上执行实际的更新。当已知计算需要很长时间时，这种模式非常有用。其他不太重要的、维护性的或非时间关键的任务，应在另一个线程上异步执行。

然后，这些任务将以较低的调度优先级运行，并且可能比主线程上的任务花费更长时间完成。这是有意为之，体现了主线程只应执行关键工作的理念。

从主线程执行异步操作最直接的方法是使用同步 API 的异步版本。让我们以网络为例。

通过使用异步的 `NSURL` 方法来替代同步网络 API，App 将保持响应。异步 API 通常通过方法名中的“asynchronously”一词或存在完成处理程序来指示。

Grand Central Dispatch 是一种强大的多线程机制，在没有异步 API 变体，或者你想要移出主线程的代码是你自己的代码时，你可以利用它。Grand Central Dispatch 提供了简单的机制，可以将任何工作 block 移动到另一个线程，无论是同步还是异步。这使得 GCD 在消除大多数常见的挂起原因方面极为有效。

要在另一个线程上异步执行一个工作 block，请将该 block `dispatch_async` 到另一个调度队列。

可以通过调度回主队列，在异步 block 内添加一个完成处理程序。

Grand Central Dispatch 还允许你预热（pre-warm）计算。通过将一个任务 `dispatch_async` 到一个队列（比如 `prefetchQueue`），该任务将开始执行，同时主线程可以自由地做其他工作。当主线程需要这些结果时，它可以 `dispatch_sync` 到 `prefetchQueue` 上来等待任务完成。我们只是触及了 GCD 能力的表面。要了解更多，请查看 2017 年的“现代化 Grand Central Dispatch 用法”讲座。

让我们了解一下刚刚讨论的解决方案的一些权衡。缓存会使用内存，因此你应该注意其大小，以避免内存大幅增长。同时，确保有一个准确的失效机制也很重要，这样值就不会过时。通知可能会很频繁。在观察一个通知时，考虑该通知触发的频率非常重要。在处理之前添加过滤器或合并多个通知可以减少 CPU 使用。在使用异步 API 时，了解所涉及的操作是否应该被异步处理非常重要，特别是要首先检查它是否对 UI 更新至关重要，因为操作系统会降低异步工作的优先级。当使用 Grand Central Dispatch 异步执行任务时，你将改变代码中任务的执行顺序。牢记哪些任务必须依赖其他任务，以确保你的 App 不会出现问题，这一点很重要。在需要时，配合串行队列使用 `dispatch_sync` 是同步操作的好方法。与挂起对用户体验造成的严重影响相比，这些权衡总是值得的。

在消除挂起时，需要记住一些注意事项：使用 Apple 框架和 API。它们已经与各种设备兼容，性能良好，并且会不断更新以提高效率和效果。在你的代码中迭代进行改进。这样，你将进行有针对性的修复，并能看到单个更改的效果。在使用系统资源时，做一个好邻居。使用超出所需的资源不仅会降低你自己 App 的性能，还可能导致系统其他部分的减速。

我们一起体验了挂起是多么突兀，以及在你的 App 中防御挂起是多么重要。展望未来，通过 Xcode Organizer 设置你的 App 的性能基线。在开发和代码审查期间，注意可能导致挂起的反面模式。我们讨论了其中七个最常见的。使用 Time Profiler 和 System Trace 工具诊断出现的问题，并利用 MetricKit 来优先处理客户最常遇到的问题。通过使用缓存、观察通知、寻找异步替代方案或利用 Grand Central Dispatch 来消除你发现的任何挂起。遵循这些步骤，你的 App 将拥有更好的性能，以提供最佳用户体验。感谢你的耐心陪伴。[音乐]
