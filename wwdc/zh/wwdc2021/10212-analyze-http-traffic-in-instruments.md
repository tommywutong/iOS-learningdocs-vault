欢迎！我是 Kacper，Apple 的一名性能工具工程师。今天，我和 Sergio 将一起讨论 Instruments 13 中新增的 HTTP Traffic Instrument。这个 Instrument 包含在 Network 模板中，允许你检查来自你的 App、通过 Apple 网络栈传输的 HTTP 流量。

这种方法有多个好处。它在所有 Apple 设备上都能直接使用。通过 URL Loading System 的所有流量都会被暴露出来，即使是通过新的 HTTP/3 协议或 VPN 发送的流量也不例外。由于系统集成，它能够将流量归属于运行它的进程。并且因为它对 Apple 网络框架进行了插桩，它甚至能揭示命中了磁盘缓存或出现网络错误的请求。所有这些都在你熟悉的更高级别 API 概念的上下文中展现，例如 URLSession 和 URLSessionTask。这个工具将帮助你理解你对 API 的使用如何转化为网络请求的生命周期。在这个实践环节中，我们首先会让你熟悉 Instruments UI 如何反映你在使用的 API 概念。

在快速介绍之后，我们将过渡到四个演示，说明如何使用这个工具来检测性能和正确性问题。即使你的 App 看起来运行完美，你也会学到如何通过审计来自它的流量来验证它是否按照你的预期运行。让我们开始了解 Networking API 如何映射到 Instruments 可视化。当我使用 Network 模板录制我的系统流量时，HTTP Traffic trace 在 Instruments 中是这样显示的。导览围绕轨道层次结构组织，我们将先详细讨论这一点。位于顶层的 HTTP Traffic Instrument 显示你的 trace 中在任何给定时刻有多少个 URLSession 任务在运行的概览，非常适合检测你的 App 生命周期中 HTTP Traffic 活动增加的时段。

下一个层次级别按进程显示活动的细分。除了来自所有可调试进程的流量外，它还允许你检查由它们发起的后台流量。每个进程下面包含它使用的所有 URLSession。这些对应于你在代码中创建的 URLSession 对象。此级别的图表允许你检查所有单个任务的间隔。为了在你的 session 对象和可视化之间建立更好的映射，你可以在代码中通过设置 session 实例上的 `sessionDescription` 属性来为它们命名。

在最后一层，流量按请求的域进行细分。此级别的图表显示有关任务的更多详细信息，包括构成任务及其状态的单个事务。

为了更好地理解什么是任务和事务，让我们分析一个例子。

这里有一些任务正在从选定的域加载数据。让我们关注其中一个来分析任务的结构。

这个单个任务间隔包含大量信息。我们可以以更抽象的方式表示它，以理解 Instruments 可视化如何映射到正在使用的 API。

在顶层，我们有一个任务对象。一个任务由一个或多个事务组成。

一个事务是一对 HTTP 请求和相应的响应。

任务级别是你的代码如何与 URL Loading System 的 API 交互的表示。当你创建一个任务并对其调用 `resume` 时，任务间隔开始。它就在你的 completion block 被调用之前结束。

每个任务都可以使用 `taskDescription` 属性被赋予一个语义名称，该名称将用于在 Instruments 中标记间隔。我们还将任务标识符显示为任务标签的一部分。你可以使用它来将任务与其他数据交叉引用。如果你的任务以错误结束，它的描述将显示在间隔标签上，以便于调试。

正如我们之前提到的，一个任务可以由多个事务组成。现在让我们来谈谈这些。

这里我们有一个加载 apple.com 起始页的任务。然而，这个 URL 不是规范的 URL。该任务请求 apple.com，但首选域是 www.apple.com。当我们创建这个任务时，URL Loading System 最初会创建一个对 apple.com 的请求。不久之后，它从服务器收到一个重定向响应，表明首选的 URL 实际上是 www.apple.com。

默认情况下，我们会跟随重定向，因此 URL Loading System 不会返回 301 响应，而是会创建一个新事务来加载首选 URL。这第二个成功事务的响应就是返回给任务的内容。

如前所述，一个事务代表了 HTTP 请求和响应的组合。它与 URLSession 在底层为处理你的任务所做的事情一致，并包含 HTTP 层的所有信息，例如请求的 URL、有关传输数据的信息等等。

就像任务一样，事务标签为你提供了事务的概览。主要是，你获得有关请求和响应的信息。

轨道层次结构告诉你请求的域，而你可以在标签本身上找到路径和查询。

除此之外，间隔标签显示 HTTP 版本、HTTP 方法，以及请求是否发送了 `Authorization` 或 `Cookie` header。这些通常有助于一目了然地理解身份验证流程。

对于响应，你可以获得状态码、响应是否包含 cookie 以及响应的内容类型。请求和响应花费了多长时间，以及作为事务一部分的其他工作的更详细的时间信息，都由事务状态（transaction states）捕获。让我们在包含它的任务的上下文中分析它们。

事务的开始是 URL Loading System 为此请求创建事务的时间点。它首先检查我们是否已经有一个有效的缓存响应。如果没有，它将尝试在某个连接上调度这个请求。

接下来，事务可能会在 Blocked 状态下等待一会儿，等待一个可用的连接。

Sending Request 状态在事务最终由某个连接处理时开始。它在我们将请求的最后字节发送到网络上时结束。接下来，事务进入空闲的 Waiting for Response 状态，然后是 Receiving Response，它将跟踪从服务器接收到的第一个到最后一个字节的跨度。

整个事务将在接收到最后一个字节后不久完成，一旦 URL Loading System 确定了这是否是一个成功的响应。实际上，对于 GET 请求，缓存查找和发送状态通常要短得多，所以更可能看起来像这样。

为了理解它为什么被阻塞，让我们将轨道显示切换到“HTTP Transactions by Connection”视图。

在左侧的轨道侧边栏中，域名的下方，有一个向下箭头，我们可以点击它来切换轨道显示。

目前，我们正在绘制“Tasks”。让我们切换到显示“HTTP Transactions by Connection”。这个视图只显示事务，并且不是按任务分组，而是可以找出它们被调度到了哪个连接上。

事务按它们使用的连接分组。总共有六个连接可用于处理这些事务。让我们分析连接 1 上发出的事务，并进一步调查一些缩略图加载事务。从上到下，可以注意到每个事务完成的时间越来越长。每个后续事务的紫色阻塞状态都在增加。实际上，这里有一个非常明显的阶梯模式。

每个事务都被阻塞，直到同一个连接上的前一个事务完成。只有这样它才能发送它的请求。这个模式对每个后续事务重复。

这被称为“队头阻塞”（Head of Line Blocking），是使用 HTTP/1 的问题之一。

令人沮丧的是，这些事务在大部分时间里什么也没做。相反，它们大部分时间都花在阻塞或等待服务器响应上。我们本可以在等待同一连接上前一个事务的响应的同时，为队列中的下一个事务发送另一个请求，但 HTTP/1 不支持这样做。队头阻塞是 HTTP/1 的主要限制之一，而 HTTP/2 的主要改进之一就是通过在单个连接上多路复用对同一服务器的多个请求来避免这种影响。

在 HTTP/2 中，我们实际上可以在第一个请求等待响应时开始发送第二个请求。你的 App 不需要做任何事情来支持它。所有 Apple 平台都支持 HTTP/2，并且从 iOS 15 和 macOS Monterey 开始，也支持 HTTP/3。客户端会选择服务器支持的最现代的 HTTP 版本。如果你想了解更多关于 HTTP/1 和 HTTP/2 之间的区别，以及 HTTP/3 提供的额外好处，请观看“使用 HTTP/3 和 QUIC 加速网络”讲座。

我们注意到的第一件事是，这个事务不是在 Connection（连接）上执行的，而是在“Local Cache”（本地缓存）上执行的。这表明该请求从未在网络上发送过，而是从本地缓存加载的。这也解释了为什么没有“Waiting for Response”状态，因为事务没有等待服务器。

所以这就是问题所在：我们的请求被缓存了，所以实际上我们没有询问服务器，总是得到缓存的响应。一个修复方法就是告诉服务器设置 cache-control header，使其永远不缓存这个响应。我们想要的是，每次用户进入收藏标签页并且新图片被添加时，都重新加载图片。我们不想要的是，如果没有任何变化，加载整个图片列表。一个好的折中办法是，如果我们可以问服务器：“嘿，有什么变化吗？如果有，请告诉我。”这实际上可以通过在请求上设置一个 cache-policy 来实现。
