但当我单步进入时，实际上进入的是另一个表达式。编译器正确地判定需要先执行 adjustedDensity。当然，我可以先跳出，然后再进入该函数，但如果需要多次重复，这会变得很繁琐。我们在这里看到的情况是，有时行断点的粒度不够细。这是因为编译器为 LLDB 生成了多于一个可以停止的位置。我们真正想要的是恰好在 convertedToVolume 执行之前暂停。在 Xcode 13 中，我们引入了列断点（column breakpoint）。当你需要在一行中的某个特定表达式处暂停时，它可以让你避开行断点的不足。要在 convertedToVolume 上设置列断点，请按住 Command 单击该表达式，调出操作弹出窗口，然后选择 Set Column Breakpoint。与行断点一样，你可以点击图标来禁用或启用它。如果需要修改断点，可以双击它调出断点编辑器。既然我们不再需要那个行断点，可以通过把它从边槽中拖走来删除它。对列断点也可以做同样的事，但我打算把它留在那里。按住 Control 或单击鼠标右键会弹出上下文菜单，其中包含我们之前的操作。这里我选择 Reveal in Breakpoint Navigator。副标题已被更新，向你显示断点所在的列。当我们继续执行时，会遍历到下一个 NutritionFact，并命中我们新设置的列断点。当断点命中时，Xcode 使用行 PC（程序计数器）告诉你暂停的行。它会在该行上绘制一条浅绿色高亮。在 Xcode 11.4 中，我们引入了列 PC。列 PC 通过在某个表达式下绘制绿色下划线来向你显示暂停的列。这样你就能知道调试器接下来要执行的表达式。既然我看到列 PC 出现在 convertedToVolume 下方，我就可以放心地一步进入该函数。列断点对 Swift 中的闭包或 Objective-C 中的 block 特别有用。有时一行 Swift 代码可以包含多个闭包，就像第 269 行这一行代码一样。当编译器在调试条件下编译文件时，它会创建一个称为行表（line table）的映射，把源代码的行和列映射到编译后的地址。因此，对于这一行上的每个闭包，编译器都会生成一个行表条目，调试器会用它来暂停。假设我想检查最后一个闭包的匿名参数 $0，我可以在 269 行设置一个行断点，但暂停之后，由于生成的行表条目，我需要做大量的单步进入和单步跳出才能到达最后一个闭包。我们已经看到，在 Xcode 13 中，我们可以直接在最后一个 $0 上设置列断点，暂停后我们就正好在想要的位置，可以随心所欲地检查 $0。嗯，看来把香浓榴莲冰沙——还当作早餐——是开启一天的好方式。真好吃！接下来谈谈符号断点（symbolic breakpoint）。这类断点针对函数名称，当这些函数被执行时会暂停进程。在源文件断点无法使用或不方便使用的情况下，它们非常有帮助。例如，你没有源文件的访问权限，因此无法用调试信息编译它们。或者，你有许多子类都实现了同一个函数，在每一个子类中分别设置文件断点非常麻烦。让我们来看一看。我们点击断点导航器底部的添加按钮。这会显示一个我们可以创建的断点类型列表。我们选择 Symbolic Breakpoint，断点编辑器随即出现，以便我们输入符号名。假设我们想在几个类中都实现了的 toggle 函数中暂停。不必逐个寻找，我们只需在这里输入 toggle。但你需要小心由常见单词构成的函数名。这是因为 LLDB 会在进程中加载的所有库（包括系统库）中匹配该名称。如果不加限制，可能会有很多已解析的断点位置，有时甚至数以千计。如果其中许多位置被执行路径不断命中，那会很烦人。值得庆幸的是，我们可以把搜索限制在特定模块内。模块是可以在执行期间加载的二进制文件或映像，包括主二进制文件。这里我们输入 "Fruta"，也就是我们 App 的二进制文件名。于是我们得到三个已解析的位置，这就好管理多了。既然我们已经选择了一款冰沙，让我们切换一下收藏按钮。我们会命中刚刚设置的符号断点。对于符号断点来说，打错字是相当容易发生的事。然后在程序执行期间，断点不命中，让你摸不着头脑。让我们尝试创建一个名为 convertToMass 的断点。

Xcode 13 的一个新特性是：如果一个断点没有被 LLDB 解析到任何位置，Xcode 会显示一个虚线图标。断点未被解析的原因有很多，但有一些常见的解释。如果你把鼠标悬停在未解析的断点图标上，会有一个工具提示来帮助你。前几个原因与断点的类型有关。对于符号断点，名称必须拼写正确，并且该符号必须存在于其所在的库中。下一个原因更具通用性：断点所在的库必须已加载。有时，库只在你执行了某些用户操作（例如点击一个按钮）之后才会加载，那时 LLDB 会自动为你解析断点。在这个例子中，我怀疑是拼写有误。让我们来弄清楚。一种方法是使用查找导航器搜索 "convert"。如你所见，结果相当多，肉眼分析它们需要一些时间。我们可以改用另一个技巧，通过 LLDB 来完成。在 Xcode 控制台中，我们输入 `image`——也就是模块——`lookup -r` 表示用正则表达式，`n` 表示按名称，`convert`，然后提供模块名 Fruta 来限制搜索范围。你可以看到只有四个匹配项，我们肯定是把函数名拼错了。应该是 "convertedToMass"。让我们把它复制并粘贴到断点编辑器中。

这一次，LLDB 成功解析了它，并给了我们 1 号位置。

未解析的断点也可能出现在源文件断点上。与它们相关的有两个原因。第一，断点所在的行必须被编译。在这个例子中，第 23 行没有被编译，因为它位于编译条件的 else 部分。此外，编译器必须为该模块生成调试信息。如果没有，你需要检查你的构建设置。接下来是运行时问题断点。运行时问题是在运行时发生的问题——例如，在后台线程中更改 UI 状态。它不像崩溃那样严重，默认情况下 Xcode 不会暂停你的进程，因为在你专注于另一个 bug 时，这可能干扰太大。相反，当运行时问题发生时，Xcode 会记录回溯并将其呈现在问题导航器中。但由于问题发生在过去，检查当前进程状态已经没有意义。所以有时你确实希望在它发生时当场捕获。设置一个运行时问题断点可以让你在调试器中暂停，并当场检查进程。运行时问题断点有不同类型。你可以使用类型弹出菜单轻松选择特定类型。请记住，对于其中一些类型，你需要在 scheme 编辑器的诊断（diagnostics）标签页中启用相应的功能。你只需点击 Go To 按钮即可前往。由于我们想使用主线程检查器运行时问题断点，我们需要启用 Main Thread Checker。希望本次 session 向你展示了我们在 Xcode 13 中对断点所做的改进。断点可以极大地提升你的调试能力，绝对应当成为你的技能储备的一部分。谢谢，祝你在 WWDC 的其余 session 中愉快。♪
