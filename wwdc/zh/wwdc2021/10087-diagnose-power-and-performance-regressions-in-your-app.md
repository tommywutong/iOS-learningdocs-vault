大家好，我是 Sonia，一名性能工具工程师。今天，我的同事 Shreyas 和我将向你展示如何诊断 App 中的功耗和性能衰退（regression）。每年，你都会努力发布最好的 App。你希望为用户在你的 App 中带来出色的体验，因此优化功耗和性能至关重要。本讲座将涵盖影响 App 性能的关键指标、帮助你发现衰退的工具、帮助你减少磁盘写入的洞察，以及用于自动化性能工作流的 API。为了帮助你优化性能，你可以通过 Xcode Organizer 和 App Store Connect API 获得一套全面的指标和诊断数据，而无需对你的 App 做任何更改。众所周知，性能优化并不容易。面对如此多的指标和诊断数据，你很容易迷失在信息的海洋中。你希望每个版本都比上一个更好，但需要一种快捷的方式来确定性能优化的优先事项。Xcode Organizer 是了解性能的绝佳工具。它目前收集了七个指标类别（metric category）的数据，包括电池、启动、挂起（hang）、内存、磁盘写入、滚动卡顿（scroll hitch）和终止。需要处理的信息量很大。接下来，让我们深入了解 Xcode Organizer 并诊断一个性能衰退。我将从查看我的 App 的不同指标开始。我可以在左侧导航栏中选择七个指标类别。某些类别，如电池和终止，可能包含多个部分以及详细描述不同事件类型的子类别。我还可以按需选择不同的设备类型，以及我的 App 顶级用户和典型用户的百分位数。Organizer 的中央部分显示了一张图表，包含最近 16 个版本的数据。在这个例子中，我想调查我的 App 中的终止问题。

屏幕上的图表显示，在最新版本中，终止次数显著增加，表明该版本可能存在问题，尤其是蓝色高亮显示的更多非法指令退出。有如此丰富而有趣的指标集可以帮助我了解线上性能，但面对如此多的设备选项、指标类别和子类别，我不清楚应该从哪里开始优化性能。这就是为什么 Organizer 现在新增了一个洞察部分，用于突出显示你所有的性能优化优先级并简化你的工作流程。Xcode Organizer 现在会处理指标数据并识别有趣的趋势，例如性能衰退。在深入探讨之前，我先谈谈什么是性能衰退以及如何检测它们。当 App 在某个功耗或性能方面的表现相对于最近几个版本变差时，就发生了衰退。例如，在某个版本发布后，启动耗时变长。在这个例子中，系统会分析最近几个版本中的指标，以确定其是否呈上升趋势。然后计算该指标在最近几个版本中的平均值，再与最新值进行比较。如果指标呈上升趋势，且最新值高于最近几个版本的平均值，它就会被标记为衰退，并在洞察部分中进行总结。在这个例子中，App 启动平均耗时 1.1 秒，然后在最近一个版本中突然跃升到 2.5 秒，导致被标记为衰退。现在你了解了如何标记衰退，让我们回到 Organizer 并深入几个例子。这是衰退标签页。它是一个一站式中心，让你可以发现最需要优先处理的性能问题。你的 App 在最近一次版本发布后是否突然崩溃？那个炫酷的新相机功能是否在耗干设备电池？你会在洞察部分找到这些及更多问题的答案。在这个首选部分中，所有你需要的数据都会被高亮显示，以帮助你了解线上性能。在这里，你可以发现不同指标类别和子类别的衰退，覆盖不同设备上典型和顶级百分位数用户的汇总数据。左侧会总结哪个指标出现了衰退、衰退了多少、涉及哪些百分位数，精确地指出你需要关注的重点，以打造更出色的 App。我的 App 在终止、内存和磁盘写入方面存在几处衰退。接下来，我将逐一举例讲解如何解读它们。我将从终止衰退开始。在讲解终止之前，请查看视频“为什么我的 App 会被终止？”以了解更多背景信息。每个衰退都会总结我最新 App 版本中的所有主要问题。该部分的顶部显示非法指令导致了崩溃，这可能发生在我的 App 访问无效函数指针时。再往下，有一张显示我 App 最近四个版本中非法指令退出的图表。图表顶部显示了受影响的百分位数和设备。在此例中，所有 iPhone 上的顶级百分位数用户在最新版本中遇到了更多崩溃。图表右侧显示了非法指令退出的平均值和最新值。在此例中，我的 App 在最新版本中开始每隔十天崩溃一次。屏幕上的终止非常具有破坏性，因为用户会被迫频繁返回主屏幕并重新启动 App。我需要移除对导致这些崩溃的无效函数指针的引用，并且可以通过查看崩溃诊断来进一步深入。请观看视频“使用 Xcode 分类处理 TestFlight 崩溃”以了解有关崩溃诊断的更多信息。

通过使用衰退和崩溃诊断，我现在知道需要在下一个 App 版本中减少屏幕上的终止。我不想只止步于屏幕上的终止，我知道还有更多可以改进的地方。我会检查 App 的衰退以发现其他改进空间。

看起来任务超时也存在衰退。有些指标可能在多种设备和百分位数上都出现衰退。在此例中，无论是典型百分位数还是顶级百分位数，所有 iPhone 上的任务超时都增加了。我可以在右侧滚动查看每个衰退，浏览最近几个版本的数据以及该指标的最新值和平均值。当 App 切换到后台时，它有 30 秒的时间来执行任务，之后系统就会将其终止。这意味着，如果未能正确结束后台任务，可能会导致 App 被更频繁地终止，进而导致用户下次切换回来时启动缓慢。我的 App 现在每三天就会在后台被终止一次。虽然不如屏幕上的终止那么具有破坏性，但后台终止可能更常见。即使我的 App 在后台被终止，也必须确保流畅的启动体验。我可以集成 UIKit 的状态恢复（state restoration）功能，以确保从任何后台退出中平稳恢复。最后，回到我 App 的衰退，还有另一个性能领域需要我关注。磁盘写入量在新版本中增加了 28%，但尚不清楚是什么原因导致的。知道存在性能问题当然好，但我在开始优化 App 之前还需要更进一步的洞察来了解从何处入手。接下来，Shreyas 将告诉你如何发现磁盘写入衰退背后的主要原因。

谢谢 Sonia。大家好，我是 Shreyas，Apple 的存储软件工程师。我将介绍如何调试磁盘写入衰退并持续跟进 App 的性能。但在深入讨论之前，为什么磁盘写入如此重要？存储空间，就像 CPU 和内存一样，是一种有限的资源。不加节制的磁盘写入会磨损并损坏底层设备。它们也是导致烦人的屏幕挂起和 UI 卡顿（hitch）的常见原因。如果不加注意，它们会迅速耗尽电池续航。这使得优化磁盘写入成为确保出色用户体验的关键一环。牢记这一点，让我们了解一下可用于诊断高磁盘写入的资源。Xcode Organizer 中的磁盘写入报告窗格是一个很好的切入点。这些报告是从同意共享 App 分析数据的设备上收集的，其中包含导致写入的堆栈跟踪（stack trace）信息。每个报告的堆栈跟踪被拆分为多个签名，所有报告中该签名的写入量都会被累计跟踪。在此报告列表中，签名按照总写入量排序显示。对于每个签名，我们都可以找到详细的堆栈跟踪，显示出写入的原因，还可以找到统计数据，例如收到了多少条日志、操作系统版本和硬件型号的分布情况等等。要识别问题区域，请密切关注你的顶级签名。在此例中，顶级签名占据了 67% 的写入量。从调用栈我们可以推断这源于一个 SQLite 函数。很多时候，一旦你知道了问题的根源，就能大大推进问题的解决。但通常，就像这个例子一样，修复方法可能并不显而易见。这里的代码对我的新功能至关重要，我没有发现任何明显的错误，也不清楚下一步该怎么做。事实证明，如果你知道往哪里看，答案就藏在堆栈跟踪里面。

有些函数深埋在堆栈之中，有时在你使用的库里面，它们可以告诉你哪里出了问题，并且通过足够的研究，还可以告诉你如何修复。但这可能非常棘手。它通常需要特定的领域知识，并且可能极其耗时。

为了帮你省去这些麻烦，在 Xcode 13 中，Organizer 增加了一个名为“洞察”的新字段。在后台，系统维护了一个仓库，收录了已知的导致高磁盘写入的反模式（antipattern）。当收到报告时，系统会扫描其中指示这些反模式的函数。当匹配到时，问题会在这里高亮出来，并附带优化建议来修复该问题。这将使你能够轻松减少 App 的写入、提高性能，同时节省大量的调试精力。例如，对于我们的顶级签名，我看到了一条优化建议：添加索引。还有一个指向文档页面的链接，该页面将详细解释问题并给出调试和修复问题的步骤。太好了。现在，让我们按照建议操作，看看它是否有帮助。为此，让我启动文件活动 Instruments。文件活动 Instruments 是调试所有存储相关问题的绝佳资源。它为我提供了 App 执行的所有读取和写入操作的详细分解。它是验证我的修复方案的完美工具。

之前，Instruments 显示对临时文件的写入量约为 180 兆字节。

这也带来了 780 毫秒的延迟。

现在，添加索引后，由此函数导致的写入降为零。这是因为 SQLite 现在更高效了。这意味着我们不再有 780 毫秒的延迟在拖慢速度。SQLite 索引只是一个例子。还有一系列其他优化建议可以改善你的 App 性能，而且我们一直在持续扩展这个列表，所以今天就去查看你 App 的洞察吧。

让我们回到洞察窗格。我们的 App 存在三个衰退。我们仔细分析了每一个衰退，并发现了解决所有这些问题的可用资源。这很重要。Xcode Organizer 中有大量的功耗和性能分析数据，而洞察应该是你发现 App 性能优化优先级的首选窗格。请充分利用它。要计划定期检查衰退和洞察，并且一定要在每次版本发布之后进行检查。

除了 Xcode Organizer，还有另一种方法可以访问我们今天讨论的所有分析数据，那就是 App Store Connect API。

如果你想以编程方式访问数据并构建自定义解决方案，这些 API 非常有用。也许你已经建立了自己的分析管道。那么这些 API 就是你集成所有这些出色分析功能的完美工具。请观看 WWDC 2020 的视频“使用功耗与性能 API 识别趋势”。它详细介绍了 API 端点和响应。让我快速概述一下部分 API 响应。对于指标，你可以向 perfPowerMetrics 端点发出 GET 请求。这会返回一个 JSON 响应，其中包含你各个最新版本的 App 指标和洞察。让我们跳转到洞察部分。在洞察中，你将找到为你的 App 识别出的所有衰退。对于每个衰退，你将看到指标类别和已识别衰退的摘要。

这是我们之前在 Xcode Organizer 中发现的由非法指令导致的屏幕终止。

接下来是群体（populations）部分。它提供了一个详细、结构化的列表，列出了受影响的百分位数和设备。你可以利用这些信息采取有针对性的措施来改进 App 的性能。

类似地，对于诊断报告，你可以向 diagnosticSignatures 端点发出 GET 请求。响应将包含顶级签名的列表，每个签名都带有一个指向其相关详细信息的链接。

向此链接发出 GET 请求将提供详细的诊断日志以及与该签名关联的洞察。在你的分析管道中使用这些 API，当你看到洞察时，应立即采取行动。现在你知道了什么是性能衰退、如何诊断它们，以及在哪里可以找到能够指导你采取行动来修复它们的数据。接下来你需要这样做。立即打开 Xcode Organizer。查看衰退窗格。找出你的 App 最主要的性能衰退是什么。了解你的 App 写了多少数据。顶级的磁盘写入调用栈是否如你预期？还是存在隐藏的错误在拖慢你的 App？最后，制定一个计划来持续跟进 App 的性能。定期检查 Xcode Organizer，并在任何自定义分析管道中使用 App Store Connect API。感谢你的关注。祝你排查衰退顺利。[欢快的音乐]
