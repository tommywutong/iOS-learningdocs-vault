为此，我想介绍一下符号化的两步过程。

第一步是返回到文件，第二步是查询调试信息。

正如我们将看到的，返回到文件就是将运行时的内存地址转换或翻译成一种更稳定、可用的形式。

这使我们能够与调试信息通信，从而在原始内存地址和源代码之间建立有意义的联系。

让我们从讨论第一步开始：返回到文件。

这一步的最终目标是将运行时内存地址——比如我们在原始 crash log 中看到的那些——转换为磁盘上二进制文件中对应的地址。

就像我们有运行时地址一样，你的 App 和框架在磁盘上也有一个地址空间！磁盘上的地址空间不同于你的 App 在运行时占用的地址空间，我们需要一种机制来找出这些差异。

首先，我们应该确切理解磁盘地址是什么。

这些地址是在你构建 App 时由链接器（linker）分配的。

具体来说，链接器将你的二进制文件分组为段（segment）。

每个段包含相关数据，并具有诸如名称、大小和分配的地址等属性。

例如，二进制文件的 `__TEXT` 段包含你编写的所有函数和方法，而 `__DATA` 段包含程序级别的状态，例如全局变量。

每个段都被分配不同的地址，以免重叠。

链接器将此信息记录在可执行文件的起始位置，作为 Mach-O 头（Mach-O header）的一部分。

Mach-O 是所有可执行二进制文件和库使用的格式，系统知道需要读取这个头才能运行你的 App。

更仔细地看，Mach-O 头包含许多加载命令（load command），这些命令保存了段的属性。

系统使用这些加载命令将段加载到内存中。

请注意，如果你的 App 是 Universal 2 架构，那么该 App 将有一个 Mach-O 头和每个架构的一组段。

我们可以通过使用 `otool -l` 命令来查看，它会打印出指定文件的加载命令。

这里，我们查看一个标识为 `LC_SEGMENT_64` 的段加载命令。

该加载命令说明 `__TEXT` 段起始于 `vmaddr` 中的地址，长度为 `vmsize` 字节。

那么，如果内核遵循这些加载命令将段加载到内存中，运行时地址和链接器地址之间到底有什么区别呢？嗯，在内核实际加载段之前，它会初始化一个随机值，称为 ASLR 偏移（ASLR slide）。

然后内核将这个 ASLR 偏移加到加载命令中的地址上。

因此，内核不会将 `__TEXT` 段加载到地址 A，将 `__DATA` 段加载到地址 B，而是将它们加载到 A+S 和 B+S，其中 S 就是 ASLR 偏移。

由于 A+S 和 B+S 是系统使用的真实地址，它们也被称为加载地址（load address）。

有了这个概念，我们现在知道运行时地址和链接器地址之间的差异就是 ASLR 偏移。

我们可以用以下公式计算 ASLR 偏移：S = L - A，其中 S 是 ASLR 偏移，L 是加载地址，A 是链接器地址。

我们很快就会看到这个公式的例子，但关键是，一旦我们知道 ASLR 偏移，我们总是可以回到文件的地址空间。

ASLR 偏移公式需要两个地址——加载地址和链接器地址——那么我们从哪里获取它们呢？我们已经看到了如何使用 `otool` 查询加载命令以获取链接器地址。

为了获知运行时地址，系统会在 crash 时或 Instruments 对其进行分析时查询你的 App 的运行时地址空间。

这些信息反映在 crash log 中的 Binary Images 列表中。

你也可以使用 `vmmap` 工具交互式地查看加载地址，该工具会枚举程序中的活动内存区域。

让我们从原始 crash log 中自己计算下 ASLR 偏移值。

在 Binary Images 列表中，我有 `__TEXT` 段的加载地址。

当我查看加载命令时，我也有磁盘上二进制文件的链接器地址。

将这两者相减，得到 ASLR 偏移值为 0x45c000。

这意味着我的程序运行时 `__TEXT` 段中的每个地址都与链接器 `__TEXT` 段地址相距 0x45c000 字节。

因此，要查看 crash log 中的回溯地址对应于文件中的哪个地址，我可以从中减去 0x45c000 以获得磁盘上的地址。

由于这个地址现在是磁盘地址空间的一部分，我可以检查我的 App 看那里有什么内容。

crash log 告诉我，一个线程在执行此地址处的任何内容时 crash 了，因此我们可以再次使用 `otool` 来查看有问题的指令。

这次，我向 `otool` 指定了 `-tV` flag，这将打印反汇编。

请注意，我还将架构指定为 arm64。

这是为了让 otool 知道要考虑哪个 Mach-O 头和段，因为该 App 是作为 Universal 2 构建的。

`otool` 的输出在该地址处揭示了一条 `brk` 指令。

`brk` 表示 App 中出现了异常或问题。

像 `atos` 这样的工具也使用我们刚才一起学习过的相同技术来计算 ASLR 偏移。

`atos` 会读取由 `-o` flag 指定的文件的加载命令，而我们通过 `-l` flag 告诉它加载地址。

正如我提到的，`vmmap` 也可以告诉我们正在运行的 App 的加载地址。

让我们再次尝试这个计算，但这次我们将使用 `vmmap` 而不是 binary image list 来确定 ASLR 偏移。

我再次运行了 MagicNumbers 程序，并在程序 crash 前获取了 `__TEXT` 段的加载地址。

使用之前的公式，我可以确定这次 ASLR 偏移值是 0x104d14000。

同样，要返回文件，我需要减去 ASLR 偏移值。

如果我从新 crash log 中最顶部的条目减去 0x104d14000，我会得到与之前完全相同的文件地址。

这并非巧合；内核只是选择了一个不同的 ASLR 值，所以我们的加载地址在不同 crash log 之间发生了变化。

然而，我们仍然可以确定导致 crash 的文件地址。

这里的要点是，我们有一种机制可以精确理解 App 在做什么，精确到指令级别，无论其运行时地址如何。

有了这个映射，我们就可以查询调试信息，以找到被编译成这些指令的源代码。

在我们继续之前，我想总结一下我们介绍的内容和使用的工具。

App 二进制文件和框架都是 Mach-O 文件。

这意味着它们在不同段中包含相关的内容。

这些段由链接器创建。

Mach-O 头加载命令描述了这些段的属性，包括地址。

我们使用带有 `-l` flag 的 `otool` 来打印加载命令。

接下来，我们了解到内核会向链接器地址添加一个随机值，称为 ASLR 偏移。

ASLR 偏移与链接器地址相加的结果称为加载地址。

我们可以在 crash log 中检查 Binary Images 列表，以查看 crash 时的加载地址，或者我们可以使用 `vmmap` 来查看正在运行的 App 的加载地址。

最后，我们通过几个计算 ASLR 偏移以返回文件地址空间的例子进行了演练。

现在我们可以讨论调试信息（debug information）了，它包含了文件地址与源代码之间的关键联系。

Xcode 在你构建 App 时创建调试信息，并将其直接嵌入到你的 App 二进制文件中，或将其存储为单独的文件，例如 dSYM。

调试信息有几种类别或类型。

每种类型都为给定的文件地址提供不同层次的细节。

今天我们将介绍三种不同类型的调试信息。

首先，我们将介绍函数起始数据（function starts），它本身不会增加太多价值，但是一个常见的起点。

接下来，我们将看到 nlist 符号表（nlist symbol table），它添加了函数和方法名称。

最后，我们将介绍 DWARF，它来源于 dSYM 和静态库。

DWARF 提供的细节最多，包括文件名、行号以及优化记录。

由于 DWARF 提供的细节最多，我们确实应该尽可能争取拥有这种类型的调试信息。

我们将学习每一种类型，以及如何使用它们来构建完全符号化的 crash log。

让我们从函数起始数据开始。

正如我们在表中看到的，函数起始数据提供的源代码细节最少。

同样如其名称所示，这种类型的调试信息只告诉我们函数的起始地址——或者说字面上的开始。

例如，它会告诉我们一个函数在某个地址开始并存在。

然而，它并不告诉我们在那些地址开始的是哪些函数，只告诉它们存在。

函数起始数据调试信息通过在你的 App 的 `__LINKEDIT` 段中编码地址列表来实现这一点。

由于这是直接嵌入到你的 App 中的，Mach-O 头也有一个加载命令来告知我们可以在哪里找到它，即 `LC_FUNCTION_STARTS`。

你可以使用 `symbols` 命令和 `-onlyFuncStartsData` flag 自行查看。

这里我们得到一个地址和空占位符的列表。

这些占位符理想情况下应该有函数和方法名称，而不是空值，但函数起始数据不提供名称。

再次强调，这不是最具描述性的数据。

然而，它确实允许对 crash log 进行小幅更新。

我们现在可以将文件地址视为相对于某个函数的偏移量。

例如，首先我们通过减去 ASLR 偏移值返回到文件。

然后，我们找到可能包含该文件地址的函数起始值。

在这种情况下，只有第一个值可能包含该地址，因为所有其他值都大于该地址。

最后，我们可以宣称我们的文件地址实际上位于此函数内部的 264 字节处。

这主要对调试器有用，因为它们可以理解该函数是如何设置的细节以及哪些寄存器被修改了。

然而，这对你来说意味着，如果你遇到一个缺少函数名的 crash log，你很可能是在处理这个最低层次的调试信息。

这是个好消息，因为这意味着有很多机会可以用更好的调试信息来丰富 crash log。

很自然地，我们想要看到的下一层细节是函数名称。

这给了我们第一个真正的机会，利用 crash log 或 Instruments 追踪来跟踪源代码中的问题。

这就引出了 nlist 符号表。

符号表建立在函数起始数据的概念之上，并在 `__LINKEDIT` 段中编码了一系列信息，并且它也有自己的加载命令。

然而，不仅仅是编码地址，它们编码的是 C 结构体。

与函数起始数据相比，这使我们能够为任何给定的条目添加更多细节。

具体来说，它们编码了 `nlist_64` 结构体。

这里我们有该结构体的定义。

粗略一看，我们可以访问一个名称和几个属性。

这些结构体字段的值由 nlist 的 `n_type` 决定。

我们感兴趣的有三种主要的 n_type，但我们现在只关注其中两种。

第一种称为直接符号（direct symbol）。

这些是你完全在你的 App 和框架中定义的函数和方法。

直接符号在 `nlist_64` 结构体中有一个名称和一个地址。

此外，它们由 `n_type` 字段中的特定位模式表示。

具体来说，`n_type` 会设置第二、第三和第四最低有效位。

这些位也称为 `N_SECT`。

我们可以通过 `nm` 并指定 `-defined-only` 和 `--numeric-sort` flag 来查看它们。

这里，`nm` 遍历了 MagicNumbers 程序中已定义的符号，并按地址顺序列出它们。

我们得到回来的名称看起来是神秘的。

这是因为符号表中实际存储的名称是修饰后的名称（mangled name）。

这些修饰后的名称帮助编译器和链接器唯一标识一个函数，但除非将它们还原，否则很难理解。

为了获得这些名称更友好的版本，我将输出传递给 `swift-demangle`。

现在我们得到了一些熟悉的名称，例如 `main` 和 `numberChoices`，因为它们是在我的 App 中直接定义的。

类似地，`symbols` 工具有一个选项可以显示 nlist 数据，并且它也会自动还原名称。

现在我们可以将函数名称与地址关联起来了，这让我们能够再次更新 crash log。

在这里我们可以观察到，我们从函数起始数据中得到的偏移表达式也与直接符号中的一个条目匹配，并且该条目有一个名称。

将这两者结合起来，我们现在可以说我们的 crash 发生在 main 函数内部的 264 字节处。

这仍然留下一些细节有待完善，因为我们知道 main 并非唯一涉及的函数。

而且，能有一个精确的行号也会有帮助。

我们在 Instruments 追踪示例中遇到了类似的情况——我们有一些可用的函数名称，但缺少其他的。

其中一个原因是，符号表只为涉及链接的函数提供了直接符号条目。

这些是你跨模块使用的函数，或从你的框架导出的函数。

这使得它对于识别 API 边界非常有用。

并且这也意味着它拥有为诸如 `dlsym()` 和 `dladdr()` 等函数的动态加载提供支持所需的数据。

然而，一个缺点是本地或静态函数在符号表中没有体现，因为它们在其模块外部没有被引用。

这最终会遗漏那些可能包含很大一部分 App 逻辑的实现函数。

此外，Release 模式构建的二进制文件通常会剥离（strip）其符号表。

这意味着从符号表中移除不必要的条目，这有助于减少 App 的大小。

如果我们想一想，App 的主要驱动者很少会将功能导出到任何地方，因此保留这些符号表条目会浪费空间。

对于我们的框架和库，我们肯定有客户应该使用的导出函数，但没有必要保留本地共享的函数，因为它们无法在其他地方使用。

剥离我们主 App 的可执行文件几乎总会让符号表实际为空。

剥离我们的框架和库只会留下导出的函数。

你可能在 Xcode 中遇到过诸如 Strip Linked Product、Strip Style 和 Strip Swift Symbols 这样的构建设置。

这些构建设置控制了你的 App 在构建期间如何被剥离。

如果启用了 Strip Linked Product，那么二进制文件将根据 Strip Style 进行剥离。

例如，All Symbols 将执行最具侵入性的移除，只留下最基本的内容。

Non Globals 会移除在 App 不同模块内使用但不导出以供其他 App 使用的直接符号。

Debugging Symbols 会移除第三种 nlist 类型，我们稍后在讨论 DWARF 时会讲到。

然而，这种 strip 样式会保留直接符号。

例如，这里我有一个框架，它定义了两个公共接口和一个内部共享实现函数。

由于所有这些函数都在链接中发挥作用，它们都有直接符号条目。

如果我剥离非全局符号，那么我只剩下我的接口。

共享实现函数仅在我的框架内部使用，因此它不被视为全局的。

类似地，剥离所有符号仍然会留下接口，因为其他 App 需要使用这些接口才能使用该框架。

你还可以在 `symbols --onlyNListData` 的输出中注意到，在直接符号之间穿插着函数起始地址。

这些地址代表那些要么从未在直接符号中，要么已被剥离的函数。

你可以根据所需的符号表可见性级别来定制这些 strip 设置。

有了这些信息，我们可以确定何时在处理直接符号。

一些明显的标志是有函数名称但没有行号或文件名；或者像我们这里的框架示例一样，函数名称和函数起始地址混杂在一起。

我们将分析的第二种 nlist 结构体称为间接符号（indirect symbol），与直接符号相对。

这是指 `n_type` 仅匹配 `N_EXT` 位模式的情况。

这些是你从其他框架或库中使用的函数和方法，例如 `print()`。

你可以通过 `nm` 查看它们，只是这次我们将指定 `--undefined-only` 而不是 `--defined-only`。

我们还将添加 `-m` flag，它会显示应该在哪里找到这些函数所在的框架或库。

例如，MagicNumbers App 依赖于在 libswiftCore 中定义的各种 Swift 函数。

既然我们已经介绍了三种调试信息类别中的两种，让我们确保理解它们的属性。

函数起始数据是一个地址列表，因此它们缺少名称，但确实允许我们确定偏移量。

nlist 符号表编码完整的信息结构体，并且可以将名称与地址关联起来。

它们描述直接符号——在你的 App 中定义的——和间接符号——由依赖项提供的。

直接符号通常保留给涉及链接的函数，并且 strip 构建设置会影响哪些直接符号可用。

最后，函数起始数据和 nlist 符号表都直接嵌入到你的 App 中。

我们还没有看到的是更丰富的细节层次，例如文件名和行号。

这些由 DWARF 提供给我们。

DWARF 将 nlist 符号表的概念带到了一个完全不同的水平。

DWARF 并非只保留一个函数子集，而是力求描述一切。

我们已经看到 nlist 符号表相比函数起始数据增加了巨量的信息。

它通过增加一个维度来实现这一点。

记住，我们在查看函数起始数据时，是从单一维度开始的，也就是地址。

然后，我们通过编码一个包含丰富信息的结构体到 nlist 符号表中，升级到了两个维度。

DWARF 增加了第三个维度，即关于关系的维度。

DWARF 认识到函数并非孤立存在。

它们调用其他函数，拥有参数，返回有意义的数据，并且定义在特定的文件中。

对这些关系的编码解锁了符号化最强大的方面。

当我们分析 DWARF 时，我们主要指的是 dSYM 包。

除了诸如 plist 等其他元数据之外，dSYM 包还包含一个带有 DWARF 的二进制文件。

是什么让这个二进制文件如此特别？该二进制文件将其数据放在一个特殊的 `__DWARF` 段中。

DWARF 规范提到了该段中的三股数据流，我们将重点关注。

`debug_info` 包含原始数据，`debug_abbrev` 为数据分配结构，`debug_line` 包含文件名和行号。

DWARF 还定义了两种词汇类型，我们将首先学习它们：编译单元（compile unit）和子程序（subprogram）。

稍后我们将介绍第三种。

一个编译单元代表构建产品时所用的单个源文件。

例如，我们可以预期项目中每个 Swift 文件都有一个编译单元。

DWARF 为编译单元分配了属性，例如文件名、SDK、其函数所占用的 `__TEXT` 段部分，以及更多。

main.swift 的编译单元在左侧的 `debug_info` 流中包含这些属性，并且在右侧的 `debug _abbrev` 流中有一个对应的条目，告诉我们这些值代表什么。

这里我们看到了文件名、编写所用的语言，以及一个代表 `__TEXT` 段范围的高低地址对。

一个子程序代表一个已定义的函数。

我们已经在 nlist 符号表中看到了已定义的函数，但子程序也可以描述静态函数和本地函数。

子程序也有一个名称及其 `__TEXT` 段地址范围。

编译单元和子程序之间的一个基本关系是子程序是在编译单元中定义的。

DWARF 用树来表示这一点。

编译单元位于树的根部，它包含子程序条目作为子节点。

子节点可以通过遵循其地址范围进行搜索。

我们可以使用 `dwarfdump` 命令更详细地检查这些内容。

首先，我们将查看一个编译单元。

这与我之前提到的编译单元的一些属性相匹配。

`dwarfdump` 方便地结合了 `debug_ info` 和 `debug _abbrev` 的内容，向你展示 dSYM 中数据的结构和内容。

如果向下滚动输出，我们会遇到一个子程序子节点。

它占用的地址范围在编译单元的范围之内，我们还可以看到函数的名称。

我提到过 DWARF 极其详细地描述其数据。

虽然我们不会花太多时间在这些细节上，但我认为看到诸如函数参数之类的细节是很有趣的。

它们有自己的词汇类型来描述参数的名称和类型。

遵循树模型，参数是一个子程序的子节点。

这里我们遇到了我们提供给某个函数的 choices 参数的条目。

接下来，文件名和行号来自 `debug_line` 流。

这个流没有树结构。

相反，它定义了一个行表程序（line table program），其中单个文件地址可以被映射回精确的代码行。

这最终生成了一个源代码细节列表，我们可以搜索它以找到文件和行号。

注意到什么奇怪的地方了吗？是的，我们有函数名称和行号，所以我们确实在使用 DWARF。

但除此之外，这与 nlist 符号表的更新并没有太大不同。

事实上，当我们将其与第一次使用 `atos` 时进行比较，它看起来仍然缺少许多有价值的函数和细节！这里发生了什么？唯一的变化是这次我们没有向 `atos` 指定 `-i`。

这个 flag 代表“内联函数”（inlined functions）。内联是编译器执行的一种常规优化。

这涉及用函数体直接替换函数调用。

它的一个很酷的效果是使代码看起来消失了。

我们可以将其想象为，不是调用 `numberChoices()`，而是将 `numberChoices()` 的全部代码直接放置到位。

突然之间，不再有对 `numberChoices()` 的函数调用了！DWARF 用内联子程序（inlined subroutine）来表示这一点。

这是我们今天要讨论的 DWARF 的第三种也是最后一种词汇类型。

内联子程序是一个子程序——所以它是一个函数——它被内联到另一个子程序中。

由于内联函数完全被关系树中的另一个节点所包含，内联子程序是那个节点的一个子节点。

这个定义也适用于递归，意味着一个内联子程序可以有其他内联的子节点。

同样，使用 `dwarfdump`，我们可以查找内联子程序。

它们被列为其他节点的子节点，并且具有与子程序相似的属性，例如名称和地址。

然而，在 DWARF 中，这些属性经常通过一个公共节点来访问，称为抽象源（abstract origin）。

如果一个特定函数有很多内联副本，那么它们通用的、共享的属性会保存在抽象源中，这样它们就不会在每个地方都被重复。

内联子程序有一个独特的属性是调用点（call site）。

这是我们源代码中编写实际函数调用的位置，但优化器替换了它。

内联函数的优化细节是让我们获得完全符号化的 crash log 的关键细节。

`atos` 的 `-i` flag 指示该工具在符号化期间考虑它们。

它们也是我们 Instruments 追踪中缺失的细节。

我们需要同时为 Instruments 和 crash log 准备 dSYM 的原因正是为了能够提取所有这些内容。

还有另一个可以找到 DWARF 的来源，那就是静态库和目标文件。

在没有 dSYM 的情况下，你仍然可以为从静态库或目标文件链接的函数收集 DWARF。

在这些情况下，你会找到 Debugging Symbols 的 nlist 类型。

这些是可被剥离的符号类型之一。

不过，它们本身并不持有 DWARF。

相反，它们将一个函数关联回其来源文件。

如果该库是使用调试信息构建的，那么 nlist 条目可以指向我们找到那个 DWARF。

这些类型的 nlist 条目可以通过 `dsymutil -dump-debug-map` 详细查看。

总结一下，DWARF 是深入符号化数据的重要来源。

DWARF 揭示了函数与文件之间的重要关系。

诸如函数内联之类的优化对符号化的质量有巨大影响，而 DWARF 可以很好地表达它。

我们还看到 dSYM 和静态库包含 DWARF。

然而，请优先选择 dSYM，因为你可以轻松地将它们传输给其他人，并且许多工具内置了对它们的支持。
