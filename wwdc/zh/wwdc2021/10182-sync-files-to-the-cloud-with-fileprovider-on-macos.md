♪ ♪ 你好，我是来自云文件提供程序团队的 Johannes Fortmann，我来向你展示 macOS 上的文件提供程序。如果你是一家将用户文件同步到 macOS 的云存储厂商，那你就来对演讲了。在引言之后，我们将讨论同步文件所涉及的一些用户流程。接着我们会在 Xcode 中跑通其中一个流程，并讨论你实现各项支持的先后顺序。我们还会快速概览其他可选的集成点以及你的后续步骤。首先，让我们谈谈文件提供程序能为你做什么。

File Provider 框架让你可以把云存储整合到 macOS 的文件系统中。它使用新的 APFS 特性来支持按需下载用户文件和文件夹。这个 API 完全运行在用户态。我们正在弃用 macOS 上的内核扩展，因此如果你之前依赖 FUSE 或 KAUTH 来拦截系统调用或按需下载文件，这是一个很好的替代方案。

你所要做的就是处理上传、下载，并告诉我们远端发生了什么变化。系统会告诉你本地发生了什么变化，并处理其余的一切。所有这些功能都与系统深度集成，特别是与访达（Finder）集成。你的提供程序会显示在边栏中。文件状态会在访达中显示和跟踪，并且有多个可自定的 UI 集成点。你需要实现一个与系统集成的 App 扩展。它的生命周期由用户操作驱动。最初，你创建一个域（domain），它表示用户可以在你的云存储中访问的文件树。系统会在访达边栏中公开该域，并在文件系统中为该域创建一个根目录。此时，设备上还没有任何实际数据，但用户已经可以开始与根目录交互了。这是如何做到的？根目录就是我们所说的无数据目录（dataless directory）。它是 APFS 中一种新类型的对象，有相应的 API 来识别它们并与它们交互。但更重要的是，对于毫无准备偶然遇到无数据对象的进程来说，它们是完全透明的。读取会触发下载，文件会在允许继续读取之前失去其无数据属性。在本次演示中，我们将看到 File Provider 框架如何让你实现一些回调，当进程读取无数据文件时这些回调会被调用。

让我们看几个用户流程，让同步运转起来。我们将考察四个关键流程，它们同时涵盖下载同步和上传同步。在每个流程中，你都会看到系统在需要新数据时就会调用你的扩展。

我们会向你展示你可以与你的云服务器通信以拉取数据，最后调用一个完成处理程序来应答。首先，我们来看看读取一个无数据文件时会发生什么。

当内核检测到对无数据文件的读取访问时，该系统调用会被暂停，同时你的扩展被调用来获取文件内容。你的扩展的 fetchContents 方法会被调用。通常，你会把它实现为执行一次下载。下载完成后，它会调用一个完成处理程序。文件内容会被交给系统，系统会在不使已打开的文件描述符失效的情况下填充原先无数据的文件。然后系统解除读取访问的暂停。既然文件不再是无数据的，后续读取就不必再牵扯你的扩展了。枚举一个目录的工作方式非常相似。内核检测到一个 readdir 调用并将其暂停。它调用你的扩展来枚举该目录中的条目。你从服务器获取这些条目的元数据。然后你以若干条目应答。枚举是分页进行的。你可以只返回部分条目而非全部，系统会从中断的地方继续枚举。一旦所有页都被枚举完毕，系统就会放行最初的调用。与文件的情况一样，一旦目录被枚举过，后续的 readdir 调用就会使用磁盘上的内容，而不必再牵扯你的扩展。

但如果这些内容在远端发生了变化呢？嗯，你必须把远端的变化告知系统。让我们看看这是如何工作的。如果有远端变更，你的服务器可以向 Mac 发送推送通知。作为对该推送通知的响应，你向系统发出信号：有一些变更需要从一个特殊的枚举器——即 .workingSet——中枚举。系统会转而去枚举 .workingSet 中发生变化的条目。一个称为 syncAnchor 的续传令牌（continuation token）被用来只枚举新的变更。这个令牌由你的扩展定义。系统会记录它上次枚举到的 syncAnchor。它会用 enumerateChanges(from syncAnchor:) 方法调用你的枚举器。作为响应，你返回发生变化的条目，完成后，交给我们一个新的 syncAnchor 供下次使用。系统会异步地去更新用户可见的文件。我们使用 APFS 的比较并交换（compare-and-swap）特性，确保本地更改不会在这个过程中丢失。此外，系统会与文件协调以及其他咨询式锁定机制集成，以便与应用程序协调。

有了这三种机制，我们就能够从云端同步文件，并在发生远端变更时保持同步。最后一个流程处理的是把本地变更同步到云端。系统会检测本地条目何时发生变化，并在你的扩展上调用 modifyItem 方法，传入发生变化的字段的精确集合。它会把底层事件聚合为对同步有意义的变更。例如，内核会检测安全保存（safe save）并透明地把你的条目标识符重映射到新的文件 ID。如果你请求，系统还会为你压缩软件包（package）文件，并呈现一致的包级别变更。

作为对 modifyItem 调用的响应，你会在服务器端更新该条目的状态。如果文件内容发生了变化，系统会交给你已更改文件的一个克隆，这样即使随后又有变更，你也能上传一个一致的版本。

完成后，你调用一个完成处理程序。完成处理程序用于更新条目的版本标识符，并向你的扩展确认变更已送达。完成处理程序还接受条目的最终状态作为参数。在云端更新一个条目可能会改变它的状态，例如，当它与某个远端变更发生冲突时。由于你把最终状态传回，系统能够更新条目的本地状态，使之与云端的真实情况一致。

还有第五个流程：清除（eviction）。当磁盘空间紧急不足时，系统会自动清除本地文件，而不牵扯你的文件提供程序扩展。例如，当用户正在录制视频或下载软件更新时，就可能发生这种情况。系统会清除释放所需磁盘空间所必需的、最少数量的最近最少使用文件，以便写入那些新文件。让我们回顾一下这些状态转换。清除把本地文件变为无数据文件，下载把无数据文件变回本地文件。如果文件是在远端创建的，它们可以一开始就是无数据的；如果是本地创建的则不是。但并非所有文件都可以被清除。系统只会清除你报告为已上传的文件，以便它可以被再次下载。所以本地文件实际上分为两类：已上传和未上传的文件。本地编辑之后，文件的新版本需要被上传，于是我们又回到了不可清除的状态。

在本次演示中到目前为止，我们已经看到系统如何调用你的文件提供程序扩展，在访问时下载文件，并在本地编辑后上传文件。虽然磁盘压力触发的清除不需要你参与，但仍有一些方法可以让你从扩展中触发或阻止清除。

以上是大量的理论。让我们在实践中看看其中一个流程。

我们编写了一个 App，它运行一个小型本地文件服务器，并内嵌一个针对该服务器运作的文件提供程序扩展。它叫 FruitBasket。我已经登录到了那台服务器，所以边栏里有一个根文件夹的条目。我还选中了根文件夹，这促使系统为该文件夹中的条目创建无数据条目。你可以从文件名旁边的云下载图标看出这些条目是无数据的。

我们将在命令行上使用「cat」来读取一个文件。由于该文件是无数据的，这会在我们的扩展中触发一次内容获取。我已经在 Xcode 中附加到了该扩展，并设置了一个断点来拦截这次内容获取。

「cat」正在运行，我们的断点已命中。由于我们阻塞了内容获取的完成，Terminal 窗口中的读取也被阻塞了。注意在访达窗口中，云图标已被进度指示器取代。系统对下载状态有着一致的认识。当然，因为我们实际上是被阻塞在调试器中而不是忙于下载，进度并没有更新。

让我们继续。我在调用完成处理程序之前设置了第二个断点。

此时，我们的提供程序已将文件内容下载到磁盘上的一个本地 URL。一旦我们调用完成处理程序，系统就会用我们下载的内容替换用户可见文件的内容。让我们在 Xcode 中继续执行，为系统解除阻塞。访达中的状态更新为显示该文件是本地的，被 cat 进程阻塞的读取也成功了。

我仍然保留着那些断点，但现在文件已经是本地的了，我可以再次运行「cat」而不会命中断点。那些读取针对的是普通的本地文件，不会牵扯我们的扩展。

当然，这只是我们示例文件提供程序功能集的一小部分。我们已经涵盖了 API 的完整功能集，并且将在本次 session 中发布源代码。让我们谈谈你可以如何着手实现我们讨论过的这些流程。首先，我们要告诉系统我们已经准备好同步。这会让一个条目出现在访达的边栏中。我们把这些条目称为域，它们通常对应于你的云服务器上的一个登录会话。每个域都有一个唯一标识符，要让它显示出来，你需要创建一个新实例并通过管理器对象添加它。你也可以移除一个域。你通常会在用户登出时这样做，但这在最初的开发和测试中也很有用。随着域显示在访达中，只要你导航到该条目，系统就会请求枚举其中的条目。所以接下来我们来实现这一点。我们的第一步是实现一个条目类。它的实例表示我们要枚举的各个条目。然后我们实现一个枚举器，在系统请求时把我们的条目提交给系统。此时，我们就可以通过导航到边栏条目来查看目录了。当然，这些目录中的所有文件都将是无数据的。让我们通过实现内容获取来改变这一点。当我们打开其中一个无数据文件时，系统会调用 fetchContents 方法。我们的任务是把文件内容下载到磁盘上的某个位置，然后用该位置的 URL 调用完成处理程序。系统会使用这些内容来填充无数据文件，然后替我们清理它们。为了让我们的目录结构保持同步，我们还要实现另一种类型的枚举器。这一个用于同步远端变更。系统会先调用 currentSyncAnchor 方法来获取同步锚点。你返回一个数据对象，描述你的数据库的变更游标。每当你发出信号表示有内容发生变化时，系统就会请求自你上次提供的锚点以来的变更。然后你可以返回这些变更，最后返回一个新锚点。最后一步是允许向上同步变更。如果系统检测到本地文件发生了变化，它会调用三个方法之一来创建、修改或删除现有条目。让我们快速看一下创建方法。系统把它要求你创建的新条目交给你。这是一个系统条目，不过它遵循与你自己的条目相同的协议。系统还会交给你一组该条目上受关注的字段。例如，条目可能附有扩展属性，也可能没有，有相应的字段来描述这一点。如果 content 字段已被设置，系统会向你传递一个带有内容的文件 URL。描述文件夹或符号链接的条目则不会有内容。你的任务是把新的本地条目的数据上传到服务器，然后用生成的远端条目调用完成处理程序。

就是这样。此时，你在 macOS 上就拥有了一个功能完备的文件提供程序，能够按需提供文件、把本地更改传播到云端、把远端更改传播到 Mac。File Provider 框架中还有许多额外的可选 API，可以实现与系统更细粒度的集成。让我们来看一看。

图标装饰可用于在访达中美化条目。你可以为文件图标添加角标、给文件夹压印图案，或标示共享状态。你通过在 App 中声明的一个 UTType 来提供用于装饰的自定义图稿。

上下文菜单操作允许用户通过上下文菜单对你的文件执行自定义操作。有带 UI 和不带 UI 两种变体。你可以用在扩展的 Info.plist 中声明的 NSPredicate 来定义这些操作适用于哪些文件。

预检提醒让你可以在用户执行可能有意外后果的操作之前向其发出警告。提醒 UI 以及激活提醒的条件同样在 Info.plist 中配置。
