在计算技术的早期，程序很难阅读，因为它们被写成一系列指令，控制流可以在各处随意跳转。你今天看不到这种情况了，因为语言使用结构化编程来使控制流更加统一。例如，if-then 语句使用了结构化的控制流。它指定一个嵌套的代码块在从上到下的执行过程中，仅在满足条件时才执行。在 Swift 中，这个代码块也遵循静态作用域，这意味着只有在封闭的代码块中定义的名称才是可见的。这也意味着在离开代码块时，其中定义的任何变量的生命周期都会结束。因此，带有静态作用域的结构化编程使得控制流和变量生命周期易于理解。

更一般地说，结构化的控制流可以自然地组合和嵌套。这让你可以自上而下地阅读整个程序。这些就是结构化编程的基础。正如你所想，这一点很容易被视为理所当然，因为对我们今天来说它太直观了。但如今的程序包含了异步和并发代码，而它们一直无法利用结构化编程来使这些代码更易于编写。首先，让我们看看结构化编程是如何让异步代码变得更简单的。假设你需要从互联网获取一系列图片，并将它们顺序调整为缩略图大小。这段代码异步地完成这项工作，它接收一个包含图片标识符的字符串集合。你会注意到，这个函数在被调用时并不返回值。这是因为该函数将它的结果或错误传递给一个给定的完成处理程序（completion handler）。这种模式允许调用者在稍后的时间点收到答案。作为这种模式的一个结果，这个函数无法使用结构化的控制流来进行错误处理。这是因为，处理从函数中抛出的错误才有意义，而处理传入函数的错误则不然。此外，这种模式会阻止你使用循环来处理每个缩略图。必须使用递归，因为在函数完成后运行的代码必须嵌套在处理程序内部。

你可以创建额外的任务来为程序增加并发。任务（Task）是 Swift 中的一个新特性，它与异步函数紧密配合。任务为运行异步代码提供了一个全新的执行上下文。每个任务都相对于其他执行上下文并发运行。在安全且高效的情况下，它们会被自动调度以并行方式运行。由于任务深度集成到 Swift 中，编译器可以帮助防止一些并发 bug。另外，请记住，调用一个异步函数并不会为该调用创建一个新任务。你需要显式地创建任务。在 Swift 中有几种不同类型的任务，因为结构化并发是关于灵活性（flexibility）和简单性（simplicity）之间的平衡。因此，在本场次的剩余时间里，Joe 和我将介绍并讨论每种任务，以帮助你理解它们之间的权衡。让我们从这些任务中最简单的一种开始，它通过一种新的语法形式创建，称为 async-let 绑定（async-let binding）。为了帮助你理解这种新的语法形式，我想先分解一下普通 let 绑定的求值过程。它有两个部分：等号右侧的初始化器表达式和左侧的变量名。在 let 前后可能还有其他语句，所以我把它们也包含在这里。一旦 Swift 遇到一个 let 绑定，它的初始化器就会被求值以产生一个值。在这个例子中，这意味着从一个 URL 下载数据，这可能需要一些时间。数据下载完成后，Swift 会将该值绑定到变量名，然后继续执行后面的语句。注意，这里只有一个执行流，如箭头追踪的每一步所示。由于下载可能需要一些时间，你可能希望程序开始下载数据，并在实际需要数据之前继续做其他工作。为了实现这一点，你只需在一个已有的 let 绑定前面加上 `async` 关键字。这将它变成了一个并发的绑定，称为 async-let。并发绑定的求值与顺序绑定有很大不同，所以让我们来了解它是如何工作的。我将从即将遇到绑定之前的那一刻开始。为了求值一个并发绑定，Swift 会首先创建一个新的子任务（child task），它是创建它的那个任务的一个子任务。因为每个任务都代表程序的一个执行上下文，所以这一步会有两个箭头同时出来。第一个箭头给子任务，它将立即开始下载数据。第二个箭头给父任务，它将立即把变量 result 绑定到一个占位值上。这个父任务就是执行前面语句的同一个任务。在子任务并发下载数据的同时，父任务继续执行并发绑定之后的语句。但是，当遇到一个需要 result 实际值的表达式时，父任务将等待（await）子任务完成，这将填充 result 的占位符。在这个例子中，我们对 URLSession 的调用也可能抛出一个错误。这意味着等待结果可能会给我们一个错误。所以我需要写 `try` 来处理它。而且别担心。再次读取 result 的值不会重新计算它。

现在你已经了解了 async-let 的工作原理，你可以用它来为缩略图抓取代码添加并发。我已经将之前代码中获取单个图片的部分提取成一个单独的函数。这里的这个新函数也从两个不同的 URL 下载数据：一个是全尺寸图片本身，另一个是元数据，其中包含最佳的缩略图尺寸。注意，对于顺序绑定，你在 let 的右侧写 `try await`，因为在那里会观察到错误或挂起。为了让两个下载并发进行，你在这两个 let 前面都写 `async`。由于下载现在发生在子任务中，你不再需要在并发绑定的右侧写 `try await`。只有在父任务使用并发绑定的变量时，才会观察到这些效果。所以你在读取元数据和图片数据的表达式前面写 `try await`。另外，注意使用这些并发绑定的变量并不需要方法调用或任何其他更改。这些变量与它们在顺序绑定中具有相同的类型。

现在，我一直谈论的这些子任务实际上是一个称为任务树（task tree）的层级结构的一部分。这棵树不仅仅是一个实现细节。它是结构化并发的重要组成部分。它会影响你的任务的属性，如取消、优先级和任务本地变量（task-local variables）。每当你从一个异步函数调用另一个异步函数时，同一个任务被用来执行该调用。因此，函数 `fetchOneThumbnail` 继承了该任务的所有属性。当创建一个新的结构化任务（如使用 async-let）时，它成为当前函数正在其上运行的任务的子任务。任务不是某个特定函数的子任务，但它们的生命周期可能被限定在该函数的作用域内。这棵树由每个父任务与其子任务之间的链接组成。一个链接强制执行一条规则：父任务只有在它的所有子任务都完成后才能完成它的工作。即使面对可能导致子任务不会被等待的异常控制流，这条规则也成立。例如，在这段代码中，我首先等待元数据任务，然后才等待图片数据任务。如果第一个被等待的任务通过抛出一个错误而结束，`fetchOneThumbnail` 函数必须通过抛出该错误来立即退出。但是，执行第二个下载的任务会发生什么？在异常退出期间，Swift 会自动将未被等待的任务标记为已取消（canceled），然后等待它完成，再退出函数。将任务标记为已取消并不会停止该任务。它只是通知任务，它的结果不再需要了。事实上，当一个任务被取消时，所有作为该任务后代的子任务也会被自动取消。因此，如果 URLSession 的实现创建了它自己的结构化任务来下载图片，这些任务也会被标记为取消。一旦所有由 `fetchOneThumbnail` 直接或间接创建的结构化任务都完成，该函数最终通过抛出错误来退出。这个保证是结构化并发的基础。它通过帮助你管理任务的生命周期，防止你意外泄漏任务，很像 ARC 自动管理内存生命周期那样。

到目前为止，我已经向你概述了取消是如何传播的。但是任务最终什么时候停止呢？如果任务正处于一个重要的事务中间，或者有打开的网络连接，直接中止任务是不正确的。这就是为什么 Swift 中的任务取消是协作式的（cooperative）。你的代码必须显式地检查取消，并以任何适当的方式结束执行。你可以从任何函数（无论它是否是异步的）中检查当前任务的取消状态。这意味着你在设计 API 时应该考虑到取消，特别是如果它们涉及长时间运行的计算。你的用户可能从一个可以被取消的任务中调用你的代码，他们会期望计算尽快停止。为了了解如何使用协作式取消是多么简单，让我们回到缩略图抓取的例子。

在这里，我重写了最初的函数（该函数被赋予了所有要抓取的缩略图），以便它使用 `fetchOneThumbnail` 函数。如果在被取消的任务中调用了这个函数，我们不想通过创建无用的缩略图来拖慢我们的应用。所以我可以在每次循环迭代的开始添加一个对 `checkCancellation` 的调用。这个调用只有在当前任务已被取消时才抛出一个错误。你也可以以布尔值的形式获取当前任务的取消状态，如果这对你的代码更合适的话。注意，在这个版本的函数中，我返回了一个部分结果，一个只包含部分请求的缩略图的字典。当这样做时，你必须确保你的 API 清楚地说明可能会返回一个部分结果。否则，任务取消可能会为你的用户触发一个致命错误，因为他们的代码即使在取消期间也需要一个完整的结果。

到目前为止，你已经看到 async-let 为你的程序添加并发提供了一种轻量级的语法，同时保留了结构化编程的精髓。我想告诉你的下一种任务称为任务组（group task）。它们提供了比 async-let 更多的灵活性，同时没有放弃结构化并发的所有优良特性。正如我们之前看到的，当并发的数量是固定的时，async-let 表现得很好。让我们考虑我之前讨论的两个函数。对于循环中的每个缩略图 ID，我们调用 `fetchOneThumbnail` 来处理它，这会创建恰好两个子任务。即使我们将该函数的主体内联到这个循环中，并发的数量也不会改变。Async-let 的作用域像变量绑定一样。这意味着两个子任务必须在下一个循环迭代开始之前完成。但是，如果我们希望这个循环启动任务来并发地抓取所有缩略图呢？那么，并发的数量就不是静态可知的，因为它取决于数组中 ID 的数量。适用于这种情况的工具是任务组（task group）。

任务组是结构化并发的一种形式，旨在提供动态数量的并发。你可以通过调用 `withThrowingTaskGroup` 函数来引入一个任务组。这个函数会给你一个作用域限定的组对象，用于创建可以抛出错误的子任务。添加到组中的任务的生命周期不能超出定义该组的块的作用域。由于我已经将整个 for 循环放在了块内部，我现在可以使用该组创建动态数量的任务。你通过调用组的 `async` 方法来在组中创建子任务。一旦添加到组中，子任务立即开始执行，并且顺序是任意的。当组对象超出作用域时，组内所有任务的完成会被隐式地等待。这是我在前面描述的任务树规则的一个结果，因为组任务也是结构化的。在这一点上，我们已经实现了我们想要的并发：每次调用 `fetchOneThumbnail` 都有一个任务，而它本身又会使用 async-let 再创建两个任务。这是结构化并发的另一个好特性。你可以在组任务内部使用 async-let，或者在 async-let 任务内部创建任务组，并且树中的并发层级会自然地组合。

现在，这段代码还不能直接运行。如果我们试图运行它，编译器会很乐意地提醒我们一个数据争用（data race）问题。问题在于，我们试图从每个子任务向一个单一的字典插入一个缩略图。这是在增加程序并发量时一个常见的错误。数据争用被意外地创建了。这个字典无法同时处理多个访问，如果两个子任务试图同时插入缩略图，可能会导致崩溃或数据损坏。在过去，你必须自己调查这些 bug，但 Swift 提供了静态检查来首先防止这些 bug 的发生。每当你创建一个新任务时，该任务执行的工作是在一种称为 @Sendable 闭包（@Sendable closure）的新闭包类型中进行的。@Sendable 闭包的主体被限制为不能捕获其词法上下文中的可变变量，因为这些变量可能在任务启动后被修改。这意味着你在任务中捕获的值必须是安全的，可以共享。例如，因为它们是值类型，如 Int 和 String，或者因为它们是被设计为可从多个线程访问的对象，如 Actor，以及实现了自己同步机制的类。我们有一个专门讨论这个主题的场次，叫做“利用 Swift Actor 保护可变状态”，所以我鼓励你去看看。为了避免我们示例中的数据争用，你可以让每个子任务返回一个值。这种设计将处理结果的唯一责任交给了父任务。在这种情况下，我指定每个子任务必须返回一个包含缩略图的 String ID 和 UIImage 的元组。然后，在每个子任务内部，不是直接写入字典，而是让它们返回键值元组供父任务处理。父任务可以使用新的 for-await 循环来迭代每个子任务的结果。for-await 循环按照完成顺序获取子任务的结果。由于这个循环是顺序执行的，父任务可以安全地将每个键值对添加到字典中。这只是使用 for-await 循环访问异步值序列的一个例子。如果你自己的类型遵循 AsyncSequence 协议，那么你也可以使用 for-await 来遍历它们。你可以在“认识 AsyncSequence”场次中找到更多信息。

虽然任务组是结构化并发的一种形式，但任务组任务与 async-let 任务在任务树规则的实现方式上有一个小差异。假设在遍历这个组的结果时，我遇到了一个以错误结束的子任务。因为该错误被抛出了组的作用域块，组中的所有任务随后会被隐式地取消并等待。这与 async-let 的工作方式相同。差异出现在你的组通过块的正常退出而超出作用域时。此时，取消不是隐式的。这种行为使你更容易使用任务组来表达分叉-连接（fork-join）模式，因为这些任务只会被等待，而不会被取消。你也可以在退出块之前使用组的 `cancelAll` 方法手动取消所有任务。请记住，无论你如何取消一个任务，取消都会自动在树中向下传播。Async-let 和组任务是 Swift 中提供作用域限定的结构化任务的两种任务类型。现在，我把时间交给 Joe，他将告诉你关于非结构化任务（unstructured tasks）的信息。

谢谢，Kavon。大家好。我是 Joe。Kavon 向你展示了当你在程序中添加具有清晰层级结构的任务时，结构化并发如何简化错误传播、取消和其他记账工作。但我们知道，当你在程序中添加任务时，并不总是有一个层级结构。Swift 也提供了非结构化任务 API，它们提供了更多的灵活性，代价是需要更多的手动管理。在很多情况下，任务可能不会落入一个清晰的层级结构。最明显的，如果你试图从非异步代码中启动一个任务来执行异步计算，你可能根本没有父任务。或者，你为一个任务设想的生命周期可能不适合单个作用域甚至单个函数的限制。例如，你可能想要在一个方法调用（使对象进入活动状态）时启动一个任务，然后在另一个方法调用（使对象进入非活动状态）时取消它的执行。这在实现 AppKit 和 UIKit 中的委托（delegate）对象时经常出现。UI 工作必须在主线程（main thread）上发生，正如 Swift Actor 场次中讨论的那样，Swift 通过声明属于主要 Actor（main actor）的 UI 类来确保这一点。

假设我们有一个集合视图，并且我们还不能使用集合视图的数据源 API。相反，我们想使用我们刚刚编写的 `fetchThumbnails` 函数，在集合视图中的项目显示时从网络获取缩略图。然而，委托方法不是异步的，所以我们不能直接 `await` 对一个异步函数的调用。我们需要为此启动一个任务，但这个任务实际上是我们响应委托操作而开始的工作的扩展。我们希望这个新任务仍然在主要 Actor 上以 UI 优先级运行。我们只是不想将任务的生命周期限制在这个单一的委托方法的作用域内。对于这样的情况，Swift 允许我们构造一个非结构化任务。让我们将代码的那个异步部分移动到一个闭包中，并将该闭包传递给 `Task` 的构造器来创建一个异步任务。现在看看运行时会发生什么。当我们到达创建任务的那一点时，Swift 会将其调度到与原始作用域相同的 Actor 上运行，在这个例子中就是主要 Actor。同时，控制权立即返回给调用者。缩略图任务会在有机会这样做的时候在主线程上运行，而不会立即阻塞主线程在委托方法上。以这种方式构造任务给了我们一个介于结构化和非结构化代码之间的中间点。直接构造的任务仍然继承其启动上下文的 Actor（如果有的话），并且它也继承原始任务的优先级和其他特性，就像组任务或 async-let 一样。然而，新任务是无作用域的（unscoped）。它的生命周期不受其启动作用域的限制。原始上下文甚至不需要是异步的。我们可以在任何地方创建无作用域的任务。作为交换所有这些灵活性的代价，我们也必须手动管理那些结构化并发本会自动处理的事情。取消和错误不会自动传播，并且除非我们采取显式操作，否则任务的执行结果不会被隐式地等待。

所以，当一个集合视图项目被显示时，我们启动了一个任务来获取缩略图，如果该项目在缩略图准备好之前滚出视图，我们也应该取消该任务。由于我们正在处理一个无作用域的任务，这种取消不会是自动的。让我们现在来实现它。在构造任务之后，让我们保存我们得到的值。当我们创建任务时，我们可以将这个值放入一个以行索引为键的字典中，以便稍后可以使用它来取消该任务。我们还应该在任务完成后从字典中移除它，这样我们就不会在任务已经完成时试图取消它。注意这里，我们可以在该异步任务的内部和外部访问同一个字典，而不会导致编译器标记数据争用。我们的委托类绑定到主要 Actor，新任务继承了这一点，所以它们永远不会并行运行。我们可以安全地在此任务内部访问绑定到主要 Actor 的类的存储属性，而无需担心数据争用。同时，如果稍后通知我们的委托说同一个表格行已从显示中移除，那么我们可以调用该值的 `cancel` 方法来取消任务。所以我们现在已经看到了如何创建不依赖于作用域运行的非结构化任务，同时仍然继承该任务原始上下文的一些特性。

但有时你不想从你的原始上下文中继承任何东西。为了获得最大的灵活性，Swift 提供了分离任务（detached tasks）。顾名思义，分离任务独立于其上下文。它们仍然是非结构化任务。它们的生命周期不受其原始作用域的限制。但分离任务也不会从其原始作用域中继承任何其他东西。默认情况下，它们不受相同 Actor 的约束，也不必以与启动时相同的优先级运行。分离任务以通用的默认值（如优先级）独立运行，但它们也可以使用可选参数启动，以控制新任务的执行方式和位置。

假设在从服务器获取缩略图之后，我们想将它们写入一个本地磁盘缓存，这样如果我们稍后试图获取它们，就不必再次访问网络。缓存不需要在主要 Actor 上进行，并且即使我们取消了所有缩略图的获取，缓存我们已经获取到的任何缩略图仍然是有用的。所以，让我们使用一个分离任务来启动缓存。当我们分离一个任务时，我们在设置该新任务如何执行方面也获得了更多的灵活性。缓存应该以较低的优先级进行，以免干扰主要的 UI，并且我们可以在分离这个新任务时指定后台优先级。让我们现在稍微规划一下未来。如果以后我们希望对缩略图执行多个后台任务，我们应该怎么做？我们可以分离更多的后台任务，但我们也可以在我们的分离任务内部利用结构化并发。我们可以将所有不同类型的任务组合起来，以发挥它们各自的优势。与其为每个后台任务分离一个独立的任务，不如建立一个任务组，并将每个后台任务作为一个子任务添加到该组中。这样做有很多好处。如果我们确实需要在未来取消后台任务，使用任务组意味着我们只需取消顶层的那个分离任务，就可以取消所有子任务。这种取消随后会自动传播到子任务，我们不需要跟踪一个句柄数组。此外，子任务会自动继承其父任务的优先级。为了将所有这项工作保持在后台，我们只需要将分离任务设为后台，这将自动传播到它的所有子任务，所以我们不必担心忘记传递设置后台优先级的操作，并意外地饿死 UI 工作。
