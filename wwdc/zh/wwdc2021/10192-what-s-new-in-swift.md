Swift Collections 是一个新的开源数据结构包，是对 Swift 标准库里已有数据结构的补充。Swift Collections 的初始版本包含了三种被请求得最频繁的数据结构的实现：Deque、OrderedSet 和 OrderedDictionary。

Deque 有点像 Array，不同的是它支持在两端都进行高效的插入和删除操作。OrderedSet 是 Array 和 Set 的一种强大混合体：像 Array 一样，OrderedSet 保持元素的顺序，并支持随机访问；像 Set 一样，OrderedSet 确保每个元素只出现一次，并提供高效的成员检测。

最后是 OrderedDictionary，当顺序很重要、或者我们需要对元素做随机访问时，它是 Dictionary 的一个很有用的替代方案。接下来，我们聊聊 Swift Algorithms。Swift Algorithms 是一个新的开源包，提供针对 Sequence 和 Collection 的算法。

我们已经给 Swift Algorithms 添加了超过 40 种算法，用来做诸如生成一个元素集合的所有组合或排列、按二个或三个一组遍历一个序列的元素、或者按某个谓词决定的分组来遍历、又或者从一个集合里选出最小的五个元素、最大的五个元素、或者干脆随机选五个这样的事情。

学习这套词汇需要花一点功夫，但一旦学会了，你会惊讶地发现，原来有这么多算法都近在眼前、只是你没注意到。

而在面向 Windows 时，Windows 路径那种复杂的根成分，也完全被所有这些新的 FilePath API 支持。接下来，我们聊聊 Swift Numerics。今年，Swift Numerics 收获了不少重大新增内容。去年，我们把 Float16 带到了 iOS、tvOS 和 watchOS。今年，我们给 Apple Silicon Mac 添加了 Float16 支持，并且支持构造基于 Float16 的复数。今年的另一项新增内容，是给所有的初等函数（比如 log、sine、cosine）都添加了复数支持。因为这些实现是用 Swift 写的，它们往往比传统的 C 库更高效，还能实现一些原本不可能做到的优化。最后，我们聊聊 Swift ArgumentParser。今年我们持续打磨了 Swift ArgumentParser，加入了一些增强功能，比如为 Fish shell 生成代码补全脚本的能力、连写的短选项，以及改进后的错误信息。今年春天，我们还迈过了一个重要的里程碑：ArgumentParser 被 Xcode 12.5 里的 Swift Package Manager 所采用。没错！如果你最近用过 Swift Package Manager 的命令行工具，那你其实已经在用 Swift ArgumentParser 了。接下来，我想聊聊我们为支持在服务器端使用 Swift 所做的一些工作。去年，我们添加了对包括 Amazon Linux 在内的一些平台的支持。今年，我们在此基础上继续推进，投入精力提升 Swift 服务器应用的性能和功能。

我们首先在 Linux 上启用了静态链接，这提升了应用的启动时间，也简化了服务器应用的部署——现在可以把它们部署成单个文件了。此外，在 Swift 5.5 里，Linux 上使用的 JSON 编码和解码被从头重新实现了一遍，在大多数常见使用场景下带来了性能提升。最后，我们增强并优化了 AWS Lambda runtime 库本身的性能。所有这些工作，让运行在 AWS Lambda 上的 Swift 程序启动速度提升了 33%，而通过 AWS API Gateway 路由的 lambda 调用耗时也缩短了 40%。除了优化 AWS runtime 库的性能之外，我们还对它做了重构，改用我们新的 async/await 模型，而不是闭包。提升 Swift 开发者体验，是 Swift 5.5 的另一个重点方向。我想先从文档讲起。提供出色的文档，是为一个框架的使用者打造顺畅、愉悦体验的关键。今年，我们要推出 DocC，一个深度集成在 Xcode 13 里的文档编译器，帮助你教会开发者怎样使用你的 Swift 框架或包。编写和分享出色的文档，现在比以往任何时候都更容易。

DocC 是从零开始构建的，用的都是你已经熟悉和喜爱的工具和技术，比如你 Swift 源代码里的 Markdown 注释，这样你就可以轻松地编写和 diff 你的文档。

我们准备了四场精彩的演讲，来给大家展示 Xcode 里 DocC 文档的方方面面，我强烈建议大家去看看。现在，我很兴奋地宣布，Swift DocC 将在今年晚些时候开源。把 Swift DocC 开源，将让开发者能更容易地在 Swift 支持的所有平台上生成出色的文档。

在 Swift 5.5 里，我们在类型检查器的质量和性能改进上做了投入。其中一个结果是，你在编译代码时会看到更少的「expression too complex」错误。我们还提升了数组字面量类型检查的性能。

在这个版本里，我们还通过三项加快增量构建的重大改进，提升了开发者的生产力。首先，我们现在支持增量导入，也就是说，当某个模块发生变化时，我们不再需要重新构建每一个导入了这个模块的源文件。此外，我们现在会提前计算好模块依赖图，这样我们就能快速地只对发生变化的部分启动增量构建。最后，我们把选择性重新编译扩展到了 extension 上，也就是说，当你修改一个 extension 的方法体时，需要重新编译的内容变少了。以 SwiftDriver 这个开源项目为例，平均而言，用上 Swift 5.5 里的增量导入之后，当被导入的模块发生变化时，我们现在需要重新编译的文件数量还不到原来的十分之一，构建时间也减少了大约三分之一。增量导入带来的性能提升，意味着你现在可以对你的项目做模块化拆分、并修改一个被导入的模块，而不用为构建性能付出巨大的代价。顺便说一句，其中一些性能提升，得益于 Swift 项目的一个重要里程碑——编译器的第一部分被改用 Swift 编写。这就是 Swift Driver，负责协调 Swift 源代码编译过程的程序。这个项目始于 2019 年末，从 Xcode 13 开始，它已经成为 Swift 编译的默认方式。最后，我们聊聊我们为让 Swift 里的内存管理更高效而做的改进，让 Swift 程序能更快地回收内存。Swift 的类实例使用自动引用计数（ARC）来追踪在任意给定时刻，某个特定对象有多少个引用。在大多数情况下，这意味着内存管理在 Swift 里是自动生效的，你自己不需要去操心内存管理。当类实例不再需要时，ARC 会自动释放它们所占用的内存。为此，Swift 编译器会在每次创建新引用时插入一次 retain 操作，并在每次某个引用不再被使用时插入一次 release 操作。今年，我们在编译器内部引入了一种追踪引用的新方式，让编译器能够显著减少 retain 和 release 操作的数量。我们已经从这项改动中看到了可衡量的性能提升和代码体积缩减。我们添加了一个 Xcode 设置项，叫 Optimize Object Lifetimes，让你能看到这项更激进的新 ARC 优化对你代码的影响。关于 ARC 的更多信息，请查看《Swift 中的 ARC》这场演讲。

以上只是 Swift 5.5 带来的部分改进。接下来，Tim 会跟大家聊聊 Swift 并发，以及 Swift 语言的其他演进。谢谢，Nicole。我们都对 Swift 并发感到非常兴奋，但在讲到这个之前，我想先聊聊我们对 Swift 做的一些其他改动，它们能简化和提升日常编程体验。

这是我们今年做的一系列人体工程学改进的清单。这些 SE 编号对应的是 Swift Evolution 提案。每一份提案都是由社区的某位成员撰写的，在 Swift Evolution 论坛上经过讨论，并在被采纳进这门语言之前，得到了 Swift 核心团队的批准。所有的 SE 提案——不论是被采纳、被拒绝，还是仍在讨论中——都可以在 GitHub 上的 Swift Evolution 仓库里找到。我们来看看其中的几项改动。首先是结果构建器（Result Builder）。当 SwiftUI 第一次公布时，它引入了一种新语法，可以用来快速、轻松地描述复杂的对象层次结构。在过去这一年里，这种语法通过 Swift Evolution 流程被标准化并加以完善，以便能更容易地用在各种各样的场景里。如果你想利用这项强大的技术，我们有一场演讲专门讲解怎样使用结果构建器。Codable 协议是序列化数据的一种便利方式，但长久以来它一直缺了一块明显的东西。设想一下这个带两个 case 的枚举，要让它遵循 Codable，你以前必须手动实现所有这些样板代码。现在，你只需要声明遵循 Codable，编译器就会替你完成所有这些工作。

里，当你向远程服务器发出请求之后，可能要过很长一段延迟，你才会收到响应、才需要做更多工作。理想情况下，你的代码在这段延迟期间应该被挂起，这样在你能够对响应做出处理之前，它就不会占用任何资源。相比之下，并发代码指的是你有两个或更多代码块，希望它们同时运行。它们通常是相互独立、但又彼此相关的操作，比如处理一段视频的好几帧，或者在你用上一组结果更新 UI 的同时，运行一次 ML 分类器的下一轮迭代。带着这些概念，我们先来看一个不使用 Swift 新特性的简单异步编程例子。如果你写过不少 iOS 或 macOS 程序，你可能已经写过很多次和这个类似的代码了。这段代码用 Foundation 的 URLSession 类来发起一次网络调用。dataTask 从语法上讲，async 和 await 这两个关键字的用法，和 throws 与 try 很类似。async 修饰函数声明，表示这个函数必须被编译成支持挂起的形式；用 await 关键字来标记任何对 async 函数、方法或闭包的调用。当然，完整的机制比我在这里展示的要有意思得多。你可以观看《认识 Swift 中的 async/await》和《Swift 并发：幕后揭秘》这两场演讲，来了解这一切具体是怎么运作的。接下来，我们来看看 Swift 全新的并发支持，它是建立在我刚才描述的 async/await 概念之上的。
