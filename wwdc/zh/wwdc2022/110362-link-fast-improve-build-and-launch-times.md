首先，链接器按命令行顺序处理文件。它找到的第一个文件是 `main.o`。它加载 `main.o` 并在符号表中找到了 `main` 的定义。但同时也发现 `main` 有一个未定义的 `foo`。然后链接器解析命令行上的下一个文件，即 `foo.o`。这个文件添加了 `foo` 的定义。这意味着 `foo` 不再未定义。但是加载 `foo.o` 也添加了一个新的未定义符号 `bar`。现在命令行上的所有 `.o` 文件都已加载，链接器会检查是否还有任何剩余的未定义符号。在这种情况下，`bar` 仍然是未定义的，因此链接器开始检查命令行上的库，看是否有库能满足这个缺失的未定义符号 `bar`。链接器发现静态库中的 `bar.o` 定义了符号 `bar`。因此链接器从归档中加载了 `bar.o`。此时不再有任何未定义的符号，因此链接器停止处理库。链接器进入下一阶段，为程序中所有的函数和数据分配地址。然后它将所有函数和数据复制到输出文件中。就这样！你得到了输出程序。注意，`baz.o` 在静态库中，但并未被加载到程序中。它没有被加载，这是因为链接器从静态库中选择性加载的方式。这一点并不明显，但它是静态库的关键特性。现在你已经了解了静态链接和静态库的基础知识。让我们继续讨论 Apple 静态链接器（称为 ld64）的最新改进。应广泛要求，我们今年花了些时间来优化 ld64。而今年的链接器...对于许多项目来说，速度快了两倍。我们是如何做到的呢？我们现在更好地利用了开发机器上的多核性能。我们发现了许多领域可以使用多核并行执行链接器工作。这包括将内容从输入文件复制到输出文件，并行构建 LINKEDIT 的不同部分，以及更改 UUID 计算和代码签名哈希以便并行执行。接下来，我们改进了许多算法。事实证明，如果你改用 C++ 的 `string_view` 对象来表示每个符号的字符串切片，导出前缀树（exports-trie）构建器的运行效果会非常好。我们还使用了最新的加密库，这些库在计算二进制文件的 UUID 时利用了硬件加速，并且我们还改进了其他算法。

在优化链接器性能的过程中，我们注意到一些 App 中存在影响链接时间的配置问题。接下来，我将讨论在项目中可以做些什么来缩短链接时间。我将涵盖五个主题。首先，你是否应该使用静态库。然后介绍三个鲜为人知但对链接时间影响很大的选项。最后，我将讨论一些可能让你感到惊讶的静态链接行为。第一个主题是，如果你正在积极开发某个源文件，而该文件构建到静态库中，那么你就引入了构建时间的减慢。因为文件被编译后，整个静态库都必须重建，包括其目录（table of contents）。这仅仅是额外的 I/O 开销。静态库最适合用于稳定的代码。也就是说，不是正在频繁变更的代码。你应该考虑将活跃开发的代码移出静态库，以减少构建时间。之前我们展示了从归档中选择性加载。但其缺点是会减慢链接器的速度。这是因为为了确保构建的可重现性并遵循传统的静态库语义，链接器必须以固定的串行顺序处理静态库。这意味着 ld64 的一些并行化优势无法在静态库上使用。但如果你并不真正需要这种历史行为，你可以使用一个链接器选项来加速构建。这个链接器选项叫做“all load”。它告诉链接器盲目地加载所有静态库中的所有 `.o` 文件。如果你的 App 最终无论如何都会从所有静态库中加载大部分内容，那么这个选项会很有帮助。使用 `-all_load` 将允许链接器并行解析所有静态库及其内容。但是，如果你的 App 使用了巧妙的技巧，有多个静态库实现了相同的符号，并且依赖静态库的命令行顺序来决定使用哪个实现，那么这个选项就不适合你。因为链接器会加载所有实现，并且可能无法获得常规静态链接模式下的符号语义。`-all_load` 的另一个缺点是它可能会使你的程序变大，因为会加入“未使用”的代码。为了弥补这一点，你可以使用链接器选项 `-dead_strip`。该选项会促使链接器移除不可达的代码和数据。死代码剥离算法速度很快，并且通常可以通过减小输出文件的大小而弥补自身的开销。但是，如果你有兴趣使用 `-all_load` 和 `-dead_strip`，你应该测试一下使用和不使用这些选项的链接器时间，看看在你的特定情况下是否有利。下一个链接器选项是 `-no_exported_symbols`。这里需要一点背景知识。链接器生成的 LINKEDIT segment 的一部分是一个导出前缀树，它是一个编码了所有导出符号名称、地址和标志的前缀树。虽然所有 dylib 都需要有导出的符号，但主 App 二进制文件通常不需要任何导出的符号。也就是说，通常不会有任何东西在主可执行文件中查找符号。如果是这种情况，你可以为 App 目标使用 `-no_exported_symbols` 来跳过在 LINKEDIT 中创建该树形数据结构，这将缩短链接时间。但是，如果你的 App 会加载链接回主可执行文件的插件，或者你使用 xctest 并以你的 App 作为宿主环境来运行 xctest bundle，那么你的 App 必须导出所有符号，这意味着你不能在该配置下使用 `-no_exported_symbols`。而且，只有当导出前缀树很大时，尝试抑制它才有意义。你可以运行下面显示的 `dyld_info` 命令来统计导出符号的数量。我们看到的一个大型 App 约有 100 万个导出符号。链接器为这么多符号构建导出前缀树需要花费两到三秒。因此，添加 `-no_exported_symbols` 可以缩短该 App 两到三秒的链接时间。稍后我会在本演讲中详细介绍 `dyld_info` 工具。下一个选项是：`-no_deduplicate`。几年前，我们向链接器添加了一个新的遍（pass），用于合并具有相同指令但不同名称的函数。事实证明，在 C++ 模板展开时，会产生很多这样的函数。但这是一个开销很大的算法。链接器必须递归地对每个函数的指令进行哈希，以帮助查找重复项。由于开销较大，我们限制了该算法，让链接器只关注弱定义（weak-def）符号。这些是由 C++ 编译器为未被内联的模板扩展而生成的符号。现在，去重是一种大小优化，而 Debug 构建注重构建速度，而非大小。因此，默认情况下，Xcode 通过为 Debug 配置向链接器传递 `-no_deduplicate` 来禁用去重优化。如果你以 `-O0` 运行 clang 链接命令，clang 也会向链接器传递 `-no_deduplicate` 选项。总之，如果你使用 C++ 并且有自定义构建（例如，你在 Xcode 中使用非标准配置，或者使用其他构建系统），你应该确保你的 Debug 构建添加了 `-no_deduplicate` 以缩短链接时间。我刚才讨论的选项是传递给 `ld` 的实际命令行参数。在使用 Xcode 时，你需要修改产品构建设置。在构建设置中，查找“Other Linker Flags”。

现在让我们谈谈在使用静态库时可能遇到的一些意外情况。第一个意外是，当你有源代码构建到你的 App 链接的静态库中，但这些代码最终并未出现在最终 App 中。例如，你为某个函数添加了 `attribute used`，或者你有一个 Objective-C 分类。由于链接器进行的选择性加载，如果静态库中的那些目标文件没有定义链接过程中需要的某个符号，那么这些目标文件将不会被链接器加载。另一个有趣的问题是静态库和死代码剥离之间的相互作用。事实证明，死代码剥离可以隐藏许多静态库问题。通常情况下，缺少符号或重复符号会导致链接器报错。但是死代码剥离会促使链接器从 `main` 开始对所有代码和数据执行可达性分析，如果发现缺失的符号来自不可达的代码，链接器将抑制缺失符号错误。类似地，如果静态库中存在重复符号，链接器会选择第一个而不会报错。使用静态库的最后一个大意外是，当一个静态库被合并到多个框架中时。每个框架单独运行时都正常，但后来某个 App 同时使用了这两个框架，那么砰的一声，你就会因为多个定义而遇到奇怪的运行时问题。最常见的情况是你会看到 Objective-C 运行时警告有多个相同的类名实例。总的来说，静态库很强大，但你需要了解它们以避免这些陷阱。静态链接部分到此结束。现在，让我们继续讨论动态链接。首先，让我们回顾一下使用静态库进行静态链接的原始示意图。现在考虑一下随着时间的推移，随着源代码越来越多，这将如何扩展。应该清楚的是，随着越来越多的库被使用，最终程序的大小可能会增长。这意味着构建该程序的静态链接时间也会随之增加。

现在让我们看看这些库是如何制作的。如果我们做这样一个转换呢？我们把 `ar` 换成 `ld`，那么输出的库现在就是一个可执行的二进制文件。这就是 90 年代动态库的开端。为简便起见，我们把动态库称为“dylib”。在其他平台上，它们被称为 DSO 或 DLL。那么这里到底发生了什么？它又如何帮助解决可扩展性问题呢？关键在于静态链接器处理动态库链接的方式不同。链接器不是将代码从库中复制到最终程序中，而只是记录一种“承诺”。也就是说，它记录从动态库中使用的符号名称以及该库在运行时的路径。这有什么好处呢？这意味着你的程序文件大小在你的控制之下。它只包含你的代码，以及它在运行时需要的动态库列表。你的程序中不再有库代码的副本。你的程序的静态链接时间现在与你的代码大小成正比，而与链接的 dylib 数量无关。同时，虚拟内存系统现在可以发挥其优势了。当虚拟内存系统看到同一个动态库被多个进程使用时，它会在所有使用该 dylib 的进程中为该 dylib 重用相同的物理 RAM 页面。我已经向你展示了动态库是如何诞生的以及它们解决了什么问题。但是这些“好处”的“代价”是什么呢？首先，使用动态库的一个好处是我们加快了构建时间。但代价是现在启动 App 更慢了。这是因为启动不再仅仅是加载一个程序文件。现在所有 dylib 也需要被加载并连接在一起。换句话说，你只是将一些链接开销从构建时间推迟到了启动时间。其次，基于动态库的程序会有更多的脏页。在静态库的情况下，链接器会将所有静态库中的全局变量共同放置在主可执行文件的同一 DATA 页面中。但使用 dylib，每个库都有自己的 DATA 页面。最后，动态链接的另一个代价是引入了新东西的需求：动态链接器！还记得在构建时记录在可执行文件中的那个承诺吗？现在我们需要在运行时有什么东西来兑现这个承诺，以加载我们的库。这就是 dyld，动态链接器的作用。让我们深入了解动态链接在运行时是如何工作的。一个可执行二进制文件被划分为多个 segment（段），通常至少有 TEXT、DATA 和 LINKEDIT。Segment 大小始终是操作系统页面大小的倍数。每个 segment 有不同的权限。例如，TEXT segment 具有“执行”权限。这意味着 CPU 可以将该页面上的字节视为机器代码指令。在运行时，dyld 需要使用 `mmap()` 将可执行文件映射到内存中，并应用每个 segment 的权限，如此处所示。由于 segment 是按页面大小对齐的，这使得虚拟内存系统可以轻而易举地将该程序或 dylib 文件设置为某个 VM 范围的备份存储。这意味着直到这些页面上有某些内存访问，触发页面错误（page fault），导致 VM 系统读取文件的相应子范围并用其内容填充所需的 RAM 页面时，才会有任何内容被加载到 RAM 中。但仅进行映射是不够的。不知何故，程序需要被“连接”或绑定到 dylib。为此，我们有一个称为“修复”（fix ups）的概念。

在图中，我们看到程序设置了一些指针，指向它使用的 dylib 的部分。让我们深入了解什么是修复。这是我们的老朋友，mach-o 文件。现在，TEXT 是不可变的。事实上，在基于代码签名的系统中，它必须是不可变的。那么，如果有一个函数调用 `malloc()`，这如何工作？`_malloc` 的相对地址在程序构建时是无法知道的。实际上，静态链接器看到 `malloc` 位于一个 dylib 中，并对调用点进行了转换。调用点变成了对链接器在同一 TEXT segment 中合成的一个桩（stub）的调用，因此相对地址在构建时是已知的，这意味着 `BL` 指令可以正确形成。这样做的好处是，桩会从 DATA 加载一个指针并跳转到那个位置。现在，运行时不需要对 TEXT 进行任何更改——只有 DATA 会被 dyld 更改。事实上，理解 dyld 的关键在于，dyld 所做的所有修复都只是 dyld 在 DATA 中设置指针。

因此，让我们更深入地研究 dyld 执行的修复。在 LINKEDIT 的某个地方存储着 dyld 驱动修复所需的信息。有两种修复。第一种称为重定位（rebases），发生在 dylib 或 App 有一个指向自身内部的指针时。现在有一种称为 ASLR 的安全特性，它会导致 dyld 将 dylib 加载到随机地址。这意味着那些内部指针不能在构建时直接设置。相反，dyld 需要在启动时调整或“重定位”这些指针。在磁盘上，如果 dylib 被加载到地址零，这些指针包含它们的目标地址。这样，LINKEDIT 只需要记录每个重定位位置的位置。然后，dyld 可以将 dylib 的实际加载地址加到每个重定位位置上，以正确修复它们。

第二种修复是绑定（binds）。绑定是符号引用。也就是说，它们的目标是一个符号名称，而不是一个数字。例如，指向函数 `malloc` 的指针。字符串 `_malloc` 实际上存储在 LINKEDIT 中，dyld 使用该字符串在 `libSystem.dylib` 的导出前缀树中查找 `malloc` 的实际地址。然后，dyld 将该值存储在绑定指定的位置。今年，我们宣布了一种编码修复的新方式，我们称之为“chained fixups”。

第一个优点是它使 LINKEDIT 更小。LINKEDIT 更小是因为新格式不再存储所有修复位置，而只存储每个 DATA 页面中第一个修复位置的位置，以及导入符号的列表。其余信息则编码在 DATA segment 本身中，即最终将设置修复的位置。这种新格式因其修复位置被“链式”连接在一起而得名 chained fixups。LINKEDIT 只声明第一个修复的位置，然后在 DATA 中的 64 位指针位置里，部分位包含指向下一个修复位置的偏移量。其中还打包了一个位，用于指示修复是绑定还是重定位。如果是绑定，其余位是符号的索引。如果是重定位，其余位是目标在镜像（image）中的偏移量。最后，对 chained fixups 的运行时支持已存在于 iOS 13.4 及更高版本中。这意味着只要你的部署目标是 iOS 13.4 或更高版本，你现在就可以开始使用这种新格式。并且，chained fixups 格式启用了我们今年宣布的一项新操作系统功能。但要理解这一点，我需要谈谈 dyld 的工作方式。

Dyld 从主可执行文件（比如你的 App）开始。解析该 mach-o 文件以找到其依赖的 dylib，即它所承诺需要的动态库。它找到这些 dylib 并对它们执行 `mmap()`。然后，对于每个 dylib，它递归地解析它们的 mach-o 结构，根据需要加载任何额外的 dylib。一旦所有内容都加载完毕，dyld 会查找所有需要的绑定符号，并在执行修复时使用这些地址。最后，在所有修复完成后，dyld 自底向上运行初始化器。五年前，我们宣布了一项新的 dyld 技术。我们意识到上面绿色的步骤在你每次启动 App 时都是一样的。因此，只要程序和 dylib 没有改变，所有绿色步骤都可以在首次启动时缓存，并在后续启动中重用。今年，我们宣布了额外的 dyld 性能改进。我们宣布了一项名为“page-in linking”的 dyld 新功能。dyld 不再在启动时对所有 dylib 应用所有修复，内核现在可以在页面调入（page-in）时，懒加载地将修复应用于你的 DATA 页面。一直以来，对某个 `mmap()` 区域中某个页面的某个地址的首次使用会触发内核读入该页面。但现在，如果它是一个 DATA 页面，内核也会应用该页面所需的修复。十多年来，我们对于 dyld 共享缓存（dyld shared cache）中的操作系统 dylib 已经有了一个特殊的 page-in linking 处理。今年我们将其通用化，并使其可供所有人使用。这种机制减少了脏内存和启动时间。这也意味着 `DATA_CONST` 页面是干净的，这意味着它们像 TEXT 页面一样可以被驱逐和重建，从而减少了内存压力。这个 page-in linking 功能将出现在即将发布的 iOS、macOS 和 watchOS 版本中。但是 page-in linking 只适用于使用 chained fixups 构建的二进制文件。这是因为使用 chained fixups，大部分修复信息将编码在磁盘上的 DATA segment 中，这意味着在页面调入时内核可以访问到这些信息。需要注意的一点是，dyld 仅在启动期间使用此机制。任何稍后通过 `dlopen()` 打开的 dylib 不会获得 page-in linking。在这种情况下，dyld 走传统路径，在 `dlopen` 调用期间应用修复。记住这一点，让我们回到 dyld 的工作流程示意图。五年来，dyld 一直在优化上述绿色步骤，通过在首次启动时缓存该工作并在后续启动时重用它。现在，dyld 可以通过实际上不执行修复来优化“apply fixup”步骤，而是让内核在页面调入时懒加载地执行它们。既然你已经了解了 dyld 的新特性，让我们谈谈动态链接的最佳实践。你可以做些什么来帮助改进动态链接性能？正如我刚才所示，dyld 已经加速了动态链接中的大部分步骤。你可以控制的一件事是你的 dylib 数量。dylib 越多，dyld 加载它们所需的工作就越多。反之，dylib 越少，dyld 需要执行的工作就越少。接下来你可以关注的是静态初始化器，它是在 main 之前总是会运行的代码。例如，不要在静态初始化器中执行 I/O 或网络操作。任何可能需要超过几毫秒的事情都不应该在初始化器中执行。正如我们所知，世界变得越来越复杂，你的用户想要更多的功能。因此，使用库来管理所有这些功能是合理的。你的目标是在动态库和静态库之间找到你的最佳平衡点。静态库太多，你的迭代构建/调试周期就会变慢。另一方面，动态库太多，你的启动时间就会变慢，你的用户会注意到。但是今年我们加速了 ld64，所以你的最佳平衡点可能已经改变，因为你可以在 App 中直接使用更多的静态库或更多的源文件，而仍然在相同的时间内完成构建。最后，如果这对你的已安装用户群有效，更新到更新的部署目标可以让工具生成 chained fixups，使你的二进制文件更小，并缩短启动时间。最后，我希望大家了解的是两个新工具，它们将帮助你深入了解链接过程。第一个工具是 `dyld_usage`。你可以用它来获取 dyld 正在做什么的跟踪信息。该工具仅在 macOS 上可用，但你可以用它来跟踪你的 App 在模拟器中启动，或者如果你的 App 是为 Mac Catalyst 构建的。以下是在 macOS 上针对 TextEdit 运行的一个示例。
