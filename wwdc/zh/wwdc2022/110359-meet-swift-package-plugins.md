♪ 轻柔的器乐嘻哈音乐 ♪ ♪ 大家好，我叫 Anders。在本视频中，我将向你展示如何上手 Swift 包插件。Swift Package 是在 Xcode 11 中引入的。它们提供了一种以源代码形式分发库的好方法。Xcode 14 把这一方式扩展到了你的开发工作流中，让你可以使用插件来做诸如在构建期间生成源代码或自动化发布任务之类的事情。我们先来看看包插件是什么以及它们如何工作，然后更详细地谈谈 Xcode 14 支持的两种包插件：命令插件（command plugin）和构建工具插件（build tool plugin）。那么首先，什么是插件？包插件是一个 Swift 脚本，它可以对一个 Swift 包或 Xcode 项目执行操作。插件使用的 API 是 Xcode 专门为此目的提供的。包插件以 Swift 包的形式实现。一个包可以把插件与库和可执行文件一起提供，也可以只专注于提供插件。一个包插件可以用多个源文件实现，一个 Swift 包可以定义多个插件。高度专用的插件可以是提供它的那个包私有的，在这种情况下，它只在该包内可用。而通用型的插件可以通过把它定义为包产品（package product）而提供给其他包使用。这让其他包也能使用它，方式类似于一个包使用另一个包的库。但与库不同，对插件的依赖不会把运行时内容带入你的 App。相反，它让你能够访问在你自己的机器上或你的构建自动化中运行的开发工具。那么包插件能做什么呢？在 Xcode 14 中有两种包插件：命令插件和构建工具插件。命令插件实现自定义操作，你可以在任何想要的时候运行它们。它们可以运行源代码格式化工具或 linter，或者作为你开发工作流的一部分执行其他任务。这可能包括基于 Git 历史更新源文件中的贡献者列表或版权日期，或者其他你今天可能需要用任意脚本去做的事情。如果有需要，命令插件可以请求修改包中文件的权限。这对代码格式化尤其有用。并非所有命令插件都需要写入权限。有些命令可以创建报告或计算关于你的代码的指标，而不需要进行任何更改。构建工具插件扩展了构建系统的依赖图。它们对于在构建过程中生成源代码或资源特别有用。与一次针对整个包或项目调用的命令插件不同，构建工具插件被应用于每个需要它们的 target。让我们看看在 Xcode 中使用命令插件。这里有一个小型 iOS App，显示各种几何形状。它由一个 App 项目和一个本地包组成。该包实现了一个库，为 App 提供核心数据类型和逻辑。我正在考虑把这个包拆分到它自己的代码仓库中以便他人使用，作为其中的一部分，我想创建一个贡献者文件，列出所有向这个包提交过代码的人。我可以编写一个自定义脚本来做这件事。但我知道有一个包提供了一些用于处理代码的实用插件，而且我认为它有一个插件恰好能做我想做的事。为了访问那些插件，我会做与需要另一个包的库时相同的事情：在我的本地包的清单（manifest）中添加一个包依赖。当我保存清单时，Xcode 会拉取远程包，它会出现在 Package Dependencies 部分。我注意到 Xcode 还拉取了 SwiftFormat，这是一个流行的代码格式化工具。这是因为那个实用工具包中的一个命令插件又依赖于 SwiftFormat。现在我已经添加了这个依赖，我就可以访问该包提供的任何插件命令了。我在想要应用该命令的包上使用上下文菜单。现在菜单里多了三个新命令：一个是用 SwiftFormat 重新格式化源代码，另外两个提供专门的操作。其中一个基于 Git 中的提交历史生成或更新贡献者列表，另一个更新我的源文件中的版权日期。中间那个命令正好是我想做的。当我在我的包上调用这个插件命令时，Xcode 会让我选择把它的哪些 target 传给插件。在这个例子中，我打算对整个包调用它。如果这个插件接受自定义实参，我也可以在这里传入。我点击 Run，因为这个插件将要修改文件系统，Xcode 会就此警告我。我可以看到插件作者陈述的想要修改我的代码的理由，但我也想看一眼插件的实现。所以我选择 Show Command，Xcode 就把我带到了代码处。

这个插件做的事情是安全的，所以我会再次调用该命令，而这一次，我会选择 Run。

我会告诉 Xcode 为这个插件记住我的选择。这个特定的插件使用 Git 历史来生成一个列出贡献者姓名的文件，但命令插件可以做的事情非常灵活。既然我们已经在 Xcode 中使用了一个命令插件，让我们更仔细地看看插件在底层是如何工作的。包插件是 Swift 脚本，会在需要时被编译和运行。每个插件作为一个单独的进程运行。插件可以访问输入包的一个提炼表示，包括它的源文件。插件还会获得关于该包的任何依赖的信息。许多插件在执行工作的过程中会调用命令行工具。插件还可以创建文件和目录，并可以使用标准库（例如 Foundation）执行其他操作。插件在一个沙盒中运行，该沙盒阻止网络访问，并且只允许写入文件系统中的少数几个位置，例如构建输出目录。但命令插件可以请求获得同时修改包源目录中文件的权限。如果用户批准，沙盒会被配置为允许写入那些位置。插件还可以把结果发回给 Xcode。它可以发出警告和错误，构建工具插件可以定义供 Xcode 在构建期间运行的工具调用。所有包插件都使用由 Xcode 提供的 PackagePlugin 模块中的 API。这个 API 允许插件访问输入包，并在适当的时候把结果返回给 Xcode。实现插件的主源文件还定义了主入口点。它应当是一个符合与插件类型相匹配的协议的类或结构体。Xcode 调用的具体入口点函数取决于插件的种类。你可以在「创建 Swift Package 插件」视频中了解更多关于 PackagePlugin API 的内容。之前，我们使用了一个命令插件来修改我们的包。让我们看看命令插件的更多细节。命令插件扩展了开发工作流。它们直接应用于一个包，而不是在构建期间。并非所有命令插件都会修改文件系统——有一些不涉及更改任何文件的有用操作。但如果一个命令确实想要写入文件系统，它必须在实现该插件的包的清单中予以声明。这会让 Xcode 在允许插件运行之前询问用户许可。插件通常都很小，而且往往依赖其他工具来完成实际工作。之前我们看到，其中一个插件把所有实际工作都交给了 SwiftFormat。对工具包的依赖可以是二进制文件也可以是源代码——Xcode 会在命令被调用之前从源代码构建任何所需的工具。请注意，提供插件的包可以与它所依赖的工具所在的包不同。在命令插件的实现中，主类型遵循 CommandPlugin 协议，插件实现 performCommand 入口点。这个入口点接受一个上下文以及用户提供的任何自定义实参。让我们看看调用命令插件的另一种方式。我将使用与之前相同的项目，由于我之前已经添加了对 SourceCodeUtilities 包的依赖，我可以在终端（Terminal）中调用相同的插件。首先我要把目录切换到 CoreLibs 包，因为那是我想要应用命令插件的包。Swift Package Manager 5.6 有一个用于插件的新子命令。我会输入 "swift package plugin --List" 来查看有哪些可用的插件。这会显示与 Xcode 菜单中相同的插件。在命令行上，每个命令还会显示运行它所应使用的动词（verb）。我会使用重新生成贡献者列表的那个动词，就像我在 Xcode 中所做的那样。这个插件请求写入文件系统的权限，因为它要创建一个文件。我输入 "yes" 允许它，插件就可以运行并更新贡献者列表了。我本也可以使用一个允许插件不经询问就写入文件系统的包管理器选项。如果你是从 CI 系统或其他构建自动化中调用它，这会特别有用。但在使用该选项之前，请务必了解这个插件在做什么。就像在 Xcode 中一样，我可以把命令行实参传给插件。插件操作动词之后的任何实参都会被传给插件。在这个例子中，我传入一个 verbose 标志，以便在插件运行时看到更多输出。每个命令插件都定义了它支持哪些实参。到目前为止，我们主要在讲命令插件。但关于构建工具插件还有一些内容要讲。与命令插件不同，构建工具插件不会立即执行它的工作。相反，它会创建并返回供 Xcode 在稍后构建包时运行的构建工具调用。每一个工具调用都有一条要运行的命令行，还有输入和输出，它们告诉 Xcode 何时运行它。构建工具插件可以定义在构建期间运行的命令和在构建之前运行的命令。我们稍后会看看两者的区别。

由构建工具插件返回的命令通常被配置为把它们的输出写到构建目录，这样它们就能在增量构建之间持久保存。与插件本身一样，由构建工具插件定义的命令运行在一个阻止网络访问、阻止对包做任何更改的沙盒中。在构建工具插件的实现中，主类型遵循 BuildToolPlugin 协议，插件实现 createBuildCommands 入口点。这个入口点接受一个上下文和要为其创建构建命令的 target。它返回任何应当在包构建时运行的自定义构建命令。构建工具插件可以返回两种基本类型的构建命令。普通构建命令指定输入和输出路径，并且只在输出缺失或输入发生变化时才运行。预构建命令（prebuild command）在构建开始之前运行，可用于输出名称事先未知的情况。预构建命令在每次构建之前都会运行，所以它们应当确保在没有更改时做尽可能少的工作。构建命令和预构建命令非常适合生成源代码或资源。那么 Xcode 如何知道应当把哪些构建工具插件应用于一个包 target？在 SwiftPM 5.6 及更高版本中，包清单里有一个新的 plugins 参数，列出某个 target 想要的构建工具插件。这个参数指定该 target 需要的任何构建工具插件，与它依赖的任何运行时库一样，这些插件可以在同一个包里，也可以在另一个包里。让我们回到 Xcode。我要配置我的 geometry App 来使用一个构建工具插件。在这个特定案例中，我有一个自定义命令行工具，它基于我的 Core Library target 中的一些数据文件生成 Swift 代码。具体细节并不重要，但我最终想要的是为每一条数据生成类型安全的 Swift 访问器。除了我的数据文件之外，我一直在使用一个自定义工具生成源代码并把它们签入我的仓库。每当我的数据文件变化时，我一直在手动运行这个工具来重新生成 Swift 包装代码并提交更改。但有了构建工具插件，我可以做得更好。我可以在构建期间生成代码，从而不必把生成的代码保存在我的仓库里。

为了访问这个插件，我前往包清单，对我想要使用的那个源代码生成器插件所在的包添加一个依赖。

我包中的那些 target 现在可以访问该包中定义的任何构建工具插件了。

现在我前往需要使用该插件的 target，并在它的定义中添加一个 plugins 参数。

这告诉 Xcode：它想把那个包中的某个特定构建工具应用到我的 target 上。现在我可以去把那些生成的源文件从我的仓库中删掉了。它们会在构建期间根据需要被创建或更新。

看，这样干净多了。现在当我构建并运行我的 App 时，只要我的数据文件发生变化，我的构建工具插件就会告诉 Xcode 调用我的代码生成工具。生成的代码会和我的其他构建文件一起存储在我的构建文件夹中，保持我的仓库整洁。在本视频中，我们讨论了 Swift 包插件是什么以及它们如何工作。我们讨论了命令插件与构建工具插件之间的一些异同。这两种类型的插件都让你可以用一种更有条理的包可扩展性方式，来取代各种各样的随意脚本。构建工具插件让你可以扩展构建系统来生成源代码和资源，或者作为构建的一部分执行其他自定义工作。命令插件让你可以用自定义操作自动化常见的开发任务。它们可以针对特定的工作流量身定制，也可以写成在各种情况下都有用的形式。要学习如何创建你自己的包插件，请务必观看「创建 Swift Package 插件」视频。感谢观看，祝你在 WWDC 2022 的其余 session 中愉快。♪
