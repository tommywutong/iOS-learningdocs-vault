平台上的分发流程。有了这些新的原生工具链安装程序，你现在可以直接从 Swift.org 下载适用于 Amazon Linux 2 和 CentOS 7 的 RPM 包。这些工具链目前还是实验性的，所以一定要在 Swift.org 论坛上和我们分享反馈。Swift 主要被用来构建 App。不过，我们的愿景一直是让 Swift 具备可伸缩性——从高层脚本，到裸机环境，什么都能用它来写。为了鼓励大家把 Swift 用到它以前从未涉足过的地方，今年 Swift 经历了一些重大的改动。为了让独立、静态链接的二进制文件里标准库的体积更小，我们去掉了对一个外部 Unicode 支持库的依赖，换成了一个更快的原生实现。在运行于事件驱动的服务器方案上时，更小、更快的二进制文件是一个巨大的好处。在 Linux 上，你现在默认就能获得静态链接，从而更好地支持服务器的容器化部署。这种体积上的缩减，让 Swift 甚至适用于一些受限的环境，这也让我们得以把它用在 Apple 的 Secure Enclave 处理器里。从 App 到服务器，再到受限的处理器，Swift 处处都能派上用场；而把这一切串联起来的，是包生态系统。今年 Swift 包里的新特性，会让你的生活更轻松。首先，Swift Package Manager 引入了 TOFU。不，不是那种美味的小吃（豆腐）。TOFU 是 Trust On First Use（首次使用即信任）的首字母缩写。这是一套新的安全协议：一个包首次被下载时，它的指纹现在会被记录下来。之后的每次下载都会校验这个指纹，如果指纹不一致，就会报错。这只是信任与安全被内建进包生态系统核心、好让你放心使用它的一个例子。命令插件是改善 Swift 开发者工作流程的一个绝佳方式。它们是打造更具可扩展性、也更安全的构建工具的第一步。命令插件可以用来生成文档、重新格式化源代码等等。你不必再把自动化脚本写在 shell 脚本里、维护一套独立的工作流程，而是可以直接用 Swift！想想那些开源的格式化工具和 linter。现在，所有这些开源工具在 Xcode 和 Swift Package Manager 里都能用上了。命令插件正是连接开源工具和 Swift Package Manager 之间的胶水。Swift 项目正在拥抱开源社区里的各种开发者工具，为你的自动化工作流程提供无缝的集成。docC 是一个能把文档集成进你源代码里的绝佳工具。今年，随着对 Objective-C 和 C 的支持，它又变得更好了。我们来看看，用 docC 创建一个插件需要做些什么。插件其实就是简单的 Swift 代码。你可以创建一个遵循 CommandPlugin 协议的 struct，来定义一个插件。然后你只需要加一个函数，告诉你的插件你想调用哪个工具。我们想调用 docC 的地方，就在这个函数里面。一旦你定义好了插件，它就会通过 Swift PM 的命令行界面、以及 Xcode 里的一个菜单项，变得可用。现在，我们可以让 Swift PM 生成文档，它会知道要把这个操作传给 docC 可执行文件。这还没完。还有第二种插件，叫作构建工具插件。这些插件是一些包，让你可以在构建过程中注入额外的步骤。当你实现一个构建工具插件时，它会为构建系统创建一条命令，在沙盒里执行。这和命令插件不同，命令插件是你随时直接执行的，而且可以被明确授予权限，去修改你包里的文件。构建工具插件可以用来生成源代码，或者对特殊类型的文件做自定义处理。如果用构建工具插件，包的布局大概是这样的。在这个例子里，plugin.swift 就是实现这个包插件 target 的 Swift 脚本。这个插件会被当作一个 Swift 可执行文件来处理。你写这个插件的方式，和写任何 Swift 可执行文件是一样的。你可以通过定义一组构建命令来实现你的插件，告诉构建系统该运行哪个可执行命令、期望得到什么样的输出。包插件是一种安全的解决方案，为你的包提供可扩展性。想了解插件是怎么运作的、以及如何实现你自己的插件，可以看看这两场演讲：《Meet Swift Package plugins》和《Create Swift Package plugins》。随着你越来越多地使用包，你可能已经遇到过模块冲突的情况。也就是两个不同的包定义了同名的模块。为了解决这种情况，Swift 5.7 引入了模块消歧。模块消歧这项特性，让你可以从定义这些模块的包外部，给它们重新命名。在我们这个 Stunning 应用里，我们引入了两个都定义了 Logging 模块的包，所以它们冲突了。要为我们的 Stunning 应用修复这个问题，你只需要在包清单的 dependencies 部分加上 moduleAliases 关键字。这样一来，你就可以用两个不同的名字，去区分这两个原本同名的模块了。Swift 5.7 带来了一些出色的性能改进。我们先来看看构建时间。去年，我们告诉过大家，我们用 Swift 重写了 Swift Driver——这个负责协调 Swift 源代码编译的程序。去年的这次架构调整，解锁了一些能显著加快构建速度的重要改动。现在，这个 driver 可以直接作为一个框架、用在 Xcode 构建系统内部，而不再是一个独立的可执行文件。这让它能和构建系统更紧密地协调构建过程，从而支持像并行化这样的能力。如果你也喜欢构建飞快的感觉，可以在《Demystify parallelization in Xcode builds》这场演讲里了解更多细节。为了让大家看看构建到底快了多少，我们来看几个例子，看看构建一些我们经常用的、用 Swift 写的工具需要多长时间。在一台 10 核的 iMac 上，这些改进带来的提升从 5% 一直到 25% 不等。接下来，类型检查的速度也有了改进。今年，我们通过重新实现泛型系统的一个关键部分——也就是根据协议和 "where" 子句这类东西计算函数签名的那部分——改进了类型检查器的性能。在旧的实现里，随着涉及的协议越来越多，时间和内存占用可能会呈指数级增长。举个例子，这里我们有一组复杂的协议，定义了一个坐标系统，里面对许多关联类型都有大量的泛型要求。以前，对这段代码做类型检查要花 17 秒。但现在，在 Swift 5.7 里，这个例子的类型检查速度快得多，不到一秒就能完成。我们在运行时方面也有一些同样令人印象深刻的改进。在 Swift 5.7 之前，我们见过在 iOS 上，App 启动时的协议检查最长要花上四秒。每次启动 App 时，协议都需要重新计算一遍，导致你添加的协议越多，启动时间就越长。现在，它们会被缓存起来。根据一个 App 的写法、以及它用了多少协议，这在 iOS 16 上运行的某些 App 里，可能意味着启动时间被砍掉一半。《Improve app size and runtime performance》这场演讲，会更深入地讲讲你要怎样在自己的应用里利用这些改进。好，现在是时候聊聊我相信大家都很期待的内容了。去年，我们引入了新的并发模型，把 Actor 和 async/await 结合在了一起。这给你应用的并发架构带来了革命性的影响。比起回调和手动的队列管理，async/await 和 Actor 更安全，也更简单。今年，我们进一步充实了这套模型，把数据争用安全放在了最前面。因为并发对你 App 的代码库来说是一项如此根本、如此重要的改进，我们让这些改动得以一路向后部署到 iOS 13 和 macOS Catalina。为了能部署到更旧的操作系统上，你的 App 会为这些旧系统打包一份 Swift 5.5 并发运行时的副本。这和把 Swift 向后部署到 ABI 稳定性之前的操作系统上，是类似的做法。接下来，我们把这套模型推向了新的方向。我们引入了新的语言特性和配套的包。首先，我们来聊聊数据争用的规避。在讲这个之前，我可能得先退一步说：Swift 一个非常重要的特性，就是默认的内存安全。Swift 用户没法做出行为不可预测的事情，比如在正修改一个值的过程中去读取它。在这个例子里，我们要从一个数组里，移除所有和这个数组自身 count 相等的数字。一开始，这个数组的 count 是 3，所以我们会把数组里的 3 移除。但一旦这么做了，count 就会变成 2。那我们是要把数组里的 3 和 2 都移除，还是只移除 3？答案是都不对。Swift 会阻止你这么做，因为在正修改一个数组的过程中去访问它的 语言易用性方面的众多改进。语言是工具，而工具有个有意思的地方——它们真的会影响你用它们造出来的东西。当你手头只有一把锤子时，你造东西就会用钉子，而不是螺丝。而且，即使你有一整套工具，如果你的锤子有一个又大又抓手的手柄，而你的螺丝刀又是塑料的、很难握住，你可能还是会更倾向于用钉子。语言也是一样的道理。如果 Swift 有一个好用的工具来表达某件事，大家就会更常用它。而今年，Swift 里用来表达你想让代码做什么的这些工具，在很多方面都有了改进。这些改动里，有一些是针对你经常做的事情提供的简单便利。举个例子，在 Swift 里，用 if let、让等号两边用同一个名字，是非常常见的写法。毕竟，解包之后的值，大概找不到比你给那个可选值取的名字更好的名字了。但当这个名字非常长的时候，这种重复就开始变得繁琐了。你可能会想把名字缩写一下，但这样一来，你的代码就会变得有点晦涩难懂。而且，如果你之后重命名了这个可选变量，这个缩写可能就会跟着对不上了。Swift 5.7 为这种常见模式引入了一种新的简写形式。如果你在解包一个可选值、并且想让解包后的值用同一个名字，你只需要把等号右边去掉就行。Swift 会假定它就是同一个名字。当然，这也适用于 guard，甚至连 while 也可以这样用。我们还关注了那些"只要做一个小改动，某个特性就会突然失效"的地方。举个例子，Swift 一直都能根据一个只有一条语句的闭包里写的代码，推断出这次调用会返回什么类型。在这个 compactMap 调用里，这个闭包返回的是 parseLine 的值，而 parseLine 函数返回一个 MailmapEntry，所以 Swift 能推断出 entries 应该是一个由 MailmapEntry 组成的数组。现在，对于那些有多条语句、或者带控制流特性的更复杂的闭包，这也同样适用了。所以你可以用 do-catch，或者 if...else，或者干脆加一句 print 调用，都不需要手动指定这个闭包的结果类型。我们关注的另一件事，是那些其实并没有标记出任何真正危险的"危险标记"。Swift 非常在意类型安全和内存安全。为了不让你犯错，它从不会在不同指针类型之间自动转换，也不会在裸指针和带类型指针之间自动转换。这和 C 很不一样，C 允许某些转换。举个例子，你可以改变被指对象的有符号性，或者把任意指针转换成 char *，把它当作字节来访问，而这都不会违反 C 的任何指针规则。但有时候，当一个 C API 被导入 Swift 时，这些指针行为上的差异会带来问题。最初的开发者在设计他们的 API 时，可能带有一些轻微的类型不匹配，这些在 C 里会靠自动转换处理掉，但在 Swift 里就会是错误。在 Swift 里，把一个类型的指针当成另一种类型来访问，是非常危险的，所以你必须非常明确地描述你在做什么。但如果我们是把这个指针直接传给 C，那这一切就都没有意义了，因为在 C 里，这种指针不匹配是完全合法的！所以在这种情况下，我们把一件其实非常直白的事情，当成了危险的事情来处理。这一点很重要，因为 Swift 固然看重类型安全，但它同样看重能轻松访问 C 系语言的代码。这正是为什么 C 和 Objective-C 的互操作性如此丰富、如此无缝，也正是为什么 Swift 项目成立了 Angela 前面提到的那个 C++ 工作组，开始打造同样强大的 C++ 互操作性。我们不希望使用像这样的 C 函数变得毫无必要地痛苦。所以，Swift 现在为调用导入进来的函数和方法，准备了一套单独的规则。它允许一些在 C 里合法、但在 Swift 里通常不合法的指针转换。这样一来，你的 Swift 代码就能无缝地使用这些 API 了。到目前为止，我们讲的都是对你已经拥有的工具做的一些小改进。但今年，Swift 还有了一个全新的工具，用来从字符串里提取信息。这里有一个函数，从一个字符串里解析出一些信息。这类任务在 Swift 里，一直都有点挑战性。你最终会一遍又一遍地搜索、拆分、切片，直到得到你想要的东西。当大家注意到这一点时，往往会聚焦在一些细枝末节上，比如操作字符串索引可能会有多啰嗦，但我觉得这有点抓小放大。因为即使我们改了这套语法，它也没法帮你回答你在看这段代码时会问的那个最基本的问题——传进去的这个 line 变量，实际上长什么样？它想要拆解的是什么样的字符串？如果你盯着它看得够久，你可能会意识到，它解析的是一个简化版的 mailmap——一种你放在 git 仓库里、用来纠正旧提交里某个开发者名字的文件。但通过搜索和切片来提取这些信息，实在是太繁琐了，很难看出这一点。你会在"该怎么切分这个字符串"这件事上迷失，以至于有点忘了这个字符串本身是什么。问题不在于这两个表达式；问题在于整件事本身。我们需要把这一切都撕掉，换成更好的东西。我们需要一种不同的方法：一种让你的代码某种程度上把你想匹配的字符串"画"出来，然后由语言去搞清楚该怎么做的方法。一种声明式的方法，而不是命令式的。在 当你在一个继承列表、泛型参数列表、泛型一致性约束，或者一个不透明结果类型里写出一个协议名字时，它表示的是"一个遵循这个协议的实例"。但在一个变量类型、一个泛型实参、一个泛型相同类型约束，或者一个函数的参数类型或结果类型里，它实际上表示的是"一个装着遵循这个协议的实例的 box（盒子）"。这个区别很重要，因为这个 box 通常会占用更多空间，操作起来也要花更多时间，而且不具备它内部实例的全部能力。但你在用 box 的地方，看起来和你没在用 box 的地方一模一样，所以很难看出你到底有没有在用它。Swift 5.7 修复了这个疏漏。当你在用一个装着遵循类型的 box 时，Swift 现在会要求你写出 any 关键字。对于在 Swift 5.7 之前就合法的代码来说，这不是强制的，但我们鼓励你这样写，而且即使你没有显式写出来，你也会在生成的接口和错误消息里看到它。所以，右边这一列里的这些东西，首选的写法都是用 any 关键字。如果你这样写，你就能分辨出自己什么时候在用这样一个 box 了。既然这个例子里的某个参数被 any 关键字标出来了，解释这两个函数之间的区别就容易多了。addEntries1 把 Mailmap 当作一个泛型类型来接收；addEntries2 把它当作一个 any 类型来接收。而且，当你碰到 any 类型的某个局限时，错误消息也更容易解释清楚到底发生了什么。举个例子，这个 mergeMailmaps 函数试图把一个 any Mailmap 传给一个泛型的 Mailmap 参数。这以前会产生一条错误，说 Mailmap 没法遵循它自己，这听起来一直有点自相矛盾。但现在有了 any 类型这个概念，我们就能更清楚地解释这里到底发生了什么。问题在于，any Mailmap——这个装着一个 mailmap 的 box——并不遵循 Mailmap 协议。但你想传的正是这个 box，而它没法放进这个泛型参数里。如果你想传的是这个 box 里面的实例，你就得想办法先打开这个 box，把里面的 mailmap 拿出来，传那个实例才行。但实际上，在像这样的简单情况下，Swift 现在会直接替你做这件事。打开这个 box，取出里面的实例，把它传给这个泛型参数。所以，你不会再像以前那样频繁地看到这条错误消息了。不过，any 类型还有一项比这更令人兴奋的改进。以前，如果一个协议用到了 Self 类型，或者有关联类型，甚至只是遵循了一个有关联类型的协议——比如 Equatable——它就没法被用作 any 类型。但在 Swift 5.7 里，这个错误就——嗖——消失了。很多开发者都曾在这个问题上吃过苦头，所以我们很高兴能从根源上把它修好。光是对 Mailmap 这样的协议来说，这就已经够令人兴奋了，但这还不止于此。因为即使是像 Collection 这样非常复杂的协议，现在也可以被用作 any 类型了。多亏了一项叫"主要关联类型"的新特性，你甚至可以指定元素类型。很多关联类型基本上都只是实现细节。你通常并不关心一个集合的 index、iterator 或者 subsequence 用的是什么类型；你只需要用它所支持的那个类型就行。但它的 Element 就是另一回事了。你可能不会总是在意一个集合具体用的是哪种 Element 类型，但你大概率会对这些元素做点什么，所以你需要对它们做约束、或者把它们返回出去之类的。当你有一个像 Element 这样、几乎每个使用这个协议的人都会关心的关联类型时，你可以把它的名字放在协议名字后面的尖括号里，把它变成一个主要关联类型。一旦你这样做了，几乎在任何能写这个协议名字的地方——包括在 any Collection 里——你都可以用尖括号语法来约束这个协议的主要关联类型。现在，你们中有些人可能会看着这个类型，想："等一下，不是已经有个叫 AnyCollection 的东西了吗，就是连写在一起、'any' 首字母大写的那个？"你说得没错，确实有！以前那个 AnyCollection，是一个类型擦除包装器——一个手写的 struct，起的作用和一个 any 类型一样。区别在于，AnyCollection 这个 struct，是你这辈子见过的最枯燥的样板代码，一行接一行；而 any 类型是一项内建的语言特性，基本上做的是同一件事——而且完全免费！不过，AnyCollection 这个 struct 还会继续保留下去，一方面是为了向后兼容，另一方面是因为它有几个特性，any 类型目前还比不上。但如果你的代码里有你自己写的类型擦除包装器，你可能会想看看，能不能用内建的 any 类型，而不是 box class 或者闭包，来重新实现它们。或者甚至干脆用类型别名来替换它们。所以，Swift 对 any 类型做了大幅改进。它引入了 any 关键字，让你能看清自己在哪里用到了它们。它让你可以把它们传给泛型实参。它废除了那条让许多协议没法和它们配合使用的限制。它甚至还让你可以约束一个 any 类型的主要关联类型。但即便有了所有这些改进，any 类型依然有它的局限。举个例子，虽然现在，当 Mailmap 遵循 Equatable 时，你可以用 any Mailmap 了，但你仍然没法对它们使用等于运算符，因为等于运算符要求两个 mailmap 具有相同的具体类型，而当你用的是两个 any Mailmap 时，这一点是没法保证的。所以，尽管 Swift 已经对 any 类型做了大量改进，它们在能力和性能上仍然有重要的局限。这也是为什么很多时候，你不应该用它们，而应该改用泛型。我们回到 addEntries 的那两个版本，把这个道理用上。这两个版本做的事情完全一样，但上面那个用的是泛型类型，下面那个用的是 any 类型。泛型版本大概率会更高效、能力也更强，所以你应该用那一个。然而，你大概还是会忍不住想用 any 类型，因为它们实在读起来、写起来都容易得多。要写出泛型版本，你需要声明两个泛型类型名，给它们都加上约束，最后，把这些泛型类型名用作参数的类型。比起写 "any Collection" 和 "any Mailmap"，这实在太累人了。所以，尽管 any 类型有这些缺点，你还是会忍不住想用它们。但这正是我前面说的那件事——因为锤子的手柄又大又抓手，就用锤子而不用螺丝刀。你本不应该被迫做这样的选择。所以，Swift 正在让泛型变得和 any 类型一样好用。如果一个泛型参数只在一个地方被用到，你现在可以用 some 关键字作为简写来写它。它甚至还支持主要关联类型，所以你可以用好理解得多的代码，接收任意由 mailmap 条目组成的集合。有了这个工具在手，你再也没有理由回避泛型了。如果你要在泛型和 any 类型之间做选择，泛型会一样好用——只需要把 "any" 换成 "some" 就行。所以，你不妨用最适合这项工作的工具。关于协议和泛型的这些改动，我只是浅尝辄止地讲了讲。想深入了解，也想全面回顾一下 Swift 所有的泛型特性，我们今年还为大家准备了两场演讲：《Embrace Swift generics》和《Design protocol interfaces in Swift》。好，Angela 和我讲了将近二十项对 Swift 的改动，但还有更多内容，这场演讲装不下。这里的每一项改动，都是在 Swift 论坛的 Evolution 板块上，公开地被提出、被提议、被评审、被接受的。而这一切，都是在 Apple 之外的社区成员的帮助下，被塑造、被实现出来的。如果你就是这些人当中的一员，感谢你让 Swift 5.7 成为如此出色的一个版本。如果你想帮忙决定接下来会发生什么，欢迎访问 Swift.org/contributing，了解怎样参与进来。感谢大家的时间。祝编程愉快。
