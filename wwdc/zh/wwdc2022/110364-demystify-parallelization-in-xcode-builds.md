两个编译器——Clang 和 Swift——都会生成链接器需要用来链接代表该 App 的可执行程序的目标文件。虽然这个顺序说得通，但它从何而来并不明显。所以让我们看一下该过程的一个例子，以及构建系统如何决定以何种顺序执行所有任务。

使用输入源文件，Swift 编译器捕获程序员的意图并将其翻译成机器可执行的二进制文件，同时沿途检查源代码中的错误。此过程可能失败，这将取消构建；但如果成功，它会为每个输入创建一个目标文件。这些目标文件用于调用链接器，链接器将它们组合起来，并添加对外部链接库的引用以生成可执行文件。这两个任务基于它们所消费和生成的内容存在依赖关系。编译器生成的目标文件被链接器消费。这在构建系统图中创建了一个依赖。文件内容本身对构建系统并不重要，但任务之间的依赖关系很重要。在执行构建时，它需要确保：生成另一任务输入的任务在所述任务可以开始之前完成。由于这一核心概念对所有类型的任务都有效，让我们切换到一个更通用的可视化，显示 Task A 与 Task B 之间的依赖。在这种情况下，A 生成 B 的部分或全部输入。

编译和链接只是构建整个 target 需要执行的许多不同任务类型中的几种，所以让我们向图中再添加一些通用任务，代表编译资源、复制文件或代码签名等其他类型。合在一起，它们代表构建一个 Framework target。同样，这些任务基于它们的输入和输出定义了依赖关系。因此，完成执行 task A 会解除运行 task B 和 C 的阻塞，而完成 task B 会解除 task D 和 E 的阻塞。被解除阻塞的任务称为「下游」，阻塞他人的任务称为「上游」。许多项目包含不止一个 framework target，所以让我们再添加两个 target，分别代表一个 App 和一个 App extension。Target 通过显式或隐式依赖在项目中定义彼此之间的依赖关系。例如，通过被添加到「Link Binary with Libraries」构建阶段。

在这种情况下，App 嵌入了 App extension 并链接了该 Framework。App extension 没有使用该 Framework，所以它们之间没有依赖关系。

在执行构建图时，不同任务花费的时间不同。这取决于完成工作所需的复杂程度，取决于所需的计算量以及输入的大小。编译许多文件通常比复制几个头文件耗时得多，把这一点纳入考量后就会得到类似这样的结果。当构建系统执行此构建时，它从运行没有依赖的任务开始。一旦这些完成，它们就会解除下游任务的阻塞，依此类推，遵循此过程直到所有计划的任务完成。

在随后的构建中，构建系统能够跳过那些输入未更改且输出仍然是最新的任务。如果某个任务因输入更改而需要重新运行——如此处 App target 的 B——若其输出发生更改，下游任务也必须重新运行。跳过所有其他任务使得在项目上迭代工作时能有非常快的周转时间。这称为增量构建（incremental build），但现在让我们先坚持讨论完整构建。

任务执行的依赖关系和持续时间定义了下游任务最早可能开始的时间。有了这些信息，就可以计算关键路径（critical path），即在理论上资源无限的情况下构建需要运行的最短时间。本场讲座的一个常见模式将是缩短这条路径，以创建高度可并行且可扩展的构建图。较短的关键路径不一定导致较短的总体构建时间，但它能确保构建随硬件扩展。关键构建路径定义了构建能有多快的限制因素——即使硬件允许，它也无法完成得更快。缩短关键路径是通过打破其中的依赖来完成的。在查看构建如何表现并想更多地了解其执行时，需要根据它们执行的时间来绘制数据。宽度仍然表示任务的长度。像这两个这样的宽元素表示长时间运行的任务，而像这些这样的窄元素表示快速完成的任务。

时，构建阶段描述了生成该 target 的产品需要完成的工作。它们在项目编辑器中定义，可以包含一组要编译的源代码文件和资源、需要复制的文件（如头文件或资源），以及应链接的库或应执行的脚本。许多构建阶段描述的任务具有来自其他构建阶段的输入或输出，从而在它们之间创建依赖。例如，target 的源文件必须在链接之前编译。不过，这并不适用于所有构建阶段。构建系统不会按线性顺序运行每个构建阶段的任务，而是会考虑构建阶段的输入和输出，以确定它们是否可以并行运行。例如，Compilation 和 Resource copying 可以并行运行，因为两者都不依赖对方的任何输出。然而，链接仍须跟在编译之后，因为它依赖该阶段生成的目标文件。现在，让我们考虑一个包含「Run Script」构建阶段的不同 target。与其他构建阶段不同，脚本阶段的输入和输出必须在 target 编辑器中手动配置。因此，构建系统会一次一个地运行连续的脚本阶段，以避免在构建过程中引入数据争用（data race）。如果 target 中的脚本被配置为基于依赖分析运行，并指定了完整的输入和输出列表，则可以将构建设置 FUSE_BUILD_SCRIPT_PHASES 设为 YES，以指示构建系统应尝试并行运行它们。不过，在并行运行脚本阶段时，构建系统必须依赖指定的输入和输出。因此请注意，脚本阶段的输入或输出列表不完整可能导致数据争用，这类问题非常难以调试。为缓解这一点，Xcode 支持用户脚本沙盒化，以精确声明每个脚本阶段的依赖。沙盒化是一项选择加入的功能，它会阻止 shell 脚本意外访问源文件和中间构建对象，除非这些对象被显式声明为该阶段的输入或输出。在此示例中，input 和 output.txt 都没有被声明为该脚本阶段的依赖。在构建项目时，沙盒会阻止脚本读取和写入这两个文件。当脚本违反沙盒时，它会以非零退出码失败，导致构建失败。除此之外，Xcode 还会列出脚本阶段试图访问但未正确声明的所有路径。把这两个文件都作为依赖信息添加到此脚本阶段可修复此问题。这样，沙盒可确保脚本不会误访问其声明的输入和输出之外的任何文件。现在，让我们探索一个有多个脚本阶段的例子，看看沙盒化如何防止数据争用和不正确的构建。有两个脚本阶段。第一个读取一个文本文件，计算其内容的校验和，并将该值写入 DERIVED_FILE_DIR 中的一个中间文件。另一个脚本读取同一文本文件以及生成的校验和，并将它们注入一个 html 文件，以便稍后在 App 中显示。如果没有为这些阶段声明精确的输入和输出依赖集，当 FUSE_BUILD_SCRIPT_PHASES 开启时，Xcode 会并行运行这两个脚本。让我们详细检查这个有问题的场景。假设「Generate HTML」缺少「checksum.txt」的输入声明，但两个脚本的所有其他输入和输出都已正确声明。在没有沙盒化的情况下，这种错误配置可能不被注意，从而在构建中造成问题。这意味着 Xcode 将无法推断两个阶段之间的依赖关系，并在 FUSE_BUILD_SCRIPT_PHASES 开启时安排它们并行运行。这里有几个隐患。由于 checksum.txt 未列为「Generate HTML」的输入依赖，在干净构建期间，脚本会在文件系统上该文件尚不可用时尝试读取它。另一个隐患是，如果由于先前运行「Calculate Checksum」而使 checksum.txt 在磁盘上可用，当两个脚本并行运行时，「Generate HTML」可能会拾取过时的文件。这是用户错误，在沙盒中执行脚本有助于防止此问题。开启沙盒化后，「Generate HTML」在尝试读取「checksum.txt」时会立即失败。错误消息将引导为该构建阶段添加缺失的输入。正确的输入和输出定义会引导 Xcode 尊重两个阶段之间的依赖关系，以便「calculate checksum」在「Generate HTML」之前运行。同时，不相关的构建阶段仍可并行执行。要为 target 启用 Sandboxed Shell Scripts，在构建设置编辑器或 xcconfig 文件中将 ENABLE_USER_SCRIPT_SANDBOXING 设为 YES。总之，沙盒化的 shell 脚本允许拥有正确的依赖信息，以实现更快、更稳健的增量构建，因为构建系统有信心：如果输入未更改且输出仍然有效，就跳过脚本阶段；否则重新运行脚本。为脚本的 target 启用该构建设置会阻止访问项目源根目录内以及 derived data 目录中的文件——如果它们未在项目中显式定义为脚本的输入或输出。沙盒不会阻止对任何其他目录的未经授权访问，因此不要把这当作安全功能。使用此功能有助于调试现有脚本阶段缺失的输入或输出，以确保有效配置。再结合前面解释的构建设置 FUSE_BUILD_SCRIPT_PHASES，通过沙盒化正确定义了依赖边的脚本阶段可以并行执行，以缩短构建的关键路径。以上就是并行化构建单个 target 的步骤。现在 Artem 将揭开构建许多 target 时并行化的神秘面纱。Artem：谢谢，Ben。既然我们已经介绍了可能进入构建项目中某个 target 的构建系统任务和阶段的基础，让我们采取更全局的视角，探索 Xcode 如何利用 Swift target 之间的依赖从你的构建中提取最大并行度，以及你的项目的结构和组织如何影响构建时间。很可能有若干层级的层次结构组成你的项目。例如，一个 App target 依赖于沿语义边界拆分成各个 target 的一组本地库，以及若干 framework。每个 target 包含许多不同的构建阶段和步骤，生成并消费与其他 target 中构建阶段之间的文件依赖。随着项目规模增长，这些任务图往往会在规模和复杂性上增加。虽然 Xcode 构建系统会展平这些层级，把构建分解成对应于所有 target 的构建阶段的任务之海。对 Swift target 而言，有一种特殊的任务是编译。将 Swift target 的源代码构建成二进制产品是一项复杂操作，通常由许多用于构建规划、编译和链接的子任务组成。这些任务的协调被委托给 Xcode 工具链中的专用工具——Swift Driver。Driver 对何时以及如何为目标源代码构造所需的编译器和链接器调用拥有专门知识。任何包含 Swift 代码的 target 也对应于一个代码分发单元：一个模块（module）。捕获此 target 公共接口的二进制模块文件是下游 target 开始编译所需的构建产品。让我们更仔细地看一个例子，了解 Swift Driver 为构建其中一个 target 所做的事情。你的 target 可能由若干源文件的集合组成。在 release 或优化构建中，driver 会安排一个包含所有源文件的编译器任务，以最大化优化机会。这个单一编译任务也会生成该 target 的 Swift 模块。在 debug 或增量编译模式中，Swift Driver 将所需的编译工作分解成可以并行运行的更小的子任务，其中一些在增量构建中可能无需重新运行。然后，生成 Swift 模块需要额外一步，以合并每个编译任务的部分中间产品。如果像本例中一样，你的 target 中的源文件数量很多，各个文件也可能根据构建系统的启发式被分配到批处理编译子任务。构建日志会高亮哪些源文件被分配到批处理编译作业，并为每个文件的诊断提供单独条目。能够跨不同源文件并行化 target 的构建对于更快、更小的增量构建至关重要，因此请确保你的 Debug 构建使用 Incremental Compilation Mode 设置。在 Xcode 14 之前，由于 Xcode 构建系统与 Swift Driver 之间的边界，target 构建阶段的编排，以及每个 target 的 Driver 实例生成的编译子任务，是彼此独立发生的，每个组件都尽其所能充分利用可用系统资源。让我们拿这个示例构建图，更深入地了解相对于彼此调度其编译阶段涉及什么。正如我们前面所学，Swift target 依赖通过让其依赖方提供捕获被依赖方公共接口的二进制模块文件来解析。解析这些依赖关系会带来以下排序，记录在显示每个 target 的顶级 Swift Driver 任务及其各个子任务的时间线中。借助 Xcode 14，由于 Swift Driver 的全新实现——它本身现在用 Swift 编写——构建系统和编译器已完全集成。Xcode 构建系统充当必须执行以编译你的代码的所有任务的中央调度器。这种中央规划机制允许 Xcode 做出细粒度的调度决策，更好地保证构建你的项目将仅使用可用资源，而不会过度订阅你的 CPU 并降低整体系统性能。

而以前在 Xcode 构建系统视野之外的子任务岛屿集合，现在完全处于构建系统调度器的领域。

当所有各个子任务都在中央任务池中时，重要的是考虑构建调度器所做的权衡。例如，在一台 8 核机器上，调度器的默认是将可用任务——那些依赖已满足、准备就绪的任务——分配到八个可用执行槽之一。一旦其中一个槽位空出，构建系统就会尝试用更多未完成的工作填满它。在更高核心数的机器上，我们能够执行更多并发工作。但那也意味着我们更有可能有空闲核心——它们可用来执行更多工作，但所有未完成的任务仍在等待由当前正在执行或等待的其他任务生成的输入。新的集成构建系统允许调度器显著减少这种空闲时间。要了解如何做到，让我们重温如何解析 target 的编译依赖——二进制模块文件。

正如我们前面介绍的，编译子任务的部分结果被合并成 target 的最终模块产品。一旦此产品可用，下游 target 就可以开始编译。Xcode 14 和 Swift 5.7 中的新功能是，target 模块的构建在一个单独的 emit-module 任务中直接从所有程序源文件完成。这意味着下游 target 的编译可以在 emit-module 任务完成后立即开始，而无需等待依赖 target 的所有其他编译器任务。能够如此早地解除下游 target 编译的阻塞，减少了在空闲 CPU 核心上等待可用工作的时间——也就是构建时间线中活动高峰之间的那些空白空间。

把这一点扩展到项目的其余部分表明，虽然我们执行的总体工作量相似，但构建系统能够更高效地使用计算机的资源，往往显著更快地完成构建。

现在，让我们看看构建系统在构建 Swift 时可以执行的第二种跨 target 优化——急切链接（Eager Linking）。基于前一个例子，我们为每个 target 添加了链接器任务，它们都在构建的关键路径上。在这种情况下，因为 Target B 链接 Target A，Target B 的链接任务必须等待 Target A 的链接输出生成，并且其自己的编译任务完成，然后才能运行。然而，通过急切链接，Target B 的链接任务可以改为依赖 Target A 的 emit-module 任务。因此，Target B 可以在构建中更早开始链接，与链接 Target A 并行运行，从而缩短关键路径。这是如何工作的？通常，具有链接产品依赖的两个 target 的依赖图看起来像这样。链接依赖方 target 需要其依赖项的链接产品，以及该 target 自己的编译输出。当急切链接时，这种依赖被打破，允许依赖方 target 更早开始链接。它不再依赖依赖项的链接产品，而是依赖构建过程中由 emit-module 任务更早生成的基于文本的动态库 stub。此 stub 包含将出现在链接产品中供依赖方使用的符号列表。你可以使用屏幕上显示的 Xcode 构建设置启用此优化。急切链接适用于所有被其依赖方动态链接的纯 Swift target。总结一下，Xcode 构建系统是一个复杂的调度引擎，它寻求通过并行运行构建阶段来提取尽可能多的并行度。而像 Script Sandboxing 这样的功能让你确保构建既最大程度并行又可靠。Xcode 和 Swift 比以往任何时候都更加集成。而项目结构：它的模块化、由 target 产品之间依赖构成的图的整体形状，以及其中构建阶段的数量和复杂性，再加上你机器上可用的计算资源——所有这些都是影响 Xcode 能够并行化和加速你的构建程度的因素。有了这些知识，以及像构建时间线这样强大的新工具，你已充分准备好检查你的项目并洞察你的构建。如果你想了解更多幕后技术细节，我们描述的许多被 Xcode 使用的技术都是开源开发的。你可以在下面的链接找到 Swift Driver 的 GitHub 仓库。要了解更多关于 Xcode 的精彩讲座，请查看今年「Xcode 的新功能」中的所有新特性和改进。并在讲座「链接加速：缩短构建和启动时间」中了解 Xcode 14 的链接器如何将链接时间最多提升两倍。感谢跟随收听。我们希望你学到了一些关于 Xcode 构建的新见解。我们迫不及待想看到你将创造什么。祝会议剩余时间愉快。
