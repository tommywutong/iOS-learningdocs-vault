我们退一步，来更好地理解一下"特定抽象类型"这个概念。

一个表示某个特定具体类型的占位符的抽象类型,叫做不透明类型。

被替换进来的那个特定具体类型，叫做底层类型。

对于不透明类型的值来说，底层类型在该值的作用域内是固定的。

这样一来，使用该值的泛型代码就可以保证每次访问该值时都得到相同的底层类型。

使用"some"关键字的类型和尖括号里命名的类型参数，两者都声明了一个不透明类型。

不透明类型既可以用作输入，也可以用作输出，所以它们可以声明在参数位置，也可以声明在结果位置。

函数箭头是这两个位置之间的分界线。

不透明类型所处的位置，决定了程序的哪一部分能看到这个抽象类型，哪一部分决定了具体类型。

命名的类型参数总是声明在输入这一侧，所以由调用方决定底层类型，而实现方使用抽象类型。

一般来说，为不透明参数或结果类型提供值的那部分程序，决定了底层类型，而使用这个值的那部分程序,看到的是抽象类型。

我们来深入了解一下这是如何运作的，顺着我们对参数值和结果值的直觉来看。

因为底层类型是从一个值推断出来的，所以底层类型总是和这个值来自同一个地方。

对于局部变量来说，底层类型是从赋值语句右侧的值推断出来的。

这意味着不透明类型的局部变量必须始终有一个初始值；如果你不提供初始值，编译器会报错。

底层类型在该变量的作用域内必须是固定的，所以尝试改变底层类型也会导致错误。

对于不透明类型的参数来说，底层类型是从调用点的参数值推断出来的。

在参数位置使用"some"是 Swift 5.7 中的新特性。

底层类型只需要在该参数的作用域内固定，所以每次调用都可以提供不同的参数类型。

对于不透明结果类型来说，底层类型是从实现中的返回值推断出来的。

一个具有不透明结果类型的方法或计算属性，可以在程序的任何地方被调用，所以这个命名值的作用域是全局的。

这意味着底层的返回类型在所有 return 语句中都必须是一样的；如果不一样，编译器就会报错，说底层的返回值类型不匹配。

对于不透明的 SwiftUI 视图来说，ViewBuilder DSL 可以对控制流语句进行转换，让每个分支都具有相同的底层返回类型。

所以在这种情况下，我们可以通过使用 ViewBuilder DSL 来解决这个问题。

在方法上写一个 @ViewBuilder 标注,并去掉 return 语句，就可以让结果由 ViewBuilder 类型为我们构建出来。

在这种情况下，结果类型取决于具体的动物类型，所以我们需要在参数类型和返回类型里都使用类型参数 A。

另一个经常需要多次引用不透明类型的地方是泛型类型。

代码常常会在一个泛型类型上声明一个类型参数，把这个类型参数用于一个存储属性，然后又在一个逐成员初始化方法里再次用到它。

声明处的尖括号有助于说明如何使用一个泛型类型，所以对于泛型类型来说，不透明类型必须始终命名。

为了支持这种灵活的存储方式，any Animal 类型在内存中有一种特殊的表示方式。

你可以把这种表示方式想象成一个盒子。

有时候，一个值足够小，可以直接放进盒子里。

而其他一些值对这个盒子来说太大了，所以这个值必须被分配到别处，盒子里存储的是指向该值的一个指针。

这种能够在运行时动态存储任意具体动物类型的静态类型 any Animal，正式的名称叫做既存类型（existential type）。

而对不同具体类型使用同一种表示方式的这种策略，叫做"类型擦除"。具体类型在编译期就被称为已擦除，而具体类型只有在运行时才是已知的。

any Animal 这个既存类型的这两个实例，具有相同的静态类型，但动态类型不同。

类型擦除消除了不同动物值之间在类型层面上的区别，这让我们可以把具有不同动态类型的值，互换地当作同一个静态类型来使用。

我们可以利用类型擦除来编写一个由值类型组成的异构数组，这正是 feedAll 方法所需要的。

所以我们会用 any Animal 数组作为参数类型。

对带有关联类型的协议使用"any"关键字，是 Swift 5.7 中的新特性。

因为我们已经消除了具体动物类型之间在类型层面上的区别，我们也就消除了所有依赖于具体动物类型的类型关系，包括关联类型。

所以，我们无法知道这只动物需要哪种食物。

要依赖这些类型关系，我们需要回到一个具体动物类型是固定的上下文中。

我们不能直接在 any Animal 上调用 eat，而是需要调用接受 some Animal 的 feed 方法。

现在，any Animal 和 some Animal 是不同的类型，但编译器可以通过拆箱底层的值，把一个 any Animal 实例转换为 some Animal，并把它直接传给 some Animal 参数。

这种拆箱参数的能力是 Swift 5.7 中的新特性。

你可以把拆箱想象成编译器打开盒子，取出里面存放的值。

在 some Animal 参数的作用域内，这个值有一个固定的底层类型，所以我们可以使用底层类型上的所有操作，包括访问关联类型。

这非常棒，因为它让我们在需要的时候可以选择灵活的存储方式，同时仍然能够回到一个上下文中，在函数的作用域内通过固定底层类型，获得静态类型系统的完整表达能力。

而且大多数时候，你不需要去考虑拆箱这件事，因为它就会按你预期的方式正常运作，这和在 any Animal 上调用协议方法实际上就是在调用底层类型上的方法是类似的。

所以，我们可以把每个动物都传给 feed 方法，在这个方法里，我们可以为每次迭代中的这只具体动物种植并收获合适的作物。

在整个这个过程中，我们看到"some"和"any"具有不同的能力。

用"some"的话，底层类型是固定的。

这让你可以在泛型代码中依赖与底层类型之间的类型关系，所以你可以完整地访问你正在使用的协议上的 API 和关联类型。

当你需要存储任意具体类型时，就使用"any"。

"any"提供了类型擦除，这让你可以表示异构集合，用可选值来表示底层类型的缺失，并把这种抽象变成一个实现细节。

一般来说，默认写"some"，只有当你知道自己需要存储任意值时，才把"some"改成"any"。

采用这种方法，你只有在需要它所提供的存储灵活性时，才会付出类型擦除及其语义限制这个代价。

这个工作流程,和默认使用 let 常量,直到你知道自己需要可变性,是类似的。

在这个 session 里，我们走了一遍随着代码演进、获得更多功能而对代码进行泛化的工作流程。

我们从编写具体类型开始。

随着代码获得越来越多的功能，我们注意到不同具体类型之间出现了重复。

从那里出发，我们识别出了共同能力，并用协议对它们进行了泛化。

最后，我们用"some"和"any"编写了抽象代码，并讨论了为什么更推荐用"some"来写出表达力更强的代码。
