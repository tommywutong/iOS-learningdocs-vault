♪ 舒缓的器乐嘻哈音乐 ♪ ♪ 大家好，我是 John Crowson，Apple Performance Tools 团队的一名软件工程师。在本讲座中，我很高兴向大家介绍几款新工具，帮助你通过 Xcode 和设备端挂起检测来追踪 App 中的挂起。我将作为你的向导，带领你了解 App 开发流程的不同阶段，并思考每个阶段最适合使用哪些工具。本次讲座分为四部分：首先，我将介绍什么是挂起？然后，我将介绍一些工具，帮助你在开发 App、Beta 测试 App 以及发布 App 后，发现并诊断挂起。让我们开始吧！我想介绍我的团队正在开发的一款新 App：Food Truck，它将帮助管理专门销售甜甜圈的餐车。让我为你介绍我创建的一些甜甜圈类型。

嗯，滚动我的甜甜圈列表花了很长时间。这个 App 变得卡顿，并且无法响应我的任何触摸操作。在 Apple，我们将这种无响应期称为“挂起（hang）”。App 的主线程负责处理用户交互和更新视图内容。当主线程忙于执行工作或等待另一个线程及系统资源，导致更新视图内容延迟至少 250 毫秒时，就会报告一次挂起。在挂起解决之前，主线程也无法处理新的用户交互。对用户来说，App 就像完全卡住了。创建响应迅速的 App 对于提供良好的用户体验至关重要。持续无响应的 App 可能会导致用户强制退出、切换到其他 App，在某些情况下，甚至删除你的 App 并留下差评。因此，追踪 App 中的挂起对于获取和维系用户群至关重要。提供响应迅速的体验能确保用户乐于使用你的 App。

如需了解更多关于挂起及其成因，以及从代码中消除挂起的策略，请观看 2021 年的讲座“了解并消除 App 挂起”。App 开发流程可分为三个阶段。首先，在使用 Xcode 的开发阶段开发最新版本的 App。然后，在没有 Xcode 的 Beta 环境中测试 App 并收集反馈。例如，你可能有一个在设备上使用开发签名或通过 TestFlight 分发的 App 版本。最后，在 App Store 上发布最新版本的 App。即使对于最主动的开发者来说，新的挂起问题也可能在任何阶段出现，因此了解在每个阶段解决问题的工具非常重要。在 iOS 16 和 Xcode 14 之前，我们提供了两个工具来帮助你发现和诊断 App 中的挂起。MetricKit 是一个框架，支持从 Beta 或公开发布版 App 的个体用户那里收集非聚合的挂起率指标和诊断报告。Xcode Organizer 则提供了来自公开发布版 App 用户的聚合挂起率指标。这里存在空白，特别是在开发你的 App 或试图理解是哪些源代码导致了公开发布版挂起率指标上升时。在 iOS 16 和 Xcode 14 中，我们引入了几个新工具来提供帮助。在详细讲解之前，我们先简要介绍一下它们。Xcode 中的 Thread Performance Checker 会在你调试 App 时提醒你可能导致挂起的线程问题，而无需主动跟踪。Xcode 中的 Instruments 现在会在跟踪你的 App 时检测并标记挂起。设备端挂起检测可以在不使用 Xcode 或跟踪的情况下提供挂起检测，在使用开发签名或 TestFlight App 时提供实时挂起通知和辅助诊断。最后，Xcode 中的 Organizer 现在支持挂起报告，提供来自最终用户的聚合挂起诊断。现在你了解了什么是挂起以及它们可能出现的不同阶段，我将介绍如何在开发 App 时使用 Xcode 追踪挂起。在 Xcode 14 中，新的 Thread Performance Checker 工具会在 Xcode Issue Navigator 中通知你，当它检测到你的 App 的主线程上存在优先级反转和非 UI 工作时，这两者都是挂起的常见原因。现在我已经回到 Xcode，诊断之前在使用 Food Truck App 滚动我创建的甜甜圈时观察到的挂起。当我构建并运行 App，并重复用户交互操作时，Thread Performance Checker 工具向我发出警报，提示存在由优先级反转导致的挂起风险。这意味着一个高优先级线程正试图与一个低优先级线程同步。这可能表明我们注意到的挂起是由主线程等待不同的低优先级线程引起的。要检测 App 主线程上的优先级反转和非 UI 工作，请从相应 scheme 的 Diagnostics 部分启用 Thread Performance Checker 工具。Thread Performance Checker 警报帮助我发现了挂起的潜在罪魁祸首，但为了进一步排查，我想知道在挂起持续期间另一个线程在做什么。让我们使用另一个工具进行更深入的分析。Time Profiler 工具通过提供调用栈，让你能够了解 App 中每个线程随时间的变化所执行的操作。Xcode 14 新增功能，Time Profiler 还能检测挂起，并直接在相应的进程轨道中对其进行标记。在 Food Truck App 中，我将使用 Time Profiler 来确认在滚动甜甜圈时是否发生了挂起，以及它是否由主线程上的优先级反转引起，并找出导致主线程等待的低优先级线程在忙于做什么。我首先从 Xcode 的 Product > Profile 菜单开始。这将为发布构建 App，并启动已配置好目标 App 的 Instruments。我启动 Time Profiler 模板，并开始记录 Food Truck App 中有问题的用户交互的跟踪。

我看到在时间线中检测并标记了一个挂起。还指定了挂起持续时间，以帮助评估问题的严重性。接下来，我可以三次点击挂起间隔，这将为挂起持续时间创建一个时间过滤器，并过滤底部详情视图中的信息，使其仅显示在此选定时间间隔内发生的事件。这也使得更容易看到在此期间其他轨道中发生了什么。我注意到的第一件事是，在挂起间隔期间，主线程几乎没有 CPU 使用率，这意味着主线程无响应是因为它正在等待另一个线程，而不是因为它自身做了太多工作。这与之前 Thread Performance Checker 的优先级反转警报一致。接下来，我看到一个工作线程在挂起期间有很高的 CPU 使用率。这可能就是主线程正在等待的那个线程。下一步是检查工作线程在挂起期间在做什么，并解决优先级反转问题。在 Instruments 中检测和标记挂起是在分析你的 App 时显现任何遇到的挂起的好方法。它在 Time Profiler 和 CPU Profiler 工具中默认可用。还有一个新的独立挂起跟踪工具，你可以将其添加到任何跟踪文档中，以便与其他工具结合使用来显现挂起。除了检测和标记挂起之外，它还允许你配置挂起持续时间阈值，以查找特定时间段的无响应状态。你现在已经学会了如何使用 Xcode 在开发阶段发现和诊断挂起。即使在开发过程中进行了很好的测试覆盖，Beta 和公开发布环境也可能在你未曾考虑的代码路径中发现挂起。接下来，我将介绍如何在 App 部署到 Beta 环境后追踪挂起。我现在已经通过 App Store Connect 将 Food Truck App 的一个构建版本部署到 TestFlight，并且已下载到我的个人设备上。我将在城里售卖甜甜圈时测试这个 App，包括在一些网络信号不强的区域。但是，如果我的设备没有连接到 Xcode，我该如何发现和诊断挂起呢？为了在这些条件下持续监控挂起，iOS 16 在开发者设置中引入了设备端挂起检测，它提供实时挂起通知和辅助诊断。此功能适用于开发签名或 TestFlight App。是时候开始卖货了。当我尝试打开当前订单时，我收到一条设备端挂起检测通知，提示我的 App 正在挂起，这次持续了超过三秒。我想知道为什么我在使用 Xcode 开发时没有注意到这个挂起？我需要使用设备端挂起检测工具提供的诊断信息来了解更多信息。一旦你的 App 设置好用于开发，可以通过打开“设置”>“开发者”>“挂起检测”，并切换开关来启用此功能。“挂起阈值”设置允许你配置要检测的挂起最短持续时间。最短挂起阈值是 250 毫秒，可以调整为 500 毫秒或更高。长时间的挂起往往有更高的用户影响，但即使是较短的挂起也可能对体验造成干扰，具体取决于上下文，尤其是当它们连续发生时。安装你的 App 后，它将出现在受监控的 App 列表中。最后一部分显示了提醒过你的挂起可用日志的时间顺序列表。请注意，这些诊断是尽力而为的，并且以后台低优先级处理，以最大限度地减少性能开销。这意味着处理可能需要更长时间，尤其是在系统繁忙时。幸运的是，当新的诊断可用时，会显示一个被动通知。让我们检查一下当我在城里售卖甜甜圈时打开 App 中的订单时检测到的挂起的诊断信息。我获得了一个基于文本的挂起日志和一个 tailspin，用于检测到的挂起。基于文本的挂起日志信息较少，但可以让我们快速了解挂起情况。要进行更深入的调查，可以在 Instruments 中打开 tailspin，以查看进程内的线程交互或识别系统资源的使用情况等。首先，我将使用“共享”按钮将基于文本的挂起日志发送到 Mac，在那里我可以对其进行符号化并在更大的屏幕上查看。通过查看我传输并符号化的基于文本的挂起日志的摘录，我看到在挂起期间，我在主线程上调用了一个我知道会执行同步网络请求的方法。当我坐在办公桌前使用 Xcode 和强大的网络连接测试应用程序时，从网络请求数据可能没有任何延迟。但是，在网络连接有限的区域测试 App 时，请求需要更长时间，从而导致挂起。在这些不同的真实世界条件下测试 App 的 Beta 版本非常重要，而设备端挂起检测允许你仅使用设备来监控挂起。至此，我已经使用开发和 Beta 阶段可用的工具发现并诊断了挂起，并且已经准备好将 Food Truck App 提供给 App Store 中的用户。现在我将介绍，当你的 App 交到用户手中，运行在各种 OS 版本、设备以及你可能无法在前期测试中复制的其他真实世界条件下时，如何追踪挂起。Xcode 14 新增功能，Xcode Organizer 支持挂起报告，以提供来自用户设备的聚合挂起诊断。收集的数据来自同意共享 App 分析数据的用户，其中包含导致挂起的主线程堆栈跟踪信息。挂起报告可从 Xcode Organizer 左侧导航栏中获取。当收集到相似的堆栈跟踪时，它们会被分组在一起，形成单个特征（signature）。列表中，特征根据用户影响排序显示。对于每个特征，你可以找到一些示例挂起日志。每个挂起日志都包含导致挂起的代码的主线程堆栈跟踪、挂起持续时间以及日志来源的设备与 OS 版本。每个特征还提供了关于该特征负责的挂起日志数量的汇总统计，以及按 OS 版本和设备划分的日志明细。要识别对用户影响最大的挂起，请密切关注你的顶部特征。在此例中，顶部特征占此版本中挂起时间的 21%。由于我提交 App 到 App Store 时包含了符号信息，挂起报告向我显示了所有函数名称，与源代码中的完全一致。通过检查此主线程调用栈中的函数，我可以推断此挂起是由在主线程上同步读取磁盘文件引起的，而这是已知会阻塞很长时间的操作。解决对用户影响最大的性能问题至关重要，而 Organizer 是识别它们的绝佳工具。请在每次 App 发布后检查此数据，以验证以往的挂起是否已解决，并处理可能出现的新的挂起。

你还可以通过 App Store Connect REST API 检索相同的挂起报告数据。这可以帮助你将性能数据集成到自己的系统中，或进行额外的分析。我强烈建议你观看“使用电源与性能 API 识别趋势”视频，以了解更多关于使用 Power and Performance API 的信息。在 Xcode 13.2 中新增，你现在可以在监控 App 的电源和性能指标时接收通知。我建议你通过点击 Xcode Organizer 的 Regressions 视图右上角的“通知”按钮来启用通知。这将在你的 App 挂起率突然上升时提醒你。更多关于性能衰退的信息，请参考 2021 年的讲座“诊断 App 中的功能和性能衰退”。为了改善你在 Xcode Organizer 中的体验，我强烈建议你构建 App 并提交到 App Store 时包含符号信息。此符号信息用于将你的 App 中的函数名称添加到 Xcode Organizer 的报告中。这使得堆栈跟踪更容易理解。它还支持从堆栈跟踪中的函数名称一键导航到 Xcode 源代码编辑器中的函数定义。提取的信息仅限于函数和方法、源代码文件的名称和路径以及行号信息。需要注意的是，有限的符号信息将被安全存储，并且永远不会被共享。太棒了！你现在知道了如何在开发流程的每个阶段发现和诊断挂起。展望未来，要在开发过程中尽可能早的阶段发现、诊断和修复挂起。使用可用的工具提供帮助，包括主动使用 Instruments 分析新功能。请确保启用 Thread Performance Checker 和设备端挂起检测。每次发布后，使用 Xcode Organizer 解决对用户影响最大的挂起，并验证之前 App 版本中的挂起是否已解决。启用衰退通知，以便主动收到性能指标衰退的警报，这可能是电源和性能问题的第一个迹象。最后，构建 App 并提交到 App Store 时包含符号信息，以提高 Xcode Organizer 的实用性。遵循这些步骤，你的 App 将拥有更好的性能，从而提供尽可能最佳的用户体验。感谢你在 WWDC 的陪伴！♪
