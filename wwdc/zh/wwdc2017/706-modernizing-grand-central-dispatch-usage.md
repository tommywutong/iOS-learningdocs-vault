今天，我们将深入 GCD 的内部。这是一场内容丰富的高级讲座。所以，我们马上开始，先来看看我们的硬件。

我们设备中神奇的芯片随着时间的推移变得越来越快。然而，速度的提升很大程度上不仅是因为芯片本身更快了，更是因为它们在运行你的代码时变得更聪明了。它们会从你的代码行为中学习，以便更高效地运行。但是，如果你的代码在完成任务之前离开了当前核心，那么它可能就无法再利用该核心积累的历史信息了。当你回到核心时，可能会损失一些性能。

我们在自己的框架中也看到了这样的例子。当我们应用今天要讨论的一些优化技术时，仅仅通过简单的改动避免这些有问题的模式，就获得了巨大的速度提升。

因此，运用这些技术，你可以用更少的精力为更多用户带来高性能的应用。

今天，我们将让你深入了解系统在幕后对你的代码做了些什么。这样你就可以调整代码，更好地利用 GCD 提供的优势。

首先，我们将讨论如何最好地表达并行（parallelism）和并发（concurrency）。以及如何选择最佳方式向 Grand Central Dispatch 表达并发。

我们将介绍统一队列标识（Unified Queue Identity），这是今年我们对 GCD 进行的一项重大的底层改进。

最后，我们将向你展示如何使用 Instruments 在你的代码中发现有问题的地方。

那么，让我们从讨论并行和并发开始。

就本次讲座而言，我们所说的并行是指代码如何在多个不同核心上同时执行。而并发是指如何将应用的独立组件组合起来并发运行。在脑海中区分这两个概念的简单方法是，认识到并行通常需要多个核心，并且你想同时使用它们。而并发即使在单核系统上也能实现。它关乎的是如何交错安排组成应用的不同任务。所以，让我们先谈谈并行，以及在编写应用时可能如何使用它。

假设你制作了一个处理巨大图像的应用。你想利用 Mac Pro 上的多个核心来更快地处理这些图像。

你要做的是将图像分解成多个块。

让每个核心并行处理这些块。

这会带来加速，因为核心们同时在处理图像的不同部分。

那么，如何实现这一点呢？首先，你应该停下来考虑一下是否可以利用我们的系统框架。例如，Accelerate 框架内置了对高级图像算法并行执行的支持。Metal 和 Core Image 可以利用强大的 GPU。

假设你决定自己实现这个功能，GCD 为你提供了一个工具，可以轻松地表达这种模式。

在 GCD 中表达并行的方式是使用名为 `concurrentPerform` 的 API。

这让框架能够优化并行情况，因为它知道你正试图在所有核心上进行并行计算。

`concurrentPerform` 是一个并行 for 循环，它会自动在你的系统所有核心之间进行负载均衡。当你在 Swift 中使用它时，它会自动选择正确的上下文来运行你的所有计算。今年，我们通过 `DISPATCH_APPLY_AUTO` 关键字，将同样的功能带到了 Objective-C 接口 `dispatch_apply` 中。

这取代了队列参数，允许系统自动选择合适的上下文来运行你的代码。

那么，现在我们来看另一个参数，迭代计数（iteration count）。这是你的 `block` 在整个系统中被并行调用的次数。

这里如何选择一个好的值呢？你可能会认为一个好的值是核心的数量。假设我们在一个三核系统上执行工作负载。

这里你可以看到理想情况，三个 `block` 在所有三个核心上并行运行。现实世界可能并不总是这么完美。

如果第三个核心被 UI 渲染占用了一段时间会怎样呢？会发生的情况是，负载均衡器必须将第三个 `block` 移到第一个核心上来执行，因为第三个核心被占用了。于是我们得到了一段空闲的 CPU 时间气泡。我们本可以利用这段时间做更多的并行工作。结果，我们的工作负载花费了更长的时间。

我们该如何解决这个问题呢？我们可以增加迭代计数，给负载均衡器更多的灵活性。

这样看起来不错了。那个空洞消失了。实际上在第三个核心上还有另一个空洞。我们也可以利用那段时间。

所以，正如 Tim 在周一所说的，我们把迭代计数调到 11 吧。好了。我们填满了空洞，实现了高效执行。我们使用了系统上所有可用的资源，直到任务完成。这仍然是一个非常简化的例子。为了应对现实世界的复杂性，你应该多使用一个数量级，比如 1000。

你可以使用足够大的迭代计数，这样负载均衡器就有灵活性来填补系统中的空隙，并最大程度地利用系统可用资源。

然而，你应该确保平衡负载均衡器的开销与并行 for 循环中每个 `block` 所做的有用工作。

请记住，并非所有 CPU 都随时可用。系统上同时运行着许多任务。此外，并非每个工作线程都会取得同等的进展。

因此，总结一下，如果你遇到了并行问题，请确保利用系统为你提供的框架。你可以利用它们的能力来解决你的问题。

另外，请确保利用 `concurrentPerform` 内部的自动负载均衡。给它足够的灵活性来发挥它的优势。

以上就是关于并行的讨论。现在，我们切换到今天的主要话题，也就是并发。

那么，并发。

假设你正在编写一个简单的新闻 App。

你会如何构建它呢？首先，你将它分解成构成 App 的各个独立子系统。

想想如何将一个新闻 App 分解成其独立的子系统：你可能有一个负责渲染 UI 的 UI 组件，也就是主线程（main thread）。你可能还有一个存储文章的数据库。你可能还有一个从网络获取文章的网络子系统。为了更好地展示这个 App 是如何工作的，以及将其分解成子系统给你带来的好处，让我们想象一下它在一个现代系统上是如何并发执行的。

假设这里有一个时间线，顶部显示的是 CPU 轨迹。假设我们只有一个可用的 CPU。其他 CPU 由于某种原因正忙。

我们只有一个核心可用。任何时候，这些线程中只有一个能在这个 CPU 上运行。

那么，当用户点击按钮刷新新闻 App 中的文章列表时会发生什么？界面渲染器响应该按钮，然后向数据库发送一个异步请求。

接着数据库决定需要刷新文章，于是向网络子系统发出另一个命令。

然而，就在此时，用户再次触摸了 App。

因为数据库是在 App 的主线程之外运行的，操作系统可以立即将 CPU 切换到处理 UI 线程，并且能够立即响应用户，而无需等待数据库线程完成。

这就是将工作移出主线程的优势所在。

当用户界面响应完毕后，CPU 可以再切换回数据库线程，然后完成网络任务。

因此，像这样利用并发可以让你构建响应式的 App。主线程始终能够响应用户的操作，而无需等待应用的其他部分完成。让我们看看这对 CPU 来说是什么样子。

上面这些白线显示了子系统之间的上下文切换（context switch）。

上下文切换是指 CPU 在这些组成应用的不同子系统或线程之间进行切换。

如果你想形象地了解这对你的应用意味着什么，可以使用 Instruments 的“系统追踪”（System Trace），它能显示 CPU 和线程在你的应用运行时正在做什么。如果你想了解更多信息，可以观看去年 Instruments 团队介绍如何使用“系统追踪”的“System Trace In-Depth”讲座。

因此，上下文切换这个概念正是并发力量的来源。让我们看看这些上下文切换可能在何时发生以及是什么原因导致的。

它们可能在一个高优先级线程需要 CPU 时开始，就像我们之前看到的 UI 线程抢占数据库线程一样。

它也可能发生在线程完成当前工作，或正在等待获取资源时。或者是在等待异步请求完成时。

然而，并发这种强大的能力也伴随着巨大的责任。好东西也可能过犹不及。

假设你的 CPU 在网络线程和数据库线程之间来回切换。

几次上下文切换没问题，这就是并发的力量——你在不同任务之间切换。

但是，如果你在极短的时间内这样做了上千次，就会遇到麻烦。你开始损失性能，因为这里的每一条白线都是一次上下文切换。上下文切换的开销会累积起来。这不仅仅是执行上下文切换所花费的时间，还有核心已经积累的历史信息，每次上下文切换后它都必须重新获取这些信息。

你还可能遇到其他影响。例如，可能还有其他线程在你前面排队等待访问 CPU。

每次上下文切换时，你都必须等待队列中剩余的任务完成，因此可能会被排在你前面的其他线程延迟。

那么，让我们看看什么可能导致过度的上下文切换。

今天我们主要讨论三个原因。第一，反复等待对被争用资源的排他性访问。第二，反复在独立操作之间切换。第三，反复在多个线程之间传递一个操作。

你注意到我重复使用了“反复”这个词几次。

这是故意的。

上下文切换几次是可以的，这就是并发的工作方式，这是我们赋予你的能力。然而，当重复太多次时，成本就开始累积了。

让我们先看第一个原因，即对被争用资源的排他性访问。

这种情况何时会发生？主要情况是当你有一个锁（lock），并且有一堆线程都在尝试获取这个锁时。

那么，如何判断你的应用中发生了这种情况呢？我们可以回到“系统追踪”。我们看看它在 Instruments 中是什么样子。

假设这显示我们有许多线程运行了很短的时间，然后它们像小瀑布一样相互交接。

让我们聚焦第一个线程，看看 Instruments 告诉了我们什么。

我们有这条蓝色轨迹，它显示线程何时在 CPU 上运行。

红色轨迹显示它何时进行系统调用（sys call）。在这种情况下，它正在进行 `mutex_wait` 系统调用。这表明它大部分时间都在等待互斥锁（mutex）变得可用。而在核心上的时间非常短，只有 10 微秒。

系统上正在进行大量的上下文切换，这显示在顶部的上下文切换轨迹上。

那么，是什么原因导致的呢？让我们回到我们简单的时间线，看看过度的争用是如何发生的。

你会在时间线上看到这种阶梯状模式。每个线程运行很短的时间，然后放弃 CPU 给下一个线程，如此循环往复很长时间。

你希望你的工作看起来更像这样。

CPU 一次专注于一件事，完成它，然后再处理下一个任务。

那么，这里发生了什么导致了这种阶梯呢？让我们放大其中一个阶梯步骤。

这里我们聚焦于两个线程，绿色线程和蓝色线程。顶部有一个 CPU。

我们在这里添加了一条新的锁轨迹，显示锁的状态以及哪个线程拥有它。在这个例子中，蓝色线程拥有锁，绿色线程正在等待。

因此，当蓝色线程解锁时，该锁的所有权转移到绿色线程，因为它是下一个排队的。

但是，当蓝色线程回过头来再次尝试获取锁时，它无法获取，因为锁已经预留给绿色线程了。

这强制进行了一次上下文切换，因为我们现在必须做其他事情。我们切换到绿色线程，CPU 可以完成锁操作，然后我们可以重复这个过程。

有时这很有用。你希望每个在等待锁的线程都有机会获取资源。但是，如果你有一个以不同方式工作的锁呢？

让我们再看看不公平锁（unfair lock）是如何工作的。

这次，当蓝色线程解锁时，锁没有被预留。锁的所有权是可争用的。

蓝色线程可以再次获取锁，并且可以立即重新获得并停留在 CPU 上，而不必强制进行上下文切换。

这可能会让绿色线程很难真正有机会获取到锁，但它减少了蓝色线程为了重新获取锁而必须进行的上下文切换次数。

总结一下，当我们谈到锁争用时，你应该确保在“系统追踪”中测量你的应用，看看是否存在问题。如果存在，通常对于应用中的对象、属性、全局状态等可能被反复获取和释放锁的情况，不公平锁效果最好。

当我提到锁时，还有一件事我想谈谈，那就是锁的所有权（lock ownership）。

还记得我们之前的锁轨迹，运行时知道哪个线程接下来会解锁这个锁。

我们可以利用这种能力自动解决应用中锁的等待者和持有者之间的优先级反转（priority inversion）问题。甚至可以启用其他优化，比如有导向的 CPU 移交给持有锁的线程。Pierre 稍后会在我们的讲座中讨论 `dispatch_sync` 时谈到这一点。

我们经常被问到，哪些原语（primitive）具有这种能力，哪些没有。

让我们看看目前哪些底层原语做到了这一点。

具有单一已知所有者的原语具有这种能力。比如串行队列（serial queue）和 `os_unfair_lock`。

然而，非对称原语（asymmetric primitive），比如 dispatch semaphore 和 dispatch group，则没有这种能力，因为运行时不知道哪个线程会发出同步原语信号。

最后，具有多个所有者的原语，比如私有并发队列（private concurrent queue）或读写锁（reader-writer lock），目前系统没有利用这种能力，因为没有单一所有者。当你选择原语时，考虑你的用例是否涉及不同优先级的线程交互。

比如高优先级的 UI 线程与低优先级的后台线程。

如果是这样，你可能希望利用一个具有所有权的原语，以确保你的 UI 线程不会因为等待一个低优先级的后台线程而被延迟。总结来说，这些低效行为通常是你的应用的涌现属性。仅通过查看代码来发现这些问题并不容易。你应该在 Instruments 的“系统追踪”中观察，以可视化你应用的真实行为，从而为工作选择合适的锁。

今天我们有很多内容要讲，所以我无法深入讨论 GCD 的基础原理。如果你是这项技术的新手，或者需要温习一下，这里列出了一些以往 WWDC 大会中涉及 GCD 以及我们多年来对其所做增强的讲座。我鼓励你去看这些视频。

不过今天我们需要了解 GCD 的一些基本概念，从串行派发队列（serial dispatch queue）开始。

这实际上是 GCD 中基本的同步原语。它为你提供了互斥（mutual exclusion）以及 FIFO 顺序。这是 Daniel 刚才提到的有序且公平的原语之一。

它有一个并发的原子入队操作，因此多个线程同时向队列中入队操作是没问题的，同时还有一个由系统提供的单一出队线程，用于执行队列中的异步工作。

让我们看一个实际例子。这里我们通过调用 `dispatch_queue` 构造器创建一个串行队列，这会给你一块内存，只要你还没使用它，它在你的应用中就只是惰性的。

现在，想象有两个线程过来调用 `queue.async` 方法，向这个队列提交一些异步工作。如前所述，多个线程这样做是没问题的，这些条目会按照它们出现的顺序入队。

因为这是异步方法，这个方法会立即返回，线程可以继续它们的路。所以，可能这个第一个线程最终会调用 `queue.sync`。这是你与队列进行同步交互的方式。因为这是一个有序的原语，它的作用是向队列中入队一个占位符（placeholder），这样线程就可以等待，直到轮到它。

现在，会有一个异步工作线程过来执行这些异步工作条目，直到遇到那个占位符，此时队列的所有权将转移给在 `queue.sync` 中等待的线程，以便它能执行自己的 `block`。

我们需要的下一个概念是 dispatch source。这是 GCD 中的事件监控原语。这里我们设置一个来监控文件描述符的可读性，使用 `makeReadSource` 构造器。你向它传入一个队列，这个队列是 source 的目标队列（target queue），我们在这里执行 source 的事件处理器（event handler），这里仅仅是读取文件描述符。

这个目标队列也是你可能放置其他应该与此操作串行化的工作的地方，比如处理已读取的数据。

然后，我们为 source 设置取消处理器（cancel handler），这是 source 实现失效模式的方式。

最后，当一切设置完毕，我们调用 `source.activate` 开始监控。值得注意的是，source 实际上只是整个操作系统中一种更通用模式的一个实例，在这种模式中，你拥有在指定的目标队列上向你传递事件的对象。如果你熟悉 XPC，那就是另一个例子，XPC 连接。

并且，值得注意的是，我们今天告诉你的关于 source 的一切实际上都适用于所有此类对象。

将这两个概念放在一起，我们得到了所谓的目标队列层次（target queue hierarchy）。

这里我们有两个 source 及其关联的目标队列，S1、S2 和队列 Q1、Q2。我们可以通过在组合中再添加一个额外的串行队列，添加一个互斥队列（mutual exclusion queue）EQ 在底层，来形成一个小树。我们这样做的方法很简单，就是将可选的 `target` 参数传入 `dispatch_queue` 构造器。所以，这为整棵树提供了一个共享的单一互斥上下文。一次只能执行一个 source 或一个队列中的一个条目。

但它保留了队列 1 和队列 2 各自独立的队列顺序。让我们看看这是什么意思。

这里我有两个队列，队列 1 和队列 2，其中按特定顺序入队了一些条目。

因为我们在底层有这个额外的串行队列，并且它执行时，它们将在 EQ 中执行，并且会有一个工作线程来执行这些条目，从而赋予你互斥属性，一次只执行一个条目。但正如你所见，来自两个队列的条目可以交错执行，同时保留它们原始队列中的各自顺序。

那么，我们今天需要的最后一个概念是服务质量（quality of service，QoS）。

这是一个相当深奥的概念，过去曾详细讨论过。特别是 2014 年的“Power Performance and Diagnostics”讲座。如果这对你来说是新的，我建议你去看一下。

但我们今天从中所需要的，主要是它抽象的优先级概念。

在接下来的讲座中，我们将稍微互换地使用 QOS 和优先级这两个术语。

系统上有四个服务质量等级。从最高的用户交互（User Interactive，UI）到用户发起（User Initiated，IN）、实用工具（Utility，UT）再到后台（Background，BG）。最低的优先级。

那么，让我们看看如何将服务质量的概念与我们刚才看到的目标队列层次结合起来。

在这个层次结构中，树中的每个节点实际上都可以关联一个服务质量标签。

例如，source 2 可能与用户界面相关。它可能是为了监控一个事件，以便在事件触发时尽快更新 UI。所以，我们可能希望将 UI 标签放在这个 source 上。

另一个常见的用例是将标签放在互斥队列上，以提供一个执行流（flow of execution），这样这个树中的任何东西都不能在这个级别之下执行，比如在这个例子中的 UT。现在，如果这个树中的其他东西触发了，比如 source 1，那么如果它没有关联自己的服务质量，我们将为这个树使用这个执行流。

一个 source 触发实际上就是一个来自内核的异步操作。和之前一样，事件处理程序最终会被入队到互斥队列中去执行。

对于来自用户空间的异步操作，你的服务质量通常由调用 `queue.async` 的线程决定。所以我们有一个用户发起线程提交一个 IN 优先级的条目到队列中，最终进入 EQ 去执行。现在，也许我们有一个 source 2 触发了，它带有这个非常高优先级的 UI 相关事件，其事件处理器被执行，并将其事件处理器入队到 EQ 中。

那么，现在你会注意到我们遇到了优先级反转的情况。我们有三个条目入队，末尾是一个非常高优先级的条目，前面是一些低优先级的条目。这些必须按顺序执行。

系统通过使用一个工作线程，以当前入队的所有条目中的最高优先级来为你解决这个反转问题。值得记住右侧这个小树，因为它稍后会在讲座中再次出现。

有了这些，让我们进入本部分的主要话题，即如何使用我们刚刚学到的知识向 GCD 表达良好的并发粒度。让我们回到 Daniel 早些时候介绍的新闻 App，重点关注网络子系统。在网络子系统中，你需要在内核中监控一些网络连接。使用 GCD，你将使用 dispatch source 和 dispatch queue 来实现，就像你刚才看到的那样。但当然，在任何网络子系统中，你通常不只拥有一个网络连接，而是会有很多个，它们都会重复相同的设置。

因此，让我们聚焦右侧的三个连接，看看它们是如何执行的。

如果第一个连接触发，就像我们刚才看到的那样，该 source 的事件处理器会入队到它的目标队列。当然，如果其他两个连接同时触发，它们也会重复同样的过程，最终你会得到三个队列，每个队列都有一个事件处理器入队。

因为你底层有三个独立的串行队列，你实际上是要求系统为你提供三个独立的并发上下文。如果所有这些队列同时活跃起来，系统会应允，并为你创建三个线程来执行这些事件处理器。

也许这正是你想要的，也许这正是你的目标，但是这些事件处理器通常很小，只是从网络读取一些数据并将其入队到一个公共数据结构中。

此外，正如我们之前看到的，你不仅仅有三个连接，如果你的子系统中有许多网络连接，你可能有很多很多个。

这可能导致 Daniel 谈到的这种上下文切换模式，以及过度的上下文切换，你执行少量工作，上下文切换到另一个线程，然后再做一次，又一次，又一次。那么，在这个例子中，我们如何改进这种情况呢？我们可以应用刚才讨论的单一互斥上下文的概念，只需在底层添加一个额外的串行队列并形成一个层次结构，就可以为所有这些网络连接获得一个单一的互斥上下文。

如果它们同时触发，和之前一样的事情会发生，事件处理器会被入队到目标队列，但因为底层有一个额外的串行队列，将只有一个线程过来按顺序执行它们，而不是我们之前那样的多个线程。

这看起来是一个非常简单的改动，但这正是那种导致 Daniel 早些时候提到的我们自己的某些代码性能提升 1.3 倍的改动。

所以，这是一个我们如何避免反复在独立操作之间切换这种有问题的模式的例子。

但它实际上属于更通用的原则：在你的应用中避免不必要且无界限的并发。

一种可能导致这种情况的方式是许多队列同时变得活跃。一个例子就是我们刚才看到的独立的每客户端 source 模式。如果你的应用中有许多独立的每对象队列（per-object queue），并且你同时向它们提交异步工作，你也可能得到完全相同的现象。

如果你同时向全局并发队列提交许多工作条目，你也会看到这种情况。

特别是当这些工作条目阻塞时。全局并发队列的工作方式是，当现有线程阻塞时，它会创建更多线程，以在你的应用中提供持续良好的并发水平。但如果这些线程再次阻塞，你可能会得到我们称之为线程爆炸（thread explosion）的情况。

这是一个我们在 2015 年的“Building Responsive and Efficient Apps with GCD”中详细讨论过的主题。如果这对你来说是新的，我建议你去看那场讲座。

那么，如何在你的应用中选择合适的并发量以避免这些有问题的模式呢？我们过去向你推荐的一个想法是每个子系统使用一个队列。

回到我们的新闻 App，我们已经为 UI 准备了一个队列，即主队列（main queue），此外我们可以为网络子系统选择一个串行队列，为数据库子系统选择一个串行队列。

但我们今天学到的更通用的思考方式实际上是每个子系统使用一个队列层次。

这为子系统提供了一个互斥上下文，你可以保持系统的其余队列事件子结构不变，只需将网络队列或数据库队列作为队列层次底层的目标。

但是，对于一个复杂的应用或复杂的子系统来说，这可能有点过于简单化了。这里重要的是在你的应用中拥有固定数量的串行队列层次。因此，对于一个复杂的子系统，可能有必要增加额外的队列层次，比如为较慢的工作或较大的工作条目增加一个次级队列，这样第一个（主要）队列就能保持子系统对外部传入的请求保持响应。

在这种上下文中，另一个重要考虑因素是提交给这些子系统的工作的粒度。

当你在子系统之间移动时，你应该使用相当大的工作条目，以获得像我们在讲座早些时候看到的那种状态，即 CPU 能够足够长时间地执行你的子系统以达到高效的性能状态。

一旦进入子系统内部，比如这里的网络子系统，细分成更小的工作条目并使用更细的粒度来提高该子系统的响应性可能是合理的。例如，你可以通过拆分你的工作并异步到队列层次中的另一个队列来实现。这不会引入上下文切换，因为你已经在该子系统内部了。

总结一下，我们在这个部分看了什么？我们看到了如何将队列和 source 组织成串行队列层次。如何使用固定数量的串行队列层次来给 GCD 一个良好的并发粒度。以及如何在本部分前面为并行工作、在这里为子系统内部和子系统之间的并发工作，合适地调整工作条目的大小。接着，我将交给 Pierre，深入探讨我们如何改进 GCD，使其总是在单个线程上执行队列层次，以及你如何现代化你的代码以利用这一点。

当你使用 `makeReadSource` 工厂按钮创建 source 时，你设置了一系列事件、处理程序和属性。但真正有趣的是当你激活对象时发生什么。

并且现在将使用我刚才谈到的同步统一标识在核心里注册 source。如果我们看树中更高优先级的 UI QOS source，我们处理它的方式与第一个非常相似，除了当你设置事件处理器时，你指定了你实际想要的 QOS。

同样，有趣的是在激活时发生什么。那正是我们拍摄快照的时候，与之前我们从层次中获取 UT 的 QOS 不同，这里我们从你的提示中获取它。

因此，我们试图用这个相当复杂的标识来解决的真正问题，是之前 OS 版本中存在的一个问题，即相关操作会在线程之间来回反弹。让我们看看它以前是如何工作的。

记住，这是我们的队列层次，让我们调出本次讲座中已经见过多次的时间线。顶部是 CPU，但现在有一个新的轨迹，排他队列轨迹，它将显示在任何给定时刻该队列上正在执行什么。这实际上就是之前 macOS Sierra 和 iOS 10 中运行时的行为方式。让我们看看如果第一个 source 触发会发生什么。之前，就像我说的，线程请求是匿名的。我们会请求一个匿名线程，在线程上传递事件，然后我们会处理这个事件。

当我们在你的应用内部处理事件时，只有到那时我们才意识到这个事件是要在一个队列上运行的。我们会将事件处理器入队。但是，由于队列无人认领，这个线程实际上可以成为那个队列并开始为你的 source 执行事件处理器。

我们就这样做了。现在，有趣的是当第二个更高优先级的 source 触发时会发生什么？实际上是一样的。由于这里是层次 QOS，更高的优先级，这正是你现在正在执行的优先级。

我们会启动一个新的匿名线程，在线程上传递那个更高优先级的事件。

并查看该事件的含义。我们会注意到它正是针对同一个队列层次，而且只有在那时才能知道。并将事件处理器入队到我们刚刚占用的那个之后。

我们摆脱了那个线程。

而且，我们当然也摆脱了我们不想要的那两次上下文切换。

当然，这很重要，因为与 Daniel 向你展示的 UI 触摸事件抢占不同，那里我们可以利用实际上有两个独立线程的优势，使你的应用响应更快。而在这里，我们没有从任何这些上下文切换中获益，因为这些事件处理器 S1 和 S2 无论如何都必须按顺序执行。所以，提前知道那个事件没有用。如果你看看今天的实际流程，看起来更像这样。

这里发生了什么？这个流程中最重要的部分是，现在如果你看这个线程，它被称为 EQ，因为这是统一标识的关键点，线程和 EQ 基本上是同一个对象。内核知道它实际上是在执行一个队列，这反映在 CPU 轨迹上。你再也看不到事件了，它只是在运行你的队列。

然而，你可能会问，我们是如何设法在没有辅助线程的情况下传递事件（第二个事件）的。这确实是个好问题。当事件触发时，现在我们知道了它将在哪里执行，你将在哪里处理它。我们只需标记线程。

不需要辅助线程。

在第一次可能的机会，我们会注意到线程被标记为“有待处理的事件”。我们会在合适的时机，即第一个处理器完成后，立即将事件出队。我们可以从内核获取事件，查看它们，并将它们的处理器入队到你的层次中。那么，我们为什么要进行这么复杂的解释呢？这是为了让你理解如何最好地利用运行时行为。

因为很明显，运行时使用你给出的每一个可能的提示来优化你应用中的行为。

并且，知道如何提示以及何时正确地提示运行时，以便我们做出正确的决策，这很重要。这引出了一个问题，对于现有的代码库，你应该做些什么来利用我们重建的这些核心技术？实际上，要充分利用这项技术，需要遵循两个步骤。第一步是激活后不进行变更（no mutation after activation）。

第二步是特别关注并留意你的目标队列层次。

这意味着什么呢？“激活后不进行变更”真正意味着，当你在 dispatch 对象上设置任何类型的属性时，你可以设置它们，但是一旦你激活了该对象，就应该停止修改它们。第二个例子，这是我们已经在讲座中看到过好几次的 source。它监控一个文件描述符的可读性。你设置了一堆属性、处理器：事件处理器、取消处理器。你可能还设置了注册处理器。

你甚至可以修改它们几次，这没问题，你可以改变主意。然后你激活 source。

这里的约定是，你应该停止修改你的对象。

在事后，例如，更改 source 的目标队列，是非常诱人的。这会导致问题。原因正如我稍早前展示的，在激活时我们会拍摄你对象属性的快照，并基于该快照在未来做出决策。如果你事后更改了目标队列层次，那将使快照失效，从而破坏许多非常重要的优化，例如 GCD 中的优先级反转避免算法、我之前介绍的用于 `dispatch_sync` 的直接移交，或者我们刚才经历的所有防御性和有意的优化。

我坚持 Daniel 早些时候提出的观点，即你们中的许多人可能从未需要在你的应用中创建 dispatch source。这没关系，这确实是它应该的工作方式。

你可能实际上通过系统框架使用了它们很多次。如果你有一个框架，需要向外提供一个 dispatch 队列，因为它们在幕后代表你将一些通知异步到该队列上，那就更常见了。在幕后，它们有这些 source 之一。因此，如果你改变了系统的假设，你实际上也会破坏所有这些优化。

所以，我希望我已经很清楚地说清楚了，你的目标层次是至关重要的，你必须保护它。
