大家下午好。欢迎来到 Core Data 最佳实践。我叫 Scott Perry，在 Core Data 团队工作。稍后我的同事 Nick Gillett 也会加入。

今天的安排如下：首先，我们聊聊开始使用 Core Data 的流程是如何随时间演化的。接着，会介绍如何利用持久化容器（persistent container）中的扩展点来更轻松地演进我们的 App。之后，我们讨论如何随着 App 需求的变化和数据增长来演变我们的模型。

然后，Nick 会谈谈我们的 App 如何即使在规模扩大到超乎想象的程度时，仍能维持其性能。最后，我们将介绍一些关于转换器、调试和测试的精彩内容。但首先，让我们来构建一个 App。我喜欢拍照，所以我们要构建一个能让我与朋友分享照片并获取他们评论的 App，哪怕只有 Nick 来问我幻灯片做得怎么样了。

我们应该把 App 的数据存放在哪里呢？嗯，可以全部放在线上，但我通常在旅行时拍照，网络连接时有时无，所以我们应该把数据存储在本地，并组织到某种持久化存储中。

现在，我们有帖子和评论，它们的实例以及它们之间的关系构成了一个对象图，我们已决定需要将这些内容持久化到磁盘上，这正是 Core Data 的用武之地。

那么，我们就用它。首先将这里的草图转换成存储能够理解的东西——托管对象模型（managed object model）。

我们需要为所有内容定义字段，包括图像数据和发布时间的特性（attribute），还需要定义帖子和评论之间的关系。我们也确定了需要一个存储，但随着时间的推移，在磁盘上维护数据涉及方方面面的工作。

幸运的是，Core Data 提供了一个持久化存储协调器（persistent store coordinator）来管理这件事。协调器可以执行诸如将 App 的模型与存储的版本进行比较，并在 App 演进时自动将数据向前迁移等操作。最后，托管对象上下文（managed object context）提供对数据的安全、快速且可预测的访问，即使我们通过查询世代（query generations）、连接池和日志跟踪等功能同时使用多个上下文也是如此。

搭建栈环境的整个过程包括找到并加载模型，以及决定存储位置。但一旦你发布了 App，这些错误路径中有许多实际上已不可能再失败。因此，Core Data 提供了一个容器类型，可以大幅减少搭建栈环境所需的样板代码。你只需按名称引用模型，持久化容器就会从主 bundle 中加载它，并将存储保存在一个一致的位置。这种持久化容器类型封装了整个栈，并包含用于获取共享主队列视图上下文的便捷方法，以及用于生成后台上下文和执行后台工作的工厂方法。它的设计也让你很容易随着 App 的增长继续使用。举个例子，假设我们想把模型层提取到它自己的框架中。我们可以在 Xcode 中创建一个新的 Framework Target，把代码移入其中。这一切都超级简单。但当我们把模型移到新 Target 时，在构建出的产品中，资源会从 App 移到新的框架中——这本该如此——但现在 `NSPersistentContainer` 却不知道去哪里找我们的模型了。这是因为默认情况下它只检查主 bundle。为什么不检查所有 bundle 呢？嗯，对一个复杂的 App 来说，搜索 App 的所有 bundle 可能会变得很慢，而这并不是你每次启动栈时都想付出的代价。

那我们怎么解决？我们可以自己从框架 bundle 中提取出模型，再使用容器提供的其他构造方法之一，比如接受显式的 `NSManagedObjectModel` 的那个。不过，`NSPersistentContainer` 实际上提供了一种方法来改变它搜索哪个 bundle。

你看，`NSPersistentContainer` 知道自己何时被派生子类，它会把子类的类型作为查找模型时的线索。我们想利用这一点，只需要创建一个子类。它甚至不需要包含任何代码。

这样一来，任何想通过容器来使用我们模型的代码，只需改用那个子类，持久化容器就会改为在我们的框架 bundle 中查找模型。这很有意思，但既然我们已经在费心提取 App 的资源，如果同时也改善一下磁盘上数据的组织方式，岂不更好？默认情况下，新的持久化容器会配备一个针对 SQLite 存储的描述（store description），并启用自动迁移，在 iOS 上存放在 App 的文稿目录下。当我们的模型代码还是 App 的一部分时，这样很好。但我们应该尽量避免让新框架的文件与 App 的文件纠缠在一起。

既然我们已经为方便查找模型而子类化了 `NSPersistentContainer`，那就让我们在此基础上进一步改进。

改变存储位置的粗暴方法是：在加载存储之前，直接修改 `persistentStoreDescription` 里的 URL。

某些情况下这正是你需要的，我们也可以在这里使用这种模式。但我们其实不必这么做，因为 `NSPersistentContainer` 在创建持久化存储描述时会调用自己的 `defaultDirectoryURL` 方法。而这个方法就是专门设计来让你重写（override）的。在这个例子中，我们只需附加一个路径组件即可。不过，这也是个好方式，能让你为缓存或其他类型的栈设置容器，这些栈需要把自己的存储放在不同的位置，比如你的 task 数据。好了，现在我们已经把 Core Data 栈都搞清楚了，让我们来看看我们写的 App 和一些视图控制器。看上去我们写了一些相当专门的视图控制器。这里有一个显示所有“我的”帖子的，还有一个显示“所有作者”所有帖子的。就连详情视图也重复了。感觉好像我们本来能少写一半代码。我们真正需要的，应该是一个用来显示帖子列表的视图控制器，以及另一个用于显示单个帖子的视图控制器。我们可以通过在视图控制器之间定义清晰的边界来实现这一点，这个边界的形式就是接收模型对象的接口。

每个控制器通过其模型参数来配置自己，然后可以根据自己是在展示“我的帖子”还是“别人的帖子”来定制视图和单元格。在设计使用 Core Data 的视图控制器时，列表视图应当接收获取请求（fetch request），详情视图应当接收托管对象（managed object）。

视图控制器还需要一个托管对象上下文，可以是容器的视图上下文，也可以是其他主队列上下文。而这种用 Core Data 泛化视图控制器的模式，并不只针对 UI；它用在工具类上也效果极佳。

面对后台工作控制器，我们不传递用于展示的 Core Data 类型，而是传递 URL 或序列化数据之类，然后用后台上下文而不是视图上下文，把它们变成新建或更新后的托管对象来完成工作。

采用这种接口和工具类模式超级简单，因为初始化方法是我们自己控制的，所以我们可以直接通过参数来要求提供创建控制器所需的依赖。但我们又是怎么把边界变量送进视图控制器的呢？嗯，如果我们用的是 segue，我们可以重写 `prepare(for:sender:)` 方法，拿到目标视图控制器（destinationViewController）的引用，然后在那里配置它。如果我们用的是 storyboard 或 nib，那我们本来就有负责创建目标视图控制器的代码，只需要在展示前把属性设上就行。而如果我们自己手动控制，就可以写一个直接明确这些边界条件的初始化方法，就像处理工具类时一样。好了。现在，我们为视图控制器准备了一个获取请求和一个上下文，但在把它们结合起来获取结果之前，我们应该再对获取请求做一点配置，以确保我们的控制器有出色的性能。

有时设置一个获取限制（fetch limit）是合理的，但对我们的列表视图来说，批处理更合理，因为我们想显示全部数据，而且我们确切地知道视图控制器在屏幕上能同时容纳多少个单元格。一般来说，对于可能返回无上限数量的结果的获取请求，总该把这两个选项中的至少一个设好。

至此，我们已经可以把获取请求转为对象，并用结果填充列表视图了。可如果我们想让 UI 随着变化的到来而实时更新呢？Core Data 也用获取结果控制器（fetched results controller）替我们解决了这个问题。获取结果控制器是从 Sierra 开始就在所有平台上都提供的。你只需要在委托协议（delegate protocol）和它要驱动的视图之间写一个适配器，就能采用它。而要创建一个，我们只需要一个获取请求和一个上下文。

获取结果控制器甚至支持驱动更高级的列表视图概念，比如分区。

如果我们想按发表日期把帖子分到分区里，可以这样：给 Xcode 生成的 Post 类型扩展一个计算属性，再把它的名字传给获取结果控制器的构造方法。

这能很好地工作。但如果我们的视图控制器并不只是一个对象列表那么简单呢？比如，我们想在 App 上展示一张“每日帖子数”的图表，怎么办？嗯，首先我们不要低估获取请求的能力。我是一个人，上个月没有哪一天发布过超过 40 张照片。在 30 天里，一次性从存储里把这些数据全取出来，依然是相当合理的数据量。如果之前定义的“day”属性是模型里实体的一部分，那么我们就可以写一个 fetch request，按帖子发布的日期来统计帖子数量。这个请求有三个部分。首先是设置范围，我们要过去 30 天的数据。其次，我们要把所有 day 属性值相同的结果放到一组里。既然我们现在获取的是聚合数据而不是一个个对象，那我们也得把结果类型改成一个更合适的类型，在这个例子里是字典。

最后，我们定义一个表达式，来代表每一组里的对象数量，并让获取请求同时返回这个计数值和它所对应的日期。

这个获取请求会返回 30 个结果，每一个结果就是我们图表上的一个数据点。

如果你熟悉数据库，下面就是 Core Data 从该获取请求生成的 SQLite 查询。它跟你自己亲手写的查询一模一样。Core Data 懂得如何把许多表达式函数转换成最优的数据库查询。GROUP BY 查询可以使用 AVERAGE 和 SUM 这类聚合函数；而标量查询就像普通的 fetch request 一样，可以使用标量数学和日期函数，比如用来取绝对值的 ABS 和用来取当前时间的 NOW。如果你想进一步了解能用 `NSExpression` 做什么，可以查阅文档里关于它支持的函数列表。Core Data 的 fetch requests 支持其中很多函数。

好。那么，通过使用表达式，fetch requests 已经能完成很多事情了。但在为我们的图表计算这些计数时，SQLite 仍然会把我们的每一个帖子都读一遍内存。这个开销对于展示一个人一个月产生的帖子数量的图表来说还行，但如果我们想展示更大量级的数据呢？如果我们想展示一整年，或者我们的小 App 开始处理数量级大得多的数据呢？那时，仅仅为了展示 30 个数据点，获取请求就要一个接一个地数至少 5 万个帖子，这就不够快了。我们的视图和模型之间的不匹配，已经到了我们需要开始做些反规范化（denormalization）工作的地步了。

反规范化，是指我们添加冗余的数据或元数据副本，以增加一些额外的记录维护开销为代价，来提升读取性能。数据库索引就是个很好的例子。

把计数的元数据加到我们的存储里，正是我们为了把图表性能拉回正轨所需要的那种取舍。那么，我们来看看模型如何把帖子按天分组并计数。我们需要一个新实体，它有两个特性，以及一些保持其准确性的额外维护工作。按天分组极大地改进了我们的获取请求，可以确保覆盖多年数据的图表都有良好的性能，所以我们只需要做这一层反规范化。那么，我们传给图表视图控制器的那个 fetch request 呢？它超级简单。

它和我们传给其他任意列表视图的 fetch request 并没有天差地别。实际上，如果你眯起眼睛看，图表视图本就是一种……嗯，特别的列表视图。

但那个额外的维护工作怎么办？每当有新帖子发布，我们得把计数加一；每当帖子被删除，就得把计数减一。我们可以在修改帖子对象相关状态的方法里做这件事，但更不易出错的办法，是响应上下文保存（context saving）来更新计数。我们可以去监听托管对象的 `NSManagedObjectContextWillSave` 通知，用一个函数遍历所有被插入的帖子，把每个受影响日期的计数加一；再用另一个循环遍历所有被删除的对象，把每个受影响日期的计数减一。这些都是在上下文提交到数据库之前影响其状态，因此整个过程都在同一个事务里发生，所以扩展性非常好。这很有用，因为我的同事 Nick Gillett 接下来要讲的是，在我们的这个小 App 扩展到超乎我们最疯狂想象的过程中，Core Data 能怎么帮到我们。Nick。谢谢 Scott。嗯，就像 Scott 说的，随着你的应用程序增长，它们会变得越来越复杂。在 Core Data 团队，你的应用程序能够增长对我们是至关重要的。事实上，这就是我们期望的。我们存在的全部意义，就在于帮你管理这一增长，让你的工作更高效，帮你为你的客户带来更多价值。但是，这个过程是以非常特定于你的应用程序的方式发生的。它也和你的客户体验——或者说你期望他们体验你 App 的方式——高度一致。不幸的是，就像所有复杂系统一样，随着系统的增长并变得更复杂，它也倾向于走向混乱。所以今天，我们要谈谈 Core Data 能如何帮你管理这种混乱，并把它结构化。我们会讨论如何构建可预测的行为，以及帮你构建可调优的容器，使其与你关注的那些体验指标对齐。

这是什么意思呢？当我们想到“指标”时，可以从几个不同的角度来思考。首先是和客户体验对齐的角度。通常我们把它定义为客户能感受到的那些东西，比如始终如一的用户界面、响应灵敏的滚动视图，还有一些愉悦感。但这些东西对工程师来说真的很难捕捉。所以，我们得把它们翻译成工程指标，诸如：峰值内存占用量、在给定任务里消耗了多少电池、在给定任务里烧掉了多少 CPU 时间，最后，在给定任务里做了多少 IO。

为了把这个讲得更具体些，我们来看看这个 App。在座的可能有人还记得去年 WWDC 上展示的那个 history 演示 App，为了这次演讲我修改了一下。我们的客户在使用 App 时有这么几个操作。第一个是，他们可以通过点按 + 按钮，往数据库里添加一条帖子。

他们也可以通过点按“Download”，从服务器下载任何待处理的数据。

最后，对于任何还没有上传到服务器上的内容，他们可以点按“Post All”。

现在，这个 App 只有一组非常小的用户可执行交互。然而，当这些操作并发进行时，它也倾向于走向混乱。所以我们可以看到，哪怕只有这么一小撮操作，并发执行的东西也可能在 App 中引起一大堆不同的状态变更——而对我们来说，最糟糕的就是最终落得个像这样的用户体验。这种“部分完成”的概念对客户来说毫无意义。事实上，对我们来说也毫无意义。

Core Data 就是来帮忙的，用的是查询世代（query generations）。查询世代是在 2016 年 WWDC 的“Core Data 新亮点” session 上推出的。所以如果你对它们还不熟悉，我强烈建议你去回看那一场 session，了解更多关于它们怎么运行的细节。你需要知道的是，它们要求使用预写日志模式（write-ahead logging），并且只能用于 SQLite。

查询世代的目标，是把你的托管对象上下文和那些会与之竞争的读写隔离开来。这些竞争操作可以是对后台的写入，也可以是某些用户触发的操作——而你对这些操作还不想让它们立刻体现在特定上下文中。

查询世代提供一个一致、持久的数据库视图。也就是说，不论其他上下文在某个时间点正在往数据库写什么，对 fetches 来说，它都会返回同样的结果。

最棒的是，我们只需要一行代码就能用上它们。

这是一个重载表格视图的典型改动。我们只需要插一句对 `NSManagedObjectContext` 的 `setQueryGenerationFromToken` 调用，把当前查询世代传进去就行。

而到了要更新它们的时候，我们可以像平时一样，通过接收 `NSManagedObjectContextDidSave` 通知来刷新。这样，我们就能够在正确的时间，把 App 数据的变更体现在 UI 里。

可如果我们要写入的数据跟 UI 没有关系呢？比如说去下载 Scott 前面提到的一些评论？这种情况下，我们不希望那些数据出现在用户界面里，也不希望它们引发 UI 改变，因为这些变更对用户来说是完全不可见的。所以，我们实际上可以借助历史跟踪（persistent history tracking）来把这些更新过滤掉。持久化历史跟踪是在 iOS 11 和 macOS 10.13 中新增的。我们在去年 WWDC 的“Core Data 新亮点” session 里介绍过它。要了解它怎么运作以及有哪些基础特性，你可以去参考那场 session。

持久化历史跟踪是一种很棒的方式，可以让你获取连接到数据库的每一次事务的持久记录。这对我们来说有好几种用处。不过针对今天的演讲，我们关注的是 `NSPersistentHistoryChange`，它提供给我们 `changedObjectID` 和一组 `updatedProperties`；还有 `NSPersistentHistoryTransaction`，它提供一组变更和一个 `objectIDNotification`。

那么，我们来考虑下面这组变更。如你所见，这是一批正在插入我们数据库的帖子。当这件事发生时，在我们的表格视图里，我们当然想刷新 UI。这个我们可以通过 `objectIDNotification` 做到。它们类似于 `NSManagedObjectContextDidSave` 通知，可以用同样的 API 来合并。

但如果我们下载了一个评论列表，而我们不希望这些数据引起对用户的 UI 更新，那我们就可以把它们过滤掉。用这一小段代码，我们就能把一个给定事务中的变更过滤一遍，判断其中是否有任何变更是和 Post 实体相关的。这样一来，我们就不会刷新 UI，也就不会给用户带来不必要的闪烁或卡顿。

但正如你在这看到的，我们其实只用了帖子内容里的很小一部分。事实上，我们只用到了两个属性：image 和 title。

所以，我们其实可以做得比仅仅按实体过滤更精细。我们实际上可以按“被更新的属性”，借助历史变更来做过滤。用这种方式，我们就可以创建高度目标明确的用户体验更新——只对用户看得见的那部分变更做响应。但是 Core Data 也可以帮你为你的用户支持新的交互。随着你的数据变复杂、规模变大，某些编辑操作的开销也可能会变高。举个例子，设想一个简单的相片浏览器。通常，当我们的 App 从后向前时，我们会想……我们会想引入一些新的功能，让执行重复性的任务更简单，比如多选。而 Core Data 可以通过使用批量操作（batch operations）来支持这一点。

实际上，我们只需要几行代码，就能把一整套相片批量标记为最爱或取消最爱。而只需要一行代码，我们就能用批量删除操作来清除或删除数据库中的一组记录。而且，这些操作的扩展方式是那种把对象触发故障（fault）进内存的方式无法企及的。举例来说，在执行删除时，传统的做法是调用 `NSManagedObject.delete`，其开销会随数据库中记录的规模而增长。当你逐个删除对象，它们的内存在被触发到上下文的过程中，数据库越大，开销就越高。但应用批量操作，我们只需要少得多的内存就能完成同样的变动。这就形成了我们随着数据增长而希望看到的那种曲线——数据集越大，我们用的内存就越少。在处理一千万行数据时，批量操作使用的内存大约只占传统删除方式的 7%。

所以，这是在用户设备上节省资源的非常强大的方式。但批量操作的一个传统问题是，它们难以交互，因为它们不产生保存通知。于是，历史跟踪又登场了。用持久化历史跟踪，我们可以把作为批量删除或批量更新的一部分发生在数据库里的事务提取出来，再用 `objectIDNotification` 这个方法，生成一个工作起来就像保存通知一样的通知。这样，获取结果控制器或者 App 里的任何其他上下文，就都能随着这些通知的到来去增量式更新了。那么，刚才那些就是你可以用 Core Data 来管理增长中数据的几种方式，但是你的工作流本身怎么办？Core Data 能为你这个开发者、工程师做点什么，让你的 App 更容易构建和测试？第一点，我们可以帮助未来的你自己。

你可能知道，`NSKeyedArchiver` 在变化。我们正在全平台推行安全编码（secure coding），而 `KeyedArchiver` API 今年为此有了非常大的变化。

对 Core Data 来说，这意味着值转换器正在改变。所以，如果你在托管对象模型里有可转换属性（transformable property），而你今天没有指定值转换器，那你以前会得到 `NSKeyedUnarchiveFromDataTransformer` 作为默认值转换器。未来，你会得到 `NSSecureUnarchiveFromDataTransformer`，它在底层实现了安全编码。你今天就应该采用它。今天早上就有一场关于这个主题的精彩演讲，叫做“你可以信任的数据”。我强烈建议你去看一下，以获取更多关于安全编码以及如何让你的 App 更具弹性的信息。

你可以在模型编辑器中，通过可转换属性里的“Value Transformer Name”字段来指定它。

而今天，我们想让你自己来把它用上。这在未来的版本里会变成默认行为。同时，在一个未来版本里，Xcode 也会开始对所有使用默认值转换器名称的情况发出警告。

如果你是在代码里构建模型，可以通过 `NSAttributeDescription` 上的 `valueTransformerName` 属性来设置。

如果你没有在编码自定义类的类型，那这件事对你应该是完全透明的。也就是说，对于 plist 类型，这属于零操作。你只需要改一下值转换器名字，就会获得新的安全编码行为。但是，如果你是在实现自定义类，那么这些类就需要遵循安全编码。你可以到实验室来找我们帮忙。不过我们能帮你的还更多。在 Core Data 这边，这些年我们一直在花时间构建新的调试工具，来帮你理解栈下面到底在发生什么。这张图是我们偏好的默认 Scheme 配置。我们有几个进程参数（process arguments），可以帮你获取更多关于 SQLite 的调试信息。但其中你最应该始终带着运行的一个，是 `com.apple.Core Data.ConcurrencyDebug`。这能捕获 App 里的任何队列使用违规（queue exceptions），比如那些你跨主队列上下文和后台队列上下文传递对象的区域，或者你没有遵守托管对象的实际上下文的区域。SQLite 也有很多有意思的环境变量，它的线程安全断言和文件系统断言，是确保你在他们 API 以及文件系统上拥有正确性的好办法。自动跟踪（auto tracing）则是让你能一窥幕后究竟的很好手段，是对调试日志的额外补充。`com.apple.Core Data.SQLDebug` 有四个级别。第一级最有趣，对性能的影响也最小。第四级输出的日志最详细，但运行时会导致显著的性能开销。当你启用 SQL 调试以及我们的多线程断言时，你会在控制台看到一些日志，这表明断言已启用并且正在正确运行。

开启 SQL 调试后，你将能看到诸如针对 fetch requests 的 select 语句以及它们耗时多久之类的信息。而如果你设成第四级，甚至还能看到 `EXPLAIN`，它会显示出给定 select 语句的查询计划。这里我们可以看到，我们的表格视图是通过全表扫描来筛选的，然后又用了一个内存中的临时 B-tree 来按时间戳做排序。这是一个潜在的性能问题。在你运行 App 的时候，可以借助这类消息来发现自己可能在哪些地方做了超出必要的工作。

好，那我们怎么去修复它呢？巧了，SQLite 3 其实可以告诉我们答案。如果我们打开一个数据库，拿着从 SQL 日志里得到的 select 查询交给它，我们可以启用一个叫“Expert”的模式。这个模式会分析查询，并通过创建一个覆盖索引（covering index）来给出优化的理想方案。

我们在模型编辑器里，通过给 Post 实体添加一个获取索引（fetch index）就能做这件事。在这里，我把它配置为对时间戳生效，并让数据按降序被取出来，因为我们要在表格视图的最上方展示最新的帖子。

当我们再次运行 App 时，我们能看到同样的 select 日志。

不过这次，我们看到 select 查询在查询过程中命中了覆盖索引。`EXPLAIN` 告诉我们，该查询会利用覆盖索引来完成它的 order by。Core Data 支持很多种索引类型，包括使用 R-tree 的复合索引。这对创建任何类型的查询，或者是去优化一个在其 select 语句里使用了边界框的查询，都很有用。最常见的情况就是和位置相关的查询。我们可以通过给我们的 Post 实体再添加一个索引来设置这一切，这个索引用到了我为这一页幻灯片添加的 latitude 和 longitude 属性。

我们在这个选择框里把查询类型改成 R-tree。然后，就可以在 fetch request 上设置谓词（predicate），来请求所有发生在中国大陆境内的帖子。

这个谓词相对更复杂一点，因为它在实际的 select 语句内部使用了函数，来命中我们在托管对象模型里建的那个索引。

当我们不用这个谓词和这个索引运行 App 时，我们看到的还是之前那个结果，只会命中时间戳索引。但当我们带着新索引和谓词运行时，我们会看到 SQLite 正在使用这个索引，为那两个 BETWEEN 语句生成更快的结果。

遗憾的是，因为我们的时间戳索引没有任何起边界作用的谓词作用在它上面，SQLite 没法拿它来做排序。所以，我们这里选择的优化策略是：用一个复合索引，先把结果集过滤到一个更小的对象集合，然后再对 order by 做一个内存中的 B-tree 排序。如你所见，这个索引把我们的获取性能提升了大约 25%。

在这个例子里，我的性能测试是在大约 10 万行的规模上跑的。我们观察到的仅仅是 fetch 操作，就有大约 130 毫秒的提升。

这也就引出了我的下一个话题——配合 Core Data 做测试。

大家可能知道，我们非常喜欢测试。测试是了不起的东西。在 Core Data 内部，我们用测试来确保正确性，也用它来学习。测试是了解 Core Data 的功能，以及我们的 API 在给定的一组条件下如何表现的好方法。

测试也是验证你对 Core Data 运作方式的假定，以及它将如何帮助你的客户在你的 App 中获得更好体验的绝佳途径。正如在前面的例子里你看到的，我们可以验证我们的 R-tree 索引即使在经历了内存 B-tree 排序的过程后，也确实给了我们性能上的好处。

测试还能捕获你的产品需求。在 Core Data 这边，这非常重要，因为它能帮助我们围绕你的期望进行交流。通过测试，我们可以看到你在代码里做了什么，以及你期望这些代码行怎样为你的客户服务。

有一些重要的事项，你可以设置好，让这件事对自己更轻松，比如写一个能生成持久化容器的基类。

屏幕上的这个基类碰巧是用 `/dev/null` 这个文件 URL 来放持久化存储的。这是让那些在少量托管对象上操作的测试运行得极其迅速的好办法，因为它们的运行将完全在内存中进行。当你这样做时，SQLite 会为你物化出一个内存中的存储，这非常高效，但因为它在内存里，如果你有大量数据，就会导致你的测试套件内存大幅增长。

不过，你至少应该保有一个测试，是实实在在地把你的存储文件落到磁盘上去跑的。这是因为，如果你的测试套件没法打开你的存储，那么你的客户很可能也打不开。

如果你的持久化容器是在 application delegate 里，你可以写一个测试基类，把那个容器取出来，直接写到那个存储里。但我必须提醒你，这么做时要非常小心，因为那意味着你在往 App 正在使用的那个存储文件上写。所以如果你在个人设备上跑测试，下次打开你的 App 时就会看到单元测试造成的效果。如果我告诉你，我可以在仅仅七行代码里插入 10 万条记录呢？我在这里是取了点巧。我本来想把这部分留给读者当练习，但这种搭建脚手架的类型，是帮你构建一个来评估你数据相关不变量的测试套件的好方法。

通过提前准备好这些方法，随着你的数据变化或你意识到你的 App 有了新的用例，你就可以基于它们迭代出新的边缘情况、为你的对象图构造新的结构，或是评估某些功能在幕后的表现，比如性能。这就是我用来给刚才那个 R-tree 查询构建性能测试的单元测试脚手架。只需要很少几行代码，我们就能对 fetch 的性能有很高的信心。

而当你试图评估 Core Data 的不同功能和特性之间的权衡时，这类测试也提供了非常丰富的信息。这三行代码会为我们的测试生成一个新的托管对象上下文和容器。这件事之所以很重要，主要是因为测试中的 setUp 和 tearDown 逻辑有时候会影响它们的性能。所以，你需要多加小心地去分析，你实际在测的到底是 tearDown 的性能，还是 setUp 的性能，又或者是你正在评估的那些查询在真实运行时（runtime）的性能。
