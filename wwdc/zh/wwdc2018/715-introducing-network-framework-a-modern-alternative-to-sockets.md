早上好。

我叫 Josh Graessley，今天早上我非常兴奋能在这里向大家介绍 Network.framework。

Network.framework 是一种现代的 Sockets 替代方案。今天，我们将讨论现代化的传输 API。这会帮助你理解 Network.framework 是什么、它如何融入系统，以及它是否适合你的 App 使用。

我们会带你创建第一个连接，从而向你介绍这个 API。

我们会讨论如何使用这个 API 来真正优化数据传输，并且其性能远远超过你用 Sockets 所能达到的任何水平。

我们还会讨论这个 API 如何帮助你处理一些复杂的移动性挑战，最后我们会介绍如何参与和开始采用。

首先，我想花一点时间谈谈现代化的传输 API。当我说传输 API 时，我指的是任何允许你在网络上的两个端点之间发送和接收任意数据的 API，这是一个相当宽泛的定义，有很多 API 可能属于这个类别。

其中最普遍的也许是 Sockets。Sockets 已经伴随我们超过 30 年了，我认为毫不夸张地说，Sockets 改变了世界，但世界也在不断变化。因此，使用 Sockets 为当今的互联网编写 App 确实非常困难。用好 Sockets 主要在三个方面很有挑战。

第一个是连接建立。用 Sockets 建立连接困难的原因有很多。首先，Sockets 连接到地址，所以大多数情况下你有一个主机名，因此你需要将该主机名解析为地址。当你这样做时，你通常最终会得到不止一个地址。你会得到一些 IPv4 地址，一些 IPv6 地址，现在你面临的挑战是，应该尝试连接哪个地址，以什么顺序？在尝试下一个之前等多久？你可能需要花费数年时间才能完善这一点。我知道，因为我们就这样做过。一旦你解决了双栈主机问题，你就会遇到一大堆其他问题。有些网络使用所谓的代理自动配置（Proxy Automatic Configuration）或 PAC。

在这些网络上，你会得到一个 JavaScript，你必须将一个 URL 传入该 JavaScript，JavaScript 运行后会输出一个答案，告诉你要么可以直接访问，要么必须使用这里的 SOCKS 代理或那边的 HTTP 连接代理。现在你的 App 必须支持 SOCKS 代理和 HTTP 连接代理，这真的很难做好。

最困难的是，你可能没有这样的网络进行测试，所以你可能会收到客户的 bug 报告，抱怨在他们的环境中无法正常工作。你可能想添加代码来修复问题，但一旦你加进去了，你实际上没有好的方法来测试它。你最终必须构建整个环境来重现他们遇到的相同环境。这确实是一个挑战。

所以，用 Sockets 连接真的很难。

使用 Sockets 时的第二个挑战是数据传输。

有很多原因导致用 Sockets 传输数据非常困难。主要问题在于读写模型本身。如果你使用阻塞式 Sockets，它很简单，但会占用一个线程，而在等待读写数据时占用一个线程并不是一个好主意。

你可以切换到非阻塞模式，但这样你会遇到一大堆其他挑战。

当你使用非阻塞模式时，你可能告诉内核我想要 100 个字节，内核会回来说，我只给了你 10 个字节，你过会儿再来吧。现在你必须构建一个状态机来跟踪你读取了多少字节以及你想要读取多少字节。这可能需要大量工作，并且要让它良好运行是一个真正的挑战。最重要的是，你真的不应该直接读写 Sockets，因为你应该使用像传输层安全（transport layer security，TLS）之类的东西。

Sockets 不支持 TLS，所以你可能正在使用某个其他库来处理 TLS，并代表你读写 Sockets，或者你正在编写该库与 Sockets 之间的胶水代码，并且你必须弄清楚如何将所有这一切与你之前加入的那些复杂的连接逻辑协调起来。这里面有很多确实非常困难的地方。

最后，由于各种原因，Sockets 的移动性可能颇具挑战。我认为这很大程度上归结于这样一个事实：当 Sockets 出现时，许多设备需要不止一个人才能移动，它们用一根线连接，拥有静态 IP 地址，一切都稳定而简单。

而今天，我们的口袋里装着这些功能极其强大的设备，它们拥有多个可能同时开启的无线通信模块，其中一些设备会在网络间移动，你的 App 必须妥善处理所有这些过渡，才能为客户提供无缝体验。

Sockets 在这方面帮不了你什么。你可以使用路由套接字（routing sockets），但这非常非常困难。我们认为传输 API 应该做得更好。

幸运的是，作为应用开发者，在我们的平台上，你有一个很棒的 API —— URLSession。

URLSession 为你处理了所有这些问题。

它主要专注于 HTTP，但也拥有流任务（Stream Task），可以让你直接访问 TCP 和 TLS 连接。

现在你可能会看着这个，如果你没有通过查看 WWDC App 中的描述而提前知道答案，你可能会认为 URLSession 是建立在你自己会使用的基本原语之上的。

但事实并非如此。URLSession 是构建在我们称之为 Network.framework 的东西之上的。

URLSession 真正专注于所有的 HTTP 细节，并将大量传输功能卸载到 Network.framework 上。

Network.framework 是我们已经开发了数年的东西，在支持 URLSession 的过程中，我们学到了很多，并将这些经验带到了 IETF。我们的许多工程师定期参与 IETF，并与其他公司的工程师会面，他们在传输服务工作小组中讨论了我们学到的大部分内容。在这些讨论中，我们获得了一些很好的反馈，我们将其带回并据此改进了 Network.framework。

我们非常激动地宣布，今年你的 App 可以直接利用这个相同的库了。我们知道人们喜欢 Sockets 的原因之一是它可以让你对几乎所有事情进行非常精细的控制，他们很不想放弃这一点。因此，在开发 Network.framework 时，我们想确保它在默认情况下能像 Sockets 做不到的那样做正确的事情，同时又提供 Sockets 拥有的所有控制旋钮。它有点像有一个渐变过程，你转动越多的旋钮，它就变得越复杂。它为你提供了所需的所有能力，但除非你确实需要其中一些，否则你不必为复杂性付出代价。

Network.framework 拥有极其智能的连接建立。

它处理双栈情况。它处理纯 IPv6 网络。它处理 PAC。它处理代理。它会帮助你在原本非常难以处理的网络上进行连接。

它拥有一个经过极致优化的数据传输路径，让你达到远超 Sockets 所能实现的性能，Tommy 稍后会介绍这部分。

它内置了安全支持。它默认支持 TLS 和 DTLS。使用起来非常简单。它提供了出色的移动性支持。它能提供与你的 App 正在建立的连接相关的网络变化通知。它在 iOS、macOS 和 tvOS 上作为带有自动引用计数（automatic reference counting）的 C API 提供，因此易于从 Objective-C 使用，并且拥有出色的 Swift API。下面，我想把时间交给 Tommy Pauly，让他带你创建第一个连接。谢谢。大家好。我叫 Tommy Pauly，我是 Apple 网络团队的成员。

我相信你们中的很多人都非常兴奋地想看看如何开始在你们的 App 中采用 Network.framework。

最好的起点就是直接开始，创建你的第一个连接。你将开始从你的本地设备连接到你的服务器，或者连接到本地网络上的其他对等设备。

但你可能会想，什么样的连接适合使用 Network.framework？有哪些使用场景？那么，让我们先探讨一些目前可能在使用 Sockets、并且未来会从采用 Network.framework 中受益匪浅的 App 场景。我想强调的第一个是游戏 App。游戏 App 通常使用 UDP 在设备之间发送关于游戏状态的实时数据。

它们非常关心优化延迟，并确保没有卡顿或丢包。

如果你有这样的 App，你会喜欢 Network.framework 如何让你真正优化 UDP 的发送和接收，使其比以前更快、延迟更低。另一种能从 Network.framework 中获得很多好处的 App 是直播 App。直播 App 通常会在其 App 中结合使用 UDP 和 TCP，但关键在于它是实时生成数据的。如果你有新的视频帧或音频帧，你需要确保这些数据能够得到良好的调度，并且不会在设备或网络上产生大量缓冲。

Network.framework 中用于读写的异步模型，对于确保减少缓冲来说将是完美的。我要强调的最后一个案例是邮件和消息类 App。

这些 App 会使用更传统的协议，比如基于 TCP 的 TLS。

然而，对于这类 App 来说，优雅地处理网络切换是至关重要的。

通常，如果你有一个消息 App，你的用户会在走出大楼时使用你的 App，给朋友发短信说他们正在路上。你需要确保你能处理好从楼内 WiFi 网络到他们将连接上的蜂窝网络之间的切换，并且确保消息不会花费很长时间才能到达他们的朋友那里。这只是可能使用这种底层网络的三类 App 的例子。还有许多其他类型的 App 可以利用这一点，所以如果你有一个类似这样的 App，或者有当前使用 Sockets 的其他用例，我邀请你跟随我们一起看看你的 App 如何受益。首先，我想重点关注最后一种情况，即邮件和消息类 App 的最简单情况，看看它们是如何建立连接的。当你想要建立到服务器的连接时，假设这是一个邮件连接，使用带 TLS 安全的 iMap，你从主机名 mail.example.com 开始。

你有一个想要连接到的端口，端口 993，并且你希望同时使用 TLS 和 TCP。那么这在传统的 Sockets 中看起来是怎样的？大概像这样开始。你会获取你的主机名。你会调用某个 DNS API 来解析该主机名。假设这是 getaddrinfo。你会得到一个或多个地址。你必须决定首先连接到哪一个。

你会使用适当的地址族调用 socket。

你会设置一系列 socket 选项。假设你想像 Josh 之前提到的那样，将你的 socket 设置为非阻塞。

然后你调用 connect 启动 TCP 连接，然后等待一个可写事件。

而这还是在你对 TLS 做任何事情之前，这本身又是一大堆其他问题。那么在 Network.framework 中这是什么样子呢？我们希望它对你来说看起来很熟悉，但要简单一些。所以你要做的第一件事是创建一个连接对象。一个连接对象基于两个东西。你有一个端点（endpoint），它定义了你想到达的目的地；这可以是地址，比如你之前有的 IP 地址，但通常，就像这个例子中，我们有一个主机名和一个端口，所以我们的端点可以就是那个主机名和端口。它也可以是我想要连接到的 Bonjour 服务。

然后我还有其他参数（parameters）。参数定义了我想要使用的协议，TLS、DTLS、UDP、TCP。它还定义了我想要的协议选项以及我想要用来进行连接的路径。我是只想通过任何网络连接，还是只想使用 WiFi？一旦你配置好了你的连接，你只需调用 start 来开始整个过程，然后等待连接进入就绪（ready）状态。这就是你为服务器建立一个完整的 TLS 连接所需要做的一切。

我想你会喜欢它在 Swift 中的样子。以下是具体做法。首先，你导入 network 模块。

然后，你创建一个 NWConnection 对象。无论是在 Swift 还是 C 中，NWConnection 都是用于读写数据的基本对象。

在这个例子中，我们有一个便捷方法，可以用主机和端口来初始化你的端点，所以我给它我的主机名 mail.example.com 和端口。这里，它是一个众所周知的端口，即 imaps。所以我可以很容易地在 Swift 中输入它，但我也可以在那里放任何其他数字常量。然后，为了定义我想要使用的协议，我传递参数，由于这是一个客户端连接，我只想要默认的 TLS 和 TCP 参数。它可以简单到只写 .TLS，现在你就有了一个功能完整的 TLS 连接。

接下来我要做的事情是设置一个状态更新处理程序（state update handler），以处理我的连接可能经历的所有状态转换。

你希望处理的第一个也是最重要的状态是就绪状态。就绪意味着你的 App 已经准备好在此连接上读写数据，连接已经完全建立，如果你使用的是 TCP 和 TLS，这意味着 TLS 握手已经完成。

我们还会让你知道等待（waiting）状态。去年在 URLSession 中，我们引入了等待连接（waits for connectivity）功能，NWConnection 的等待状态完全相同。并且这是默认开启的。所以当你创建连接并启动它时，如果没有可用的网络，我们不会失败，只会告诉你我们正在等待网络可用。我们会给你一个有用的原因代码，但你自己不需要做更多事情来监视网络切换。移动性是本 API 的一个必不可少的关键部分。如果有致命错误，我们也会让你知道。假设我们必须从服务器重置或 TLS 失败，我们会将其作为一个失败事件提供给你。一旦你设置好了这些，你只需调用 start 并提供你希望接收回调的 dispatch queue。

我想深入探讨一下当你调用 start 时会发生什么。到底会发生什么？这是一个小状态机，NWConnection 的内部机制。当我们从设置（setup）状态开始并调用 start 时，我们会进入准备（preparing）状态。

所以准备状态所做的远不止是在 TCP socket 上调用 connect。

对于 TCP socket，那只是向你要连接的服务器发送一个 SYN 数据包。

但是，当你对 NWConnection 调用 start 时，它实际上处理了 Josh 之前提到的所有事情。

它会评估你当前所在的网络，并尝试为你建立尽可能快的连接。我想进一步探讨一下这一点。这就是我们所说的智能连接建立（Smart Connection Establishment）。当你调用 start 时，我们做的第一件事是获取你的端点，然后评估当前所有对我可用的网络。

在这种情况下，我们有 WiFi 和蜂窝网络。

通常我们更喜欢 WiFi 网络，因为它对用户的成本较低。

所以我们会先看看那个网络。

然后，我们检查这个网络上是否有特殊配置。是否有 VPN？是否有代理？我们会为你评估这些。

在这个例子中，假设有一个配置了自动配置文件的代理，如果代理不适用于你的连接，它也会允许你直接连接。我们会评估这两种选项。

我们会检查是否需要使用代理，如果需要，就连接它，在那里建立一个 TCP 连接。

但如果不需要，我们会代表你直接进行 DNS 解析，获取所有 DNS IP 地址答案，然后一个接一个地连接它们，或者让它们并行进行。我们会对它们进行竞速（racing），以尽可能快地为你获取连接。

然后，如果 WiFi 出了问题，比如因为你正走出大楼导致 WiFi 无线电信号质量变得非常差，我们实际上可以利用一个名为 WiFi 辅助（WiFi Assist）的功能，无缝地回退到蜂窝网络，在那里进行 DNS 解析，并一个接一个地尝试连接。这样，你的连接建立就非常有弹性，能为你处理 VPN、处理代理，并提供最好的连接。当然，你可能不想尝试所有这些选项，你可能想限制连接建立的行为，所以我们有许多不同的旋钮和控制方式让你做到这一点，今天我想强调其中的三个。

第一个是，你可能不想使用昂贵的网络，比如蜂窝网络，因为这个连接只在 WiFi 上适用。

因此，在连接的参数中，有一些选项可以用来控制你使用的接口。如果你不想使用蜂窝网络，只需将蜂窝网络添加到禁止的接口类型列表中。实际上更好的做法是，也禁止所有昂贵的网络，因为这也将阻止在 Mac 上使用个人热点。另一种限制连接建立的方式是，专门选择你想使用的 IP 地址族。假设你真的很喜欢 IPv6，因为它更快并且是未来的方向。你完全不想在你的连接中使用 IPv4。你可以通过进入你的参数，深入到 IP 特定选项来实现这一点，这里有你会从当前的 socket 选项中熟悉的选项，你也可以专门定义你想使用的 IP 版本。这将影响你的连接以及你的 DNS 解析。最后，你在特定连接上可能不想使用代理。也许你的连接不适合通过 SOCKS 代理。在这种情况下，你也可以直接禁止使用代理。这就是在准备状态中发生的事情。

我之前提到过，事情可能会出错。当你尝试建立连接时，可能没有网络，我们在进入准备状态后，如果发现没有好的选项、DNS 失败、没有网络（比如你可能处于飞行模式），我们会进入等待状态，并告诉你原因。

并且，每次网络发生变化，系统认为你的连接现在有可能成功建立时，我们都会再次回到准备状态，我们会为你处理所有这些，并在每次重新尝试时通知你。

最终，希望你的连接确实能够建立。此时，我们将进入就绪状态。正如我之前提到的，就绪状态意味着你的连接已经完全建立。这意味着你协议栈中直到 TLS 的所有协议都已就绪，例如。

此时，你可以进行读写操作，这也是我们为你提供有关你正在经历的网络切换回调的地方。所以，如果你的连接已经建立，然后你切换了网络，我们会向你提供相关更新，这样你就可以优雅地处理移动性，我们将在后面的演讲中讨论这一点。

如果连接出现错误，无论是在连接建立期间还是在你已经连接之后，我们都会提供一个带有错误信息的失败状态。然后，当你完全完成了连接，比如你已经关闭了它，或者你收到了另一端的关闭请求，并且你想使连接失效，你可以调用 cancel，我们会进入已取消（cancelled）状态。这保证是我们将传递给你的对象的最后一个事件，因此你可以清理所有与其关联的内存并继续。

它叫做 contentProcessed。每当网络栈消耗掉你的数据时，我们就会调用它。这并不意味着数据已经被发送出去或被另一端确认。它完全等同于阻塞式 socket 调用返回给你的时刻，或者非阻塞 socket 调用能够消耗你发送的所有字节的时刻。在这个完成处理程序中，有两件事你可以检查。

首先，你可以检查是否有错误。如果有错误，意味着我们在尝试发送你的数据时出了问题，通常表示整体连接失败。

然后，如果没有错误，这正是去查看你的 App 是否还有更多数据要生成的最佳时机。因此，如果你正在生成实时数据帧，就去从视频流中获取另一帧，因为现在是你实际上可以排队等待下一个数据包的时候。这允许你调度好所有数据的发送。

因此，正如你在这里看到的，我们基本上形成了一个循环，使用这个异步发送回调来持续地从我们的连接中排出数据，并非常优雅地处理它。

第一个是我们已经在 WWDC 上多次讨论过的，即 ECN（显式拥塞通知，Explicit Congestion Notification）。

它提供了一种平滑连接的方法，通过让网络在出现拥塞时通知终端主机，这样我们就可以很好地调度数据的发送。

很棒的一点是，ECN 在你的所有 TCP 连接上默认是启用的。你不需要做任何事情。

但在过去，将 ECN 用于基于 UDP 的协议是非常困难的。

所以我想在这里向你展示如何做到这一点。你要做的第一件事是创建一个 ipMetadata 对象。ECN 由 IP 数据包中的标志位控制，所以你有这个 ipMetadata 对象，它允许你为每个数据包设置各种标志，你可以将其包装到一个上下文（context）对象中，该对象描述了你要与单次发送关联的各种协议的所有选项，以及该特定消息的相对优先级。

然后，除了你的内容之外，你还可以将上下文作为一个额外的参数传入 send 调用。

所以现在当你发送时，任何由此内容生成的报文都将拥有你想要标记的所有标志。这非常简单。

你也可以在连接上接收时获得相同的标志。你将拥有与你的接收关联的相同上下文对象，并且你将能够读出你想要获取的特定底层标志。类似地，我们有服务类别（service class）。

这是一个在 URLSession 中也可用的属性，它定义了你的流量的相对优先级，这会影响流量在本地接口上排队的方式（当我们发送时），以及在 Cisco Fastlane 网络上流量的工作方式。因此，你可以通过在参数对象中使用 serviceClass 参数，将你的服务类别作为整个连接的属性进行标记。在这个例子中，我们展示了如何使用后台服务类别，这是标记你的连接相对较低优先级的一个好方法。我们不希望它妨碍用户交互数据。所以我们强烈建议，如果你有后台传输，请将它们标记为后台服务类别。

但对于那些 UDP 连接，你也可以基于每个数据包来标记服务类别。

假设你有一个连接，其中语音和信令数据在同一个 UDP 流上。

在这种情况下，你可以创建我们之前介绍过的同一个 IP 元数据对象，现在标记你的服务类别而不是 ECN 标志，将其附加到一个上下文，并发送出去。这样你就基于每个数据包标记了优先级。另一种优化连接的方法是减少建立连接所需的往返次数（round trips）。

这里我想强调两种方法。

一种是在你的连接上启用快速打开（Fast Open）。TCP 快速打开允许你在 TCP 发送的第一个数据包（SYN）中发送初始数据，这样你就不必等待整个握手完成才开始发送你的应用数据。为了做到这一点，你需要与连接签订一个来自 App 的契约，说明你将提供这个要发送的初始数据。

要启用此功能，你在参数上标记 allowFastOpen。然后你创建你的连接，之后，在你调用 start 之前，你实际上可以调用 send 并发送你的初始数据。现在我想在这里指出，这里的完成处理程序被一个标记替换，表明这个数据是幂等的（idempotent）。幂等意味着该数据可以安全地被重放，因为初始数据可能会在网络上被重新发送，所以你不希望它在被重发时产生副作用。

然后，你只需调用 start，当我们进行连接建立时，我们之前提到的所有尝试，我们将尽可能使用该初始数据通过 TCP Fast Open 发送。我想指出另一种使用 TCP Fast Open 的方法，它不需要你的 App 发送自己的数据。

如果你在 TCP 之上使用 TLS，来自 TLS 的第一条消息（客户端 hello）实际上可以用作 TCP Fast Open 的初始数据。

如果你只想启用这个功能而不提供你自己的 Fast Open 数据，只需进入 TCP 特定选项并标记你要在那里启用 Fast Open，它会自动获取来自 TLS 的第一条消息，在连接建立期间将其发送出去。

还有另一件你可以做的事情来优化你的连接建立并节省一个往返，这就是 Stuart 在上一场会议中提到的，我们称之为乐观 DNS（Optimistic DNS）。

这允许你使用之前已经过期但生存时间（TTL）很短的 DNS 应答，并在我们并行进行新的 DNS 查询时尝试连接到它们。

因此，如果你之前接收到的已经过期的地址仍然有效，并且你将 expiredDNSBehavior 标记为 allow。当你调用 start 时，我们会首先尝试连接到这些地址，而不必等待新的 DNS 查询完成。这可以从你的连接建立中削减大量时间，但因为我们在尝试多个不同的连接选项，如果第一个地址不起作用（例如你的服务器确实更换了地址），我们会优雅地等待新的 DNS 查询返回，并也尝试那些地址。

所以这是一个非常简单的方法，如果它适用于你的服务器配置，你可以获得更快的连接建立。

关于性能，我想讨论的下一个方面是你实际上不需要在你的 App 中做任何事情就能获得的。这是你使用 URLSession 或 Network.framework 连接时完全免费获得的，那就是用户空间网络（User-Space Networking）。这是我们去年在 WWDC 上介绍的东西，它在 iOS 和 tvOS 上已启用。这里我们完全绕过了 socket 层，并将传输协议栈移入了你的 App。为了让你了解这是在做什么，我想从通常的协议栈遗留模型开始。假设你正在从网络接收一个数据包。它来自 WiFi 接口。该数据包会进入驱动程序，会被送入内核中的 TCP 接收缓冲区，然后当你的 App 在 socket 上读取时，这会产生一次上下文切换并将数据从内核复制到你的 App 中，然后，通常如果你正在使用 TLS，它将不得不进行另一次转换来解密这些数据，然后你才能实际将其发送到 App。那么当我们进行用户空间网络时，这看起来是怎样的呢？正如你所见，主要的变化是我们将传输协议栈（TCP 和 UDP）移到了你的 App 中。这给我们带来了什么？现在，当一个数据包从网络进入，像以前一样进入驱动程序，但我们将其移入一个内存映射区域，你的 App 可以自动从中取出数据包，而无需进行拷贝、无需额外的上下文切换，并自动开始处理这些数据包。这样，我们唯一进行的转换就是我们必须为 TLS 做的解密。这确实可以减少发送和接收数据包所需的 CPU 时间，特别是对于像 UDP 这样的协议，你的 App 会直接来回发送大量数据包。为了展示这是如何工作的以及它可能带来的影响，我想向你展示一个视频，该视频使用 Eric 之前展示的同一个 App，来演示带有用户空间网络的 UDP 性能。在这个例子中，我们将同时运行两个视频。左边的设备正在从一个使用 Sockets 编写的 App 接收视频流。

右边的设备将从一台 App 使用 Network.framework 编写的设备上接收完全相同的视频流，这样可以充分利用用户空间网络协议栈。在这个场景中，我们正在传输视频。它只是原始帧。没有压缩。画质也不是很好，但有很多数据包在来回传输。

我们特别选择在这个演示中，当遇到争用或无法足够快地发送数据包时，不去降低质量或丢弃任何东西，而是如果需要的话，就减慢速度。这可能不是你的 App 在现实生活中会做的事情，但它精确地突出了这两个协议栈之间的性能差异。现在让我们看看。

完全相同的视频数据，完全相同的帧，尽可能快地通过网络发送出去，我们看到右边的那个明显超过了左边。

事实上，如果你看差异，仅在接收端我们就观察到了 30% 的开销减少。

这归功于当你比较 Sockets 和用户空间网络时，我们在发送和接收 UDP 数据包所需的 CPU 百分比中看到的巨大差异。当然，这只是一个例子。这不会是你每个 App 的情况，因为你会以不同的方式进行压缩。你已经会尝试让你的连接更高效。

但是，如果你有一个生成实时数据的 App，特别是如果你使用 UDP 发送和接收大量数据包，我邀请你尝试在你的 App 中使用 Network.framework，并通过 Instruments 运行它。衡量使用 Network.framework 与 Sockets 时 CPU 使用率的差异，我相信你会对看到的结果感到非常满意。

所以我们今天要谈的最后一个话题是如何解决网络移动性带来的问题，这是我们试图用 Network.framework 解决的关键领域。第一步就是确保我们能够优雅地启动连接。

我们之前已经提到过这一点，但我想稍微回顾一下。

等待状态是在你的连接第一次启动时处理网络切换的关键。它会表明，当你正在进行 DNS 或 TCP 时，出现了连接缺失或连接发生变化。我们强烈建议，请避免在建立连接之前使用像可达性（reachability）这样的 API 来检查网络状态。

这会导致竞态条件，并且可能无法提供连接中实际发生情况的准确画面。如果你需要确保你的连接不通过蜂窝网络建立，不要事先检查设备当前是否在蜂窝网络上，因为这可能会改变。只需使用 NWParameters 限制你想使用的接口类型。

因此，一旦你启动了连接并处于就绪状态，我们会给你一系列事件，让你知道网络何时发生了变化。

第一个叫做连接可行性（connection viability）。

可行性意味着你的连接能够通过其接口发送和接收数据，并且拥有有效的路由。为了演示这一点，假设你的连接是在设备连接到 WiFi 网络时启动的。

然后，你的用户走进电梯，他们不再有信号。此时，我们会给你一个事件，让你知道你的连接不再可行。

那么此时你该怎么办？两件事。我们建议，如果你的 App 适用，你可以让用户知道他们当前没有连接。如果他们正在尝试发送和接收数据，现在无法正常工作。

但是，不一定非要拆除你的连接。

此时，你无论如何也没有更好的接口可以使用，而且那个最初的 WiFi 接口可能会回来。

通常，如果你走出电梯回到同一个 WiFi 网络上，你的连接可以从中断的地方恢复。我们给你的另一个事件是更好的路径（better path）通知。

我们采用同样的场景，你通过 WiFi 网络连接。

假设你走出大楼，现在你没有 WiFi 了，但你确实有蜂窝网络可用。此时，我们会告诉你两件事。

首先，和之前一样，你的连接不可行，但我们还会告诉你，现在有一条更好的路径可用。如果你再次连接，你将能够使用蜂窝网络。这里的建议是，如果对你的连接适用，尝试迁移到一个新的连接，如果你能恢复之前正在进行的工作的话。但只有在新连接完全就绪后才关闭原始连接。同样，WiFi 网络可能会回来，或者通过蜂窝网络的连接可能会失败。我想强调的最后一个场景是，你最初通过蜂窝网络连接，然后用户走进大楼，现在他们有了 WiFi 接入。

在这种情况下，你的原始连接完全没有问题。你的连接仍然可行，但你现在也有一条更好的路径可用。在这种情况下，同样地，如果你能迁移你的连接，这可能是尝试建立新连接并将数据移过去的好时机。这将节省用户的流量费用。但是，继续使用原始连接，直到新连接完全建立好。

为了显示这在代码中是什么样子，我们有可以在连接中设置的 viabilityUpdateHandler，我们会返回一个布尔值，让你知道你的连接是否可行，还有一个 betterPathUpdateHandler，让你知道何时有更好的路径可用或不再可用。

现在，处理网络移动性的更好解决方案是我们前几年已经讨论过的，那就是多路径连接（Multipath TCP）。

因此，如果你能在服务器上启用 Multipath TCP，并且你可以通过参数中的 multipathServiceType 在客户端启用它，那么你的连接将在网络出现和消失时自动在网络之间迁移。这是一种很棒的无缝体验，不需要在你的 App 中做任何工作来处理。

这也是在 URLSession 中可用的相同服务类型。我想在这里强调几点，它们特定于 Network.framework。

如果你限制了你允许在 NWParameters 中使用的接口类型，这将适用于 MPTCP，因此你仍然可以选择不在多路径连接中使用蜂窝网络，而是当不同的 WiFi 网络变得可用时，我们会在它们之间无缝迁移。

另外，我之前提到的连接可行性处理程序对于 Multipath TCP 略有不同，因为每当我们更换网络时，我们会自动为你迁移，只有当没有任何网络可用时，你的连接才不可行。因此，结合等待连接、可行性、更好的路径、MPTCP，我们真心希望你的 App 中使用像 SCNetworkReachability 这样的工具手动检查网络变化的所有用例都已经被取代。然而，我们确实认识到，在某些场景下，你仍然想知道当前可用的网络是什么，以及它何时发生变化。

为此，Network.framework 提供了一个名为 NWPathMonitor 的新 API。

Path Monitor 不再监视可达性并尝试预测给定主机的可达性，它只是让你知道设备上接口的当前状态以及它们何时发生变化。

它允许你遍历所有可以连接的接口，以防你想通过每个接口建立连接，并且每当这些网络发生变化时，它都会通知你。

如果你想要更新你的 UI 以让用户知道他们是否已连接，这会非常有用。正如 Stuart 在上一场会议中提到的，可能存在一些场景，用户需要填写一个冗长的表单，但他们并不一定想要在填写过程中才意识到根本没有网络连接。

因此，在任何这些仅仅拥有一个等待连接还不够的场景中，请使用 Network Path Monitor。综合所有这些，我们真的很希望看到人们从使用 reachability 转向，并且比以往任何时候都更优雅地处理网络切换。说到这里，我想请 Josh 回到台上，告诉你如何参与并开始采用 Network.framework。谢谢 Tommy。

所以我为你带来了一个很棒的新 API，我们认为你会喜欢它。

我们想谈谈你今天就可以开始用它做什么，但首先我想谈谈我们希望你不要再做的几件事，这样我们才能真正利用像用户空间网络这样的新技术。

如果你在 macOS 上，并且你有一个网络内核扩展（Network Kernel Extension），而且你在该扩展中做的事情无法通过其他方式完成，请立即联系我们。我们需要为你提供一个更好的替代方案，因为网络内核扩展与用户空间网络不兼容。

我们想提前告知你，对于 URLSession，FTP 和文件 URL 将不再支持用于代理自动配置（Proxy Automatic Configuration）。今后，唯一支持的 URL scheme 将是 HTTP 和 HTTPS。

我们希望你不要再使用 CoreFoundation 层的一些 API。它们最终将被标记为已废弃（deprecated）。它们目前还没有被标记为已废弃。这些 API 是 CFStreamCreatePairWith 以及与 Sockets 相关的任何东西，还有 CFSocket。

这些 API 无法利用我们在新的 Network.framework 中提供的许多连接建立功能，也无法利用新的用户空间网络。所以我们真的希望你从这些 API 迁移出来，以便利用通过 Network.framework 和 URLSession 获得的极其强大的连接改进和更高的性能。

还有一些 Foundation API 我们也希望你迁移。如果你正在使用任何 NSStream、NSNetService 或 NSSocket 的 API，请迁移到 Network.framework 或 URLSession。

最后，如果你正在使用 SCNetworkReachability，我们认为等待连接（Wait for Connectivity）模型是一个更好的模型，所以我们真心希望你迁移到它。对于那些等待连接不是正确答案的少数情况，NWPathMonitor 是未来更好的解决方案。

既然我们已经讨论了一些我们希望你不要再做的事情，我想把重点放在我们真正希望看到你做的事情上。

未来，我们平台上首选的网络 API 是 URLSession 和 Network.framework。URLSession 主要专注于 HTTP，但 Stream Task 提供了对 TCP 和 TLS 连接相当简单的访问。

如果你需要更高级的功能，Network.framework 为 TCP、TLS、UDP、DTLS 提供了出色的支持。它处理入站连接和出站连接的监听，并且我们有 Path Monitor 来处理一些移动性相关的事情。接下来的步骤，我们真的希望看到你采用它们，采用 Network.framework 和 URLSession。你的客户会欣赏你的连接变得多好、多可靠，并且他们会欣赏由于性能更好而带来的更长电池寿命。

在你开发这些功能时，专注于如何处理发送和接收，以真正优化性能。并花大量时间处理可行性支持和更好的路径变化支持。这对于提供无缝的网络体验至关重要。
