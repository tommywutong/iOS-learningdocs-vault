IPv6 的使用持续增长。

为什么这很重要？因为 IPv6 被证明比 IPv4 有更好的性能。如果你关心性能，就要确保不仅你的 App，而且你的 App 通信的服务，都支持原生 IPv6。

世界上有些地方在这方面的表现比其他地方更好。

在美国，我们现在有 87% 的移动运营商提供 IPv6。印度等地也表现相当不错。让我们多关注一点印度。

这是 Apple 网络团队今年早些时候收集的关于印度蜂窝网络上 TCP 连接建立时间和持续往返延迟的数据。蓝色线条是 IPv6。例如，如果我们看第 75 百分位，可以说 75% 的 v6 TCP 连接建立时间少于 150 毫秒。IPv4 的可比数字更差，超过 325，慢了不止一倍。所以如果你想要为用户打造快速、响应迅速的应用，如果你还没上 IPv6，就赶紧上。

另一种通过减少丢包和重传来改善性能的技术是 Explicit Congestion Notification。我们已经在 macOS 和 iOS 中默认启用这项功能多年，所以你的应用无需做任何事情就能利用它。

请确保你的服务支持 ECN。在我们对 Alexa 前一百万网站进行的调查中，上个月我们发现 Alexa 前一百万服务中现在已有 77% 支持 ECN，相比几年前是很大改进。另一项帮助改善连接性能和弹性的技术是 Multipath TCP。用户常常在办公室通过 Wi-Fi 建立连接，然后走到室外丢失 Wi-Fi 信号。对于传统 TCP，连接就断了，你必须重新连接、重新开始。Multipath TCP 的数据包路由决策是按数据包进行的，而不是按连接，所以它能将连接实时切换到不同的接口。

我们去年讲过如何在你的应用中启用它。当然，也要与你的服务器运营方确认，确保服务器支持 Multipath。

我们最近调查了 Apple 在全球合作的移动运营商，目前他们 78% 的网络可与 Multipath TCP 协同工作。只有 22% 的运营商仍在阻断 Multipath 连接。TCP Fast Open 是一种可以避免 TCP 连接建立正常往返延迟的技术。TCP Fast Open 让你把初始数据放入 TCP 连接建立数据包中。

你可以从三年前的视频查看更多细节。并请确认你的服务器运营方确保服务器支持 TCP Fast Open。现在进入一些新消息。有一种很多你可能听说过的技术，叫 Quick。

Quick 是一种新的传输协议，是 30 年来第一个认真考虑用来替代 TCP 的候选者。它最初是 Google 几位工程师的实验。实验成功了。现在它已被 IETF 采纳为工作组项目进行标准化。

Apple 的工程师正在参与其中。事实上，我们现在就有工程师在瑞典举行的 Quick 会议上。

这还不到投入生产的时候。标准尚未完成，但 Apple 正在推进。一旦准备就绪，你可以期待 Apple API 支持它。继续性能主题，我们观察到了一种非常常见的行为。大量网站和互联网服务对其 DNS 记录使用相当短的生命周期。他们这样做是因为如果一个数据中心宕机，他们希望能够更新 DNS 并非常迅速地把流量导向另一个数据中心。

这种方法的问题在于，你为几乎从不发生的事情付出了性能代价。数据中心很少宕机。

这意味着每次 DNS 地址记录过期，你的客户端都得再花一个往返延迟等待 DNS 服务器的响应，而那和它上次已知的答案相同。所以思考这个问题，我们意识到可以做一项优化。如果你传入标志 opting into this new behavior，那么当你进行 DNS 查询时，如果缓存中有过期的陈旧答案，我们会立即给你那个答案，同时并行地进行我们原本就会做的正常 DNS 查询。

如果答案回来相同，正如我们预测几乎总会如此，一切正常，你只是节省了一个往返时间并更快地开始了连接。如果答案回来是不同的地址，我们会再给你的客户端一个异步通知，告知有新地址可用，它也应该尝试。要利用这一点，你必须结合 Happy Eyeballs 算法使用。这意味着你并行地竞速多个连接。

你尝试 IPv4、IPv6、多个地址、多个接口。如果这听起来工作很多且很难做对，你完全正确。确实工作很多。休息后留下来，我们会告诉你一些新的 API，让你无需自己完成所有艰苦工作就能利用这一点。

现在进入一些指导。我们看到一种常见模式，许多开发者把 SCNetworkReachability 用作预检。

他们想预测未来。他们想知道下一次网络操作是否会成功或失败。不幸的是，预测未来总是很难。你现在可能有连接，但两秒后用户走出了大楼，你就丢失了 Wi-Fi 信号。所以无法保证未来的操作是否会成功。

我们看到这种模式：他们检查。预检说可以。他们尝试。失败了。他们回去。再次检查。这也是一大堆工作，很多很多难以做对的事情，包括带代理的网络。

更好的方式是使用 waitsForConnectivity 选项直接建立连接。你可以通过观看去年的视频了解更多。这意味着如果你想要一个连接，你告诉系统我想要一个连接。现在如果可以，否则稍后。如果设备处于飞行模式，那么当它离开飞行模式时你的连接就会成功。这比自己构建重试循环容易得多。

我们看到开发者有一种情况是合理的：如果你要让用户在表单中回答很多信息，如果你有充分理由相信之后可能失败，你可能不想浪费用户时间。

如果你关心这个用例，休息后留下来，因为我们有新的更好的方式来处理。安全一如既往地重要。

在使用 TLS 1.2 十年后，互联网现在准备好转向其继任者 TLS 1.3。它有若干改进的安全特性。它减少了连接建立时间，类似于 TCP Fast Open。

该标准现在已最终确定。最终草案今年早些时候已获互联网工程指导组批准发布。

我们正在等待 RFC 编辑器发布实际的已发布文档。一旦发布，我们会默认开启 TLS 1.3。

安全的另一个新元素是证书透明度。你可能听说过证书颁发机构因恶意或无能而向不该颁发的实体签发流氓证书的案例。

解决方案是某种称为证书透明度日志的东西。每个合法的证书颁发机构现在都发布它签发的每个证书的公开声明。这些被记录在公开日志中供任何人检查。

这意味着如果流氓证书颁发机构签发了伪造证书，如果它发布出来，他们会立刻被抓住。如果他们不发布，客户端会抓住他们。

这是你可能熟悉的设置。新的实体是日志。

当证书颁发机构向服务器签发证书时，它也向日志记录该证书，日志给服务器一个签名宣誓书，证明其证书已被公开记录。然后当客户端连接时，服务器可以把所有这些信息给客户端，客户端可以验证不仅这是一个签名证书，它还是一个公开记录的签名证书。

现在假设我们有一个流氓证书颁发机构，不公开暴露它签发的流氓证书。

客户端会拒绝它，因为它没有宣誓书来证明它被记录在公开日志中。

从今年晚些时候开始，我们将强制执行这一点。

所有新签发的 TLS 证书必须包含它们已被公开记录的验证。如果它们没有，客户端将拒绝它。你的 App 不需要做任何更改，但如果你为服务器定制了证书，确保你的证书颁发机构把它们记录在公开证书透明度日志中。现在我们有一点给硬件开发者的消息。

让我们进入今天的第一个议程：降低延迟。

假设你和朋友去一家餐厅，服务员走过来，你说："能给我一杯水吗？"服务员说："当然"，走开，给你拿了一杯水。

你的朋友然后说："我也能要一杯水吗？"服务员说："当然"，走开，给你的朋友拿了一杯水。如果服务员同时接受所有人的点单并减少往返次数，不会更快吗？降低延迟的想法很简单。减少获取资源时的往返次数。

让我们看看你的 App 如何做到这一点。首先，让我们看看 HTTP/1.1 的一些问题。

你的 App 想获取一个资源，你可以创建一个 URLSession 任务并调用 resume。

URLSession 会为你创建一个新连接，包括 DNS、TCP 和 TLS。

一旦与服务器的连接建立，我们就会发出你的请求。然后我们等待从服务器获取响应。这是网络空闲时间，你的 App 不做任何网络活动，等待从服务器得到响应。一旦我们得到响应，我们会调用你的完成块或消息你的委托，表示加载已完成。假设在加载过程中，你的 App 想从同一服务器获取另一个资源。你可以创建另一个 URLSession 任务 called resume，URLSession 会创建一个新连接来获取这个资源，因为它在连接池中没有空闲连接。

如果你的 App 想从同一服务器再获取一个资源，你可以创建另一个 URLSession 任务并调用 resume，我们会创建另一个连接来获取该资源。在这个例子中，我向你展示了我们为从同一服务器获取这些资源创建了三个不同的连接。

如果你注意，我们花了很多时间打开新连接。让我们看看使用单个连接时会怎样。

这是单个连接的情况。我们通过不打开新连接节省了很多时间，但还有另一个问题。

编号为二的绿色请求必须等到响应一完全接收后才能进行。

同样的问题适用于编号为三的橙色请求，它必须等到响应二完全接收后才能进行。

这个问题被称为 HTTP 队头阻塞。

考虑迁移到 HTTP/2。

HTTP/2 使用单个连接，并且它也解决了 HTTP 队头阻塞问题。HTTP/2 在单个连接上多路复用多个流，允许你并行接收响应。让我们再分析一下这个例子，看看 HTTP/2 如何表现得更好。

注意你的 App 想获取资源的时间和请求发出的时间。

在 HTTP/1.1 情况下，你的 App 渴望资源的时间与请求发出的时间之间有显著延迟。

HTTP/2 可以显著减少这种延迟，并允许我们在 App 渴望资源时几乎立刻发出请求。还要注意这些灰色框。

如果你还记得，这是网络空闲时间，你的 App 不做任何网络活动，等待从服务器得到响应。

HTTP/2 可以显著减少这种网络空闲时间，让你更好地利用带宽并更快地加载资源。

我们刚讨论了使用 HTTP/2 而非 HTTP/1.1 的许多好处，但让我们快速总结一下。

HTTP/2 解决了 HTTP 层的队头阻塞问题。它还允许你更好地利用带宽。

如果你的 App 使用 URLSession，你不需要做任何客户端更改。

只需在服务器上启用 HTTP/2，你就会看到这些好处。
