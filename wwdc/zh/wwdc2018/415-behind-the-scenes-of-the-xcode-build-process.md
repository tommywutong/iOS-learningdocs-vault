各位下午好！欢迎来到《Xcode 构建过程揭秘》。

我叫 Jake Petroules，是 Xcode 构建系统团队的一名工程师。今天我们将探索 Xcode 的构建过程。首先，我会向大家介绍 Xcode 10 的全新构建系统，它用 Swift 从头编写，性能和可靠性都有所提升。

我们将解答一些问题，比如当你按下 Command B 时究竟发生了什么？构建过程是如何组织的？Xcode 如何利用项目文件中的信息来确定构建过程的建模和编排方式？接着，我们将进入编译器领域。了解 Clang 和 Swift 如何将你的源代码构建成目标文件（object files）。

我们将展示头文件和模块（modules）的工作原理。了解编译器如何找到你代码中的声明，以及 Swift 的编译模型与 C、C++ 和 Objective-C 有何根本不同。最后，我们将介绍链接器（linker），它执行构建过程的最后步骤之一。我们会解释什么是符号（symbols）以及它们与你的源代码有何关系。还要介绍链接器如何将编译器生成的目标文件拼接在一起，从而为你的应用或框架生成最终的可执行文件。

顺便提一句，在本次演讲中，我们将以一个名为 PetWall 的小型示例 App 作为贯穿始终的例子。它只是一个显示我们宠物照片的简单 iOS App。那么，让我们先来理解什么是构建过程，以及当你在 Xcode 中构建像 PetWall 这样的典型 App 时，构建过程是如何工作的。在这里你可以看到，我们有一个 App target、一个框架、以及一堆用 Swift 和 Objective-C 编写的不同源代码文件。这可能看起来有点像你自己的项目。

当你构建一个 App 时，从项目中的源代码和资源到最终交付给客户或上传到 App Store 分发的软件包，需要经历许多步骤。你需要编译和链接源代码；复制并处理诸如头文件、资源目录（asset catalogues）和 storyboard 等资源；最后还要进行代码签名（code signing），甚至可能通过 shell 脚本或 makefile 执行一些自定义工作，比如为你的框架构建 API 文档，或运行代码检查（linting）和验证工具。

在构建过程中，这些任务大多是通过运行命令行工具来完成的。比如 Clang、LD、AC tool、IB tool、Code sign 等等。

这些工具必须根据你的 Xcode 项目配置，以一组非常特定的参数并按特定顺序执行。因此，构建系统为你所做的，就是在你每次执行构建时，自动编排和执行这些任务。

而且，由于构建过程可能涉及成千上万甚至更多的任务，并形成一张复杂的依赖关系图，这绝对不是你每天想在终端里手动输入 110 次的事情。让构建系统为你代劳吧。

刚才我提到，构建过程中的任务是按特定顺序执行的。接下来我们谈谈这个顺序是如何确定的，以及它为何重要。

构建任务的执行顺序是根据依赖信息（dependency information）来确定的，具体来说就是任务、任务消耗的输入以及任务产生的输出。

例如，一个编译任务消耗一个源代码文件（如 `PetController.m`）作为输入，并产生一个目标文件（如 `PetController.o`）作为输出。

类似地，一个链接任务消耗先前编译任务产生的多个目标文件，并产生一个可执行文件或库作为输出。比如将放入我们 `.app` bundle 中的 PetWall 可执行文件。希望你已经开始从中看出一些规律。

你可以看到依赖信息是如何在这张图结构中流动的，最终决定了执行顺序。

现在，如果你把图中的编译任务想象成一条条车道，你会发现编译任务在各自的车道上完全是相互独立的，因此可以并行运行。而链接任务需要其他所有任务的输出，因此我们知道它必须排在最后。

所以，构建系统利用依赖信息来确定任务应该运行的顺序，以及哪些任务可以并行运行，我们称之为依赖顺序（dependency order）。

现在我们已经了解了什么是构建过程，接下来让我们更详细地了解一下它的工作方式。

当你按下 Build 键时会发生什么？第一步，构建系统获取构建描述（build description），也就是你的 Xcode 项目文件。它解析该文件，将项目中的所有文件、targets 及其依赖关系、你的构建设置都纳入考量，然后将其转换成一个称为有向图（directed graph）的树状结构。这张图表示了你项目中输入和输出文件之间的所有依赖关系，以及将执行以处理这些文件的任务。接下来，底层执行引擎处理这张图，查看依赖规格，确定需要执行哪些任务、这些任务必须运行的序列或顺序，以及哪些任务可以并行运行。然后，引擎会继续执行它们。

顺便说一下，我们用于新构建系统的底层构建执行引擎叫做 `llbuild`。它是开源的，在 GitHub 上开发。如果你对构建系统开发感兴趣，欢迎查看并了解它的运作方式。在演讲结束时，我们会提供该引擎以及构建过程相关其他开源组件的链接。

好了，我们来谈谈发现的依赖（discovered dependencies）。既然依赖信息永远不嫌多，构建系统实际上可能会在任务执行过程中发现更多信息。

例如，当 Clang 编译一个 Objective-C 文件时，它会如你预期那样生成一个目标文件。但它还可以生成另一个文件，其中包含该源文件包含了哪些头文件的清单。下次你构建时，构建系统会利用这个文件中的信息，确保如果你更改了它包含的任何头文件，它会重新编译该源文件。你可以通过 `PetController.h`、`PetController.d`……一直到 `.o` 文件看到这条依赖路径。

刚才我们一直在讨论构建系统的主要职责是执行任务。

当然，你的项目越大，构建过程耗时就会越长。所以你不想每次构建都运行所有这些任务。

相反，构建系统可能只执行图中的一部分任务。具体取决于你自上次构建以来对项目所做的更改。

我们称之为增量构建（incremental build），而拥有准确的依赖信息对于增量构建正确且高效地工作至关重要。现在，我们已经讨论了更改如何影响构建系统，以及它们与增量构建的关系。那么，构建系统实际上是如何检测更改的呢？构建过程中的每个任务都有一个关联的签名（signature），这是一种根据与该任务相关的各种信息计算得出的哈希值。

这些信息包括任务输入的状态信息（如文件路径和修改时间戳）、实际执行命令时使用的命令行参数，以及其他特定于任务的元数据（例如所使用的编译器的版本）。

构建系统会跟踪当前构建和上一次构建中任务的签名。这样它就知道每次执行构建时是否需要重新运行某个任务。

如果某个给定任务的签名与上一次构建中的签名不同，构建系统就会重新运行该任务。

如果相同，则跳过。这就是增量构建工作方式的基本思路。

那么，既然我们已经了解了构建过程是什么以及它是如何工作的，你能如何帮助构建系统更好地完成其工作呢？让我们暂时回到基础。构建过程是按特定顺序执行的一系列任务。但请记住，构建被表示为一个有向图。

所以我们不应该去思考这些任务的执行顺序，因为那是构建系统的工作。

相反，作为开发者，我们需要考虑任务之间的依赖关系，让构建系统根据图的结构找出最佳执行方式。这使得构建系统能够正确地对任务排序，并在可能的情况下实现并行化，以充分利用多核硬件。

那么，依赖关系从何而来？对于某些任务，依赖信息来自构建系统内置的知识。构建系统附带编译器、链接器、资源目录和 storyboard 处理器等的规则。这些规则定义了接受哪些类型的文件作为输入，以及会产生哪些输出。

此外还有 target 依赖关系，它大致决定了 targets 的构建顺序。

在某些情况下，构建系统可以并行编译不同 targets 的源文件。在之前的 Xcode 中，构建一个 target 需要等到它所依赖的整个 target 编译完成后才能开始。

在 Xcode 10 的新构建系统中，targets 可以更早地开始构建。这意味着你的“编译源代码”构建阶段可以更早启动，免费为你提供一定的并行化能力。但是请注意，如果你使用了任何运行脚本构建阶段（run script phases），则需要这些脚本阶段完成后，并行化才能生效。

与 target 依赖关系有些关联的是隐式依赖关系（implicit dependencies）。

例如，如果你在“链接二进制文件与库（Link Binary with Libraries）”构建阶段中列出了一个 target，并且在 Scheme 编辑器中启用了隐式依赖（顺便说一下，默认是启用的），则即使该 target 没有被列在 target 依赖关系中，构建系统也会建立一个对该 target 的隐式依赖。

接下来是构建阶段（build phase）依赖关系。在 target 编辑器中，你会注意到有许多构建阶段。复制头文件、编译源代码、复制 bundle 资源等等。

与每个阶段关联的任务，通常会根据阶段的排列顺序分组运行。但如果构建系统知道更优的方式，它可能会忽略这个顺序。例如，如果你把“链接二进制文件与库（Link Binary with Libraries）”阶段排在“编译源代码”阶段之前。需要注意的是，在某些情况下，错误的构建阶段顺序可能会导致构建问题或失败，所以请确保了解自己的依赖关系，并验证你的构建阶段是否处于正确的顺序。

还有 Scheme 顺序依赖。如果你在 Scheme 设置中启用了“并行构建（Parallelize Build）”复选框，你将获得更好的构建性能，并且 Scheme 中 targets 的顺序无关紧要。但是，如果你关闭了并行构建，Xcode 将尝试按照你在 Scheme 的构建操作中列出的顺序，逐个构建你的 targets。在确定哪个 target 优先构建时，target 依赖关系仍然具有更高的优先级。但在其他方面，Xcode 会遵循你指定的顺序。即使你没有正确设置依赖关系，这样做可能看起来很诱人，因为它能给你一个可预测的构建顺序。但这样做会牺牲大量的并行化能力，从而拖慢你的构建速度。因此，我们建议你保持启用“并行构建”复选框，正确设置 target 依赖关系，而不要依赖顺序。

最后，依赖信息来自你——开发者。如果你正在创建自定义的 shell 脚本构建阶段或构建规则，请务必告诉构建系统它的输入和输出是什么。这让构建系统能够避免不必要地重新运行脚本任务，并有助于确保它们按正确的顺序执行。你可以在“运行脚本”阶段编辑器中定义输入和输出。这些文件的路径将作为环境变量提供给脚本。

不要依赖 auto-link 来处理项目中 targets 之间的依赖关系。

Clang 编译器有一个称为 auto-link 的特性，可以通过“自动链接框架（Link Frameworks Automatically）”构建设置来启用。

此设置允许编译器自动链接到你导入的任何模块（modules）所对应的框架，而无需在“链接二进制文件与库”构建阶段显式链接它们。然而，需要注意的是，auto-link 不会在构建系统层面建立对该框架的依赖。因此，它不能保证你所依赖的 target 在你尝试链接它之前已经实际构建完成。所以，你应该仅在针对平台 SDK 中的框架时依赖此特性。比如 Foundation 和 UIKit，因为我们知道这些框架在构建开始前就已存在。对于你自己项目中的 targets，请务必要添加显式库依赖。

你可能还需要通过将另一个 Xcode 项目拖放到项目文件导航器中来创建项目引用（project references），以便揭示你所依赖的其他项目的 targets。

总而言之，有了准确的依赖信息，构建系统可以更好地并行化你的构建，并有助于确保你每次都能获得一致的结果，这样你就可以花更少的时间构建，花更多的时间开发。

第一个特性叫做头文件映射（header maps），以及我们如何使用它们将信息从 Xcode 构建系统传递给 Clang 编译器。

第二个特性叫做 Clang 模块（Clang modules），以及我们如何使用它们来加速你的构建。你们中有些人现在可能只使用 Swift。

但我想告诉大家，Swift 在幕后使用了 Clang。所以这里可能也有一些让你感兴趣的东西。

那么，什么是 Clang？Clang 是 Apple 官方的 C 编译器，也适用于所有其他 C 语言家族，比如 C 和 C++，当然还有用于绝大多数框架的 Objective-C。正如 Jake 开头提到的，编译器会针对每个输入文件被调用一次，并恰好创建一个输出文件，该文件随后由链接器使用。

如果你想访问 iOS 的 API，或者想访问你自己代码中的实现，你通常需要包含一个叫做头文件（header file）的东西。头文件是一个承诺。

你承诺在别处存在这个实现。它们通常是匹配的。当然，如果你只更新了实现文件而忘了更新头文件，你就违背了你的承诺。这种情况通常不会在编译时报错，因为编译器信任你的承诺。

通常，这会在链接时报错。编译器通常包含不止一个头文件，而且每次编译器调用都是如此。

但让我们只集中关注真正重要的部分，那就是搜索路径。我说搜索路径，你们很多人可能期望现在会看到指向你们源代码的搜索路径。但现实并非如此。

相反，你会看到一些叫做头文件映射（headermaps）的东西。

Xcode 构建系统使用头文件映射来传递那些头文件的位置。

那么让我们来看看它们。我们来看看我们最关心的两个重要的头文件映射文件。

头两个条目只是把框架名称附加到你的头文件上。开头的这两个头文件是公开头文件（public headers）。

我说过你不应该依赖这个特性。原因是，我们保留这个是为了让现有项目能继续工作，但将来在与 Clang 模块一起使用时可能会出现问题，所以我们建议你在包含自己框架中的公开或私有头文件时，始终要指定框架名称。

第三个条目是一个项目头文件。在这个例子中，这不是必需的。

头文件映射的全部目的是指向你的源代码。如你所见，我们对公开和私有头文件都做了同样处理。

我们总是指向你的源代码。我们这样做是为了让 Clang 能够为源目录中的文件生成有用的错误和警告消息，而不是对构建目录中某个潜在的副本发出消息。由于很多人没有意识到我们使用了头文件映射，你可能会遇到某些问题。一个非常常见的问题是，我们忘记把某个头文件添加到项目中。

它存在于源目录中，但不在项目本身。所以，始终要把你的头文件添加到项目中。

另一个问题是，如果有同名的头文件，它们可能会互相遮蔽（shadow）。

因此，始终要尽量为你的头文件使用唯一的名称。

这也适用于系统头文件。如果你项目中有一个本地头文件与某个系统头文件同名，它会遮蔽系统头文件，所以你应该尽量避免这种情况。

但没关系。我们来试试下一个条目。

我们将讨论什么是链接器。

我们将讨论它接收的输入，也就是 dylibs 和目标文件，并解释它们是什么。我们还将讨论符号，也就是这些文件里包含的内容。

在这个部分的最后，我会用一个实例把这一切串联起来——因为这些内容相当密集。所以如果现在听起来有点费解，请先别急，希望我们稍后能把它讲明白。那么，什么是链接器？如我所说，它是构建过程中后期的步骤之一。我们所做的是将两个编译器生成的所有这些 `.o` 文件合并成一个可执行文件。

它的所有工作只是移动和修补代码。它无法创建代码，这一点很重要，我将在示例中展示。

我们接收两种输入文件。第一种是目标文件（object files）。它们来自你的构建过程。第二种是库，其中包括几种类型：dylibs、TBD 文件和 `.a` 文件，也就是静态归档（static archives）。

那么什么是符号？符号只是一个用来引用代码片段或数据片段的名称。

这些片段可能会引用其他符号。比如你写一个函数，而这个函数又调用了另一个函数时就会看到这种情况。

符号可以有一些属性，这些属性会影响链接器的行为。而且有很多这样的属性。我只举一个例子，也就是弱符号（weak symbol）。弱符号是符号上的一个注解，表示当我们构建——当我们在系统上运行可执行文件时，它可能并不存在。这就是所有那些说明“此 API 在 iOS 12 上可用”“那个 API 在 iOS 11 上可用”的可用性标记的本质，当它到达链接器时，所有这一切都归结于此。这样链接器就能确定哪些符号是肯定存在的，哪些符号可能是它需要在运行时处理的。

语言也可以通过名称重整（mangling）将数据编码到符号中，正如 Devin 之前提到的。在 C++ 和 Swift 中你都会看到这一点。所以我们有了符号，这些是指代代码和数据的名称。编译器生成目标文件。而这些目标文件只是这些代码和数据的集合。它们是**不可执行**的。虽然它们是编译后的代码，但它们尚未完成。有些缺失的部分需要链接器来拼接和修正。这些文件中的每个片段都由一个符号来表示。所以对于 `printf` 函数，有一个符号代表的代码。对于 PetKit 中的任何函数也一样，我们马上就会看到。而且片段可能会引用未定义的符号（undefined symbols）。所以如果你的 `.o` 文件引用了另一个 `.o` 文件中的函数，那个 `.o` 文件就是未定义的。链接器会去寻找这些未定义的符号并将它们链接起来。

那么，我说了目标文件是编译器操作的结果。那库又是什么？库是定义了不属于你正在构建的 target 的符号的文件。

我们有动态库（dynamic libraries），它们是 Mach-O 文件，暴露了可供可执行文件使用的代码和数据片段。

这些作为系统的一部分进行分发。这就是我们的框架。你们中很多人也使用自己的框架。还有 TBD 文件，也就是基于文本的 dylib 存根（text-based dylib stubs）。那它们又是什么呢？嗯，当我们为 iOS 和 macOS 制作 SDK 时，我们有这么多 dylib，里面有这么多你可能想用的优秀函数，比如 MapKit 和 WebKit 中的那些。但我们不想在 SDK 中附带这些 dylib 的完整副本，因为那会很大。而且编译器和链接器也不需要。它们只在运行程序时才需要。所以，我们创建了一种叫做存根 dylib（stub dylib）的东西，其中我们删除了所有符号的函数体，只保留了名称。

然后，在那样做之后，我们又制作了它们的文本表示形式，这样对我们来说更容易使用。目前，它们只用于分发 SDK，以减小体积。

所以你可能会在你的项目中看到它们，但不必担心它们。它们只包含符号。

最后，我们还有静态归档（static archives）。静态归档就是用 `ar` 工具、有时也用 `libtool` 来构建的 `.o` 文件的集合。根据 `ar` 手册页的描述，“`ar` 工具创建并维护组合成归档的文件组。”

这听起来可能很像 TAR 文件或 ZIP 文件，而实际上它也确实是。事实上，`.a` 格式是在更强大的工具出现之前，UNIX 所使用的原始归档格式。

但当时的编译器和链接器天生就能理解它们，于是就一直沿用下来了。所以说，它实际上就只是一个归档文件。

有一点值得注意的是，它们也早于动态链接，因此在那时候，所有的代码都是以归档的形式分发的。正因为如此，如果你只用到一个函数，你可能不想包含整个 C 库。所以其行为方式是，如果某个 `.o` 文件里有一个符号，我们会把整个 `.o` 文件从归档里拉出来。但其他 `.o` 文件则不会被引入。如果你在它们之间有符号引用，你需要的所有内容都会被引入。如果你使用了某种与符号无关的行为，比如静态初始化器，或者你正将它们重新导出为你自己的 dylib 的一部分，你可能需要显式地使用 `-force_load` 或 `-all_load` 之类的东西，告诉链接器全部引入。即使表面上没有链接关系。

那么，我们用一个例子试着把这一切串联起来。

这里展示了一个 `playSound` 函数的例子，因为光看宠物而不听它们叫，那多没意思。而且你知道它调用了 `playSound`。你看，这是对猫的对象调用了 `playSound` 方法。这看起来很简单。我们看看它生成的汇编代码。

这是编译后生成的 `cat.o`。看看这个，我们可以看到这里有一个字符串 `purr.aac`，也就是我们的 AAC 声音文件。它被拷贝到 `cat.o` 里了。你会注意到，`purr` 这个文件名本身并没有在任何地方出现。原因是，它是一个 `static` 变量。如果熟悉 C，你就知道这意味着它是一个非导出的名称。没有其他人能引用它。既然没人能引用它，我们也就不需要这个名称。所以它没有被包含进去。

然后我们看到 `Cat purr` 变成了一个真实的符号：很短，就像 `-[Cat purr]`。

这基本上就是你期望看到的。然后我们看到，我们实际上需要获取这个我们要传入 `playSound` 的变量。你会注意到，有两条指令在引用它。这是因为我们不知道这个字符串最终会在可执行文件的哪个位置。我们没有它的具体地址。但我们知道，在这个汇编代码所面向的 ARM64 架构上，地址生成最多需要两条指令。所以编译器给我们留下了两条指令。它留下了符号偏移量，也就是 `page` 和 `pageoff` 这些符号值，链接器稍后会进来把它们修正。

最后，既然我们已经把那个字符串加载到了 `x0`，我们就可以调用 `playSound` 了——只不过我们调用的不是 `playSound`。我们调用的是 `__Z9playSoundPKc`。那是什么？那是一个重整后的符号（mangled symbol），因为如果你注意看，它会显示 `cat.mm`。这是 Objective-C++。而 `playSound` 实际上是一个 C++ 函数。

所以如果你不熟悉这些，你可以去终端，那里有一些可用的工具。如果你运行 `swift-demangle` 并传入一个符号，它会尝试去重整这个符号。这里没能成功。这不是一个 Swift 符号。但 `c++filt`，也就是 C++ 的去重整工具，它告诉我们这实际上就是 `playSound` 的符号。而且它不仅是 `playSound`，我们还知道它接受一个参数。而且那个参数是一个 `const char *`，因为 C++ 把那些额外数据编码进了重整后的符号里。

好了，现在我们有了一个 `.o`。事实上，我们在构建一个项目时，会有很多这样的 `.o` 文件。那我们拿它们怎么办？首先，构建系统会把所有这些 `.o` 作为输入传给链接器。链接器会先创建一个要把它们放进去的文件。在这里，我们是在构建 PetKit，它是 PetWall 内的一个内嵌框架（embedded framework）。所以我们就从复制开始。我们会创建所谓的文本段（text segment）。

也就是我们存放应用程序所有代码的地方。然后我们取出 `cat.o`，把它复制进去。但我们要把它分成两个区段（sections）。一个给那个字符串，另一个给可执行代码。但现在，我们知道了这些东西的绝对地址，所以链接器可以去重写 `cat.o`，让它从特定的偏移量加载。你会注意到，第二条指令就没了。我们用一个空指令，也就是一个啥都不干的指令取代了它。

但是我们不能移除那条指令，因为我们不能凭空创建或移除代码。那会破坏我们已完成的所有大小计算工作。所以它只能被替换掉，被替换成一个空操作。最后我们进行分支跳转。

好了，但我们进行了分支跳转，然后要做什么呢？因为我们还有这个未定义的符号？嗯，我们会继续找，而这时候我们所有的 `.o` 文件都已经包含进来了。

于是我们开始查看静态归档，那里面有 `PetSupport.a`。在 `PetSupport.a` 里面，有一批文件，包括 `PetSounds.o`。看看这个，我们发现存在那个匹配的符号，也就是 `playSound`。

所以我们把它拉进来。我们会注意到，我们没有拉入 `PetCare.o`。因为那个 `.o` 文件中，没有任何被这个应用程序其他部分引用的符号。好了，我们拉入了它，但现在它又需要 `open`，这是我们没定义的。你会看到，在那个……在我们复制进去的转换中，我们实际上用了一个叫做 `open$stub` 的东西替换了它。为什么这么做？嗯，我们继续查找，并且找到了 `open` 的一个副本。那个 `open` 的副本在 libSystem 的 TBD 文件中。

于是我们说，我知道这是系统库的一部分。我不会把它拷贝到我的应用程序里。但我需要放上足够的信息，使得能够调用到它。所以我们创建了一个伪函数，它只是一个模板，在这里我们用从 libSystem 拉过来的任何东西——这个例子中是 `open`——替换了函数。如果你看看那个函数内部，它实际上是从一个指针 `open$pointer$` 加载。

然后跳转到那里。所以我们只需要一个函数指针，就像任何普通的 C 函数指针。于是我们会在数据段（data segment）里创建它，也就是存放全局变量的地方，如果你有任何全局变量的话。

但它只是被设为零。所以如果我们解引用空指针并跳转过去，程序就会崩溃。

所以我们又添加了一个叫做链接编辑段（link edit segment）的东西。链接编辑是一种元数据，是链接器工具留下的信息，好让操作系统和所谓的动态链接器（dyld）在运行时把它修复好。要了解更多相关信息，你应该去看看 2016 年的《优化 App 启动时间》讲座。那么，我想回顾一下我们今天所讲的内容。Jake 讨论了构建系统，以及如何利用依赖关系来为多核优化你的构建过程。Jurgen 带你了解了 Clang 以及它是如何为你查找头文件的。还有通过模块你能做些什么来优化你的构建。

Devin 带你了解了 Swift 如何扩展模块，以及我们今年为实现这些所做的一切，比如通过批处理来加速你的构建。最后，链接器接收两个编译器的输出，并将它们构建成你的应用程序。到这一步，Xcode 会继续进行代码签名，并将其与你的应用程序其他部分一起打包，以备分发。
