Swift 包管理器使在 Swift 生态系统中开发和分发源代码变得更加容易。今天我们将讨论它的目标、部分设计，以及未来可能的发展方向。

我们先讲为什么决定在 Swift 项目中创建一个新的包管理器。然后展示如何使用它，再深入其设计与功能。

我相信大多数人都熟悉包管理器，它们是共享和复用代码的好方式。但为什么我们要为 Swift 创建一个新的？首先，Swift 是跨平台语言，因此我们希望有出色的跨平台工具来构建你的 Swift 代码。这使得你可以用一致的方式配置代码，并在 Swift 支持的所有平台上运行。SwiftPM 包含自己的完整构建系统，允许你用一个工具配置软件、构建、测试，甚至运行它。

我们还希望尽可能让你与任何人共享你的 Swift 库，无论他们在哪里，通过在 Swift 项目中提供规范的包管理器，我们希望为分发库定义通用标准。这便于扩展 Swift 生态系统，让 Swift 对所有人都更好。你们中的许多人可能对想添加的功能有很棒的想法。但我们希望谨慎地将内容加入核心库，以维护谨慎且完善的 API。优秀的包管理器便于把这些想法作为包分发，而不必放入核心库。最好的想法可以随时间在社区中有机地获得认可，并越来越标准化。

最后，通过与 Swift 一起构建包管理器，我们能够利用 Swift 的力量与哲学。SwiftPM 本身就是用 Swift 编写的，它甚至是一个 Swift 包。此外，我们有机会与 Swift 语言和核心库项目紧密合作，构建能让你的 Swift 代码大放异彩的优秀包管理器功能。

SwiftPM 是 Swift 开源项目的一部分，在 Swift.org 和 GitHub 上都有自己的主页。Swift.org 的 Swift Package Manager 部分是很好的起点。

当你准备试用时，可以在每个 Swift 工具链中找到它，也可以从 Swift.org 下载。当然，它也包含在 Xcode 的每个版本中，与 Swift 工具一起。

现在切回幻灯片，讨论 SwiftPM 的基本概念。

一个包由三大部分组成：依赖、目标和产物。我们将在下文更详细地看每一部分。

依赖是你在开发功能时可以使用的 Swift 包。每个依赖提供一个或多个产物，如库，供你的包使用。让我们看看依赖在包的 Swift 清单文件中长什么样。每个依赖都有源位置，并且有版本。

目标是包的基本构建块。

目标描述如何将一组源文件构建为模块或测试套件。

目标可以依赖同一包中的其他目标，以及声明为依赖的其他包导出的产物。

产物是可执行文件或库，由一个或多个目标的构建产物组装而成。

包通过定义产物为其他包提供库。默认情况下，你不必显式声明库类型，SwiftPM 会根据使用情况为你选择。如果需要，你可以显式声明库为静态或动态。让我们看看目标在清单中如何配置。在我们的示例中有三个目标。

第一个叫 libdealer，包含我们主要功能的实现。它有一个依赖：我们早先声明的依赖提供的 deck of playing cards 产物。

第二个目标 dealer 依赖它，提供我们刚才运行的命令行工具。最后，我们还有测试目标，依赖其他两个目标，用于对我们功能进行单元测试。

在示例包中，我们还配置了两个产物。

第一个是对应 libdealer 目标的库产物。它把我们的实现作为库提供给外部使用。第二个是可执行目标，依赖 dealer 目标，提供命令行使用的可执行文件。

接下来我将讲 Swift 包管理器的设计。

SwiftPM 遵循 Swift 的哲学：快速、安全、富有表现力。它因隔离的构建环境以及构建不能运行任意命令而安全。它因使用可扩展到大型依赖图的构建引擎而快速。它因使用 Swift 语言作为包清单而富有表现力，这也允许你使用已经熟悉的编程语言。在本节剩余部分，我将带你经历创建自己的 Swift 包时会遇到的不同步骤。我们从配置开始。

如早先所见，SwiftPM 的清单基于 Swift。使用 Swift 使其易于理解，因为无需学习新语言。我们遵循 Swift 的 API 设计指南，使其更熟悉。它还允许我们利用为 Swift 编写的现有工具；但编写自己的清单时，仍应优先使用声明式语法并避免副作用。

因为 SwiftPM 不保证源代码何时或以何种频率被求值。左侧这里有一个不真正声明式的示例。我们看不到正在生成的名称，且它在包中被使用几次。相比之下，右侧我们通过使用字符串常量得到完全声明式的清单。它易于理解和看清目标。

如你所见，不使用声明式语法也会让你和用户的清单更难理解。

源文件在磁盘上按包中每个目标命名的文件夹组织。这便于入门，并允许包采用通用结构，以便你能快速导航。

包管理器与其他构建工具常在用户显式配置与包管理器施加的约定之间存在张力。

如我早先所说，源文件从约定的基础位置自动拾取，因此你可以非常容易地添加或移除源文件而无需编辑包清单。

然而，产物和目标值得显式配置，以便更容易理解包及其定义，而无需与磁盘布局交叉引用。

这也让客户端仅通过查看清单就能轻松看到包提供什么。

SwiftPM 还支持为其他程序管理语言构建源代码，如 C、C++ 和 Objective-C。这便于与现有代码集成。

注意，我们不支持在同一目标中混用这些语言与 Swift。接下来，我们看依赖与版本。

为确保你的包能从 bug 修复中受益而无需持续 churn，Swift 包应遵循语义化版本。

这是常用标准，为版本号的每个组件赋予特定语义。

主版本号表示破坏性变更，要求客户端更新代码。

变更示例包括删除现有类型、删除消息或更改其签名。它们还包括向后不兼容的 bug 修复，或对现有 API 行为的重大更改。次版本号应在以向后兼容方式添加功能时更新。例如添加新方法或类型。最后，修订版本号应在进行向后兼容的 bug 修复时增加。

这允许客户端从 bug 修复中受益而无需冒险破坏源代码。SwiftPM 需要在准备好构建前确定包图中所有包的确切版本。我们通过名为依赖解析的过程完成。作为其中一部分，SwiftPM 查看为包指定的所有要求，并找到与所有要求兼容的最新版本。让我们用之前演示的包更仔细地看 SwiftPM 在此过程中做什么。

演示中的 dealer 包有两个直接依赖。一个是 SwiftPM 本身，另一个是 deck of playing cards。SwiftPM 会解析这些直接依赖的版本。对于第一个，这很直接，因为我们指定了精确版本，恰好对应那个标签。对于第二个，我们使用 from 语法。这意味着我们获取次版本或修订版本的更新。这种情况下，我们最终得到标签 3.1.4。整个过程是递归的。因此接下来 SwiftPM 会查看所有直接依赖的传递依赖。PM 没有进一步依赖，因此在那里无事可做。但 deck of playing cards 依赖 Fisher-Yates 和 playing card 包。接下来 SwiftPM 必须再次解析这些包的版本。对于 Fisher-Yates 包，这与之前一样，因为我们也使用 from 语法。这种情况下我们最终得到标签 2.2.5。对于 playing card 包，我们使用 up to the next minor 语法。这意味着我们只获取修订版本的更新。

如果你希望更保守地对待依赖，只接受 bug 修复，你可能想用该语法。这种情况下我们最终得到标签 3.0.2。最后，查看目标时，SwiftPM 必须将所需产物与我们解析的包匹配。为此，我们查看演示中的 dealer 目标，如你所见，utility 产物由 SwiftPM 包提供。

其余包提供其他产物。依赖解析后，解析结果记录在名为 package.resolved 的文件中。该文件的目的是让你与团队其他成员或持续集成基础设施共享解析版本，以便获得可靠的构建结果，并让你能主动选择何时更新依赖。当你准备好更新时，运行 Swift Package Update 即可。注意，这是包含 package.resolved 的顶层包。如果某个传递依赖包含 package.resolved 文件，它在依赖解析中会被忽略。

接下来，让我们看看构建你的包。SwiftPM 使用 llbuild 作为底层构建引擎。llbuild 是一组用于构建构建系统的库，围绕通用且可复用的构建引擎构建。这使我们能够进行快速且正确的增量构建。它也被 Xcode 的新构建系统使用。它也是 Swift 开源项目的一部分。

在所有依赖显式声明的隔离环境中开发软件，确保即使具有复杂需求的包也能在不同环境中可靠地构建和使用。

SwiftPM 不允许将包全局安装到系统中，只允许你使用显式依赖的包。

我们还利用构建沙盒，使构建期间不能向文件系统任意位置写入。

SwiftPM 不允许在构建过程中执行任意命令或 shell 脚本。

这使我们能完全理解你的构建图及其所有输入和输出，从而进行快速且正确的增量构建。因为我们掌握所有依赖的视图。如我之前演示所示，SwiftPM 也支持测试。这基于你熟悉的 XCTest 框架。我们支持并行测试，以便更快得到测试结果。

我们支持测试过滤，以便运行测试子集并迭代单个功能。随着 SwiftPM 的演进，我们考虑工作流功能，尤其是让你能在命令行完成所有开发。其中一个功能是 edit 模式，允许用本地检出的副本覆盖特定包的所有传递出现，以便进行临时编辑，并在无需预先转发图中所有包的情况下测试对传递依赖的更改。

分支依赖允许依赖没有严格版本要求的包。这在同时开发多个包时很有用。

这是仅开发功能，因此在发布标签前你必须切换到特定版本依赖。本地包允许你直接从文件系统使用包，而不是从 git 仓库。这便于在初始创建时拉起多个包。

所以，最后话题，我想讲采用新版本的 SwiftPM 和 Swift 语言。Swift 的每个新版本都可以带来 package.swift 清单 API 的新版本。之前的 API 仍然可用，因此你可以利用新的源工具而无需更新包或失去对现有包的访问。

新 API 可以独立于为包的源代码更改 Swift 语言版本而采用。为指定正在使用的 API 版本，我们在 package.swift 清单文件顶部使用 Swift Tools Version 命令。这指定处理给定清单所需的 Swift 工具最小版本。每个包还可以声明它用于编译源代码的 Swift 语言版本。这是列表，因此你可以通过使用编译器指令，用同一包版本支持多个 Swift 版本。包图可以混合使用不同语言版本的包。

Swift 使用开放的演进过程，意味着任何人都可以贡献想法，包括你。如果你正在寻找灵感，我们想分享一些想法，但这些都不是既定计划。我们分享这些想法，以便你能看到 Swift 包管理器的潜力。我们欢迎你提供反馈、评论和你自己的想法，随着产品演进。

我今天要讲的想法分为四个主题。

让 Swift 包管理器与其他可能构建于其上的工具集成。帮助你发布包的新版本并部署其产物。支持比 SwiftPM 今天能构建的更复杂包。最后，关于包发现与信任的前瞻性思考。虽然 SwiftPM 命令行体验很重要，我们希望确保 SwiftPM 能与其他工具集成，如开发环境、自动化等。

我们已通过 SwiftPM 基于库的架构奠定基础。SwiftPM 今天没有稳定 API，但对于愿意跟进 SwiftPM 变化的工具，它可供采用与扩展。

如果你希望在开发者工具中构建 SwiftPM 支持，我们欢迎你的贡献与讨论。我们希望 SwiftPM 成为开发者工具繁荣生态的一部分。最近在 Swift 论坛上有人请求一种方式，让自动化工具编辑 package.swift 清单，而不是总让用户直接编辑源代码。我们认为 SwiftPM 可以支持这一点，可能通过使用 libSyntax。libSyntax 是 Swift 开源项目中正在开发的库，使其他工具更容易理解和操作 Swift 语法。

Boris 早先告诉过你，应该为 package.swift 清单优先使用声明式语法，这也是另一个原因。这将使 SwiftPM 更容易理解你的清单，以便进行自动更改，如这里所示添加新依赖或目标。因此，SwiftPM 也有很多空间添加新功能，帮助你发布包的新版本并部署其产物。

今天，当你想发布包的新版本时，你用 git 手动打标签。如果你想检查已发布的标签，也直接用 git。

我们可以添加新功能来自动化此过程，并执行你可能希望作为精简发布工作流一部分的额外内务、验证和其他辅助任务。

这里尤其有用的功能是协助维护正确的语义化版本。SwiftPM 可以分析你包新版本的 API 差异，检测你是否做了编译时不对等的更改，从而建议更新包的主版本。

我们还能做的是让从 SwiftPM 部署包产物更容易。你可能想自定义与库的链接，或为特定部署环境定制产物布局，无论本地还是服务器。或者，你可能想在产物中包含关于构建了哪些包的版本信息。或者，你希望在产物中某处使用 SwiftPM 对你包的上下文。SwiftPM 可以添加新命令支持所有这些需求。

今天用 SwiftPM 可以构建很多东西，但我们也希望支持具有更复杂需求的包。

我们目前最大的缺口可能是资源支持。如果你有图片、数据文件或其他资产，SwiftPM 当前无法将它们与产物打包。

Foundation 核心库实际上在今年春天刚添加了跨平台资源 API，因此如果我们想构建该功能，SwiftPM 可以采用该 API。

我们知道一些用户还希望支持指定编译器标志、链接器标志，以及 SwiftPM 今天不支持的其他属性。如果能添加健壮的构建设置模型会很好，可能包括条件设置，或对包的哪些部分获得哪些设置值的细粒度控制。

Boris 早先也讲过 SwiftPM 的构建隔离及其重要性。

我们不允许运行任意 shell 脚本。但许多用户可能希望对构建有一定定制，要么因为他们想支持自定义语言或处理器，要么想运行自己的文档生成器，或者有其他需要带入构建过程的步骤。我们认为 SwiftPM 可以安全地支持这一点，可能通过真实工具包把新工具带入构建过程。这里需要确保的重要一点是，任何带入构建过程的新工具都必须正确声明其输入和输出依赖，以便 SwiftPM 能继续维护正确、可并行的增量构建。

最后，我想讲一点关于包发现、信任与管理的前瞻性思考。Git 本身支持的协议提供安全机制如 TLS，以确保你确实在与你以为的远程仓库通信。但恶意攻击者仍可能攻破远程仓库并放入恶意内容。实际上，任何时候使用第三方代码，你都应意识到这类风险。但 Swift 包管理器为我们提供了构建安全功能以确保你真正得到预期包内容的机会。

SwiftPM 还阻止 package.swift 清单求值在构建中逃逸并写入文件系统或访问网络。我们今天使用 macOS 的沙盒技术。这很好。但我们希望把这种安全带到其他平台。

许多用户可能希望轻松 fork 包，要么因为他们想对图中的某个包做私有定制，要么甚至只是想覆盖获取每个包的 origin URL，以便指向他们控制的私有镜像，而不依赖原始包始终存在。最终，我希望某天我们能有真正的 Swift 包索引。除了提供标准化命名空间并使发现新包更容易外，我们甚至可以支持包的质量指标。比如它的自动化测试覆盖率是多少？或者评估你正在考虑采用的新包的可信度方式。所以，我讲了很多，但这些只是部分可能性。最终，对于感兴趣的人，我们希望得到你的反馈、想法和贡献，帮助使 Swift 包管理器成为开发者社区的最佳工具。因此，为了讲如果你愿意如何做到，我想讲 Swift 的开源流程。

如我早先所说，包管理器是 Swift 开源项目的一部分。Swift.org 也是了解社区与流程的好地方。

SwiftPM 使用 Swift 语言演进过程，意味着任何人都可以为 Swift 包管理器的主要新功能或更改提交提案。

不过，在你起草完整正式提案之前，我建议你先到 Swift 论坛的包管理器版块与社区交流你的想法。你可能得到很多反馈，帮助让想法更好。如果你有兴趣从较小贡献开始，bugs.swift.org 上的 Swift bug 跟踪器有很多想法。特别是，你可能想查找标有 starter bug 标签的 bug。而且，如我说的，SwiftPM 是用 Swift 编写的，你可能会发现深入查看其实相当容易。当然，如果你在使用 SwiftPM 时发现 bug，我们鼓励你也在 bugs.swift.org 上提交，以便跟踪我们如何处理。SwiftPM 得以利用 Swift 项目相同的优秀持续集成基础设施。这意味着拉取请求可以在合并前自动构建并运行测试。因为 SwiftPM 代码库本身有很好的测试覆盖，我们发现该基础设施对我们非常有用。

当你准备好试用最新更改时，可以在 Swift.org 下载定期更新的 Trunk Snapshot 工具链。

我们对迄今 SwiftPM 社区的增长非常满意。已有 180 多人通过 bug、功能或新功能贡献。Swift 包生态也在健康增长，经常有跨平台包，GitHub 上有很多公共包。这意味着你可以专注于产品特别之处，让包依赖处理其余部分。有几件事我建议你今天就试用 SwiftPM，即使它未来还有很大成长空间。这两件事是命令行工具和库，以及在服务器上用 Swift 开发。

服务器端 Swift 社区大量使用 Swift 包管理器。服务器端 Swift 自身也在良好增长，现在有许多框架可用于 Web 和后端开发。如果你愿意看看这种方法，我认为你会发现 Swift 是进行此类跨平台开发的优秀语言。
