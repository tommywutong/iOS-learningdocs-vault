那么首先，为什么要创建自定义 Instruments？Instruments 本身已经附带了大量强大的工具，例如这里展示的 System Trace，你可以看到你的 App 如何与调度器和虚拟内存交互。

今年我们引入了一个新的游戏性能模板，它结合了 System Trace 和 Metal System Trace，来帮助你发现 App 中的卡顿和丢帧问题。如果你在处理 App 的网络部分，我们还提供了 Network Connections Instrument，它可以显示进出你 App 的 TCP/IP 流量。当然，很多人对 Time Profiler 也很熟悉。Time Profiler 是查看 App 时间花在哪里的绝佳方式，无论是在网络层、游戏引擎还是其他部分。

这些工具的共通之处是，如果你了解正在分析的代码，它们会非常有用。也就是说，如果你知道那些 IP 地址的含义，知道不同的函数以及 Time Profiler 调用栈的含义，那么分析起来就容易得多。但是，如果有人对你的 App 进行分析，却不熟悉其中的代码呢？如果他们只是想看看 App 是否在网络层花费了大量时间，如果是，又在做什么呢？一个好的做法是使用自定义 Instrument，以一种不懂代码的人也能理解和欣赏的方式，来讲述你的层或你的 App 在做什么。

在高级部分，我们将展示如何利用 Instruments 内置的专家系统技术，从而创建一个即使在你不场的情况下，也能自动查找代码中的不良模式并识别反面模式（anti-pattern）的 Instrument。

好，让我们看看实现这一切的构架。为此，我们得从头开始。从一开始，Instruments 的工作方式就与今天大致相同。仍然有一个库，你仍然将 Instruments 拖放到跟踪文档中，然后按下“录制”按钮，就像同时运行多个性能工具一样。那时和现在的主要区别在于，那时的 Instruments 基础设施并没有提供太多帮助来让我们快速编写 Instruments。在当时，这还可以接受，因为我们继承了不少已有的功能和性能工具。它们都有自己的录制技术和分析逻辑，我们只需要构建一个自定义存储机制来将数据放入跟踪中，以及一个自定义 UI 来帮助它与 App 的其他部分集成。但随着时间的推移，Instruments 的维护成本以及维护这种模式的成本急剧上升。原因在于，每次我们想要添加一个新功能，都必须修改七个自定义 UI 和七个自定义存储机制，这不是我们希望你们继承的模式。我们不想让你们继承这种维护成本。所以，在讨论自定义 Instruments 功能之前，我们需要先解决这个问题，我认为我们做到了。因此，在新版本的 Instruments 中，我们不再使用自定义 UI 和自定义存储机制，而是采用了两个标准化组件：Standard UI 和 Analysis Core。Standard UI 实现了现代 Instrument 的整个用户界面，并且与 Analysis Core 紧密耦合。你可以把 Analysis Core 看作是数据库和专家系统的结合体。这两者都针对时间序列数据进行了优化，这为构建 Instruments 奠定了坚实的基础。当你使用现代架构构建 Instrument 时，你所做的实际上就是创建 Standard UI 和 Analysis Core 的一个自定义配置。

现在，如果你看看我一开始展示的那些强大 Instruments 的截图，我们有 System Trace、Game Performance 模板、Network Connections 模板和 Time Profiler。所有这些文档中的 Instruments 都是完全使用 Standard UI 和 Analysis Core 构建的。所以你可以做和他们完全一样的事情。在 Xcode 10 和 Instruments 10 中，我们为你提供了完全相同的工具来构建你的 Instruments。因此，一个随 Xcode 发布的 Instrument 与你构建的 Instrument 之间的唯一区别只是谁构建了它。现在，你的 Instruments 会出现在我们的库中，就像顶部的 Activity Monitor 一样。同样地，你可以将你的 Instrument 拖放到跟踪文档中并进行录制。然后，Instruments 会用数据填充 Analysis Core，Standard UI 会作出响应，创建图形和表格视图。

表格是行的集合，其结构由表格模式（table schema）定义。对，这和数据库应用程序非常相似。模式定义了列、列名以及类型。Analysis Core 使用一种非常丰富的类型系统，称为工程类型（engineering type），它既告诉了我们如何存储数据，也告诉了我们在 Standard UI 中如何可视化和分析数据。

此外，当模式描述表格的结构时，你可以使用属性（attribute）——键值对——来描述内容。这有助于描述表格中包含什么。你可以将模式视为 Objective-C 或 Swift 中的类，而行就像实例。所以，你的模式名使用单数形式很重要，就像我们在 Objective-C 中类名使用单数形式一样，例如 `NSString` 而不是 `strings`。这在高级部分会更重要，但我现在提出来，这样我们就知道我们在看什么。好的，这里有一个模式的例子：`tick`。这是 Instruments 内部使用的模式之一，用于保存合成时钟滴答的表格，我们稍后会在 modeler 中用于统计计算。它非常简单，只有一个定义的列，即 `time`，使用的是工程类型 `sample-time`。它还定义了一个可选属性（attribute），可以附加到该表格实例上，名为 `frequency`。所以，如果你为 `tick` 模式创建一个带有 `frequency = 10` 属性的表格，那么该数据的提供者就知道它需要每秒用十个时间戳填充该表格，对吧。这就是一种沟通你想要填充到表格中的内容的方式。

从图形轨道开始。

你看到了 Kacper 如何使用我们称之为 `plot` 元素的方式定义图形和轨道。`plot` 元素是告诉 Standard UI 我们应该获取表格的整个内容并尝试在特定轨道中绘制它的方法。`plot` 元素决定如何绘制、绘图处理应该是什么的方式，是通过查看模式和被指定为值来源的列。如果模式是间隔模式（interval schema），意味着它有 `time` 和 `duration`，或者如果是点模式（point schema），意味着它只有一个时间戳，它们的处理方式不同。如果被指定的列具有量级，意味着它可以绘制条形图，那么它将绘制这样的条形图。另一种选择是我们的生命周期轨道，它仍然是一个间隔模式，但我们指定的是一个状态列，而状态本身没有量级。所以在这里绘制条形图没有意义。因此 Standard UI 会自动选择一种状态样式处理，即使用标签和圆角矩形绘制这些间隔，这样你就可以将其与普通的条形图区分开来。Standard UI 能够为你选择这些处理方式非常重要，因为这样才能保持 Instruments UI 的一致性。所以如果你定义了一个状态图，而我们也定义了一个状态图，Standard UI 会强制它们看起来一样，这使得 Instruments 的用户能更容易地在不同 Instrument 之间切换。如果你想根据数据的内容动态创建图形或轨道数量，你可以定义所谓的绘图模板（plot template）。绘图模板的定义与绘图非常相似，只是其中多了一个元素，允许你选择表格中的一列，它将为每个唯一值创建一个单独的轨道。

如果你只是寻找活动高峰或活动周期，我们有所谓的直方图（histogram），你可以将时间线分成特定大小的桶（例如 100 毫秒），然后使用 count、sum、min 或 max 等函数，根据不同点或间隔的交叉情况来驱动这些桶的量级。这是寻找活动高峰的好方法，例如在 System Trace 中，我们寻找上下文切换或虚拟内存中的活动高峰。现在让我们谈谈详细信息视图。详细信息视图位于 UI 的下半部分。

你已经看到了第一种，即列表。这是表格、Analysis Core 和 UI 中的表格视图之间非常简单的映射。我们还有聚合（aggregations）。当你想要剔除时间成分并查看数据的聚合情况时，聚合非常有用。你想对表格中的所有内容应用一些统计信息。因此，当我们定义聚合时，这次各列变成了函数。你可以使用 sum、average、count 和其他几个统计函数来帮助你创建想要的聚合视图。

聚合的另一个好处是，你还可以定义层次结构。所以这里我们定义了一个进程线程（process thread）到虚拟内存操作（virtual memory operation）的层次结构，这样我们可以查看按进程、然后按该进程中的每个线程、再按该线程或进程中的每种操作类型细分的总数。所以聚合是一种非常强大且简便的查看大量数据摘要的方式。

另一种聚合类型称为调用树（Call Tree）。

当你有一个列是回溯（backtrace），而另一个列是权重时，调用树就很有用。你可以使用调用树创建一个加权的回溯或加权的调用树视图，就像你在 Time Profiler 中看到的那样。

另一种样式称为叙述（narrative）。叙述用于传达那些最好用技术语言表达的信息，例如专家系统的输出，它与叙述工程类型配合使用。

最后一种详细信息类型称为时间切片（time slice）。时间切片看起来很像列表，只是其内容被过滤，只包含与你在图形上看到的蓝色线相交的间隔。这条蓝线被称为检查头（inspection head）。因此，当你在图形上移动检查头时，列表的内容将被过滤，以匹配与该检查头相交的内容。

所有这些 UI 都绑定到 Analysis Core 中的表格。当你按下“录制”按钮时，数据通过 Instruments 应用传入，并填充到 Analysis Core 中。让我们更详细地谈谈这个过程。

在你可以按下“录制”按钮之前的第一步是，Analysis Core 将接受在其中创建的表格，并在核心中映射并为它们分配存储空间。如果一个表格具有完全相同的模式和完全相同的属性，那么根据定义，它们是完全相同的数据，因此它将映射到完全相同的存储（store）。

对于每个存储，第二步是尝试为数据寻找提供者。有时我们可以通过数据流直接从目标录制数据，有时我们必须使用 modeler 来合成数据。

Modeler 可以有自己的输入需求，而这些输入可以是其他 modeler 的输出，也可以直接从数据流录制，这就是我们如何合成那些我们不知道如何直接录制的其余数据。

一旦我们为 Analysis Core 中的所有存储找到了数据源，这就构成了所谓的绑定方案（binding solution）。第三步是优化绑定方案。在这里，你可以看到 Instruments 正在可视化它自己对于所谓线程叙述（thread narrative）的绑定方案。

关于绑定方案的下一点是，它是跟踪范围性的，因此当你将 Instruments 拖放到跟踪中时，Instruments 会计算最佳的录制方案，以尽量减少对目标的录制影响。当你创建自己的表格或创建表格实例时，你必须为它们提供一个模式。Instruments 已经定义了超过 100 个模式。所有这些模式都可以为你所用，并且包含在你之前在包管理 UI 中看到的包中。你可以简单地将模式导入到你自己的包中。如果这个模式包含在一个不是基础包的包中，你还必须在 Xcode 的构建设置中将该包链接为“链接的 Instruments 包”，这样我们就可以在构建时找到你引用的那个额外包并进行一些类型检查。

由于所有这些模式都在其他包中定义，当你按下“录制”时，所有具有这些模式的表格都会被填充，因为它们要么定义了 modeler，要么我们知道如何从数据流录制。因此，这些是你自己 Instrument 的绝佳构建块，但更重要的是，它们也是编写你自己的 modeler 的绝佳输入。你可以在 Instruments 包中使用 `modeler` 元素编写或定义一个 modeler，并且你还可以为该 modeler 创建一个自定义输出模式。如果你只有单个时间点，可以使用 `point-schema`；如果你有起止时间和持续时间，则可以使用 `interval-schema`。Modeler 能够定义它需要的输入，这告诉了绑定方案如何填充数据流图的其余部分。因此你的 modeler 将直接接入绑定方案。Modeler 实际上是微型的专家系统，它们是用 Clips 语言编写的，这意味着它们非常强大，但也相当高级。因此，我们将把如何创建 modeler 的细节留到高级部分；然而，能够定义你自己的模式非常重要，而且今年我们有新的 os signpost API，这是将数据输入 Instruments 的好方法。所以我们创建了一个小捷径。

好的，现在我们看到了如何将 os signpost 数据与自定义 Instruments 结合使用。我们认为你可以充分利用这两者，这个组合可以走得很远。现在，我们可以讨论一些高级主题，特别是如何创建和定义 modeler。

从概念上讲，modeler 是一个非常简单的机器。它接收一系列输入，对这些输入进行一些推理，并产生输出。

Modeler 的输入总是完美地按时间排序，所以如果你请求几个不同的输入表，这些表格会先按时间排序，然后合并成一个按时间排序的队列，该队列馈送到工作内存（working memory）中。因此，当我们逐个取出这些事件时，它们被输入到 modeler 的工作内存中。当 modeler 观察工作内存的演变时，它可以进行推断。当它看到想要为其产生输出的模式时，它只需将其写入其出站输出表格。让我们通过一个有点趣味性的例子来看看如何使用 modeler。假设你定义了一个名为 `playing_with_matches` 的模式。这是一个 os signpost interval schema，用于你定义的一个 os signpost，表示你将在代码中执行某种危险操作。我们再定义另一个模式 `app_on_fire`。它也是一个 signpost 模式，但这些 signpost 意味着 App 已进入不良状态，我们真的很想知道原因。

所以，你创建一个输出模式，它是一个点模式（point schema），将保存正在玩火柴的对象以及起火的时间。我们将其称为 `started_a_fire` 模式。Modeler 的世界看起来像这样。我们按时间顺序设置好所有输入准备就绪，左侧的虚线称为 modeler 的时钟。

当我们抓取第一个输入并将其输入到工作内存时，modeler 的时钟移动到该间隔的开始处。然后我们抓取下一个输入，modeler 的时钟再次移动到该间隔的开始处，并将其输入到工作内存中。现在 modeler 在工作内存中看到了这两者，它可以发现如果玩火柴在 App 着火之前开始，那没什么大不了的；如果是相反的情况，即已经着火，那么我们可以得出一个逻辑结论，称为起火原因，并将其输入到工作内存中。

当我们抓取这第三个输入时，你会注意到 modeler 时钟已经移动，并且不再与我们的前两个输入相交。因此它们从工作内存中被移除。如果起火原因具有所谓的逻辑支持（logical support），它也将从内存中被移除。回顾一下，时钟总是设置为当前输入的时间戳。对于一个输入来说，要留在工作内存中，它必须与 modeler 中的当前时钟相交。这有助于我们建立同时性。它允许我们修剪旧数据，也允许我们查看是否存在可能在时间上相关的输入。

Modeler 推理其工作内存的方式由你通过所谓生产系统（production system）来定义。

生产系统处理工作内存中的事实，并由规则（rules）定义，规则具有左侧、生产运算符和右侧。左侧是工作内存中必须出现以激活规则的模式，右侧是当该规则触发时将执行的动作。动作可能包括向输出表添加一行，或随着建模过程的进行向工作内存中声明一个新事实。

事实有两个来源。一是来自你看到的表格输入，这些将使用我展示的带有建模时钟的规则自动声明为事实；二是它们也可以由生产规则右侧的断言产生。

如果你要创建自己的事实，Clips 允许你定义所谓的事实模板（fact template），这可以为你的事实提供结构并进行一些基本类型检查。让我们看一些 Clips 中的规则。我们要看的第一个规则叫做 `found_cause`。

它说的是，如果有一个对象在 t1 时刻玩火柴，并且 App 在 t2 时刻着火，并且 t1 发生在 t2 之前，那么在这个生产规则的右侧，我们可以声明一个新事实，称为 `cause_of_fire`，其属性为引发火灾的对象。这将被输入到工作内存中。

现在我们来看第二个规则，叫做 `record_a_cause`，如果我们有一个在某起始时间着火的 App，并且我们知道着火原因，并且我们有一个绑定到我们追加端的表（即 modeler 的输出侧），并且该表恰好是我们定义的名为 `started_a_fire` 的模式，那么我们就可以在该表中创建一行，然后将时间以及是谁点着了火设置为模式中捕获到的值。这样，我们就用这两个规则创建了我们的第一个专家系统，用于查找 App 中的不良模式。

你可能已经注意到，这些规则前缀是 `modeler` 或 `recorder`。这些在 Clips 中称为模块（modules），它们允许你对规则进行分组，同时控制规则的执行顺序。例如，如果你将所有产生输出表的规则都放在 `recorder` 模块中，那么你可以确保在 `modeler` 的推理过程中不会写入输出，因为 `recorder` 中的任何规则都必须等 `modeler` 中的所有规则执行完毕后才能执行。

我前面提到了逻辑支持。逻辑支持通常与所谓的对等推理规则（peer inference rules）相关联，这些规则说的是，如果 A 和 B 成立，那么 C 成立。对。因此，通过为你的生产规则添加逻辑支持，你是在说，如果 A 和 B 不再存在于工作内存中，那么 C 应该自动被撤销。也就是说，C 在逻辑上由 A 和 B 的存在所支持。这很重要，因为它可以限制工作内存的膨胀，有助于节省资源，同时对于移除不再有效的工作内存中的事实也很重要。如果 A 和 B 不再有效，那么你真的应该移除 C。因此，要为你的生产规则（此处是你的规则）添加逻辑支持，你只需用关键字 `logical` 包裹模式，那么当你断言任何在规则右侧的内容时，它们会在这些事实前进时自动被撤销。你可能会注意到，这两个规则……抱歉，这两个事实的名称来自我们的模式。所以这些是输入，因此当 modeler 的时钟向前移动时，它们将自动被撤销。

好的。谢谢你，Kacper。我们已经看到了如何在 Instruments 中创建一些基本的专家系统。好，现在我们来谈谈我们学到的一些最佳实践。第一点是编写不止一个 Instrument。我不是说练习编写 Instruments。我的意思是，如果你已经拥有一个 Instrument，并且想为其添加一些功能，有时候你会很想直接添加它们，为你的 Instrument 添加额外的图形或详细信息，但你真的应该考虑，这个功能是否可以成为一个独立的 Instrument。原因在于，如果你创建粒度更细的 Instruments，你就给了 Instruments 用户更多的选择。他们可以从库中只拖出他们需要的 Instruments，这将最大限度地减少对目标的录制影响。如果你专注于一个包含许多功能的 Instrument，那有点像是一个“全有或全无”的方案。

现在，如果你想创建一组针对某个特定问题的 Instruments，更确切地说，你希望所有这些 Instruments 同时被一起使用，那么你可以做的是创建你自己的自定义模板，就像我们为联网所做的那样。要开始，创建一个文档，以你想要的方式拖入 Instruments，配置它们，然后前往“文件”并选择“另存为模板”。然后，你可以使用 Kacper 添加到我们联网模板中的元素在你的包内部使用该模板。因此，使用多于一个 Instrument 是更好的使用工具的方式。

第二点是，立即模式（immediate mode）很困难。立即模式指的是 Instruments 的一种录制模式，我们在其中近乎实时地可视化正在传入的数据。说它困难，实际上有两个原因。第一个原因是它需要一些额外的支持，尽管我们今天很想涵盖，但实在做不到。我们就是没有时间。所以我们将会在文档方面继续努力。但第二个原因，也是更重要的原因是，因为它是间隔数据，对吧。间隔在关闭之前不能进入 Analysis Core 的表格，这意味着我们必须同时看到开始和结束。因此，当你实时查看录制时，你有一堆所谓的开放间隔（open intervals）。如果你的 modeler 需要这些作为输入（这完全可行），那么你会注意到，如果上游有一个开放间隔，那么下游所有 modeler 的时钟都必须停止，直到该间隔关闭，因为请记住，modeler 的视野是按时间顺序的。所以在所有上游间隔关闭之前，它不能将时钟向前移动。因此，如果你有一些长时间运行的间隔，你会注意到你的 modeler 的输出似乎停止了。当用户点击“停止录制”按钮时，所有开放间隔都会关闭，一切处理恢复正常，数据也被填充。但这不是一个好的用户体验。所以如果你遇到这种情况，你有两种选择。第一个是将你的 Instrument 选择退出立即模式支持，你可以通过向你的 Instrument 添加 `limitation` 元素来实现；第二个是将间隔数据作为 modeler 的输入移除，就像我们在我们的专家系统演示中所做的那样。我们实际上使用的是 os signpost 点事件，而不是间隔。

我知道我们让它看起来很容易，但立即模式实现起来有点棘手。第三点，如果你创建的 Instruments 要处理大量输入数据，那么最后五秒录制模式是最有效的。切换方式是在跟踪文档的录制选项中，你会看到可以在立即、延迟和最后 N 秒模式之间进行选择。最后 N 秒模式会高效得多，因为它允许录制技术使用缓冲来提高性能，从而不用实时地将数据馈送给 Instruments。这可以产生深远的影响，尤其是在 signpost 数据上，在最后五秒模式下速度可以提高十倍。当然，代价是你只能看到最后五秒的数据，但对于产生大量数据的 Instruments 来说，这通常是件好事。因此，这是 System Trace、Metal System Trace 和 Game Performance 模板的常用模式。如果你正针对这类应用，我建议也把你的 Instrument 设置为不支持立即模式，这样用户就不会获得糟糕的体验，Instruments 也不会因为试图获取数据而严重落后，或者你不会遇到间隔问题。
