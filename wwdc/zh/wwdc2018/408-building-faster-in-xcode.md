现在，Shaders target 生成一个 meta library，本质上是一包将在显卡上运行的 GPU 代码。

我们将看到，这个小小的增量变化实际上对整体构建时间线有巨大而显著的影响。

刚刚移动进来的那个新的绿色方框是我们新的 Code Gen target。我们之所以能把 utilities target 缩小，是因为把那部分工作移到了 Code Gen。

而且由于 Code Gen 没有其他依赖，它可以移动到构建过程的最前端。它还可以与 Physics target——底部的红色方框——并行构建。

最后，由于 Shaders 不再依赖 Utilities，它不必等到 Utilities 和 Physics target 都构建完成。相反，它可以在 Code Gen target 完成后就构建。现在，我要和你谈的最后一种依赖，是我称之为「被遗忘者」的依赖。在我们产品和代码的演进或生命周期过程中，我们倾向于移动代码和删除东西。我们得到的是死代码。同样的事情也会发生在依赖上。有时我们只是忘记清理它们。

在这些情况下，实际上安全地移除那个依赖即可。

这个最后的改动进一步收紧了我们的构建图，允许 Utilities target 在 Code Gen target 之后立即构建，而不是必须等待所有 Physics target 完成。以前在 Xcode 中，当你构建依赖于另一个 target 的 target 时，你必须等待被依赖的 target 完成其整个构建过程。我们在 Xcode 10 中有新功能，允许我们免费为你的构建引入一些并行性。我们通过在依赖的构建阶段中满足我们编译所需的阶段完成后，就立即开始编译你的 target 来实现这一点。

但我现在也有自由把它变得更 Swift 风格。这可读得多、可维护得多。而且它在快速、合理的时间内编译。现在，这个部分的最后一个例子，适用范围不会像前两个那么广。它关于 Any Object 这个类型。

Any Object 是一个方便的类型，描述任何类实例。不是 struct 或 enum。肯定是类。但它还有从 Objective-C 的 ID 类型继承来的额外功能。

那就是方法调用语法。如果你试图在 Any Object 类型的值上调用方法或访问属性，Swift 会允许你这样做，只要该方法在你的项目某处可见并暴露给 Objective-C 运行时。

然而，这确实有代价。

因为编译器不知道你将调用哪个方法，它必须在你的项目和导入的框架中搜索任何可能的实现，并假设它们可能就是将被使用的那个。

它必须这样做，因为如果没有一个匹配，它就需要向你呈现错误。

所以，我们可以做一些更好、更——再次强调——声明我们意图的事情。我们可以定义一个协议。

这可以在同一文件或不同文件中完成，但重要的是，一旦我们把这个 delegate 属性改为使用我们的协议而不是 Any Object，编译器就知道它调用的确切是哪个方法。

现在你也有机会让所有实现类型被检查，确认它们正确实现了该方法。

所以，我们谈到了几种减少编译器在决定重新编译文件后所做工作的技巧。

但如果不重新编译文件呢？是什么让编译器决定文件是否需要重新编译？为此，我们需要理解 Swift 的依赖模型。

现在，Swift 的依赖模型基于文件。这有点棘手，因为 Swift 中没有头文件。我们默认就能看到 target 中某处定义的一切。

在这个例子中，我在左边的文件中声明了一个 struct point。如果我引入右边的文件，编译器知道我引用的是第一个声明。对右边文件中 X 和 Y 属性的使用也是如此。现在，这种基于文件的依赖意味着，如果我修改左边的文件，两个文件都需要重新编译。

这很重要，因为我们要调用这个初始化方法。我们想确保正确地调用它。编译器足够智能，知道当你在函数体内做修改时——在这个例子中是让断言更合适——只有那个文件需要重新编译。

其他文件不必改变它们使用第一个文件 API 的方式。然而，它需要保守。所以如果我给这个文件添加一个单独的类型，人类可以判断这个 path segment struct 不会影响右边的文件。但编译器仍然会保守，重建两者。让我们看看这如何应用到 David 早先使用的 game 示例。

这里我们有 app target 和 Utilities framework。我展示了每个 target 中的一些 Swift 文件。

所以如果我修改 App target 中的文件，我们已经知道那个文件需要重新编译。当然，任何依赖那个文件的东西也需要重新编译。

但 Utilities target 中没有任何东西会被重新编译的机会。

它在单独的 target 中。它有显式依赖。并且在那两组文件之间没有隐式可见性。类似地，如果我修改 framework target 中的某些内容，那么我需要重新编译那个文件以及 Utilities framework 中任何依赖它的其他内容。

然而，这些依赖更粗粒度。所以 Xcode 也会重新编译 Game target 中的一切，除非修改完全局限于函数体。所以回顾这些规则：编译器需要保守。即使人类能判断修改不影响其他文件，编译器不一定能。

然而，编译器确实知道如何处理的一种修改是函数体。它知道这不影响文件的接口。因此不会要求其他文件重新编译。

这种基于每个文件的依赖发生在 module 内部，Swift 声明在那里默认彼此可见。

当你通过 import 或桥接头文件处理跨 module 依赖时，这些是针对整个 target 的依赖。所以这是关于 Swift 依赖和 Swift target 的所有良好信息。但我知道在座许多人都有 Objective-C 和 Swift 混合的 target。所以最后一部分将聚焦于这一点，如何减少混合源码 App 中 Swift 和 Objective-C 代码之间的接口。

对于生成头文件，你最强的工具将是 private 关键字。所以在这个例子中，我有一个在 Swift 中定义的 view controller。它有一个 IBOutlet 属性和一个 IBAction 方法。

再次，唯一的要求是方法暴露给 Objective-C。它实际上不需要被项目中的任何其他文件——Swift 或 Objective-C——使用。所以我可以把它标记为 private。

再次减少生成头文件的大小。在这样的情况下，通常还有另一个选项。那就是切换到基于 block 的 API。

在很多情况下，这甚至能清理你的代码，因为你可以在注册通知的函数中隐式捕获状态，而不是不得不把它作为某种上下文对象携带。现在，减少生成头文件内容的最后一个技巧实际上是一个很老的技巧。你可以迁移到 Swift 4。

你已经听说今年你必须这样做。Xcode 10 将是最后一组支持 Swift 3 模式的发布。

所以，这是你 anyway 会做的事。Edit → Convert → To Current Swift Syntax。

然而，当你做这个迁移时，你可能实际上选择了为特定构建设置保留 Swift 3 兼容模式。那就是 Swift 3 @objc 推断。

这是迁移到 Swift 4 时的一个选项，保留 Swift 3 中的一条规则：在 NSObject 的任何子类上，内部方法和属性会自动暴露给 Objective-C。现在，如果你用 Swift 3 编写，你可能依赖这个功能。但在很多情况下，你实际上并不以任何方式依赖它——无论是运行时还是编译时。

所以，一旦你到了已经显式地把所有 Objective-C 依赖标记为 @objc 或 IBOutlet、IBAction 等（视情况）的那一点，你也可以选择这个构建设置并点击 Delete，把它恢复到默认模式，此时 @objc 属性只会在方法和属性满足协议要求或覆盖来自 Objective-C 的方法时被推断。我们谈了很多关于生成头文件以及你对 Swift 代码能做什么。但你也有 Objective-C 代码。Objective-C 代码同样会导致重建。
