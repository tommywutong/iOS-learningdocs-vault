Swift 使用自动内存管理，并且和 Objective-C 一样，使用引用计数来管理对象实例。

在这张幻灯片里，我用注释标注出了编译器在哪里插入了 retain 和 release。

这就是它在 Swift 4.1 中的行为方式。当一个对象被创建时，会有一个与之关联的 +1 引用计数。当时的约定是：如果这个对象被作为参数传递给另一个函数，那么由那次函数调用来负责释放这个对象。所以基本上，你是把释放它的责任转交给了这次调用。

这带来了一些性能上的机会，可以把某些对象的生命周期缩短到它们最小的使用范围。

不过，代码往往看起来更像这样：你把这个对象多次传递给不同的 API。而由于有这个调用约定，你仍然要经历这样一套流程：最初的引用计数要靠最后一次调用来平衡，但中间的每次调用都被期望要有这些额外的 retain 和 release，因为这就是约定的要求。

这其实很浪费，因为这个对象实际上只会在这整个函数的执行期间内存活。所以在 Swift 4.2 中，我们改变了调用约定，使得释放对象不再是被调用方的义务。这意味着所有这些 retain 和 release 都不再需要了，这大幅减少了 retain / release 的流量。

这带来了两方面的影响。既是代码体积上的胜利，因为那些调用都没有了，也带来了运行时性能上的提升。

我们做的另一个重要优化是针对 string 的。在 Swift 4.2 中，string 现在大小是 16 字节，而之前是 24 字节。我们认为这是在内存占用和性能之间一个很好的权衡。

不过，它仍然大到足以进行一项重要的小字符串优化。如果一个字符串能放进 15 字节以内，那么这个字符串就会被直接表示在 string 类型内部，而不需要跑到堆上分配一个单独的缓冲区来表示这个字符串。这显然也是内存和性能上的双重胜利。这和 string 内部已有的一项优化是类似的。我们实际上可以表示更大的字符串。

而这其实不太好，因为你在向编译器重复你自己已经声明过的东西。所以在 Swift 4.2 中，我们添加了一个新的 CaseIterable 协议，如果你声明遵循这个协议，编译器就会为你合成一个 allCases 属性。好了，这个讲完了，又快又好。接下来我们来看下一项改进，看看如何消除另一种样板代码的来源。这次是当你没办法让你的代码做到足够通用的时候。

在 Swift 4 中，我们有 sequence 上的这个 contains 方法。它要求 sequence 的元素类型是 Equatable 的，这样它才能找到它要找的那个元素。

当然，我可以在一个字符串数组上调用它，因为 string 是 Equatable 的。但如果我在一个数组的数组上调用它呢？

比如一个 Int 数组的数组，这里的元素类型并不是 Equatable 的，这就意味着我只会得到一个编译时错误。

你可能会问，那为什么标准库不干脆让所有数组都变成 Equatable 呢？但那样也说不通，因为如果数组的元素类型本身不是 Equatable 的，比如一个函数，那么这个数组也没法变成 Equatable。

但可以肯定的是，如果数组的元素类型是 Equatable 的，那么我就可以在数组上定义一个相等性操作，只需要逐对比较各个元素就行。

而这正是条件一致性（conditional conformance）让标准库能够做到的事。所以现在，对于元素类型是 Equatable 的情况，数组会获得一个 Equatable 的实现。而在 Swift 4.2 中，我们之前看到的这个例子现在就可以正常运行了。除了数组变成 Equatable 之外，标准库还定义了一系列其他的条件一致性。举例来说，当元素类型是 Equatable 的时候，optional 和 dictionary 现在也是 Equatable 的了，同样的道理也适用于 Hashable、Encodable 和 Decodable 一致性。

这让你可以用以前做不到的方式来组合各种集合。

在 Swift 中有一个常见的模式：我有一个结构体，里面有一堆存储属性，而所有这些存储属性本身都是 Equatable 的。然后我想让这个结构体也变成 Equatable 的，只需要比较两个值的这些属性就行。在 Swift 4 里，之前你得手动把这些都写出来。而这纯粹就是样板代码。如果我给这个结构体加了一个新的存储属性，我就得记得去更新这个 Equatable 的实现，而这很容易出现复制粘贴的错误，或者别的什么失误。所以在 Swift 4.1 中，我们引入了合成相等性实现这个能力。只要你把实现留空，编译器就会替你把它填上，前提是所有那些存储属性本身都是 Equatable 的。

这对 Hashable 同样适用。

现在，也有一些情况下，你确实必须手动实现相等性和哈希运算。我们来看一个这样的例子。

假设我有一个表示一座城市的数据类型，它有一个名字，有它所在的州，还有人口数量。假设为了这个例子的目的，我在判断相等性时只需要比较名字和州，如果我知道这两者相等，我就不需要再检查人口数量了。所以，如果我在这里让编译器合成相等性的实现，它就会做一些不必要的工作，因为它会去比较那个人口字段。

但我当然可以手动把它写出来，而且在这个例子里，可能也不算太糟。

但 Hashable 呢？如果我想计算这个 city 对象的哈希值，那我得先计算 name 的哈希值和 state 的哈希值，然后我得想办法把它们组合起来。可是该怎么组合呢？我可以用一个异或（exclusive or）操作，或者用我在网上找到的某个随机数学公式，又或者自己凭空想一个出来。但这两种做法都不太令人满意，感觉这些哈希组合函数里藏着不少玄乎的东西。而做错的代价相当高，因为你期望从 dictionary 或 set 中获得的性能特性，其实非常依赖于一个高质量的哈希函数。

这里面还有一个安全层面的考量。如果一个攻击者能够精心构造出一批哈希值全都相同的输入，然后想办法通过网络发给你的 App，那可能会把你的 App 拖慢到根本没法用的地步，从而造成一次拒绝服务攻击。所以在 Swift 4.2 中，我们为此添加了一个更好的 API。

回想一下 Swift 4 和 4.1 中的 Hashable 协议。它只有一个单一的 hashValue 要求，产生一个单一的整数值。

在 Swift 4.2 中，我们重新设计了 Hashable 协议，现在有了一个不同的 hash(into:) 要求。它不再是产生单一的哈希码值，hash(into:) 接受一个 Hasher 实例，然后你可以把多个值喂给这个 Hasher，它会把这些值组合成一个哈希码。

所以，回到我们那个 city 数据类型的例子，我们要做的就是实现 hash(into:)，递归地对 name 和 state 分别调用 hash(into:)，把我们拿到的那个 Hasher 对象实例传进去。

而 Hasher 里的哈希组合算法，在哈希码的质量和性能之间做了很好的平衡，而且作为防范拒绝服务攻击的一层额外保护，它使用了一个在你的 App 启动时生成的随机预处理种子。

我们认为，把你的代码迁移到使用新的 Hashable 协议应该相当容易，我们也鼓励你这样做。唯一需要留意的一点是：你可能有一些代码，期望哈希值在你 App 的不同运行之间保持不变，或者期望在遍历一个 dictionary 或 set 时，元素总是以相同的顺序出现。而由于那个随机预处理种子的存在，情况已经不再是这样了。所以你需要修一下你的代码。

为了让这件事更容易做到，我们添加了一个构建设置，也就是 Swift Deterministic Hashing 环境变量，你可以在 scheme editor 里启用它，来临时禁用那个预处理随机种子。好，我们来聊聊生成随机数这件事。

那么，今天你是怎么在 Swift 里生成随机数的呢？你得使用导入进来的 C API。而这其实并不理想，因为它们在不同平台之间是不一样的，名字不同，行为也不同，所以你得用构建配置检查。而且它们还相当底层，这些常见的操作实现起来也不那么直观。

举例来说，如果我想得到一个 1 到 6 之间的随机数，我可能会想到直接调用 Darwin 的 arc4random 函数，然后计算除以 6 的余数。但那样实际上会得到一个在 1 到 6 之间并不均匀分布的结果。

所以在 Swift 4.2 中，我们添加了一整套新的 API，让这类事情变得更容易。

首先，所有数值类型现在都定义了一个 random 方法，它接受一个范围，返回一个在该范围内均匀分布的数字。它使用了正确的算法，甚至对浮点数也同样适用。

对于更高层的代码，我们在 collection 协议上添加了一个 randomElement 方法。而且和 min、max 一样，它返回一个 optional，所以如果你传入一个空集合，你得到的就是 nil。

最后，collection 上还有一个 shuffled 方法，它会给你一个数组，里面是该集合元素的一个随机排列。我们认为，默认的随机数生成器对大多数 App 来说都是不错的选择。但你也可以实现自己的随机数生成器。

我们来"拆开"一下隐式解包可选值（Implicitly Unwrapped Optionals）。这个双关语有点糟糕。好，隐式解包可选值可能会让人有点困惑，我们先来回顾一下理解隐式解包可选值的思维模型。我该怎么理解它们呢？从 Swift 3 开始，它们就不再是某个表达式的类型了。不要把它想成一种类型。相反，把隐式解包可选值想成是一个声明的属性（attribute）。

而当你引用这样一个声明时，编译器会怎么做呢？它首先会尝试把它当作一个普通的可选值来做类型检查，如果这在使用它的上下文中说不通，它就会继续把它解包，然后把它当作底层类型来做类型检查。

我们来看第一种情况的一个例子。

这里我有两个函数，第一个产生一个隐式解包的可选整数，第二个接受任意类型的一个值。我要用第一个函数的结果去调用第二个函数。在这种情况下，我可以把一个可选 Int 存进一个 Any 里，所以不会执行强制解包。这个值就单纯变成了一个普通的可选值。我们现在来看第二种情况的一个例子。

这里，第一个函数现在产生——抱歉，是第二个函数现在接受一个整数。所以当我用第一个函数的结果去调用第二个函数时，我就不能把一个可选 Int 传到一个期望 Int 的地方。所以编译器必须插入一次强制解包，然后一切就都说得通了，因为现在我有的是一个 Int 和另一个 Int。这个思维模型让隐式解包可选值变得非常容易理解。但直到最近，编译器里还有一些边缘情况，并不总是遵循这个模型。回想一下，你不能让一个隐式解包可选值成为另一个类型的一部分。在 Swift 4.2 中依然如此。我不能有一个由隐式解包 Int 组成的数组。

不过，之前在 Swift 4 里，是有一些像这样的边缘情况的。我可以定义一个类型别名，其底层类型是隐式解包的 Int，然后我可以做一个这种类型别名的数组，这样我就会从编译器那里得到非常令人困惑的行为，让代码变得难以理解。所以在 Swift 4.2 中，我们重新实现了隐式解包可选值，让它精确地匹配我前面概述的那个思维模型，而这个之前令人困惑的代码例子，现在会产生一条编译时警告，编译器会把它当作一个普通的、由可选整数组成的整数数组来解析。

现在，大多数代码都不会受到这次隐式解包可选值改动的影响，但如果你之前不小心依赖了这些边缘情况，我建议你去看看 Swift.org 上的这篇博客文章，里面详细讲了这次改动的内容和方式，还有很多例子。好，今天就只剩最后一件事了。我们来聊聊内存独占检查（memory exclusivity checking）。

但我们来看看我们这个 path 数据类型的这种用法。

这里我有一个存在局部变量里的 path，然后我在它上面调用 withAppended，在闭包内部，我又访问了那个局部变量，把它打印出来。那这里的问题是什么呢？其实，这段代码是有歧义的，因为当我在闭包内部访问那个局部变量时，它已经在被这个 withAppended 方法（一个会做变更的方法）修改了。所以这个歧义在于：我指的是我调用 withAppended 之前 path 的原始值，还是指正在被修改的当前值（不管那意味着什么）。

除了改进——好，你同样可以用同样的方法，通过把它作为参数传给闭包，来解决这个歧义。除了改进静态检查之外，我们还添加了在 release 构建中使用运行时独占性检查的能力。这会带来一些开销，但如果你的 App 对性能不是那么敏感，我们鼓励你试一试，并且一直保持开启。将来，我们会把这些动态检查的开销降低到可以一直保持启用的程度，它会像今天的数组越界检查或整数溢出检查一样，给你多一层保护。Swift 4.2 里还有很多今天没有讲到的内容。我们鼓励你在自己现有的 App 上试一试。我们也希望你去试试这些新特性，如果有任何问题，欢迎到 lab 来找我们。谢谢大家。
