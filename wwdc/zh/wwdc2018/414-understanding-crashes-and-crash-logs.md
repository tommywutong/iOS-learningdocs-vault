但是崩溃日志文件包含更多信息，它包含的信息远不止栈回溯（stack trace）。经常查看这些额外信息对于调试你的问题非常有用。

那么这个文件里有什么呢？让我们看看。文件的顶部以一些摘要信息开始，包含你的 App 名称、版本号、运行时的操作系统版本以及崩溃的日期和时间。

在它下面，我们有崩溃的原因。这是具体的错误，是操作系统发送来杀死进程的具体信号。

我们还可以看到一些日志信息，“应用特定信息”部分。在某些情况下，这个部分会包含控制台日志，如果你有一个未捕获的异常（unhandled exception），它可能包含异常回溯（exception backtrace）。

这个部分并非总是可用，在 iOS 设备上，它经常因个人隐私原因而被隐藏。但在模拟器（Simulator）到 macOS 上，这个部分可能包含有用的信息。

在它下面，我们有线程栈（thread stacks），这些是崩溃发生时所有正在运行的线程的回溯（backtraces）。其中一个被标记为崩溃线程，我们还有在进程死亡时正在运行的其他线程。

在它下面，我们有一些底层信息，我们有崩溃线程的寄存器状态，以及加载到进程中的二进制映像。这是 App 的可执行文件和所有其他库。Xcode 使用这些信息进行符号化（symbolication），以便查找符号（symbols）、文件和行号信息，用于栈回溯（stack traces）。这就是崩溃日志文件的内容。

那么我们如何调试它，如何阅读它，我们看什么呢？我们从崩溃原因、异常类型（exception type）开始。

在这个例子中，异常类型是 `EXC_BAD_INSTRUCTION`（错误指令异常），`SIGILL` 信号是非法的指令信号。这意味着 CPU 试图执行一条不存在的、或由于某种原因无效的指令，这就是进程死亡的原因。我们也可以看看崩溃的线程，看看崩溃时正在运行什么代码。这里我们看到了 Swift 运行时的 `fatal error message` 函数。至于 `fatal error message` 函数做什么，就不用猜了。

在这个例子中，错误信息包含在“应用特定信息”中，所以我们可以知道 Swift 运行时在进程退出时打印了什么。

让我们更仔细地看看那个栈回溯（stack trace）。我们看到了 `fatal error message` 函数，它被我们代码中的一个函数调用。我们有一个 `Recipe` 类，一个 `image` 函数被调用，该函数又因为某个错误而调用了 `fatal error message`。

因为这是一个带有完整调试信息的符号化（symbolicated）栈回溯（stack trace），所以我们有崩溃所在代码的文件名和行号。

我们可以看看那一行，我们可以打开我们的项目，这是 `RecipeImage.swift`，第 26 行是崩溃日志中标出的那一行。

你们这些有经验的 Swift 程序员，应该能很好地猜到为什么这行代码会崩溃。

我们有一个强制解包运算符。

我们有一个函数，`UIImage` 构造函数，它返回一个可选值（optional value）。如果可选值为 `nil`，强制解包运算符将中止进程，生成一个崩溃日志并退出。

如果我们还记得“应用特定信息”，其中包含了 Swift 运行时在这个错误检查失败时打印的错误信息，它说“在解包一个可选值时意外发现 nil”。

这很好，这与代码是一致的。我们在第 26 行有一个强制解包运算符，崩溃日志中有一条错误信息，说我们在解包一个可选值。这一切都构成了一个前后一致的解释，说明导致这次崩溃的原因。

所以，强制解包失败是代码中前置条件（precondition）或断言（assertion）的一个例子。前置条件和断言是错误检查，当发生错误时有意地停止进程。

我们刚刚看到的可选值强制解包当然是其中的一个例子。Swift 运行时会断言可选值不为 `nil`，如果为 `nil` 则会崩溃。

越界访问 Swift.Array 是另一个例子。如果你访问一个数组，而索引越界了，Swift 运行时将会失败，中间检查会在前置条件处失败并中止进程。

Swift 算术溢出也包含断言。如果你将两个数字相加，结果对于整型变量来说太大，这里有一个前置条件，进程会中止。未捕获的异常（Uncaught exceptions）通常是由代码中的前置条件引起的。有许多错误检查，如果前置条件失败，它会抛出一个异常，如果异常没有被捕获，这个未捕获的异常将导致一个崩溃日志。当然，你也可以在你自己的代码中编写断言和前置条件，如果你有一些错误，你希望这些错误导致进程崩溃并生成崩溃日志作为响应。

崩溃日志的另一个例子是操作系统从外部杀死你的进程的情况。一个例子是看门狗事件（watchdog events），比如超时。如果你的 App 花了太长时间做某事，操作系统可能会检测到这一点，杀死进程，并在此过程中生成一个特定的崩溃日志。

环境条件也可能导致操作系统中止进程。如果设备过热，操作系统会杀死使用太多 CPU 的进程。如果设备内存不足，操作系统会杀死使用大量内存的进程。

另一种情况是无效的代码签名。操作系统强制要求代码必须签名，如果签名无效或代码未签名，操作系统会杀死进程并生成一种特定类型的崩溃日志。

这些由操作系统导致的终止可以在 Xcode 的“设备窗口”（Devices Window）中找到，也可以在 macOS 的“控制台”（Console）中找到。它们并不总是出现在 Xcode 管理器（Organizer）中，所以要注意这一点。

在 Apple 的开发者文档中，我们有一篇技术说明（technote），描述了像这些特定例子一样的崩溃日志的许多不同特征和结构，它们看起来是什么样子，你如何识别它们，它涵盖的细节比我们今天有时间讲的要多得多。

但是让我们看一个例子，这是另一个崩溃日志文件，同样，为了理解崩溃日志，我们从崩溃原因开始。在这个例子中，崩溃原因是 `EXC_CRASH`（崩溃异常）和 `SIGKILL` 信号。

`SIGKILL` 信号通常用于操作系统想要停止你的进程时。它发送 `SIGKILL` 信号，`SIGKILL` 信号无法被处理，你的进程无法捕获它，进程将在这个信号的作用下死亡。

这个特定的错误值看起来非常像 `malloc` 内存分配器的地址范围，这个范围恰好在这个崩溃日志中可用。所以我们有内存分配器使用的地址范围，而我们的无效地址看起来像是在 `malloc` 范围内，但是它被移位了 4 位，被旋转了 4 位。所以它看起来像一个旋转过的有效 `malloc` 地址。

这是来自内存分配器本身的线索。让我给你们解释一下这是为什么。这是我们对象在仍然有效时的样子。一个对象以一个 `isa` 字段开始，`isa` 字段指向对象的类。Objective-C 对象就是这样布局的，一些 Swift 对象也是这样布局的。那么 `objc_release` 函数做什么呢？它读取 `isa` 字段，然后解引用 `isa` 字段，以便访问类对象并执行方法查找。

当然，通常情况下这是正常工作的，这就是它应该工作的方式。

如果我们的对象已经被释放了，会发生什么？当 `free` 函数删除一个对象时，它会将它插入到其他死亡对象的空闲列表（free list）中。它会将一个空闲列表指针写入到原来 `isa` 字段所在的位置，指向列表中的下一个对象。

有一点小小的变化，它不会向那个字段写入一个指针，它写入一个旋转后的指针。它想确保写入那里的值不是一个有效的内存地址，正是为了让对该对象的错误使用会导致崩溃。

所以当 `objc_release` 去读取 `isa` 字段时，反而得到了一个旋转过的空闲列表指针。当它解引用这个旋转过的空闲列表指针时，它崩溃了。

内存分配器为我们做了这件事，它故意旋转了那个指针，以确保如果我们再次使用它就会崩溃。

这就是我们在崩溃日志中看到的特征。我们的无效地址字段看起来像是 `malloc` 区域中的一个指针，但是以与 `malloc` 旋转其空闲列表指针相同的方式旋转了。所以这是一个强烈的信号，表明无论我们在这段代码中试图释放什么对象，都已经被解分配了，这就是发生的内存错误。

这为我们的故事增加了更多细节。我们的对象正在被解分配，我们正在清理它的实例变量，其中一个实例变量已经是一个被释放的对象，这就是导致我们崩溃的原因。

另一个常见的内存错误症状是“无法识别的选择器异常”（unrecognized selector exception）。

这些通常发生在你有一个某种类型的对象，有代码正在使用该对象，然后该对象被解分配并再次被使用时。

但并不是得到我们之前在崩溃日志中看到的 `malloc` 空闲列表特征，而是在旧对象原来所在的地址上分配了一个新对象。所以当代码试图使用旧对象，在旧对象上调用一个函数时，我们在同一个地址上有一个不同对象、不同类型的对象，它根本不识别那个函数，我们就得到了一个“无法识别的选择器异常”。

内存错误的另一个常见症状是内存分配器（memory allocator）本身内部的 `abort`，即在 `malloc` 和 `free` 函数内部。这是我们之前看到的那个前置条件的一个例子，这是内存分配器内部的一个前置条件。它可能是在识别 `malloc` 内存的堆数据结构已被内存错误破坏的情况，并中止进程作为响应。或者它可能是在检测到对 `malloc` API 的错误使用。例如，如果你连续两次释放同一个对象，`malloc` 分配器有时可以识别出这是一个“双重释放”，并立即中止进程。

那么让我给你们一些关于分析崩溃日志（特别是分析内存错误）的最终建议。

在我们刚刚查看的崩溃中，我们大部分时间都花在查看崩溃的代码上，崩溃的具体代码行，以及崩溃的线程。查看进程中与崩溃代码相关的其他代码也很重要。例如，在这个崩溃中，`ivarDestroyer` 函数没有错，那不是 bug 所在。bug 在别处，是其他一些代码不正确。

你还应该查看崩溃日志中除了崩溃线程之外的栈回溯（stack traces）。崩溃日志包含进程中所有的栈回溯（stack traces），这可以包含有用的信息和线索，帮助你弄清楚进程在做什么。也许其他线程显示了更多关于它在 App 中何处运行的细节，也许它正在执行网络代码，这在其他某个栈回溯（stack trace）中可见。或者可能存在一个多线程错误，其他线程可能提供了关于线程竞争是什么的线索。

你还应该针对一个特定的崩溃原因查看多个崩溃日志。

Xcode 管理器（Organizer）会根据崩溃在代码中的位置，方便地将你的崩溃分组。

有时，在同一个崩溃点会有多个崩溃，但是有些日志包含的信息比其他日志更多。例如，我们刚刚看到的 `malloc` 空闲列表特征可能会出现在某些崩溃日志中，但不会出现在其他日志中。因此，浏览同一崩溃组中的多个崩溃以查看其中一些是否包含更有用的信息是很有用的。

此外，管理器（Organizer）在将崩溃分组时，有时会将不同原因的崩溃放在同一个组中。可能还有其他线程或崩溃线程的回溯（backtrace），它们会向你指出——通过人眼识别——这组崩溃有多个原因，即使 Xcode 管理器把它们放在了一起。如果你只看了其中一个崩溃日志，你可能都不知道第二个崩溃存在，直到你修复了第一个崩溃、发布并开始从你的用户那里收到崩溃日志。

正如 Greg 提到的，一些内存损坏可能由多线程问题引起。

多线程 bug 通常是最难诊断和重现的 bug 类型之一。它们尤其难以重现，因为它们只是偶尔才导致崩溃，所以你的代码可能在 99% 的情况下看起来工作正常。而这些 bug 可能会在很长一段时间内不被注意到。

通常，监控 bug 会导致内存损坏，你在崩溃日志中看到的看起来就像内存损坏，我们在上一节中已经看到了一些例子。所以当你处理 `malloc`、`free` 或引用计数操作内部的崩溃时，这些是内存损坏的典型症状。

多线程 bug 也有特定的症状。

崩溃日志通常包含多个正在执行你代码相关部分的线程。因此，如果一个特定的类或方法在崩溃日志的多个线程中出现，这是潜在多线程 bug 的一个迹象。

由多线程问题引起的内存损坏通常非常随机。所以你可能会看到崩溃发生在略有不同的代码行或略有不同的地址。正如 Greg 提到的，即使它是同一个 bug，你也可以看到这些表现为 Xcode 中不同的崩溃点。

并且，崩溃线程实际上可能不是 bug 的罪魁祸首，因此在崩溃日志中查看其他线程的栈回溯（stack traces）很重要。现在让我们更仔细地看一个多线程 bug 的例子，我将向你们展示如何用一个叫做 Thread Sanitizer 的工具（它是 Xcode 的一部分）来诊断这样的 bug。
