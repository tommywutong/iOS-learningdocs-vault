大家好，欢迎收看。今天我将介绍并解释 Xcode 中构建 Swift 和 Clang 模块的新方式，称为显式构建模块（explicitly built modules）。我会先概述什么是模块，然后解释模块是如何被用来构建你的代码的，接着介绍你在新版 Xcode 中会看到的变化，最后讲解如何通过最大化复用已构建的模块来优化你的构建。

从本质上讲，模块是描述某个库或框架接口的代码分发单元。一个 Swift target 包含多个 Swift 文件，它们共同构成一个模块；一般而言，单个 target 或框架中的所有 Swift 源文件都属于同一个模块。它们所表示的接口在 Swift 中通过访问限定符显式标记。

这个类及其变量被标记为 public，使它们对导入者可见。

模块还可以导入其他模块，为整个项目形成一个无环的模块图。

Swift 编译器会把你编写的外部接口总结为一个文本形式的 .swiftinterface 文件，其中只包含接口。

Objective-C 中的模块则以不同的方式表示。与 Swift 不同，在 C 语言家族中，模块的接口是手工编写的。

我们从大家熟知的概念——头文件——出发，在旁边添加一个称为模块映射（module map）的文件，它描述了这些头文件如何构成一个模块。这是 UIKit 模块的一个例子。我们从 UIKit 的一个头文件开始，然后添加 UIKit 的模块映射。这个模块映射告诉编译器关于 UIKit 模块的几件不同的事情。首先，这是一个框架模块；其次，它的名字是 UIKit。正是这个名字让 @import 得以工作，因为源代码本身并没有定义名字。

然后它声明 UIKit.h 包含了属于该模块的所有头文件，最后它声明该模块所导入的每个模块都可以被导入了 UIKit 的代码使用。

只要你的代码包含对某个命名模块的导入，或者包含属于某个模块的头文件，你就在使用模块。这是一个名为 ResearchKit 的项目。它同时包含使用模块的 Swift 代码和 Objective-C 代码。

我们来看 ResearchKit 的一个 Swift 源文件。它以对 SwiftUI 的导入开始——这是一个 Swift 模块——随后是对 ResearchKit 模块的导入，后者是一个 Clang 模块，在项目本身中用 Objective-C 实现。

另一个标签页中是一个 Objective-C 文件。它包含一些对项目头文件的导入、对 UIKit 的导入，以及一些对 SDK 头文件的 include，Clang 会把这些 include 转换为模块导入。

模块还让编译器能够在不同源文件之间共享对接口的解析。这是通过把每个模块单独编译成一个二进制文件来实现的，编译器在编译项目源码时读取该文件，然后在该模块被引用时导入其公共接口。在 Swift 中，这种编译后的形式表现为 *.swiftmodule 文件；在 Clang 中，它表现为 *.pcm 文件，即预编译模块文件。

但要实现这种复用，这些模块首先需要被发现并编译。这是怎么发生的？当编译器遇到一个导入时，它首先找出该导入引用的是哪个模块，然后获取该模块的编译后表示。当编译器遇到 @import UIKit 时，它首先在 SDK 中找到 UIKit 的模块映射。既然它已经知道 UIKit 模块是什么，接下来它就需要找到 UIKit 的编译后 .pcm 文件——但如果那个文件还不存在呢？这就引出了构建模块的两种高层方式，以及 Xcode 16 的不同之处。第一种是隐式构建模块（implicitly built modules），由编译器之间自行协调来管理模块的构建，而 Xcode 的其他部分并不知道它们的存在。自诞生以来，Swift 和 Clang 就是这样构建模块的。

当一个包含 Swift、C 和 Objective-C 代码的项目使用隐式构建模块时，构建中常常会包含许多长时间运行的任务。每一行代表 Xcode 可以运行构建任务的一条独立执行通道。构建系统启动编译任务，每个独立的编译器会隐式地发现模块，并视情况：如果碰巧先到达，就构建一个模块；否则在过程中加载已经存在的模块。

在时间线视图中，这可能看起来像这样：构建开始处的编译任务比靠近末尾的编译任务耗时更长。

使用隐式构建模块时，你可能遇到一个编译任务在隐式地构建某个模块，而另一个同样需要该模块的任务却被阻塞，等待它被构建完成。

这种情况甚至可能在构建的许多地方同时发生。

Xcode 16 通过显式构建模块改变了这一点：由 Xcode 与编译器协调来发现和构建模块。显式构建模块把构建模块的隐式工作提升为显式的构建系统任务。

为此，Xcode 把每个源文件的编译拆分为三个独立的阶段：扫描、构建模块，最后构建原始代码。

Xcode 首先扫描每个源文件，为整个项目构建一个模块图，甚至跨 target 共享模块。在构建模块图的同时，它还可以开始分派模块编译任务。这些是构建日志中的显式任务，被直接提供了它们所依赖的已编译模块。最后一步是在原始编译任务被修改、加入其所依赖的已编译模块之后执行它们。

对于显式构建模块，时间线视图现在包含显式的扫描任务、模块编译任务和原始的源文件任务，但现在耗时显著减少。

构建系统感知模块带来的一个好处是，它现在可以避免用尚未就绪的任务填满执行通道。相反，它会等待任务所需模块就绪后再运行任务。这让构建系统能够高效地利用可用的执行通道。

这种构建模块的方式有几个好处。首先是构建更可靠。有了暴露给构建系统的精确依赖关系和确定性的构建图，编译器每次都以相同的方式运行，任何构建失败都可以通过单独重新运行失败的任务来复现。其他地方不再维护任何隐式状态。这也意味着纯净构建（clean build）现在会重新构建模块。这也让构建更高效。既然构建系统完全了解模块图，它就可以做出更明智的调度决策，而不是让执行通道被等待模块构建完成的编译任务阻塞。构建系统协调模块构建的另一个好处是，它现在会在 Xcode 中调试时把 Swift 模块传递给调试器。

当一个项目使用隐式构建模块构建时，Xcode 的构建与调试器拥有完全独立的模块图。使用显式构建模块后，调试器现在能够复用已经构建好的模块。这避免了在调试器需要了解 Swift 类型（例如在使用 "p" 或 "po" 求值表达式时）时重新构建模块。

显式构建模块还影响任务在构建日志中的呈现方式。

在 Xcode 16 中，所有 C 和 Objective-C 代码都使用显式构建模块，并且可以为 Swift 启用预览。我将从在项目导航器中选择 ResearchKit 项目开始，为 Swift 启用显式构建模块……

选择 'Build Settings'，然后在过滤框中输入“explicitly built”。

然后我选择 'Explicitly Built Modules' 设置，并将其设为 'Yes'。

既然 Clang 和 Swift 都已启用显式构建模块，我就可以开始一次构建了。

构建日志将包含许多扫描任务。它们针对你项目中的每个源文件各运行一次，并为构建系统生成一个模块导入图。这是一个内置任务，不会派生新进程。这让构建系统可以在被扫描的源文件之间缓存信息。

第二种新任务是编译模块任务。你不会发现这些任务附着在某个特定的项目或 target 上。相反，它们是顶层任务，因为它们可以在 target 之间共享。对于这些任务，构建系统会为每一个派生一个单独的编译器进程。该任务把指定的模块构建成一个已编译的模块文件。这就是在隐式构建模块时发生在正常编译期间、现在被拆分出来的工作。构建模块时遇到的任何诊断信息都会附加在这里，而不是附加到碰巧最先构建该模块的那个源文件上。你可能注意到同一个模块被构建了多次。在这次构建中，UIKit 模块出现了多次，因为不同 target 上的某些构建设置要求构建该模块的不同变体。这次构建有 2 个 Swift 模块变体和 4 个 Clang 模块变体。

仔细观察其中两个，Xcode 显示它们具有不同的哈希值。这个哈希代表了构建该模块变体所需的命令行参数集合。这些标志通常是诸如语言标准、特性宏或 include 路径差异之类的东西。这是你经常会遇到的情况，在隐式构建模块时同样会发生，只是因为模块构建没有暴露在构建系统中而更难察觉。编译器会在扫描期间优化这个参数列表，剔除那些不影响模块构建方式的参数，包括诸如未使用的头文件搜索路径之类的东西。让我们回到 ResearchKit，移除多余的变体。首先，我想收集一些关于我的项目所构建模块的额外信息。

我会清理构建文件夹以重新构建项目中的所有模块，然后使用 Product => Perform Action => Build with Timing Summary 来收集关于构建性能的额外信息。多个模块变体是由不同源文件拥有不兼容的构建设置引起的。例如，一个 C 源文件和一个 Objective-C 源文件解析某些模块的方式差异很大。不必要的模块变体会产生构建必须执行的额外工作。

模块变体的一些常见来源包括：额外的预处理宏、额外的语言模式（例如把单个 C 文件与 Objective-C 混在一起）、语言版本（例如使用 Objective-C 配合较新的 C 版本如 C17），以及禁用自动引用计数。构建完成后，我前往过滤器并输入 'modules report'。

选择 Clang modules report 会显示 UIKit 有 2 个变体，其他许多模块也是如此。

选择 Swift modules report 同样显示有 2 个变体。这两个报告共同解释了我们之前在构建日志中识别出的 UIKit 的 4 个不同变体。为了减少变体数量，我可以检查常导致变体的那些构建设置。我在项目导航器中选择 ResearchKit，然后在过滤框中输入 'macros'，看看是否设置了多余的宏。项目级别没有，于是我接着查看 ResearchKit target 的构建设置。

这个 target 有一个其他 target 上没有的额外 ENABLE_FEATURE 宏。

我选择 'Levels' 模式，以便同时查看项目级别的设置。

我从 target 中移除这个宏，把它上移到 ResearchKit 项目。

我选择 'Product'、'Clean Build Folder'，然后再次选择 'Build with Timing Summary'。

这一次，构建日志只显示 3 个 UIKit 变体。一个用于 Objective-C，两个用于 Swift。一个用于 Clang 模块，一个用于 Swift 模块。

通过统一项目设置，我们能够把这些各自独立的图合并为一个。一般而言，你应当把构建设置尽可能合理地放到更宽的层面上。与其在 target 级别设置语言标准，不如把它上移到项目或工作区级别。这样，模块就能尽可能地在源文件之间共享。以上就是显式构建模块。

从本次演讲中需要记住的要点是：显式构建模块让构建系统掌控模块构建。你的构建日志现在会呈现不同的样子，模块构建所花的编译时间现在会显示为独立的任务，而不是被并入编译任务；你还可以通过让设置在整个项目中保持统一来减少被构建的模块变体数量，让为某个源文件构建的模块能够跨 target 共享。感谢观看。
