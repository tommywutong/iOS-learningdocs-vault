我也想在我的 DisplayBoard 容器中支持灵活组合。为此，我需要改变实现。第一步是重构我的容器，以便它只能用视图构建器初始化。我从用单个通用视图属性替换现有数据驱动属性开始。

通过添加 ViewBuilder 属性，我的默认初始化器会自动用尾随视图构建器闭包构造内容。接下来，我需要更新视图 body 以使用新内容视图。我可以借助新 API ForEach(subviewOf:) 来做。这个新 ForEach 初始化器接受单个视图值作为输入，并把它的每个子视图传回尾随视图构建器，允许把它们转换成不同类型的视图，如我的卡片视图。有了这个新实现，我现在可以把前面的歌曲想法 List……

并把相同内容包裹在 DisplayBoard 中，把每个 Text 视图转换成板上的卡片。

这是个大改进，但理解它是如何工作的很重要。回到我的实现，我将深入这个新 API。ForEach(subviewOf:)：子视图到底是什么？子视图只是包含在另一个视图中的视图。检查内容，有多少子视图？嗯，像所有伟大问题的答案一样，视情况而定！只考虑代码中的顶层视图，有四个。三个 Text 视图和 ForEach 视图。但 ForEach 不只是单个视图，它代表从数据生成的视图集合。

在本例中，它解析为九个子视图，Sam 最喜欢的每首歌一个。意味着这个 DisplayBoard 的内容实际上解析为总共十二个不同的子视图。这在板上显示的十二张卡片中很明显。

这也与 List 中相同内容显示十二个独立行一致。

理解这两种不同子视图之间的区别很重要。

DisplayBoard 代码中的四个子视图（橙色高亮）被称为声明的子视图。而屏幕上会出现的视图（蓝色高亮）被称为解析的子视图。这些包括我手动定义的三个 Text 视图，以及 ForEach 生成的九个 Text 视图。

在 SwiftUI 的声明式系统中，声明的子视图定义在 SwiftUI App 运行时产生解析子视图的配方。

例如，ForEach 视图是声明子视图，本身没有特定视觉外观或行为。相反，ForEach 视图的全部目的是产生解析子视图集合。

Group 视图是另一个内置容器示例，代表解析子视图集合。例如，三个 Text 视图的 Group 会解析为恰好三个对应的子视图。

某些声明子视图甚至可能根本不产生解析子视图，如 EmptyView。或条件性地解析为不同数量的子视图，如 if 语句的不同分支。

新的 ForEach(subviewOf:) API 只迭代内容的解析子视图。这使我的容器能支持任何可能的内容组合，甚至更少代码，因为 SwiftUI 会为我解析子视图，无论这些子视图在代码中如何声明。

支持灵活组合，让向板添加新歌曲变得极其容易。除了 Sam 的歌曲，Sommer 也慷慨推荐了几首她最喜欢的歌曲，我可以使用另一个 ForEach 视图添加。这无需在我的容器实现中做任何额外更改。然而，添加新想法变得如此容易，现在看到所有卡片变得压倒性。为修复，我将按比例缩小卡片大小，当板太拥挤时。我想当板上添加超过 15 张卡片时缩小卡片。要计数卡片数量，我可以使用另一个新 API。它叫 Group(subviewsOf:)，我可以把它包裹在实现中的 ForEach 周围。与之前的 ForEach(subviewOf:) API 一样，这个视图接受视图作为输入并解析其子视图。

但不是一次迭代一个，Group(subviewsOf:) API 传回所有解析子视图的集合。

我可以使用集合上的 count 属性检查卡片总数，当超过 15 张时配置 CardView 使用更小缩放。

重新运行 App 时，更小的尺寸防止卡片过度重叠。这对阅读卡片有帮助，但我的板仍感觉有点无组织。所以接下来，我将通过添加 section 支持来清理。

List 是支持 section 的内置容器示例，使用 SwiftUI 的 Section 视图。Section 视图行为很像 Group 视图，但带有额外的 section 特定元数据，如可选的页眉和页脚。对于我的展示板，我的目标是为每个人最喜欢的歌曲创建单独 section。然而，自定义容器默认不支持 section，因此我需要做额外工作来启用它们。

这里是我在脑海中设计的粗略草图，把板分成每个 section 的垂直列，页眉出现在顶部。

在实现中，我从把现有卡片布局代码分解到自己的视图开始。

我将重用这个视图在每个独立 section 内布局卡片。

它叫 ForEach(sectionOf:)。这与 ForEach(subviewOf:) 类似，接受视图实例作为输入。

但这个版本迭代它在视图中检测到的每个 section，把 section 配置传入其视图构建器。每个 section 有 content 视图属性，我可以传给前面创建的辅助视图来布局卡片。

为了额外润色，我将给每个 section 添加自定义背景，以帮助视觉区分。

再次运行 App，我可以看到卡片比之前更有组织，每个 section 在自己的列中布局。现在我将添加显示 section 页眉的支持。

在我的展示板中，我希望支持修改卡片，以便我决定不选某首歌时把它划掉。有一个新 API 用于构建这类容器特定修饰符，叫做 container values。Container values 是一种新的键控存储，类似于 Environment 和 Preferences 等概念。

但与传递给整个视图层级的 environment values 不同。或 Preferences，把值向上传递给每个包含视图。解析子视图的 container values 只能被其直接容器访问，使它们成为实现容器特定自定义选项的完美工具。

在我的展示板中，我将使用 container values 创建自定义视图修饰符来划掉卡片。定义新 container value 只需要几行代码。

首先，我创建 ContainerValues 类型的扩展，这是 SwiftUI 中的新类型。

在我的扩展内，我将用新 Entry 宏声明属性，存储布尔值以跟踪卡片是否被拒绝。

Entry 宏是新 API，为 SwiftUI 键控存储类型（包括 environment values、focus values 等）添加新值提供便捷语法。

接下来，我声明自定义视图修饰符作为设置属性的便利，它调用新的 containerValue() API 修饰符，传递属性的 key path 和要设置的新值。

现在我将在容器内添加对我新 container value 的支持。在我的 section 实现中，我需要根据其内容是否被拒绝来自定义每个卡片视图。我可以使用新的 containerValues 属性做到。Container values 可以从解析子视图和 section 读取。
