我叫 John McCall，今天我们要一起探索 Swift 性能。

当你在一门编程语言里工作得足够多时，对这门语言里不同操作的性能有良好的直觉就非常重要。来自 C 的程序员往往具备这种直觉。不管好坏，C 到机器码的翻译相当直白。

像这样的局部变量会分配在栈上。

只有在发起调用时才会发生堆分配。编译器可能仍然会把东西挪到寄存器里、优化内存，找出各种其他聪明的办法让代码更快。但对于代码大致是怎么编译的，总有一条你可以信赖的基准线。

Swift 就不总是这么简单了。部分原因和安全性有关，C 那种直白的翻译，如果你的代码写错了，会很乐意在内存上到处乱写。但 Swift 也提供了很多 C 没有的抽象工具，比如闭包、泛型等等。这些抽象都有非平凡的实现，其成本不像显式调用 malloc 那样直观可见。但这不意味着你没法对你的代码实际运行方式培养出类似的直觉。而这一点，在你需要做性能相关工作时至关重要。所以在这场演讲里，我们要探索 Swift 的底层性能。

首先，我们会讨论我们所说的"性能"到底是什么意思。接下来，我们会讨论在看底层性能时，你应该考虑的一些原则。最后，我们会探讨 Swift 里一些关键特性的实现细节，以及它们对性能的影响。

那么，我们所说的性能是什么意思呢？这是个相当深的问题。如果你能直接把你的程序丢给某个工具，让它吐出一个单一的数字，那这个数字就是我们需要知道的关于性能的一切，那该多好。也许 Safari 的性能得分是 9.2。可惜，事情不是这么运作的。性能是多维度、依情况而定的。通常，我们关心性能，是因为某个宏观问题。我们的守护进程耗电太多，或者我们的 UI 点起来感觉别扭地慢，或者我们的 App 一直被系统强制终止（jetsam）。

当你在调查这些问题时，你通常是自上而下地工作。你用 Instruments 之类的工具做测量，它会告诉你该往哪里深入排查。

很多时候，你会靠算法层面的改进来解决这些问题，根本不需要深入到代码的底层性能。

但有时候你确实需要深入到底层性能。也许你已经把调查范围缩小到执行轨迹里的某一个部分，在算法层面已经没什么可做的了。它就是显得很慢。要进一步排查，就需要理解你的代码实际是怎么运行的，而这需要一种更自下而上的方法。底层性能往往由这四个方面主导：第一，我们做了很多没有被有效优化的调用。第二，因为数据的表示方式，我们浪费了大量时间或内存。第三，我们在内存分配上花了太多时间；或者第四，我们在不必要的值拷贝和销毁上花了大量时间。Swift 里的大多数特性都会对这些成本中的一个或多个产生影响。我会把这些都讲到，不过先让我补充最后一个考虑因素。Swift 有一个强大的优化器。有些东西你永远不会把它们当作性能问题，因为编译器很擅长把它们消除掉。优化是有限度的。你写代码的方式，会对优化器能做多少事情产生显著影响。所以在讲解的过程中，我也会谈到优化潜力，因为这是为性能编程时很重要的一部分。如果你不太放心依赖优化器，我给你一个建议。当性能是你项目里重要的一部分时，你需要经常性地监控它。所以，当你在自上而下的调查中找到热点时，试着找到测量它们的办法，然后把这些测量自动化，作为你开发流程的一部分。一旦你这么做了，你就能很好地识别性能衰退，不管这是因为你不小心把优化器搞糊涂了，还是仅仅因为你不小心加了个平方复杂度的算法。而且，你现在也是在验证优化器仍然在按你的要求做事。

说了这么多，让我们深入到底层性能的这四个原则中。第一个是函数调用。

函数调用有四项相关成本。其中三项是我们要做的事。首先，我们得为这次调用准备好参数。

我们还得解析出我们要调用的函数的地址。

而且我们得为函数的局部状态分配空间。

第四项是我们不做的事：这整件事可能会在调用方和被调用函数两边都抑制优化。

所以，四项成本。

我们先来看参数传递。这个成本分两个层次。在最底层，当我们发起调用时，我们得把参数放到调用约定要求的正确位置。在现代处理器上，这些成本通常会被寄存器重命名机制掩盖，所以在实践中影响不大。

不过在更高层次上，编译器可能得添加值的拷贝，来匹配函数的所有权约定。这在性能画像（profile）里经常表现为调用一侧或另一侧多出来的 retain 和 release。我几分钟后会回来讲这个。

接下来的两项成本，函数解析和优化影响，最终都归结到同一个问题：我们在编译时是否确切知道我们在调用哪个函数？如果知道，我们就说这次调用用的是静态派发；否则，就是动态派发。静态派发效率更高，在处理器层面稍快一些，但更重要的是，如果编译器能看到函数定义，编译时就有很多优化的可能，比如内联和泛型特化。但动态派发才使得多态和其他强大的抽象工具成为可能。

在 Swift 里，只有特定种类的调用会用动态派发，而且你可以通过查看你调用的那个声明来判断。

在这个例子里，我在一个协议类型的值上调用了 update。这是哪种调用，取决于这个方法是在哪里声明的。

如果它是在协议主体里声明的，那它就是一个协议要求，对它的调用会用动态派发。

但如果它是在一个协议扩展里声明的，这次调用会用静态派发。这是一个非常重要的区别，无论在语义上还是在性能上都是如此。

函数调用的最后一项成本，是为局部状态分配内存。为了运行，这个函数需要一些内存。它是一个普通的同步函数，所以它会在 C 栈上分配这块内存。在 C 栈上分配空间，只需从栈指针里减去相应的数值就可以了。

如果你编译这段代码，你会得到在函数开始和结束时操作栈指针的汇编代码。

当我们进入这个函数时，栈指针指向 C 栈内部。我们先从栈指针里减去某个数值，在我们的汇编代码里，我们能看到这是 208 字节。这就分配出了传统上称为 CallFrame（调用帧）的东西，为函数的执行提供了空间。现在我们可以运行函数体了。

在返回之前，我们会把 208 字节加回栈指针，释放掉之前分配的内存。

你可以把 CallFrame 想象成有着类似 C struct 的布局。理想情况下，函数的所有局部状态都会变成 CallFrame 里的字段。我说把东西放进 CallFrame 是理想做法的原因是，编译器总是会在函数开始时发出那条减法指令。它必须这么做，才能腾出空间保存返回地址之类的关键信息。减去一个更大的常数并不会花更长时间，所以如果我们在函数里需要内存，把它当作 CallFrame 的一部分来分配，几乎就是免费的。

这就很自然地引出了我们要看的下一个底层原则：内存分配。

传统上，我们认为内存有三种。当然，对计算机来说，它们最终都来自同一个 RAM 池；但我们的程序会以不同的模式分配和使用它们。而这一点对操作系统来说很重要，也因此对性能很重要。

全局内存是在程序加载时分配和初始化的。这不是完全免费的，但已经很接近了。全局内存最大的缺点是，它只适用于特定的模式：固定数量的内存，而且要在程序的整个生命周期内一直存活。这和全局变量、静态成员变量很契合，但对其他大多数东西就不太适合了。

我们已经讲过 CallFrame，作为栈分配的一个例子。和全局内存一样，栈内存非常便宜，但它只适用于特定的模式。在这种情况下，内存必须是有作用域的：当前函数里必须存在这样一个点，在这个点上我们能保证不会再有对这块内存的使用。

这和一个典型的局部变量很契合。

最后一种内存是堆。堆内存非常灵活：你可以在任意时刻分配它，并在之后的任意时刻释放它。

正是这种灵活性，让分配和释放的成本大大高于另外两种内存。

堆被用于一些显而易见的场景，比如 class 实例，但它也被用于一些静态生命周期约束不够强、没法用别的方式处理的特性上。

通常，当我们分配堆内存时，这块内存最终会拥有共享所有权，也就是说，我们对同一块内存有多个相互独立的引用。Swift 用引用计数来管理这些分配的生命周期。

在 Swift 里，我们把递增引用计数叫作 retain，把递减引用计数叫作 release。

既然我们已经讲了内存分配，我想讲讲 Swift 是怎么用这些内存来存储值的。我们把这称为内存布局。

在大多数关于 Swift 的讨论中，当我们谈到值的时候，我们通常谈的是一个高层概念，而不管内存里具体存了什么、存在哪里。

举个例子，在这次初始化之后，我们可能会说这个变量的值是一个由两个 double 组成的数组。

当我们需要谈论东西在内存里长什么样的时候，有些人仍然会用"值"这个词。在这场演讲里，这样说会造成混淆，所以我会改用一个更专业的词：表示（representation）。一个值的表示，指的是它在内存里是怎么排布的。变量 array 是一段内存的名字，这段内存持有一个指向缓冲区对象的引用，而这个缓冲区目前被初始化为两个 double 值的表示。

我还会用"内联表示"（inline representation）这个说法，专指不需要经过任何指针就能拿到的那部分表示。所以，我们变量 array 的内联表示就是一个缓冲区引用，不管这个缓冲区里实际装的是什么。标准库里的 MemoryLayout 类型度量的正是内联表示。所以对 array 来说，它就是 8 字节——一个 64 位指针的大小。

好，Swift 里的每一个值都属于某个容纳它的上下文（context）。

局部作用域包含它内部使用的所有值：局部变量、中间结果，等等。struct 和 class 包含它们所有的存储属性。Array 和 Dictionary 通过它们的缓冲区包含它们所有的元素，等等。

Swift 里的每一个值也都有一个类型。

值的类型决定了这个值在内存里是怎么表示的，包括它的内联表示。而值所在的上下文，决定了用来容纳这个内联表示的内存来自哪里。

那让我们看看这在我们的例子里是什么样子。我们的 array 是一个局部变量。所以我们有一个 array 值，被一个局部作用域容纳着。

局部作用域会尽可能把内联表示放进函数的 CallFrame 里。在这里是可行的，所以在这个 CallFrame 的某个地方，有一块空间用来存放一个 Array of Double 的内联表示。

一个 Array of Double 的内联表示是什么样的呢？Array 是一个 struct，而一个 struct 的内联表示，就是它所有存储属性的内联表示。如果你看标准库的源码，这一点可能有点不好看出来，但我剧透一下：说到底，Array 只有一个存储属性，而且它是一个 class 引用。一个 class 引用其实就是一个指向对象的指针。

所以，实际上，我们的 CallFrame 里存的就是那个指针。

在 Swift 里，struct、tuple 和 enum 都使用内联存储：它们包含的所有东西都内联布局在它们的容器里，通常是按声明的顺序。

class 和 actor 使用外联存储（out-of-line storage）：它们包含的所有东西都内联布局在一个对象里，而容器只存一个指向那个对象的指针。这个区别对性能有重大影响。为了解释这一点，我需要讲讲我们最后一个底层原则：值拷贝。现在，Swift 里有一个基本概念叫所有权（ownership）。对一个值拥有所有权，意味着要负责管理这个值的表示。

我们刚看到，Array 的内联表示是一个指向缓冲区对象的引用。这样的引用是用引用计数来管理的。当我们说一个容器拥有某个 Array 值的所有权时，意思是存在这样一个不变量：底层的 array 缓冲区，作为把这个值存进容器的一部分，已经被 retain 了。而这个容器就要负责最终用一次 release 来平衡那次 retain。

至少，在这个例子里——容器是一个局部作用域——当这个容器消失时，这件事就必须发生：当变量离开作用域时，这个对象就会被 release。

在 Swift 里，对一个值或变量的任何使用，都会以某种方式和这个所有权系统发生交互；这是内存安全的一个关键部分。所有权交互主要有三种：一个值可以被消耗（consumed）、可以被改变（mutated），或者可以被借用（borrowed）。

消耗一个值，意味着把它表示的所有权从一个地方转移到另一个地方。自然而然需要消耗一个值的最重要操作，就是把这个值赋值进内存。

现在，在我们的例子里就发生了这种情况：初始化一个变量，要求我们把初始值的所有权转移到这个变量里。

有时候我们可以不做任何拷贝就完成这件事。在这个例子里，变量的初始值是一个数组字面量，它天然就会产生一个全新的、独立的值。Swift 可以直接把那个值的所有权转移到这个变量里。

如果我们用第一个变量的值来初始化第二个变量，我们同样需要把一个值的所有权转移到新变量里。

但这次，初始值表达式并不会天然地产生一个新值：它只是引用了一个既有的变量。我们不能直接把值从那个变量里"偷"过来，因为可能还有其他地方在用它。

为了得到一个独立的值，我们必须拷贝旧变量当前的值。因为这个值是一个数组，拷贝它就意味着 retain 它的缓冲区。

不过，这是一个经常被优化的地方。如果编译器能看出原变量之后不会再被用到，它就应该能在这里直接转移这个值，而不需要拷贝。

你也可以用 consume 运算符显式地请求这么做。如果你在这个点显式消耗之后还想使用这个变量，Swift 会报错，告诉你那里已经没有值了。

使用一个值的第二种方式是改变（mutation）。改变一个值，意味着暂时取得存储在某个可变变量里的当前值的所有权。和消耗的关键区别在于，这个变量之后仍然期望拥有这个值的所有权。

当你像这样调用一个 mutating 方法时，你是把变量里当前值的所有权转移给了这个方法。在这次调用期间，Swift 会阻止你以任何其他方式同时使用这个变量。

当这个方法执行完毕时，它会把新值的所有权转移回这个变量。这就维持了"变量拥有其值的所有权"这一不变量。

使用值的最后一种方式是借用它们。借用一个值，意味着断言没有其他人可以消耗或改变它。当你只是想读取一个值的时候，这自然就是你想做的事。你唯一关心的，是没有别人在你不知情的情况下改变或销毁那个值。

传递一个参数是通常应该只是借用的最常见场景之一。如果我把我的 array 传给 print，理想情况下，这应该只是把信息传递过去，而不做任何额外的工作。然而，在某些情况下，Swift 需要防御性地拷贝参数，而不是借用它们。为了借用一个值，Swift 必须证明没有同时存在改变或消耗它的尝试。在这个简单的例子里，它应该能可靠地做到这一点。在更复杂的例子里，它有时候会力不从心。举个例子，当存储在一个 class 的属性里时，Swift 就很难证明这个属性没有被同时修改，所以它可能就得添加一次防御性拷贝。

这是 Swift 正在积极改进的一个领域，一方面在改进优化器，另一方面也在增加新特性，让你可以显式地借用值，从而避免拷贝。

拷贝一个值实际上意味着什么呢？这取决于这个值的内联表示。拷贝一个值，意味着拷贝它的内联表示，从而得到一个拥有独立所有权的新内联表示。

这意味着，拷贝一个 class 值，就是拷贝这个引用的所有权，也就是 retain 它所指向的对象。拷贝一个 struct 值，则是递归地拷贝这个 struct 的所有存储属性。

这意味着，在内联存储和外联存储之间做选择，涉及一些实实在在的权衡。内联存储避免了在堆上分配内存，对于小类型来说，这非常棒。对于更大的类型，如果你发现自己做了大量拷贝，拷贝的成本会明显拖累性能。这里没有一条放之四海而皆准的规则来获得最佳性能。

拷贝大型 struct 的成本分两部分。首先，当我们拷贝值类型时，我们往往不只是在拷贝比特位。这三个存储属性都是用对象引用表示的，当我们拷贝外层 struct 时，它们都得被 retain。所以，如果我们把这个改成 class，拷贝它就得对这个 class 对象做一次 retain。但把它拷贝成 struct，实际上仍然要对这几个独立字段做三次 retain。

而且，这个值的每一份拷贝，都需要为所有这些存储属性准备自己的存储空间。所以，如果我们预期会大量拷贝这个值，我们最终可能会用掉多得多的内存。如果这个类型改用外联存储，每一份拷贝都会指向同一个对象，内存就能被复用了。同样，没有硬性规则，但这是你应该考虑的事情。

在 Swift 里，我们鼓励你写具有值语义的类型，也就是说，一个值的拷贝，其行为就好像和它被拷贝的来源完全无关。

struct 就是这样的行为，但它总是用内联存储。class 类型用外联存储，但它们天然具有引用语义。

一种既能获得外联存储、又能获得值语义的办法，是把 class 包在一个 struct 里，然后使用写时复制。标准库在 Swift 所有基础数据结构里都用了这种技巧，比如 Array、Dictionary 和 String。

我们花了不少时间讲这四条基本原则。作为其中的一部分，我们也看到了它们是怎么转化成一些基础 Swift 特性的，比如 struct、class 和函数。现在让我们把它们结合起来，聊聊 Swift 里的一些高层特性。我们先从动态大小类型开始。C 里的 struct 总是常量大小的，但 Swift 类型的大小可以在运行时才确定。这在两种情况下会出现。

首先，SDK 里的很多值类型都保留了在未来的操作系统更新中添加和修改其存储属性的权利，其中就包括 Foundation 的 URL 这样的类型。

这意味着，关于它们布局的一切，都必须在编译时被当作未知的。

其次，泛型类型的类型参数通常可以被替换成任何具有任意可能表示的类型，所以我们同样必须把它的布局当作未知的。

不过，第二条规则有一个例外：当类型参数被约束为一个 class 时。在这种情况下，我们知道它必然具有 class 类型的表示，也就是说，永远是一个指针。如果你能接受这个约束，即使泛型替换没有发生，这也能带来效率高得多的代码。

好，那当编译器在静态上不知道一个类型的表示时，Swift 是怎么处理内存布局和分配的呢？这取决于是什么样的容器在存储这个值。对于大多数容器，Swift 可以直接在运行时做布局。举个例子，这个 Connection struct 包含一个 URL。因为 URL 的布局在静态上是未知的，Connection 的布局也就没法在静态上确定了。但这没关系，这就变成了容纳这个 Connection 的那个东西的问题。

编译器知道 Connection 的静态布局，一直到遇到第一个动态大小的属性为止。布局剩下的部分，会在这个程序第一次需要这个类型的布局时，由 Swift 运行时动态填充。

如果 URL 最终是 24 字节，那 Connection 在运行时的布局，就会和编译器在静态知道这一点的情况下所做的布局完全一样。编译器只是得动态地加载大小和偏移量，而不是能用常量。

然而，有些容器必须具有恒定大小。在这些情况下，编译器必须为这个值单独分配内存，和容器的主分配分开。

举个例子，编译器只能请求恒定数量的全局内存。如果你创建一个 URL 这样类型的全局变量，编译器会创建一个指针类型的全局变量。当你第一次访问这个全局变量、作为惰性运行其初始化器的一部分时，Swift 也会惰性地在堆上为它分配空间。

局部变量也会发生类似的事情，因为 CallFrame 同样必须具有恒定大小。

这个 CallFrame 只是包含一个指向 URL 的指针。当这个变量进入作用域时，函数就得动态地分配它，然后在它离开作用域时释放它。

不过，因为局部变量是有作用域的，这次分配仍然可以在 C 栈上完成。当我们进入函数时，我们照常分配 CallFrame。

当变量进入作用域时，我们只需再从栈指针里为这个变量的大小减去相应的数值。

当变量离开作用域时，我们可以把栈指针重置回之前的值。

到目前为止，我们只讲了同步函数。那异步函数呢？异步函数的核心理念是，C 线程是一种宝贵的资源，仅仅为了阻塞而占着一个 C 线程，并不是在善用这个资源。因此，异步函数以两种特殊方式实现：第一，它们把自己的局部状态保存在一个和 C 栈分开的独立栈上；第二，它们在运行时实际上会被拆分成多个函数。

那么，让我们看一个异步函数的例子。

这个函数里有一个潜在的挂起点：await。

所有这些局部函数的使用都跨越了那个挂起点，所以它们没法保存在 C 栈上。

我们刚讲过同步函数是怎么通过从栈指针减去数值、在 C 栈上分配它们局部内存的。

异步函数在概念上以同样的方式工作，只是它们不是从一整块连续的栈里分配内存。

相反，异步任务持有一个或多个内存"薄片"（slab）。

当一个异步函数想在异步栈上分配内存时，它会向任务申请内存。栈会尝试从当前的 slab 里满足这个请求，如果可以，那就太好了。

任务会把 slab 里的那部分标记为已使用，然后交给这个函数。

不过，如果这个 slab 大部分都已被占用，这次分配可能就放不下了。

这时任务就得用 malloc 分配一个新的 slab。

这次分配就从那里出来。

不管是哪种情况，释放都只是把内存交还给任务，让它被标记为未使用。

因为这个分配器只被单个任务使用，并且采用了栈式的管理方式，它通常比 malloc 快得多。整体的性能画像和同步函数类似，只是调用的开销略高一点。

现在，为了真正能运行，一个异步函数必须被拆分成多个"部分函数"，这些部分函数跨越了函数各个潜在挂起点之间的间隔。在这个例子里，因为函数里有一个 await，我们最终得到两个部分函数。

第一个部分函数从原函数的入口开始。如果这个数组是空的，它就直接返回给异步调用者。否则，它会取出第一个任务并 await 它。

另一个部分函数从那次 await 之后接着执行。首先，它把刚 await 的那个任务的结果加到输出数组里，然后尝试继续这个循环。如果没有更多任务了，它就返回给异步调用者。否则，它会循环回去，await 下一个任务。

这里的关键点在于，C 栈上最多只会有一个部分函数。

我们进入一个部分函数，像一个普通的 C 函数一样运行，直到下一个潜在的挂起点。如果这个部分函数需要一些不需要跨越挂起点的局部状态，它可以把这些状态分配到它自己的 C CallFrame 里。

到了那个点，这个部分函数会尾调用下一个部分函数。它的 CallFrame 会从 C 栈上消失，然后为下一个部分函数分配帧。

然后那个部分函数运行，直到它到达一个潜在的挂起点。

如果一个任务真的需要挂起，它只需在 C 栈上正常返回，这通常会直接进入并发运行时，这样这个线程就能立刻被挪去做别的事情。

在我目前的例子里，我一直展示的是 func 声明。那闭包是怎么运作的呢？它们对局部分配有什么影响？闭包总是作为函数类型的值传来传去的。这个函数接收一个非逃逸函数作为参数。

在 Swift 里，函数值总是一对：一个函数指针和一个上下文指针。所以，用 C 的说法，这个函数签名大概长这样。

在 Swift 里对一个函数值发起调用，其实就是调用那个函数指针，并把上下文指针作为一个隐式的额外参数传进去。

一个从外层作用域捕获值的闭包表达式，必须把这些值打包进上下文里。这具体是怎么运作的，取决于它要生成的函数值的种类。

因此，这个上下文就只是一个包含被捕获值的简单结构体。

这个上下文可以分配在栈上，它的地址会被传给 sumTwice。

对于逃逸闭包来说，情况就不一样了。我们不再能确定这个闭包只会在这次调用期间被使用。因此，这个上下文对象必须在堆上分配，并用 retain 和 release 来管理。

这个上下文本质上表现得就像一个匿名 Swift class 的实例。

在 Swift 里，当你在闭包里引用一个局部 var 时，你是按引用捕获这个变量的。这让你能对这个变量做出的改动，在原来的作用域里被观察到，反过来也一样。

如果这个 var 只被非逃逸闭包捕获，这不会改变这个变量的生命周期。因此，闭包可以只捕获一个指向这个变量所在内存的指针来处理这件事。

但如果这个 var 被一个逃逸闭包捕获，这个 var 的生命周期就可能被延长，只要这个闭包还存活。

因此，这个 var 也必须在堆上分配，而这个闭包上下文必须持有一个指向那个对象的引用。

在像这样的泛型函数里，类型表和见证表变成了隐藏的额外参数。这个签名在运行时对应的一切，都能直接和原始 Swift 签名里的东西对应上。

当我们处理协议类型的值时，情况就不一样了。在这个例子里，我们让这个函数更灵活了，数组里的每个元素现在都可以是不同类型的数据模型。但这在运行效率上是有权衡的。

一个像 AnyDataModel 这样的协议的内联表示，用 C 表示大概长这样。我们有用来存这个值的存储空间，还有用来记录这个值的类型、以及我们已知它具备的任何一致性的字段。

但这必须是一个固定大小的类型，它的表示不能因为要支持不同种类的数据模型而改变大小。不管我们把值的存储空间做得多大，总有可能存在一个数据模型放不进去。那我们该怎么办呢？Swift 用了一个任意选定的、3 个指针大小的缓冲区。如果协议类型里存的值能放进那个缓冲区，Swift 就会把它内联地放在那里。否则，它就在堆上为这个值分配空间，然后只在缓冲区里存那个指针。

所以，这两个函数签名看起来很相似，但它们的特性其实非常不同。

第一个函数接收的是一个由同类数据模型组成的数组。这些数据模型会被紧密地打包在这个数组里。类型信息只会作为单独的顶层参数，传给这个函数一次。

如果调用者知道它是用什么类型调用的，这个函数也可以被特化。这里我们是在一个已知类型的数组上调用它。优化器可以轻松地要么内联这次调用，要么生成一个专门针对这个具体参数类型的函数版本。这就消除了泛型带来的任何抽象成本，让这次 update 调用直接进到它在 MyDataModel 的一致性里的实现。

第二个函数接收的是一个由不同类型数据模型组成的异构数组。这更灵活，如果你有不同类型的数据模型，这可能正是你需要的。但现在数组的每个元素都有自己的动态类型，这些值在数组里也不会被紧密地打包。

在实践中优化这一点也要困难得多；编译器得完美地推理出数据是怎么流入这个数组、又是怎么在这个函数里被使用的。这并不会彻底毁掉你的性能，但这确实意味着，在这个地方，你从编译器那里得到的帮助会少得多。而在这场演讲快结束的时候，这正是我想留给大家的一点。请不要从这场演讲里带走这样的想法："John 告诉我们不要用协议类型。"我在这场演讲里提到的每一项成本，就只是成本本身：它是一种代价，而有时候，这种代价是值得付出的。因为抽象是一个强大而有用的工具，你应该好好利用它。我希望这场演讲里的信息，能帮你为你的 Swift 代码的性能培养出一种直觉。感谢观看！
