Swift 宣布的第二年，它被开源，并在 Linux 上可用。我们还为语言和标准库引入了社区驱动的演进流程。

2016 年，我们随 Swift 3 一起引入了 Swift Package Manager。

这是第一个使用新演进流程的语言版本，包含超过 80 个语言提案。

如果你和我们经历过从 Swift 2 到 3 的迁移，你可能记得那是充满挑战的。我们从那次经历中吸取教训，在 Swift 4 中我们找到了如何引入新的语言模式而无需所有 Swift 代码同时迁移的方法。同一个编译器可以支持多种语言模式，所以你可以在同一程序中自由混合编译为 Swift 3 和 Swift 4 的模块。这种新方法使得在整个生态系统中增量采用新的语言模式成为可能，以便每个开发者都能在准备好时迁移。

2018 年带来了泛型系统的改进，比如条件一致性，今天我们把它们视为 Swift 的理所当然。

这也为我们最重要的发布之一铺平了道路：在 Swift 5 中，我们引入了 Apple 平台上的稳定 ABI。对于 App 开发者，这意味着更小的下载大小，因为你不再需要在 App 中捆绑 Swift 标准库的完整副本。相反，Swift 标准库成为 OS 本身的一部分，针对该 OS 优化，并在所有 Swift App 和框架之间共享。

这代表了根本性的转变，因为现在我们可以使用 Swift 的全部表达能力来构建更好、更安全的 API 和框架。我们确实这样做了，随着 SwiftUI 的引入，它利用 Swift 的独特特性来更好地、更快地构建 UI App。

到 2020 年，Swift 来到了更多平台，社区到 Windows 的移植在 swift.org 上正式可用。

我们引入了一个关键特性：并发模型，包含 async/await、Actor 和结构化并发。次年，我们引入了分布式 Actor，使构建网络服务更容易。我们还继续完善并发模型。

同年，社区发布了 VSCode 的 Swift 扩展，为 Swift 开发提供跨平台编辑体验。

去年，我们引入了与 C++ 的双向互操作性。这使得把 Swift 的安全性和表达性带入改进大型跨平台 C++ 代码库变得更容易。

我们还引入了宏，帮助减少重复的样板代码，并启用了新一代更富表现力的 API，如 SwiftData。

这 brings 我们来到 Swift 6。Swift 6 改进了可移植性、性能和整体开发者体验。它还引入了 Swift 6 语言模式，提供数据争用安全保证，帮助你编写正确的并发程序。

我们将介绍 Swift 项目的一些关键成就和新投资。我们还将看看 Swift 可用的一些新地方。我们还将讨论一些新的语言特性，包括新的语言模式 Swift 6。Swift 编程语言是更大生态系统的一部分，包含工具、包和包括你在内的充满活力的社区。让我们谈谈社区如何演进。最初，Swift 核心团队是唯一的指导小组，负责语言演进流程以及更多。

随着社区的发展，过去几年我们扩展了指导小组和工作组的数量。今年，我们引入了平台指导小组，专注于把 Swift 带到更多地方。此外，Swift 核心团队还积极致力于创建新的生态系统指导小组，专注于开发者体验和更广泛的生态系统。为了继续底层环境的势头，Swift 核心团队还致力于引入新的 Embedded 工作组。我们欢迎你加入 Swift 社区，并在 swift.org/community 探索不同的指导小组和工作组。swift.org 是 Swift 项目的主页。网站工作组对主页和入门指南进行了重大改进。这些指南现在包含各种新教程，包括跨平台库和 Web 服务，帮助你探索 Swift 中的不同技术。

Swift 继续作为跨平台语言增长，因为它被移植到越来越多的平台。Swift 在 Apple 平台、Linux 和 Windows 上得到官方支持。此外，还有许多由 Swift 社区带来的平台，包括 WebAssembly。

现在让我们深入探讨 Swift 中的一些关键库。

Foundation 是许多应用程序的重要组成部分，提供包括 JSON 解码、日期和时间格式化、文件系统操作等重要 API。它也是我们最长寿的框架之一，历史可追溯到 macOS X 的开端。

当 Swift 开源时，我们知道这个 API 在所有平台上都会很有用。所以，我们引入了 swift-corelibs-foundation 项目。从那时起，语言已经演进，使我们现在可以在所有平台上使用单一的统一实现。这就是为什么我们把 Foundation 从旧的 C 和 Objective-C 重写为现代的、可移植的 Swift。

结果更加一致，质量更高，性能更好。新特性和改进会同时来到所有支持的平台，就像 Swift 本身一样。这个 Swift 实现去年秋天首先在 iOS 和 macOS 发布。甚至 Objective-C 应用程序也获得了这些改进的好处。更好的是，swift-foundation 是开源的。我们邀请社区贡献，并有一个开放的演进流程来添加新 API。

例如，Predicate 是一个 API，现在通过 swift-foundation 在 Swift 6 中在所有平台上可用。

今年，它还获得了对正则表达式的支持。

我们对 Foundation 的新方向感到兴奋，包括它的新实现和与社区的密切互动。

让我们谈谈一个新框架，Swift Testing。它易于上手、表达力强、灵活且可扩展。它利用现代 Swift 特性如宏，并与并发无缝集成。该包在开源中开发，考虑跨平台。它设计为与多个 IDE 如 Xcode 和 VSCode 无缝集成。

Swift Testing 库的愿景是成为生态系统的官方默认测试解决方案，你可以在 Swift 演进愿景文档中阅读完整的 API 方向。让我们探索 Swift Testing 的一些特性。

要声明一个测试，你向函数添加 Test 属性。你可以提供自定义显示名称，作为 Test 属性的参数。这可以帮助更容易理解测试在做什么。你可以使用 expect 来验证结果是否满足，它是一个宏，所以你可以编写简单或复杂的 Swift 表达式。

Swift Testing 允许你使用标签来组织和过滤测试。你可以使用参数来避免为多个输入重复相同的测试。这只是突出 Swift Testing 的一些特性。如果你想了解更多信息，请查看"Meet Swift Testing"和"Go further with Swift Testing"。

在测试代码之前，你需要构建它，所以我们改进了 Xcode 构建代码的方式。

当你构建 Swift 代码时，每个模块都依赖其他模块，通常是 SDK 中的。

当 Swift 编译器遇到像 SwiftUI 这样的模块时，它可能需要构建该模块的二进制版本。

这隐式地发生，所以你可能除了偶尔的 slowdown 之外甚至不会注意到它。然而，它隐藏了很多工作，因为它必须构建所有使用的模块，包括用 Objective-C 或 C++ 编写的，按顺序。

当另一个 Swift 模块被构建时，它会重用相同的二进制模块，但它可能必须等待它们准备就绪，这意味着我们没有从构建中获得我们想要的那么多并行性。

此外，调试器可能必须构建所有这些模块文件自己的版本。这可能导致在调试器中首次打印变量时长时间暂停。

显式构建模块把这些隐式步骤变成显式构建步骤。

这意味着模块构建可以并行执行，并且它们会在构建日志中清晰显示。

结果导致更可预测和可靠的构建。

调试器现在可以与构建共享二进制模块，从而加快调试。

显式模块构建可以在 Xcode 构建设置中启用。要了解更多信息，请参见"Demystify explicitly built modules"。

在过去的 10 年里，Swift 成长了很多。它交了新朋友，经历了独特的经历，现在是时候它搬进自己的空间了。Swift 将移动到 github.com/swiftlang 上的新组织。并将由 Swift 项目管理。这将包括 Swift 编译器、Foundation 和许多更多 Swift 生态系统包。我们很快将开始迁移，详情将发布在 swift.org。我们很高兴看到 Swift 在它的新空间中增长。

同时，Swift 6 有许多新改进，使 Swift 更好。让我们从谈论不可复制类型开始。所有 Swift 类型，无论是值类型还是引用类型，默认都是可复制的。不可复制类型抑制这种默认的可复制性。使它们适用于你想表达唯一所有权的场景。例如，一个唯一的系统资源如文件可以表示为带有析构器的不可复制结构体，析构器会自动关闭它。这种表示防止运行时问题，如多个写入者写入同一文件。它还防止资源泄漏，没有自动清理的话很容易引入。

然而，这种表示仍然不理想。初始化器接受一个打开的文件描述符。这是不直观的，也不安全。

你可能在打开文件和初始化之间引入一些代码，终止程序，析构器永远没有机会运行，导致资源泄漏。我们可以用一个可失败的初始化器来修复，它接受文件名，打开文件，并在文件名有效时完成初始化。

这个初始化器返回可选的不可复制文件类型；可选值是标准库中的泛型类型。Swift 5.10 对不可复制类型的支持仅限于具体类型。

Swift 6 引入了对所有泛型上下文中的不可复制类型的支持，以及标准库的关键泛型类型如可选值。有了这个，你现在可以编写不可复制类型如文件类型的可失败初始化器。

这种强大能力，能够泛型地抽象可复制和不可复制类型，扩展了不可复制类型的可用性。要了解更多信息，请查看"Consume noncopyable types in Swift"。除了表达唯一所有权，不可复制类型还让你对性能进行细粒度控制。在资源严重受限的底层系统中，复制可能变得代价高昂，不可复制类型在那里也适用。

底层系统在内存、存储和运行时能力上受限。由于它们的低占用，C 和 C++ 一直是这类系统编程的主要选择。现在，你可以使用 Swift。

Embedded Swift 是 Swift 的一个新的语言子集和编译模型，可以生成极其小的独立二进制文件，适用于高度受限的系统。它关闭需要运行时支持的某些语言特性，如反射和 any 类型，并使用编译器技术如完全泛型特化和静态链接来生成合适的二进制文件。

尽管关闭了一些语言特性，Embedded Swift 子集感觉非常接近"完整"Swift，并使继续编写惯用、易读的 Swift 代码变得容易。

配备 Embedded Swift，用 Swift 编写的 games 现在可以在像 Playdate 这样的紧凑游戏机上运行。二进制大小只有几 KB 的游戏！但 Embedded Swift 不仅仅是乐趣和游戏。它可以用于构建工业应用的多种 ARM 和 RISC-V 微控制器。

Apple 安全隔区处理器使用 Embedded Swift。安全隔区是与主处理器隔离的子系统。专门用于保护敏感数据安全。

这类系统中安全性至关重要，Embedded Swift 把 Swift 的安全保证带入其中。配备 Swift 与 C 和 C++ 的互操作性，你可以在嵌入式项目中增量采用 Swift。要了解更多信息，请查看"Go small with Embedded Swift"。

去年，我们引入了与 C++ 的双向互操作性。Swift 可以直接与 C++ 互操作，提供无缝的开发者体验和零桥接成本。我们继续扩展可互操作的语言特性，随着 Swift 6，C++ 虚方法、默认参数、仅移动类型和关键的 C++ 标准库类型可以直接导入 Swift。互操作性涉及映射类似的语言概念并进行必要的调整以匹配语义。C++ 虚方法和默认参数被映射到它们等价的 Swift 版本。C++ 仅移动类型如 Person 类型被映射到 Swift 中的不可复制类型。

Swift 编译器在需要时插入对 C++ 移动构造函数的调用。如果你无意中尝试复制不可复制的值，Swift 编译器会为你诊断。C++ 是一种广泛使用的编程语言，但其缺乏安全保证使其容易受到安全攻击。你可以在 C++ 项目中增量采用 Swift，并改善你的安全性和生产力。在 Mac 上，Finder 现在使用 C++ 互操作性。Browser Company 使用它在 Windows 上启动他们的 ARC 浏览器。Swift Godot 使用它为 Godot 游戏引擎提供 Swift 绑定。

C++ 是一种大语言，与它的互操作性是一个不断演进的故事，前往 swift.org 保持更新。

要了解 C++ 互操作性的更多信息，请观看去年的"Mix Swift and C++"。

Swift 有对抛出、传播和捕获错误的一流错误处理支持，当你的代码遇到异常条件时。错误符合 error 协议，你可以用 throws 关键字编写抛出函数。

抛出的错误是类型擦除的，在 catch 处理器中以 any Error 类型出现。由于类型擦除丢失了错误的具体类型信息，你可能必须插入动态类型检查，在你想要详尽处理错误的罕见情况下。类型擦除还涉及装箱和拆箱。在没有运行时分配能力的高度受限系统中，这构成挑战。Swift 6 引入了 typed throws 来克服这个问题。Typed throws 让你可以在 throws 关键字旁边指定错误类型。没有类型擦除，错误以具体类型出现在 catch 块中。

Typed throws 是我们拥有的错误处理系统的泛化。Untyped throws 与 typed throws 使用 any Error 类型相同。非抛出函数与 typed throw Never 类型的函数相同。typed throws 引入的这种形式，让你能够以泛型方式处理错误类型。例如，map 函数接受一个可能抛出的闭包，并将闭包映射到其元素上。

有了 typed throws，map 函数可以泛型地写在 Failure 类型上，抽象抛出和非抛出两种情况。这避免了代码重复并指定了精确的 API 契约。

由于 typed throws 在 API 契约中指定了失败类型，它限制了 API 的演进。

如果你想保持更改抛出错误类型的灵活性，继续使用 untyped throws。

在使用内部函数、传播其参数错误的函数、或在受限环境中 untyped throws 代价高昂时，使用 typed throws。

除了 typed throws 和我们讨论的其他更新，Swift 6 编译器还有若干其他语言改进，以及性能和健壮性的底层改进。除此之外，Swift 6 编译器还有一个新的 Swift 6 语言模式，默认实现数据争用安全。

数据争用是编写并发程序时常见的编程错误。当多个线程共享数据且其中一个尝试修改它时，可能发生。数据争用可能导致意外的运行时行为、程序崩溃和难以复现的问题。自创建以来，数据争用安全一直是 Swift 并发的主要目标，我们一直在向其逐步推进。

Swift 并发围绕实现数据隔离的机制设计，Actor 用于保护可变状态，Sendable 用于安全数据共享。Swift 5.10 在 complete concurrency checking 标志下实现了数据争用安全。

新引入的 Swift 6 语言模式默认实现数据争用安全。把 App 中的所有数据争用问题变成编译时错误。大幅改善 App 的安全性并减少 Crunch-time 调试冒险。

由于你可能需要对代码进行调整以适应新的语言模式，你可以在准备好时采用它。你可以按模块采用它，甚至与可能已迁移或未迁移到 Swift 6 语言模式的依赖项互操作。数据争用安全是启用 Swift 6 语言模式唯一治理的更新。所有其他更新在你更新到 Swift 6 编译器时默认可用。

我们还显著改进了数据争用检查。为了确保安全，Swift 5.10 的 complete concurrency checking 禁止所有非 Sendable 值跨越 Actor 隔离边界传递。Swift 6 可以识别在它们不再能从原始隔离边界引用的场景中，传递非 Sendable 值是安全的。例如，把 non-Sendable 的 client 引用从 MainActor 传递到 ClientStore actor，在 Swift 5.10 的 complete concurrency checking 下会产生编译器警告。

然而，client 引用在被发送到 ClientStore actor 之后不再被 MainActor 引用。由于 client 的状态在 MainActor 和 ClientStore actor 之间没有共享，不可能有数据争用。随着 Swift 6 中数据争用检查的改进，这能成功编译。

如果你在把 client 引用传递给 ClientStoreActor 之后引入一个 client 引用，编译器会报错以指示数据争用。

除了 Actor 提供的高层同步模型，Swift 6 包含一些新的底层原语。

Synchronization 模块引入了 Atomics。它们对任何在平台上提供高效无锁实现的类型都是泛型的。Atomic 值应始终存储在 "let" 属性中以进行安全的并发访问。

对 atomics 的所有操作都是显式的，带有类似于 C 和 C++ 内存模型的内存排序参数。

Synchronization 模块还引入了 Mutex。与 atomics 一样，mutex 应该存储在 let 属性中，并可以安全地并发访问。

对由 mutex 保护的存储的所有访问都通过传递给 withLock 方法的闭包，确保互斥访问。
