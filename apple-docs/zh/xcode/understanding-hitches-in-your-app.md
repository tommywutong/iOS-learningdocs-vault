# 了解你的 App 中的卡顿

<sub>文章</sub>

通过检查渲染循环来确定动作中断的原因。

## 概述

人类的感知对动作中断非常敏感。当屏幕上流畅的动作短暂地_卡住_时，即使只有几毫秒也可能被察觉到。这种类型的中断被称为_卡顿（hitch）_。卡顿发生在持续交互（比如滚动或拖动）期间，或动画期间。每一次卡顿都会影响用户体验，因此你希望 App 中的卡顿越少越好。尽可能降低卡顿率，为用户提供最佳体验。

Xcode Organizer 中的「卡顿」指标会追踪 App 中所有动画交互（不仅仅是滚动）中的动画中断情况。「卡顿」指标以每秒暂停的毫秒数（ms/s）衡量 App 中每种动画类型的卡顿率。卡顿率在 10 ms/s 或以下为良好；在 25 ms/s 或以下为警告；在 50 ms/s 或以下为严重；超过 50 ms/s 则需要立即关注。使用「卡顿」指标来识别并优先处理你界面各个部分中与卡顿相关的衰退。

> [!note] 注意
> 本文假定你已经基本了解事件处理和渲染循环，也基本了解挂起（hang）和卡顿（hitch）以及它们之间的区别。如果你不熟悉挂起和卡顿，请参阅[了解用户界面的响应能力](understanding-user-interface-responsiveness.md)，了解有关它们以及事件处理和渲染循环的更多信息。

当显示屏没有按预期节奏更新时，就会发生动作中断。当下一帧还没有准备好显示时，显示屏就无法及时更新，因此这一帧就会延迟。

由于帧延迟导致的延误通常会导致系统跳过一个或多个后续帧，这也是这种行为被称为_掉帧_的原因。不过，掉帧只是系统用来从延迟帧中恢复的一种可能应对方式，并非每一次卡顿都会导致掉帧。

当一帧延迟时，通常是因为渲染循环中的某个环节出现了延误。这些延误是主线程中出现延迟的结果，最常发生在提交阶段，称为_提交卡顿_，或者发生在渲染阶段的延迟，称为_渲染卡顿_。

> [!tip] 提示
> 卡顿与挂起有关，因为无响应的主线程可能同时导致这两种情况。主线程上长时间运行的工作会导致提交卡顿还是挂起，取决于该主线程工作与哪种用户交互重合。挂起检测工具可以检测到主线程长时间无响应的所有情况，因此它们也能检测到提交卡顿的主要来源之一。如果你修复了正在调查的 App 区域中的所有挂起，你很可能也会同时消除许多卡顿。有关挂起的更多信息，请参阅[了解你的 App 中的挂起](understanding-hangs-in-your-app.md)。

> [!note] 注意
> 「卡顿」检测工具不适用于 visionOS，Xcode Organizer 中的卡顿指标也不适用于 tvOS 或 visionOS。对于 visionOS App，请使用 Instruments 中的 RealityKit Trace 模板来分析渲染性能和掉帧情况。有关更多信息，请参阅[分析你的 visionOS App 的性能](../visionos/analyzing-the-performance-of-your-visionos-app.md)。

### 了解渲染循环

主线程一次只处理一个事件，而渲染循环则分多个阶段准备一帧画面。尽管每个阶段一次只处理一帧，但所有阶段会并行处理多个帧。每个阶段都有一个紧迫的截止时间，需要将其帧交给下一个阶段，以确保它能为屏幕刷新做好准备。

以 120 Hz 刷新率更新的显示屏每秒更新 120 次，即每 8.3 毫秒更新一次。这意味着 App 需要每 8.3 毫秒更新一次界面，并每 8.3 毫秒渲染一帧新画面。默认情况下，每个阶段随后也有最多 8.3 毫秒的时间来完成其工作。

即使只是几毫秒的额外延迟，也可能导致某个阶段错过其截止时间。尽管渲染服务器是一个独立的进程，但它是代表 App 执行工作的，而这项工作可能过于复杂，无法及时完成。要发现并理解卡顿，你需要同时查看主线程上的工作_以及_渲染服务器上的工作。

### 了解显示刷新间隔及相关截止时间

Apple 设备以固定但可变的刷新率更新其显示屏。在用户交互期间，显示屏以设备支持的最高刷新率更新。当没有新内容要显示时，某些显示屏会降低刷新率。显示屏更新的那个时间点称为_垂直同步_或 _vsync_。每当发生 vsync 时，新的一帧就需要准备就绪，以便显示驱动程序开始更新显示屏的像素。

因此，对于每一帧，渲染循环都会以未来某个特定的 vsync 为目标来显示新的一帧，这称为_呈现时间_。然后它会从这个时间点向前逆推计算出中间的截止时间。渲染循环以多个阶段运行，每个阶段都有各自的截止时间，从你 App 主线程上的界面更新开始。

![](../../../attachments/0c5a775387e36772da93963f7de027d7/understanding-hitches-in-your-app-2@2x.png)

<sub>由两个水平色块和三条竖直虚线组成的时间线示意图，三条虚线分别标为「开始时间」「提交截止时间」和「呈现时间」。第一个水平色块标为「主线程工作」，位于「开始时间」线和「提交截止时间」线之间，它包含两个较小的色块，分别标为「事件处理 + 界面更新」和「CA 提交」。第二个水平色块标为「渲染服务器」，位于「提交截止时间」线和「呈现时间」线之间，它包含两个较小的色块，分别标为 CPU 和 GPU。</sub>

你 App 的主线程处理事件并计算出新的界面更新。界面框架收集界面的所有更改，并将新状态发送给渲染服务器，这一过程称为 _Core Animation 提交_。与离散交互中的挂起不同——在离散交互中，只有主线程上 100 毫秒或更长的延迟才会变得明显——人们对流畅动作中的中断要敏感得多。即使只是几毫秒的延迟，也可能导致主线程的工作错过提交截止时间，从而造成明显的卡顿。

在提交截止时间之后，渲染服务器立即开始工作，将你 App 的界面表示转换为要在屏幕上显示的位图。渲染服务器分两步完成这项工作：

1. 在 CPU 上，预先计算它需要渲染的工作。
2. 在 GPU 上，执行实际的渲染工作，并将新的一帧渲染到渲染缓冲区中。

渲染服务器完成渲染后，在下一个 vsync 间隔期间，显示驱动程序会从准备好的渲染缓冲区中读取数据，并使用这些信息来更新屏幕。

在这个过程中有三个重要的时间点：呈现时间、提交截止时间和开始时间。这些时间通常（但不总是）与底层显示屏的 vsync 对齐，也就是说呈现时间位于某个 vsync，提交截止时间是它之前的一个 vsync，而开始时间则是提交截止时间之前的一个 vsync。

- **呈现时间** — 这是给定帧计划出现在屏幕上的时间。错过这个时间意味着该帧必须等到下一个 vsync，显示驱动程序才能将其换入屏幕，导致该帧延迟出现在屏幕上。
- **提交截止时间** — 这是提交需要完成的时间，以便渲染服务器有足够的时间为呈现时间渲染出这一帧。为了最大化它能花在一帧上的时间，渲染服务器会在提交截止时间之后立即开始渲染。如果 App 错过了提交截止时间，渲染服务器会在下一个提交截止时间（通常是下一个 vsync）开始渲染，该帧就会再次延迟。
- **开始时间** — 这是 App 能为给定帧提交界面更新的最早时间。更早提交会干扰前一帧的界面更新。通常，给定帧 B 的开始时间就是前一帧 A 的提交截止时间。

尽管渲染服务器在提交截止时间之后立即开始工作，显示驱动程序也随着 vsync 开始更新显示屏，但其他工作不一定与这些时间对齐。渲染服务器的工作可能在呈现时间之前就已完成，在这种情况下，它会等到下一个提交截止时间才开始处理下一帧的工作。

根据平台的不同，主线程上的工作可能与开始时间或提交截止时间对齐，也可能不对齐。为了减少输入延迟，系统可能会在事件到达后立即处理它们，具体取决于渲染模式、输入设备和平台。或者，系统也可能会保留事件，仅在开始时间才将其交付给 App 的主线程，以最大化 App 在下一个提交截止时间之前为下一帧计算界面更新所拥有的时间。无论一帧的工作实际何时开始，开始时间都是系统能为该帧开始工作的最早时间。

尽管 App 本身一次只处理一帧，但渲染循环的各个阶段可以并行进行。因此，当显示屏正在显示某一帧、渲染服务器正在渲染下一帧时，App 可以开始处理再下一帧的工作。

尽管开始时间和提交截止时间通常与 vsync 对齐，但情况并非总是如此。例如，对于可变刷新率的显示屏，刷新率可能会在你 App 运行期间发生变化，导致这些时间与显示屏更新不同步。设备也可能切换到低延迟模式，在这种模式下，渲染服务器处理一帧所花的时间少于一个 vsync 间隔，因此 App 会尝试尽快处理事件，以最小化用户输入和屏幕更新之间的延迟，比如在绘图类 App 中。

> [!note] 注意
> 在大多数情况下，开始时间和提交截止时间会与 vsync 对齐，因此本文中的示意图展示的就是这种情形。不过，如果它们不一致，或者如果你打算基于这些时间进行计算，请使用相关 API 的开始时间、提交截止时间和呈现时间，而不是 vsync。

### 了解帧生命周期和卡顿时长

大多数 Apple 设备以双缓冲模式运行，也就是说渲染服务器和显示驱动程序共享两个缓冲区。显示驱动程序使用其中一个缓冲区读取屏幕的像素值，渲染服务器使用另一个缓冲区渲染要显示的下一帧。当 vsync 发生时，渲染服务器和显示驱动程序会交换缓冲区。因此显示驱动程序使用新渲染好的缓冲区来更新屏幕，而渲染服务器则将新的一帧渲染到显示驱动程序用于上一帧的那个缓冲区中。

由于显示驱动程序更新屏幕上所有像素可能需要长达一个 vsync 间隔的时间，从触发显示更新到屏幕上最后一个像素更新之间的时间是三个 vsync 间隔——一个在主线程上，一个在渲染服务器上，一个在显示驱动程序上。不过，App 的主线程和渲染服务器各自只有一个 vsync 间隔来完成各自的工作。单个 vsync 间隔在 60 Hz 刷新率下可以短至 16.7 毫秒（1 秒/60），在 120 Hz 刷新率下可以短至 8.3 毫秒（1 秒/120）。这意味着在双缓冲模式下，从 App 开始处理屏幕更新到屏幕实际更新之间的延迟，在 60 Hz 下是 50 毫秒，在 120 Hz 下是 25 毫秒，但每一帧实际只在屏幕上停留这段时间的三分之一。

_预期帧生命周期_是开始时间和呈现时间之间的时间，也就是 App 和渲染服务器处理这一帧所拥有的时间。_实际帧生命周期_从开始时间开始，到将该帧换入显示屏的那个 vsync 结束。这两种帧生命周期都不包括显示驱动程序更新屏幕所花的时间。正因如此，尽管 App 开始工作到屏幕上最后一个像素更新之间的预期延迟是三个 vsync 间隔，预期帧生命周期只衡量前两个间隔。

当一切正常运行时，预期帧生命周期和实际帧生命周期是相同的。当实际帧生命周期比预期帧生命周期更长时，新的一帧无法及时出现在屏幕上，因此前一帧必须比预期停留在屏幕上更长时间，卡顿就此发生。实际帧生命周期与预期帧生命周期之间的差值称为_卡顿时长_，也就是该帧延迟的时间量。因此在下图中，卡顿时长为一个 vsync 间隔，在 60 Hz 刷新率下为 16.7 毫秒。

根据各种情况，渲染也可以以三缓冲模式进行。三缓冲模式的工作方式与双缓冲模式类似，不同之处在于，在任意时刻，渲染服务器可能会并行处理接下来的两帧，并可能为此使用两个独立的缓冲区，而显示驱动程序则在屏幕上显示第三帧。

<sub>标题为「渲染流水线——三缓冲模式」的时间线示意图，由五列三行组成。三条竖直虚线分别标为「开始时间」「提交截止时间」和「呈现时间」，构成第一列的左右边界，以及第三列的右边界。第一行标为 App，第二行标为渲染服务器，分为两个子行，第三行标为显示屏。在三行下方，一条标为「帧生命周期」的水平线横跨第一列和第三列，从「开始时间」线延伸到「呈现时间」线。第一列的宽度标为 vsync 间隔。时间线下方的图例有四个条目，分别是 App：你的 App 代码，CA：Core Animation 提交，CPU：CPU 上的渲染工作，GPU：GPU 上的渲染工作。第一行在第一列中包含两个标为 App 和 CA 的绿色矩形，第二列中有两个标为 App 和 CA 的橙色矩形，第三、四、五列为空白。第一子行在第一列中有一个标为 GPU 的蓝色矩形，第二列中有一个标为 CPU 的绿色矩形，随后是一个标为 GPU、延伸进入第三列的绿色矩形，第四、五列为空白。第二子行在第一列中有一个标为 CPU 的灰色矩形，随后是一个延伸进入第二列、标为 GPU 的灰色矩形，第三列中有一个标为 CPU 的橙色矩形，随后是一个延伸进入第四列、标为 GPU 的橙色矩形，第五列为空白。第三行在每一列中都有一个横跨该列宽度的水平矩形。该水平矩形在第一列中为红色，第二列为蓝色，第三列为紫色，第四列为绿色，第五列为橙色。每个水平矩形中都有一个带虚线轮廓、标为「更新」的较小矩形。</sub>

在三缓冲模式下，App 仍需要在单个 vsync 间隔内完成所有工作，但渲染服务器有两个 vsync 间隔来完成其工作，并可以并行处理两帧。在这种模式下，一帧的开始时间与呈现时间之间的延迟——即预期帧生命周期——为三个 vsync 间隔，在 120 Hz 下为 25 毫秒，在 60 Hz 下为 50 毫秒。相应地，App 开始处理一帧到屏幕上最后一个像素更新之间的延迟为四个 vsync 间隔，在 120 Hz 下为 33.3 毫秒，在 60 Hz 下为 66.7 毫秒。尽管这个延迟比双缓冲模式下更长，但没有一帧会比预期延迟出现。显示屏以预期刷新率更新，并在每个 vsync 都显示新的一帧，从而在屏幕上实现流畅的动作。

### 了解提交卡顿和渲染卡顿

更新屏幕的工作由两部分组成——App 进程执行的工作和渲染服务器执行的工作。由于每一块工作都有各自的截止时间，你可以区分不同类型的卡顿。在上面的「提交卡顿」示意图中，App 进程没有赶上提交截止时间，导致渲染服务器延迟一个 vsync 才开始，从而造成卡顿。由于 App 进程要为这次卡顿负责——Core Animation 提交没有在该 vsync 之前完成——这被称为_提交卡顿_。

尽管显示驱动程序从渲染缓冲区更新屏幕像素所需的时间与界面的复杂程度无关，始终相同，但渲染服务器的情况并非如此。复杂的渲染请求可能导致渲染服务器耗时超过可用时间，从而错过截止时间。当 App 进程中的工作按时完成，但渲染服务器上的工作没有按时完成时，这被称为_渲染卡顿_。

系统之所以可能切换到三缓冲模式，原因之一就是为了从渲染卡顿中恢复。在下图中，渲染服务器没能在一个 vsync 间隔内渲染完绿色的那一帧，因此在呈现时间之前渲染还没有完成。为此，渲染服务器使用了第三个帧缓冲区，并切换到三缓冲模式，在 GPU 完成上一帧的工作的同时开始渲染下一帧。这避免了绿色帧被丢弃，但它仍然比计划晚一个 vsync 才出现在屏幕上，这可能导致动作出现可察觉的中断，从而造成卡顿。

![](../../../attachments/bc679b99d0fba79d5a5141ceadcfc81f/understanding-hitches-in-your-app-4a@2x.png)

在下图中，该帧的实际帧生命周期同样为三个 vsync，因为渲染服务器正以三缓冲模式运行。这是预期之中的，并不属于卡顿，因为它此后设法在每个 vsync 都成功更新了屏幕。

出于各种原因，系统在常规运行期间也可能使用三缓冲模式，比如通过让 GPU 以低功耗模式运行、给它更多时间完成工作来节省能耗，或者当某个特定用例需要比单个 vsync 间隔更多的时间在 CPU 和 GPU 上完成渲染时。

渲染的准备步骤发生在 CPU 上，实际渲染发生在 GPU 上。尽管 GPU 可以并行执行工作，但 CPU 不能。因此，即使在三缓冲模式下，渲染服务器的 CPU 工作仍需要在单个 vsync 间隔内完成，以避免延迟开始下一帧的 CPU 工作，并给 GPU 留出足够的时间在呈现时间之前完成其工作。

尽管渲染发生在渲染服务器内部，而不是在 App 本身中，但渲染卡顿通常还是由 App 引起的，比如计划中的界面更新过于复杂，无法及时渲染完成。你需要同时关注提交卡顿和渲染卡顿。卡顿的类型可以为其根本原因提供线索，也能提示你需要优化 App 的哪个部分，以避免今后再发生这种卡顿。
