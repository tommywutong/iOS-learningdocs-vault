> 原文：[Core Data 和数据库的区别 | Cocoa with Love](https://www.cocoawithlove.com/2010/02/differences-between-core-data-and.html)　·　Cocoa with Love (Matt Gallagher)

[Core Data 编程指南](http://developer.apple.com/Mac/library/documentation/Cocoa/Conceptual/CoreData/index.html)明确指出 Core Data 并非数据库，但由于 Core Data 和数据库都提供了可搜索的持久化存储方式，它们具体在哪些方面以及为什么不同，可能并不清晰。在这篇文章中，我将考察 Core Data 的工作方式，并探讨其特性和能力与常见 SQL 数据库不同的原因——即便 SQL 数据库可能被用作其后备存储。

## 引言

Core Data 和 SQL 数据库都提供了在可搜索的存储中持久化保存结构化数据的手段。

由于程序员通常熟悉数据库，而且 Core Data 实际上由 SQLite 数据库作为后端支持，因此 Core Data 常常被当作 SQLite 的包装器来对待和使用，这是可以理解的。

认识到以下这点很重要：尽管你可以这样使用 Core Data（事实上，它这样工作得很好），但 Core Data 实际上运行在与 SQLite 不同的领域——这意味着它提供了许多 SQLite 没有的服务，但 Core Data 也无法提供 SQLite 所能提供的某些服务。即使对于两种技术都提供的功能，也存在不同的性能考量。

## 数据库的主要功能

我将使用的数据库的狭义描述是：以表、行、列格式存储数据的持久化、可搜索存储，其主要目标是始终保持磁盘上的数据为最新，次要目标是实现强大、专注、精确的获取和更新能力。

数据库的实现有很多，许多提供的功能远超此描述，但我主要关注的是许多程序员熟悉的、直接的 SQLite 风格数据库实现的关键组件。

尽管许多数据库被称为“关系型”（这意味着它们在一定程度上支持对象连接），但 SQLite 和许多其他关系型数据库并不处理连接对象的机制；在列、行或表之间维护状态（如对象关系）的工作留给了数据库使用者。从这个意义上说，数据库是“愚蠢的”存储——行的行为除了“读取”和“写入”之外寥寥无几，扩展或自定义它们的行为将涉及扩展数据库系统本身。即使有触发器可用，其编程能力也很有限。

## Core Data 的主要功能

Core Data 的核心是一个具有生命周期、搜索和持久化功能的对象图管理器。对于 Core Data，对象图管理包括：

- 你可以将对象 A 连接到对象 B，并且 A 端和 B 端的连接会始终保持同步。
- 如果你更改 A 端的连接，B 端将被更新，并且所有更改都会触发通知（你可以将任意代码附加到这些通知上）。
- 删除连接某一端的对象可以触发级联删除或置空响应。
- 除非实际跟随连接（此时会加载所连接的对象），否则连接的另一端可以存在于内存之外（处于 faulted 状态）。

与典型数据库不同，Core Data 可以完全在内存中使用。虽然 Core Data 常被称为“对象持久化”框架（因为预期你会使用其持久化功能），但实际上完全可以在没有持久化的情况下，在内存中使用 Core Data。当然，一旦你有了数据，合理地保存这些数据是必要的，因此持久化被视为该框架的主要功能，但重要的是要知道持久化并非强制要求。

同样与数据库不同的是，可以在没有任何搜索的情况下使用 Core Data。如果你分配并连接了所有对象，你需要做的就是持有其中一个，然后你就可以遍历所有对象，而无需获取请求。这种无需搜索的行为并不是因为 Core Data 透明地执行了搜索：一旦数据加载到内存中，跟随连接就不涉及搜索。

所有 Core Data 对象都是完全实例化的 Objective-C 对象，它们管理自己的大多数属性、关系和生命周期。这也意味着它们的属性和行为是通过方法实现的，这使得它们既可被观察又可被重写。

## 数据库和对象图管理并非天生互斥

虽然 SQLite 默认不提供，但 MySQL 的“外键”和其他符合 SQL:2003 标准的数据库可以处理不同表中标识符的同步，甚至在需要时级联删除。可重写对象的程序化自定义能力不可用，但图管理的基本要素是存在的。

还有其他对象关系框架的工作方式更接近 Core Data 的模型，但它们试图表现得像一个原子性、事务性的数据库。要更新对象图，这些框架必须：

- 从数据库加载相应的行
- 从这些行实例化对象
- 对现在内存中的图对象进行更改
- 将更改提交回数据库

为了保持适当的原子性，这些步骤必须作为单个事务执行（在事务期间不对受影响的行进行其他读写）。虽然某些系统可能需要如此，但对于通用的对象图系统来说，这太慢了。

Core Data 不遵循此模型，因为 Core Data 旨在成为一个更通用的对象管理系统——这意味着它需要比该模型允许的更好的性能和灵活性。

## 在内存中运行与在磁盘上运行

由于没有源代码可参考，情况不完全清楚。我们只能假设 `NSManagedObjectContext` 在堆或某种结构化容器中跟踪实例化的对象，以便再次找到它们。

这个跟踪结构可能有点像内存数据库，但它仅用于跟踪实例化对象的存在——需要注意的是，它本身不存储任何数据。还要注意，中心化的 `NSManagedObjectContext` 及其可能维护的任何结构不是你与实例化 `NSManagedObject` 交互的方式——你是通过向 `NSManagedObject` 指针发送消息来与 `NSManagedObject` 交互的。

Core Data 专注于内存中表示的原因是速度。对于影响多个对象的对象图更改，如果它们都已经在内存中，速度会快得多，而不必在数据库中再次搜索它们。

对于临时对象（不必保存到磁盘的数据），Core Data 可以比 SQLite 快得多地创建、更改和操作对象，因为 SQLite 必须更新索引和 B 树中的节点，以及简单地分配空间和设置值。Core Data 可以在几秒内分配数百万个对象，而 SQLite 可能需要几分钟才能完成相同数量的分配。

采用内存方法的折衷之处在于，SQLite 仍然被用作后备存储。从磁盘读取和保存到磁盘涉及到 SQLite 的所有开销，再加上 Core Data 到 SQLite 转换过程的开销——因此总是比单独使用 SQLite 慢。

## Core Data 不处理的常见数据库任务

我已经讨论了 Core Data 拥有而数据库没有的功能。考虑 Core Data 的方法在哪些方面相对于数据库有所不足也很重要。

### Core Data 无法在不将数据加载到内存中的情况下操作数据

在 SQL 中，你可以简单地使用 “`DROP tableName`” 删除整个表，或使用 “`UPDATE tableName SET key1 = value WHERE key2 = otherValue`” 等命令更新表中的每一列。这些命令可以高效地更新大量数据，因为它们在任何时候都只需要将少量数据加载到内存中。

Core Data 不以这种始终保持磁盘操作的方式工作——它仅对内存中的对象进行操作。即使你只想删除一个对象，也必须将其加载并在内存中实例化。

当然，这是必要的，因为该对象及其可能被重写的行为必须被加载和调用。还需要与其他对象保持连接更新。

然而，这个限制有其影响：如果你试图更改大量对象（数万或更多），你将需要考虑控制你的内存占用空间。这可以通过定期将未更改的值重新设置为 fault 状态（`refreshObject:mergeChanges:`）、避免获取对象的数据（在 `NSFetchRequest` 上使用 `setIncludesPropertyValues:NO`）、甚至保存整个上下文并释放你持有的所有对象来实现。

### Core Data 不处理数据逻辑

SQL 包含一些与数据相关的功能，一个很好的例子是“唯一”键，Core Data 并不包含这些。

这可能有几个技术原因。子类可以重写某个属性的 getter 和 setter，以至于无法确定它是否唯一。事实上，瞬态 Core Data 属性甚至不需要支持 `isEqual:`。

然而，我猜测这种区别实际上是因为 Core Data 根本不提供对属性行为的真正支持。Core Data 管理“图”（连接），但数据属性全部由程序其余部分的业务逻辑负责；虽然这很方便，但它超出了 Core Data 的概念领域。

### 多线程、多用户场景

Core Data 不提供任何程度的线程支持。公平地说，`SQLite` 也是单线程的，但许多其他数据库是多线程和多用户的。

Core Data 是为单用户环境（在桌面和 iPhone App 内运行）设计的。消除线程和锁定使得框架在其标准使用场景中更快、更易于使用。

然而，仍然存在你需要多个线程读取数据的情况。`NSManagedObject` 及其 `NSManagedObjectContext` 应该仅从单个线程访问。如果你需要另一个线程处理相同的数据，你需要保存文件并在另一个线程中使用不同的 `NSManagedObjectContext` 重新打开。

## 总结

| **数据库** | **Core Data** |
|---|---|
| 主要功能是存储和获取数据 | 主要功能是图管理（尽管读写磁盘是重要的支持特性） |
| 对存储在磁盘上的数据进行操作（或最小量、增量地加载） | 对存储在内存中的对象进行操作（尽管它们可以从磁盘延迟加载） |
| 存储“愚蠢的”数据 | 处理功能全面的对象，这些对象自行管理其大部分行为，并且可以被派生子类并进行自定义以实现更多行为 |
| 可以是事务性的、线程安全、多用户 | 非事务性、单线程、单用户（除非你围绕 Core Data 创建完整的抽象层来提供这些功能） |
| 可以删除表和编辑数据而无需加载到内存 | 仅在内存中操作 |
| 持续保存到磁盘（并且通常具有崩溃恢复能力） | 需要保存过程 |
| 创建数百万新行可能很慢 | 可以非常快速地在内存中创建数百万新对象（尽管保存这些对象会很慢） |
| 提供数据约束，如“唯一”键 | 将数据约束留给程序的业务逻辑部分 |
