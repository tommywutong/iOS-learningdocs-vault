> 原文：[Method names in Objective-C | Cocoa with Love](https://www.cocoawithlove.com/2009/06/method-names-in-objective-c.html)　·　Cocoa with Love (Matt Gallagher)

与其他语言相比，Objective-C 中的方法名确实有些怪异。它们很长、很啰嗦，包含参数名称，而且似乎还在重复你本可以从其他地方获取的信息。尽管存在这些表面上的缺点，Objective-C 的方法命名却能为你节省时间和精力。我将向你展示方法是如何命名的，这样即使没有文档你也能预测方法名，并能仅从名称就理解方法如何工作以及如何使用其参数。

## 引言：Objective-C 是一只丑小鸭

除了方括号和绝大部分为 Apple 独有这两个特点之外，方法名也是 Objective-C 最常被诟病的部分之一。我看到过有人批评它们：

- 又长又啰嗦
- 重复或冗余
- 每个参数都带有名称
- 使用驼峰命名

尽管这些指责都点到了事实，但其中没有一条是真正的缺点——虽然驼峰命名涉及主观审美，我会忽略它，因为这篇文章只考虑方法命名约定的**结构**层面。

Objective-C 的方法名是所有 C 衍生语言中最具可预测性、规律性和自描述性的——也正是这些特点实现了上述优点。当然，如果不了解其约定并做到能理解和预测，这些好处也就无从谈起。

## 背景：其他类 C 语言中的命名约定

为了帮助你理解 Objective-C 方法名背后的逻辑，我将首先描述 C 语言中方法和函数的命名方式。我从 C 语言开始讲，因为 Objective-C 的方法命名在某些方面就是 C 语言命名风格的扩展，并在此基础上进行了改进以克服其局限性。

### 标准 C 的命名风格

是的，标准 C 确实有一些隐含的命名约定。许多标准 C 函数由三部分组成：

1. 指出操作的数据类型
2. 操作
3. 次要对象的描述

我们可以从以下函数中看到这些例子：

- `sscanf` —「s」（作用于 `char *`）、「scan」（从字符串中提取字符数据）、「f」（格式字符串是次要对象）
- `fprintf` —「f」（作用于 `FILE`）、「print」（将字符数据输出到文件）、「f」（格式字符串是次要对象）
- `strlen` —「str」（作用于 `char *`）、「len」（计算长度）。没有次要对象。
- `fesetround` —「fe」（作用于「浮点环境」）、「set」（改变状态值）、「round」（新的舍入值是次要对象）。

### 标准 C 命名风格的失败

对于这些方法，这种风格是可行的。问题在于各个组成部分过于简短（通常是单个字母），导致我们很难确切知道它们所指的是什么。`math.h` 中的许多方法都暴露了这些局限性：

- `lround` —「l」（不再是「作用于」，这里的第一个部分表示「返回 `long`」）、「round」（舍入到最接近的整数）。没有对主参数进行描述——你被预期假定参数是 `double` 类型。
- `acosl` — 这里的「l」指的是主参数，意思是 `long double`，而在上面的 `lround` 方法中它却表示 `long`。这里的「a」不是前缀，而是操作部分的一部分。

这就是 C 语言的命名风格失效的地方——虽然 `math.h` 确实有自己的命名约定，但那只是它自己的约定。你可以学习 `math.h` 的技巧，但它们是那个库独有的，并非适用于所有函数的标准。

除了这些问题，C 语言还普遍缺乏对**任何**约定的遵从，更别提始终保持一致的约定了。大多数函数实际上只是一个 4 到 6 个字符的操作描述。虽然这在技术层面上也许足够了，但这使得如果不阅读文档，几乎不可能知道如何首次使用 `system`、`raise`、`atexit` 甚至 `malloc` 这样的函数。

### 其他语言

很少有其他语言在方法结构上拥有独特的方法。我主要使用的语言（C++、C#、Java）中，压倒性的约定仅仅是一个简短的动词加上可能的修饰语。

某些语言确实有自己的美学（例如，C++ 标准库使用简洁的下划线分隔单词），但这并不代表一种结构上的约定。

这些语言之所以放弃了标准 C 函数的三部分风格，原因如下：

1. 操作的数据类型现在是调用方法的对象本身，从而省去了解释这一部分的需要。
2. 参数重载意味着任何参数的描述都需要模糊（因为参数的使用方式可能不一致）。

因此，方法最终不过是动词加上可选的修饰语。

结果是，那些行为微妙或以特定方式使用其参数的方法，只能通过仔细阅读文档才能使用。

## Objective-C 中的方法命名约定

Objective-C 的目标是比它的同行具备更强的自文档性。其意图是所有类中的所有方法都应遵循同一套规则，使得行为上的细微差别易于发现和理解——即使你对该类还不熟悉。

这个目标与 Objective-C 的命名参数结合在一起，产生了与其他语言截然不同的方法。

考虑到其他语言缺乏约定，以及 Objective-C 命名参数的特殊性，Objective-C 的方法名让新程序员感到困惑也就不足为奇了。

### Objective-C 方法名的结构

Objective-C 方法由几个不同的组件组成。我在这里列出这些组件，后面将提供例子：

1. 如果有返回值，方法应以返回值的属性名（对于访问方法）或返回值所属的类名（对于工厂方法）开头。
2. 一个动词，描述改变接收者状态的操作，或接收者可能执行的次要操作。那些不会导致接收者状态改变的方法通常会省略这一部分。
3. 如果第一个动词作用在一个直接对象上（例如接收者的一个属性），而该属性在第一个参数的名称中没有明确体现时，使用一个名词。
4. 如果主参数是方法主要动词的间接宾语，则使用介词（即「by」「with」「from」）。这个介词部分用于指示参数使用的方式，但更多是为了让方法名读起来像一个完整的句子。
5. 如果使用了介词，而第一个动词不适用于主参数或不存在，则可以使用另一个动词来描述涉及主参数的直接操作。
6. 一个对主参数的名词性描述（通常是类名或类似类名的名词），如果这个描述没有在某一个动词中明确体现的话。
7. 后续参数的名词性描述。介词、连词或次要动词可能出现在后续参数名称之前，但仅在该后续参数对方法至关重要的情况下。这些额外的词是为了突出次要参数的重要性。在少数情况下，次要参数名称可能仅由一个介词组成，不带名词，用以指示来源或目的地。

此外，Objective-C 方法应具有最大的可读性——它的读法应该像句子一样流畅，并且应避免缩写，除非是普通通用的缩写（即便如此，也优先使用音节缩写而不是单字母缩写）。

需要考量的因素很多。幸运的是，大多数组件只对特定类型的方法有意义。

### 将命名约定应用于属性访问方法

```objc
length
```

这个方法展示了获取属性或计算值的 getter 方法的典型形式。只应用了方法名的第一个组件。

与其他语言相比，最重要的注意事项是：getter 方法不使用动词「get」，因为提取这个属性不需要显式的操作或状态变化（隐式操作或因内部原因而采取的操作不应通过方法名传达出来）。

```objc
encodedLength
```

这个方法展示了一种变形，使用修饰语来描述长度。我们将修饰语放在属性名之前，因为像 `lengthWhenEncoded` 这样的结构太接近于 `lengthForEncoding:`（后者用于当编码作为参数传入时）。

```objc
sharedApplication
```

单例访问方法（例如访问全局 `UIApplication` 对象的这个方法）和其他全局数据访问方法的形式与实例访问方法完全相同：返回值的描述（这里简称为「Application」）加上一个形容词来消除歧义（这里需要消歧是因为单独的类名会被认为是工厂方法——见下文）。按惯例使用术语「shared」来标识单例。

```objc
doubleValue
```

这个方法与前一个具有相同的结构，但它展示了当与抽象属性（如「value」）一起使用时，返回的类有时会充当修饰语。

```objc
isEditable
```

这个方法实际上是对传统规则的一个例外。动词「is」本不应该出现在这里——动词通常保留用于描述状态变化或次要操作。

我猜这种用于返回 `BOOL` 值的访问方法风格的发展，是为了让方法读起来更像个句子。你也可以认为「is」是一个系动词，因此它不表示一个操作。

```objc
setLength:
```

设置方法的构成方式与获取方法不同。没有返回值，第一部分是一个描述操作的动词：「set」。

第二部分「Length」可以被认为是动词组件的直接宾语（即内部属性）。在这种情形下，它也是第一个参数的名称。由于它们传达相同的信息，因此只使用其中一个。

像 `setValueUsingDouble:` 和 `setValueUsingNumber:` 这样在第一个参数前使用介词的方法很少使用，尽管它们看起来是用不同数据类型明确设置像「value」这样的属性的好方法。相反，属性本身通常会被赋予一个不同的名称（即 `setDoubleValue:` 或 `setNumberValue:`）。这样，对于一个给定的属性，永远只有一个 setter（尽管属性可能包含依赖关系）。

### 将命名约定应用于工厂方法

```objc
string
```

这个 `NSString` 方法返回一个空字符串。它的格式与 getter 方法完全相同，不同之处在于你在类对象上调用它，而不是在实例上，并且它不包含属性名。

这可能看起来像是在提供冗余信息——我们已经知道一个类的工厂方法将返回该类的实例——但在这里标识返回类型有两个目的：

- 工厂方法之所以能被识别，正是因为它们以类名开头
- 它保持了**一致性**（当返回值是方法的目的时，总是描述返回值）

不过，对第二点有一个快速补充：只有当返回值是方法的目的时才需要描述它。作为错误指示返回的 `BOOL` 值以及其他返回值属于次要效果的情况（比如 `autorelease` 返回的是接收者），则不需要描述返回值。

```objc
stringWithString:
```

这里的参数名为「String」，表明它是一个没有其他约束的 `NSString` 实例。阅读这个方法的正确方式是：它从其字符串参数中以最简单的方式创建一个新字符串——即该字符串的一个副本。

这里的介词除了让方法名读起来像句子之外，其实没有多少语义目的。介词的选择很简单：如果像读句子一样读它，什么最合适就用什么。出于这个原因，类工厂方法通常使用「With」，而实例工厂方法通常使用「By」，因为它暗示了接收者数据的某种参与（比如 `stringByAppendingString:`）。

`NSArray` 的方法 `isEqualToArray` 展示了一种带介词的状态询问方法，但同样，选择介词只是为了方法名读起来像句子。

### 将命名约定应用于操作方法

```objc
release
```

这是一个简单操作方法的例子：一个动词，描述方法如何改变状态或执行次要操作。

```objc
addObject:
```

这又是一个非常简单的例子：动词加一个描述第一个参数的名词（任何「Object」）。

```objc
addObserver:forKeyPath:options:context:
```

这里重要的补充是第二个参数之前使用了介词「for」。是的，「KeyPath」是方法动词「add」的间接宾语，但这里真正的目的是突出这个参数的重要性——指出这个参数比后面的参数更重要。

为了解释这一点，思考一下这个方法并不是 `addObject:forKeyPath:usingOptions:andContext:`——options 和 context 实际上是外围参数，而 keyPath 则是一个重要的考量因素，尽管它是第二个参数。

这个方法可以和非常相似的 `NSNotificationCenter` 方法 `addObserver:selector:name:object:` 进行比较。在 `NSNotificationCenter` 的方法中，`name:` 是对应于 `forKeyPath:` 的参数，然而这里并没有使用介词（它不是 `forName:`）。这反映了 name 参数是可选的（可以为 `nil`）这一事实。

但是你不应该推断缺少介词就意味着「可选」——远非如此。相反，正确的含义是：有介词表示比其他次要参数更重要。`addObserver:selector:name:object:` 方法中的 `selector:` 参数是强制的，但在这个方法中没有被赋予特殊地位。它对于路由通知是必要的，但在很多时候，它仅仅反映它所观察的通知（即 `@selector(windowWillCloseNotification:)`）。

### 一个小例外：委托方法

```objc
windowDidChangeScreen:
```

这个方法以一个类名开头，但它既不是工厂方法，也不是返回接收者变异版本的方法。它实际上是一个委托方法，而委托方法并不完全遵循任何约定。

如果遵循常规标准，它的名字应该是 `receiveWindowDidChangeScreenNotification:`。你可以认为委托方法是被动的——委托没有被要求执行操作，而是被告知其他东西执行了操作——所以省略动词是可以的。就我而言，打破约定让我心里感到一丝不快。

更令人困惑的是，委托方法的第一个参数很少由其最接近的名词标识。相反，第一个参数要么是发送通知的对象，要么是一个通知对象（它将包含发送者）。在上面的例子中，最接近的名词是「screen」，但第一个参数是一个 `NSNotification`。在 `applicationOpenUntitledFile:` 这个例子中，最接近的名词是「File」，但参数是发送消息的 `NSApplication` 对象。

## 总结

在描述方法格式时，我重复了很多次。实际情况是，Objective-C 几乎在所有地方都使用一种方法命名约定。

Objective-C 方法名非常有规律。如此有规律以至于你应该不用查文档就能预测方法名——输入你猜测的方法名，然后由自动补全来完成。不止是预测名字，你通常还能预测参数是怎样使用的，因此再次避免查阅文档，并知道你需要什么。

再看一下我在开头列出的对 Objective-C 方法名的批评：

### 又长又啰嗦

是的，Objective-C 方法被设计成读起来像句子。它们包含介词（这在其他语言中几乎从未见过），包含返回参数的类型，使用完整单词而非缩写。

其目的是让方法尽可能快速地读取。

这是一个值得的取舍，因为你会阅读一个方法很多次，但只会输入它一次（借助代码补全，甚至不到一次）。

> Xcode 会自动建议代码补全。随时按下回车键来选择它提供的补全。按下 Code Sense 补全键（默认是 F5），它会显示一个匹配选项的弹出列表。Control-/ 会逐步切换参数以便你填写。

### 重复或冗余

虽然像 `+[UIApplication sharedApplication]` 这样的方法看起来可能多余，但实际上 `+[UIApplication shared]` 会有不同的含义（它会是一个名为「shared」的静态类属性的访问方法），而 `+[UIApplication singleton]` 由于省略了类名，未能传达该方法在首次调用时也作为工厂方法工作——重复类名是有意义的，并非冗余。

### 每个参数都带有名称

是的，但这样做使得确定每个参数是什么变得更加容易，并且允许传达像重要性这样的元数据。

### 使用驼峰命名

是的。选择驼峰命名还是下划线分隔单词在很大程度上是审美问题。虽然选择 Pascal 命名（与大驼峰相同，但第一个单词的首字母大写而非小写）是因为大写首字母保留给具有全局作用域的名称——比如类名、函数名和全局常量。

## 结语

很少有其他语言像 Objective-C 那样严格执行其约定。学习约定可能很烦人——因为它们乍看之下可能随意且不必要——但一旦学会，它们就是有规律、可预测且鲜有意外。当试图让计算机服从时，这很好。
