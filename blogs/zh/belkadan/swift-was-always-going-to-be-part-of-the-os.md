## [Swift 从一开始就注定要成为操作系统的一部分](#)

最近在 Swift 论坛上，有人抱怨说把 Swift 放进操作系统里只是让开发者的日子更难过了。我的第一反应是带点讽刺地回一句「欢迎来到随操作系统一起发布的库的世界」，但这既没什么帮助，也没能反驳他们的观点。所以这篇博客文章想聊聊我们是怎么走到今天这一步的，覆盖的是我在 Apple 参与 Swift 开发的那段时间。不过我得从更早的地方讲起，才能把这个问题说清楚……

### 操作系统依赖

在我上一篇文章「[动态链接对 App 不利，静态链接对 App 也不利](https://belkadan.com/blog/2022/02/Dynamic-Linking-and-Static-Linking/)」里，我聊过对于随你的 App 一起发布的库来说，静态链接和动态链接之间存在一种权衡取舍。但那些随操作系统一起发布的库又是怎么回事呢？到了这一步，你就动用了动态链接最主要的力量、也是它最主要的诅咒：你构建和测试时用的库，未必就是你运行时用的库，而这时候你就得对自己所依赖的东西小心得多。

在这一点上，我们可以想象一条光谱：一端是你完全不使用宿主操作系统提供的*任何*东西，另一端是你完全依赖它：

- 这个起点其实已经不复存在了，除非你本身*就是*操作系统；不过曾几何时，个人计算机的工作方式，是把整台计算机的控制权交给正在运行的进程，这个进程可以对整台机器、内存、以及其他一切为所欲为。即便是这些程序，操作系统也可能会提供「库函数」，这些函数要么随程序一起被加载，要么在程序加载时被留在内存中某个已知的位置；但你*可以*写一个完全不用这些东西的程序，它基本上就是它自己的操作系统，完全没有任何动态依赖。
- 如今，即便是一个「静态链接」的程序，也不再「掌管」整台机器了。操作系统*内核*始终也在运行，提供基础的操作系统服务，并暴露出某种「系统调用」接口，程序可以通过它请求某些特权操作（比如读取一个文件，或者分配更多的内存页）。~~大多数现代操作系统都允许你生成这种工作方式的程序，包括 Windows 和 Linux。~~ Linux 是最广为人知的、允许程序以这种方式工作的现代操作系统，在这种方式下，你唯一依赖的就是你能用到的那组系统调用。
- 如今最常见的编程方式，是至少依赖操作系统随附的*一些*库，哪怕只是 C 标准库和它那份最小的运行时。如今的 Apple 操作系统把这个叫做「最低系统 API 边界」：系统调用接口在不同操作系统版本之间*并不*稳定，所以你「必须」使用 C/POSIX 标准库及其扩展来完成哪怕最基础的原语操作。^[1](#fn:go) 编辑：Windows 也类似，只不过它「稳定」的接口是 C 标准库*之下*的那一层库（感谢 [Slava](https://twitter.com/slava_pestov/status/1579275297408499712) 和 [Kyle](https://twitter.com/optshiftk/status/1579283783563743232)）。
- 我不认为你能*真的*说有哪个程序处在另一个极端，也就是它*所有*的行为都来自依赖项，某些平凡的例子除外。但从某种角度看，每一个*被解释执行*的程序都是这样工作的。一段 shell 脚本本身不会直接执行*任何*机器指令；是 shell 根据脚本里写的内容去执行的。（字节码运行时和 JIT 编译器也让这条界线变得模糊。）

由此可见，程序可以在不同程度上依赖它们的宿主操作系统，而 Apple 尤其是全面押注在了「库」这套模型上。我们来仔细看看这套模型：

### Apple 的模型（Swift 之前）

在 Swift 出现之前，Apple 几乎所有的公开 API 都是用 C 或 Objective-C 写的，并以已编译的原生代码形式提供，而不是某种字节码（比如 [JVM](https://en.wikipedia.org/wiki/Java_virtual_machine) 或 [CIL](https://en.wikipedia.org/wiki/Common_Intermediate_Language)）。新的操作系统版本会包含现有库的新的二进制兼容版本，（理论上）提供上一版本 API 的一个超集。这样，旧的 App 就能继续运行，而新的 App 则可以用上新特性。「弱链接（weak linking）」加上 Objective-C 里天生基于名字的派发机制，甚至还允许新 App*有条件地*用上新 API，同时仍然能在旧操作系统上运行。这后来正式演变成了[可用性模型](https://belkadan.com/blog/2021/10/Swift-Delight-Available/)，不过这是后话了。

这套模型最大的缺点是，新特性和新 API 都绑定在新的操作系统版本上。如果你有一个 App，想在运行 v7 系统时也用上随 v9 系统一起发布的新 API，那……你做不到。Apple 当然希望所有人都尽快升级到新系统，但不是每个人都会这么做；也许新系统不支持他们的电脑，也许它跟他们用的某个 App 不兼容，诸如此类。所以 App 开发者只能等，等到有足够多的人升级到 v9，他们才能在不损失营收、不损失用户好感之类的前提下，放弃对 v7 和 v8 的支持。而在另一边，Apple 也不能改变一个既有库的行为，因为哪怕这个行为原本是有 bug 的，改动也可能破坏现有的 App。

我们稍后会更多地聊聊其他的替代方案，但眼下先把背景交代清楚：Swift 的设计目标之一，就是不需要改变这套模型。库仍然会是已编译的原生代码；新版本仍然会与旧版本保持二进制兼容。我们把这些当作设计约束接受了下来，同时还接受了要和 Objective-C 紧密互操作、以及不依赖 JIT。^[2](#fn:jit)

### Swift「beta」1 到 <5

从 Swift 1 到 Swift 5 之间发生了*海量*的变化：API 设计不断调整，ARC 函数调用约定不断改变，缺失的优化被逐渐补上，我们也在不断学习在这门新语言里什么才是切实可行、地道的写法。在这整个过程中始终笼罩在我们头顶的，是「ABI 稳定性」——也就是使用两个不同版本 Swift 的代码能够互操作的那个临界点。为什么这一点如此重要，而其他那么多语言似乎都不怎么在乎它呢？因为这正是 Apple 那套基于操作系统的库发布模型的根本前提：用 Swift 5 编译的 App 要能在基于 Swift 6 构建的操作系统上正常工作；用 Swift 6 编译的 App 仍然要能「向后部署」到基于 Swift 5 构建的操作系统上。没有这一点，*Apple 就没法在自己的公开 API 里使用 Swift。*

所以这从一开始就是 Swift 的一个目标。开发者们也在抱怨：每个用 Swift 的人都得把它所有的库一起打包进自己的 App，这会让 App 体积增加不少。此外，那些做闭源库的开发者，还得为每一个新版本的 Swift 单独发布一个版本，因为不同版本之间未必二进制兼容。但与此同时，ABI 稳定性也意味着你再也不能改动这些东西了！（直到今天，Swift 的枚举布局里仍然存在一些低效之处，没法改善，因为那会改变 ABI。）

到了 Swift 5，我们终于走到了这样一个阶段：*大多数*事情都已经相当不错了，我们已经摸索出该怎么处理运行更早版本 Swift 的旧 App，而且我们也已经因为破坏源码兼容性的改动而饱受*恶评*。更别提来自 Apple 内部的压力：这个项目已经进行了好几年，却依然处处受限。

### 过渡

到了要把 Swift 放进操作系统里的时候，我们必须搞清楚该怎么做才能不破坏

- 已经构建好的现有 App，它们内嵌了自己早期版本的 Swift
- 现有的*项目*，它们希望继续支持更早版本的 iOS

第一个问题是通过*刻意*改变 Swift 的 ABI 解决的，这样 Swift 5 就不会和 Swift 1-4 里的任何东西发生冲突。在少数几个新旧 Swift 需要交互的地方——也就是 Objective-C——Swift 5 类型的元数据被打上了不同于 Swift 1-4 的标记，这样旧版 Swift 就会把新版的类当成某种怪异的 Objective-C 类来看待。这需要费不少工夫去搞定，但最终其实相当直截了当。

第二个问题没法用同样的方式解决；我们*希望*新的 App 能和系统提供的 Swift API 交互。所以我们得想办法既继续允许 App 随身携带 Swift 库，又要*同时*避免在足够新的操作系统上出现两份 Swift 副本。我们当然不希望一个 App 内嵌的 Swift 5 库，把第二年操作系统里的 Swift 5.1 给覆盖掉！那样会破坏第二年操作系统里依赖 Swift 5.1 的部分功能。

我们最终（不太正规地）利用了一个叫做「[rpath](https://www.mikeash.com/pyblog/friday-qa-2009-11-06-linking-and-install-names.html)」（即「运行时搜索路径」）的特性，它允许一个可执行文件不通过写死的路径、而是通过搜索一系列目录来找到自己的动态库。通过让搜索顺序从 `/usr/lib/swift/` 开始、然后再搜索 App bundle，我们就能保证：如果系统里存在 Swift 的操作系统版本，App 就会使用它，否则就回退到自己内嵌的版本。^[3](#fn:usr)

![](https://belkadan.com/blog/2022/10/Swift-in-the-OS/rpath.png)

我想在这里说清楚一点：这是一种把操作系统库的**第一个**版本向后部署的技巧。你没法对*第二个*版本玩同样的 rpath 把戏，因为第一个版本已经在磁盘上了。就在去年，Swift Concurrency 也用了同样的技巧，结果在那第一个版本里发现了一个严重的 bug……而这个 bug 没法在向后部署库里「修复」，因为那些仍然内置着 libswiftConcurrency 1.0 的操作系统上根本用不上它。这反过来又会造成支持上的一处断层：

![](https://belkadan.com/blog/2022/10/Swift-in-the-OS/discontinuity.png)

……好吧，操作系统更新里一直都在不停地引入 bug、又不停地修复 bug，所以也许有些时候这样做还是值得的，但重点在于，这不是一个百分之百的解决方案，而且对*新*的 API 来说，它会破坏可用性模型。

### 我们失去了什么

所以，Swift 现在进了操作系统！App 不再需要内嵌 Swift 了！既然 Swift 和 Objective-C 的运行时是一起发布的，一大堆性能改进也就能顺理成章地做了！而且，终于，终于，Apple 可以把 Swift 的 API 作为操作系统的一部分发布出去了。

而几乎与此同时，外部的 Swift 贡献者们也很快发现了 Apple 的框架工程师们每年都要面对的东西：

- 粗略地说，你永远没法删掉任何东西，只能弃用它，因为否则现有的 App 可能就会*启动失败*，或者[丢失用户数据](https://belkadan.com/blog/2021/11/Swift-Mangling-Regret-The-Old-Mangling/)。
- 发布周期被绑定在了操作系统的发布周期上。（Swift 的发布周期一直都绑在 Xcode 的发布周期上，这已经够糟糕了，但操作系统是比 Xcode 大得多的「载体」，就算你真的觉得有必要，也更难去改变它的走向。）
- 而这也是这篇文章最主要的诱因：**新 API 只会出现在新的操作系统里。**（更糟的是，这也就意味着它们全都必须标注可用性。）

这最后一条是 Go 没有的问题，Rust 也没有的问题，Swift 1-4 那时候也没有的问题，而原因都是一样的：这些语言随附自己所用的 App 一起发布（过）自己的标准库。它们不是操作系统的一部分，所以它们几乎没有动力去追求稳定的 ABI、或者支持库的演进（它们也确实没有）。

我们（Apple）在这次转型的时候，曾试着[管理好所有这些预期](https://www.swift.org/blog/abi-stability-and-apple/)。但这终归是一种权衡取舍，所以在 Swift 进入操作系统之后的这几年里，Apple 和 Swift 团队想出了几种技巧，用来支持一些常见的向后部署场景：

- 可以给特定函数标注一个「尚不支持」的属性，让它们被拷贝进客户端代码里，而不是通过符号名引用——这有点像在头文件里定义的 C `static` 函数。不过这只对函数、方法之类不需要*身份*的东西有效；如果同样的实现被用在一个全局的存储型变量上，你最后就会得到这个全局变量的多份副本。而且这也只有在该实现同时兼容它所依赖的 API 的过去版本和未来版本时才有效。（这方面确实出现过一些真实的 bug。）
- 有些 Apple 的库是刻意*不*随操作系统一起发布的；你可以选择像第三方依赖那样，把它们内嵌进自己的 App。[ResearchKit](http://researchkit.org) 就是最早这么做的库之一，甚至比 Swift 成为操作系统一部分还要早。
- 在某些情况下，Swift 团队会包含一个「兼容性」库，只链接进*主 App*（这样才能保证只有一份），用来把旧操作系统的部分支持能力补齐到最新水平。这些库有时会用到运行时里的「定制点」——也就是我们事先就知道某些东西可能会变化的地方；有时也会用一些很糟糕的手段，依赖旧运行时或旧操作系统的实现细节（这种做法 Apple 对自己用还算说得过去，比外部开发者这么做要好一点，因为 Apple 可以向自己保证不会再进一步改动那个旧的操作系统版本）。

不过，这些方法没有一个是完美的。目前没有一套标准机制，能对标准库和操作系统里其他 Swift 库新增的功能做「按需向后部署」（如果你 App 里有多个 target 都想负责这件事，情况可能会变得很棘手），而对*修改*做向后移植可能就更难了。要是你的新特性是一个泛型函数，而它依赖的协议去年根本不存在，怎么办？要是那个协议*确实*存在，但你想在新特性里用到的某些类型，直到今年才采纳它，又该怎么办？

Swift *必须*是一门可以用来定义操作系统库的语言，而这自动就会让一大堆事情变得更难。这正是那种本能反应的由来：做一个操作系统库的开发者，比做一个第三方库的开发者（或者只在操作系统内部使用的库的开发者！）要难得多。但这应该被理解为一种权衡取舍，而对权衡两侧赋予不同的权重也是完全合理的，尤其是考虑到其中一些负面影响[几乎每年都会冒出来一次](https://forums.swift.org/t/build-time-sdk-availability-check/59679)，这也是 Apple 做事方式使然。

### 替代方案

Apple 本可以做一些、或者依然可以做一些合理的事情，来改善开发者的处境。Apple *会*这么做吗？也许会，也许不会。

#### 库去重

当你手机上十五个不同的 App 都用了同一个开源库时，它们用起来多少都会有点不一样。也许它们的构建设置不同，也许它们做过一些本地修改。但如果它们用的是同一个*闭源*库，而且是一个*动态*库，Apple 理论上*可以*把磁盘上这些库去重，为终端用户省下一些空间。代码签名让这件事变得更棘手了，但我不认为这是不可能的，因为（如果我没记错的话）App Store 本来就会对你 App bundle 里的所有库重新签名。这一点*绝对*适用于 Swift 的兼容性库，我甚至隐约记得当年有过实现这个方案的讨论，所以它说不定真的已经实现了。但这不会改变商店里任何一个 App 显示出来的下载体积（因为你不会希望这个体积因为你还装了别的什么东西而变化，除非那恰好是同一个开发者的东西），而对于第一方库来说，它只在向后部署时才用得上，这自然也就让 Apple 对它没那么感兴趣了。

这个办法在 macOS 上也基本行不通，因为在 macOS 上 App 并不是百分之百由操作系统管理的；不过 macOS 也正是 Apple 各平台里，你最不太可能在意单个 App 代码体积问题的那个平台。

#### 显式的「polyfill」支持

「polyfill」这个词源自网页开发领域，指的是给旧版浏览器补上新特性、同时抹平不同浏览器之间的差异。在 JavaScript 里这件事比较容易，因为你可以在安装自己的实现之前先检查某个特性是否已经存在，这件事在 Objective-C 里能做，但做起来有点笨拙，而在 Swift 里则完全做不到。（「编译期」和「运行时」之间的差异，让这一切对 ObjC、尤其是对 Swift 来说都变得更复杂。）

在 ObjC*和* Swift 里更常见的做法，是添加一个像这样的方法：

```
func backportFoo() -> String {
  if #available(iOS 16, *) {
    return foo()
  }
  // 回退实现
  return "foo: \(self)"
}
```

当你包装的是一个*类型*而不是一个*操作*时，这件事会变得更棘手，但通常还是可以借助一个协议来实现，有时也可以用一个基类，让其中一个实现委托给操作系统，另一个用于向后移植。如果 Swift 能显式支持这种做法就好了™，但要设计这样一个特性*极其*棘手，很容易掉进「[如果两个人都这么做了怎么办](https://devblogs.microsoft.com/oldnewthing/20050607-00/?p=35413)」这类问题里。当人们像这样临时拼凑出这套做法时，至少对使用这个变通方案的人来说，行为是清楚的，因为就语言本身而言，这个变通方案跟那个未做向后移植的 API 毫无关系。

#### 显式的向后部署支持

与其采用第三方的「polyfill」方式、或者显式的包装函数、包装类型、抽象协议，Swift 其实可以直接让*标准库*（以及操作系统里作为其一部分的其他 Swift 库）更容易支持新特性的向后部署：把它们「按需」打包进 App 里，同样也「按需」加载。这件事很棘手，因为它意味着任何客户端代码现在都得能用两种不同的方式工作（再说一遍，对于一个现有库里的新特性，我们没法玩 rpath 那套把戏）。我不想把这件事说得好像很简单、很容易实现，因为它并不是，但我相信这是*可能*做到的。（想尝个鲜，感受一下这需要做多少事情，可以看看我以前写的一篇文章，「[可向后部署的一致性](https://forums.swift.org/t/backwards-deployable-conformances/29876/10)」。）

Android 其实相当常见地在做这件事，至少在它的 Java API 上是这样。这件事在 Android 上设置起来要容易一些，一方面是因为它的 App 和库用的是一种中间格式，而不是原生代码，另一方面是因为 Java 没有扩展这个概念，所以能拿来修改现有类型的方式也更少。他们把这个叫做「[脱糖（desugaring）](https://developer.android.com/studio/write/java8-support)」。

#### 没有 Swift-in-the-OS 的 ABI 稳定性

最后一种可能性是：Apple 本可以承诺 Swift 的 ABI 稳定性，但实际上并不把 Swift 放进操作系统里。任何 Apple 想要发布的闭源 Swift 库，都可以提供给每一个想用它们的 App 去内嵌，也许再辅以上面提到的「去重」策略。但 Apple *希望*能够把库的更新作为操作系统发布、以及安全更新的一部分来推送。正是这种能力，让他们可以在不强迫所有人提前发布新版本 App、而且事后也只需要相对最少量的条件判断的前提下，做到全系统范围的界面调整和重新设计。你可以争论这到底是不是件好事，但这是 Apple 永远不会放弃的能力。

### 结论

Swift-in-the-OS *对*应用开发者来说是一次糟糕的权衡取舍吗？也许是，如果你不太在意代码体积的话。^[4](#fn:code-size) 但如果不这样做，Apple 就没法用 Swift 来写系统库了，而那从来就不是一个可选项。

附言：Swift on Windows 目前仍是一个年轻的项目，它并没有 Apple 平台上那种关于操作系统库的顾虑……但 Windows 上的闭源第三方库，也比 Linux 上多得多。所以在不太遥远的将来，[我们有可能会拥有一个具备 ABI 稳定性、却*没有* Swift-in-the-OS 的平台](https://forums.swift.org/t/question-is-swift-abi-stable-on-windows-how-far-are-we-from-there/59601)。

#### 编辑：这里说的很多东西并不是 Swift 独有的新问题

我讲的很多东西，其实都是*库随操作系统一起发布*这件事本身带来的后果。值得一提的是，Objective-C 用过「[ARCLite](https://bignerdranch.com/blog/illuminating-arclite/)」——一个像上面说的那样「只链接进主 App」的兼容性*静态*库——来小心地支持若干新语言特性的向后部署，但有些特性仍然只限于最新的操作系统版本才能用（感谢 [Nick](https://twitter.com/nicklockwood/status/1579354730807328770)）。更普遍地说，Apple 从来没有支持过 *Foundation*（在 Apple 平台上，它实质上就是「Objective-C 的标准库」）新增功能的向后部署。人们对此同样一直不满，但也从来没有出现过什么齐心协力去「解决」它的推动力。

Swift 到底改变了什么？这里确实有一处技术层面的变化：相比 Objective-C，「编译期」和「运行时」之间的天平更偏向「编译期」一侧。但我真心觉得，最大的变化其实是社会层面的，而不是技术层面的：

1. Swift 标准库是一个开源项目的一部分，而 Foundation 不是。
2. 曾经有好几年的时间，Swift 表现得更像一个第三方依赖，而不是一个操作系统库，因此受到的约束也更少。（这也是这篇文章大部分内容想讨论的东西，试着说服你没必要对那段时期抱有太多怀旧之情。）Swift 在非 Apple 平台上至今仍然是这样工作的，所以这种怀旧情绪也就一直没有真正消失。
3. 由于 Apple 的操作系统发布节奏，过去这些年里，一直存在这样一种情况：某个 Xcode 里搭载着一个新的 Swift 编译器，配的却是一个旧的 Mac SDK，因而也就是一个旧的 Swift 标准库。这对 [Apple 的 Swift 团队来说是一个兼容性隐患](https://forums.swift.org/t/clarification-needed-on-unsafecontinuation-documentation/57803/16)，因为他们的编译器得同时支持这两种 SDK 一段时间（说不定旧的标准库里还有 bug 呢！），但这对开发者来说也很让人头疼，因为他们现在得区分 Swift *语言*层面的变化和 Swift *标准库*层面的变化。这种情况本来在 Objective-C 上也可能发生，但 Clang 和 Foundation 并不共用版本号，所以这一点没有那么扎眼。

这说得通吗？这就看你怎么想了。但既要支持可更新的操作系统库、又要保持向后兼容，是件很困难的事，而 Apple 会优先考虑前者、而不是后者，也就是那种「大家都应该升级到最新操作系统」的前瞻性思路，这一点应该不会让人感到意外。

1. 当 [Go](https://go.dev) 刚问世的时候，它在 macOS 上直接发起系统调用，以避开动态链接。Apple 告诉 Go 团队说这是不受支持的行为，而事实也的确如此：在下一个 macOS 大版本里，系统调用接口就变了。Go 项目不得不迅速推出一个新版本，根据操作系统版本对系统调用做条件判断，最终他们改成了 Apple 推荐的做法，转而使用 C 标准接口。

   Apple 是不是应该改变方向去跟 Linux 保持一致，明知道改变内核接口会破坏现有程序？这很难说。「不是所有改变都是进步，但所有进步都是改变」，而兼容性从定义上就是在限制改变。

   这是一个更大的话题，没有完美答案，所以我在这里就不多展开了。[↩︎](#fnref:go)
2. 出于安全原因，iOS 默认不允许 JIT；内置的 JavaScript JIT 是主要的例外。我不觉得这是个多大的缺点，因为 JIT *确实*会有续航上的代价（记住，Swift 项目是十多年前开始的），不过我的一些同事对 JIT 比我更乐观，尤其是因为 JIT 可以跨越操作系统库和 App 客户端的边界做优化，而不用担心向前或向后兼容性。也许有一天这还是会发生，但我并不抱太大期望；更可能的情况是，会出现其他一些能跨越 ABI 边界起作用的、小而有针对性的技巧。[↩︎](#fnref:jit)
3. 系统团队后来对我们挺不满的，因为他们当时正试图逐步淘汰 `/usr/lib` 下面的子目录。哎呀。不过我觉得我们本可以说服他们，说这么做是值得的，因为我们也不希望一个 App 的 rpath 仅仅因为它依赖了 Swift，就在 `/usr/lib/` 里找到其他*不相关*的库。

   另外，我知道我在图里把这些发布版本标成了「iOS」，但操作系统库那部分用的却是访达的图标。没关系，别在意这个。[↩︎](#fnref:usr)
4. Swift 的原生代码也并不总是最紧凑的，这部分是因为它那套非常动态的泛型模型，并不要求值都有统一的表示形式，再加上编译期特化，有时还会为一个函数多生成一份优化过的副本。相比之下，Objective-C 采用统一的表示形式，编译期优化的机会也很少，所以它的代码体积虽然可能比 C 更臃肿，但总体上是相当一致的。这也是又一个例子，说明 Swift 曾经非常有野心、也确实取得了一些了不起的灵活性，但可能在其他方面付出了代价。好在，即便不破坏 ABI，这方面依然*有*改进空间，而且这些改进也确实在持续进行。[↩︎](#fnref:code-size)
