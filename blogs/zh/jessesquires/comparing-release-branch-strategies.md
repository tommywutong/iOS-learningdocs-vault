> 原文：[Comparing release branch strategies](https://www.jessesquires.com/blog/2022/03/27/comparing-release-branch-strategies/)　·　Jesse Squires

我的[上一篇文章](https://www.jessesquires.com/blog/2022/03/26/gh-action-merge-release-to-main/)引发了一些关于发布分支策略的问题和讨论。据我所知，主要有两种策略，我在不同的团队和项目上都使用过。我认为有必要详细阐述这两者之间的区别，尤其是在考虑为管理发布而采用不同类型的自动化时，[这也是我上一篇文章的主题](https://www.jessesquires.com/blog/2022/03/26/gh-action-merge-release-to-main/)。

通常，发布流程涉及创建一个发布分支，并让它“浸泡”一段时间，通常是一两周。在此期间，会执行各种测试（自动化或人工），并对任何有问题的部分进行修复。到了某个时间点，你认为一切就绪，就可以发布你的 App 或部署你的网站。在发布流程中，一个主要任务是确定这些修复**在哪里**以及**如何**进行。

### 术语说明

在本文的其余部分，我假设你使用 Git 作为版本控制系统，并将主分支/默认分支称为 `main`，将发布分支称为 `release/*`，表示如 `release/1.5.3` 这样的命名模式。

“热修复发布（hot-fix release）”是指针对主要发布中发现的严重错误而进行的快速后续发布。例如，如果你发布了 App 的 `3.2.0` 版本，随后发现了一个影响大量用户的崩溃问题，那么你会尽快修复该问题并发布 `3.2.1` 版本。

无论你是否使用 Git，这里的一般概念应该可以轻松迁移到其他系统，例如 Mercurial。关于发布策略，我不确定它们是否有“官方”名称，但我将把它们分别称为“cherry-pick 到发布分支”策略和“合并发布分支到主分支”策略。

### Cherry-pick 到发布分支

在这种策略中，你从 `main` 创建一个 `release/*` 分支，然后就不再回溯。该发布分支**永远不会**合并回 `main`。完成后，可以在 Git 中为发布打上标签，用于历史记录。通常，该发布分支会被保留，要么无限期保留，要么直到确定可以安全删除且无需后续热修复发布为止。

主分支 `main` 上的开发继续全速进行。`release/*` 上出现的任何问题都**首先**在 `main` 上修复，然后将这些提交通过 cherry-pick 放入 `release/*`。如果两个分支已经充分分叉，或者 cherry-pick 过程中存在冲突，那么修复方案会**单独**直接应用于 `release/*`，不同于应用到 `main` 的修复——这会导致分支进一步分叉。但这种分叉不是问题，因为这些分支永远不会合并。结果是，并非所有来自 `release/*` 的提交都会回到 `main`。

如果需要热修复发布，则从主 `release/*` 分支创建一个热修复发布分支，其余流程与热修复发布分支相同。

看待这种发布策略的方式是，它是“以 `main` 为中心的”。你的主要焦点在 `main` 上，修复应用于 `main`，而 `release/*` 分支独立存在，不与其他分支交互。

### 合并发布分支到主分支

在这种策略中，你从 `main` 创建 `release/*` 分支，并持续保持两个分支同步。也就是说，`release/*` 分支会反复合并回 `main`，因为修复和更改**首先**发生在 `release/*` 上。完成后，可以在 Git 中为发布打上标签，最后执行一次从 `release/*` 到 `main` 的合并，然后可以删除 `release/*` 分支。

主 `main` 上的主要开发继续进行，但两个分支永远不会分叉。`release/*` 上出现的所有问题**首先在发布分支上修复**，然后该分支合并回 `main`。如果在尝试将修复带回 `main` 时两个分支之间存在冲突，则在一个中间分支上解决冲突，然后将该中间分支合并到 `main` 并随后删除。结果是，所有提交（最终）都回到 `main` 上，并且 `main` 始终领先于 `release/*`。

如果需要热修复发布，则从需要修补的发布的 Git 标签上创建一个热修复发布分支。然后继续相同流程。

看待这种发布策略的方式是，它是“以发布为中心的”。`release/*` 上的任何更改或修复都会合并回 `main`，确保 `release/*`（最终）没有任何领先于 `main` 的提交。

### 哪种策略最好？

在构建发布流程时，这里没有客观的“最佳”选项。哪种效果最好取决于你的团队和项目配置——但通常情况下，这些场景中会存在一些强制因素，从而为你应该使用哪种策略提供明确的答案。

根据我的经验，“cherry-pick 到发布分支”策略在大型公司的大型团队中最常见，尤其是在单一仓库（monorepo）中工作的情况下。事实上，我认为这种策略基本上是强制性的，否则发布流程将无法维持。在 Instagram/Facebook，我们遵循“cherry-pick 到发布分支”的方法——他们有一个包含所有 App 在所有支持平台上的所有代码的单一仓库，每天有数千人推送数十次提交。尝试持续将发布分支合并回 `main`（针对所有平台的所有 App！）在那种规模下几乎是不可能的。此外，他们构建了各种自定义基础设施来仅支持“以 `main` 为中心”的开发——一切必须先到达 `main`，并且有一个完整的管线来管理减少冲突，同时每天排队并落地数千个提交。“合并发布分支到主分支”方法在这种条件下根本不可行。

在较小的公司和较小的团队中，“合并发布分支到主分支”方法最为常见——在我看来，也最为合适。小型公司和团队常常试图模仿大公司，但大公司解决的问题远远超出了小公司可能遇到的范围。因此，如果你的（小）团队正在制定发布流程，我建议先选择更简单的选项。我认为“合并发布分支到主分支”策略在概念上更容易理解，尤其是关于 Git 分支的工作方式。这种策略本质上是 pull request 工作流的一个特例。在小团队中，你的分支上没有大公司那么多的流量，冲突的概率也很小，尤其是[当你自动化](https://www.jessesquires.com/blog/2022/03/26/gh-action-merge-release-to-main/)将 `release/*` 合并到 `main` 时。使用这种策略可以产生更清晰、更易理解的 Git 历史，并且你可以安全地立即修剪发布分支。由于你的团队中每个人都了解 pull request，这些知识可以直接迁移到发布流程中。

通常，特别是对于小团队，“cherry-pick 到发布分支”具有更高的维护成本。你必须先在 `main` 上落地、测试和验证修复，然后将其 cherry-pick 到 `release/*`，然后**再次**在 `release/*` 上进行测试和验证。自动化此过程虽然并非不可能，但更加困难和繁琐，因为你需要确切知道要从 `main` 中挑选哪些提交到 `release/*` 中。即使自动化了，通常也需要手动向某个工具提交一个提交 SHA，然后机器人可以尝试进行 cherry-pick。“cherry-pick 到发布分支”的另一个缺点是你最终需要处理分叉的分支，这在概念上更困难。相比之下，使用“合并发布分支到主分支”方法，你直接在 `release/*` 上落地、测试和验证，并且你知道这些更改会合并回 `main`。因此，你可以对从 `release/*` 合并到 `main` 的修复充满信心，并避免再进行一次测试和验证循环。此外，[自动化相当简单](https://www.jessesquires.com/blog/2022/03/26/gh-action-merge-release-to-main/)，因为你只是合并分支，而不是寻找特定的提交进行 cherry-pick。

最后需要指出的一点是，团队和项目往往会随着时间的推移而增长。虽然你最初可能会选择“合并发布分支到主分支”，但最终你可能别无选择，只能切换到“cherry-pick 到发布分支”。随着你的团队和项目发生变化，你的发布流程也应随之改变。
