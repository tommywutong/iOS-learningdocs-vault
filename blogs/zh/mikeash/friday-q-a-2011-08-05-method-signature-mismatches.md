Friday Q&A 2011-08-05：方法签名不匹配

作者：[Mike Ash](https://www.mikeash.com/)

**消息发送回顾**  
每当你在代码里写下一个 `[obj foo]` 这样的消息发送（message send），编译器都会在内部把它翻译成对下面这个函数的一次标准函数调用：

```
    id objc_msgSend(id self, SEL op, ...);
```

它还有几个变体，用来处理结构体返回值和对 `super` 的调用之类的情况，但它们本质上做的都是同一件事。

这个调用本身很正常，但这个函数却奇特而不寻常。被调用时，它会利用 `self` 和 `SEL` 参数查找需要调用的方法。找到方法之后，就跳转过去执行。它完全无视其他所有参数和返回值。

上面列出的原型直接取自 Apple 的 `objc/runtime.h` 头文件。它表明这个函数接受一个 `id`、一个 `SEL`，以及跟在其后的可变参数（variable arguments），并返回 `id`。这个原型是个谎言。由于这个函数奇特而不寻常的性质，它实际上并没有固定的原型。`objc_msgSend` 的正确原型，就是与它将要调用的那个方法的原型相匹配的原型。这就是所谓的「方法签名（method signature）」。如果调用方使用的原型与方法本身使用的原型不匹配，就会发生一些有趣的事情。

如果你想更详细地了解消息传递（messaging）和 `objc_msgSend` 究竟是如何工作的，请参阅我之前的文章[Objective-C 消息传递](https://www.mikeash.com/pyblog/friday-qa-2009-03-20-objective-c-messaging.html)。

**方法签名**  
Objective-C 是一门动态类型的面向对象语言，那么，方法签名必须匹配这件事又有什么大不了的呢？你可以把一个 A 类型的对象传给期望 B 类型的代码，只要它的行为举止得当，一切仍然照常工作。

遗憾的是，这只说对了一半，具体来说是「Objective」的那一半。在「C」的那一半里，上面说的统统不成立。在那个世界里，类型全是静态的，而且强制得并不那么严格；当你告诉编译器某个东西是 A 类型、而它实际上是 B 类型时，编译器会相信你。如果 A 和 B 在内存中的布局不一样，或者以其他方式不能精确匹配，就会酿成大乱。

方法签名无非就是各个参数的类型加上返回值类型。当你在类的 `@implementation` 里声明一个方法时，你给了编译器两条关键信息。第一，它声明了方法的名字，让这个类的使用者知道存在一个叫这个名字的方法。第二，它声明了方法的签名，让调用方知道如何生成正确的代码来调用它。

编译器在不知道方法签名的情况下，是不可能生成正确代码的。看看下面这个相当无害的调用：

```
    [foo doThing: 0];
```

现在再来看看这个方法几种不同的声明：

```
    - (void)doThing: (double)x;
    - (void)doThing: (void *)x;
    - (void)doThing: (char)x;
```

在这三种情况里，你传入的都是一个 `int`，它会被隐式转换（implicit conversion）成另一种类型。这个隐式转换发生在_调用点_（call site）。如果 `doThing:` 期望的是一个 `double` 参数，那么这个参数_必须_在调用发生之前就被转换成 `double`。如果编译器不知道参数类型，它就不会知道需要做这个转换。结果就是，调用方把一个 `int` 放在一个地方，而方法那边却从一个完全不同的地方去取一个 `double`，得到的数据毫无意义。

**ABI**  
这种情况下究竟会发生什么，取决于你所运行的具体架构在函数调用方面的底层细节。这些细节记录在相关架构的 ABI（application binary interface，应用二进制接口）里。这些细节在不同架构之间截然不同。例如，i386、x86-64 和 ARM 使用的函数调用约定（calling convention）就完全不同。本文我会把重点放在 ARM 上，因为它是这批架构里最干净的一个。其中的原则可以照搬到其他架构，尽管细节照搬不过去。

ARM 的函数调用约定可以从 ABI 文档的第 15 页开始找到，文档在这里：

[`http://infocenter.arm.com/help/topic/com.arm.doc.ihi0042d/IHI0042D_aapcs.pdf`](http://infocenter.arm.com/help/topic/com.arm.doc.ihi0042d/IHI0042D_aapcs.pdf)

这些细节大多在这里并不太重要，但有几条是关键。

函数的前四个参数通过寄存器 `r0-r3` 传递，每个寄存器可容纳 32 位。如果函数的参数多于四个，多余的参数就通过压栈来传递。不过，这假定参数都是 32 位的数据类型。对于 `long long` 和 `double` 这类 64 位数据类型，相关参数会占用两个寄存器（或两个栈槽），并且还会被对齐到从偶数序号的位置开始。

返回值通过存入 `r0` 来返回。这同样假设是 32 位数据类型。64 位数据类型则通过 `r0` 和 `r1` 返回。大于 32 位的结构体在返回时，由调用方分配一块内存来存放返回值，再把一个额外的隐藏参数传给函数，其中存放着那块内存的地址。

C 标准在这里也要掺和进来。当编译器完全找不到方法签名时，它会假定该方法签名接受 `...` 可变参数。C 为可变参数规定了类型提升（type promotion）。任何小于 `int` 的整数类型都会被提升为 `int`，`float` 类型的参数则会被提升为 `double`。

**后果**  
现在我们知道了参数是如何传递的，但这究竟_意味着_什么呢？

方法签名不匹配最常见的情形，是方法的声明完全不可见，于是编译器假定它接受 `...` 可变参数。这通常发生在忘记导入包含声明的头文件时。如前所述，类型在作为可变参数传递时会被提升。

就整数类型而言，这是无害的，至少在 ARM 上是这样。所有不超过 `int` 的整数类型都在单个寄存器或栈槽里传递，调用方最终会从数据中提取出正确的部分。

就浮点类型而言，如果方法接受一个 `float`，这就会造成大麻烦。这个 `float` 会被提升为 `double`，而 `double` 占用两个寄存器或栈槽。这样不仅方法只会加载到一半的数据（反正这半截数据单靠自己也没有任何意义），而且其后所有参数都会向下错位一个位置，导致方法给这些参数取到的也全是垃圾。如果这个 `float` 是奇数序号的参数，为了正确对齐，这个 `double` 还会被再往下推。

如果调用方传入的数值类型与方法期望的类型不同，同样会造成大麻烦。C 会在数值类型之间做静默转换。正常情况下，如果方法期望一个 `float` 而调用方传入一个 `int`，编译器会悄悄把这个值转换成 `float`，皆大欢喜。然而，如果没有方法签名可用，编译器就会原样把这个 `int` 传过去。方法随后会试图把这个位模式（bit pattern）解释成一个 `float`，结果自然毫无意义。如果两边使用的数据类型大小还不一样，比如期望 `double` 的地方传入了 `int`，或者期望 `long long` 的地方传入了 `char`，情况还会更糟。这不仅会让提取出来的数据出错，还会再一次让其余所有参数整体错位，最后它们拿到的也都是坏数据。

最后，返回类型冲突也可能带来问题。当没有任何声明时，编译器假定该方法返回 `id`。如果你会用到这个返回值，任何冲突都会很快暴露出来。如果你把返回值当成 `int` 来对待，编译器会就这个不匹配报一个错误。

问题出在你不用返回值的时候。如果方法返回的是指针或整数，那一切安好。然而，如果方法返回一个大的结构体，就会插入一个额外的隐藏参数来存放调用方为该结构体准备的存储空间的地址，这最终会让所有东西整体错位，所有参数里装的都是垃圾。如果你运气足够差，方法真的执行了返回，它会把返回值写到你的第一个参数所指示的任意位置，几乎可以肯定这不是你想要的结果。在某些架构上，某些浮点类型必须使用 `objc_msgSend_fpret` 变体，这里的不匹配可能导致之后出现离奇的崩溃，因为 CPU 的浮点状态已经变坏了。

（请注意，一般而言，语言本身并没有做出任何真正的保证，说当方法期望固定参数时，传递可变参数就一定能行得通。只不过碰巧，在你可能遇到的那些架构上，它_通常_能奏效。）

这种局面也让编译器无法检查你的代码。即使你只使用安全的数据类型，如果你不小心把一个 `NSNumber *` 传给了期望 `int` 的参数，编译器也无从向你大吼。这会导致对象的指针值被解释成一个数字，这不是你想要的。而有方法签名可用时，编译器就会改为给你报一个错误。

更少见的是真正存在方法签名不匹配的情况。这种情况发生在调用方看到的声明与方法实现所用的不一致的时候。这要求代码里同时存在两个名字相同但签名不同的方法。当一个对象变量声明为某个类型、但存进去的对象实际上是另一个类型时，就可能发生这种冲突。使用 `id` 类型的变量时也可能发生这种情况：要么编译器只看到了错误的那个声明，要么它两个都看到了却选错了那个。虽然编译器在不得不从多个不同的声明中做选择时会发出警告，但如果它只看到错误的那个声明，情况就格外恶劣，因为编译器_完全_看不出有什么问题，因此也就发不出任何形式的警告。

我们来看一个例子。下面是两个方法，分别声明在两个不同的类里：

```
    @interface Foo (MoreMethods)
    - (void)makeThingOfWidth: (int)width;
    @end

    @interface Bar (MoreMethods)
    - (void)makeThingOfWidth: (float)width;
    @end
```

这两个方法名字相同但签名不同。如果我们写的代码把这两个头文件都导入了，那么试图在一个 `id` 上使用这些方法的代码就会陷入麻烦：

```
    id obj = ...;
    [obj makeThingOfWidth: 42]; // 危险！
```

根据 `obj` 究竟是 `Foo` 还是 `Bar`，以及编译器决定使用哪个方法签名，最终可能会把垃圾数据传进方法。所幸这种情况编译器会发出警告。

更危险的是只导入了_一个_头文件、但最终却操纵了另一个类的实例的代码：

```
    #import <Foo.h> // 注意：没有 Bar.h

    id obj = [otherObj getMeABar];
    [obj makeThingOfWidth: 42];
```

这种代码_注定_会出错，而编译器对此_无法_生成任何错误或警告，因为在它看来根本不存在什么潜在问题。

总的来说，要同时避免这种情形和「多个签名同时可见」那种较为良性的情形，我建议在切实可行的情况下，尽量保证签名不同的方法也使用不同的名字。当做不到这一点时，用静态类型代替 `id`，要么能解决问题，要么至少会给出一个错误或警告，提示有地方出了问题。

**结语**  
方法签名不匹配会导致一些真正诡异的行为：从方法参数里冒出来的离奇数据，到看似随机的崩溃，而且这类崩溃往往要等到不匹配发生很久之后才会出现。

良好的 Objective-C 代码应该始终做到构建时零警告，而这是一个绝佳的例子，说明了这一点为什么重要。对于_几乎_所有可能导致方法签名不匹配的情况，编译器都会发出警告；而当它发出警告时，就必须把问题修好，才能消除这条警告。

在某些罕见的情况下，不匹配也可能在没有任何警告的情况下发生。所幸这种局面很难撞上，不太可能偶然发生。不过，正因为 Objective-C 对多个名字相同但签名不同的方法处理得如此之差，最好还是尽量保证签名不同的方法也使用不同的名字。
