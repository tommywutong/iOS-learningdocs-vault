Friday Q&A 2012-12-28：加载一个内存字节时会发生什么

作者 [Mike Ash](https://www.mikeash.com/)

**代码**
先从加载内存字节的代码开始。在 C 中，它看起来大致是这样：

```
    char *addr = ...;
    char value = *addr;
```

在 `x86-64` 上，这会编译成类似这样的代码：

```
    movsbl (%rdi),%eax
```

这条指令让 CPU 把位于 `%rdi` 中地址处的字节加载到 `%eax` 寄存器。在 ARM 上，编译器会生成：

```
    ldrsb.w r0, [r0]
```

虽然指令名称不同，但效果基本相同。它会加载位于 `r0` 中地址处的字节，并把值放入 `r0`。（编译器在这里复用了 `r0`，因为之后不再需要这个地址。）

现在 CPU 已经拿到了指令，软件部分就完成了。嗯，也许吧。

**指令解码与执行**
我不想在这里深入讨论 CPU 一般是如何执行代码的。简而言之，CPU 从内存中加载上面的指令，并对其解码以确定操作码和操作数。看到这是一条加载指令后，它就会在适当的地址发起内存加载。

**虚拟内存**
如今你可能会编程所针对的大多数硬件，以及过去几十年里的任何 Apple 平台，都使用虚拟内存。简单来说，虚拟内存将程序看到的内存地址与计算机实际 RAM 的物理内存地址分离开来。换句话说，当程序访问地址 `42` 时，实际访问的可能是物理 RAM 地址 `977305`。

这种映射按_页_进行。每页是一个 4kB 的内存块。如果为内存中的每个字节跟踪虚拟地址映射，开销会大得难以承受，因此实际映射的是页面。页面足够小，可以提供不错的粒度；又足够大，不会在维护映射时产生过多开销。

现代虚拟内存系统还能够为页面设置权限。页面可以是可读、可写或可执行的，也可以是它们的任意组合。如果程序尝试对一个没有相应权限的页面执行操作，或访问一个完全没有映射的页面，程序就会被暂停，并向操作系统引发一个故障。操作系统随后可以采取进一步措施，例如终止程序并生成崩溃报告，这就是你遇到常见的 `EXC_BAD_ACCESS` 错误时发生的事情。

负责这项工作的硬件叫作内存管理单元（Memory Management Unit，MMU）。MMU 会拦截所有内存访问，并根据当前的页面映射重新映射地址。

CPU 加载一个内存字节时，首先会把地址交给 MMU 进行转换。（这并不总是如此：某些 CPU 中，MMU 之前还有一层缓存。不过总体原理仍然不变。）

MMU 对地址做的第一件事是切掉最低的 12 位，留下一个纯粹的页面地址。2^12 等于 4096，因此最低的 12 位描述了地址在其页面内的位置。其余地址重新映射之后，再把最低的 12 位加回去，就能得到完整的物理地址。

拿到页面地址后，MMU 会查询转换后备缓冲区（Translation Lookaside Buffer，TLB）。TLB 是页面映射的缓存。如果所涉及的页面最近访问过，TLB 会记住该映射，并迅速返回物理页面地址，此时 MMU 的工作就完成了。

当 TLB 不包含给定页面的条目时，这称为 TLB 未命中（TLB miss），必须搜索整个页表来查找该条目。页表是一块描述当前进程中每个页面映射的内存。最常见的情况是，操作系统按照一种 MMU 能够直接理解的特殊格式，把页表放在内存中。TLB 未命中后，MMU 会搜索页表以找到适当的条目。如果找到了，就把它加载到 TLB 中并执行重新映射。

在某些架构上，页表映射完全由操作系统负责。当 TLB 未命中发生时，CPU 将控制权交给操作系统，由操作系统查找映射并将其填入 TLB。这种方式更灵活，但速度慢得多，在现代硬件中已经不常见。

如果在页表中找不到条目，就意味着给定地址根本不存在于 RAM 中。CPU 会通知操作系统，操作系统随后决定如何处理这种情况。如果操作系统认为该地址无效，就会终止程序，你会得到 `EXC_BAD_ACCESS`。有时操作系统认为地址有效，只是数据当前不在 RAM 中。如果数据被换出到磁盘、属于内存映射文件，或是刚刚分配且后备内存要按需提供，就可能出现这种情况。在这些情况下，操作系统会把相应数据加载到 RAM 中，向页表添加一个条目，然后让 MMU 在后备数据可用后将虚拟地址转换成物理地址。

**缓存**
拿到地址后，CPU 会查询自己的内存缓存。在很久以前，CPU 会直接与 RAM 通信。然而，CPU 速度的提升比内存速度快得多，直接访问已经不再可行。如果现代 CPU 每次内存访问都必须直接与现代 RAM 通信，我们的计算机速度会相对慢得像爬行一样。

缓存是一个将一组内存地址映射到内存内容的硬件结构。缓存按缓存行组织，每行通常为 32 到 128 字节。缓存中的每个条目都保存一个地址，以及与该地址对应的一整条缓存行。从缓存加载数据时，CPU 会检查请求的地址是否存在于缓存中；如果存在，就从该地址的缓存行中返回相应数据。

缓存通常有多个级别。由于硬件设计上的限制，更大的缓存必然更慢。通过设置多个级别，可以先检查一个小而快的缓存，再使用较慢但更大的缓存，从而避免访问 RAM 的代价。CPU 首先检查 L1 缓存，也就是第一级缓存。这个缓存很小，通常约为 16-64kB。如果其中包含所需数据，内存加载就完成了！但这太无聊了，所以我们假设这里的缓存都不包含正在加载的数据。

接下来是 L2 缓存。它更大，通常在 256kB 到数 MB 之间。某些 CPU 中，L2 缓存就是最后一级，因此这类 CPU 通常会配备更大的 L2 缓存。其他 CPU 还会有 L3 缓存，此时 L2 通常较小，并由一个很大的 L3 缓存作为补充。L3 通常有数 MB，一些高性能芯片甚至配备了高达 20MB 的 L3 缓存。

所有级别的缓存都尝试过之后，如果没有任何一级包含所需数据，就该尝试主存了。由于缓存按整行工作，即使我们只加载一个字节，也会一次性从主存中加载整条缓存行。这在常见的访问相邻内存的情况下能大幅提高效率，因为随后对相邻数据的加载可以从缓存中完成；代价是在内存使用分散时会浪费时间。

**内存**
终于到了查询 RAM 的时候。到此为止 CPU 已经等待了相当长时间，而在拿到所需数据之前还要等待很久。

加载操作会交给内存控制器，它是实际知道如何与 RAM 通信的硬件部分。在很多现代硬件上，内存控制器直接集成在 CPU 中；而在一些系统中，它是一个叫作“北桥”（northbridge）的独立芯片的一部分。

随后内存控制器开始从 RAM 加载数据。现代 SDRAM 一次传输 64 位数据，因此必须进行多次传输才能填满请求的整条缓存行。

内存控制器把加载地址放到 RAM 的地址引脚上，然后等待返回数据。在内部，RAM 使用地址引脚上的值激活一行内存单元，单元中的内容随后会出现在 RAM 的输出引脚上。

RAM 并非瞬时响应：从内存控制器请求一个地址到数据可用之间存在明显延迟，在当前硬件上约为 10 纳秒。为填满缓存行而进行的后续加载还需要更多时间，但这些加载可以流水线化，因此总传输时间可能只增加约 50%。

内存控制器从 RAM 获得数据后，会把数据交还给缓存。缓存会存储这些数据，以备很快需要同一缓存行中的其他数据。最后，请求的字节被交给 CPU，CPU 将数据放入指令所要求的寄存器中。经过所有这些工作之后，CPU 终于可以继续运行需要这个数据字节的代码了。

**后果**
这一切的工作方式会带来许多实际后果。特别是，内存访问相对来说_很慢_。你的计算机每秒真的可以完成上述工作数千万次，这很不可思议；但它每秒还可以完成数十亿次其他工作。一切都是相对的。

假设 MMU 命中 TLB（这是 MMU 的快速情况），完成这一切总共需要几十纳秒。在 2GHz CPU 上，这可能意味着大约 50 个时钟周期，而在这段时间里理论上可以执行约 150 条指令。这已经很多了。TLB 未命中可能会让这个延迟翻一倍或三倍。

现代 CPU 采用流水线和并行化设计。这意味着它们很可能会提前发现需要读取内存，并在那时启动加载，从而减轻影响。并行执行意味着，CPU 在等待加载时，可能能够继续执行加载指令_之后_的一些代码，尤其是不依赖所加载值的代码。不过这种能力是有限的，要找到 150 条可以在等待 RAM 时执行的指令并不容易。你几乎肯定会遇到程序执行必须停止并等待内存加载完成的时刻。

顺便说，这正是超线程（hyperthreading）能够带来优势的地方。CPU 核心不必在等待 RAM 时完全闲置，超线程可以让它切换到完全不同的执行线程，运行_那个_线程的代码，于是等待期间仍能完成有用的工作。

访问模式是影响性能的_关键_。关于微优化的讨论通常集中在使用某些指令而不是另一些、避免除法等方面。相对而言，很少有人讨论内存访问模式。然而，如果操作所访问的内存以不利于内存系统的方式加载，那么无论单条指令优化得多好都无济于事。如果每加载一块新数据都要等待几十个周期，那么零星节省几个周期根本毫无意义。例如，图像数据虽然用下面这种方式表达更自然，但你绝不应该这样写循环：

```
    for(int x = 0; x < width; x++)
        for(int y = 0; y < height; y++)
            // use the pixel at x, y
```

图像通常按连续的行排列，而这个循环_没有_利用这一事实。它访问的是列：加载完整的第一列之后，才回到第一行中的下一个像素。这会导致缓存和 TLB 未命中。与先遍历行、再遍历列相比，这个循环的速度会慢得多：

```
    for(int y = 0; y < height; y++)
        for(int x = 0; x < width; x++)
            // use the pixel at x, y
```

在许多情况下，仅仅因为内存访问延迟的惩罚如此之大，上面的循环即使循环体使用快速代码，也会被下面循环体使用慢速代码的循环远远超过。

更糟的是，诸如 Instruments 中 Apple 的 Time Profiler 之类的分析器并不擅长显示这些延迟。它们会告诉你哪些指令耗费了时间，但由于现代 CPU 的流水线和并行特性，真正承担内存加载代价的指令可能并不是实际的加载指令。CPU 执行到加载指令时，会把目标寄存器标记为数据尚未就绪，然后继续执行。当 CPU 执行到真正需要该寄存器值的指令时，_那时_才会停止并等待。一个线索是：对同一个值进行一连串操作时，第一条指令耗时_远远_超过后面的指令，也远远超过它本应耗费的时间。例如，如果你的代码执行 `load`、`add`、`mul`、`add`，而分析器显示第一个 `add` 占用了绝大多数时间，那么这很可能是内存延迟，而不是 `add` 本身很慢。

**结论**
现代计算机运行在难以想象的时间尺度上。对人类来说，单个 CPU 周期所需的时间和硬盘寻道所需的时间都短得无法区分，仿佛是瞬间完成的；然而它们相差许多个数量级。计算机是一个极其复杂的系统，加载内存中的一小块数据就需要大量事情发生。了解这一过程在硬件中如何发生很有趣，甚至还能帮助你写出更好的代码。再想想你用来阅读这篇文章的计算机每秒真的会执行这组复杂操作数百万次，这就更加不可思议了。
