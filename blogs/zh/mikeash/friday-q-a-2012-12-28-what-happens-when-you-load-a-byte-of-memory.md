Friday Q&A 2012-12-28：当你加载一个字节的内存时会发生什么

作者：[Mike Ash](https://www.mikeash.com/)

**代码**
我们先从加载一个字节内存的代码开始。在 C 语言中，它看起来像这样：

```
    char *addr = ...;
    char value = *addr;
```

在 `x86-64` 上，这会被编译成类似这样的指令：

```
    movsbl (%rdi),%eax
```

这条指令指示 CPU 加载存储在 `%rdi` 中的地址所指向的字节，并将其放入 `%eax` 寄存器。在 ARM 上，编译器会产生：

```
    ldrsb.w r0, [r0]
```

尽管指令名称不同，效果基本相同。它加载存储在 `r0` 中的地址所指向的字节，并将值放入 `r0`。（编译器在这里重用了 `r0`，因为地址不再需要了。）

CPU 有了它的指令之后，软件部分就完成了。嗯，也许吧。

**指令解码与执行**
我不想深入探讨 CPU 通常如何执行代码的细节。简而言之，CPU 从内存中加载上述指令并解码，以确定操作码和操作数。一旦它发现这是一条加载指令，就会在相应的地址发起内存加载。

**虚拟内存**
在当今你可能为之编程的大多数硬件上，以及过去几十年来的任何 Apple 平台上，系统都使用虚拟内存。简而言之，虚拟内存将你的程序看到的内存地址与你计算机中实际 RAM 的物理内存地址分离开来。换句话说，当你的程序访问地址 `42` 时，它可能实际上访问的是物理 RAM 地址 `977305`。

这种映射是按**页**进行的。每页是一个 4kB 的内存块。跟踪内存中每个字节的虚拟地址映射的开销会过于巨大，因此改为映射页。它们足够小以提供良好的粒度，但又足够大，不会在维护映射时产生过多开销。

现代虚拟内存系统还可以在页上设置权限。一个页可以是可读、可写或可执行的，或这些权限的某种组合。如果程序试图对一个不被允许的页进行操作，或试图访问一个根本没有映射的页，程序会被挂起，并向操作系统抛出一个错误（fault）。然后操作系统可以采取进一步行动，例如终止程序并生成崩溃报告，这就是当你遇到常见的 `EXC_BAD_ACCESS` 错误时发生的事情。

处理这项工作的硬件称为内存管理单元（Memory Management Unit，MMU）。MMU 拦截所有内存访问，并根据当前页映射重新映射地址。

当 CPU 加载一个字节的内存时，发生的第一件事就是将地址交给 MMU 进行转换。（这并不总是正确的。在某些 CPU 上，MMU 之前有一层缓存。然而，总体原理保持不变。）

MMU 对地址做的第一件事是切掉低 12 位，剩下一个纯粹的页地址。2^12 等于 4096，所以低 12 位描述地址在其页面内的位置。一旦地址的其余部分被重新映射，就可以加上低 12 位来生成完整的物理地址。

拿到页地址后，MMU 会查询转换后备缓冲区（Translation Lookaside Buffer，TLB）。TLB 是页映射的缓存。如果所查询的页最近被访问过，TLB 会记住映射，并快速返回物理页地址，此时 MMU 的工作就完成了。

当 TLB 中没有给定页的条目时，这被称为 TLB 未命中，必须通过搜索整个页表来找到该条目。页表是一块描述当前进程中每个页映射的内存。最常见的是，页表由操作系统以一种 MMU 可以直接理解的特殊格式布局在内存中。在 TLB 未命中后，MMU 会在页表中搜索相应的条目。如果找到，它会将其加载到 TLB 中并执行重新映射。

在某些架构上，页表映射完全由操作系统负责。当 TLB 未命中发生时，CPU 将控制权传递给操作系统，操作系统负责查找映射并用它填充 TLB。这种方式更灵活，但慢得多，在现代硬件中已不多见。

如果在页表中没有找到条目，那就意味着给定的地址在 RAM 中根本不存在。CPU 会通知操作系统，然后由操作系统决定如何处理这种情况。如果操作系统认为该地址无效，它将终止程序，你会得到 `EXC_BAD_ACCESS` 错误。在某些情况下，操作系统认为地址是有效的，只是数据不在 RAM 中。这种情况可能发生在数据已被换出到磁盘、是内存映射文件的一部分、或是新分配的且后备内存是按需提供的时候。在这些情况下，操作系统会将相应的数据加载到 RAM 中，向页表添加一个条目，然后让 MMU 在后备数据可用时，将虚拟地址转换为物理地址。

**缓存**
拿到地址后，CPU 会查询其内存缓存。在往昔岁月中，CPU 会直接与 RAM 通信。然而，CPU 速度的增长快于内存速度，这已不再可行。如果现代 CPU 每次内存访问都必须直接与现代 RAM 通信，我们的计算机将会慢得如同爬行。

缓存是一个从一组内存地址到内存内容的硬件映射。缓存被组织成缓存行（cache line），每个缓存行通常在 32-128 字节的范围内。缓存中的每个条目保存一个地址和与该地址对应的单个缓存行。当从缓存加载数据时，它会检查所请求的地址是否存在于缓存中，如果存在，则返回该地址缓存行中的相应数据。

通常有多个级别的缓存。由于硬件设计限制，较大的缓存必然较慢。通过拥有多个级别，可以先检查一个小而快的缓存，然后使用较慢、较大的缓存，以避免从 RAM 获取数据的成本。CPU 首先检查 L1 缓存，这是第一级。这个缓存很小，通常在 16-64kB 左右。如果它包含所请求的数据，那么内存加载就完成了！由于这很无趣，我们假设缓存不包含这里正在加载的数据。

接下来是 L2 缓存。这个更大，通常在 256kB 到几兆字节之间。在某些 CPU 中，L2 缓存是最后一级，这些 CPU 通常有更大的 L2 缓存。其他 CPU 还有一个 L3 缓存，在这种情况下，L2 通常更小，并通过一个大容量的 L3 缓存来补充，L3 缓存通常为几兆字节，一些高性能芯片拥有高达 20MB 的 L3 缓存。

当所有级别的缓存都尝试过后，如果它们都不包含必要的数据，那么就该尝试主内存了。因为缓存操作的是整个缓存行，所以即使我们只加载一个字节，整个缓存行也会一次性从主内存加载。这在访问附近其他内存的常见情况下极大地提高了效率，因为后续的邻近加载可以从缓存中获取，但代价是在内存使用分散时会浪费时间。

**内存**
终于到了开始查询 RAM 的时候了。CPU 至此已经等待了相当长的时间，而在它获得想要的数据之前，还要等待更长的时间。

加载任务被交给内存控制器（memory controller），这是实际知道如何与 RAM 通信的硬件部分。在许多现代硬件上，内存控制器直接集成到 CPU 中，而在某些系统上，它是称为“北桥”（northbridge）的独立芯片的一部分。

然后，内存控制器开始从 RAM 加载数据。现代 SDRAM 一次传输 64 位数据，因此必须进行多次传输才能填满所请求的整个缓存行。

内存控制器将加载地址放置在 RAM 的地址引脚上，并等待数据返回。在内部，RAM 使用地址引脚上的值来激活一行内存单元，这些单元的内容随后暴露在 RAM 的输出引脚上。

RAM 不是瞬时响应的，从内存控制器请求地址到数据可用之间存在明显的延迟，在当前硬件上大约为 10 纳秒。执行缓存行所需的后续加载需要更多时间，但这些加载可以流水线进行，因此总传输时间可能增加约 50%。

当内存控制器从 RAM 获取数据时，它将这些数据交还给缓存，缓存存储这些数据，以防同一缓存行中的其他数据很快被需要。最后，所请求的字节被交给 CPU，CPU 将数据放入指令请求的寄存器中。在所有这些工作完成之后，CPU 终于可以继续运行需要那个字节数据的代码。

**影响**
以上所有机制的运作方式，带来了许多实际影响。特别是，内存访问相对来说是**慢**的。你的计算机每秒能够执行字面上数千万次上述所有工作，这很惊人，但它可以每秒执行字面上数十亿次其他操作。一切都是相对的。

假设 TLB 命中（MMU 的快速情况），所有这些所需的总时间大约是几十纳秒。在一个 2GHz 的 CPU 上，这可能意味着大约 50 个时钟周期，在这段时间内可能执行大约 150 条指令。这很多。一次 TLB 未命中可能会使这个延迟数字加倍或三倍。

现代 CPU 是流水线和并行化的。这意味着它们可能会提前看到内存读取的需求，并在那时发起加载，从而减轻冲击。并行执行意味着 CPU 可能能够在加载指令**之后**继续执行一些代码，同时等待加载，尤其是那些不依赖于加载值的代码。然而，这些事情是有限度的，找到 150 条可以在等待 RAM 时执行的指令是一个高要求。你几乎肯定会遇到程序执行必须停止并等待内存加载完成的时刻。

顺便提一下，这正是超线程（hyperthreading）获得优势的地方。超线程不是让整个 CPU 核心在等待 RAM 时空闲，而是让它切换到完全不同的执行线程并运行**那个**线程的代码，这样它仍然可以在等待时完成有用的工作。

访问模式对于性能来说是**关键**。关于微优化的讨论往往集中在使用某些指令而非其他、避免除法等方面。相对较少的话题会谈论内存访问模式。然而，如果你的单个指令操作的内存是以对内存系统不友好的方式加载的，那么这些指令本身优化得再好也无济于事。如果每加载一个新数据块你都要等待几十个周期，那么这里省几个周期那里省几个周期就毫无意义。例如，这就是为什么尽管是更自然的表达方式，你永远不应该像这样编写循环来访问图像数据：

```
    for(int x = 0; x < width; x++)
        for(int y = 0; y < height; y++)
            // 使用位于 x, y 的像素
```

图像通常按连续的行布局，而这个循环**没有**利用这一事实。它访问列，只有在加载完整个第一列之后才回到第一行的下一个像素。这会导致缓存和 TLB 未命中。这个循环将比你先迭代行再迭代列的循环慢得多：

```
    for(int y = 0; y < height; y++)
        for(int x = 0; x < width; x++)
            // 使用位于 x, y 的像素
```

在许多情况下，循环体中有快速代码的顶部循环，其性能将远远不如循环体中有慢速代码的底部循环，仅仅是因为内存访问延迟可能非常严重。

更糟糕的是，性能分析器（例如 Instruments 中的 Apple Time Profiler）并不擅长显示这些延迟。它们会告诉你哪些指令花费了时间，但由于现代 CPU 的流水线和并行特性，承担内存加载代价的指令可能不是实际的加载指令。CPU 会命中加载指令，将其目标寄存器标记为尚未拥有数据，然后继续执行。当 CPU 命中一条实际需要该寄存器值的指令时，**才会**停下来等待。这里的线索是，当一系列对同一值进行操作的指令中的第一条指令所花费的时间**远**长于其余指令，并且远长于其应有时间时。例如，如果你的代码执行了 `load`、`add`、`mul`、`add`，而分析器显示第一个 `add` 占据了绝大多数时间，那么这很可能是内存延迟，而不是 `add` 指令本身慢。

**结论**
现代计算机在难以想象的时间尺度上运行。对人类来说，单个 CPU 周期所需的时间和执行一次硬盘寻道所需的时间都看似瞬间完成，然而它们之间相差多个数量级。计算机是一个极其复杂的系统，需要发生大量的事情才能从内存中加载一个数据块。了解在硬件层面发生了什么是令人着迷的，甚至可以帮助你编写更好的代码。更令人难以置信的是，你用来阅读本文的计算机中，每秒都发生着数百万次这样复杂的操作序列。
