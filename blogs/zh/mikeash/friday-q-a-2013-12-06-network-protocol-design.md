Friday Q&A 2013-12-06：网络协议设计

作者：[Mike Ash](https://www.mikeash.com/)

**TCP 和 UDP**  
我想读者已经了解 TCP 和 UDP 了，但以防你不了解或需要复习，我简单介绍一下。

基础的互联网协议被称为（富有想象力地）Internet Protocol（IP）。有多个版本，其中最常用的是版本 4 和版本 6，分别称为 IPv4 和 IPv6。这些协议处理网络通信中最基本的路由和寻址任务。

更智能的协议构建在此基础上。有很多协议，但最常用的是两种：TCP 和 UDP。UDP（User Datagram Protocol，用户数据报协议）是 IP 之上的一个简单层，它提供了寻址特定计算机上的单独**端口**的能力，以及可选的数据完整性校验和。数据仍然作为独立的包发送，这些包可能会丢失、重复或乱序接收。

TCP（Transmission Control Protocol，传输控制协议）是一种更复杂、功能更强的协议。它抽象了互联网不可靠的基于包的本质，为应用程序提供了一个简单的流接口，其中字节在一端传输，在另一端接收。它会自动重传丢失的数据并确保正确的顺序。

选择哪种协议取决于你的需求。如果你想要一个具有可靠传递的字节流，那么 TCP 是显而易见的选择。然而，TCP 坚持恢复丢失数据会损害性能。在某些情况下，例如游戏，你宁愿跳过丢失的包而不是等待重新传输，TCP 的智能反而会拖慢你。因此，UDP 是实时游戏、低延迟音频/视频流以及其他类似任务的不错选择。

**多连接**  
许多复杂的协议使用多个并发连接。可能有一个 TCP 连接用于会话初始化和控制，另一个 TCP 连接用于批量数据传输，一个 UDP 连接用于时间敏感数据等。

无论你做什么，都不要这样做。将事物分开管理似乎更简单，但它最终会极大地复杂化协议。这意味着每一方都必须管理多个套接字（socket）而不是一个。这意味着线路协议现在必须了解底层传输协议，并且突然之间，一堆本来不关心的代码现在必须知道 IPv4 和 IPv6 之间的区别。它还会对 NAT 和防火墙造成严重破坏，因为你必须打开多个端口而不是一个，并且其中一些端口可能是动态选择的，因此难以在防火墙上列入白名单。

始终使用单个连接。如果你需要支持多个流，请使用一个在单个连接上处理多路复用多个流的基础协议。如果某些数据需要 TCP 而其他数据需要 UDP，那么你最好的选择是在 UDP 之上重新实现必要的 TCP 功能。如果你想流式传输大量数据，那么编写代码将其分解为块并单独发送。抽象地看，仅仅打开一个单独的 TCP 连接并让套接字库为你处理它是个好主意，但最终得不偿失。

**握手**  
在开始传输实际数据之前，双方交换一些握手信息通常很方便。以某种标识符（例如你的 App 的 bundle ID）开始传输，有助于明确是什么产生了流量，并防止其他软件的意外连接进行得太远。

随着软件的发展，版本信息在扩展协议时极其有用。我喜欢传输一个主版本号和一个次版本号，两者都是普通整数，不打算与软件的人类可读版本号同步。次版本号旨在指示可选功能或旧版本的已知特性，但版本不匹配时仍应允许连接继续。主版本号不匹配应用于指示无法进行通信。传输该信息允许版本较新的一方回退到较早的版本——如果你编写了代码仍然支持旧版本的话。

**帧划分**  
TCP 连接通常需要某种方式来分帧，以指示一段数据在哪里结束，下一段数据从哪里开始。这可能用于分隔多个命令、请求或数据块。你可以将分帧方式合并到你的通用数据格式中，但最好保持两者分离。通过拥有一个仅仅保持任意数据块分离的帧协议，你最终会得到更可重用的代码。该协议通常也更容易理解和调试，因为你可以分别考虑帧协议和内部数据协议。

构建帧协议的一个简单方法是使用长度前缀。传输帧的字节长度，然后传输帧数据，然后重复。长度可以是二进制或文本，取决于你的意愿。这易于读写，但不适用于大型流数据，因为你必须在传输任何数据之前知道帧的大小。

一个不错的帧协议是 Consistent Overhead Byte Stuffing（COBS，一致开销字节填充）。它的工作原理是用零字节终止每个帧，然后对帧内的数据进行编码以消除所有零字节。这会带来少量开销，不到数据长度的 1%。该编码适用于流数据，并且占用很少的 CPU 资源。

**文本与二进制**  
数据格式应该是文本还是二进制的问题是一个长期的争论，没有定论。有时存在一些约束使得答案变得显而易见。例如，媒体数据更适合以二进制格式存储，因为涉及的数据量很大。旨在以原始格式供人类阅读的数据应该是文本，因为人类很难阅读二进制。

在其他情况下，文本与二进制的问题并不那么明确。这个问题目前正在 HTTP 世界中上演，其中主要基于文本的 1.1 版本正在被基于二进制的 2.0 版本所取代。二进制更高效，但文本通常更容易使用。

当有疑问时，倾向于基于文本的协议。能够从命令行 telnet 到你尚未完全实现的服务器，并在嗅探器中无需额外工作就能读取线路协议，可以真正加快开发速度。

**文本格式**  
在文本格式领域有很多可能性。传统格式往往是行分隔的临时格式，这些格式不一定发展得很好。例如，HTTP 对于传输超文本来说是一个足够好的协议，但随着时间的推移，它积累了越来越多的 hack 来处理媒体文件、管道连接、流和断点续传，以某种方式适应了最初的设计。

像 JSON 或 Apple 属性列表（property list，plist）这样的东西非常适合这个。协议可以在更高级别上以字典、映射、字符串等术语进行设计，然后可以使用标准、可读的格式进行编码，以便在线路上发送。

属性列表的一个有趣优势是，你可以在原型设计时使用 XML 格式，然后在网络代码稳定后切换到二进制格式以获得更好的性能。当然，缺点是属性列表在非 Apple 平台上的支持不够好。

始终考虑可扩展性。对于 JSON 和属性列表，这意味着顶级对象**永远不**应该是数组，或除字典之外的任何东西。这允许随时添加额外的键，而软件的旧版本只会忽略它们。

我遇到过提供带有任意键的字典的软件，而接收方旨在遍历所有键。这实际上提供了一组键/值对，并遭受与数组相同的可扩展性问题。不要这样做。

**二进制格式**  
虽然我倾向于在合理的情况下使用文本，但有时候你真的需要二进制格式，要么出于性能原因，要么仅仅因为它更适合你的数据。

[Google Protocol Buffers](https://code.google.com/p/protobuf/)，即 protobuf，在这里是一个很好的选择。它们结构化程度足够高，可以提供属性列表或 JSON 的大部分好处，同时还提供了二进制格式的性能优势。它们的工作方式与大多数常见的序列化（serialization）库略有不同，因为你编写一个格式定义，然后将其编译为代码并包含到你的 App 中。然后编译后的代码就知道如何编码和解码符合你格式的 protobuf。这使得它们在项目中使用起来不那么自然，因为生成的代码必须以某种方式包含在内，但这也意味着生成的代码很快。

如果你想创建自己完全自定义的二进制格式，那么有一些指南可以让你的生活更轻松。

在合理的情况下，使整体格式可扩展。太多的格式被指定为固定数量的固定宽度字段。当添加另一个字段时，混乱随之而来，必须使用全新的格式版本，并且任何想要同时处理两者的代码都需要开始特殊处理新字段。相反，给每个字段一个名称，即使简单如四个字符的代码，并通过查看字段名称来编写能够处理任意顺序字段的代码。还要在数据本身中指定每个字段的长度，以便不了解某个字段的读取器仍然可以跳过其数据并继续读取它知道的其他字段。

在存储原始整数时，你必须在它们存储为大端序（最高有效字节在前）还是小端序（最低有效字节在前）之间做出选择。从技术上讲，你可以通过添加一个标志来指示特定字段使用哪种顺序来支持两者，但这完全是疯狂的。做出这个选择应该很简单：**使用大端序**。如今这并非特别自然的选择，因为我们几乎总是在小端序计算机上运行代码（x86 始终是小端序，iOS 以小端序模式运行 ARM）。然而，大端序被定义为“网络字节顺序”，并且是 IP 和 TCP 等协议中使用的标准字节顺序。在这种情况下，最好不要兴风作浪。做其他人都在做的事情，并使用网络字节顺序（即大端序）通过网络传输你的二进制数字。

另外，考虑你的整数数据是否应该具有固定宽度。想当然地说“这是一个 32 位值”然后继续是很有诱惑力的，但这可能会引起麻烦。如果将来你需要该值包含大于 2^32-1 的内容，你就完蛋了。在更可能的情况下，该字段中存储的大多数值都很小，你就会浪费字节。可变长度整数编码可以很好地解决这些问题。如果你已经在格式中传输了字段的长度，那么你可以利用这一点只使用实际需要的字节数来表示数字。如果你传输的值小于 256，只写出一个字节。如果你传输的值小于 65,536，写出两个字节。对于不适合这种情况的地方（例如编码长度字段本身），你可以使用可变长度整数编码。

编码可变长度整数的一种常见方法是借用每个字节的最高位来指示你是否已经到达数字的末尾。最高位为 `1` 的字节表示后面还有更多字节。最高位为 `0` 的字节表示这是最后一个字节。然后数字以七位一组的方式编码，仅在最后一个字节中最高位设置为 `0`。解码器可以一直读取字节，直到看到最高位为 `0`，然后从每个字节的其他七位构造数字。维基百科将此称为[可变长度量](http://en.wikipedia.org/wiki/Variable-length_quantity)，其变体用于许多不同的数据格式。

最后，让我们谈谈文本。二进制格式通常仍然需要存储文本，例如元数据或用户输入。有很多表示文本的方法，但再一次，选择很简单：使用 UTF-8。不要使用任何其他编码，甚至**不要考虑**使用任何其他编码。使用 UTF-8，然后完成。

有几种理由偏好 UTF-8。首先，它可以表示 Unicode 中可以表示的任何文本，这几乎是任何内容。其次，使用不同编码编码的文本极不可能产生能解码为有效（但不正确）UTF-8 的数据，这意味着你可以高度确信你解码的 UTF-8 字符串确实是用 UTF-8 编码的。第三，UTF-8 在编码 ASCII 字符时与 ASCII 相同，这使得 UTF-8 字符串易于手动阅读和易于处理。第四，UTF-8 在最佳情况下相当节省空间，在最坏情况下也只比其他 Unicode 编码略低效。

还要确保文本以可变长度格式存储，要么使用长度前缀，要么使用终止零字节。这里的原因与整数的原因相同，甚至更甚。文本长度的变化远大于整数长度，而固定宽度的文本字段是直接走向疯狂的好方法。

**结论**  
自定义网络协议不是常见需求，但它们偶尔仍然会出现。首先，根据你的需求在 TCP 和 UDP 之间做出选择。在单个连接上运行所有内容，如果需要，在协议内部处理多路复用。在通过 TCP 运行时使用单独的帧协议，而不是尝试在格式内部界定数据。尽可能偏好基于文本的格式，并在有意义时构建可扩展、合理的二进制格式。在所有地方为所有文本使用 UTF-8。
