Friday Q&A 2017-06-30：深入剖析 ARM64 上的 objc_msgSend

作者：[Mike Ash](https://www.mikeash.com/)

**概述**  
每个 Objective-C 对象都有一个类（class），每个 Objective-C 类都有一个方法列表。每个方法都有一个选择器（selector）、一个指向实现的函数指针以及一些元数据。`objc_msgSend` 的任务是接收传入的对象和选择器，查找对应方法的函数指针，然后跳转到该函数指针。

查找方法可能极其复杂。如果在当前类上没有找到方法，则需要继续在超类（superclass）中搜索。如果完全找不到方法，则需要调用运行时的消息转发代码。如果这是发送给某个特定类的第一条消息，则必须调用该类的 `+initialize` 方法。

在常见情况下，查找方法还需要极其快速，因为每次方法调用都会执行此操作。这，当然，与复杂的查找过程存在冲突。

Objective-C 解决此冲突的方案是方法缓存（method cache）。每个类都有一个缓存，它以选择器和函数指针（在 Objective-C 中称为 `IMP`）对的形式存储方法。这些方法组织成一个哈希表，因此查找速度很快。查找方法时，运行时首先查询缓存。如果缓存中没有该方法，则遵循缓慢而复杂的过程，然后将结果放入缓存，以便下次可以快速查找。

`objc_msgSend` 是用汇编语言编写的。原因有二：一是无法在 C 语言中编写一个能保留未知参数并跳转到任意函数指针的函数。该语言没有表达此类事物所需的特性。另一个原因是 `objc_msgSend` 的速度极其重要，因此它的每条指令都是手工编写的，以便尽可能快。

当然，你不想用汇编语言编写整个复杂的消息查找过程。也没有必要，因为一旦开始执行这个过程，无论怎样速度都会变慢。消息发送代码可以分为两部分：`objc_msgSend` 本身的**快速路径（fast path）**，用汇编编写；以及用 C 实现的**慢速路径（slow path）**。汇编部分在缓存中查找方法，如果找到则跳转到它。如果缓存中没有该方法，则调用 C 代码来处理。

因此，当我们查看 `objc_msgSend` 本身时，它执行以下操作：

1. 获取传入对象的类。
2. 获取该类的缓存。
3. 使用传入的选择器在缓存中查找方法。
4. 如果不在缓存中，则调用 C 代码。
5. 跳转到该方法的 `IMP`。

它是如何完成所有这些的呢？我们来看看！

**逐条指令分析**  
`objc_msgSend` 根据情况有几种不同的执行路径。它有专门处理发送给 `nil`、标签指针（tagged pointer）以及哈希表冲突等情况的代码。我将首先查看最常见的直线路径，即向非 `nil`、非标签指针发送消息，并且无需扫描就在缓存中找到方法的场景。在分析过程中，我会指出各个分支点，然后在我们完成常见路径后，我会绕回来查看所有其他路径。

我会列出每条指令或指令组，然后说明它的作用以及原因。请记住向上查找以找到正在讨论的文本所对应的指令。

每条指令前面都有一个从函数起始位置的偏移量。这既充当计数器，也让你能够识别跳转目标。

ARM64 有 31 个 64 位宽的整数寄存器。它们使用 `x0` 到 `x30` 表示。也可以将每个寄存器的低 32 位当作一个单独的寄存器来访问，使用 `w0` 到 `w30`。寄存器 `x0` 到 `x7` 用于将前八个参数传递给函数。这意味着 `objc_msgSend` 在 `x0` 中接收 `self` 参数，在 `x1` 中接收选择器 `_cmd` 参数。

让我们开始吧！

```
    0x0000 cmp     x0, #0x0
    0x0004 b.le    0x6c
```

这执行了 `self` 与 `0` 的有符号比较，如果值小于或等于零则跳转到其他地方。值为零是 `nil`，因此这处理了向 nil 发送消息的特殊情况。这还处理了[标签指针](https://www.mikeash.com/pyblog/friday-qa-2012-07-27-lets-build-tagged-pointers.html)。在 ARM64 上，标签指针通过设置指针的高位来表示。（这与 x86-64 形成有趣的对比，后者使用的是低位。）如果高位被设置，则该值以有符号整数解释时为负数。对于 `self` 是普通指针的常见情况，不会执行此分支。

```
    0x0008 ldr    x13, [x0]
```

这通过加载 `x0` 指向的 64 位量来加载 `self` 的 `isa`，`x0` 包含 `self`。`x13` 寄存器现在包含 `isa`。

```
    0x000c and    x16, x13, #0xffffffff8
```

ARM64 可以使用[非指针 isa](http://www.sealiesoftware.com/blog/archive/2013/09/24/objc_explain_Non-pointer_isa.html)。传统上 `isa` 指向对象的类，但非指针 `isa` 通过将一些其他信息也塞入 `isa` 来利用空闲位。此指令执行逻辑 AND 来屏蔽所有额外位，并将实际的类指针留在 `x16` 中。

```
    0x0010 ldp    x10, x11, [x16, #0x10]
```

这是我在 `objc_msgSend` 中最喜欢的指令。它将类的缓存信息加载到 `x10` 和 `x11` 中。`ldp` 指令将内存中的数据加载到前两个参数命名的寄存器中。第三个参数描述了从哪里加载数据，这里是从 `x16` 偏移 `16` 的位置，这是类中保存缓存信息的区域。缓存本身看起来像这样：

```
    typedef uint32_t mask_t;

    struct cache_t {
        struct bucket_t *_buckets;
        mask_t _mask;
        mask_t _occupied;
    }
```

在执行 `ldp` 指令后，`x10` 包含 `_buckets` 的值，`x11` 在其高 32 位包含 `_occupied`，低 32 位包含 `_mask`。

`_occupied` 指定哈希表包含的条目数，在 `objc_msgSend` 中不起作用。`_mask` 很重要：它描述了哈希表的大小，作为一个方便的、可进行 AND 操作的掩码。它的值总是 2 的幂减 1，用二进制表示就是类似 `000000001111111` 的形式，末尾有可变数量的 1。这个值是确定选择器的查找索引，以及在搜索表时处理到达末尾后折回所必需的。

```
    0x0014 and    w12, w1, w11
```

此指令计算传入的 `_cmd` 的起始哈希表索引。`x1` 包含 `_cmd`，因此 `w1` 包含 `_cmd` 的低 32 位。`w11` 包含上面提到的 `_mask`。此指令将两者进行 AND 运算，并将结果放入 `w12`。结果等同于计算 `_cmd % table_size`，但无需昂贵的取模运算。

```
    0x0018 add    x12, x10, x12, lsl #4
```

仅有索引还不够。要开始从表加载数据，我们需要实际的加载地址。此指令通过将表索引与表指针相加来计算该地址。它先将表索引左移 `4` 位，相当于乘以 `16`，因为每个表 bucket 是 `16` 字节。`x12` 现在包含要搜索的第一个 bucket 的地址。

```
    0x001c ldp    x9, x17, [x12]
```

我们又见到了老朋友 `ldp`。这次它是从 `x12` 指向的地址加载数据，该地址指向要搜索的 bucket。每个 bucket 包含一个选择器和一个 `IMP`。`x9` 现在包含当前 bucket 的选择器，`x17` 包含 `IMP`。

```
    0x0020 cmp    x9, x1
    0x0024 b.ne   0x2c
```

这些指令将 bucket 中的选择器（`x9`）与 `_cmd`（`x1`）进行比较。如果它们不相等，则此 bucket 不包含我们正在查找的选择器的条目，在这种情况下，第二条指令跳转到偏移量 `0x2c`，用于处理不匹配的 bucket。如果选择器匹配，则说明找到了我们想要的条目，执行将继续到下一条指令。

```
    0x0028 br    x17
```

这执行无条件跳转到 `x17`，其中包含从当前 bucket 加载的 `IMP`。从这里开始，执行将进入目标方法的实际实现，这是 `objc_msgSend` 快速路径的终点。所有参数寄存器都未被更改，因此目标方法将接收所有传入的参数，就像它被直接调用一样。

当一切都被缓存且所有条件都完美配合时，此路径在现代硬件上的执行时间可以少于 3 纳秒。

这是快速路径，那其余的代码呢？让我们继续查看处理不匹配 bucket 的代码。

```
    0x002c cbz    x9, __objc_msgSend_uncached
```

`x9` 包含从 bucket 加载的选择器。此指令将其与零比较，如果为零则跳转到 `__objc_msgSend_uncached`。零选择器表示一个空的 bucket，而空的 bucket 意味着搜索失败。目标方法不在缓存中，此时需要回退到执行更全面查找的 C 代码。`__objc_msgSend_uncached` 处理这种情况。否则，bucket 不匹配但不为空，搜索继续。

```
    0x0030 cmp    x12, x10
    0x0034 b.eq   0x40
```

此指令将 `x12` 中的当前 bucket 地址与 `x10` 中的哈希表起始地址进行比较。如果相等，则跳转到将搜索折回哈希表末尾的代码。我们还没有看到，但实际上这里执行的哈希表搜索是**向后**进行的。搜索检查递减的索引，直到到达表头，然后从末尾重新开始。我不确定为什么采用这种方式，而不是更常见的递增地址然后折回开头的方式，但可以肯定是因为这种方式最终更快。

偏移量 `0x40` 处理折回的情况。否则，执行继续到下一条指令。

```
    0x0038 ldp    x9, x17, [x12, #-0x10]!
```

又是一个 `ldp`，再次加载一个缓存 bucket。这次，它从当前缓存 bucket 地址减去 `0x10` 的偏移量处加载。地址引用末尾的感叹号是一个有趣的特性。这表示**寄存器写回（register write-back）**，意味着寄存器会用新计算出的值更新。在这种情况下，除了加载新的 bucket 之外，它实际上还执行了 `x12 -= 16`，这使得 `x12` 指向这个新的 bucket。

```
    0x003c b      0x20
```

既然新的 bucket 已加载，执行可以恢复检查当前 bucket 是否匹配的代码。这会循环回到上面标记为 `0x0020` 的指令，并使用新值再次运行所有这些代码。如果持续遇到不匹配的 bucket，此代码将继续运行，直到找到匹配、遇到空 bucket 或到达表头。

```
    0x0040 add    x12, x12, w11, uxtw #4
```

这是搜索折回时的目标地址。`x12` 包含当前 bucket 的指针，在这种情况下也是第一个 bucket。`w11` 包含表掩码，即表的大小。此指令将两者相加，同时将 `w11` 左移 4 位，即乘以 `16`。结果是 `x12` 现在指向表的末尾，搜索可以从那里继续。

```
    0x0044 ldp    x9, x17, [x12]
```

现在熟悉的 `ldp` 将新的 bucket 加载到 `x9` 和 `x17` 中。

```
    0x0048 cmp    x9, x1
    0x004c b.ne   0x54
    0x0050 br     x17
```

这段代码检查 bucket 是否匹配，并跳转到 bucket 的 `IMP`。它是上面 `0x0020` 处代码的副本。

```
    0x0054 cbz    x9, __objc_msgSend_uncached
```

和之前一样，如果 bucket 为空，则表示缓存未命中，执行进入用 C 实现的全面查找代码。

```
    0x0058 cmp    x12, x10
    0x005c b.eq   0x68
```

这**再次**检查是否折回，如果第二次到达表头则跳转到 `0x68`。在这种情况下，它会跳转到用 C 实现的全面查找代码：

```
    0x0068 b      __objc_msgSend_uncached
```

这实际上应该永远不会发生。表会随着条目的添加而增长，并且永远不会 100% 满。当哈希表太满时，会变得效率低下，因为冲突变得过于常见。

为什么这里要这样做？源代码中的一条注释解释了原因：

> 当缓存损坏时，克隆扫描循环以避免**挂起（hang）**而转至未命中。慢速路径可能会检测到任何损坏并随后停止。

我怀疑这种情况不常见，但显然 Apple 的人看到过导致缓存充满错误条目的内存损坏，跳转到 C 代码可以改善诊断。

此检查的存在对未遭受此损坏的代码影响最小。没有它，原始的循环可以被重用，这可以节省一些指令缓存空间，但影响很小。无论如何，这个折回处理程序都不是常见情况。它只会在选择器被散列到哈希表开头附近时被调用，并且仅当存在冲突且之前的所有条目都被占用时才会被调用。

```
    0x0060 ldp    x9, x17, [x12, #-0x10]!
    0x0064 b      0x48
```

此循环的其余部分与之前相同。将下一个 bucket 加载到 `x9` 和 `x17` 中，更新 `x12` 中的 bucket 指针，并返回循环顶部。

`objc_msgSend` 的主体到此结束。剩下的是处理 `nil` 和标签指针的特殊情况。

**标签指针处理程序**  
你会记得，最开始的几条指令检查了这些并跳转到偏移量 `0x6c` 进行处理。让我们从那继续：

```
    0x006c b.eq    0xa4
```

我们到达这里是因为 `self` 小于或等于零。小于零表示标签指针，零是 `nil`。这两种情况的处理方式完全不同，因此这里的代码首先检查 `self` 是否为 `nil`。如果 `self` 等于零，则此指令分支到 `0xa4`，这是 `nil` 处理程序所在的位置。否则，它是一个标签指针，执行继续到下一条指令。

在我们继续之前，让我们简要讨论一下标签指针的工作原理。标签指针支持多个类。标签指针（在 ARM64 上）的最高四位指示该“对象”属于哪个类。它们本质上就是标签指针的 isa。当然，四位远不足以容纳一个类指针。相反，有一个特殊的表，存储了可用的标签指针类。通过在该表中查找与最高四位相对应的索引，可以找到标签指针“对象”的类。

这还不是全部。标签指针（至少在 ARM64 上）还支持扩展类。当最高四位全部设置为 `1` 时，接下来的八位用于索引到扩展标签指针类表。这允许运行时支持更多标签指针类，代价是可供它们使用的存储空间更少。

让我们继续。

```
    0x0070 mov    x10, #-0x1000000000000000
```

这将 `x10` 设置成一个整数，其最高四位被设置，所有其他位为零。这将用作一个掩码来从 `self` 中提取标签位。

```
    0x0074 cmp    x0, x10
    0x0078 b.hs   0x90
```

这检查是否是扩展标签指针。如果 `self` 大于或等于 `x10` 中的值，则意味着最高四位全被设置。在这种情况下，分支到 `0x90`，它将处理扩展类。否则，使用主标签指针表。

```
    0x007c adrp   x10, _objc_debug_taggedpointer_classes@PAGE
    0x0080 add    x10, x10, _objc_debug_taggedpointer_classes@PAGEOFF
```

这一小段代码加载了 `_objc_debug_taggedpointer_classes` 的地址，这是主标签指针表。ARM64 需要两条指令来加载一个符号的地址。这是类 RISC 架构上的标准技术。ARM64 上的指针是 64 位宽，而指令只有 32 位宽。不可能将整个指针放入一条指令中。

x86 没有这个问题，因为它有可变长度指令。它可以直接使用一个 10 字节的指令，其中两个字节标识指令本身和目标寄存器，八个字节保存指针值。

在具有固定长度指令的机器上，你需要分块加载该值。在这种情况下，只需要两块。`adrp` 指令加载值的高位部分，然后 `add` 指令加上低位部分。

```
    0x0084 lsr    x11, x0, #60
```

标签类索引位于 `x0` 的最高四位。要将其用作索引，需要将其右移 `60` 位，使其成为一个范围在 `0-15` 的整数。此指令执行该移位并将索引放入 `x11`。

```
    0x0088 ldr    x16, [x10, x11, lsl #3]
```

这使用 `x11` 中的索引从 `x10` 指向的表中加载条目。`x16` 寄存器现在包含此标签指针的类。

```
    0x008c b      0x10
```

类在 `x16` 中，我们现在可以分支回主代码。从偏移量 `0x10` 开始的代码假定类指针已加载到 `x16` 中，并从那里执行派发。因此，标签指针处理程序可以分支回那段代码，而无需在此处复制逻辑。

```
    0x0090 adrp   x10, _objc_debug_taggedpointer_ext_classes@PAGE
    0x0094 add    x10, x10, _objc_debug_taggedpointer_ext_classes@PAGEOFF
```

扩展标签类处理程序看起来类似。这两条指令加载指向扩展表的指针。

```
    0x0098 ubfx   x11, x0, #52, #8
```

此指令加载扩展类索引。它从 `self` 中的第 `52` 位开始提取 `8` 位到 `x11`。

```
    0x009c ldr    x16, [x10, x11, lsl #3]
```

和之前一样，该索引用于在表中查找类并加载到 `x16`。

```
    0x00a0 b      0x10
```

类在 `x16` 中，它可以分支回主代码。

这几乎就是全部了。剩下的只有 `nil` 处理程序。

**`nil` 处理程序**  
最后我们来看 `nil` 处理程序。以下是它的全部内容。

```
    0x00a4 mov    x1, #0x0
    0x00a8 movi   d0, #0000000000000000
    0x00ac movi   d1, #0000000000000000
    0x00b0 movi   d2, #0000000000000000
    0x00b4 movi   d3, #0000000000000000
    0x00b8 ret
```

`nil` 处理程序与其余代码完全不同。没有类查找或方法派发。它对 `nil` 所做的只是向调用者返回 `0`。

由于 `objc_msgSend` 不知道调用者期望哪种返回值，这个任务有点复杂。这个方法返回一个整数、两个整数、一个浮点值，还是什么都不返回？

幸运的是，所有用于返回值的寄存器都可以安全地覆盖，即使它们不用于此特定调用的返回值。整型返回值存储在 `x0` 和 `x1` 中，浮点返回值存储在向量寄存器 `v0` 到 `v3` 中。返回较小的 `struct` 时会使用多个寄存器。

这段代码清除了 `x1` 和 `v0` 到 `v3`。`d0` 到 `d3` 寄存器指的是相应 `v` 寄存器的下半部分，向它们写入会清除上半部分，因此四条 `movi` 指令的效果是清零这四个寄存器。完成后，它将控制权返回给调用者。

你可能会想为什么这段代码不清除 `x0`。答案很简单：`x0` 持有 `self`，在这种情况下是 `nil`，所以它已经是零了！通过不清除 `x0` 可以节省一条指令，因为它已经包含了我们想要的值。

那不适合存放在寄存器中的更大 `struct` 返回值呢？这需要调用者的一点配合。大结构体返回是通过让调用者为返回值分配足够的内存，然后将该内存的地址传入 `x8` 来实现的。函数随后写入该内存以返回值。`objc_msgSend` 无法清除这块内存，因为它不知道返回值有多大。为了解决这个问题，编译器会生成代码在调用 `objc_msgSend` 之前用零填充该内存。

这就是 `nil` 处理程序的结尾，也是整个 `objc_msgSend` 的结尾。
